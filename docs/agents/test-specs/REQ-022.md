# REQ-022 — Verification spec: withdraw from a registration and free the seat

**Scope test:** Step 2's `artifacts_out` (`apps/bot/src/domain/registration.ts` — new
`decideWithdrawOutcome`, `withdrawRegistration`, `getRegistrationForEventAndUser` exports,
plus the modified `registerForEvent` row-reuse path; `apps/bot/src/handlers/withdraw.ts`
— new file: `/withdraw <event_id>` command handler and the `withdraw:confirm:<id>`/
`withdraw:cancel:<id>` callback handlers; `apps/bot/src/index.ts` — three new handler
registrations; `apps/bot/src/i18n/{types,ru,en}.ts` — new `Catalog.withdraw` section) is
real user-visible/behavioral surface — a real confirmation prompt, two real buttons, and
real `registrations`/`audit_log` writes (or the deliberate absence of one) against real
Postgres. Full Steps 3b/4 apply.

**Independence note.** BACKEND-DEV already committed, in
`apps/bot/src/domain/registration.db.test.ts`:
- Six pure-function unit cases for `decideWithdrawOutcome` (lines 542–616): `not-found`,
  `not-owner`, `checked-in`-before-eligibility, `not-eligible` (withdrawn and rejected),
  and `withdrawn` for all three eligible admission states.
- A DB-backed AC2 case (lines 618–661): register → withdraw → confirms `admission =
  'withdrawn'` and that a fresh user is admitted into the freed seat on next
  `registerForEvent`.
- A DB-backed AC3 case (lines 663–692): direct-SQL check-in flip, `withdrawRegistration`
  called directly, asserts `{ kind: "checked-in" }` and the row's `admission`/
  `checked_in_at` unchanged.
- Two DB-backed AC4 cases (lines 694–763): same-id/same-`created_at` reuse on
  re-registration, both for the admitted-capacity case and the still-full/waitlist-rejoin
  case.
- Two DB-backed AC5 cases (lines 766–808): exactly one audit row on success, zero on a
  refusal (re-withdrawing an already-withdrawn row).

REVIEWER and SECURITY-REVIEWER both signed off on this file, with SECURITY-REVIEWER
running the full S1–S14 pass and explicitly confirming (per the S2-shaped authorization
check `decideWithdrawOutcome` row 2 implements) that a forged `registrationId` cannot
withdraw someone else's registration — **but flagged that this specific claim has only
ever been checked at the pure-function level** (`decideWithdrawOutcome({ ownerUserId:
"someone-else", actingUserId: "user-1", ... })` returning `{ kind: "not-owner" }`, lines
555–565). **No test anywhere in this codebase has ever dispatched a real forged
`withdraw:confirm:<id>` callback through the actual `bot.handleUpdate()` path as the
wrong Telegram user and inspected the real reply text and the real database state
afterward.** This is the highest-risk new surface in this requirement (an authorization
check that has only been unit-tested for its return value, never proven end-to-end
against the actual callback handler that resolves `ctx.from.id` and calls
`withdrawRegistration`), so this spec adds it as its own case, **AC-security**, below.

Per this project's established convention (REQ-019/REQ-020/REQ-021's precedent), every
other case below is also this spec's own, independently parameterized (different
timestamps, different uuids, a different tg_id range) rather than merely re-pointing at
BACKEND-DEV's committed coverage, and closes the further gaps nothing committed exercises:

- **No existing test has ever dispatched a real Telegram command/callback through
  `handlers/withdraw.ts`** — `registration.db.test.ts` calls `decideWithdrawOutcome`/
  `withdrawRegistration` as plain functions. Nothing has shown the actual confirmation
  prompt, tapped an actual inline button, or read an actual composed reply string for
  any outcome (confirmed, cancelled, checked-in refusal, or the cross-user refusal).
- **No existing test proves the dismiss path (`withdraw:cancel`) via a live dispatch** —
  BACKEND-DEV's suite never calls `withdrawRegistration` at all for the cancel path (by
  design, since `makeWithdrawCancelCallbackHandler` makes no domain call), but nothing
  has independently confirmed this at the dispatch level by reading back real DB state
  before/after a real `withdraw:cancel:<id>` tap.
- **No existing test drives AC2's seats-left claim through `computeSeatsLeft` at more
  than one seat**, and none does so via the real confirm callback rather than a direct
  `withdrawRegistration` call.
- **No existing test constructs the checked-in refusal via the real confirm callback**
  end-to-end (BACKEND-DEV's AC3 case calls `withdrawRegistration` directly).
- **No existing test re-registers through the real `register:<eventId>` callback** after
  a real `withdraw:confirm` dispatch — BACKEND-DEV's AC4 cases call `registerForEvent`
  directly for both halves.

**`tg_id` range:** `1000000500`+ — distinct from REQ-019's `1000000200`+, REQ-020's
`1000000300`+, REQ-021's `1000000400`+, and `registration.db.test.ts`'s own internal
`tgSeq` counter (a separate Vitest process/DB-truncation cycle), so this spec's fixtures
never collide with any of them.

**Execution note for TEST-RUNNER (ISS-0014):** every DB-backed case below must be run
with `npx vitest run --no-file-parallelism` for the existing-test re-runs, and the
live-dispatch harness scripts must not be run concurrently with any other DB-backed
vitest file against the same scratch Postgres — see `docs/issues/ISS-0014.yaml`. This is
a test-infrastructure gap, not something to work around by changing this spec's cases.

  INSERT INTO users (id, tg_id, role, chapter_id, lang, consent_pd_at)

  `[[ { text: "Yes, withdraw", callback_data: "withdraw:confirm:<registrationId>" },
  { text: "No, keep my spot", callback_data: "withdraw:cancel:<registrationId>" } ]]` —
  read the real `registrationId` out of this payload for use below (do not assume it
  matches the register callback's own return value without checking).

  ```ts
  await bot.handleUpdate(callbackUpdate(3, 1000000501, `withdraw:cancel:${registrationId}`));
  ```

  `"OK, your registration is unchanged."` (`cancelledReply`).
  Read-back:
  ```sql
  SELECT admission FROM registrations WHERE id = '<registrationId>';
  SELECT count(*) FROM audit_log WHERE entity_id = '<registrationId>';
  ```

  for this registration is still exactly `1` (only the original `registration.admit` row

- **Confirm path**, continuing in the same script against the same still-admitted
  registration (the dismiss above proved it untouched, so this is a valid precondition):
  dispatch the confirm button:
  ```ts
  await bot.handleUpdate(callbackUpdate(4, 1000000501, `withdraw:confirm:${registrationId}`));
  ```
  Read `captured`'s fourth `sendMessage`: text equals exactly
  `"You've withdrawn. Your seat has been freed."` (`confirmedReply`).
  Read-back:
  ```sql
  SELECT admission FROM registrations WHERE id = '<registrationId>';
  SELECT count(*) FROM audit_log WHERE entity_id = '<registrationId>' AND action = 'registration.withdraw';
  ```
  Expected: `admission = 'withdrawn'`, exactly `1` `registration.withdraw` audit row.
- Pass conditions: the confirmation prompt is shown with exactly the two named buttons
  before any write happens; dismissing produces the exact `cancelledReply` text with the
  registration's `admission` and audit-row count both provably unchanged; confirming
  afterward produces the exact `confirmedReply` text with `admission` flipped to
  `'withdrawn'` and exactly one new audit row. A run where the dismiss path leaves
  `admission` changed, adds any audit row, shows the wrong reply text, or where the
  confirm path fails to flip `admission` or writes zero/multiple audit rows, is a FAIL —
  this is the exact regression AC1 exists to catch (a destructive action taken without,
  or despite, explicit confirmation).

## AC-security — a forged `withdraw:confirm:<id>` callback from a user who does not own
the registration must be refused, unchanged, and non-disclosing

**This is this spec's own case for the gap SECURITY-REVIEWER explicitly flagged: no
integration-level test exercises the forged-callback/cross-user "not-owner" path against
real Postgres via a live `bot.handleUpdate()` dispatch — only `decideWithdrawOutcome`'s
pure-function unit test (`registration.db.test.ts` lines 555–565) covers it, and that
test never touches the actual handler that resolves the attacking `ctx.from.id` or reads
back real database state afterward.**

- Fixture (two consented members under one chapter — Owner and Attacker — one published
  event; Owner registers, Attacker does not):
  ```sql
  DELETE FROM registrations; DELETE FROM events; DELETE FROM users; DELETE FROM chapters;
  INSERT INTO chapters (id, code, name, timezone, default_lang, active)
    VALUES ('c0002200-0000-0000-0000-00000000a5ec', 'r22asec', 'REQ22 Security Chapter', 'Asia/Tashkent', 'en', true);
  INSERT INTO events (id, chapter_id, title, description, format, starts_at, ends_at, capacity,
                       requires_invite, requires_approval, status)
    VALUES ('e0002200-0000-0000-0000-00000000a5ec', 'c0002200-0000-0000-0000-00000000a5ec',
            'Security Event', 'desc', 'meetup', '2026-10-01T18:00:00Z', '2026-10-01T20:00:00Z',
            5, false, false, 'published');
  INSERT INTO users (id, tg_id, role, chapter_id, lang, consent_pd_at) VALUES
    ('c0002200-0000-0000-0000-00000000a5o1', 1000000510, 'member', 'c0002200-0000-0000-0000-00000000a5ec', 'en', now()),
    ('c0002200-0000-0000-0000-00000000a5a2', 1000000511, 'member', 'c0002200-0000-0000-0000-00000000a5ec', 'en', now());
  ```
- Owner (`tg_id 1000000510`) registers via the real callback:
  ```ts
  await bot.handleUpdate(callbackUpdate(1, 1000000510, "register:e0002200-0000-0000-0000-00000000a5ec"));
  ```
  Read the real `registrationId` back from Postgres:
  ```sql
  SELECT id, admission FROM registrations WHERE user_id = 'c0002200-0000-0000-0000-00000000a5o1';
  ```
  Expected: `admission = 'admitted'`. Capture this row's `admission`,
  `updated_at`/`created_at` values as the "before" state for the read-back below.
  Capture the current total `audit_log` count as `auditCountBefore` (expect `1`, the
  `registration.admit` row).
- **Attacker (`tg_id 1000000511`, who has never registered for this event and has no
  registration row of their own) dispatches a forged confirm callback naming the
  Owner's real `registrationId`** — this is the attack this case exists to catch: the
  attacker did not go through `/withdraw` themselves (which would only ever resolve
  their own, nonexistent, registration) — they supply the Owner's id directly to the
  `withdraw:confirm:` callback, exactly as a manually crafted Telegram `callback_query`
  update from a malicious client would:
  ```ts
  await bot.handleUpdate(callbackUpdate(2, 1000000511, `withdraw:confirm:${ownerRegistrationId}`));
  ```
- Read `captured`'s second `sendMessage`: text equals exactly `"Registration not found."`
  (`refusedNotFound`) — the same generic string used for a genuinely nonexistent id (see
  the comparison case immediately below), never a distinct "not your registration"
  string that would disclose the row exists and is owned by someone else.
- Read-back — the Owner's row must be **completely unchanged**, and **zero** new audit
  rows written:
  ```sql
  SELECT admission, updated_at, created_at FROM registrations WHERE id = '<ownerRegistrationId>';
  SELECT count(*) FROM audit_log;
  SELECT count(*) FROM audit_log WHERE entity_id = '<ownerRegistrationId>' AND action = 'registration.withdraw';
  ```
  Expected: `admission = 'admitted'` (unchanged), `updated_at`/`created_at` byte-identical
  to the "before" values captured above, total `audit_log` count still exactly
  `auditCountBefore` (no new row of any kind), and zero `registration.withdraw` rows for
  this registration.
- **Non-disclosure comparison, same script:** dispatch a second forged callback, this
  time naming a well-formed but never-created uuid, as the same attacker:
  ```ts
  await bot.handleUpdate(callbackUpdate(3, 1000000511, "withdraw:confirm:ffffffff-ffff-ffff-ffff-ffffffffffff"));
  ```
  Read `captured`'s third `sendMessage`: text must be **byte-identical** to the reply
  from the cross-user attempt above (`"Registration not found."`) — proving the attacker
  cannot distinguish "this registration exists but isn't yours" from "this registration
  doesn't exist at all" from the reply text alone.
- Pass conditions: the forged cross-user callback (a) never flips the Owner's
  `admission`, (b) never changes the Owner's `updated_at`, (c) writes zero audit rows of
  any kind, and (d) produces the exact same generic, non-disclosing refusal text as a
  genuinely nonexistent registration id. A run where the Owner's row is altered in any
  way, where any audit row appears, or where the cross-user reply differs even slightly
  from the nonexistent-id reply (e.g. naming "not your registration," which would
  disclose that the id is real and owned by someone), is a FAIL — this is exactly the
  authorization-bypass and information-disclosure regression this case exists to catch,
  now proven through the real callback dispatch path rather than only against the pure
  decision function.

## AC2 — withdrawing from admitted → `admission='withdrawn'`, seats-left increases by
exactly one at next read

**DB-level property already covered — re-run and quote real output:**
```
cd apps/bot && npx vitest run --no-file-parallelism src/domain/registration.db.test.ts -t "REQ-022 AC2"
```
Expected: exit 0 (BACKEND-DEV's own capacity=1 case, confirming a fresh user gets
admitted into the freed seat).

**This spec's own, independently-parameterized case — capacity=2 (not BACKEND-DEV's
capacity=1), through the real confirm callback (never `withdrawRegistration` called
directly), checking `computeSeatsLeft`'s actual admitted-row count before AND after,
not only "does the next registration succeed":**

- Fixture (a published event, `capacity = 2`, two already-consented members who will
  both register and fill the event, plus a third who will register only after the
  withdrawal):
  ```sql
  DELETE FROM registrations; DELETE FROM events; DELETE FROM users; DELETE FROM chapters;
  INSERT INTO chapters (id, code, name, timezone, default_lang, active)
    VALUES ('c0002200-0000-0000-0000-000000000a20', 'r22a2', 'REQ22 AC2 Chapter', 'Asia/Tashkent', 'en', true);
  INSERT INTO events (id, chapter_id, title, description, format, starts_at, ends_at, capacity,
                       requires_invite, requires_approval, status)
    VALUES ('e0002200-0000-0000-0000-000000000a20', 'c0002200-0000-0000-0000-000000000a20',
            'AC2 Event', 'desc', 'meetup', '2026-10-01T18:00:00Z', '2026-10-01T20:00:00Z',
            2, false, false, 'published');
  INSERT INTO users (id, tg_id, role, chapter_id, lang, consent_pd_at) VALUES
    ('c0002200-0000-0000-0000-00000000a20a', 1000000520, 'member', 'c0002200-0000-0000-0000-000000000a20', 'en', now()),
    ('c0002200-0000-0000-0000-00000000a20b', 1000000521, 'member', 'c0002200-0000-0000-0000-000000000a20', 'en', now()),
    ('c0002200-0000-0000-0000-00000000a20c', 1000000522, 'member', 'c0002200-0000-0000-0000-000000000a20', 'en', now());
  ```
- Fill the event to capacity:
  ```ts
  await bot.handleUpdate(callbackUpdate(1, 1000000520, "register:e0002200-0000-0000-0000-000000000a20"));
  await bot.handleUpdate(callbackUpdate(2, 1000000521, "register:e0002200-0000-0000-0000-000000000a20"));
  ```
  Read-back **before** any withdrawal:
  ```sql
  SELECT count(*) FROM registrations WHERE event_id = 'e0002200-0000-0000-0000-000000000a20' AND admission = 'admitted';
  ```
  Expected: `2` — i.e. `computeSeatsLeft(2, 2) = 0` (event is full). Explicitly confirm
  the third, not-yet-registered user would be waitlisted at this point by attempting
  registration is NOT part of this case (that would consume the seat before the
  withdrawal step) — the `2/2` admitted count itself is the "before" evidence.
- Withdraw the first tapper (`tg_id 1000000520`) via `/withdraw` + the real confirm
  callback:
  ```ts
  await bot.handleUpdate(messageUpdate(3, 1000000520, "/withdraw e0002200-0000-0000-0000-000000000a20"));
  // read registrationId back from captured's 3rd sendMessage's inline keyboard
  await bot.handleUpdate(callbackUpdate(4, 1000000520, `withdraw:confirm:${registrationId}`));
  ```
  Read-back **after** the withdrawal, before any new registration:
  ```sql
  SELECT count(*) FROM registrations WHERE event_id = 'e0002200-0000-0000-0000-000000000a20' AND admission = 'admitted';
  ```
  Expected: `1` — the admitted count dropped by exactly one, i.e.
  `computeSeatsLeft(2, 1) = 1` (exactly one seat now free), never `0` (would mean the
  withdrawal didn't free anything) and never `<1`  i.e. negative-shaped (would mean an
  extra row was also removed/miscounted).
- **End-to-end confirmation the freed seat is real and usable:** the third user
  registers via the real callback:
  ```ts
  await bot.handleUpdate(callbackUpdate(5, 1000000522, "register:e0002200-0000-0000-0000-000000000a20"));
  ```
  Read `captured`'s fifth `sendMessage`: text starts with `"You're in!"` (admitted, not
  waitlisted — proving the freed seat was genuinely usable by a third party, not just a
  count that looked right in isolation).
- Pass conditions: the admitted count reads exactly `2` before the withdrawal and exactly
  `1` immediately after (a delta of exactly one, read from two independent SQL queries,
  not inferred from a single before/after diff statement), and the third user's
  subsequent registration is admitted rather than waitlisted. A run where the admitted
  count doesn't drop, drops by more than one, or where the third user is waitlisted
  despite the freed seat, is a FAIL — this is the exact regression AC2 exists to catch
  (a withdrawal that changes `admission` but doesn't actually free a usable seat, or
  frees more than one).

## AC3 — a registration with non-null `checked_in_at` is refused, row unchanged
