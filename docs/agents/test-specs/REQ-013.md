# REQ-013 — Verification spec: Bot i18n scaffold with RU/EN catalogs and /lang

**Scope test:** Step 2's `artifacts_out` includes real behavioral surface — new files
under `apps/bot/src/i18n/`, `apps/bot/src/domain/`, `apps/bot/src/handlers/`, and
`apps/bot/src/index.ts`'s new command registrations. A live Telegram bot process replies
differently depending on `users.lang`/`chapters.default_lang`, and `/lang` has a real
persistence side effect. This is user-visible/behavioral surface → full Steps 3b/4 apply,
not a docs-only skip.

**Harness note (read before running any case):** AC2, AC3 and AC4 all require dispatching
a real command/callback through the bot's actual grammY routing and a real Postgres row,
per REQ-013's own design artefact (`docs/agents/design/REQ-013.md` §3.1, which explicitly
rejects verifying these three ACs via a pure `resolveLang()` unit-test substitute — AC2's
and AC4's literal wording is "verified against a live bot instance" / "sending /start").
This spec uses the exact grammY-dispatch method BACKEND-DEV and REVIEWER already built and
independently confirmed twice on this same run
(`handoffs/WF02-REQ-013/step-02c-backend-dev-rework.json`,
`handoffs/WF02-REQ-013/step-02d-reviewer-regate.json`): a real `grammy.Bot` instance
constructed with a dummy token + manually-supplied `botInfo` (skips the network `getMe()`
call), the same handlers `apps/bot/src/index.ts` registers, `bot.api.config.use()`
intercepting only outbound API calls (no real Telegram network traffic), and
`bot.handleUpdate()` dispatching synthetic `Update` objects through the bot's real
command/callback-query matcher and real `Context` construction. §4 of this document
records the explicit decision on whether to commit this as reusable infrastructure now —
short answer: not committed here; each case below gives the exact scratch code to write
and delete, matching the pattern already used twice.

## Shared setup (run once, before AC2/AC3/AC4 — NOT needed for AC1 or AC5)

1. `cd apps/bot && docker compose up -d` — starts the throwaway dev Postgres on host port
   `55432` (`apps/bot/docker-compose.yml`, user/password/db all `bot`).
2. Wait for readiness: `docker compose exec postgres pg_isready -U bot` until it reports
   `accepting connections` (poll every 2s, do not sleep-guess a fixed duration).
3. `export DATABASE_URL=postgres://bot:bot@localhost:55432/bot` (PowerShell:
   `$env:DATABASE_URL = "postgres://bot:bot@localhost:55432/bot"`).
4. From `apps/bot`: `npx drizzle-kit migrate` — applies REQ-010/REQ-011's migrations to
   the scratch database. Expected: exits 0, no error output.
5. Seed fixture rows via `psql "$DATABASE_URL" -c "<statement>"` (or a single `psql -f
   seed.sql`) — exact statements are given per-case below, since each AC needs different
   rows. Use `tg_id` values in the `600000000` range (arbitrary, never colliding with a
   real Telegram id) so cases can be run independently without cross-contaminating rows.
6. Write the harness script below to a scratch file, e.g. `apps/bot/scratch-verify-req013
   .ts` (NOT committed — delete it at the end of the run, per File Placement Rules'
   "scratch" row).

**Harness script (`apps/bot/scratch-verify-req013.ts`), exact content:**

```ts
import { Bot } from "grammy";
import { makeStartHandler } from "./src/handlers/start.js";
import { makeLangCommandHandler, makeLangCallbackHandler } from "./src/handlers/lang.js";
import { createDbClient } from "./src/db/client.js";

const { db } = createDbClient(process.env.DATABASE_URL!);

const bot = new Bot("000000:DUMMY_TOKEN_NOT_REAL", {
  botInfo: {
    id: 1,
    is_bot: true,
    first_name: "Test",
    username: "test_bot",
    can_join_groups: true,
    can_read_all_group_messages: false,
    supports_inline_queries: false,
  },
});

const captured: Array<{ method: string; payload: unknown }> = [];
bot.api.config.use(async (_prev, method, payload) => {
  captured.push({ method, payload });
  return { ok: true, result: true } as never;
});

bot.command("start", makeStartHandler(db));
bot.command("lang", makeLangCommandHandler(db));
bot.callbackQuery(/^lang:(ru|en)$/, makeLangCallbackHandler(db));

function messageUpdate(updateId: number, tgId: number, text: string) {
  return {
    update_id: updateId,
    message: {
      message_id: updateId,
      date: Math.floor(Date.now() / 1000),
      chat: { id: tgId, type: "private" as const },
      from: { id: tgId, is_bot: false, first_name: "Test" },
      text,
      entities: [{ type: "bot_command" as const, offset: 0, length: text.split(" ")[0].length }],
    },
  };
}

function callbackUpdate(updateId: number, tgId: number, data: string, callbackQueryId: string) {
  return {
    update_id: updateId,
    callback_query: {
      id: callbackQueryId,
      from: { id: tgId, is_bot: false, first_name: "Test" },
      message: {
        message_id: updateId - 1,
        date: Math.floor(Date.now() / 1000),
        chat: { id: tgId, type: "private" as const },
      },
      data,
      chat_instance: "1",
    },
  };
}

async function main() {
  await bot.init();
  // --- dispatch calls inserted per-case below, in order ---
  console.log(JSON.stringify(captured, null, 2));
  process.exit(0);
}

main();
```

Each case below states the exact `bot.handleUpdate(...)` calls to insert at the
`--- dispatch calls ---` line, and the exact expected entries in the printed `captured`
array. Run with `npx tsx scratch-verify-req013.ts` from `apps/bot` (with `DATABASE_URL`
set per step 3 above).

**Teardown (after all of AC2/AC3/AC4 are done):** delete `apps/bot/scratch-verify-req013
.ts`, `docker compose down -v` (from `apps/bot`), confirm `git status --porcelain` shows
nothing under `apps/bot/scratch-verify-req013.ts` or any other stray file.

## AC2 — `User.lang='en'` gets English /start+/lang, `User.lang='ru'` gets Russian

- Route: live bot dispatch via the harness (see Shared setup).
- Fixture rows (`psql "$DATABASE_URL" -c "..."`, run once):
  ```sql
  INSERT INTO users (tg_id, lang) VALUES (600000001, 'en');
  INSERT INTO users (tg_id, lang) VALUES (600000002, 'ru');
  ```
- Harness dispatch calls (insert at the `--- dispatch calls ---` line, in order):
  ```ts
  await bot.handleUpdate(messageUpdate(1, 600000001, "/start"));
  await bot.handleUpdate(messageUpdate(2, 600000002, "/start"));
  await bot.handleUpdate(messageUpdate(3, 600000001, "/lang"));
  await bot.handleUpdate(messageUpdate(4, 600000002, "/lang"));
  ```
- Expected `captured` entries, in order, exact payloads:
  1. `{"method":"sendMessage","payload":{"chat_id":600000001,"text":"This is the AI Qadam Events bot."}}`
  2. `{"method":"sendMessage","payload":{"chat_id":600000002,"text":"Это бот AI Qadam Events."}}`
  3. `{"method":"sendMessage","payload":{"chat_id":600000001,"text":"Choose your interface language.","reply_markup":{"inline_keyboard":[[{"text":"Русский","callback_data":"lang:ru"},{"text":"English","callback_data":"lang:en"}]]}}}`
  4. `{"method":"sendMessage","payload":{"chat_id":600000002,"text":"Выберите язык интерфейса.","reply_markup":{"inline_keyboard":[[{"text":"Русский","callback_data":"lang:ru"},{"text":"English","callback_data":"lang:en"}]]}}}`
- Pass condition: entries 1 and 3 (`tg_id` 600000001, `lang='en'`) are entirely in English
  (`"This is the AI Qadam Events bot."`, `"Choose your interface language."`); entries 2
  and 4 (`tg_id` 600000002, `lang='ru'`) are entirely in Russian. Any English text for the
  `ru` user or Russian text for the `en` user is a FAIL.

## AC3 — `/lang` offers exactly ru/en; selection persists; confirmation in new language

- Route: live bot dispatch via the harness, reusing the `tg_id 600000001` (`lang='en'`)
  row seeded for AC2 — run AC2 first, or seed it fresh with the same `INSERT` if run in
  isolation.
- Harness dispatch calls:
  ```ts
  await bot.handleUpdate(messageUpdate(5, 600000001, "/lang"));
  await bot.handleUpdate(callbackUpdate(6, 600000001, "lang:ru", "cb-1"));
  ```
- **Exactly-two-options check:** inspect the `reply_markup.inline_keyboard` on the
  `sendMessage` entry produced by the `/lang` command dispatch (see AC2 entry 3's shape,
  or re-capture here). Expected: `inline_keyboard` is an array containing exactly one row,
  that row is an array of exactly 2 button objects, with `callback_data` values exactly
  `"lang:ru"` and `"lang:en"` (no third button, no third row). A keyboard with any other
  button count or any `callback_data` other than those two exact strings is a FAIL.
- **Callback dispatch → expected captured entries, in order:**
  1. `{"method":"answerCallbackQuery","payload":{"callback_query_id":"cb-1"}}`
  2. `{"method":"sendMessage","payload":{"chat_id":600000001,"text":"Язык интерфейса: русский."}}`
- Pass condition on confirmation text: the confirmation (`"Язык интерфейса: русский."`) is
  the **Russian** catalog's `lang.confirmed` string — the newly-selected language — not
  the pre-selection English (`"Interface language: English."`). Receiving the English
  string here is a FAIL (it would mean the confirmation was read from the pre-tap
  language, contradicting the design's §2.2 closing note).
- **DB read-back (persistence):**
  ```sql
  SELECT lang FROM users WHERE tg_id = 600000001;
  ```
  Expected: exactly `ru` (changed from the seeded `en`). Run this query AFTER the
  callback dispatch above, not before — a read taken before the tap is not evidence of
  persistence.

- Fixture rows (`psql "$DATABASE_URL" -c "..."`, run once — capture the generated chapter


- Harness dispatch call:

- Expected `captured` entry:
  `{"method":"sendMessage","payload":{"chat_id":600000003,"text":"This is the AI Qadam Events bot."}}`

  default `'en'` matches). A Russian reply here is a FAIL (it would mean the fallback

  `chapterDefaultLang` was not read/joined correctly).

## 4. Decision: not committing a reusable grammY-dispatch harness in this test design

**The recurring-cost threshold is real, but committing the harness now is still the
wrong call for this step — reasoning below, not a default.**

**Evidence the cost is real:** the exact `Bot` + manually-supplied `botInfo` +
`bot.api.config.use()` interception + `bot.handleUpdate(syntheticUpdate)` technique has
now been hand-built three times on this single run alone —
`handoffs/WF02-REQ-013/step-02-backend-dev.json`'s original attempt (a Context-shaped
stub REVIEWER rejected), `step-02c-backend-dev-rework.json`'s rebuild after REVIEWER
demonstrated the real-dispatch method, and `step-02d-reviewer-regate.json`'s independent
third build for re-gating — each as an uncommitted scratch script deleted afterward. This
is a materially higher-volume signal than the precedent in
`docs/agents/test-specs/REQ-010.md` §"Open question," which deferred a raw
`postgres:16-alpine` container script after only two hand-builds and explicitly flagged
"once `apps/bot` accumulates enough schema-testing volume." Every later bot requirement
that dispatches a live command (REQ-014 onward, per PRD 14's build order) will need this
same grammY-dispatch shape again — at minimum once for BACKEND-DEV's build, once for
REVIEWER's gate, and again here at TEST-DESIGNER/TEST-RUNNER — so the threshold for "this
harness specifically is worth a standing artefact" is crossed.

**Why it is still not committed as part of THIS test design, though:**

1. **It is a design/architecture decision, not a test-spec decision.** Where the harness
   would live (`apps/bot/src/test-support/`? a root-level shared helper, given future
   requirements will dispatch through the same `apps/bot/src/index.ts` registrations?),
   whether it becomes a real committed Vitest integration-test suite or stays a
   documented-but-uncommitted procedure, and — the actually hard part — whether CI's
   `npm test` step should be made to provision a throwaway Postgres for it, are all
   choices with more than one defensible answer that no single TEST-DESIGNER run can
   infer from `docs/agents/requirements.yaml` or the `decisions/` directory. Per
   `core-directives.md`'s "Zero Manual Work" item 1, this is exactly the case for filing
   a `docs/agents/decisions/000x-*.md` draft naming the options — not silently picking
   one inside a Step 3 test-spec artefact.
2. **`decisions/0006-test-framework-vitest.md` already settles what Vitest is for here**,
   and its own stated boundary ("fake timers do not reach Postgres") is about
   *in-process, clock-dependent* logic being unit-testable — it says nothing about
   promoting a Postgres-backed, live-dispatch integration harness into the same `npm
   test` gate that CI already runs unconditionally on every build. Wiring a
   Postgres-requiring test into that gate without CI itself provisioning Postgres would
   make `npm test` fail in CI the moment the file is committed — a decision record is
   never quietly extended past what it actually states (Instruction Precedence, "a
   decisions/ record is never overridden by anything above it" — the inverse also
   applies: don't stretch it further than it says either).
3. **REQ-013's own design artefact already settled the verification *mode* for AC2/AC4**
   (`docs/agents/design/REQ-013.md` §3.1): these criteria are worded as live-bot,
   live-command checks pasted into a verification report, not as a standing automated
   suite. Building committed test infrastructure here would be answering a question
   (should this become a permanent automated integration test?) that CODE-DESIGNER,
   working from the same acceptance-criteria text, did not decide either — it is not
   TEST-DESIGNER's call to make unilaterally two steps later in the same pipeline.
4. **TEST-DESIGNER's own mandate is the spec, not new shared code.** Writing automated
   test code is in-scope once a framework exists (Vitest does), but that licenses writing
   *this run's own* verification as runnable code — it does not license standing up new,
   reusable cross-requirement infrastructure as a side effect of one Step 3 artefact,
   especially infrastructure with a real external-service dependency (Postgres) that
   changes what "green CI" means project-wide.

**Recommendation, filed as an open recommendation rather than acted on:** ORCH should
route a REQ-ANALYST/decision-draft task titled something like "reusable grammY-dispatch
test harness for apps/bot" once REQ-013 closes — scoping exactly this technique (real
`Bot` + `botInfo` + `bot.api.config.use()` + `bot.handleUpdate()`), separate from and in
addition to REQ-010's already-flagged raw-Postgres-container fixture question, since the
two are independent pieces of recurring cost (one is "spin up a database," the other is
"dispatch a synthetic Telegram update through real routing") that happen to currently
co-occur in the same test runs but are not the same reusable unit.
