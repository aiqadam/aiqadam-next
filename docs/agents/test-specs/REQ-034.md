## AC1 — registering creates exactly one `registrations` row with `admission='requested'`

**Case 1 (row shape, already existing, unmodified):**
`apps/bot/src/domain/registration.db.test.ts` → `describe("registerForEvent — AC6: ...")`
→ `it("creates a 'requested' registration, never admits, when requires_approval is
true...")`. Asserts `outcome.kind === "requested"` and `outcome.qrToken === undefined`.

**Case 2 (NEW — the persisted row itself, exact-one-row):**
Same file, same `describe` block → new
`it("REQ-034 AC1/AC5: the persisted row has admission='requested', qr_token NULL, and is
the only row for (event, user)")`. Seeds a published, `requires_approval=true`,
`capacity=5` event; one fresh user calls `registerForEvent`; reads the `registrations`
table back directly filtered by `(eventId, userId)`.
**Expected:** exactly one row (`rows).toHaveLength(1)`), `rows[0].admission === "requested"`,
`rows[0].qrToken === null`.
**What this would catch:** any regression that writes a second row instead of the
unique-constrained one, or writes any admission value other than the literal string
`"requested"`.

## AC2 — the confirmation states decision-will-follow + `registration_closes_at` in chapter-local time; the NULL case exercises the stated fallback

**Case 1 (NEW — non-null `registration_closes_at`):**
`apps/bot/src/handlers/registration.test.ts` → new
`describe("makeRegisterCallbackHandler -- REQ-034 AC2: ...")` → first `it`. Seeds a
chapter (`timezone: "Asia/Tashkent"`, `seedChapter`'s fixed value), a
`requires_approval=true` event with `registrationClosesAt = new
Date("2026-09-25T15:00:00Z")`, and dispatches a real `register:<eventId>`
`callback_query` through `bot.handleUpdate` (grammY, not a mocked handler call).
**Expected reply text** (independently computed via the same
`formatDateTimeInTimezone` production helper, imported directly into the test — the same
convention `scheduler/reminderJobs.db.test.ts` already establishes):
- contains `catalog.registration.requestedPrefix`, the event title
  (`"Approval Gated Event"`), `` `${startsAtText}–${endsAtText}` ``,
  `` `${catalog.registration.requestedDecisionByPrefix} ${closesAtText}` `` (the exact
  chapter-local rendering of `registrationClosesAt`), and
  `catalog.registration.requestedWhatNext`.
- does **NOT** contain `catalog.registration.requestedDecisionByFallback` (the two
  branches are mutually exclusive).
- DB cross-check: exactly one row, `admission="requested"`, `qrToken IS NULL`.
**What this would catch:** a wrong/omitted timezone conversion, the wrong catalog key
used, or both branches' text appearing together.

**Case 2 (NEW — `registration_closes_at IS NULL`, the fallback branch):**
Same `describe` block, second `it`. Same event, `registrationClosesAt: null`.
**Expected:** reply contains `requestedPrefix`, the `startsAtText–endsAtText` line, and
`catalog.registration.requestedDecisionByFallback`; does **NOT** contain
`requestedDecisionByPrefix`; and does not match `/null|undefined|Invalid Date/i` anywhere
in the composed text (the "not empty or malformed" half of the AC).
**What this would catch:** a null `registrationClosesAt` leaking through
`formatDateTimeInTimezone` as `"Invalid Date"` or a literal `"null"`, or the fallback
string silently being dropped when the real branch's precondition isn't met.

## AC3 — a second request shows the CURRENT pending status, exactly one row remains

**Case 1 (NEW — DB/domain level):**
`apps/bot/src/domain/registration.db.test.ts` → new
`it("REQ-034 AC3: a second request against the same approval-gated event reports the
existing 'requested' status, still exactly one row")` in the AC6 `describe` block. First
call → `{ kind: "requested" }`; second call, same `(eventId, userId)` →
`toEqual({ kind: "already-registered", admission: "requested" })`; DB read confirms
exactly one row, `admission="requested"`.

**Case 2 (NEW — full handler/reply level):**
`apps/bot/src/handlers/registration.test.ts` → new
`describe("makeRegisterCallbackHandler -- REQ-034 AC3: ...")`. The SAME `tgId` taps
`register:<eventId>` twice via two separate `bot.handleUpdate` calls. First reply
contains `requestedPrefix`; second reply contains `alreadyRegisteredPrefix` AND
`statusRequested` (the actual rendered pending-status label a person would read, not just
the outcome kind). DB read after both taps: exactly one row for that event,
`admission="requested"`.
**What this would catch:** a second row being inserted instead of refused, or the
second-tap reply showing a generic/blank error instead of the person's actual current
status.

## AC4 — a request succeeds even when the event is already at full capacity

This is the case the design (`docs/agents/design/REQ-034.md` §0.2) traces as structural
— covered at **two layers**, both new:

**Layer 1 (NEW — pure decision boundary, `apps/bot/src/domain/registration.test.ts`):**
Two new `it`s in the existing `describe("decideRegistrationOutcome — §2.2's
first-match-wins table")`, immediately after the existing row-6 test:
- `"row 6 (REQ-034 AC4): requires_approval yields 'requested' even at exactly zero seats
  left"` — `seatsLeft: 0` → `{ kind: "requested" }` (not `waitlisted`).
- `"row 6 (REQ-034 AC4): requires_approval yields 'requested' even when seatsLeft is
  negative (over capacity)"` — `seatsLeft: -3` → `{ kind: "requested" }`.
**What this would catch:** exactly the regression the requirement calls out —
`decideRegistrationOutcome`'s `requiresApproval` row being accidentally reordered after
the `seatsLeft > 0` check, or a new `seatsLeft`-based guard being added inside that
branch. Both would flip these two cases to `waitlisted`.

**Layer 2 (NEW — real DB fixture actually AT capacity, `apps/bot/src/domain/registration.db.test.ts`):**
New `it("REQ-034 AC4: an approval-gated event already at full capacity still creates a
'requested' row, not 'waitlisted' or a refusal")`, same `describe` block as AC1/AC3
above. Seeds a `capacity: 1, requiresApproval: true` event; **directly inserts** one
`admission: "admitted"` filler row (this is the only way to reach "admitted count ==
capacity" for a `requires_approval=true` event, since `registerForEvent` itself can never
produce `"admitted"` on this path — stated explicitly in the test's own comment); asserts
the fixture sanity (`admittedRows` has length 1, i.e. the event genuinely is at its
capacity of 1) **before** the real assertion; then a fresh user calls `registerForEvent`.
**Expected:** `outcome.kind === "requested"` (not `"waitlisted"`, not a refusal kind),
`outcome.qrToken === undefined`, and the DB row for `(eventId, requestingUserId)` reads
`admission="requested"`.
**What this would catch:** the same regression as Layer 1, but proven against the real
transactional write path (`registerForEvent`'s actual `seatsLeft` computation and
`admittedCount` query) rather than only the pure function in isolation — a run against an
event with seats remaining would not exercise this at all, matching the AC's own wording.

## AC5 — `qr_token IS NULL` on the created row; `/my` shows the pending state with NO QR image

**Case 1 (row-level `qr_token IS NULL`):** covered by AC1's Case 2 above (same test,
`rows[0].qrToken === null`) — not duplicated here.

**Case 2 (NEW — `/my`'s actual rendering, `apps/bot/src/handlers/my.test.ts`):** the
existing `describe("makeMyCommandHandler -- REQ-024 AC3/AC4/AC5: QR gating and the
shared renderer")` → its one `it` (real grammY dispatch of `/my` through
`bot.handleUpdate`) is extended in place with a fifth registration row,
`admission: "requested"`, against a fifth event for the same user. The test now asserts:
- 6 total sends (header + 5 rows), 1 photo send, 4 text sends (was 5/1/3 before this run).
- one of the 4 text sends' `payload.text` contains
  `catalog.registration.statusRequested` (the actual rendered pending-state label), and
  that same send's `payload.photo` is `undefined`.
- the pre-existing loop-assertion (`for (const send of textSends) { expect(...photo...).toBeUndefined(); }`)
  now covers the `requested` row too, since it iterates the whole (now 4-item) `textSends`
  array.
**What this would catch:** `/my`'s QR gate (`row.admission === "admitted" && row.qrToken
!== null`) ever being loosened to also fire for `"requested"`, which would attach a photo
to a registration nobody has been admitted to yet — exactly the single-purpose-token
violation security-invariants.md S4 names.

## AC6 — creating a request writes exactly one `audit_log` row naming actor/action/entity/entity_id

**Case (NEW, `apps/bot/src/domain/registration.db.test.ts`):** new
`describe("registerForEvent — REQ-034 AC6: exactly one audit_log row for a 'requested'
outcome")` → one `it`. Counts `audit_log` rows before and after one `registerForEvent`
call against a `requires_approval=true` event.
**Expected:** `afterCount === beforeCount + 1`; the row filtered by
`entityId = outcome.registrationId` has length 1 (not zero, not two); its `action ===
"registration.request"`, `entity === "registration"`, `actorUserId === userId` (the
requesting user's own id — the same actor-scoping REQ-034's own security review
independently re-derived in `handoffs/WF02-REQ-034/step-02c-security-reviewer.json`).
**What this would catch:** a missing audit write (zero rows), a duplicate write (two
rows, e.g. from a double-transaction bug), or the wrong action string/actor being
recorded.

## AC7 — an event with `requires_approval=false` is unaffected (still admits/waitlists per REQ-020/021)

No new test needed here — busywork would be adding a second copy of a case that already
exists, unmodified, and already re-passed in this exact run
(`handoffs/WF02-REQ-034/step-02b-reviewer.json`'s independently re-run
`668 tests passed`). Pointing `TEST-RUNNER` at the exact pre-existing cases that already
constitute this AC's proof:

- **Admitted + waitlisted pair, same event, DB level:**
  `apps/bot/src/domain/registration.db.test.ts` →
  `describe("registerForEvent — qr_token issuance")` →
  `it("issues a qr_token only for an admitted outcome, none for waitlisted")`. Capacity 1,
  `requiresApproval` defaults to `false`; user A → `admitted` with a real qr_token, user B
  → `waitlisted` with `qrToken === undefined` and the DB row's `qr_token IS NULL`. This is
  the exact admitted/waitlisted pairing AC7 asks for, and it is structurally guaranteed to
  still exercise rows 7/8 of the first-match-wins table unchanged by this diff (§1 of the
  design; row 6, the only changed row, is unreached whenever `requiresApproval` is
  `false`).
- **Pure decision layer, both outcomes, unchanged:**
  `apps/bot/src/domain/registration.test.ts` →
  `describe("decideRegistrationOutcome — §2.2's first-match-wins table")` →
  `it("row 7: seatsLeft > 0 -> admitted")` and `it("row 8: seatsLeft <= 0 -> waitlisted")`
  — both call `baseInput()`, whose default is `requiresApproval: false`, and neither was
  touched by this run's diff.

`TEST-RUNNER` must actually re-run these (not just cite the prior report) as part of the
full `npm test` invocation Step 4 already requires — a fresh, independent execution is
what makes this AC's "unaffected" claim current evidence rather than a stale report.
