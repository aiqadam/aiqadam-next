# ISS-0020 — regression test spec (WF-03 Step 4)

**Issue:** ISS-0020 (`docs/issues/ISS-0020.yaml`) — S10 ("blocked users are skipped in
both [transactional and marketing] cases", `docs/agents/instructions/security-invariants.md`)
was violated by `apps/bot/src/handlers/staff.ts`'s two notification call sites
(`makeStaffAddHandler`, `makeStaffRemoveHandler`).

**Design:** `docs/agents/design/ISS-0020-fix.md` (reworked revision — the first
implementation was FAILed by SECURITY-REVIEWER for `ISS-0020-SEC-1`, a timing
side-channel; the rework makes both branches perform one Bot API network round-trip,
differing only in which method is called: `ctx.api.getMe()` for a blocked target vs.
`ctx.api.sendMessage(...)` for a non-blocked one).

**Test code:** `apps/bot/src/handlers/staff.test.ts` (new file — no prior test file
existed for `staff.ts`). Vitest + real grammY dispatch (`bot.handleUpdate()`), same
infrastructure as `apps/bot/src/handlers/withdraw.test.ts` and
`apps/bot/src/handlers/event.dispatch.test.ts`: a real, migrated scratch Postgres
(`apps/bot/docker-compose.yml`, `TEST_DATABASE_URL`, default
`postgres://bot:bot@localhost:55432/bot`), network replaced by a `bot.api.config.use`
capturing transformer (no `sendMessage`/`getMe` ever leaves the process). Must be run
with `--no-file-parallelism` per ISS-0014 (this file truncates `users`/`events`/
`event_staff`/etc. tables shared with every other DB-backed suite).

## Verification cases

### Case 1 — Regression: blocked target added as staff receives no notification (AC: "A blocked target assigned as staff receives no Telegram send")

- **File / test:** `apps/bot/src/handlers/staff.test.ts` →
  `describe("ISS-0020 regression: makeStaffAddHandler skips notification for a blocked
  target")` → `it("blocked target: never sent a Telegram message, but IS assigned as
  staff and the organizer is told delivery failed")`.
- **Setup:** seed a chapter, an organizer (`role: "organizer"`, `chapterId` set to match,
  per `domain/eventAuthorization.ts`'s `checkOrganizerForChapter`), a published event, and
  a target user with `users.blocked = true` set directly via `db.update(schema.users)`.
- **Route (bot command):** `bot.handleUpdate()` dispatching
  `/staff_add <eventId> blocked-target-add` from the organizer's own `tgId`.
- **Mechanism:** `bot.api.config.use` capturing transformer — every outbound Bot API
  call (`sendMessage`, `getMe`, etc.) is captured as `{ method, payload }`, never reaches
  a real network.
- **Expected (exact):**
  1. `captured.filter(c => c.method === "sendMessage").map(c => c.payload.chat_id)` does
     **not** contain the blocked target's `tgId` (numeric, matching grammY's actual
     payload shape — confirmed by direct inspection, not assumed).
  2. `captured.map(c => c.method)` **does** contain `"getMe"` — the structural
     timing-cover assertion (see "Timing-cover decision" below).
  3. The organizer's own reply (`sendMessage` with `chat_id === organizer.tgId`)
     contains `getCatalog("ru").staff.notificationFailedNote`.
  4. `event_staff` has a row for `(eventId, target.userId)` — the assignment itself
     still committed despite the notification being withheld.
- **Fail-then-pass:** proven above — this exact case FAILED at `09377bd` (assertion 1
  above found the blocked user's `tgId` among `sendMessage` recipients) and PASSES at
  `850726d`.

### Case 2 — Regression: blocked target removed from staff receives no notification (AC: "A blocked target removed from staff receives no Telegram send")

- **Test:** same file →
  `describe("ISS-0020 regression: makeStaffRemoveHandler skips notification for a
  blocked target")` → its one `it(...)`.
- **Setup:** as Case 1, plus the target is pre-inserted into `event_staff` (so the
  "not assigned" pre-check does not short-circuit the handler).
- **Route:** `/staff_remove <eventId> blocked-target-remove` from the organizer.
- **Expected (exact):** identical shape to Case 1's assertions 1-3, plus: the
  `event_staff` row for `(eventId, target.userId)` is now **absent** (the removal itself
  still committed).
- **Fail-then-pass:** proven above — FAILED at `09377bd`, PASSES at `850726d`.

### Case 3 — Non-regression: non-blocked target added as staff still receives the real notification (both handlers, add case)

- **Test:** `describe("ISS-0020 non-regression: makeStaffAddHandler still notifies a
  non-blocked target")`.
- **Setup:** as Case 1 but `blocked: false` on the target.
- **Route:** `/staff_add <eventId> clear-target-add`.
- **Expected (exact):**
  1. A `sendMessage` call exists with `chat_id === target.tgId` whose `text` contains
     `getCatalog("ru").staff.assignmentNotificationBody.replace("{event}", <event
     title>)` (the real notification, unchanged from pre-fix behavior).
  2. The organizer's own reply does **not** contain `notificationFailedNote`.
  3. The `event_staff` row exists for `(eventId, target.userId)`.
- **Why this case matters even though it "already worked" pre-fix:** it locks down
  that the fix's added branching (`if (targetUser.blocked) { getMe() } else {
  sendMessage() }`) did not accidentally invert the condition, misroute the non-blocked
  path through `getMe()`, or otherwise regress the happy path while fixing the blocked
  one. Confirmed to pass at both `09377bd` and `850726d` (see fail-then-pass proof
  above) — a stable positive control, not a case expected to discriminate old-vs-new
  code.

### Case 4 — Non-regression: non-blocked target removed from staff still receives the real notification (remove case)

- **Test:** `describe("ISS-0020 non-regression: makeStaffRemoveHandler still notifies a
  non-blocked target")`.
- **Setup/route/expected:** mirrors Case 3 exactly, using `/staff_remove` and
  `removalNotificationBody`, plus asserting the `event_staff` row is now absent.
- Confirmed to pass at both `09377bd` and `850726d`, same reasoning as Case 3.

## Timing-cover (SEC-1) verification decision

The design's whole point in its reworked form is that both branches perform **the same
shape of work** — one DB read (`resolveLangForTg`) plus exactly one Telegram Bot API
network round-trip — so an organizer cannot distinguish "target is blocked" from "target
threw some other send failure" by the wall-clock latency of their own reply.

**Decision: assert the STRUCTURAL presence of the equalizing call (`ctx.api.getMe()`
was actually invoked on the blocked path), not a wall-clock timing measurement.**

Reasoning:
- A literal timing assertion (`expect(elapsedMs).toBeLessThan(N)` or a two-sample
  comparison) in a Vitest suite is measuring in-process function latency under a fake,
  synchronous-resolving `bot.api.config.use` transformer that returns instantly for
  every method — `sendMessage` and `getMe` both resolve on the same "immediately
  resolved Promise" tick in this test harness. There is no real network round-trip in
  this test environment at all, so any wall-clock delta measured here would be pure
  test-harness noise (GC pauses, event-loop scheduling jitter, CI runner contention) —
  exactly the flakiness class `core-directives.md`'s "no substance" and
  `qa_testing_guide.md`'s discipline both would flag as a case with nothing real to
  fail against. It could not actually detect a regression to the pre-rework FAILed
  shape (immediate return, zero awaits) reliably, because the *simulated* zero-awaits
  case and the *simulated* one-await case both complete in an equally negligible
  number of milliseconds inside this fake transformer.
- What **is** real and mechanically checkable in this harness: whether the blocked
  code path actually calls a second Bot API method at all before setting
  `notificationFailed`. The FAILed pre-rework shape (guard clause returning before
  entering the `try` block) would show up here as `captured.map(c => c.method)`
  **not** containing `"getMe"` for the blocked case — a clean, deterministic,
  non-flaky signal that directly encodes "did the code perform the equalizing round-trip
  or did it skip straight to the reply." This is exactly Case 1/2's assertion 2 above.
- This also has real discriminating power against the *specific* prior wrong
  implementation: if a future edit reintroduced the FAILed guard-clause shape (`if
  (targetUser.blocked) { notificationFailed = true; } else { try { ... } }` — no `try`
  entered, no `getMe()` call, on the blocked path), Case 1/2's `getMe`-presence
  assertion would fail immediately, independent of any timing measurement. That is a
  stated, falsifiable claim about what wrong code this catches — not a vague "seems
  related" case.
- A wall-clock assertion remains out of scope for automated coverage entirely (not
  deferred to TEST-RUNNER either) — SECURITY-REVIEWER's re-gate of the rework
  (`handoffs/ISS-0020/step-03c-security-reviewer.json`, PASS) already re-derived the
  real-network timing argument by reading the code's control flow, which is the
  correct level for that property; a flaky in-process timer in CI would not add
  evidence beyond what the structural assertion above already provides.

## What a wrong implementation would look like and why each case would catch it

- **If the blocked check were inverted** (skip for non-blocked, send for blocked):
  Case 1/2 would fail at assertion 1 (blocked target's `tgId` would appear in
  `sendMessage` chat_ids) and Case 3/4 would fail at assertion 1 (non-blocked target
  would receive no `sendMessage`).
- **If the blocked branch called `sendMessage` to the target anyway** (e.g. the
  original ISS-0020 gap, unfixed): Case 1/2 assertion 1 fails — proven directly by the
  pre-fix run above.
- **If the blocked branch's guard clause skipped the `try` block entirely** (the FAILed
  SEC-1 shape): Case 1/2 assertion 2 fails (no `getMe` call captured).
- **If the mutation were rolled back for a blocked target** (over-correcting S10 into
  refusing the staff action itself): Case 1/2 assertion 4 fails (`event_staff` row
  missing/present when it should be the opposite).
- **If `notificationFailedNote` were dropped from the blocked-path reply** (silently
  going fully silent instead of the design's chosen "tell the organizer" behavior):
  Case 1/2 assertion 3 fails.

## How to run

```
TEST_DATABASE_URL="postgres://bot:bot@localhost:55432/bot" npx vitest run apps/bot/src/handlers/staff.test.ts --no-file-parallelism
```

Requires the scratch Postgres from `apps/bot/docker-compose.yml` running and migrated
(`docker compose -f apps/bot/docker-compose.yml up -d`, then
`npm run migrate -w apps/bot` if not already applied). If unreachable, all four `it`
blocks call `t.skip()` via the file's own `dbAvailable` guard (same pattern as every
other DB-backed suite in this codebase) rather than failing — TEST-RUNNER must confirm
`dbAvailable` was actually `true` (i.e., the suite did not silently skip) by checking the
test output does not contain the file's `console.warn` skip message, and that all 4 tests
report as run (not skipped).
