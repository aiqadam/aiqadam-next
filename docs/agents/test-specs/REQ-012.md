# REQ-012 — Verification spec

Requirement: "Bot config loading, Postgres connection and migration runner wired into
apps/bot startup" (`docs/agents/requirements.yaml` REQ-012). Design:
`docs/agents/design/REQ-012.md`.

Method note (scope test): this requirement's user-visible surface is process/DB-level
(exit codes, stdout/stderr content, Postgres table state, file diffs), not application
logic reducible to a pure function beyond what `apps/bot/src/config.test.ts` already
covers. Per the same reasoning REQ-010/REQ-011's specs used: pure-function behavior gets
Vitest, process/DB-level properties get a scripted checklist. All four ACs here are
process/DB/file-level, so all four are scripted checklists — no new Vitest is added by
this spec. Where `config.test.ts` already gives real Vitest coverage of a sub-behavior,
this spec references it instead of re-deriving it (see the coverage table at the bottom).

All commands below are run from the repository root (`c:\Users\tvolo\dev\aiqadam-next`),
using the Bash tool (git-bash / POSIX sh), on branch `feature/WF02-REQ-012` after
`npm run build -w apps/bot` has produced `apps/bot/dist/`. Re-run the build if `dist/` is
stale relative to `apps/bot/src/`.

## AC1 — Migration idempotency, reports which migrations applied

Acceptance criterion text: "`npm run migrate -w apps/bot` (or REQ-009's chosen
equivalent, named in the verification report) applied against an empty Postgres creates
every table from REQ-010 and REQ-011, and running the SAME command a second time against
the now-migrated database exits 0 and applies nothing further — verified by capturing
both runs' output."

Uses the CORRECTED method from design §3.3: CLI stdout is identical
(`[✓] migrations applied successfully!`) on both runs and is NOT usable as evidence by
itself — the evidence is `drizzle.__drizzle_migrations` row state queried directly,
before and after each run.

### Steps

1. Ensure a clean scratch Postgres (no leftover volume from a prior run):
   ```bash
   docker compose -f apps/bot/docker-compose.yml down -v
   docker compose -f apps/bot/docker-compose.yml up -d
   ```
   Expected: both commands exit 0; `docker compose -f apps/bot/docker-compose.yml ps`
   shows the `postgres` service `running`/`healthy` (wait up to 15s and re-check `ps` if
   not yet ready — do not proceed to step 2 until it reports running).

2. Set the migration target and confirm the tracking table does not yet exist:
   ```bash
   export DATABASE_URL="postgres://bot:bot@localhost:55432/bot"
   psql "$DATABASE_URL" -c "SELECT hash, created_at FROM drizzle.__drizzle_migrations ORDER BY created_at;"
   ```
   Expected: the command errors with `relation "drizzle.__drizzle_migrations" does not
   exist` (schema `drizzle` has not been created yet) — this is the expected "0 rows,
   before" state, not a failure of this check.

3. Run the migration runner for the FIRST time and capture its output:
   ```bash
   npm run migrate -w apps/bot 2>&1 | tee /tmp/req012-migrate-run1.log
   echo "RUN1_EXIT:$?"
   ```
   Expected: exit code 0; log contains `migrations applied successfully` (per design
   §3.3, do not expect filenames or a count in this line — that is the known CLI
   limitation this spec works around in step 4).

4. Query the tracking table AFTER run 1:
   ```bash
   psql "$DATABASE_URL" -c "SELECT hash, created_at FROM drizzle.__drizzle_migrations ORDER BY created_at;"
   ```
   Expected: exactly 2 rows. Record the two `hash` and `created_at` values verbatim in
   the test report as `ROW1_AFTER_RUN1` and `ROW2_AFTER_RUN1` — these are the evidence of
   "which migrations it applied" (they correspond 1:1 to `apps/bot/drizzle/0000_tough_lilith.sql`
   and `apps/bot/drizzle/0001_tired_annihilus.sql`).

5. Confirm every REQ-010/REQ-011 table now exists:
   ```bash
   psql "$DATABASE_URL" -c "\dt"
   ```
   Expected: the listing includes at minimum `chapters`, `users`, `profiles` (REQ-010)
   and `venues`, `events`, `registrations`, `event_staff`, `audit_log` (REQ-011) — exact
   table names per REQ-010/REQ-011's migration files; if a name differs from this list,
   confirm it against those two migration files' `CREATE TABLE` statements rather than
   failing the check on a naming assumption.

6. Run the IDENTICAL migration command a SECOND time and capture its output:
   ```bash
   npm run migrate -w apps/bot 2>&1 | tee /tmp/req012-migrate-run2.log
   echo "RUN2_EXIT:$?"
   ```
   Expected: exit code 0; log contains `migrations applied successfully` (same line as
   run 1 — per design §3.3 this line does not itself distinguish the runs, which is why
   step 7 is the actual evidence).

7. Query the tracking table AFTER run 2:
   ```bash
   psql "$DATABASE_URL" -c "SELECT hash, created_at FROM drizzle.__drizzle_migrations ORDER BY created_at;"
   ```
   Expected: still exactly 2 rows, and both rows' `hash` and `created_at` values are
   byte-for-byte identical to `ROW1_AFTER_RUN1`/`ROW2_AFTER_RUN1` captured in step 4 (no
   new row, no changed `created_at`). This unchanged-row-state is the evidence that run 2
   "applies nothing further."

8. Teardown (optional, but leaves a clean state for a re-run):
   ```bash
   docker compose -f apps/bot/docker-compose.yml down -v
   ```

**Fails if:** step 1's Postgres never reports healthy; step 3 or step 6 exits non-zero;
step 4's row count is not exactly 2; step 5 is missing any REQ-010/REQ-011 table; step 7's
row count, `hash` values, or `created_at` values differ from step 4's.

## AC2 — Missing DATABASE_URL exits non-zero naming it; SECRETPW never logged

Acceptance criterion text: "Starting apps/bot with the database URL environment variable
unset exits non-zero and names that variable; the captured stdout/stderr from a start
WITH a dummy URL containing the string `SECRETPW` does not contain `SECRETPW` anywhere
(security-invariants.md S11), verified by grepping the captured output."

Two scripted sub-cases. Both require `apps/bot/dist/index.js` to exist (`npm run build -w
apps/bot` beforehand).

### AC2a — DATABASE_URL unset exits non-zero, names it

```bash
unset DATABASE_URL
BOT_TOKEN=dummy-token node apps/bot/dist/index.js > /tmp/req012-ac2a.log 2>&1
echo "EXIT:$?"
cat /tmp/req012-ac2a.log
grep -c "DATABASE_URL" /tmp/req012-ac2a.log
```

Expected: `EXIT:` is non-zero (not `0`); `grep -c "DATABASE_URL"` reports `1` or more
(the missing-variable message names it); the log does NOT contain the literal string
`BOT_TOKEN` as a *missing*-variable complaint (only `DATABASE_URL` should be reported
missing, since `BOT_TOKEN` was supplied) — read the actual message text to confirm it
reads as "Missing required environment variable(s): DATABASE_URL" per
`apps/bot/src/config.ts`'s message format, not just that the substring appears somewhere
incidental.

### AC2b — dummy URL containing SECRETPW never printed

```bash
BOT_TOKEN=dummy-token DATABASE_URL="postgres://baduser:SECRETPW@127.0.0.1:1/nonexistent" node apps/bot/dist/index.js > /tmp/req012-ac2b.log 2>&1 &
PID=$!
sleep 8
kill "$PID" 2>/dev/null
wait "$PID" 2>/dev/null
cat /tmp/req012-ac2b.log
grep -c "SECRETPW" /tmp/req012-ac2b.log
```

Expected: `grep -c "SECRETPW"` reports `0` — the string never appears anywhere in
stdout/stderr, including in any pool-connection-error text (port `1` on `127.0.0.1` is
chosen to guarantee an unreachable/refused connection, which is expected to surface some
connection-failure output within the pool's 5000ms `connectionTimeoutMillis`; that output
appearing is fine, it containing `SECRETPW` is the failure condition). The process is
killed after 8s regardless of whether it exited on its own — this AC does not require the
process to exit, only that the dummy secret string never appears in the captured output.

**Fails if:** AC2a's exit code is 0, or `DATABASE_URL` does not appear as a named missing
variable in the message text; AC2b's grep count is 1 or more.

**Note on `config.test.ts` overlap:** `apps/bot/src/config.test.ts` already has real
Vitest coverage that `loadConfig({ BOT_TOKEN: "t" })` throws naming `DATABASE_URL`, and
that a present variable's *value* never appears in the thrown message — that is the pure
`loadConfig` function-level proof. AC2 here is NOT redundant with it: AC2 verifies the
process-level wiring (`index.ts`'s `try/catch/process.exit(1)`, actual OS exit code, and
actual stdout/stderr of a spawned `node` process) that `config.test.ts` cannot observe
since it calls `loadConfig` directly in-process and never spawns `apps/bot`. Reuse
`config.test.ts`'s existing assertions as sufficient evidence for the pure
"which variable gets named" logic; this checklist supplies the exit-code and
process-output evidence config.test.ts structurally cannot.

## AC3 — Pool max is single-digit, PRD-1-load-justified

Acceptance criterion text: "The connection pool's configured maximum is a single-digit
value and the verification report cites PRD 1's load figures as the justification; a
pool max of 20 or more fails this criterion absent a written load argument."

This AC splits into two distinct checks — state which is which, since they are checked
differently:

### AC3a — Code inspection (mechanical, no judgment)

```bash
grep -n "max:" apps/bot/src/db/client.ts
```

Expected: a line of the form `max: <N>` inside the `new Pool({...})` call, where `<N>` is
a single ASCII digit (`1`–`9`, i.e. a value from 1 to 9 inclusive — not `10` or greater,
and not `20`). At the time this spec was written the live value is `max: 5`
(`apps/bot/src/db/client.ts` line 39) — TEST-RUNNER must re-read the actual line at
verification time rather than trusting this note, since the file may have changed.

### AC3b — Documentation-content check (not code — verifies TEST-RUNNER's own report)

This half of the AC is a requirement on the **verification report TEST-RUNNER writes**,
not on the source code: the report must cite PRD 1's specific load figures as the
justification, not merely assert "single-digit, justified." TEST-RUNNER's report for this
AC must include, verbatim or paraphrased with the numbers intact, all of the following
figures (present already as commentary in `apps/bot/src/db/client.ts` lines 9-17 and
design §2.2, so this is a copy-forward-and-confirm task, not new research):
- ~1,000 users
- ~10 events/year
- peak throughput 0.06 requests/second
- database under 50MB
- PRD 1's stated conclusion: "one Postgres and one bot process are sufficient — do not
  add infrastructure"

**Fails if:** AC3a's `max` value is absent, is `10` or greater, or is not a literal
integer (e.g. reads from an unvalidated env var with no fallback bound); AC3b's report
omits any one of the five figures listed above.

## AC4 — Compose file under apps/bot/, deploy/ unchanged

Acceptance criterion text: "The local Postgres compose file lives under apps/bot/ and
deploy/docker-compose.qa.yml and deploy/docker-compose.prod.yml are unchanged (verified
by `git diff --stat`), keeping the site's production deploy surface untouched by bot
work."

```bash
git diff --stat master -- deploy/docker-compose.qa.yml deploy/docker-compose.prod.yml
```

Expected: **empty output** (no lines at all) — any output, even a single changed line,
fails this AC.

```bash
git status --short apps/bot/docker-compose.yml
```

Expected: the file exists and is tracked (either no output, if already committed and
clean, or an `A ` / `M ` status line if this run's own commit is still pending — it must
not report the file as absent/untracked-and-ignored).

```bash
git diff --stat master -- apps/bot/docker-compose.yml
```

Expected: non-empty output (a real diff exists against `master`, proving the file is new
content added by this branch, not a pre-existing file left untouched).

**Fails if:** the first command's output is non-empty; the second command shows the file
missing; the third command's output is empty (i.e. no actual compose file was added).
