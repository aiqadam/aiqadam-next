## AC1 — admission changes to `withdrawn` directly in DB, survives an intervening
page-turn re-render, then a stale toggle press → no check-in, stated refusal

New `it(...)`, designed here for TEST-RUNNER to write in the new (not yet written) test
file — own fixture and own interleaving, genuinely
different from BACKEND-DEV's own AC1 case (bare render → DB change → tap) and from
REVIEWER's independent re-check:

- Seed one chapter, one organizer, one published event, `capacity: 20`. Register 12
  attendees (all `admitted`; capacity not exhausted) via `registerForEvent`, each with a
  distinct `firstName`/`lastName` so `PAGE_SIZE = 10` produces exactly 2 pages. Record the
  registration id of the **11th** attendee (alphabetically last on page 0's own sort order
  is not guaranteed — seed with `lastName` values `"A0"`..`"A11"` so ordering is
  deterministic, and target the attendee whose `lastName` is `"A10"`, which lands on page
  1 — `PAGE_SIZE = 10` means indices 0–9 are page 0, index 10 is page 1).
- Dispatch `bot.handleUpdate(commandUpdate(staffTgId, "/checkin " + eventId))` — the
  **stale render**, page 0. Capture its `sendMessage` reply (not used for the toggle —
  page 0 doesn't contain the target attendee's button).
- Dispatch a page-turn: `bot.handleUpdate(callbackUpdate(staffTgId, "checkin:page:" +
  eventId + ":1", <the page-0 message as a FakeMessage>))` — a real, intervening
  `editMessageText` re-render that the design (§1.5) explicitly says does not require
  knowing any prior page/search state beyond what's encoded in `callback_data`. Capture
  this `editMessageText` call's `reply_markup` — this is where the target attendee's
  toggle button (`checkin:toggle:<A10's registrationId>`) actually appears.
- Extract the target attendee's `callback_data` from the page-1 keyboard.
- Directly, via `pool.query`, `UPDATE registrations SET admission = 'withdrawn' WHERE id =
  $1` for the A10 attendee — modeling "admission changed directly in the DB" after the
  page-1 render, exactly as AC1 requires, but with a page-turn (not just the initial
  render) sitting between the render that produced this exact button and the stale tap.
- Dispatch the stale toggle: `bot.handleUpdate(callbackUpdate(staffTgId, <A10's
  callback_data>, <the page-1 message as a FakeMessage>))`.
- **Pass conditions:**
  1. `registrations` row for A10: `checkedInAt`/`checkedInBy`/`checkInMethod` all still
     `null`; `admission` still `'withdrawn'`.
  2. The toggle dispatch's `answerCallbackQuery` call has `show_alert: true` and
     `text === getCatalog("ru").checkin.refusedNotAdmitted`.
  3. No `editMessageText` call was made as a result of the toggle dispatch specifically
     (i.e. exactly one `editMessageText` call total across the whole test — the page-turn
     one — not two).
  4. Zero new `audit_log` rows with `action IN ('registration.checkin',
     'registration.checkin_undo')` for A10's `registrationId`.
- **Failure mode this catches:** a regression where the toggle handler (or
  `toggleCheckIn`) trusts a page-render-time snapshot of `admission` carried forward
  through an intervening re-render rather than re-reading fresh state at write time —
  specifically a bug that only manifests once a page turn (not just the very first
  render) has happened, which BACKEND-DEV's own single-render AC1 case cannot expose
  since it never exercises `makeCheckinPageCallbackHandler` at all.

## AC4 — live counter reflects two real toggle writes through the handler chain, own
before/after comparison

New `it(...)`, designed here for TEST-RUNNER to write in the new (not yet written) test
file — deliberately driven through `toggleCheckIn` via
real dispatch rather than a raw SQL `UPDATE` (BACKEND-DEV's own AC4 case uses a raw SQL
`UPDATE` to move the counter):

- Seed one chapter, one organizer, one published event, `capacity: 5`. Register 3
  attendees (all `admitted`).
- Dispatch `/checkin <eventId>`. Assert the header line reads `checkedInCount = 0`,
  `totalAdmitted = 3` (exact string match against
  `getCatalog("ru").checkin.listHeader` with the three placeholders substituted).
- Extract attendee 1's and attendee 2's toggle `callback_data` from the rendered keyboard.
- Dispatch a toggle for attendee 1 (check-in). Read the `editMessageText` payload's new
  header line — assert `checkedInCount = 1`, `totalAdmitted = 3`.
- Dispatch a toggle for attendee 2 (check-in). Read the second `editMessageText` payload's
  header line — assert `checkedInCount = 2`, `totalAdmitted = 3`.
- Dispatch a **second** toggle for attendee 1 (undo). Read the third `editMessageText`
  payload's header line — assert `checkedInCount = 1`, `totalAdmitted = 3` (the counter
  goes back down, proving it isn't a monotonic/cached increment).
- **Pass conditions:** all four header-line assertions above (0/3, 1/3, 2/3, 1/3, in that
  order) pass; `SELECT count(*) FROM events` payload columns for this event are unchanged
  across the whole sequence (direct `pool.query` `SELECT * FROM events WHERE id = $1`
  compared before the first dispatch and after the last toggle — full-row deep-equality,
  not just a spot check).
- **Failure mode this catches:** any per-render or per-toggle caching of the counter
  (e.g. computing it once and reusing it across the check-in/undo/check-in sequence,
  which BACKEND-DEV's raw-SQL-`UPDATE`-based AC4 case would not detect since it only ever
  moves the counter up once, never exercises a toggle-driven down-then-up-again sequence
  through the real handler); any accidental write to `events` from inside `toggleCheckIn`
  or the toggle handler's re-render path.

## Cross-event forged toggle — permanent regression test for SECURITY-REVIEWER's ad hoc
finding

New `it(...)`, designed here for TEST-RUNNER to write in the new (not yet written) test
file. This formalizes
`handoffs/WF02-REQ-028/step-02c-security-reviewer.json`'s "CROSS-EVENT FORGED TOGGLE"
finding, which was verified with a temporary test SECURITY-REVIEWER wrote, ran, and then
reverted via `git checkout --` — leaving **zero** permanent coverage today. Own fixture,
not copied verbatim from the security reviewer's prose:

- Seed two chapters (or one — chapters don't need to differ for this scenario; one
  chapter is sufficient and simpler), two organizers, two published events, Event A and
  Event B, each `capacity: 5`.
- Add a staff member ("Staff-A") to Event A **only** (`addEventStaff`, never added to
  Event B's `event_staff`).
- Register one attendee ("Victim") to Event B, landing `admitted`. Record Victim's
  `registrationId`.
- Staff-A never renders Event B's `/checkin` list at all (no genuine render ever produces
  `checkin:toggle:<Victim's registrationId>` for Staff-A) — the forged `callback_data` is
  hand-built: `` `checkin:toggle:${victimRegistrationId}` ``, paired with a hand-built
  `FakeMessage` (arbitrary `text`/`reply_markup`, since no real message ever existed for
  this pairing — mirrors how a forged/replayed callback would arrive with attacker-chosen
  but structurally-valid `callback_data` against a message the bot did send at some
  point).
- Dispatch `bot.handleUpdate(callbackUpdate(staffATgId, "checkin:toggle:" +
  victimRegistrationId, <the hand-built FakeMessage>))`.
- **Pass conditions:**
  1. `answerCallbackQuery` call has `show_alert: true` and `text ===
     getCatalog("ru").checkin.notAuthorized` (**not** `refusedNotAdmitted` — this is an
     authorization refusal against Event B, distinct from AC1's admission-state refusal;
     asserting the exact string distinguishes the two refusal paths, which share the same
     "no write happens" surface but must route through different code branches).
  2. Victim's `registrations` row: `checkedInAt`/`checkedInBy`/`checkInMethod` all still
     `null`.
  3. No `editMessageText` call was made.
  4. An `audit_log` row exists with `action = 'checkin.refused'` and `entityId =
     '<Event B's id>'` (confirms `requireEventStaffForEvent` was reached and correctly
     evaluated against the **freshly-derived** Event B, not Event A — if the handler ever
     regressed to authorizing against a caller-supplied or cached Event A context, this
     row's `entityId` would read Event A's id instead, or the whole gate would spuriously
     pass).
  5. Zero `audit_log` rows with `action IN ('registration.checkin',
     'registration.checkin_undo')` for Victim's `registrationId`.
- **Failure mode this catches:** any regression that has `makeCheckinToggleCallbackHandler`
  derive `eventId` from something other than a fresh `getEventIdForRegistration` read
  keyed strictly on the callback's own `registrationId` — e.g. reusing an `eventId` cached
  from the staff member's most recent `/checkin` command, or trusting an `eventId`
  threaded through some other channel — which would let a staff member of one event
  forge a toggle against another event's registration and either be wrongly authorized or
  be refused against the wrong event (masking the real vulnerability behind a
  coincidentally-still-refused outcome).

## Genuine concurrent double-toggle — locks in the READ COMMITTED serialization property

New `it(...)`, designed here for TEST-RUNNER to write in the new (not yet written) test
file. Not a same-process *sequential* repeat (which
would prove nothing about locking) — two `Promise.all`'d dispatches of the exact same
toggle callback fired concurrently, formalizing SECURITY-REVIEWER's structural trace
("S6 CONCURRENT-TOGGLE RACE TRACE") as a permanent, empirically-run regression test:

- Seed one chapter, one organizer, one published event, `capacity: 5`. Register one
  attendee, `admitted`, `checkedInAt` initially `null`.
- Build the toggle's `callback_data`/`FakeMessage` pair once (via a real `/checkin`
  dispatch and captured reply, same as every other case here).
- Fire **two** toggle dispatches concurrently against the identical starting state:
  ```
  await Promise.all([
    bot.handleUpdate(callbackUpdate(staffTgId, toggleCallbackData, message) as never),
    bot.handleUpdate(callbackUpdate(staffTgId, toggleCallbackData, message) as never),
  ]);
  ```
  (Two separate `bot.handleUpdate()` calls against the same in-process `bot`/`db` pool —
  each internally opens its own `db.transaction`, so this genuinely exercises two
  concurrent Postgres transactions racing on the same row, not two calls serialized by a
  single JS event-loop tick before any `await` — `toggleCheckIn`'s very first statement is
  an `await tx...for("update")`, which is where the two transactions actually contend.)
- **Pass conditions:**
  1. After both complete, `registrations.checkedInAt` for the attendee is **not** `null`
     — i.e. the net effect is exactly one check-in, matching the well-defined outcome
     SECURITY-REVIEWER's trace predicts (first transaction commits `"check-in"`; the
     second, blocked until the first commits, then re-reads the now-committed row under
     READ COMMITTED and correctly re-decides `"undo"` — **not** a second `"check-in"`
     racing the first). Restated precisely: the pass condition is not "checked in" XOR
     "not checked in" arbitrarily — it is deterministically "not checked in" is WRONG and
     "checked in" is the one correct final state, because the second transaction's fresh
     read after acquiring the lock sees the first's commit and flips back to undo, and
     then there is no third call to flip it again — **so the actual expected final state
     is `checkedInAt === null`** (check-in, then immediate undo). State this precisely in
     the test's own comment referencing the security reviewer's trace, and assert
     `checkedInAt` is `null` — not merely "not undefined" — as the single, exact expected
     value.
  2. Exactly one `audit_log` row with `action = 'registration.checkin'` for this
     registration, and exactly one with `action = 'registration.checkin_undo'` — never
     two of either (this is the property that would fail under a lost-update/race bug: a
     regression that let both concurrent transactions independently observe
     `checkedInAt === null` and both write `"check-in"` would produce **two**
     `registration.checkin` audit rows instead of one check-in followed by one undo).
  3. No unhandled promise rejection / thrown error from either `bot.handleUpdate()` call
     (`Promise.all` itself would reject and fail the test if either handler threw — assert
     the `Promise.all` above resolves without throwing, and additionally assert both
     `answerCallbackQuery` calls were captured, confirming neither dispatch silently
     dropped without ever reaching that point).
- **Failure mode this catches:** any change that weakens `toggleCheckIn`'s row lock (e.g.
  switching `.for("update")` to a plain `SELECT`, or moving the decide-then-write outside
  the transaction boundary) — such a regression would let both concurrent calls read the
  same pre-toggle `checkedInAt === null` snapshot and both independently decide
  `"check-in"`, producing two `registration.checkin` audit rows and/or a `checkedInAt`
  value from whichever `UPDATE` happened to commit last, which this test's exact
  audit-row-count and final-state assertions would catch but a looser "some check-in
  happened" assertion would not.
