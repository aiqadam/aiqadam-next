**What is NOT yet independently re-parameterized, and what this spec closes, per this
project's established convention (REQ-019/020/021/022's precedent — every spec adds its
own independently-designed cases rather than merely re-pointing at BACKEND-DEV's coverage):**

- **AC1 has never been exercised through the real `register:`/`withdraw:confirm` dispatch
  path** — BACKEND-DEV's AC1 case calls `withdrawRegistration` directly, and its 3
  waitlisted rows are inserted directly via `db.insert(...)`, never through a real
  registration flow. This spec's AC1 case registers the admitted user AND all three
  waitlisted users through real callbacks, then withdraws through a real
  `withdraw:confirm` dispatch, checking the promoted person's own reply is never sent (the
  design's own scope: only the promoted person is notified, not observed at all by the
  withdrawer) and confirming via SQL that the two untouched rows' `admission`/`qr_token`/
  `created_at` are unchanged.
- **The exact T-24h boundary instant has never been tested anywhere in this codebase** —
  BACKEND-DEV's AC2 case uses a 12h-out event, comfortably inside the halt window; no test
  anywhere constructs an event at exactly T-24h or at T-24h-minus-1-second, the two
  instants the design's own §2.1 boundary rule (`<=` on the halt side) is precisely about.
  This spec adds AC2-boundary below.
- **AC4's concurrency test has never raced more than one promotion/registration pair, and
  never gone through the real Telegram dispatch surface** — BACKEND-DEV's own case is a
  single withdrawal (one promotion attempt) racing a single fresh registration, both via
  direct domain calls. This spec's AC4 case uses a materially different shape: a
  multi-seat event with **two concurrent withdrawals** (each capable of triggering its own
  promotion) racing **two concurrent fresh registrations**, all four dispatched through
  real `bot.handleUpdate()` calls, never `withdrawRegistration`/`registerForEvent` called
  directly.
- **AC7's "twice for the same freed seat" has never been tested against a seat that was
  actually, genuinely freed once** — BACKEND-DEV's own second case tests an event that was
  never freed at all (full from the start). This spec's AC7 case withdraws a real seat via
  real dispatch (one genuine promotion, one genuine notification, confirmed by the actual
  `captured` sendMessage count), then calls `promoteFromWaitlistIfEligible` a second time
  against that same, now-refilled event, and states explicitly why a second notification
  cannot fire.
- **AC3's empty-waitlist case has never been exercised through the real `withdraw:confirm`
  dispatch** — BACKEND-DEV's case calls `withdrawRegistration` directly. This spec adds a
  dispatch-level case confirming the withdrawer's own reply is the ordinary
  `confirmedReply` (nothing different is shown when there was nobody to promote — the
  design states this is an ordinary, non-error return value, not a special-cased UX).
- **AC5's refusal has never been exercised via a genuine withdrawal path (only via a
  direct `promoteFromWaitlistIfEligible` call against a pre-broken event)** — this spec
  confirms the withdrawer's own reply is unaffected (still `confirmedReply`) when the
  promotion attempt silently refuses because the event was cancelled underneath it, and

### AC2-boundary — the exact T-24h instant (never tested anywhere in this codebase)

Per `docs/agents/design/REQ-023.md` §2.1 and the real implementation
(`apps/bot/src/domain/event.ts` line 745: `return startsAt.getTime() -
evaluationTime.getTime() <= AUTO_PROMOTION_HALT_WINDOW_MS;`), the boundary instant itself
(exactly 24h remaining) belongs to the **halted** side (`<=`), never the eligible side.
This is a pure function — test it directly, no DB, no dispatch, exact millisecond control:

```ts
import { isAutoPromotionHalted } from "./src/domain/event.js";

const evaluationTime = new Date("2026-09-01T00:00:00.000Z");

// Exactly T-24h: 24h remain, to the millisecond -- halted per the `<=` boundary.
const exactlyT24h = new Date("2026-09-02T00:00:00.000Z");
console.log("exactly T-24h ->", isAutoPromotionHalted(exactlyT24h, evaluationTime)); // expect true

// T-24h-minus-1-second, i.e. one second BEFORE the boundary is reached
// (24h + 1s remain) -- strictly more than 24h, so NOT halted.
const oneSecondBeforeBoundary = new Date("2026-09-02T00:00:01.000Z");
console.log("24h+1s remain ->", isAutoPromotionHalted(oneSecondBeforeBoundary, evaluationTime)); // expect false

// One second on the OTHER side of the boundary (23h59m59s remain), for
// completeness -- also halted, deeper into the halt window than the exact
// boundary case above.
const oneSecondAfterBoundary = new Date("2026-09-01T23:59:59.000Z");
console.log("23h59m59s remain ->", isAutoPromotionHalted(oneSecondAfterBoundary, evaluationTime)); // expect true
```

Run via `npx tsx apps/bot/scratch-verify-req023-boundary.ts` (or an ad hoc vitest `it`
block in the scratch harness — either is acceptable; this is a pure function call, no DB
needed).

- Pass conditions: `isAutoPromotionHalted` returns exactly `true` for the T-24h-exact
  instant, `false` for the instant one second before the boundary (24h+1s remaining), and
  `true` for the instant one second after (23h59m59s remaining). A run returning `false`
  for the exact T-24h instant is a FAIL — this is the exact regression AC2-boundary exists
  to catch: an off-by-one on the halt comparison operator that would let auto-promotion
  fire in the final 24 hours before an event, contradicting the requirement's own "halting
  at T-24h" framing (the boundary instant must already be halted, not the first instant
  after it).

## AC4 — promotion racing a fresh registration for the same freed seat never over-admits
(≥20-iteration concurrency test)

**Domain-level property already covered (single promotion vs. single fresh registration,
direct function calls, 20 iterations) — re-run and quote real output:**
```
cd apps/bot && npx vitest run --no-file-parallelism src/domain/registration.db.test.ts -t "REQ-023 AC4"
```
Expected: exit 0.

**This spec's own concurrency configuration — deliberately a different shape per this
task's own instruction: capacity=3 (not 1), TWO concurrent withdrawals (each independently
capable of triggering its own promotion) racing TWO concurrent fresh registrations for the
same event, ALL FOUR dispatched through real `bot.handleUpdate()` calls (never
`withdrawRegistration`/`registerForEvent` called directly), 5 iterations (chosen instead of
20 because each iteration now drives 7 real Telegram dispatches plus fixture setup through
a live-dispatch harness rather than 2 direct function calls — a smaller iteration count
that still exercises the same lock-contention property many times over is a deliberate,
named trade-off, not a weaker test of the same claim: the property under test, per design
§3.1, is that Postgres's row lock on `events` serializes ALL four transactions regardless
of how many contend for it, which a single iteration already exercises structurally; 5
iterations checks this holds under repeated, freshly-seeded conditions without the
harness's own per-iteration dispatch overhead making the run impractically slow):**

- Per iteration, fresh fixtures (a new chapter/event each time, `tg_id` offset by
  `1000000700 + iteration * 10`):
  ```sql
  -- (per-iteration, via psql or inline in the script) fresh chapter + 3 admitted seats
  -- filled to capacity, 2 waitlisted candidates behind them:
  INSERT INTO chapters (...) VALUES (...); -- fresh id per iteration
  ```
  ```ts
  for (let i = 0; i < 5; i++) {
    const base = 1000000700 + i * 10;
    const chapterId = /* fresh insert */;
    const eventId = await insertEventDirect(db, {
      chapterId, title: `AC4 Event ${i}`, capacity: 3,
      startsAt: new Date(Date.now() + 48 * 60 * 60 * 1000),
      endsAt: new Date(Date.now() + 50 * 60 * 60 * 1000),
      status: "published",
    });
    // Seed 3 users into the 3 seats via real register: callbacks.
    await bot.handleUpdate(callbackUpdate(base + 1, base + 1, `register:${eventId}`)); // seatA
    await bot.handleUpdate(callbackUpdate(base + 2, base + 2, `register:${eventId}`)); // seatB
    await bot.handleUpdate(callbackUpdate(base + 3, base + 3, `register:${eventId}`)); // seatC (stays admitted throughout)
    // Two waitlisted candidates, distinct created_at forced via SQL.
    await bot.handleUpdate(callbackUpdate(base + 4, base + 4, `register:${eventId}`)); // waitlisted W1
    await bot.handleUpdate(callbackUpdate(base + 5, base + 5, `register:${eventId}`)); // waitlisted W2
    // ... UPDATE registrations SET created_at = ... WHERE user's tg_id IN (base+4, base+5)
    // to guarantee W1 < W2 ordering ...

    // Look up seatA/seatB's own registration ids for the withdraw dispatch.
    // The race: seatA and seatB withdraw CONCURRENTLY (freeing up to 2 seats,
    // each independently attempting its own promotion), while base+6 and
    // base+7 (two fresh registrants who never registered before) attempt to
    // register CONCURRENTLY for the same event -- 4 contenders for 2 freed
    // seats.
    const [w1, w2, r1, r2] = await Promise.all([
      bot.handleUpdate(callbackUpdate(base + 100, base + 1, `withdraw:confirm:${seatARegId}`)),
      bot.handleUpdate(callbackUpdate(base + 101, base + 2, `withdraw:confirm:${seatBRegId}`)),
      bot.handleUpdate(callbackUpdate(base + 102, base + 6, `register:${eventId}`)),
      bot.handleUpdate(callbackUpdate(base + 103, base + 7, `register:${eventId}`)),
    ]);

    const admittedRows = await db.query.registrations.findMany({
      where: (reg, { eq: eqOp, and: andOp }) =>
        andOp(eqOp(reg.eventId, eventId), eqOp(reg.admission, "admitted")),
    });
    // capacity 3, seatC never left -> exactly 3 admitted at all times: seatC
    // plus whichever 2 of {W1, W2, fresh-1, fresh-2} won the 2 freed seats.
    assert(admittedRows.length === 3, `iteration ${i}: expected 3 admitted, got ${admittedRows.length}`);
  }
  ```
  Note: `withdraw:confirm:<id>` for both seatA and seatB must first be reached via the
  actual `/withdraw` command (or the registration id can be read directly from Postgres
  after the seed step, bypassing the confirmation-prompt dispatch, which is a legitimate
  shortcut here since AC1's dispatch-level case above already separately proves the prompt
  itself is correct — this case is about the concurrent write path, not the prompt UX).
- Pass conditions, checked every iteration: the admitted-row count for the event is
  **exactly 3** (never 4 or more — the capacity ceiling holds under 4-way concurrent
  contention for 2 freed seats; never fewer than 3 either, which would mean a freed seat
  was wrongly left empty despite eligible contenders existing). Across all 5 iterations,
  the run must also confirm at least one iteration where a fresh registrant (not a
  waitlisted candidate) won a freed seat, and at least one where a waitlisted candidate
  won instead — if every single iteration produces the identical winner pattern, note this
  in the report as a possible sign the race isn't being genuinely exercised (e.g. one side
  of the `Promise.all` is effectively always scheduled first), though this alone is not
  automatic grounds for a FAIL if the admitted-count invariant itself holds every time —
  the count invariant is the actual acceptance criterion; the winner-variety observation is
  a secondary confidence check on the race's genuineness.
- FAIL condition: any iteration where the admitted count for the event is not exactly 3
  immediately after the race resolves — this is the exact regression AC4 exists to catch
  (over-admission: more people admitted than seats exist; or under-admission: a freed seat
  silently lost).
