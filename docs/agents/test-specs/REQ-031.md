## AC4 — exactly one T+24h reminder; nothing thereafter, verified across a T+24h run, an immediate re-run, and a T+48h run

New `it(...)`, own fixture (a registration that never engages — the "ignores the request"
case):

- Seed one chapter, one organizer. Seed one published event, `endsAt =
  2026-09-01T00:00:00Z`.
- Seed registration A: admitted + checked-in (`checkedInAt = 2026-09-01T00:05:00Z`).
  **Never** answer NPS for A at any point in this test — this is what "ignores the
  request" means per design §5.3's own stated reading (a `feedback` row's mere existence,
  not completion, is what excludes someone).
- **Run 1 — the genuine T+24h send:** `evaluationTime24 = 2026-09-02T00:05:00Z` (24h + 5min
  after `endsAt`, inside the reminder job's window). `await
  makeFeedbackReminderJob(db, sender, 300000).run(evaluationTime24)`.
  - **Pass:** `sent` has length exactly 1; `notification_ledger` has exactly one row
    (`registrationId = A`, `kind = "feedback_reminder"`).
- **Run 2 — immediate re-run at the SAME evaluationTime (direct ledger-dedup proof):**
  `await makeFeedbackReminderJob(db, sender, 300000).run(evaluationTime24)` again, same
  `sender`/`sent` array.
  - **Pass:** `sent` still has length exactly 1 (unchanged from after Run 1) — the second
    `run()` re-selects A (nothing about A's state changed), but
    `sendLedgeredNotification`'s own `INSERT` into `notification_ledger` collides on the
    pre-existing `(registrationId, kind)` row (REQ-025's `UNIQUE` constraint) and resolves
    to `skipped-already-sent`, never calling `sender.send` a second time. `
    notification_ledger` still has exactly one `feedback_reminder` row for A (not two).
  - **This is the case that directly exercises the named AC4 mechanism** (the ledger
    `UNIQUE(registration_id, kind)` constraint), independent of the window logic below.
- **Run 3 — a much later re-run, T+48h:** `evaluationTime48 =
  2026-09-03T00:05:00Z` (48h + 5min after `endsAt`). `await
  makeFeedbackReminderJob(db, sender, 300000).run(evaluationTime48)`.
  - **Pass:** `sent` still has length exactly 1 (unchanged from after Runs 1–2).
  - **Documented mechanism, read directly from `selectRegistrationsForFeedbackReminder`'s
    own window arithmetic, not assumed:** at `evaluationTime48`, `windowEnd = endsAt +
    24h`, `windowStart = windowEnd - CATCH_UP_WINDOW_MS(2h) = endsAt + 22h`. The
    selection condition requires `endsAt > windowStart`, i.e. `endsAt > endsAt + 22h` —
    false. **A's registration is therefore excluded from Run 3's candidate list by the
    window itself, before the ledger is ever consulted a third time** — a *different*
    half of the same "exactly one, nothing thereafter" property than Run 2 proves, and
    this spec states both explicitly rather than assuming Run 3 exercises the ledger path
    too.
  - Confirm this directly: assert the ledger still has exactly one `feedback_reminder` row
    for A after Run 3 (not merely `sent`'s length — a regression that widened
    `CATCH_UP_WINDOW_MS` enough to re-include A at T+48h would still be caught here via a
    second ledger-collision `skipped-already-sent`, and `sent`'s length-1 assertion alone
    would not distinguish "excluded by window" from "included but deduped," but the total
    across all three runs is the property AC4 actually asks for and both readings satisfy
    it).
- **Total across all three runs: exactly 1 send, exactly 1 ledger row.** This is the
  literal count-across-runs check the task requires.
- **Failure mode this catches:** a regression that gives `"feedback_reminder"` the same
  ledger key shape as `"feedback_request"` (collapsing the two kinds), or one that resends
  on every job tick regardless of ledger state (e.g. bypassing `sendLedgeredNotification`),
  or one that widens `CATCH_UP_WINDOW_MS` unboundedly (re-including A at T+48h and beyond)
  without the ledger dedup catching it.

- Seed one chapter, one organizer, one published event. Seed registration A (admitted +
  checked-in) for user U.

  - **Pass:** `feedback` now has exactly one row for A: `nps = 8`, `liked/improve/
    topicVotes` all `null`, all three `*_skipped` columns `false`. The reply captured is
    the `liked` prompt: text contains `catalog.feedback.likedPrompt`, and its
    `reply_markup` is `{ force_reply: true }`. Capture this message's full text as
    `likedPromptText` (needed by the stale-reply case below).

  - **Pass:** `feedback.liked === "Great speakers and food"`, `likedSkipped === false`.
    Next reply is the `improve` prompt (`catalog.feedback.improvePrompt`, `force_reply`).
    Capture its text as `improvePromptText`.
- Dispatch `replyUpdate(U.tgId, "skip", improvePromptText)` (the literal
  `catalog.feedback.skipButton` keyword, case-insensitive per `isFeedbackSkipReply`).
  - **Pass:** `feedback.improve === null` (unchanged), `improveSkipped === true`. Next
    reply is the `topicVotes` prompt. Capture its text as `topicVotesPromptText`.

  - **Pass:** `feedback.topicVotes` deep-equals `["AI", "Web3", "Blockchain"]` (per
    `parseTopicVotes`'s split-on-newline-and-comma, trim, drop-empty rule).
    `topicVotesSkipped === false`. Next reply is the broadcast-ask prompt
    (`catalog.feedback.broadcastAskPrompt`) with two buttons (`feedback:broadcast:yes:A`,
    `feedback:broadcast:no:A`).
- **`feedback` table has exactly 1 row for registration A** at this point — the entire
  flow, however many steps, never inserts a second row (every step after the first is an
  `UPDATE`).
- **The direct duplicate-`INSERT` proof (AC2's own literal wording), mirroring REQ-025's
  ledger-uniqueness test pattern:**

  await expect(

## AC3 (continued) — full-skip path saves the row anyway; and the stale-reply field-match gate (the rework's entire point)

**Sub-case A — skip all three optional fields, feedback still saves:**

New `it(...)`, own fixture (registration B, distinct from A above):

- Tap NPS (`feedback:nps:4:${B}`). Skip `liked`, skip `improve`, skip `topicVotes` (three
  `replyUpdate`s, each with the literal skip keyword, each captured prompt fed to the
  next).
- **Pass:** `feedback` row for B exists: `nps = 4`, `liked/improve/topicVotes` all `null`,
  `likedSkipped = improveSkipped = topicVotesSkipped = true`. The flow still advances to
  the broadcast-ask prompt (`isFeedbackComplete`/`determineNextFeedbackField` treats a
  skipped field as resolved, not missing) — confirming "every question except NPS
  skippable, feedback still saves" concretely, with the row's actual column values, not
  merely "no crash occurred."

**Sub-case B — the stale-reply field-match gate:**

New `it(...)`, own fixture (registration C):

- Tap NPS (`feedback:nps:7:${C}`) → capture `likedPromptTextC`.
- Reply to `likedPromptTextC` with `"Loved the networking"` → `feedback.liked ===
  "Loved the networking"`. Capture the NEXT prompt (`improve`)'s text as
  `improvePromptTextC`. **At this point the flow's currently-expected field is
  `"improve"`; `likedPromptTextC` is now a SUPERSEDED prompt for a DIFFERENT, already-
  resolved sibling field.**
- Snapshot `feedback` row for C in full (`liked`, `improve`, `likedSkipped`,
  `improveSkipped`, `updatedAt`) and the length of `captured`.
- **The stale reply:** dispatch `replyUpdate(C's tgId, "Actually the venue was too small",
  likedPromptTextC)` — i.e. reply to the OLD `liked` prompt (`parsed.field === "liked"`)
  while the flow's freshly-derived `step.field === "improve"`.
- **Pass conditions:**
  1. `feedback.liked` is **unchanged** — still `"Loved the networking"`, NOT overwritten
     to `"Actually the venue was too small"`.
  2. `feedback.improve` is **unchanged** — still `null` (the stale reply's text was not
     misattributed to the currently-expected `improve` field either).
  3. `feedback.improveSkipped` is still `false`, `updatedAt` is byte-identical to the
     snapshot (no `UPDATE` of any kind occurred for this row as a result of the stale
     reply).
  4. `captured`'s length is **unchanged** from the snapshot — `advanceFeedbackFlow` is
     never called for this update (the handler's field-match gate returns *before*
     `advanceFeedbackFlow`, `handlers/feedback.ts:267`), so no new Telegram message of any
     kind was sent in response to the stale reply.
- **This is the exact case the task names as the whole point of the rework** (§1.2/§6.3
  step 8 of the design): a reply to an older, already-superseded prompt for one field,
  arriving while a DIFFERENT sibling field is now expected, is a silent no-op — never
  misattributed to either the old field (already resolved) or the new one (not what was
  replied to). **Failure mode this catches:** reverting `handlers/feedback.ts`'s gate from
  `step.kind !== "feedback-field" || step.field === "nps" || step.field !== parsed.field`
  back to only the first two clauses (the design's own stated pre-rework bug) would let
  this stale reply overwrite `feedback.improve` with `"Actually the venue was too small"`
  — condition 2 is what specifically catches that regression; condition 1 catches the
  (less likely but structurally possible) alternative bug of overwriting `liked` a second
  time instead.

## S3 exploit — forged/reused registration id in a callback or reply is refused, no write, across all three handlers

New `it(...)`, own fixture, mirroring `checkinQr.forgery.test.ts`'s exact
seed-two-identities/cross-tap pattern:

- Seed one chapter, one organizer, one published event. Seed registration A for user
  **Alice** (admitted + checked-in). Seed a SEPARATE user **Bob** (own `tgId`, own
  registration for a different event — Bob's own identity is irrelevant to A's flow, only
  his `tgId`/resolved `flowUser.id` matter as the attacker's own).
- Drive Alice's flow far enough to have both a `feedback` row and a captured `liked`
  prompt: tap `feedback:nps:6:${A}` as Alice, capture `likedPromptTextA`.
- **Attack 1 — NPS callback forgery:** dispatch `callbackUpdate(Bob.tgId,
  \`feedback:nps:9:${A}\`)` — Bob taps a callback naming Alice's own registration id.
  - **Pass:** `ctx.answerCallbackQuery`'s payload has `show_alert: true`, `text ===
    catalog.feedback.notYourFeedback`. `feedback.nps` for A is **still `6`**, not
    overwritten to `9`. No new `feedback` row was created for Bob (row count for
    `registrationId != A` is 0).
- **Attack 2 — text-reply forgery:** dispatch `replyUpdate(Bob.tgId, "Fake answer",
  likedPromptTextA)` — Bob replies to Alice's own `liked` prompt (which carries Alice's
  `registrationId` in its ref line).
  - **Pass:** `feedback.liked` for A is **still `null`** (unchanged) — Bob's reply is
    silently dropped at `handlers/feedback.ts:254`'s ownership check (`context.userId !==
    flowUser.id`), never reaching the write. `captured` gains no new `sendMessage` entry
    for this update (the passive-listener convention: silent no-op, not an alert).
- **Attack 3 — broadcast callback forgery:** drive A's flow to the broadcast-ask step
  (answer/skip the remaining optional fields as Alice), then dispatch
  `callbackUpdate(Bob.tgId, \`feedback:broadcast:yes:${A}\`)`.
  - **Pass:** `ctx.answerCallbackQuery`'s payload: `show_alert: true`, `text ===
    catalog.feedback.notYourFeedback`. Alice's own `users.broadcastOptIn`/
    `broadcastOptInAskedAt` are **unchanged** from immediately before this tap (still
    whatever Alice's own flow had set, or both `false`/`null` if not yet reached). **Bob's
    own** `users.broadcastOptIn`/`broadcastOptInAskedAt` are **also unchanged** — the
    forged tap cannot corrupt the attacker's own row either, since `writeBroadcastOptInAnswer`
    is never called at all (the gate fails before any write function is named).
- **Failure mode this catches:** any of the three ownership checks
  (`handlers/feedback.ts:144`, `:200`, `:254`) being weakened, removed, or reordered to run
  after a write instead of before it — each attack independently exercises one handler's
  own check, mirroring `checkinQr.forgery.test.ts`'s own one-negative-case-per-handler
  discipline.
