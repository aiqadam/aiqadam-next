## Shared setup (run once before AC1–AC7)

1. `cd apps/bot && docker compose up -d` — starts the throwaway Postgres (host port
   `55432`, user/password/db all `bot`).
2. Poll until ready: `docker compose exec postgres pg_isready -U bot` reports
   `accepting connections` (poll every 2s; do not sleep-guess).
3. `export DATABASE_URL=postgres://bot:bot@localhost:55432/bot` (PowerShell:
   `$env:DATABASE_URL = "postgres://bot:bot@localhost:55432/bot"`).
4. From `apps/bot`: `npx drizzle-kit migrate` — applies every migration, including
   `0004_fancy_zombie.sql` (AC-schema below independently confirms its exact statements).
5. Seed fixture rows via `psql "$DATABASE_URL" -c "<statement>"` — exact statements given
   per case. Cases are NOT assumed to share fixture state unless a case explicitly says
   so — run each case's own `DELETE` cleanup first otherwise.
6. Write the harness scripts under `apps/bot/scratch-verify-req019*.ts` (NOT committed —
   delete all of them at the end of the run). Shared shape for the single-process cases
   (AC2 through AC7):

```ts
import { Bot } from "grammy";
import {
  makeProfileCommandHandler,
  makeProfileEditHandler,
  makeProfileChapterHandler,
  makeProfileChapterCallbackHandler,
  makeProfileSkipCallbackHandler,
  makeProfileStudentCallbackHandler,
  makeProfileExperienceCallbackHandler,
  makeProfileTextAnswerHandler,
  makeProfileContactHandler,
} from "./src/handlers/profile.js";
import { makeStartHandler, makeChapterCallbackHandler, makeConsentCallbackHandler } from "./src/handlers/start.js";
import { createDbClient } from "./src/db/client.js";

const { db } = createDbClient(process.env.DATABASE_URL!);

const bot = new Bot("000000:DUMMY_TOKEN_NOT_REAL", {
  botInfo: {
    id: 1, is_bot: true, first_name: "Test", username: "test_bot",
    can_join_groups: true, can_read_all_group_messages: false, supports_inline_queries: false,
  },
});

const captured: Array<{ method: string; payload: unknown }> = [];
bot.api.config.use(async (_prev, method, payload) => {
  captured.push({ method, payload });
  return { ok: true, result: true } as never;
});

bot.command("start", makeStartHandler(db));
bot.callbackQuery(/^chapter:(.+)$/, makeChapterCallbackHandler(db));
bot.callbackQuery(/^consent:agree(?::.+)?$/, makeConsentCallbackHandler(db));
bot.command("profile", makeProfileCommandHandler(db));
bot.command("profile_edit", makeProfileEditHandler(db));
bot.command("profile_chapter", makeProfileChapterHandler(db));
bot.callbackQuery(/^profile:chapter:(.+)$/, makeProfileChapterCallbackHandler(db));
bot.callbackQuery(/^profile:skip:(phone|email|linksGithub|linksLinkedin|linksSite)$/, makeProfileSkipCallbackHandler(db));
bot.callbackQuery(/^profile:student:(yes|no)$/, makeProfileStudentCallbackHandler(db));
bot.callbackQuery(/^profile:experience:(user|builder|advanced|expert)$/, makeProfileExperienceCallbackHandler(db));
bot.on("message:contact", makeProfileContactHandler(db));
bot.on("message:text", makeProfileTextAnswerHandler(db));

function messageUpdate(updateId: number, tgId: number, text: string) {
  const isCommand = text.startsWith("/");
  return {
    update_id: updateId,
    message: {
      message_id: updateId, date: Math.floor(Date.now() / 1000),
      chat: { id: tgId, type: "private" as const },
      from: { id: tgId, is_bot: false, first_name: "Test" },
      text,
      ...(isCommand ? { entities: [{ type: "bot_command" as const, offset: 0, length: text.split(" ")[0].length }] } : {}),
    },
  };
}

function callbackUpdate(updateId: number, tgId: number, data: string) {
  return {
    update_id: updateId,
    callback_query: {
      id: String(updateId), from: { id: tgId, is_bot: false, first_name: "Test" },
      message: {
        message_id: updateId - 1, date: Math.floor(Date.now() / 1000),
        chat: { id: tgId, type: "private" as const }, text: "prompt",
      },
      chat_instance: "1", data,
    },
  };
}

async function main() {
  await bot.init();
  // --- dispatch calls inserted per-case below, in order ---
  console.log(JSON.stringify(captured, null, 2));
  process.exit(0);
}

main();
```

## AC1 — kill+restart mid-form resumes at the next unanswered field, first answers
preserved

**Unit-level property already covered — re-run and quote real output:**
```
cd apps/bot && npx vitest run --no-file-parallelism src/domain/profile.test.ts -t "AC1's own case"
```
Expected: exit 0, the case passes (`determineNextProfileField` correctly names the 4th
field, `position`, once the first 3 required fields are set).

**Live-integration gap this unit test cannot catch, and the specific gap this AC's own
wording ("kill+restart") calls out:** the unit test hand-builds a `ProfileRecord` inside
one Vitest process — it never proves that a genuinely separate OS process, started fresh
with no shared memory of any kind, correctly re-derives "what's next" purely by reading
Postgres, or that the first three answers actually survived a hard kill of the process
that wrote them (as opposed to sitting in some unflushed in-process buffer that a
graceful `process.exit()` would have flushed but a kill would not). **This case
therefore requires two separate `npx tsx` process invocations with a real, forceful kill
of the first between them — not two calls inside one script.**

- Fixture (a chapter, and a user already past consent+chapter — this case is about the
  profile stage specifically, not re-testing AC3's consent gate):
  ```sql
  DELETE FROM profiles; DELETE FROM users; DELETE FROM chapters;
  INSERT INTO chapters (id, code, name, timezone, default_lang, active)
    VALUES ('c0000001-0000-0000-0000-000000000000', 'r19a1', 'REQ19 AC1 Chapter', 'Asia/Tashkent', 'en', true);
  INSERT INTO users (id, tg_id, role, chapter_id, lang, consent_pd_at) VALUES
    ('c0000001-0000-0000-0000-00000000000c', 1000000201, 'member', 'c0000001-0000-0000-0000-000000000000', 'en', now());
  ```

- **Phase 1 script** (`apps/bot/scratch-verify-req019-ac1-phase1.ts`, built on the shared
  shape above): after `bot.init()`, dispatch in order:
  ```ts
  await bot.handleUpdate(messageUpdate(1, 1000000201, "First"));   // answers firstName
  await bot.handleUpdate(messageUpdate(2, 1000000201, "Last"));    // answers lastName
  await bot.handleUpdate(messageUpdate(3, 1000000201, "Acme Co")); // answers company
  console.log(`PROCESS_READY_TO_KILL pid=${process.pid}`);
  await new Promise(() => {}); // hang forever — never calls process.exit itself
  ```
  Run it detached/backgrounded: `npx tsx scratch-verify-req019-ac1-phase1.ts` — capture
  stdout, wait for the `PROCESS_READY_TO_KILL pid=<N>` line (poll, do not sleep-guess),
  then **forcibly kill that exact PID**: PowerShell `Stop-Process -Id <N> -Force`, or
  POSIX `kill -9 <N>`. This is a real SIGKILL/forced termination of a live process, not
  a graceful shutdown and not merely letting the script finish — confirm the process is
  actually gone afterward (PowerShell `Get-Process -Id <N> -ErrorAction SilentlyContinue`
  returns nothing; POSIX `kill -0 <N>` fails).
- Read-back check, immediately after the kill, before starting phase 2:
  ```sql
  SELECT first_name, last_name, company, position, is_student, experience_level
    FROM profiles WHERE user_id = 'c0000001-0000-0000-0000-00000000000c';
  ```
  Expected: exactly one row, `first_name = 'First'`, `last_name = 'Last'`,
  `company = 'Acme Co'`, `position`/`is_student`/`experience_level` all `NULL` — the
  first three answers survived the kill (each was its own committed `INSERT`/`UPDATE`,
  §2.4's per-answer upsert, never buffered), and the row is a legal partial state only
  because `0004_fancy_zombie.sql` relaxed these columns' `NOT NULL` (AC-schema).
- **Phase 2 script** (`apps/bot/scratch-verify-req019-ac1-phase2.ts`, a SEPARATE file,
  its own fresh `npx tsx` invocation, its own new process, no import of or reference to
  phase 1's script or process in any way): after `bot.init()`, dispatch:
  ```ts
  await bot.handleUpdate(messageUpdate(4, 1000000201, "Some Position"));
  ```
  Run it: `npx tsx scratch-verify-req019-ac1-phase2.ts`.
  Expected `captured` (phase 2's own, freshly-started `captured` array — it starts
  empty, proving nothing about "what was already asked" is remembered by this process;
  the correctness comes entirely from what phase 2 reads out of Postgres): **the message
  dispatched (`"Some Position"`) is accepted as the answer to `position`** — i.e. no
  prompt is re-sent for `firstName`/`lastName`/`company` (those are not re-asked), and
  the very next `sendMessage` after this dispatch is the prompt for the field AFTER
  `position` in the fixed order — `isStudent` (`catalog.profile.promptIsStudent` with
  the student keyboard). If phase 2 instead re-prompts `firstName` (the resumability
  bug this case exists to catch) or accepts `"Some Position"` as an answer to the wrong
  field, that is a FAIL.
- Read-back check after phase 2:
  ```sql
  SELECT first_name, last_name, company, position, is_student, experience_level
    FROM profiles WHERE user_id = 'c0000001-0000-0000-0000-00000000000c';
  ```
  Expected: `first_name = 'First'`, `last_name = 'Last'`, `company = 'Acme Co'`
  (byte-for-byte unchanged from before the kill — phase 2 never overwrote them),
  `position = 'Some Position'` (newly written by phase 2), `is_student`/
  `experience_level` still `NULL`.
- Pass conditions: the phase-1 process is verifiably killed (not merely exited) after
  exactly 3 answers land as committed rows; phase 2, a wholly separate process reading
  only from Postgres, resumes at exactly the 4th field (`position`) without re-asking or
  losing the first 3 answers, and correctly advances to the 5th field (`isStudent`)
  after phase 2's own answer lands. Any re-prompt of an already-answered field, any lost
  or altered first-three-answer value, or phase 2 treating its dispatched text as
  anything other than the `position` answer is a FAIL — this is the exact regression
  class ("resumability relies on something that doesn't survive a real crash") AC1
  exists to catch, which is why this case is deliberately built as two independent OS
  processes rather than two function calls in one script.

## AC1b — SECURITY-REVIEWER's field-mismatch and stale-replay scenarios, restated as
this spec's own resumability-integrity cases

These map to AC1 rather than AC3 (the SECURITY-REVIEWER handoff's own suggestion) on
this spec's judgment: neither scenario touches the consent gate at all — both are about
whether a forged or stale `profile:skip:<field>` callback can desynchronize "what's
actually next" from "what gets written," which is exactly AC1's resumability property
under adversarial rather than well-behaved input.

- Fixture (single-process script; a user already past consent+chapter, all 6 required
  fields already answered so the current step is `phone`, the first optional field):
  ```sql
  DELETE FROM profiles; DELETE FROM users; DELETE FROM chapters;
  INSERT INTO chapters (id, code, name, timezone, default_lang, active)
    VALUES ('c0000001-0000-0000-0000-00000000001b', 'r19a1b', 'REQ19 AC1b Chapter', 'Asia/Tashkent', 'en', true);
  INSERT INTO users (id, tg_id, role, chapter_id, lang, consent_pd_at) VALUES
    ('c0000001-0000-0000-0000-0000000001bc', 1000000202, 'member', 'c0000001-0000-0000-0000-00000000001b', 'en', now());
  INSERT INTO profiles (id, user_id, first_name, last_name, company, position, is_student, experience_level)
    VALUES ('c0000001-0000-0000-0000-0000000001bd', 'c0000001-0000-0000-0000-0000000001bc',
            'A', 'B', 'C', 'D', false, 'user');
  ```
- **Field-mismatch dispatch:** a forged `profile:skip:email` callback while the real
  current step is `phone`:
  ```ts
  await bot.handleUpdate(callbackUpdate(1, 1000000202, "profile:skip:email"));
  ```
  Read-back:
  ```sql
  SELECT phone_skipped, email_skipped FROM profiles WHERE user_id = 'c0000001-0000-0000-0000-0000000001bc';
  ```
  Expected: both `false` — neither flag changed. The gate compares the callback's
  claimed field (`email`) against the actual derived step (`phone`); they mismatch, so
  `markOptionalProfileFieldSkipped` is never called for either field. Also confirm
  `captured` contains exactly one `answerCallbackQuery` plus a re-prompt for `phone`
  (from the trailing `advanceAfterWrite` re-derive), never a prompt for `github` (which
  would imply `email` was wrongly treated as answered).
- **Stale-replay dispatch:** answer `phone` for real via its own correct skip, advancing
  to `email`, then replay the ORIGINAL (now-stale) `profile:skip:phone` callback data a
  second time:
  ```ts
  await bot.handleUpdate(callbackUpdate(2, 1000000202, "profile:skip:phone")); // real, honored
  await bot.handleUpdate(callbackUpdate(3, 1000000202, "profile:skip:phone")); // stale replay
  ```
  Read-back after both:
  ```sql
  SELECT phone_skipped, email_skipped FROM profiles WHERE user_id = 'c0000001-0000-0000-0000-0000000001bc';
  ```
  Expected: `phone_skipped = true` (from the first, honored call), `email_skipped =
  false` — the replay is NOT reinterpreted as answering the now-current field (`email`);
  its claimed field (`phone`) no longer matches the derived step (`email`), so it is a
  pure no-op followed by a harmless re-prompt for `email`.
- Pass conditions: a callback naming a field other than the actual current step never
  writes anything, for either the wrong-field-from-the-start case or the
  stale-after-advancing case. A run where either forged/stale callback is honored (any
  flag or column changes as a result) is a FAIL.

## AC3b — SECURITY-REVIEWER's chapter-but-no-consent and forged-skip-while-unconsented
scenarios, restated as this spec's own consent-gate-integrity cases

- **Chapter-but-no-consent via `/profile` directly (bypassing `/start`):** an
  inconsistent/adversarial DB state — a user with a chapter already assigned but
  `consent_pd_at` still `NULL` (something REQ-019's own handlers never produce, but
  which this case proves is still handled safely if it ever occurred, e.g. via a future
  admin tool or data migration).
  ```sql
  DELETE FROM profiles; DELETE FROM users; DELETE FROM chapters;
  INSERT INTO chapters (id, code, name, timezone, default_lang, active)
    VALUES ('c0000003-0000-0000-0000-0000000003b0', 'r19a3b', 'REQ19 AC3b Chapter', 'Asia/Tashkent', 'en', true);
  INSERT INTO users (id, tg_id, role, chapter_id, lang, consent_pd_at) VALUES
    ('c0000003-0000-0000-0000-0000000003bc', 1000000205, 'member', 'c0000003-0000-0000-0000-0000000003b0', 'en', NULL);
  ```
  Dispatch:
  ```ts
  await bot.handleUpdate(messageUpdate(3, 1000000205, "/profile"));
  ```
  Expected: `sendMessage` with `text` equal to `consent.prompt` — never a chapter or
  profile-field prompt, since `determineOnboardingStep` checks `!hasConsented` before
  ever looking at `hasChapter` (domain/onboarding.ts, step 1 of the rule table).
