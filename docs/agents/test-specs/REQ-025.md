## AC1 — send, KILL process, restart, run same job again → exactly ONE delivery (genuine
two-process test, kill point AFTER the first send resolves)

**This is the property REQ-025.md §3.2/§3.3 states most precisely — the kill point is not
a free choice.** Per §3.2's closing paragraph: killing mid-flight inside `sender.send()`
(before it returns) is a different, also-correct scenario (zero deliveries) that does NOT
prove "exactly one." The kill must happen strictly after `sender.send()` has already
resolved in the first run.

**Fixture (built by `scratch-verify-req025-p1.ts` on its first run, `p2` reuses the same
row):**
- One chapter/venue, one published event (`EVENT_ONE`, 48h out, capacity 5).
- One user `RESTART_SUBJECT` (`tg_id 1000000901`), created via `resolveOrCreateUser`.
- One registration for `RESTART_SUBJECT` on `EVENT_ONE` via a real `registerForEvent`
  call (admitted — capacity 5, first registrant) — this is the `registrationId` both
  processes pass to `sendLedgeredNotification`.
- `kind: "reminder_24h"` (per REQ-025.md §7's own note: no real T-24h job exists yet in
  this requirement's scope, so this AC verifies `sendLedgeredNotification` directly with
  a literal `reminder_24h` argument, standing in for what REQ-026's job body will later
  call), `classification: "transactional"`.

**Stub `NotificationSender` shared by both processes** (each process constructs its own
instance of this shape — not a shared object, since they are separate processes; the
"sharing" is only through the delivery-log file and the DB):
```ts
const sender: NotificationSender = {
  async send(tgId, text) {
    // The "real send" this stub performs: append one line to a shared file,
    // synchronously, so the write is durable before this call returns.
    fs.appendFileSync(
      "./scratch-verify-req025-deliveries.json",
      JSON.stringify({ tgId: tgId.toString(), text, pid: process.pid, at: new Date().toISOString() }) + "\n",
    );
  },
};
```

**`scratch-verify-req025-p1.ts` (process 1):**
1. Build the fixture above (chapter/venue/event/user/registration) if the delivery-log
   file does not already exist; write the resulting `registrationId` to a small sidecar
   file (`./scratch-verify-req025-fixture.json`) for `p2` to read.
2. Call `sendLedgeredNotification({ db, sender, registrationId, kind: "reminder_24h",
   classification: "transactional", userId: subject.id, composeMessage: () => "test
   reminder" })` — **do not `await` its settlement inside a `try`/`finally` that could run
   extra code after**. Instead:
   ```ts
   sendLedgeredNotification({ ... }).then(() => {
     process.exit(0);
   });
   ```
   This constructs the kill point precisely where REQ-025.md §3.2 requires it: the
   promise `sendLedgeredNotification` returns only resolves *after* step 5's
   `sender.send(...)` call has itself already resolved (the file write in the stub above
   has already happened, durably, by the time `.then()`'s callback runs) — `process.exit(0)`
   then terminates the process immediately, with no further application code (no logging,
   no second DB write, nothing) executing afterward. This is the genuine "kill right after
   the first send resolved" point, not a mid-flight kill and not a graceful shutdown.
3. Run: `npx tsx scratch-verify-req025-p1.ts` (a real, separate OS process — `npx tsx`
   spawns a fresh Node process with its own heap; nothing from this process's memory
   survives into `p2`).
4. Confirm the process actually exited (its own exit code observed by the shell is `0`,
   not left hanging) before proceeding to step 5 below — TEST-RUNNER must not start `p2`
   until `p1`'s process has visibly terminated.
5. Independently confirm, by direct SQL against the shared Postgres (a fresh `psql`/query,
   not reading `p1`'s in-memory state, which no longer exists): exactly one row in
   `notification_ledger` for `(registration_id = <that registrationId>, kind =
   'reminder_24h')`, and exactly one line in `scratch-verify-req025-deliveries.json`.

**`scratch-verify-req025-p2.ts` (process 2 — the "restart," run same job again):**
1. Read `registrationId` back from the sidecar file (simulating "the same job re-running
   with the same inputs after a restart" — a real scheduled job would re-derive the same
   `registrationId` from its own query, e.g. "registrations needing a reminder," which is
   exactly why the ledger's key is `(registration_id, kind)` and not a run-id).
2. Open a **fresh** `Pool`/`drizzle` instance — no state from `p1` is imported or shared
   in-process.
3. Call the identical `sendLedgeredNotification({ ..., registrationId, kind:
   "reminder_24h", classification: "transactional", ... })` with the same stub `sender`
   shape (a fresh object instance, appending to the same file) as `p1`.
4. Capture the returned `SendOutcome` and write it to
   `./scratch-verify-req025-p2-outcome.json` before exiting normally (`process.exit(0)`
   after the write — no kill-point discipline needed here, since this run's own delivery
   correctness is exactly what's being asserted, not a second kill scenario).
5. Run: `npx tsx scratch-verify-req025-p2.ts`.

**Pass conditions (all must hold):**
- `p2`'s captured `SendOutcome` is exactly `{ kind: "skipped-already-sent" }` — **not**
  `"sent"`.
- `scratch-verify-req025-deliveries.json` contains **exactly one** line (the one `p1`
  wrote) — `p2`'s run added zero lines, i.e. `sender.send` was never invoked by `p2`.
- Direct SQL after both runs: exactly one row in `notification_ledger` for
  `(registration_id, kind='reminder_24h')` — the duplicate insert attempted by `p2`'s call
  never landed (or rather, was rejected and converted to `skipped-already-sent` before
  ever reaching `sender.send`).

**Failure mode this catches:** an in-memory idempotency guard (a module-level `Set`/`Map`
keyed by `registrationId+kind`) would pass a *single-process* two-call test but fail this
one specifically — `p2`'s fresh process starts with an empty guard, so if the real
mechanism were in-memory, `p2` would call `sender.send` a second time, producing a second
line in the delivery log and `{ kind: "sent" }` as `p2`'s outcome. Only a durable,
DB-backed constraint survives the process boundary this test actually crosses. A bug that
reordered steps 4/5 (send before ledger insert) would also be caught in a rarer run: if
`p1`'s kill happened to land after `sender.send` but the ledger insert had not yet
committed (impossible under the current step ordering, but exactly the ordering §3.2
explicitly rejects as the alternative design), `p2` would re-send — this test is
constructed at the one kill point that specifically exercises "ledger row committed,
send confirmed" being the durable, correctly-ordered state.

```sql
-- Using a real registration row's id (reuse AC1's RESTART_SUBJECT registration, or seed
-- a fresh chapter/venue/event/user/registration via the same helpers if AC1 has not run

INSERT INTO notification_ledger (registration_id, kind) VALUES ('<registrationId>', 'admission_result');
INSERT INTO notification_ledger (registration_id, kind) VALUES ('<registrationId>', 'admission_result');
```

  **second**, identical statement fails with Postgres error code `23505` (unique
  violation), naming constraint `uq_notification_ledger_registration_kind` in its error
  detail (`psql`'s own error text: `duplicate key value violates unique constraint
  "uq_notification_ledger_registration_kind"`).
- A third statement with the same `registration_id` but a **different** `kind` (e.g.
  `'waitlist_promotion'`) must succeed — confirms the constraint is genuinely composite
  `(registration_id, kind)`, not accidentally unique on `registration_id` alone (which

  in its lifetime).

  enforced by an index that isn't actually unique) — this case would either reject the
  first insert (if `kind` alone were unique and a prior row with that kind existed) or
  silently accept the duplicate (if the constraint doesn't exist at all), either of which
  fails one of the three assertions above.

async function seedRegistration(
  db: NodePgDatabase<typeof schema>,
  tgId: number,
  opts: { blocked?: boolean; broadcastOptIn?: boolean } = {},

  const chapterId = await seedChapter();
  const eventId = await seedPublishedEvent(chapterId);
  const user = await resolveOrCreateUser(db, { tgId: BigInt(tgId), tgUsername: `u${tgId}`, lang: "ru" });

    await db.update(schema.users).set({
      ...(opts.blocked !== undefined ? { blocked: opts.blocked } : {}),
      ...(opts.broadcastOptIn !== undefined ? { broadcastOptIn: opts.broadcastOptIn } : {}),

  const result = await registerForEvent(db, user.id, eventId, new Date());

## AC6 — HTTP 429 then 200 → backoff-and-retry, message delivered exactly once

New `it(...)` in `notification.test.ts`, exercising `createRateLimitedSender` against a
real `Bot` instance (grammY), stubbing the network boundary via `bot.api.config.use` —
the same interception point every `handlers/*.test.ts` file already uses, but here
configured to fail the *first* call and succeed the second:

```ts
it("a 429 on the first attempt is retried and the message is delivered exactly once", async () => {
  const bot = new Bot("000000:TEST-TOKEN-NOT-REAL", { botInfo: FAKE_BOT_INFO });
  let callCount = 0;
  const sendMessageCalls: unknown[] = [];
  bot.api.config.use(async (_prev, method, payload) => {
    if (method !== "sendMessage") {
      return { ok: true, result: true } as never;
    }
    sendMessageCalls.push(payload);
    callCount += 1;
    if (callCount === 1) {
      return {
        ok: false,
        error_code: 429,
        description: "Too Many Requests: retry after 0",
        parameters: { retry_after: 0 }, // 0s so the test does not actually wait ~1s+
      } as never;
    }
    return {
      ok: true,
      result: { message_id: 1, date: Math.floor(Date.now() / 1000), chat: { id: 0, type: "private" } },
    } as never;
  });

  const sender = createRateLimitedSender(bot, {
    maxMessagesPerSecond: 25,
    maxRetries: 5,
    initialBackoffMs: 1000,
    maxBackoffMs: 30000,
  });

  await sender.send(123456789n, "hello");

  expect(callCount).toBe(2); // exactly one retry: attempt 1 (429), attempt 2 (200)
  expect(sendMessageCalls.length).toBe(2); // the underlying Telegram-call level: 2
  // attempts total, but the RECIPIENT only ever receives ONE delivered message —
  // attempt 1 never reached "delivered" (it 429'd), attempt 2 is the one and only
  // successful delivery. There is no code path here that could deliver twice for
  // one logical sender.send(...) call.
});
```

- Pass condition: `sender.send(...)` resolves (does not throw) after exactly 2 underlying
  `sendMessage` calls; the retry uses `parameters.retry_after` (here `0`, chosen only to
  keep the test fast — a nonzero value, e.g. `1`, is equally valid and TEST-RUNNER may
  substitute it to also observe the actual wait, at the cost of a slower test run).
- A second `it(...)` in the same block confirms **exhaustion**: a transformer that always
  returns the 429 shape (never a 200) causes `sender.send(...)` to **reject** after
  exactly `maxRetries` attempts (`callCount === maxRetries` at the point of rejection,
  using a small `maxRetries: 2` config to keep the test fast) — confirming §5's
  "exhaustion" row propagates as a rejection rather than resolving silently or retrying
  forever.
- A third `it(...)` confirms **non-429 errors are not retried**: a transformer returning
  `{ ok: false, error_code: 403, description: "Forbidden: bot was blocked by the user" }`
  on the first call causes `sender.send(...)` to reject immediately with `callCount === 1`
  — proving a non-429 failure propagates as a single attempt's failure rather than being
  retried per §5's "Non-429 errors" row.
- **Failure mode this catches:** a retry loop that does not actually distinguish 429 from
  other errors (retrying everything, or retrying nothing) — cases 1–3 together pin down
  all three of §5's distinct behaviors (retry-and-succeed, retry-until-exhausted,
  don't-retry-at-all) rather than only the happy path.

## Concurrent-call race — two simultaneous calls to `sendLedgeredNotification` for the
SAME `(registrationId, kind)`, committed as permanent regression coverage

**Why this belongs here even though SECURITY-REVIEWER and REVIEWER already verified this
ad hoc:** both gates' sign-off (per this run's own task brief) traced the race at two
granularities, including across two separate DB connection pools — but neither committed
a test, so nothing today would catch a regression here. This is a core correctness
property (S9's actual threat model is exactly "two overlapping attempts to send the same
notification," not only "two sequential attempts across a restart," which AC1 already
covers) and deserves the same permanent coverage AC1 gets.

```ts
it("two concurrent calls for the same (registrationId, kind) result in exactly one send", async () => {
  const { userId, registrationId } = await seedRegistration(db, nextTgId++, { blocked: false });
  const { sender, sentTo } = makeFakeSender();

  const callOnce = () =>
    sendLedgeredNotification({
      db,
      sender,
      registrationId,
      kind: "admission_result",
      classification: "transactional",
      userId,
      composeMessage: () => "concurrent test",
    });

  // Two genuinely concurrent calls — issued without awaiting between them, so both
  // reach step 1's user lookup and race toward step 4's INSERT before either has
  // committed, exercising the DB's own row-level uniqueness enforcement rather than
  // any in-process sequencing this test's own code might accidentally impose.
  const [outcomeA, outcomeB] = await Promise.all([callOnce(), callOnce()]);

  const outcomes = [outcomeA.kind, outcomeB.kind].sort();
  expect(outcomes).toEqual(["sent", "skipped-already-sent"]);
  expect(sentTo.length).toBe(1); // the recipient was messaged exactly once, not twice
  const ledgerRows = await db
    .select()
    .from(schema.notificationLedger)
    .where(
      and(
        eq(schema.notificationLedger.registrationId, registrationId),
        eq(schema.notificationLedger.kind, "admission_result"),
      ),
    );
  expect(ledgerRows.length).toBe(1); // the DB constraint, not application code, is what
  // resolved the race — exactly one row survives regardless of which call's INSERT
  // physically committed first.
});
```

**Second granularity — two separate DB connection pools**, matching the task brief's
description of what SECURITY-REVIEWER already traced ad hoc, now committed:
```ts
it("two concurrent calls from two SEPARATE connection pools still result in exactly one send", async () => {
  const { userId, registrationId } = await seedRegistration(db, nextTgId++, { blocked: false });
  const poolB = new Pool({ connectionString: TEST_DATABASE_URL });
  const dbB = drizzle(poolB, { schema });
  const { sender: senderA, sentTo: sentToA } = makeFakeSender();
  const { sender: senderB, sentTo: sentToB } = makeFakeSender();

  const [outcomeA, outcomeB] = await Promise.all([
    sendLedgeredNotification({
      db, sender: senderA, registrationId, kind: "waitlist_promotion",
      classification: "transactional", userId, composeMessage: () => "pool A",
    }),
    sendLedgeredNotification({
      db: dbB, sender: senderB, registrationId, kind: "waitlist_promotion",
      classification: "transactional", userId, composeMessage: () => "pool B",
    }),
  ]);
  await poolB.end();

  const outcomes = [outcomeA.kind, outcomeB.kind].sort();
  expect(outcomes).toEqual(["sent", "skipped-already-sent"]);
  expect(sentToA.length + sentToB.length).toBe(1);
});
```

**Pass conditions (both cases):** exactly one `"sent"` and one `"skipped-already-sent"`
among the two outcomes (never `"sent"`/`"sent"`, and never a `"failed"` from an
unhandled, non-23505 error — if either outcome is `"failed"`, the case fails and the
`error` field must be inspected: an unhandled error here would mean `isUniqueViolation`'s
error-code detection missed a real duplicate-key error shape); exactly one `sentTo` entry
total across both calls; exactly one `notification_ledger` row for the pair.
**Failure mode this catches:** a check-then-insert race (e.g. "does a ledger row already
exist? if not, insert" as two separate statements instead of one atomic `INSERT` relying
on the constraint itself) would let both concurrent calls pass the "does it exist" read
before either commits its insert, producing two `"sent"` outcomes and two real sends —
exactly the double-delivery this requirement exists to prevent. The two-pool variant
additionally rules out a bug that accidentally relied on same-connection/same-transaction
locking rather than the constraint itself.
