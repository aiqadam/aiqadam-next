# REQ-009 — Verification spec: apps/bot workspace skeleton (grammY, Drizzle, Vitest)

**Requirement:** docs/agents/requirements.yaml REQ-009.
**Format note:** REQ-009 has no rendered page, no route/viewport/theme — its surface is
build/CI/process behavior. Per docs/agents/decisions/0006-test-framework-vitest.md, a
case verifying a genuine function-of-code-behavior property (AC4, part of AC5) points to
runnable Vitest code; a case verifying a build/CI/process-level property that isn't
unit-testable logic (AC1, AC2, AC3, the process-exit half of AC5, AC6) is a precise
scripted checklist of exact commands and exact expected output, per
docs/guides/qa_testing_guide.md §3's "precise enough to run without judgment" bar. Each
case below states which kind it is and why.

All commands assume the repo root as the working directory and a shell where `grep`,
`node`, and `git` are on PATH (Git Bash on this machine). Where a step requires a
temporary edit to a committed file, the revert step is mandatory and is part of the case
— a case that leaves the repo dirty has not passed.

---

## AC1 — "apps/bot/package.json exists as a workspace member and `npm install` at the
repo root resolves both apps/web and apps/bot without error; `npm run lint` and
`npm run build` from the repo root both exit 0 and cover apps/bot (verified by
deliberately introducing a type error in apps/bot/src and confirming `npm run build`
then FAILS, then reverting — a build that passes without ever compiling apps/bot is not
evidence)."

**Kind:** scripted checklist (build-pipeline coverage is a process property, not a unit
of code behavior).

**Case AC1.1 — baseline install/build/lint pass**
- Commands:
  ```bash
  npm install; echo "INSTALL_EXIT:$?"
  npm run build; echo "BUILD_EXIT:$?"
  npm run lint; echo "LINT_EXIT:$?"
  ```
- Expected: all three `EXIT` lines read `0`. `npm run build`'s output contains a `tsc`
  invocation (or its output) for both `apps/web` and `apps/bot` — confirmed by the
  presence of the `apps/bot` workspace name in the npm workspace-run banner lines (npm
  prints `> bot@...` / `> apps/bot` per-workspace headers when running
  `-w apps/web -w apps/bot`).

**Case AC1.2 — deliberate break proves apps/bot is actually compiled**
- Step 1: Edit `apps/bot/src/index.ts`. Immediately after the existing
  `import { loadConfig } from "./config.js";` line, insert one new line:
  ```ts
  const req009TypeErrorCheck: number = "not-a-number";
  ```
- Step 2: Run:
  ```bash
  npm run build; echo "BUILD_EXIT:$?"
  ```
- Expected: `BUILD_EXIT` is non-zero, and the output contains a TypeScript diagnostic
  naming `apps/bot/src/index.ts`, error code `TS2322`, and text matching
  `Type 'string' is not assignable to type 'number'`.
- Step 3 (revert, mandatory): remove the inserted line so `apps/bot/src/index.ts`
  matches its committed state exactly:
  ```bash
  git checkout -- apps/bot/src/index.ts
  git diff --stat apps/bot/src/index.ts
  ```
  Expected: the `git diff --stat` line prints nothing (no output) — confirms exact
  revert.
- Step 4: Run again:
  ```bash
  npm run build; echo "BUILD_EXIT:$?"
  ```
  Expected: `BUILD_EXIT` is `0`, matching Case AC1.1's baseline.

**This case fails if:** the build is 0 in Step 2 (would mean apps/bot's `tsc` project is
not actually part of the root `npm run build`), or the file is not restored to its
original content afterward.

## AC2 — "apps/bot/package.json depends on `grammy`, `drizzle-orm`, `drizzle-kit` and a
Postgres driver, and the repo root depends on `vitest` — every one pinned to an exact
version (no `^` or `~`)... A dependency on `telegraf`, `prisma`/`@prisma/client` or
`jest` is a FAIL, as is any grammY plugin added at this stage; separately, no test file
may import `node:test`."

**Kind:** scripted checklist (a package.json literal and a grep are not unit-testable
code behavior).

**Case AC2.1 — required dependencies pinned exactly**
- Command:
  ```bash
  grep -n '"grammy"\|"drizzle-orm"\|"drizzle-kit"\|"pg"' apps/bot/package.json
  grep -n '"vitest"' package.json
  ```
- Expected exact matches (line content, whitespace aside):
  - `"grammy": "1.46.0",`
  - `"drizzle-orm": "0.45.2",`
  - `"pg": "8.23.0",` (the Postgres driver)
  - `"drizzle-kit": "0.31.10",`
  - `"vitest": "5.0.0"` (root `package.json`)
- Expected additionally: none of the five matched lines contains a `^` or `~` character
  before the version number — confirm by eye on the grep output; a version string like
  `"^1.46.0"` fails this case.

**Case AC2.2 — forbidden dependencies absent**
- Command:
  ```bash
  grep -n '"telegraf"\|"prisma"\|"@prisma/client"\|"jest"' package.json apps/bot/package.json apps/web/package.json
  ```
- Expected: no output (grep finds zero matches across all three files).

**Case AC2.3 — no grammY plugin added at this stage**
- Command:
  ```bash
  grep -n '@grammyjs/' apps/bot/package.json
  ```
- Expected: no output (zero matches — no `@grammyjs/conversations`,
  `@grammyjs/session`, `@grammyjs/runner`, `@grammyjs/ratelimiter`, or any other
  `@grammyjs/*` plugin).

**Case AC2.4 — no test file imports the `node:test` built-in**
- Command:
  ```bash
  grep -rln "node:test" apps/bot/src apps/web/src 2>/dev/null
  ```
- Expected: no output (zero matching files) — every test in this repo runs on Vitest's
  own `describe`/`it`/`expect` (imported from `"vitest"`), never Node's built-in test
  runner.

**This case fails if:** any grep in AC2.2/AC2.3/AC2.4 produces output, or any version in
AC2.1 does not match the exact pinned string (including a `^`/`~` prefix appearing).

## AC3 — ".github/workflows/ci-cd.yml runs `npm test` in the build job, and a
deliberately failing test makes the workflow fail (verified by pushing a failing
assertion on a scratch branch and reading the actual red run, then reverting — a test
step that cannot fail the build is not a gate...)."

**Kind:** scripted checklist. A genuine red GitHub Actions run is the criterion's literal
text, but per this task's framing a full remote CI round-trip is expensive to spec as a
mandatory case here — the case below specifies the decisive **local** equivalent (does
`npm test`'s own exit code actually go non-zero on a real failing assertion, and does the
workflow file actually invoke that same command in the `build` job before any deploy
step) — and then states the residual gap explicitly rather than silently treating the
local proxy as if it were the remote check.

**Case AC3.1 — CI workflow actually wires `npm test` into the build job, before Build**
- Command:
  ```bash
  grep -n -B2 -A2 "npm test" .github/workflows/ci-cd.yml
  ```
- Expected output (line numbers may shift slightly, content must not):
  ```
  - name: Lint
    run: npm run lint
  - name: Test
    run: npm test
  - name: Build
    run: npm run build
  ```
  confirming the `Test` step exists inside the `build:` job, runs `npm test` verbatim,
  and sits between `Lint` and `Build` — i.e. before the Docker image build step, so a
  failing test blocks everything after it in that job.

**Case AC3.2 — local proxy: `npm test`'s exit code is actually decisive on a real failure**
- Step 1 (baseline): 
  ```bash
  npm test; echo "TEST_EXIT:$?"
  ```
  Expected: `TEST_EXIT:0`, and the Vitest summary reports `Tests  5 passed (5)`.
- Step 2: Edit `apps/bot/src/config.test.ts` line 7, changing:
  ```ts
  expect(config).toEqual({ botToken: "t", databaseUrl: "d" });
  ```
  to:
  ```ts
  expect(config).toEqual({ botToken: "WRONG", databaseUrl: "d" });
  ```
- Step 3:
  ```bash
  npm test; echo "TEST_EXIT:$?"
  ```
  Expected: `TEST_EXIT` is non-zero (Vitest's own `run` mode exit code), the summary
  reports `1 failed`, `4 passed`, and the failure output names the specific test
  `"returns the config when both required variables are present"` with an assertion
  diff showing expected `"WRONG"` vs. received `"t"`.
- Step 4 (revert, mandatory):
  ```bash
  git checkout -- apps/bot/src/config.test.ts
  git diff --stat apps/bot/src/config.test.ts
  ```
  Expected: the `git diff --stat` line prints nothing.
- Step 5:
  ```bash
  npm test; echo "TEST_EXIT:$?"
  ```
  Expected: `TEST_EXIT:0` again, `Tests  5 passed (5)`, matching Step 1.

**Explicit residual gap — state this in the test report verbatim, do not silently drop
it:** no agent in this run has pushed a failing commit to a scratch branch and observed
an actual red `build` job on GitHub Actions. Case AC3.1 (static file content) plus Case
AC3.2 (local exit-code behavior of the exact command CI invokes) together are strong
circumstantial evidence the gate works, but they are not the same event as watching CI
itself turn red. **This is a named residual gap for RELEASE-VALIDATOR to explicitly
decide** — accept the local-equivalent evidence as sufficient for REQ-009 sign-off, or
require an actual scratch-branch red run before marking REQ-009 done. TEST-RUNNER must
not resolve this itself either way; it reports Case AC3.1/AC3.2's real results and
carries this paragraph forward into its report.

## AC4 — "`npm test` at the repo root runs Vitest and reports at least one passing
assertion against REAL behaviour — the skeleton's environment-variable validation is the
intended target. An assertion such as `expect(true).toBe(true)` is a FAIL of this
criterion."

**Kind:** points to existing Vitest code — `apps/bot/src/config.test.ts` — plus a
command and an exact-shape expected output.

**Case AC4.1 — run the suite, confirm shape**
- Command:
  ```bash
  npm test
  ```
- Expected exact shape in the Vitest summary:
  - `Test Files  1 passed (1)`
  - `Tests  5 passed (5)`
  - process exit code `0`

**Case AC4.2 — confirm none of the 5 assertions is a placeholder**
Read `apps/bot/src/config.test.ts` directly (not from a summary) and confirm each `it`
block's real target:
1. `"returns the config when both required variables are present"` — asserts
   `loadConfig({ BOT_TOKEN: "t", DATABASE_URL: "d" })` returns exactly
   `{ botToken: "t", databaseUrl: "d" }` — real target: the env-to-config mapping is
   correct, not just "didn't throw".
2. `"throws naming the missing variable when BOT_TOKEN is absent"` — asserts the thrown
   error's message matches `/BOT_TOKEN/` — real target: the specific missing-variable
   name appears.
3. `"throws naming the missing variable when DATABASE_URL is absent"` — asserts the
   thrown message matches `/DATABASE_URL/` — same real target, other variable.
4. `"throws naming both variables when neither is present"` — asserts the thrown
   message matches `/BOT_TOKEN.*DATABASE_URL/` — real target: both names appear, and in
   the stated order.
5. `"never includes the value of a present variable in the thrown message"` — asserts
   that a real present value (`"super-secret-token-value"`) does NOT appear anywhere in
   the thrown message — real target: the security property this project cares about
   (S11), not just the happy path.
- Expected: all 5 confirmed present with the targets above, matching exactly what is
  read in the file — no assertion reduces to a tautology (`expect(true).toBe(true)` or
  equivalent) anywhere in the file (confirm by reading the whole 30-line file, it is
  short enough to read in full).

**This case fails if:** the summary in AC4.1 does not read `5 passed (5)` with exit 0,
or reading the file in AC4.2 finds any assertion whose target is not one of the five
above (e.g. a `.toBeDefined()` with no behavioral content, or `expect(true).toBe(true)`).

## AC5 — "Starting apps/bot with the bot-token environment variable unset exits non-zero
and prints a message naming the missing variable; starting it with the variable set to a
dummy value does NOT print that value anywhere in stdout/stderr (security-invariants.md
S11), verified by running both cases and grepping the captured output for the dummy
value."

**Kind:** scripted checklist — process stdout/stderr behavior under real environment
variables is not a unit-testable property in the Vitest sense (it requires actually
spawning the built process), even though `config.test.ts`'s AC4/AC5-overlapping unit
assertions (case 2/3/4/5 above) already cover the pure-function half of this criterion.
This case covers the actual process, end to end.

Pre-requisite: `apps/bot/dist/index.js` must exist and be current —
```bash
npm run build -w apps/bot
```

**Case AC5.1 — missing BOT_TOKEN exits non-zero, names the variable**
- Command (BOT_TOKEN deliberately absent, DATABASE_URL present so only one variable is
  missing — isolates the "names the missing one" behavior):
  ```bash
  DATABASE_URL="postgres://dummy:dummy@localhost:5432/dummy" node apps/bot/dist/index.js; echo "EXIT_CODE:$?"
  ```
- Expected: stderr contains exactly
  `Missing required environment variable(s): BOT_TOKEN` and the printed line reads
  `EXIT_CODE:1`.

**Case AC5.2 — dummy value never appears in stdout/stderr**
- Command (spawns the built process with a clearly-synthetic token value, captures
  combined stdout+stderr for 4 seconds, then kills it — the bot process would otherwise
  run forever trying to long-poll Telegram, so a bounded capture is required):
  ```bash
  node -e "
  const { spawn } = require('node:child_process');
  const child = spawn(process.execPath, ['apps/bot/dist/index.js'], {
    env: { ...process.env, BOT_TOKEN: 'DUMMY_TOKEN_VALUE_12345', DATABASE_URL: 'postgres://dummy:dummy@localhost:5432/dummy' }
  });
  let out = '';
  child.stdout.on('data', (d) => { out += d; });
  child.stderr.on('data', (d) => { out += d; });
  setTimeout(() => { child.kill(); process.stdout.write(out); process.exit(0); }, 4000);
  " > req009-ac5b-capture.txt
  cat req009-ac5b-capture.txt
  grep -c "DUMMY_TOKEN_VALUE_12345" req009-ac5b-capture.txt
  ```
- Expected: the captured output contains the line `bot starting` (proving config
  validation passed and execution reached past `loadConfig`), and the final
  `grep -c` line prints `0` (the dummy token value appears zero times anywhere in
  stdout or stderr).
- Cleanup: delete the scratch capture file after reading it —
  ```bash
  rm -f req009-ac5b-capture.txt
  ```

**This case fails if:** Case AC5.1's exit code is `0` or its stderr does not name
`BOT_TOKEN`, or Case AC5.2's `grep -c` prints anything other than `0`.

## AC6 — "`git grep -n` over apps/bot finds no committed bot token, database password,
or connection string literal — every such value comes from `process.env`."

**Kind:** scripted checklist.

**Case AC6.1 — no Telegram-bot-token-shaped literal committed**
- Command (Telegram bot tokens have the shape `<7-10 digit id>:<35-char alphanumeric>`):
  ```bash
  git grep -n -E "[0-9]{6,10}:[A-Za-z0-9_-]{30,40}" -- apps/bot
  ```
- Expected: no output (zero matches).

**Case AC6.2 — no Postgres connection-string-with-credentials literal committed**
- Command:
  ```bash
  git grep -n -E "postgres(ql)?://[^\"'[:space:]]+:[^\"'[:space:]]+@" -- apps/bot
  ```
- Expected: no output (zero matches).

**Case AC6.3 — positive confirmation values are sourced from the environment**
- Command:
  ```bash
  git grep -n "process.env" -- apps/bot/src
  ```
- Expected: matches only inside `apps/bot/src/config.ts` (reading `env.BOT_TOKEN` /
  `env.DATABASE_URL` from its `NodeJS.ProcessEnv` parameter counts as the same source —
  `config.ts` is the sole place credentials are read) and `apps/bot/src/index.ts`
  (passing `process.env` into `loadConfig`). No match should appear assigning a literal
  string directly to a variable named `token`, `botToken`, `databaseUrl`, `password`, or
  `connectionString` outside of test fixtures.

**Note on `config.test.ts`'s fixture values** (`"t"`, `"d"`,
`"super-secret-token-value"`): these are synthetic Vitest fixtures, not real secrets —
confirm none of them matches the token-shape or connection-string-shape patterns in
AC6.1/AC6.2 (they don't, by construction: `"super-secret-token-value"` contains no colon
followed by digits, and `"t"`/`"d"` are single characters). State this explicitly in the
test report rather than silently excluding `config.test.ts` from the grep — the grep
already covers it and correctly reports zero matches there.

**This case fails if:** AC6.1 or AC6.2 produces any output, or AC6.3 finds a
`process.env` read anywhere outside `config.ts`/`index.ts`, or a literal credential-like
assignment anywhere in `apps/bot` outside a test fixture.
