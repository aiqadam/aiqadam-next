# Test Spec — REQ-008: Repoint Dockerfile/deploy compose files/CI at apps/web

**Scope test:** IN SCOPE for the full Step 3/3b/4 procedure. This requirement has a
concrete runnable behavioral surface — a Docker image that must build and an HTTP server
inside it that must respond correctly at specific routes with specific content. It is not
a docs-only requirement.

**Environment assumption:** all commands run from the repo root, on branch
`feature/WF02-REQ-008`, with Docker available and host port `3120` free. If `3120` is
already bound on the host, TEST-RUNNER must free it or fail the run and report which
process holds it — do not silently substitute a different host port, since AC2's literal
command uses `-p 3120:3120`.

Per `docs/agents/design/REQ-008.md` §0/§1: no diff is expected to `Dockerfile`,
`deploy/docker-compose.qa.yml`, `deploy/docker-compose.prod.yml`, or
`.github/workflows/ci-cd.yml` for this requirement — the actual code change is the root
`.dockerignore` added in Step 2 (fixing a host `node_modules` leak into the build
context). Case 5 below exists specifically to verify that fix held.

---

## AC1 — `docker build -t aiqadam-next:req008 .` from repo root exits 0

**Command:**
```
docker build -t aiqadam-next:req008 .
```

**Expected:**
- Exit code: `0`.
- Build output shows both stages completing (`FROM node:22.14.0-alpine AS builder` and
  `AS runtime` stages both run to completion) with no `ERROR` lines.
- No manual judgment: a non-zero exit code from the `docker build` process itself is a
  FAIL, regardless of how far the build progressed.

---

## AC2 — Container serves 200 at `/health` and renders `/ru`, `/uz`, `/en`, `/kk` with matching `<html lang>`

**Step 1 — start the container:**
```
docker run --rm -d --name req008-ac2 -e PORT=3120 -p 3120:3120 aiqadam-next:req008
```
Wait for the container to be ready before curling: poll
`docker inspect -f "{{.State.Running}}" req008-ac2` is `true`, then retry the `/health`
curl below every 1s for up to 20s until it returns `200` (Next.js's production server
typically becomes ready within a few seconds; do not treat an early connection-refused as
a failure until the 20s budget is exhausted).

**Step 2 — health check:**
```
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3120/health
```
Expected: `200` exactly.

```
curl -s http://127.0.0.1:3120/health
```
Expected: response body is JSON containing `"status":"ok"` (exact route source:
`apps/web/src/app/health/route.ts` returns `{ status: "ok", service: "aiqadam-next" }`
with HTTP 200).

**Step 3 — locale routes, one curl per locale, checking both HTTP status and the
`<html lang="...">` attribute in the returned HTML body:**

```
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3120/ru
curl -s http://127.0.0.1:3120/ru | grep -o '<html[^>]*lang="[a-z]*"'
```
Expected: status `200`; grep output contains `lang="ru"`.

```
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3120/uz
curl -s http://127.0.0.1:3120/uz | grep -o '<html[^>]*lang="[a-z]*"'
```
Expected: status `200`; grep output contains `lang="uz"`.

```
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3120/en
curl -s http://127.0.0.1:3120/en | grep -o '<html[^>]*lang="[a-z]*"'
```
Expected: status `200`; grep output contains `lang="en"`.

```
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3120/kk
curl -s http://127.0.0.1:3120/kk | grep -o '<html[^>]*lang="[a-z]*"'
```
Expected: status `200`; grep output contains `lang="kk"`.

This is the full locale set declared in `apps/web/src/i18n/routing.ts`
(`locales: ["ru", "uz", "en", "kk"]`) — all four must be checked; checking a subset does
not satisfy this AC. Each locale's expected `lang` value must match that specific route
(a `lang="ru"` returned for `/kk` is a FAIL, not a partial pass) — this is what would
catch a locale-routing/middleware regression, not just "the server responds."

**Step 4 — teardown:**
```
docker stop req008-ac2
```
(container was started with `--rm`, so it is removed automatically on stop; no separate
`docker rm` needed.)

**FAIL conditions:** any curl returns a non-200 status; `/health`'s body lacks
`"status":"ok"`; any locale route's `<html lang>` value doesn't match its own locale code;
the container fails to become ready within the 20s poll budget (report the container logs
via `docker logs req008-ac2` before it is torn down).

## AC3 — `docker compose ... config` parses and resolves the repo-root Dockerfile

**Command:**
```
docker compose -p aiqadam-next-qa -f deploy/docker-compose.qa.yml config
```

**Expected:**
- Exit code: `0`.
- The rendered YAML output's `services.web.build` block must show:
  - `context:` resolving to the repo root's absolute path (i.e. the parent directory of
    `deploy/` — `docker compose config` expands `context: ..` to the absolute filesystem
    path of the repo root; confirm the printed path is the repo root, not `deploy/`
    itself and not a `.` relative value).
  - `dockerfile: Dockerfile` present under that same `build` block.
- Also confirm the output includes `PORT: "3120"` under `services.web.environment` — this
  is what makes AC3 meaningfully connected to AC2's port rather than a check of unrelated
  compose fields.

**FAIL conditions:** non-zero exit code; any YAML parse error printed to stderr; the
resolved `context` path does not end at the repo root (e.g. still shows a relative `..`
un-expanded, or resolves to `deploy/` itself); `dockerfile` field missing or pointing
anywhere other than `Dockerfile`.

## AC4 — `deploy/deploy.sh` is unchanged

**Command:**
```
git diff --stat origin/master -- deploy/deploy.sh
```

**Expected:** empty output (no lines printed at all) — proving zero modification to this
file on this branch relative to `master`.

**FAIL condition:** any output at all (even a single changed line) is a FAIL. If
`origin/master` is stale in the local checkout, run `git fetch origin master` first, then
re-run the diff against `origin/master`.

## Case 5 (regression check — the actual Step 2 fix, not a separate AC but load-bearing
for AC1/AC2)

**What this catches:** Step 2's design doc (`docs/agents/design/REQ-008.md` §3) flagged
that the npm-workspaces symlink `node_modules/app -> ../apps/web` is the one load-bearing
assumption AC1/AC2 depend on, and that a naive `docker build` run from a host machine with
its own local `node_modules/` present (and no `.dockerignore`) will silently let the
host's copy of `node_modules` (with a Windows-absolute or otherwise-broken `app` symlink)
overwrite the correct Linux-relative symlink `npm ci` created inside the container — a
regression that would NOT necessarily crash the health-route hot path, making it exactly
the kind of failure that "the container started and /health returned 200" would miss. This
case exists specifically to catch that regression if `.dockerignore` were ever removed or
narrowed.

**Command (run against the same image built in AC1 — no separate build needed if AC1's
image `aiqadam-next:req008` is still present):**
```
docker run --rm aiqadam-next:req008 sh -c "readlink /app/node_modules/app"
```

**Expected:** output is exactly `../apps/web`.

**FAIL conditions:** command exits non-zero (no such symlink, or `readlink` reports it
isn't a symlink); output is any value other than `../apps/web` (e.g. an absolute Windows
path, empty output, or a broken/dangling target). A FAIL here means `.dockerignore` (or
equivalent build-context exclusion) is missing or insufficient, and this run must be
reworked, not silently accepted because AC2's HTTP checks happened to still pass.

| AC1 | `docker build` exit-code check | Yes — any non-zero exit or build error fails it |
| AC2 | `/health` status+body, all 4 locale routes' status+`<html lang>` | Yes — any wrong status code or mismatched `lang` value fails it |

result is an exact exit code, exact string/substring, or exact command output.
