# Test Spec — REQ-004 (replace every placeholder in messages/en.json with real English copy)

Source requirement (from `handoffs/WF02-REQ003-REQ004/step-09-test-designer.json`
`context.requirement_text.REQ-004`, and the fuller acceptance criteria carried on
`handoffs/WF02-REQ003-REQ004/step-07-content-ba.json`):

> CONTENT-BA wrote real English copy for all 177 keys in `messages/en.json` (previously
> Russian-duplicated placeholders from REQ-003). REVIEWER PASSed. Acceptance criteria:
> (1) every key has a non-empty, translated value, except where a key's value consists
> solely of an untranslatable literal — event/date codes, country/role/brand names,
> URLs, numeric values, or proper product names — which are permitted to match
> `ru.json` verbatim; (2) no Cyrillic characters anywhere in `messages/en.json`; (3)
> domain vocabulary (Event, Chapter, Talk, Speaker, CFP, Agenda, Check-in, Going,
> Watching) appears verbatim with no synonym substitution; (4) status-label keys
> (`Streams.stream{N}Status`, `MapSection.chapter{N}Status`) hold plain lowercase
> English values; (5) no exclamation marks, slogans, or emoji anywhere in
> `messages/en.json`.

Scope test result: this requirement has real user-visible surface (rendered English
copy across all 12 landing sections, on the public `/en` route added by REQ-003) —
continuing to the full procedure per WF-02 Step 3. Not routed to RELEASE-VALIDATOR
directly.

This spec follows the same structure as `docs/agents/test-specs/REQ-002.md` (the
analogous Uzbek-translation spec): script-based key/value/Cyrillic/punctuation checks
plus a rendered-page content-completeness check. Component under test has no light/dark
theme split relevant to this requirement's own change — REQ-004 changes text content
sourced from a translation catalog, not styling — so most cases below have no theme
dimension; the one exception is AC6 (content-completeness), which follows
`docs/guides/qa_testing_guide.md` §5 and checks both themes to also catch anything that
only reveals missing content when a theme-dependent element is visible, matching
`docs/agents/test-specs/REQ-003.md` AC6's precedent.

All commands below assume the repo root as the working directory and were run against
the current state of `messages/ru.json` / `messages/en.json` on branch
`feature/WF02-REQ003-REQ004` (177 keys each). AC6's curl checks assume the app is
running on `localhost:3000` (`npm run build && npm run start`, matching
`docs/agents/test-specs/REQ-003.md`'s port convention for this same branch); every
command's "Expected" output below is the actual output observed during spec authoring,
not a guess.

## AC1 — Every key has a non-empty, translated value, except stated untranslatable literals

- Route: N/A (static file check)
- Viewport: N/A
- Theme: N/A
- Steps: run the following from the repo root:
  ```
  node -e "
  const ru = require('./messages/ru.json');
  const en = require('./messages/en.json');
  function keys(obj, prefix=''){let out=[];for(const k in obj){const p=prefix?prefix+'.'+k:k; if(typeof obj[k]==='object'&&obj[k]!==null) out=out.concat(keys(obj[k],p)); else out.push(p);} return out;}
  const rk = keys(ru).sort();
  let identical = [];
  let empty = [];
  for (const k of rk) {
    const rv = k.split('.').reduce((o,p)=>o[p], ru);
    const ev = k.split('.').reduce((o,p)=>o[p], en);
    if (typeof ev !== 'string' || ev.trim() === '') empty.push(k);
    if (rv === ev) identical.push(k);
  }
  console.log('total_keys:', rk.length);
  console.log('empty_en_values:', JSON.stringify(empty));
  console.log('identical_value_pairs:', JSON.stringify(identical));
  "
  ```
- Expected: output is exactly three lines:
  ```
  total_keys: 177
  empty_en_values: []
  identical_value_pairs: ["Events.talk1Role","Events.talk2Role","Events.talk3Role","Events.talk4Role","Footer.contactsTelegram","Footer.hashtag","Hero.eyebrow","Hero.nextEventWhatBold","Hero.pillKazakhstan","Hero.pillUzbekistan","Metrics.metric1Source","Metrics.metric3Label","Streams.foundationLink","Streams.foundationTitle","Team.team1Role","Team.team2Role","Team.team3Role","Team.team4Role"]
  ```
  `empty_en_values` must be `[]` — any entry is an unconditional FAIL (an empty/blank
  value, regardless of the untranslatable-literal exception).

  `identical_value_pairs` listing exactly the 18 keys above is a PASS, **not** a FAIL —
  every one of the 18 is a standalone untranslatable literal that is legitimately
  identical across locales (verified by inspecting each value directly):
  - Country/role codes rendered as-is: `Events.talk1Role`–`talk4Role` (`"UZ"`,
    `"UZ · BEELAB"`, `"UAE · SAIDE"`, `"UZ · EPAM"`), `Hero.pillKazakhstan`
    (`"KAZAKHSTAN"`), `Hero.pillUzbekistan` (`"UZBEKISTAN"`) — English country names
    used as pill labels by design.
  - Already-English job titles: `Team.team1Role` (`"Founder Global"`), `Team.team2Role`
    (`"Country Lead — KZ"`), `Team.team3Role` (`"Co-founder"`), `Team.team4Role`
    (`"Board"`) — English org-title conventions used identically in the source.
  - Brand/contact literals: `Footer.contactsTelegram` (`"Telegram · @RETURN_VOID_0"`),
    `Footer.hashtag` (`"#AIQadam"`), `Hero.eyebrow` (`"AI Qadam · UZ · KZ · KG · TJ"`),
    `Streams.foundationLink` (`"build.aiqadam.org →"`, a URL), `Streams.foundationTitle`
    (`"AI Qadam Build"`, a proper product name), `Hero.nextEventWhatBold`
    (`"Fail Stories #1"`, a proper event name).
  - A numeric value and an acronym: `Metrics.metric1Source` (`"158 + 142"`),
    `Metrics.metric3Label` (`"NPS"`, an internationally-used acronym).

  Any key appearing in `identical_value_pairs` that is **not** one of these 18 is a FAIL

  rather than translated (the failure mode REQ-004 exists to close). This matches the
  count independently confirmed by REVIEWER at
  `handoffs/WF02-REQ003-REQ004/step-08-reviewer.json` ("exactly 18 identical values").

## AC3 — Domain vocabulary appears verbatim, no synonym substitution

Domain vocabulary set (per `docs/guides/content_ba_guide.md` §4 and this run's own
domain-vocabulary decision recorded on
`handoffs/WF02-REQ003-REQ004/step-07-content-ba.json`): Event, Chapter, Talk, Speaker,
CFP, Agenda, Check-in, Going, Watching.

- Route: N/A (static file check)
- Viewport: N/A
- Theme: N/A
- Steps: run the following from the repo root:
  ```
  node -e "
  const en = require('./messages/en.json');
  function leaves(obj, prefix) {
    let out = [];
    for (const k of Object.keys(obj)) {
      const p = prefix ? prefix + '.' + k : k;
      if (obj[k] && typeof obj[k] === 'object' && !Array.isArray(obj[k])) out = out.concat(leaves(obj[k], p));
      else out.push([p, obj[k]]);
    }
    return out;
  }
  const all = leaves(en, '');
  const terms = ['Event','Chapter','Talk','Speaker','CFP','Agenda','Check-in','Going','Watching'];
  for (const t of terms) {
    const re = new RegExp(t, 'gi');
    let count = 0;
    for (const [,v] of all) { const m = String(v).match(re); if (m) count += m.length; }
    console.log(t + '_count=' + count);
  }
  console.log('nav_events=' + JSON.stringify(en.Nav.events));
  console.log('nav_chapters=' + JSON.stringify(en.Nav.chapters));
  console.log('events_eyebrow=' + JSON.stringify(en.Events.eyebrow));
  console.log('creed_principle2Body=' + JSON.stringify(en.Creed.principle2Body));
  console.log('band_lede=' + JSON.stringify(en.Band.lede));
  console.log('doors_door2Body=' + JSON.stringify(en.Doors.door2Body));
  console.log('mapsection_ctaLaunchChapter=' + JSON.stringify(en.MapSection.ctaLaunchChapter));
  console.log('mapsection_nodeAlmatySub=' + JSON.stringify(en.MapSection.nodeAlmatySub));
  "
  ```
- Expected: output is exactly these 17 lines:
  ```
  Event_count=16
  Chapter_count=17
  Talk_count=22
  Speaker_count=1
  CFP_count=2
  Agenda_count=0
  Check-in_count=0
  Going_count=1
  Watching_count=0
  nav_events="Events"
  nav_chapters="Chapters"
  events_eyebrow="Events"
  creed_principle2Body="Speakers talk about what they did themselves. A real case beats a polished framework."
  band_lede="Next event — August 26. Next meetup — September, CFP is open."
  doors_door2Body="CFP for meetup #3 in September is open. We need your own case — what you did, what broke, what worked."
  mapsection_ctaLaunchChapter="Launch a chapter in your city"
  mapsection_nodeAlmatySub="KZ CHAPTER · SINCE 06.20.2026"
  ```
  `Agenda_count=0`, `Check-in_count=0`, and `Watching_count=0` are PASS conditions, not
  failures — those three terms are not present in this content's scope (matching
  CONTENT-BA's own note: "Check-in/Agenda/Going/Watching are not present in this
  content's scope, so no forced insertion" — `Going_count=1` refers to the generic verb

  vocabulary-substitution concern). The specific-value checks confirm:
  - `Nav.events`/`Events.eyebrow` render exactly `"Events"` (Title Case nav-label
    convention), not a synonym like "Meetups" or "Sessions".
  - `Nav.chapters`/`MapSection.ctaLaunchChapter` use "Chapter(s)" verbatim, not
    "Region"/"Branch".
  - `Creed.principle2Body` uses "Speakers" verbatim, not "Presenters"/"Panelists".
  - `Band.lede`/`Doors.door2Body` use "CFP" verbatim (unexpanded acronym, matching
    `ru.json`'s own usage), not "call for papers" spelled out or "submissions".
  A FAIL is any case where a value in the file uses a synonym in place of one of the
  nine domain terms in a context where the term is domain-specific (e.g. "Session" where
  a Talk is meant, "Sign-up" where Check-in is meant) — none was found in this content.

## AC5 — No exclamation marks, slogans, or emoji anywhere in messages/en.json

This AC is checked in three parts: (a) exclamation marks, (b) emoji, (c) slogan
spot-check.

- Route: N/A (static file check)
- Steps: `grep -n "!" messages/en.json`
- Expected: no output; `grep` exits `1` (no match found). Any printed line, or exit code
  `0`, is a FAIL.

### 5b — No emoji (common emoji Unicode ranges)

- Route: N/A (static file check)
- Steps: run the following from the repo root (a `node` script, for the same
  UTF-8/locale reason as AC2 — `grep -P` with a Unicode range fails on this shell):
  ```
  node -e "
  const fs = require('fs');
  const content = fs.readFileSync('messages/en.json', 'utf8');
  const emoji = /[\u{1F300}-\u{1FAFF}\u{2600}-\u{26FF}\u{2700}-\u{27BF}\u{2B00}-\u{2BFF}\u{1F000}-\u{1F0FF}\u{1F100}-\u{1F1FF}\u{1F200}-\u{1F2FF}\u{FE0F}]/gu;
  const matches = content.match(emoji);
  console.log('emoji_matches:', matches ? matches.length : 0);
  console.log('matched_chars:', matches ? JSON.stringify([...new Set(matches)]) : '[]');
  "
  ```
  Note: the plain typographic arrow `→` (U+2192) appears 10 times in `en.json` as a UI
  navigation affordance, not an emoji. It falls in the general Unicode Arrows block
  (U+2190–U+21FF), which this scan deliberately excludes to avoid a false positive —
  only the actual pictographic/dingbat/symbol emoji blocks are scanned.
- Expected: output is exactly two lines:
  ```
  emoji_matches: 0
  matched_chars: []
  ```
  Any count greater than 0 is a FAIL.

`messages/en.json`, reads as a marketing slogan (exclamatory, hype-driven, or
sales-oriented tone) rather than plain functional/factual copy, per
`docs/guides/content_ba_guide.md` §2's voice principles (no hype, functional
operator-facing tone).

- Route: N/A (manual read of the file)
- Steps: read `messages/en.json` in full, focusing on `title`, `lede`, `ctaPrimary`,
  `ctaSecondary`, and `cta` keys across all 12 sections.
- Expected: every such value is a plain declarative or imperative statement (e.g.
