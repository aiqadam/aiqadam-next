## AC3 — at-capacity add requires confirmation; confirming writes exactly one `audit_log` row; dismissing creates no registration

Two new `it(...)`s, own fixture (own names/phones, own capacity-1 event, distinct from
BACKEND-DEV's "First Person"/"Second Person"):

**Override-confirm case:**

- Seed one chapter, one organizer. Seed one published event (`capacity: 1`).
- Fill the seat: `/walkin <eventId> Bota Suleimenova|Nomad Labs|+77011112222`, then tap
  Confirm — admits, fills capacity.
- Second walk-in: `/walkin <eventId> Ruslan Abenov|Steppe Analytics|+77022223333`, tap
  Confirm.
- **Pass conditions (before the override tap):**
  1. The edited message (the reply to the Confirm tap) is the override-offer message
     (design §7.2) — its text contains the literal placeholder pattern for
     `overridePrompt`'s interpolated numbers (`"1"` admitted, `"1"` capacity — assert both
     substrings present) and its `reply_markup` has exactly one button with
     `callback_data === "walkin:override:" + eventId`.
  2. `registrations` has **zero** rows for Ruslan Abenov's resolved `userId` at this
     point.
  3. `users`/`profiles` **do** already carry a row for Ruslan Abenov at this point
     (design §6.2 step 7 / Open Question 3 — the resolve-or-create step already ran and
     committed before the capacity check was reached).
- Tap the override-confirm button (`walkin:override:<eventId>`, using the override-offer
  message's own text).
- **Pass conditions (after the override tap):**
  1. `registrations` now has exactly one row for Ruslan Abenov: `admission = 'admitted'`,
     `checkedInAt` not null, `checkInMethod = 'manual'`.
  2. Exactly one `audit_log` row for that registration's id with
     `action = 'registration.walkin_override_admit'`.
  3. `payload.previousAdmission` on that row is `null` (this registration row was freshly
     inserted, never existed with a prior admission value).

**Dismiss case, separate fixture (own capacity-1 event, own names):**

- Seed one chapter, one organizer. Seed one published event (`capacity: 1`).
- Fill the seat with one walk-in exactly as above (own name, e.g. "Damir Zhaksybekov").
- Second walk-in: `/walkin <eventId> Aliya Mamedova|Aral Systems|+77033334444`, tap
  Confirm → reaches the override-offer message. Tap `walkin:cancel` (the Dismiss button)
  using the override-offer message's own text.
- **Pass conditions:**
  1. `registrations` has zero rows for Aliya Mamedova's resolved `userId`.
  2. **Zero** `audit_log` rows anywhere with `action` in
     `('registration.walkin_admit', 'registration.walkin_override_admit')` referencing
     Aliya Mamedova's `userId` — not just "zero registration rows," a direct query of
     `audit_log` itself.
  3. The final reply's text equals `getCatalog("ru").walkin.cancelled`.
- **Failure mode this catches:** (override-confirm case) a regression collapsing the
  two-step override into a single write, or omitting the audit row, or mislabeling
  `previousAdmission`; (dismiss case) a regression where `walkin:cancel`'s shared handler
  is accidentally wired to call `commitWalkin` for the override-offer's Dismiss button
  specifically (since it is visually a different button from the initial Cancel, a
  copy-paste error routing it through the override tap's own callback pattern instead of
  the shared no-op handler would create a registration and/or an audit row that only an
  `audit_log` query, not a registration-count check, would catch).

## AC4 — adding an existing person (phone match) reuses existing rows, no duplicates

New `it(...)`, own fixture — own two-differently-formatted-phone-numbers pair, distinct
from BACKEND-DEV's `"+998 90 111-22-33"` / `"+998901112233"`:

- Seed one chapter, one organizer. Seed two published events ("Event Alpha", "Event
  Beta", `capacity: 10` each).
- **Fixture phones, chosen to collide under a pure digit-strip** (design §3.2: every
  non-digit character removed, digit order preserved) — first walk-in phone
  `"+77074445566"` (strips to `"77074445566"`), second walk-in phone
  `"7 707 444-55-66"` (strips to `"77074445566"`) — same digit string, different visible
  formatting (a leading `+` plus no separators, vs. no leading `+` plus spaces/a dash),
  independent of BACKEND-DEV's own chosen pair (`"+998 90 111-22-33"` /
  `"+998901112233"`).
- First walk-in against Event Alpha: `/walkin <eventAlphaId> Nurbek Aitmatov|Jibek Joly
  Trading|+77074445566`, tap Confirm.
- Snapshot `users`/`profiles` row counts and the created profile's `company` value
  (`"Jibek Joly Trading"`).
- Second walk-in against Event Beta, same physical number in the second format above:
  `/walkin <eventBetaId> Nurbek A. (door typo)|Wrong Co Name|7 707 444-55-66`, tap
  Confirm.
- **Pass conditions:**
  1. `users`/`profiles` row counts are unchanged from the snapshot — the second walk-in's
     phone normalizes to the same digit string as the first, so `getUserIdByPhone` finds
     the existing row and no new `User`/`Profile` is created.
  2. The stored profile's `company` is still `"Jibek Joly Trading"` (the first walk-in's
     value) — the second walk-in's `"Wrong Co Name"` is never written, confirming design
     §6.2 step 3's "no write to `users`/`profiles` on a phone match" rule with an
     independent fixture from BACKEND-DEV's own identical assertion.
  3. Exactly 2 `registrations` rows exist for this person's `userId` — one per event —
     both `admission = 'admitted'`.
- **Failure mode this catches:** a regression in `normalizePhoneForMatching` (e.g. an
  accidental length check, or a comparison of raw strings instead of stripped digits) or
  in `getUserIdByPhone`'s SQL-side digit-strip expression that stops recognizing two
  differently-formatted representations of the same number as a match, silently creating
  a duplicate `User`/`Profile` pair — the specific bug AC4 exists to prevent.

## AC5 — phone appears in no log line, no `audit_log` payload

New `it(...)` plus one static check, own fixture (own phone value, distinct from
BACKEND-DEV's `"+998912345678"`):

**Dynamic check (own fixture):**

- Seed one chapter, one organizer. Seed one published event (`capacity: 10`).
- `/walkin <eventId> Saltanat Yerbolova|Tengri Soft|+996700998877`, tap Confirm.
- **Pass conditions:**
  1. Every `audit_log` row whose `entityId` matches the created registration's id: (a)
     `JSON.stringify(payload)` does not contain the literal substring `"+996700998877"`;
     (b) `Object.keys(payload)` does not include `"phone"`, under any casing.
  2. Re-run the identical two assertions for the **override-admit** path in the same
     test: fill the event to capacity first with a second, own walk-in, then use a third
     walk-in with its own phone (`"+996700111222"`) that requires an override tap —
     confirming the `registration.walkin_override_admit` audit row's payload is equally
     clean, since design §6.2 step 9's payload shape is shared by both audit actions and
     BACKEND-DEV's own AC5 case only exercises the plain-admit path.
- **Why this is the correct dynamic check, not a log-capture harness:** direct reads of
  `domain/walkin.ts` and `handlers/walkin.ts` (done for this spec) confirm **zero** calls
  to `log.debug`/`log.info`/`log.warn`/`log.error`/`console.*` exist anywhere in either
  file — nothing in this flow logs anything at all, successful or refused. A runtime
  test that spies on `console.log`/`log.ts`'s exports and asserts "the captured output
  contains no phone" would be **vacuously true** regardless of whether the flow logged
  anything, since it never calls the logger — this is exactly the "a check with nothing
  real to fail against" pattern to avoid. The genuine, fail-able assertion for "no log
  line ever carries the phone" in this specific flow is therefore the **static** check
  below, not a dynamic one.

**Static check (source-level, run once, not per-fixture):**

- `git grep -n "log\.\(debug\|info\|warn\|error\)\|console\.\(log\|warn\|error\)" apps/bot/src/domain/walkin.ts apps/bot/src/handlers/walkin.ts` — expected to return **zero
  matches**. This is the actual proof that S11 cannot be violated by this flow today (no
  logging call exists to leak through), and it is also the check that would **fail** the
  moment someone adds a `log.info("walkin committed", { phone: args.phone })`-style call
  in a future change to this flow — the real failure mode this AC guards against.
- Run as a TEST-RUNNER Step 4 action alongside the vitest run, not as a vitest `it(...)`
  itself (a `git grep` assertion, same treatment REQ-029's AC7 check received).

New `it(...)`, own fixture, no existing coverage:

- Seed two chapters, Chapter A and Chapter B. Seed one organizer for Chapter A only
  (`role: "organizer"`, `chapterId: <Chapter A's id>`).
- Seed one organizer for Chapter B (`chapterB-organizer`) and, as that user, run the
  legitimate flow: `/walkin <eventUnderChapterB> Zarina Bekturova|Tashkent Robotics|
  +998887776655`, capturing the bot's own confirm-message reply text and the button's
  `callback_data` (`"walkin:confirm:" + eventUnderChapterBId`).
- Now dispatch a `callbackUpdate` using **Chapter A's organizer's own `tgId`**, the
  **same** `callback_data` and the **same** message text captured above — simulating that
  message reaching (by any means: a forward that preserves buttons is not ordinarily
  possible in Telegram, but a shared screen, a leaked deep link replicating the same
  callback, or simply testing the authorization boundary directly) a user who was never
  the one this message was addressed to.
- **Pass conditions:**
  1. `ctx.answerCallbackQuery`'s payload: `show_alert: true`,
     `text === getCatalog("ru").walkin.notAuthorized`.
  2. `registrations` has zero rows for Zarina Bekturova's resolved `userId`.
  3. `users`/`profiles` row counts for Zarina Bekturova are whatever the legitimate first
     half of the flow already produced (design §6.2 step 3 runs only inside
     `commitWalkin`, which this forged tap never reaches) — assert specifically that no
     **second** `users`/`profiles` row was created by the forged tap (count before the
     forged tap === count after).
  4. Zero `audit_log` rows of any `registration.walkin_*` action reference Zarina
     Bekturova's `userId`.

  anything derived from the message's own content or the mere existence of a working
  button — rather than re-deriving authorization fresh, at tap time, from the **tapping**
  user's own role/chapter against the event's real `chapterId` read from `callback_data`
  (design §8.2 step 4, mirroring REQ-028 §3.3/REQ-029 §4.3's "the tap is the action,
  re-authorize on the action" discipline). Because `eventId` in this flow always comes
  from `callback_data` and never from re-parsed message text (design §7.1's "the
  authoritative `eventId` for every write always comes from the tapped button's

  re-authorization call is identical in shape at the override tap (§8.3 inherits §8.2
  steps 1-5 verbatim), this single case against the confirm tap is sufficient to prove
  the property for both taps — a second, structurally identical case against
  `walkin:override:` would exercise the same `requireOrganizerForChapter` call against
  the same authorization function with no different code path to catch a distinct bug.

## Malformed/corrupted message text — `parseWalkinMessageFields` failing cleanly, never crashing, never writing

New `it(...)`, own fixture, no existing coverage:

- Seed one chapter, one organizer. Seed one published event (`capacity: 10`).
- Run the legitimate command once to obtain a real, valid `callback_data`
  (`"walkin:confirm:" + eventId`) — but construct the callback update's `message.text`
  as a **corrupted** string missing the `"Phone: "` line entirely (e.g. `"Event: Test\nName: Someone\nCompany: —"` — no fourth line at all), simulating a client-side edit,
  a truncated message, or any scenario where the live message's content no longer
  matches the canonical format design §7.1 requires.
- Dispatch the confirm callback with this corrupted text.
- **Pass conditions:**
  1. The call does not throw — `bot.handleUpdate()` resolves normally.
  2. `ctx.answerCallbackQuery`'s payload: `show_alert: true`,
     `text === getCatalog("ru").walkin.staleMessage`.
  3. `registrations` row count is unchanged from immediately before the dispatch.
  4. `users`/`profiles` row counts are unchanged from immediately before the dispatch —
     `commitWalkin` (and therefore its own resolve-or-create step, §6.2 step 3) is never
     reached at all, since `parseWalkinMessageFields` fails before `commitWalkin` is ever
     called (design §8.2 step 5 precedes step 6).
- Repeat the same shape with the `"Name: "` line missing instead, in the same test (a
  second, cheap assertion, not a second seeded fixture) — confirms the `{ ok: false }`
  branch triggers on **any** of the three missing prefixes, not only the one exercised
  above.
- **Failure mode this catches:** a regression in `parseWalkinMessageFields` that throws
  on malformed input instead of returning `{ ok: false }` (an unhandled exception would
  surface as a 500-equivalent crash of the update handler rather than a clean, logged
  refusal), or one that silently defaults a missing field to `""` and proceeds into
  `commitWalkin` anyway — writing a registration from corrupted, no-longer-organizer-
  visually-confirmed data, which is precisely what the design's re-parse-from-canonical-
  format mechanism (§1.1) exists to prevent.
