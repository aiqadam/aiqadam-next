# Test Spec — REQ-002 (replace every placeholder in messages/uz.json with real Uzbek translations)

Source requirement (from `handoffs/WF02-REQ-002/step-05-test-designer.json`
`context.requirement_text.REQ-002`):

> Replace every placeholder in `messages/uz.json` with real Uzbek translations.
> Acceptance criteria: (1) every key has a non-empty value not byte-identical to
> ru.json's corresponding value, except standalone domain-vocabulary terms (none found
> in this catalog); (2) no Cyrillic characters anywhere in `messages/uz.json`; (3)
> status-label-shaped values render correctly per the design's casing convention
> (confirmed CSS-driven uppercase, so lowercase JSON values are correct); (4) no
> exclamation marks, slogans, or emoji anywhere in `messages/uz.json`.

Scope test result: this requirement has real user-visible surface (rendered Uzbek copy
across all 12 landing sections, on the public `/uz` route) — continuing to the full
procedure per WF-02 Step 3. Not routed to RELEASE-VALIDATOR directly.

Component under test has no light/dark theme split relevant to this requirement — this
requirement changes text content sourced from a translation catalog, not styling.
**Theme-checking does not apply to this spec.** No case below has a theme dimension.

This spec follows the structure established by `docs/agents/test-specs/REQ-001b.md`
(regex sweeps + key-diff scripts + curl/grep spot checks + a clean build), but where
REQ-001b verified *mechanism* correctness (copy actually routed through next-intl at
all), this spec verifies *translation-content* correctness (the uz.json values are real
Uzbek, not leftover Russian/placeholder text, and contain no residual Cyrillic,
punctuation, or emoji artifacts).

All commands below assume the repo root as the working directory and were run against
the current state of `messages/ru.json` / `messages/uz.json` on branch
`feature/WF02-REQ-002` (177 keys each). AC4's curl checks assume the app is running on
`localhost:3100` (`npm run build && npm run start -- -p 3100`); every command's
"Expected" output below is the actual output observed during spec authoring, not a
guess.

## AC1 — Every key has a non-empty value not byte-identical to ru.json's corresponding value, except standalone domain-vocabulary terms

- Route: N/A (static file check)
- Viewport: N/A
- Theme: N/A
- Steps: run the following from the repo root:
  ```
  node -e "
  const ru = require('./messages/ru.json');
  const uz = require('./messages/uz.json');
  function keys(obj, prefix=''){let out=[];for(const k in obj){const p=prefix?prefix+'.'+k:k; if(typeof obj[k]==='object'&&obj[k]!==null) out=out.concat(keys(obj[k],p)); else out.push(p);} return out;}
  const rk = keys(ru).sort();
  let identical = [];
  let empty = [];
  for (const k of rk) {
    const rv = k.split('.').reduce((o,p)=>o[p], ru);
    const uv = k.split('.').reduce((o,p)=>o[p], uz);
    if (typeof uv !== 'string' || uv.trim() === '') empty.push(k);
    if (rv === uv) identical.push(k);
  }
  console.log('total_keys:', rk.length);
  console.log('empty_uz_values:', JSON.stringify(empty));
  console.log('identical_value_pairs:', JSON.stringify(identical));
  "
  ```
- Expected: output is exactly three lines:
  ```
  total_keys: 177
  empty_uz_values: []
  identical_value_pairs: ["Events.tabFailStories","Events.tabMeetup1","Events.tabMeetup2","Events.talk1Role","Events.talk2Role","Events.talk3Role","Events.talk4Role","Footer.contactsTelegram","Footer.hashtag","Hero.eyebrow","Hero.nextEventWhatBold","Hero.pillKazakhstan","Hero.pillUzbekistan","Metrics.metric1Source","Metrics.metric3Label","Streams.foundationLink","Streams.foundationTitle","Team.team1Role","Team.team2Role","Team.team3Role","Team.team4Role"]
  ```
  `empty_uz_values` must be `[]` — any entry is an unconditional FAIL (an empty/blank
  value, regardless of the domain-vocabulary exception).

  `identical_value_pairs` listing exactly the 21 keys above is a PASS, **not** a FAIL —
  every one of the 21 is a standalone domain-vocabulary term that is legitimately
  identical across locales (verified by inspecting each value directly):
  - Event/date codes and tags with no translatable content: `Events.tabFailStories`
    (`"FAIL STORIES · 26.08.2026"`), `Events.tabMeetup1` (`"MEETUP #1 · 25.04.2026"`),
    `Events.tabMeetup2` (`"MEETUP #2 · 20.06.2026"`), `Hero.nextEventWhatBold`
    (`"Fail Stories #1"`, a proper event name).
  - Country/company/role codes rendered as-is: `Events.talk1Role`–`talk4Role`
    (`"UZ"`, `"UZ · BEELAB"`, `"UAE · SAIDE"`, `"UZ · EPAM"`), `Hero.pillKazakhstan`
    (`"KAZAKHSTAN"`), `Hero.pillUzbekistan` (`"UZBEKISTAN"`) — English country names used
    as pill labels by design, `Team.team1Role`–`team4Role` (`"Founder Global"`,
    `"Country Lead — KZ"`, `"Co-founder"`, `"Board"` — English org-title conventions used
    identically across this bilingual team's bios in both locales).
  - Brand/contact literals: `Footer.contactsTelegram` (`"Telegram · @RETURN_VOID_0"`),
    `Footer.hashtag` (`"#AIQadam"`), `Hero.eyebrow` (`"AI Qadam · UZ · KZ · KG · TJ"`),
    `Streams.foundationLink` (`"build.aiqadam.org →"`, a URL), `Streams.foundationTitle`
    (`"AI Qadam Build"`, a proper product name).
  - A numeric/acronym metric: `Metrics.metric1Source` (`"158 + 142"`), `Metrics.metric3Label`
    (`"NPS"`, an internationally-used acronym).

  Any key appearing in `identical_value_pairs` that is **not** one of these 21 is a FAIL
  — it means a real translatable string was left as a Russian copy-paste rather than
  translated (the failure mode REQ-002 exists to close).

## AC2 — No Cyrillic characters anywhere in messages/uz.json

- Route: N/A (static file check)
- Viewport: N/A
- Theme: N/A
- Steps: run the following from the repo root:
  ```
  node -e "
  const fs = require('fs');
  const content = fs.readFileSync('messages/uz.json', 'utf8');
  const cyr = /[Ѐ-ӿ]/g;
  const matches = content.match(cyr);
  console.log('cyrillic_matches:', matches ? matches.length : 0);
  console.log('matched_chars:', matches ? JSON.stringify([...new Set(matches)]) : '[]');
  "
  ```
  (Same rationale as REQ-001b AC1: `grep -P` with a Unicode range is not usable in this
  shell — `grep: -P supports only unibyte and UTF-8 locales`, exit 2 — so the check is a
  `node` script that reads the file as UTF-8 directly.)
- Expected: output is exactly two lines:
  ```
  cyrillic_matches: 0
  matched_chars: []
  ```
  Any count greater than 0, or a non-empty `matched_chars` array, is a FAIL — it means at
  least one uz.json value still contains a raw Cyrillic character (a leftover
  Russian/placeholder fragment).

## AC3 — Status-label-shaped values render correctly per the design's casing convention (CSS-driven uppercase; lowercase JSON values are correct)

- Route: N/A (static source check), then `/uz` (rendered check)
- Viewport: N/A
- Theme: N/A
- Steps (source confirmation — verifies the CSS rule this AC depends on actually
  exists and is unconditional, not locale-specific):
  ```
  grep -n "text-transform" src/app/globals.css
  ```
- Expected: output includes the line (line number may shift, content must match):
  ```
  152:.status{font-family:var(--mono);font-size:10px;letter-spacing:.12em;text-transform:uppercase;
  ```
  The `.status` selector must include `text-transform:uppercase` unconditionally (not
  inside a `:lang(ru)`/`:lang(uz)`-scoped block) — confirming casing is applied uniformly
  by CSS regardless of locale, so a lowercase value in `uz.json` is not a defect.

- Steps (rendered check, app running on `localhost:3100`):
  ```
  curl -s http://localhost:3100/uz | grep -o -E '<span class="status[^"]*"[^>]*>[a-z '"'"']+</span>'
  ```
- Expected: output is exactly these 8 lines (order as rendered — `MapSection`'s 4
  chapter statuses followed by `Streams`' 4 stream statuses):
  ```
  <span class="status live">faol</span>
  <span class="status live">faol</span>
  <span class="status">rejalashtirilgan</span>
  <span class="status">rejalashtirilgan</span>
  <span class="status live" style="align-self:flex-start">ishlaydi</span>
  <span class="status prog" style="align-self:flex-start">ishlanmoqda</span>
  <span class="status" style="align-self:flex-start">rejalashtirilgan</span>
  <span class="status" style="align-self:flex-start">rejalashtirilgan</span>
  ```
  Each value is the raw lowercase Uzbek word (`faol` = "active", `rejalashtirilgan` =
  "planned", `ishlaydi` = "works", `ishlanmoqda` = "in progress") from
  `MapSection.chapter{1..4}Status` and `Streams.stream{1..4}Status` in `messages/uz.json`
  — lowercase in the HTML source is the PASS condition (the browser renders it uppercase
  via the CSS rule confirmed above). A value already uppercase in the JSON/HTML (e.g.
  `FAOL`), or any status span missing from this list, is a FAIL — the former means the
  translator second-guessed the CSS convention and hardcoded casing, which would produce
  double-uppercased or mismatched-transform text; the latter means a status value didn't
  render.

## AC4 — No exclamation marks, slogans, or emoji anywhere in messages/uz.json

This AC is checked in two parts: (a) exclamation marks, (b) emoji.

### 4a — No exclamation marks

- Route: N/A (static file check)
- Steps: `grep -n "!" messages/uz.json`
- Expected: no output; `grep` exits `1` (no match found). Any printed line, or exit code
  `0`, is a FAIL.

### 4b — No emoji (common emoji Unicode ranges)

- Route: N/A (static file check)
- Steps: run the following from the repo root (a `node` script, for the same
  UTF-8/locale reason as AC2 — `grep -P` with a Unicode range fails on this shell):
  ```
  node -e "
  const fs = require('fs');
  const content = fs.readFileSync('messages/uz.json', 'utf8');
  const emoji = /[\u{1F300}-\u{1FAFF}\u{2600}-\u{26FF}\u{2700}-\u{27BF}\u{2B00}-\u{2BFF}\u{1F000}-\u{1F0FF}\u{1F100}-\u{1F1FF}\u{1F200}-\u{1F2FF}\u{FE0F}]/gu;
  const matches = content.match(emoji);
  console.log('emoji_matches:', matches ? matches.length : 0);
  console.log('matched_chars:', matches ? JSON.stringify([...new Set(matches)]) : '[]');
  "
  ```
  Note: the plain typographic arrow `→` (U+2192) appears 9 times in `uz.json` (matching
  9 occurrences in `ru.json`, e.g. `Doors.door1LinkUzbekistan`, `Streams.foundationLink`)
  as a UI navigation affordance, not an emoji. It falls in the general Unicode Arrows
  block (U+2190–U+21FF), which this scan deliberately excludes to avoid a false
  positive — only the actual pictographic/dingbat/symbol emoji blocks are scanned.
- Expected: output is exactly two lines:
  ```
  emoji_matches: 0
  matched_chars: []
  ```
  Any count greater than 0 is a FAIL.

- Companion check (slogans/exclamatory tone spot-check, since "slogan" isn't
  mechanically detectable by regex): manually confirm none of the 21 identical-value
  keys from AC1 and no value adjacent to them reads as a marketing slogan rather than
  plain label text. All 21 are event codes, country/role codes, or brand literals (see
  AC1's breakdown) — none is a slogan. No further action needed; this is a documentation
  cross-reference, not a new command.

## AC6 (supporting check) — `/uz` renders with real Uzbek strings and no next-intl error markers

Not one of REQ-002's 4 numbered acceptance criteria on its own, but required by the
handoff's task description as direct evidence that the translated catalog actually
renders correctly in the browser, not just passes static file checks. Checked in two
parts: (a) no next-intl error markers, (b) spot checks of real Uzbek strings spanning
four different namespaces.

With the app running on `localhost:3100` (`npm run build && npm run start -- -p 3100`):

### 6a — No next-intl error markers on `/uz`

- Route: `/uz`
- Steps: `curl -s http://localhost:3100/uz | grep -o -E "MISSING_MESSAGE|IntlError"`
- Expected: no output; `grep` exits `1` (no match found). Any printed `MISSING_MESSAGE`
  or `IntlError` substring, or exit code `0`, is a FAIL.

- Route: `/ru` (control — confirms the check methodology itself is sound and that `/ru`
  was not broken by this change)
- Steps: `curl -s http://localhost:3100/ru | grep -o -E "MISSING_MESSAGE|IntlError"`
- Expected: no output; `grep` exits `1`.

### 6b — Spot checks: four real Uzbek strings spanning four different namespaces

Values below were read directly from the current `messages/uz.json` (not guessed).

- Route: `/uz`, namespace `Nav.events`
- Steps: `curl -s http://localhost:3100/uz | grep -o '<a href="#events"[^>]*>[^<]*</a>'`
- Expected: exactly `<a href="#events">Tadbirlar</a>` (`Nav.events` = `"Tadbirlar"`,
  Uzbek for "Events" — confirms the top-nav link resolves to real translated text, not
  the Russian `"События"` or an empty string).

- Route: `/uz`, namespace `Hero.title` (`t.rich()` emphasis case)
- Steps:
  `curl -s http://localhost:3100/uz | grep -o '<h1 class="rv">.*birgalikda\.</em></h1>'`
- Expected: exactly
  `<h1 class="rv">Markaziy Osiyoda AI quradigan muhandislar — <em>birgalikda.</em></h1>`
  (`Hero.title`, rendered via `t.rich("title", { em: (chunks) => <em>{chunks}</em> })` in
  `src/components/landing/Hero.tsx` — confirms both that the translated Uzbek text
  renders and that the `t.rich()` emphasis wrapper still produces a real `<em>` element,
  not escaped markup, for the Uzbek value specifically).

- Route: `/uz`, namespace `Doors.door1Title`
- Steps: `curl -s http://localhost:3100/uz | grep -o '<h3>Kelish</h3>'`
- Expected: exactly `<h3>Kelish</h3>` (`Doors.door1Title` = `"Kelish"`, Uzbek for
  "Come"/"Attend" — confirms a `Doors` card title resolves to real Uzbek, not the
  Russian `"Прийти"`).

- Route: `/uz`, namespace `Footer.about`
- Steps:
  `curl -s http://localhost:3100/uz | grep -o '<p style="[^"]*">Markaziy Osiyo muhandislarining notijorat hamjamiyati\. Brend hamjamiyatga tegishli\.</p>'`
- Expected: exactly
  `<p style="margin:0;max-width:34ch">Markaziy Osiyo muhandislarining notijorat hamjamiyati. Brend hamjamiyatga tegishli.</p>`
  (`Footer.about`, translated from Russian `"Некоммерческое сообщество инженеров
  Центральной Азии. Бренд принадлежит сообществу."` — confirms the Footer's about text
  resolves to real Uzbek. Note: an unanchored `grep -o` for this string alone would
  double-match, because the same text also appears verbatim inside the page's embedded
  RSC data payload later in the same HTML response — anchoring the pattern to the
  rendered `<p style="...">` wrapper, as above, restricts the match to the one real
  DOM element and avoids that false duplicate.)

- Route: `/uz`
- Steps: `curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3100/uz`
- Expected: exactly `200`.
