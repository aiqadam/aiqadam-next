# REQ-018 — Verification spec: EventStaff assignment and the staff-only
check-in surface gate

**Scope test:** Step 2's `artifacts_out` (`apps/bot/src/domain/{eventStaff,eventStaffAuthorization}.ts`
new, `apps/bot/src/domain/user.ts` extended, `apps/bot/src/handlers/{staff,checkin}.ts` new,
`apps/bot/src/i18n/{types,ru,en}.ts` new `staff.*`/`checkin.*` keys, `apps/bot/src/index.ts`)
is real user-visible/behavioral surface — three new live Telegram commands
(`/staff_add`, `/staff_remove`, `/checkin`) that write/delete real `event_staff` rows,
write real `audit_log` rows, and send real notification messages against real
`events`/`users`/`event_staff`/`audit_log` rows. Full Steps 3b/4 apply.

**Independence note.** BACKEND-DEV already wrote `apps/bot/src/domain/eventStaff.test.ts`
(pure-function coverage of `parseStaffCommandArgs`) and
`apps/bot/src/domain/eventStaffAuthorization.test.ts` (pure-predicate coverage of
`checkEventStaffAuthorization` — including AC1's structural shape, AC3's boundary at
exactly `endsAt`, and the "no role short-circuit" property — plus `buildCheckinRefusalAudit`'s
per-reason payload shape from the SECURITY-REVIEWER S5 rework). Those are real,
already-passing, and this spec does not duplicate them wholesale — TEST-RUNNER is told
exactly which existing tests to re-run as part of AC1/AC3/AC7 below. What this spec adds
is coverage of the parts **no unit test exercises at all**, because both existing test
files call pure functions directly with hand-built arguments, never through a live
handler or a live database:

- `getEventStaffRow`/`addEventStaff`/`removeEventStaff` against a real `event_staff`
  table (the INSERT/DELETE + exactly-one-audit-row transaction shape, AC5)
- `getUserByTgUsername` against a real `users` table (the new `domain/user.ts` addition)
- `requireEventStaffForEvent`'s live composition — `resolveActingUser` →
  `getEventStaffRow` → `checkEventStaffAuthorization` → (on refusal)
  `writeAuditLog` — actually producing an `audit_log` row on every refusal branch
  (AC7, the security-driven addition)
- `/staff_add`/`/staff_remove`/`/checkin`'s own handler composition: argument parsing,
  the organizer-gate ordering, the "already assigned"/"not assigned" pre-checks, the
  notification send in the **target's** language (AC4), and the reply composition —
  none of which a pure unit test over hand-built objects can catch (e.g. a handler that
  authorizes with the wrong chapter id, sends the notification in the organizer's
  language instead of the target's, or never actually calls `addEventStaff`/
  `removeEventStaff`)
- `/venue_new` and `/event_publish` actually refusing a live EventStaff-only user end to
  end (AC2) — the unit tests never dispatch through these handlers at all
- i18n catalog parity and command registration (mechanical checks)

**Harness note (read before running any case):** reuses REQ-013/014/015/016/017's
established grammY-dispatch method — a real `grammy.Bot` built with a dummy token +
manually-supplied `botInfo`, `bot.api.config.use()` intercepting outbound calls,
`bot.handleUpdate()` dispatching synthetic `Update` objects through the real command
matchers, against the real fixture Postgres from `apps/bot/docker-compose.yml`. Not
committed as reusable infrastructure — the harness script is written, run, then deleted
at the end of the run.

**`tg_id` range:** `1000000100`+ — distinct from REQ-013/014/015/016/017's ranges, so all
specs can run against the same scratch DB without collision.
