## AC2 judgment call — same-process repeat call, not a genuine two-process harness

**Decision: a same-process repeated-call test is sufficient here; a genuine two-process
kill-restart harness (REQ-025/026's pattern) is not warranted for this requirement.**
Reasoning:

1. **The idempotency primitive itself is unchanged and already has a genuine
   two-process proof.** AC2's guarantee rests entirely on
   `notification_ledger`'s `uq_notification_ledger_registration_kind` unique index and
   `sendLedgeredNotification`'s step 4 atomic `INSERT` (REQ-025 §3.1) — REQ-027 adds no
   new mechanism here, only a new `kind` value (`"event_cancelled"`) flowing through the
   same existing function (confirmed by reading `handlers/event.ts`'s
   `notifyNonWithdrawnRegistrants`, which calls `sendLedgeredNotification` unchanged).
   That exact primitive already has a genuine two-process kill-then-restart proof:
   REQ-025's own AC1 spec (`scratch-verify-req025-p1/p2.ts`, referenced in REQ-026's spec
   as reused unmodified) and REQ-026's AC3 spec (`scratch-verify-req026-p1/p2.ts`,
   `docs/agents/test-specs/REQ-026.md` lines 140-236) both already demonstrate that a
   real process kill between the ledger `INSERT` and any further work, followed by a
   fresh `Pool` in a second OS process, cannot produce a second send for the same
   `(registrationId, kind)` pair. A third repetition of that same two-process harness
   against the same unchanged primitive, only substituting `"event_cancelled"` for
   `"reminder_24h"`, would prove nothing about REQ-027's own new code
   (`selectNonWithdrawnRegistrantsForEvent`, `composeCancellationMessage`,
   `notifyNonWithdrawnRegistrants`) that the existing two proofs don't already establish
   about the shared mechanism underneath it.
2. **REQ-027 has no scheduled/interval re-entry point.** REQ-026's reminder jobs are
   polled on every process boot by `scheduler/runner.ts` and re-select the same
   candidates until each becomes ineligible — that recurring, restart-triggered
   re-invocation is exactly why REQ-026 needed a real process-boundary test (a
   module-level in-memory "already handled" set would survive a single-process re-run
   but not a real process kill). REQ-027's `notifyNonWithdrawnRegistrants` is invoked
   exactly once, synchronously, from inside a single command handler's execution — there
   is no scheduler, no interval, and no code path that re-invokes it automatically after
   a restart. The only way AC2's "twice" scenario occurs in production is an actual
   second `/event_cancel` dispatch or a manual re-run of the batch — both of which a
   same-process repeated call already models faithfully (a fresh `sender`/fresh call,
   same as REVIEWER's own independent AC1/AC2 re-check with fresh fixtures/fresh `Pool`
   per this run's task brief).
3. **SECURITY-REVIEWER's structural finding closes the "double-cancel" half of AC2
   entirely**, per this run's task brief: repeated trigger via the command surface is
   structurally impossible, because `events.status`'s state machine has no path back
   from `'cancelled'` — `makeEventCancelHandler`'s own `event.status !== "published"`
   guard (confirmed by reading `handlers/event.ts`) refuses a second `/event_cancel` on
   an already-cancelled event with `cancelRefusedNotPublished`, before `cancelEvent` or
   `notifyNonWithdrawnRegistrants` is ever reached a second time through that path. The
   only residual scenario AC2 actually needs to cover, then, is "the batch itself is
   invoked twice by some means other than a second command dispatch" (e.g. a crash
   mid-loop and an operator or process manager re-running the same logical batch) — which
   is precisely what a same-process repeated call to `notifyNonWithdrawnRegistrants`
   models, and precisely the scenario the ledger's unique index (not any in-process
   state) is what prevents, per point 1.
4. Where this spec's AC2 case still adds value over BACKEND-DEV's own committed AC2
   case: BACKEND-DEV's case calls `notifyNonWithdrawnRegistrants` directly twice; this
   spec's AC2 case instead dispatches `/event_cancel` once through real
   `bot.handleUpdate()` (proving the full handler chain sends the first batch), and only
   then calls `notifyNonWithdrawnRegistrants` a second time directly to model the
   "batch re-run after the handler already completed" scenario — the same
   real-dispatch-then-repeat shape used nowhere in BACKEND-DEV's file.

If this reasoning is later found insufficient (e.g. a future requirement adds a
scheduled/retriable path into this batch), a genuine two-process harness should be added
then — this is a judgment call about the current design's actual re-entry surface, not a
blanket exemption.

## AC1 — 2 admitted + 5 waitlisted + 2 withdrawn → exactly 7 notifications, none to
either withdrawn registrant, via real `/event_cancel` dispatch

New `it(...)` in the new committed file:

- Seed one chapter, one organizer, one published event with `capacity: 2`.
- Register exactly 9 users in sequence, via `registerForEvent`:
  1. Registrants 1-2 land `admitted` (capacity 2, first-come).
  2. Registrants 3-7 land `waitlisted` (5 registrants, capacity already exhausted).
  3. Registrants 8-9 also land `waitlisted` initially, then are each withdrawn directly
     (via `withdrawRegistration`, setup-only, same usage `event.db.test.ts`'s own
     fixtures already make of it) — becoming the fixture's 2 `withdrawn` rows.
  - Final admission split: **2 admitted, 5 waitlisted, 2 withdrawn** — 7 non-withdrawn
    total, deliberately different from both BACKEND-DEV's committed `3/2/1` case and
    REVIEWER's independent `2/1/3` re-check (per this run's task brief).
- Dispatch `bot.handleUpdate(commandUpdate(organizerTgId, "/event_cancel " + eventId))`
  — a **real** command dispatch through `makeEventCancelHandler`, not a direct call to
  `notifyNonWithdrawnRegistrants`.
- **Pass conditions:**
  1. Exactly 7 `sendMessage` calls captured by `bot.api.config.use` with a chat id
     matching one of the 7 non-withdrawn registrants' `tgId`s — **zero** captured
     `sendMessage` calls to either withdrawn registrant's `tgId`.
  2. Exactly one additional captured `sendMessage`/reply is the organizer's own
     `cancelSuccessPrefix` confirmation (8 total `sendMessage` calls: 7 registrant
     notifications + 1 organizer reply), and it is the **last** captured call
     (confirms the design's stated ordering: `notifyNonWithdrawnRegistrants` completes
     **before** the organizer's own `ctx.reply`).
  3. `notification_ledger` has exactly 7 rows with `kind = 'event_cancelled'`, one per
     non-withdrawn registrant's `registrationId`, and zero rows for either withdrawn
     registrant's `registrationId`.
  4. `events.status` for the event is `'cancelled'`.
- **Failure mode this catches:** an authorization check silently swallowing the cancel
  (regressing the whole chain to a no-op); a `selectNonWithdrawnRegistrantsForEvent`
  filter regression that includes a withdrawn row (`ne` reversed or dropped in
  `domain/registration.ts`); the handler's call-site ordering being swapped so the
  organizer's confirmation goes out before (or interleaved with) the registrant batch,
  which the "last captured call" assertion would catch even if the total count still
  matched.

## AC2 — running the batch a second time (after a real dispatch) adds no messages

New `it(...)` in the new committed file — see "AC2 judgment call" above for why this is
a same-process repeated-call case, not a two-process harness:

- Seed one chapter, one organizer, one published event, `capacity: 5`. Register 3 users
  (all `admitted`, capacity not exhausted).
- Dispatch `bot.handleUpdate(commandUpdate(organizerTgId, "/event_cancel " + eventId))` —
  the **first** run, through the real handler chain (proving the full first batch sends
  correctly, not just that the domain function does).
- **Pass conditions after the first dispatch:** exactly 3 registrant `sendMessage`
  calls plus 1 organizer confirmation (4 total); exactly 3 `notification_ledger` rows
  for `kind = 'event_cancelled'`.
- Then call `notifyNonWithdrawnRegistrants(db, sender2, eventId, title)` directly a
  **second** time, with a fresh `sender2` capturing its own `sent` array (modeling "the
  batch is re-run by some means other than a second command dispatch" — see judgment
  call point 4 above; a second real `/event_cancel` dispatch is not used here because
  the handler's own `event.status !== "published"` guard would refuse it before reaching
  the batch at all, which is a *different*, already-structurally-proven property per
  SECURITY-REVIEWER's finding, not what this case is isolating).
- **Pass conditions after the second call:** `sender2`'s captured `sent` array has
  **zero** entries; `notification_ledger` still has exactly 3 rows for
  `kind = 'event_cancelled'` (no new rows, no duplicates) — counted across both runs,
  never reset between them.
- **Failure mode this catches:** any in-memory "already sent" tracking that would
  reset between calls but happens to survive one repeat in a way that masks the real DB
  constraint being what actually stops the resend; a regression in
  `sendLedgeredNotification`'s duplicate-key handling that lets a second `INSERT` for the
  same `(registrationId, "event_cancelled")` pair either throw uncaught or silently
  double-send instead of resolving to `skipped-already-sent`.

## AC4 — every `registrations` row for the event survives cancellation with `admission`
unchanged, via real dispatch (own before/after comparison)

New `it(...)` in the new committed file:

- Seed one chapter, one organizer, one published event, `capacity: 2`.
- Register 4 users: 2 land `admitted`, 2 land `waitlisted`. Withdraw a 5th registrant's
  registration first (via `withdrawRegistration` directly, setup-only), so the fixture
  has one already-`withdrawn` row present before cancellation too (mirrors AC1's
  "none to withdrawn" concern for AC4's "unchanged" concern as well).
- Read and store the full `registrations` row set for the event (`sortById`, same
  stable-comparison helper shape `event.db.test.ts`'s own AC4 case already uses) —
  **before** cancellation.
- Dispatch `bot.handleUpdate(commandUpdate(organizerTgId, "/event_cancel " + eventId))`.
- Read the full `registrations` row set again — **after** cancellation and the
  notification batch have both completed.
- **Pass conditions:**
  1. Row count unchanged (5 rows, before and after).
  2. `afterSorted` deep-equals `beforeSorted` (every column, every row, byte-for-byte —
     not just `admission`) — this is the stronger form of "unchanged" AC4 actually
     names; a weaker per-field spot check alone could miss an unrelated column (e.g.
     `created_at`, `qr_token`) being silently touched by a regression elsewhere in the
     call chain.
  3. Explicit spot checks by identity: the 2 admitted rows still read `'admitted'`, the
     2 waitlisted rows still read `'waitlisted'`, the pre-existing withdrawn row still
     reads `'withdrawn'`.
  4. `events.status` for the event is `'cancelled'` (the one row this requirement's
     handler chain IS expected to change, confirming the before/after comparison is
     correctly scoped to `registrations` only, not silently passing because nothing
     changed anywhere).
- **Failure mode this catches:** any accidental `UPDATE`/`DELETE` against `registrations`
  introduced anywhere in `selectNonWithdrawnRegistrantsForEvent`,
  `composeCancellationMessage`, or `notifyNonWithdrawnRegistrants` — all three are
  designed to be read-only against `registrations` (§design's AC4 mapping); this
  deep-equality check would catch a regression that a narrower "admission field only"
  check would miss.
