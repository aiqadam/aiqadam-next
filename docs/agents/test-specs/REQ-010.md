# Test spec — REQ-010 (Bot data model and initial migration for Chapter, User, Profile)

## Verification kind: scripted docker/psql checklist (not a Vitest integration test)

**Call:** this spec is a scripted checklist — exact `docker run`/`psql` commands with
exact expected output — not a Vitest test file that spins up its own Postgres container.

**Reasoning:**

- All 6 acceptance criteria are properties of the *migration applied to a real Postgres*
  (nullable-unique behavior, column defaults, NOT NULL enforcement, `\d+` schema shape).
  Per decision `0006-test-framework-vitest.md`, that decision's driving cases are bot
  *logic* that fake timers make testable in-process (state machines, clock-dependent
  predicates). Nothing here is clock-dependent or in-process logic — it is entirely
  "does Postgres itself enforce this constraint," which requires a real running Postgres
  regardless of which tool issues the SQL.
- Writing this as a Vitest integration test would require a reusable
  spin-up-Postgres-in-CI fixture (container lifecycle, port allocation, readiness wait,
  teardown) that does not exist anywhere in this repo yet. REQ-012 (pending, scope read
  directly from `docs/agents/requirements.yaml`) wires a persistent runtime Postgres
  connection and a migration runner for `apps/bot`'s own startup — its acceptance
  criteria are about `npm run migrate` idempotency and env-var validation, not about
  handing TEST-DESIGNER a reusable ephemeral test-database fixture. Building that
  fixture *inside* this one data-model requirement's test design would be inventing new
  test infrastructure silently, which `core-directives.md`'s Instruction Precedence
  section (decision records aren't contradicted casually) and the Zero-Manual-Work
  "don't force-fit new kinds of work into existing roles" rule in `AGENTS.md` both argue
  against doing off-handedly here.
- Both prior pipeline steps (BACKEND-DEV, REVIEWER) already independently verified all 6
  ACs the same way — a throwaway `docker run postgres:16-alpine` container plus `psql`.
  A scripted checklist in the same shape is re-runnable by TEST-RUNNER without asking it
  to invent commands, and keeps this requirement's verification consistent with what has
  already been done twice rather than diverging into a third method.
- **Note on exact command provenance:** `handoffs/WF02-REQ-010/step-02-backend-dev.json`
  and `step-02b-reviewer.json` record prose summaries of what each agent verified
  (e.g. "two NULL tg_id inserts succeeded, duplicate non-null failed on the unique
  constraint") but neither handoff records the literal `docker run`/`psql` command text
  they typed — there is no shell transcript checked in. This spec reconstructs the
  standard scratch-container pattern (`postgres:16-alpine`, a throwaway named container,
  `psql -c` calls) from that description and from `apps/bot/drizzle.config.ts`'s own
  conventions, rather than being able to copy verbatim commands. TEST-RUNNER should run
  the commands exactly as written below; if actual output differs in shape (not
  substance) from "Expected" below, that is expected tool-version drift, not a spec
  defect.

**Open question (not resolved here, flagged for a future decision):** once `apps/bot`
accumulates enough schema-testing volume (REQ-011's eight entities, PRD 12's DB-level
invariants like `UNIQUE(event_id, user_id)`) that every future data-model requirement is
paying this same "spin up a throwaway container by hand" cost, a reusable
Postgres-test-fixture package for `apps/bot` (container lifecycle + readiness wait +
teardown, usable from either a scripted checklist or a real Vitest integration test) is
worth its own requirement or decision record. Not proposed as in-scope here — REQ-010 is
one schema, verified the same way it already was twice.

## AC1 — UUID primary keys and created/updated timestamps on all three tables

> "The migration creates chapters, users and profiles with UUID primary keys and
> created/updated timestamp columns on all three; verified by applying the migration to
> a scratch Postgres database and inspecting the resulting schema (the `\d+` output
> pasted into the verification report)."

- Route: N/A (backend/data, not a rendered page)
- Environment: `req010-pg-verify` container from Shared setup, database `verify`

Steps:
```bash
docker exec req010-pg-verify psql -U postgres -d verify -c '\d+ chapters'
docker exec req010-pg-verify psql -U postgres -d verify -c '\d+ users'
docker exec req010-pg-verify psql -U postgres -d verify -c '\d+ profiles'
```

Expected (all three tables):
- An `id` column: type `uuid`, `not null`, default `gen_random_uuid()`, and listed as the
  table's `"<table>_pkey" PRIMARY KEY, btree (id)` index.
- A `created_at` column: type `timestamp with time zone`, `not null`, default `now()`.
- An `updated_at` column: type `timestamp with time zone`, `not null`, default `now()`.

This case fails if any table's `\d+` output is missing any of the three properties above
on any of the three columns (e.g. `id` not `uuid`, `created_at` nullable, no default on
`updated_at`).

## AC2 — `users.tg_id` is nullable AND unique

> "users.tg_id is nullable AND unique, verified by executing two inserts of users with
> NULL tg_id (both must succeed, proving nullability does not collide on the unique
> index) and one duplicate non-null tg_id insert (must fail) against the scratch
> database — a schema read alone is not sufficient evidence for the null-collision case."

Steps:
```bash
docker exec req010-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (NULL);"
docker exec req010-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (NULL);"
docker exec req010-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (123456789);"
docker exec req010-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (123456789);"
```

Expected:
- First `INSERT ... NULL` → `INSERT 0 1`.
- Second `INSERT ... NULL` → `INSERT 0 1` (this is the case a naive unique index would
  fail — two NULLs must NOT collide; Postgres unique indexes treat NULL as distinct from
  NULL by default, and this case exists specifically to prove the schema relies on that
  default rather than accidentally opting out of it).
- First `INSERT ... 123456789` → `INSERT 0 1`.
- Second `INSERT ... 123456789` → fails with:
  ```
  ERROR:  duplicate key value violates unique constraint "users_tg_id_unique"
  DETAIL:  Key (tg_id)=(123456789) already exists.
  ```

This case fails if either NULL insert errors, or if the duplicate non-null insert
succeeds instead of erroring.

## AC3 — `profiles`' optional columns are nullable at the database level

> "profiles.phone, profiles.email, profiles.public_bio, profiles.photo_file_id and every
> links column are nullable, verified by inserting a profile row supplying only the PRD 5
> required fields (first_name, last_name, company, position, is_student,
> experience_level) and confirming it succeeds (PRD 5 'if nothing uses it, it is
> optional')."

Steps (uses one of the `tg_id=123456789` user rows created in AC2 to satisfy the
`profiles.user_id` foreign key):
```bash
docker exec req010-pg-verify psql -U postgres -d verify -c "INSERT INTO profiles (user_id, first_name, last_name, company, position, is_student, experience_level) SELECT id, 'Test', 'User', 'Acme', 'Engineer', false, 'builder' FROM users WHERE tg_id = 123456789 LIMIT 1;"
docker exec req010-pg-verify psql -U postgres -d verify -c "SELECT phone, email, public_bio, photo_file_id, links_github, links_linkedin, links_site FROM profiles WHERE first_name = 'Test';"
```

Expected:
- The `INSERT` → `INSERT 0 1` (no NOT NULL violation on any omitted column).
- The `SELECT` returns exactly one row with all 7 columns reading back empty/blank
  (SQL NULL, rendered by `psql` as an empty field between `|` separators):
  ```
   phone | email | public_bio | photo_file_id | links_github | links_linkedin | links_site
  -------+-------+------------+---------------+--------------+-----------------+------------
         |       |            |               |              |                 |
  (1 row)
  ```

This case fails if the INSERT errors with a `null value in column "..." violates
not-null constraint` on any of phone/email/company/position/is_student/
experience_level/links_github/links_linkedin/links_site/public_bio/photo_file_id, or if
any of the 7 queried columns reads back non-NULL.

## AC4 — Three consent columns exist in their PRD-specified homes, defaulting to false

> "Three distinct consent columns exist in their PRD-specified homes —
> users.consent_pd_at (timestamp), users.broadcast_opt_in (boolean),
> profiles.publish_consent (boolean) — with broadcast_opt_in and publish_consent both
> DEFAULT FALSE, verified by inserting a row that supplies neither and reading back false
> for both (security-invariants.md S1, S14)."

Steps:
```bash
docker exec req010-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (999999999) RETURNING broadcast_opt_in, consent_pd_at;"
docker exec req010-pg-verify psql -U postgres -d verify -c "SELECT publish_consent FROM profiles WHERE first_name = 'Test';"
```

Expected:
- First command's `RETURNING` row: `broadcast_opt_in` = `f`, `consent_pd_at` = empty
  (NULL) — this row supplied neither column, proving the DEFAULT FALSE / nullable-with-
  no-default behavior without the insert itself naming them.
- Second command: `publish_consent` = `f` for the AC3 profile row, which also never
  named `publish_consent` in its INSERT column list.

This case fails if either boolean reads back anything other than `f` (e.g. `t`, or the
insert errors for lacking a value on a column that should have a default), or if
`consent_pd_at` reads back non-NULL.

## AC5 — No column exists for a PRD 5 computed-never-stored value

> "No column exists anywhere in this migration for a PRD 5 computed-never-stored value —
> specifically no no_show, waitlist_position, seats_taken, registration_open or finished
> column — verified by grepping the migration file for each of those five names and
> finding zero matches."

Steps (run from the repo root, not inside the container):
```bash
grep -inE "no_show|waitlist_position|seats_taken|registration_open|finished" apps/bot/drizzle/0000_tough_lilith.sql
```

Expected: no output, and the command's exit code is `1` (grep's "no match" exit code).

This case fails if grep prints any matching line (exit code `0`) — meaning one of the
five forbidden computed-value names appears as a column (or anywhere else) in the
migration file.

## AC6 — Design artefact states `tg_id` is never a business key

> "The design artefact under docs/agents/design/ states explicitly that tg_id is never a
> business key and that every later lookup resolves to User.id (PRD 5)."

Steps (run from the repo root):
```bash
grep -n "never a business key" docs/agents/design/REQ-010.md
grep -n "resolves to \`User.id\`\|resolves to User.id" docs/agents/design/REQ-010.md
```

Expected: at least one match for each grep, both inside or adjacent to a section
explicitly about `tg_id` (§5.1 in the current artefact, heading "`tg_id` is never a
business key"). As of this spec's writing the exact line reads:

> "**`tg_id` is never a business key; every later lookup resolves to `User.id`.**"

This case fails if either grep returns no match, or if the only match is a hedge/
deferral (e.g. "should probably never be a business key," "TBD") rather than the
unambiguous statement PRD 5 requires.
