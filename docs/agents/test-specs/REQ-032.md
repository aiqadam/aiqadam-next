## AC1 + AC6 — never-checked-in admitted registration receives exactly one message with five reasons + free text; checked-in registration receives nothing; the send reaches a `broadcast_opt_in = false` user

New `it(...)`:

- Seed one chapter, one organizer. Seed one published event, `endsAt` fixed at
  `2026-09-01T00:00:00Z`.
- Seed registration A: `registerForEvent` only — **never** set `checkedInAt` (stays
  `null`). This is the admitted-and-never-checked-in shape AC1 is about. Directly set
  `users.broadcastOptIn = false` for A's user (this is what the AC6 assertion below
  piggybacks on).
- Seed registration B: `registerForEvent`, then directly set `checkedInAt =
  2026-09-01T00:05:00Z`, `checkInMethod: "qr"` — the "WAS checked in" case AC1 says must
  receive nothing.
- `evaluationTime = 2026-09-01T00:10:00Z` (10 minutes after `endsAt` — inside
  `selectRegistrationsForNoShowReasonRequest`'s window: `endsAt <= evaluationTime` is
  `2026-09-01T00:00:00Z <= 2026-09-01T00:10:00Z`, true; `endsAt > evaluationTime -
  CATCH_UP_WINDOW_MS(2h)` is `endsAt > 2026-08-31T22:10:00Z`, true).
- `const { sender, sent } = makeFakeSender(); await makeNoShowReasonRequestJob(db, sender,
  300000).run(evaluationTime);`
- **Pass conditions:**
  1. `sent` has length exactly **1** — B never appears, by construction (`checked_in_at IS
     NULL` excludes it structurally, the AC1 mechanism per design §3.2).
  2. The one sent message's `buttons` has length **6**: five entries with `callbackData
     === \`noshow:reason:${code}:${registrationId of A}\`` for each of `work_ran_over`,
     `illness`, `forgot`, `transport`, `lost_interest` in that exact order (matching
     `NO_SHOW_REASON_CODES`'s declared order), plus a sixth entry with `callbackData ===
     \`noshow:other:${registrationId of A}\``.
  3. `notification_ledger` has exactly one row: `registrationId = A`, `kind =
     "no_show_reason_request"`. Zero ledger rows reference B's `registrationId`.
  4. `registrations.no_show_reason` is still `null` for both A and B (no answer has been
     given yet — merely being asked does not write anything).
- **AC6 assertion, same test, no extra fixture:** re-read `users` for A's `userId` and
  confirm `broadcastOptIn === false` — condition 1 already proved the send happened
  despite this. **Failure mode this independently catches:** a future refactor that
  accidentally reclassifies this call as `"marketing"` (or otherwise starts reading
  `broadcastOptIn`) would silently start filtering A out purely from this test's own
  fixture value, which condition 1's exact count of 1 would then fail.
- **Failure mode (AC1's "checked-in receives nothing" half):** any regression to the
  `checked_in_at IS NULL` selection clause (e.g. weakened to `admission = 'admitted'`
  alone) would let B through — condition 1's exact count of 1 (not "at least 1") is what
  catches it.

## AC3 — the job re-run at T+24h and T+48h delivers NO further message to the same registration, across all runs (zero reminders, not "exactly one" — REQ-032's departure from REQ-031's own reminder AC)

New `it(...)`, own fixture (registration A: admitted, never checked in, same event shape
as above, `endsAt = 2026-09-01T00:00:00Z`):

- **Run 1 — the genuine first send, shortly after `endsAt`:** `evaluationTime0 =
  2026-09-01T00:10:00Z`. `await makeNoShowReasonRequestJob(db, sender,
  300000).run(evaluationTime0)`.
  - **Pass:** `sent` has length exactly 1; `notification_ledger` has exactly one row
    (`registrationId = A`, `kind = "no_show_reason_request"`).
- **Run 2 — immediate re-run at the SAME `evaluationTime0` (direct ledger-dedup proof,
  same `sender`/`sent` array):** `await makeNoShowReasonRequestJob(db, sender,
  300000).run(evaluationTime0)` again.
  - **Pass:** `sent` still has length exactly 1 (unchanged) — the second `run()`
    re-selects A (nothing about A's state changed), but `sendLedgeredNotification`'s own
    `INSERT` into `notification_ledger` collides on the pre-existing `(registrationId,
    kind)` row (REQ-025's `UNIQUE` constraint) and resolves to `skipped-already-sent`,
    never calling `sender.send` a second time. `notification_ledger` still has exactly one
    row for A.
- **Run 3 — T+24h:** `evaluationTime24 = 2026-09-02T00:10:00Z`. `await
  makeNoShowReasonRequestJob(db, sender, 300000).run(evaluationTime24)`.
  - **Pass:** `sent` still has length exactly **1** (unchanged from after Runs 1–2).
  - **Documented mechanism, read directly from `selectRegistrationsForNoShowReasonRequest`
    itself, not assumed:** at `evaluationTime24`, the window clause requires `endsAt >
    evaluationTime - CATCH_UP_WINDOW_MS(2h)`, i.e. `2026-09-01T00:00:00Z >
    2026-09-01T22:10:00Z` — false. **A is excluded from Run 3's candidate list by the
    window itself**, before the ledger is ever consulted a third time — a different
    mechanism than Run 2's ledger-dedup, and this spec states both explicitly.
- **Run 4 — T+48h:** `evaluationTime48 = 2026-09-03T00:10:00Z`. `await
  makeNoShowReasonRequestJob(db, sender, 300000).run(evaluationTime48)`.
  - **Pass:** `sent` still has length exactly **1** (unchanged from after Runs 1–3), by the
    identical window-exclusion mechanism as Run 3 (an even larger margin).
- **Total across all four runs: exactly 1 send, exactly 1 ledger row, counted across all
  runs — this is the literal cross-run count AC3 requires, and it is zero additional
  messages after Run 1, not "one more" the way REQ-031's own reminder AC allowed.**
- **Failure mode this catches:** any code path that adds a second job/`NotificationKind`
  for a no-show "reminder" (the exact thing STORY-DETAILS D3 refuses) would show up here
  as `sent.length` growing past 1 on Run 3 or Run 4; a regression that widened
  `CATCH_UP_WINDOW_MS` unboundedly would also show up here as `sent.length` growing past 1
  on Run 3/Run 4 specifically (Run 2 alone cannot catch a widened window, since it reuses
  the same `evaluationTime` — this is why Runs 3 and 4 are both required, not just Run 2).

## AC2 — selecting a fixed reason writes it to `registrations.no_show_reason` (verified by reading the row back); the free-text "other" path writes the raw trimmed text

Two new `it(...)`s (both required — the task explicitly names both the fixed-reason and
free-text write paths):

**Sub-case A — fixed-reason button:**

- Seed one chapter, one organizer, one published event. Seed registration A (admitted,
  never checked in) for user U.
- **Pre-condition check:** read `registrations` for A — `no_show_reason` is `null`.
- Dispatch `callbackUpdate(U.tgId, \`noshow:reason:illness:${A}\`)`.
- **Pass conditions:**
  1. `answerCallbackQuery` was called with no `text`/`show_alert` (the plain ack, not a
     refusal alert).
  2. Re-read `registrations` for A directly from the DB: `no_show_reason === "illness"` —
     the literal `NoShowReasonCode` string, not a localized label.
  3. The captured reply's text equals `catalog.noShow.thanksMessage`.
- **Re-tap gate, same test:** dispatch `callbackUpdate(U.tgId,
  \`noshow:reason:forgot:${A}\`)` again (simulating a stale second tap on an already-
  answered registration).
  - **Pass:** `registrations.no_show_reason` for A is **still `"illness"`** — unchanged,
    NOT overwritten to `"forgot"`. The reply is still `catalog.noShow.thanksMessage` (a
    stale re-tap is a friendly no-op, never an error), but no write occurred — this is the
    literal "asked once, no write of a second answer" gate (design §4.1 step 8).

**Sub-case B — the free-text "other" path:**

- Seed a fresh registration B (admitted, never checked in) for user V, same event.
- Dispatch `callbackUpdate(V.tgId, \`noshow:other:${B}\`)`.
  - **Pass:** the captured reply's `reply_markup` is `{ force_reply: true }`, and its text
    contains `catalog.noShow.otherPrompt` and ends with the literal line `"No-show ref:
    " + B` (the ref line `formatNoShowTextPrompt` appends). Capture this full text as
    `otherPromptText`.
- Dispatch `replyUpdate(V.tgId, "  My train was cancelled at the last minute  ",
  otherPromptText)` (leading/trailing whitespace deliberately included in the reply text).
  - **Pass:** re-read `registrations` for B: `no_show_reason === "My train was cancelled
    at the last minute"` — the raw text with leading/trailing whitespace **trimmed**
    (`writeNoShowReason`'s caller trims before writing, per design §4.3 step 8), not the
    literal untrimmed string, and not one of the five fixed-reason codes.
- **Failure mode this catches:** a regression that stores the untrimmed reply text, or
  that accidentally routes the free-text answer through the fixed-reason write path (which
  would store the literal string `"My train was cancelled..."` as if it were a
  `NoShowReasonCode`, still technically satisfying "writes a string" but violating the
  design's own closed-set/free-text distinction) — condition 1's exact trimmed-text
  equality is what catches either.

## S3 exploit — a forged/leaked `registrationId` across all three entry points (fixed-reason callback, "other" callback, free-text reply) is refused, with no write, in every case

New `it(...)`, mirroring `handlers/feedback.db.test.ts`'s own S3 exploit shape, adapted to
`noShow.ts`'s three entry points instead of `feedback.ts`'s three:

- Seed one chapter, one published event ("S3 Event"). Seed Alice's registration `A`
  (admitted, never checked in) via `seedAdmittedRegistration`.
- Seed Bob as a separate user with his own, unrelated registration for a second event
  (`eventTwo`) — Bob's own identity is all that matters here; his own registration is
  never referenced by any attack below.

**Attack 1 — fixed-reason callback forgery:** Bob taps
`callbackUpdate(bobTgId, \`noshow:reason:illness:${A}\`)` (naming Alice's registration id,
never his own).
- **Pass conditions:**
  1. `answerCallbackQuery` was called with `show_alert: true` and `text ===
     catalog.noShow.notYours`.
  2. Re-read `registrations` for A: `no_show_reason` is still `null` — Bob's forged tap
     never wrote anything to Alice's row.
  3. No `sendMessage` call was captured as a result of this update (only the
     `answerCallbackQuery` refusal).

**Attack 2 — "other" callback forgery:** Bob taps `callbackUpdate(bobTgId,
\`noshow:other:${A}\`)`.
- **Pass conditions:**
  1. `answerCallbackQuery` was called with `show_alert: true` and `text ===
     catalog.noShow.notYours`.
  2. No `force_reply` prompt was sent to anyone as a result of this update (grep captured
     `sendMessage` calls since before this attack: none carry `reply_markup: {
     force_reply: true }`) — Bob is never handed Alice's free-text prompt.
  3. `registrations.no_show_reason` for A is still `null`.

**Attack 3 — free-text reply forgery:** first, Alice legitimately triggers her own
"other" prompt (`callbackUpdate(aliceTgId, \`noshow:other:${A}\`)`) and the resulting
`otherPromptTextA` is captured. Then Bob replies to THAT message (a message his own
Telegram client would never actually have received, but the handler must not rely on
Telegram-level delivery guarantees for this refusal — the ownership check is what must
catch it): `replyUpdate(bobTgId, "Fake answer", otherPromptTextA)`.
- **Pass conditions:**
  1. `registrations.no_show_reason` for A is still `null` after this dispatch (unchanged
     from before the reply).
  2. No new `sendMessage` was captured as a result of this update (the handler returns
     silently on ownership mismatch, §4.3 step 6 — a passive listener, no alert).
- **Then, immediately after, Alice's own legitimate reply to the same prompt succeeds** —
  `replyUpdate(aliceTgId, "Lost interest, honestly", otherPromptTextA)` — confirming the
  refusal above was specific to Bob's forged identity, not a broken handler:
  `registrations.no_show_reason` for A becomes `"Lost interest, honestly"`.

- **Failure mode this catches:** any of the three handlers resolving authorization from
  the `registrationId` embedded in `callback_data`/the reply's ref line (rather than from
  `getFlowUserByTgId(ctx.from.id)` cross-checked against `context.userId`) would let one
  or more of Attacks 1–3 through — each attack's own "no write occurred" assertion
  independently catches a regression in its own entry point, since a shared regression
  (e.g. a helper that skips the ownership check entirely) would fail all three
  simultaneously, while a regression scoped to one handler only would fail exactly that
  attack's own case.

## AC5 — the `isNoShow` derivation returns exactly one no-show for a constructed admitted-checked-in / admitted-not-checked-in / withdrawn triple, evaluated after `ends_at`

**Verification method, stated explicitly:** AC5 is about the pure function `isNoShow`
itself (`domain/registration.ts`), not about a job's DB selection — the requirement's own
wording ("the no_show derivation returns the correct set for a constructed event...")
names the derivation directly. The most precise, most directly-failing check is therefore
a plain (no-DB) unit test calling `isNoShow` with the three constructed inputs, added to
the existing `apps/bot/src/domain/registration.test.ts` (already a plain, framework-free,
no-DB suite for this file's other pure functions — `decideRegistrationOutcome`,
`generateQrToken`, `resolveRegistrationSource` — per that file's own header comment), not
a new DB-backed file: a DB round-trip would only add indirection around the same three
`isNoShow(...)` calls this unit test makes directly, without testing anything a DB-backed
version would catch that this doesn't.

New `describe("isNoShow — REQ-032.md §1's first-match-wins table, the constructed
admitted-checked-in / admitted-not-checked-in / withdrawn triple", () => { ... })` in
`apps/bot/src/domain/registration.test.ts`:

- Fix `endsAt = new Date("2026-09-01T00:00:00Z")`, `evaluationTime =
  new Date("2026-09-01T02:00:00Z")` (strictly after `endsAt` — the "event has ended"
  condition every row of the table requires to even reach the last branch).
- **Registration 1 — admitted, checked in:** `isNoShow("admitted",
  new Date("2026-09-01T00:05:00Z"), endsAt, evaluationTime)`.
  - **Pass:** returns `false` (table row 2 — checked in wins regardless of `endsAt`).
- **Registration 2 — admitted, never checked in:** `isNoShow("admitted", null, endsAt,
  evaluationTime)`.
  - **Pass:** returns `true` (table row 5 — the exact no-show condition).
- **Registration 3 — withdrawn:** `isNoShow("withdrawn", null, endsAt, evaluationTime)`.
  - **Pass:** returns `false` (table row 1 — `admission !== "admitted"` short-circuits
    before `checkedInAt`/`endsAt` are even consulted).
- **Pass condition, stated as the requirement's own literal count:** across the three
  constructed registrations, exactly one (`Registration 2`) evaluates to `true` —
  `expect([false, true, false]).toEqual([reg1, reg2, reg3].map(...))`, or equivalently
  three independent `expect(...).toBe(...)` assertions as above (either shape satisfies
  the "exactly one row is a no-show" requirement; the three independent assertions are
  preferred since a failure names exactly which registration's expected value broke).
- **Failure mode this catches:** any reordering of the first-match-wins table (e.g.
  checking `endsAt`/`evaluationTime` before `checkedInAt`, or treating `withdrawn`
  differently than any other non-`admitted` state) would flip one of these three
  assertions independently, naming exactly which row of the table regressed.
