event's token, and the audit row names the registration

## AC2 — repeat scan is a genuine zero-write report, proven at the storage layer via `xmin`

New `it(...)`, own fixture:

- Seed one chapter, one organizer, one published event (`capacity: 5`), one staff member,
  one attendee (own names, distinct from BACKEND-DEV's "Bek N").
- Dispatch `/start ci_<qrToken>` once (the first, real scan). Confirm `checkedInAt` is set,
  `checkInMethod = 'qr'`, exactly one `registration.checkin` audit row.
- **Why `updated_at` is not usable as the zero-write proxy here:** direct inspection of
  `apps/bot/src/db/schema.ts` (`registrations` table) and every write path in
  `apps/bot/src/domain/registration.ts` confirms `updated_at` has no `.$onUpdate()`
  trigger in the Drizzle schema, no Postgres `BEFORE UPDATE` trigger exists anywhere in
  `apps/bot/drizzle/*.sql` (confirmed via `grep -rn "TRIGGER" apps/bot/drizzle`), and no
  `.set(...)` call anywhere in this file's write paths (including `performQrCheckIn`)
  assigns `updatedAt`. This means `updated_at` never changes on **any** UPDATE in this
  schema today — it would read identically whether zero or ten writes occurred, so it
  cannot serve as the "did an UPDATE run" proxy the task asked for.
- **The actual proxy: Postgres's own hidden `xmin` system column.** Every UPDATE — even one
  that writes back the same values — creates a new MVCC tuple version with a new `xmin`
  (the id of the transaction that created that row version). This is a storage-layer fact
  independent of which application columns the `UPDATE`'s `SET` clause happens to name, so
  it is a genuine "was this row physically rewritten" proof, not merely "did this one
  column's value change."
  - Capture `const before = await pool.query("SELECT xmin::text AS xmin FROM registrations
    WHERE id = $1", [registrationId])` immediately after the first scan.
- Dispatch `/start ci_<qrToken>` a **second** time (same token, same staff).
  - Capture `const after = await pool.query(<same query>)`.
- **Pass conditions:**
  1. `before.rows[0].xmin === after.rows[0].xmin` — the row was never physically rewritten
     by the second scan (the genuine zero-writes proof).
  2. `checkedInAt`/`checkedInBy`/`checkInMethod` unchanged (byte-for-byte, via
     `.getTime()` on `checkedInAt`), matching AC2's own wording.
  3. Still exactly one `registration.checkin` audit row (no second one written).
  4. The second reply's text equals `checkinQr.alreadyCheckedIn` with `{at}`/`{by}`
     correctly interpolated from the first scan's own values.
- **Failure mode this catches:** a regression that turns the `"already-checked-in"` branch
  into a no-op `UPDATE ... SET checked_in_at = checked_in_at` (or any other accidental
  write-back with unchanged values) — a case checking only "the *value* is unchanged"
  (as BACKEND-DEV's own AC2 case does) would pass even though a real, unnecessary write
  occurred; only the `xmin` check would catch it.

## AC3 — one registration row cycled through `waitlisted` → `requested` → `withdrawn`,
each scan refused with its own specific reason and its own override offer

New `it(...)`, own fixture — a single registrant exercised across all three non-admitted
states in sequence, rather than BACKEND-DEV's split of one withdrawn-only test plus a
separate two-registrant waitlisted/requested loop:

- Seed one chapter, one organizer, one published event (`capacity: 5`), one staff member.
- Register one attendee, landing `admitted` (own names). Record `qrToken`/`registrationId`.
- For each `admission` in `["waitlisted", "requested", "withdrawn"]`, in this exact order
  against the **same** `registrationId`:
  1. `pool.query("UPDATE registrations SET admission = $1 WHERE id = $2", [admission,
     registrationId])` — the same "flip while preserving the already-issued token"
     construction the design's §3.2 table itself calls for (no public API path produces a
     token-bearing non-admitted row directly — see design §3.2's own commentary and
     BACKEND-DEV's identical technique for `waitlisted`/`requested`).
  2. Dispatch `bot.handleUpdate(commandUpdate(staffTgId, "/start ci_" + qrToken))`.
  3. Assert the reply text equals the exact expected catalog key for that `admission`
     (`refusedWaitlisted` / `refusedRequested` / `refusedWithdrawn`).
  4. Assert the reply's `reply_markup` contains exactly one inline button with
     `callback_data === "checkin:override:" + registrationId` and `text ===
     catalog.checkinQr.overrideButtonLabel` — asserted on **all three** iterations, not
     only one.
  5. Assert `registrations` row: `checkedInAt` still `null`, `admission` still the
     iteration's value (no side effect from the refusal).
- **Pass conditions:** all 3×(text + button + null-checked-in) assertions above pass, in
  order.
- **Failure mode this catches:** (a) any per-`admission` catalog-key mismatch in
  `REFUSAL_CATALOG_KEY` (e.g. `requested`/`waitlisted` swapped) — a bug BACKEND-DEV's own
  split tests would also catch individually, but this case additionally catches (b) a
  regression where the override button is attached only for some refusal reasons and not
  others (e.g. an `if (admission === "withdrawn")` guard accidentally added around the
  keyboard-building code in `resolveCheckinQrDeepLink`) — BACKEND-DEV's waitlisted/requested
  test never inspects `reply_markup` at all, only the AC3 withdrawn-only test does.

## Stale-token recheck (S4) — dedicated case, closes the zero-coverage gap

**Why a direct `performQrCheckIn` call, not only a full `/start` dispatch, is required
here.** `getRegistrationByQrTokenForCheckin` (design §2.1) looks a row up **by its current
`qr_token` value**. The instant a registration's token is regenerated (re-registration,
design §2.1/registerForEvent step 8; or waitlist promotion, `promoteFromWaitlistIfEligible`
step 5), a scan of the OLD token no longer matches *any* row at that unlocked-lookup stage
— `resolveCheckinQrDeepLink` replies `unknownToken` at its very first step and never
reaches `performQrCheckIn` at all under ordinary, sequential dispatch. This means
`performQrCheckIn`'s own step-2 defensive recheck (`row.qrToken !== qrToken`, design §3.3
step 2 — the actual code SECURITY-REVIEWER and CODE-DESIGN-VALIDATOR flagged) is only
reachable in production via a genuine **race** (a scan whose unlocked lookup reads the old
token milliseconds before a concurrent re-registration commits a new one, but whose locked
recheck runs after that commit) — a race this suite has no reliable way to force
deterministically without adding test-only instrumentation to production code, which is out
of scope. **The correct, deterministic way to exercise this exact line is to call
`performQrCheckIn` directly** with a real `registrationId` (obtained from a genuine
re-registration) and the real, now-superseded old token — this is not a synthetic input:
both values are produced by actual domain calls, and the direct call exercises precisely
the code path a race would otherwise trigger nondeterministically. This case supplements,
not replaces, the full-dispatch case below, which proves the ordinary user-facing behavior
(refused as unknown) end to end.

New `it(...)`:

- Seed one chapter, one organizer, one published event (`capacity: 1`, no waitlist
  involved — keeps the construction to the simpler of the two regeneration paths the
  design names, re-registration).
- Register attendee "Alma Dzhaksybekova" — genuinely `admitted` via `registerForEvent`.
  Record `registrationId = R` and the issued token as `T1`.
- `withdrawRegistration(db, R, attendee.userId, new Date())` — genuine `admitted →
  withdrawn` transition (capacity freed; `promotion.kind` will be `"no-waitlist"` since
  nothing is waitlisted — not itself asserted, just confirms nothing extraneous happens).
  Confirm via a direct `SELECT qr_token FROM registrations WHERE id = $1` that the row's
  `qr_token` is still `T1` at this point (matches REQ-028/AC3's already-established "a
  withdrawn row keeps its old token" fact).
- `registerForEvent(db, attendee.userId, eventId, new Date())` — the attendee re-registers
  for the SAME event. Assert the result's `registrationId === R` (REQ-022's "reuse the
  withdrawn row" behavior — same row, not a new one) and the result's `qrToken`
  (call it `T2`) is defined and **`T2 !== T1`**. Confirm via a direct `SELECT` that the
  live row's `qr_token` is now `T2`.
- **Sub-case A — full dispatch, the user-facing behavior:**
  - Dispatch `bot.handleUpdate(commandUpdate(staffTgId, "/start ci_" + T1))` — scanning the
    OLD, superseded token.
  - Pass conditions: reply text equals `checkinQr.unknownToken`; `registrations` row for
    `R`: `checkedInAt` still `null` (the re-registration itself never checks anyone in —
    confirm this is the re-registration's own admitted-but-not-checked-in state, not a
    false pass from an unrelated check-in).
- **Sub-case B — direct call, the defensive code path itself:**
  - Capture `const before = await pool.query("SELECT xmin::text AS xmin FROM registrations
    WHERE id = $1", [R])`.
  - `const outcome = await performQrCheckIn(db, R, T1, staffUserId, new Date())` — the
    real registration id `R`, paired with the now-stale `T1`, called directly.
  - Pass conditions:
    1. `outcome.kind === "unknown-token"` — the recheck at design §3.3 step 2 is what
       produces this, since a plain "does a row with this id exist" check would otherwise
       have found `R` and moved on to `decideQrCheckinOutcome`.
    2. `pool.query(<same xmin query>)` afterward returns the **same** `xmin` as `before` —
       no `UPDATE` ran (the genuine zero-write proof, same technique as AC2).
    3. Zero new `audit_log` rows with `action = 'registration.checkin'` for `R`.
- **Failure mode this catches:** a regression that has `performQrCheckIn` look its row up
  by `registrationId` alone and never re-verify `qr_token` against the token the call was
  invoked with (i.e. deleting or weakening design §3.3 step 2) — such a regression would
  let sub-case B's direct call silently check `R` in using the stale `T1`, which is exactly
  the "a stale printed/screenshotted QR code could keep working through an id-based
  re-lookup" failure S4 exists to prevent, per the design's own §3.3 step 2 commentary.
