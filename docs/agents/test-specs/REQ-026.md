## AC3 — run, KILL process, restart, run same job again → exactly ONE message
(genuine two-process test)

**Fixture (built by `scratch-verify-req026-p1.ts` on its first run, `p2` reuses the same
row):**
- One chapter (`timezone: "Asia/Almaty"`), one venue, one published event
  (`EVENT_KILL`, `startsAt` set so `evaluationTime + 1h` falls inside the 24h window,
  e.g. `evaluationTime = 2026-11-10T00:00:00Z`, `startsAt = 2026-11-10T20:00:00Z`).
- One user `KILL_SUBJECT` (`tg_id 1000000991` — REQ-025 spec's own range was
  `1000000900`+; this fixture picks `1000000991`, inside that same family but a value no
  REQ-025 case used, since both harnesses are scratch and never run in the same process),
  created via `resolveOrCreateUser`.
- One admitted registration for `KILL_SUBJECT` on `EVENT_KILL`, via a real
  `registerForEvent` call.

**Stub `NotificationSender` shared by both processes** (each process constructs its own
instance):
```ts
const sender: NotificationSender = {
  async send(tgId, text, buttons) {
    fs.appendFileSync(
      "./scratch-verify-req026-deliveries.json",
      JSON.stringify({ tgId: tgId.toString(), text, buttons, pid: process.pid, at: new Date().toISOString() }) + "\n",
    );
  },
  async sendPhoto(tgId, _photo, caption) {
    fs.appendFileSync(
      "./scratch-verify-req026-deliveries.json",
      JSON.stringify({ tgId: tgId.toString(), caption, pid: process.pid, at: new Date().toISOString() }) + "\n",
    );
  },
};
```

**`scratch-verify-req026-p1.ts` (process 1):**
1. Build the fixture above if the delivery-log file does not already exist; write the
   resulting `registrationId` to `./scratch-verify-req026-fixture.json` for `p2`.
2. Call `makeReminder24hJob(db, sender, 300000).run(new Date("2026-11-10T00:00:00Z"))` —
   **do not `await` inside a `try`/`finally`**. Instead:
   ```ts
   makeReminder24hJob(db, sender, 300000).run(new Date("2026-11-10T00:00:00Z")).then(() => {
     process.exit(0);
   });
   ```
   The kill point is constructed precisely after the job's one candidate has already
   completed its `sendLedgeredNotification` call (whose `sender.send` has already
   resolved, durably writing the delivery-log line) — `process.exit(0)` terminates with
   no further code executing. This is the same "kill right after the first send resolved"
   discipline REQ-025's AC1 established, extended to a real job's `run(evaluationTime)`
   rather than a bare `sendLedgeredNotification` call, since AC3's literal wording is
   about "run[ning] the job."
3. Run: `npx tsx scratch-verify-req026-p1.ts` — a real, separate OS process.
4. Confirm the process actually exited (exit code `0`) before starting `p2`.
5. Independently confirm by direct SQL: exactly one row in `notification_ledger` for
   `(registration_id = <that registrationId>, kind = 'reminder_24h')`, and exactly one
   line in `scratch-verify-req026-deliveries.json`.

**`scratch-verify-req026-p2.ts` (process 2 — the "restart," run same job again):**
1. Read `registrationId` back from the sidecar file.
2. Open a fresh `Pool`/`drizzle` instance — no state from `p1` is shared in-process.
3. Call `makeReminder24hJob(db, sender, 300000).run(new Date("2026-11-10T00:00:00Z"))`
   again — the same job, same `evaluationTime`, re-selecting the same candidate from
   `selectRegistrationsForReminder24h` (the registration is still admitted and the event
   is still inside the window, exactly as a real restarted process would re-derive the
   same candidate set).
4. After the `run(...)` promise resolves, query `notification_ledger` and the delivery
   log directly (do not rely on any in-memory outcome — `run()` returns `void`, so this
   case's proof is entirely in the DB/file side effects, unlike REQ-025's AC1 which could
   also inspect `sendLedgeredNotification`'s own returned `SendOutcome`).
5. Run: `npx tsx scratch-verify-req026-p2.ts`.

**Pass conditions (all must hold):**
- `scratch-verify-req026-deliveries.json` contains **exactly one** line after both runs —
  `p2`'s run added zero lines.
- Direct SQL after both runs: exactly one row in `notification_ledger` for
  `(registration_id, kind='reminder_24h')`.
- `KILL_SUBJECT`'s registration is still `admitted` and unaffected by either run (this job
  never writes to `registrations`).

**Failure mode this catches:** any per-process or in-memory notion of "already handled
this tick" (e.g. a module-level `Set` of `registrationId`s the job's own code maintained,
independent of the ledger) would pass a single-process re-run but fail this genuine
process-boundary test — `p2` starts with an empty heap, so only the DB-backed
`notification_ledger` constraint (unchanged from REQ-025, reused unmodified by
`sendLedgeredNotification`'s steps 1–4) can make `p2`'s attempt a no-op. This also
transitively re-confirms REQ-025's own AC1 property still holds when reached through a
**real job's** `run()` entrypoint rather than a bare `sendLedgeredNotification` call — a
regression in how `reminderJobs.ts` wires the job to `sendLedgeredNotification` (e.g. if a
future edit made the job retry sends outside the ledgered call) would be caught here even
though REQ-025's own committed tests could never see it, since they don't exercise
`reminderJobs.ts` at all.

**Teardown:** delete `apps/bot/scratch-verify-req026-p1.ts`,
`apps/bot/scratch-verify-req026-p2.ts`, `apps/bot/scratch-verify-req026-fixture.json`, and
`apps/bot/scratch-verify-req026-deliveries.json` after this AC's run; confirm
`git status --porcelain` shows nothing stray from these files afterward.

- **Failure mode this catches:** `composeMessage`'s `admission !== "admitted"` check
  (§5.1 step 2 of the design) being omitted or checking the wrong field — would send a

## AC8 — non-doors-only agenda → `starts_at` alone, no leaked agenda time (this spec's
own deliberately different agenda-kind strings)

New `it(...)` in the new committed file, its own fixture:

- A fresh event (own chapter, own `startsAt: 2026-11-06T00:00:00Z`, `endsAt:
  2026-11-06T05:00:00Z` — wide enough to keep both agenda items' `at` values within
  `validateAgenda`'s `at <= endsAt` rule), agenda set to `[{ kind: "workshop", at:
  "2026-11-05T21:00:00Z", label: "Hands-on workshop" }, { kind: "afterparty", at:
  "2026-11-06T04:00:00Z", label: "Afterparty" }]` — deliberately
  different `kind` strings from BACKEND-DEV's own AC8 case (`"networking"`/`"close"`), to
  confirm `findDoorsAgendaItem`'s `kind === "doors"` check is a real string-equality test
  against the literal `"doors"` value, not something that happens to also reject
  BACKEND-DEV's own two chosen non-doors strings for some other structural reason (e.g. a
  bug that instead checked `kind.length` or matched a hardcoded blocklist of
  `"networking"`/`"close"` rather than genuinely testing `=== "doors"`).
- Run the T-3h job for this event/candidate.
- Pass conditions:
  1. `message.caption` contains the start-time line (`catalog.reminder3h.startLabel` plus
     `formatDateTimeInTimezone(event.startsAt, ...)`).
  2. `message.caption` does **not** contain `catalog.reminder3h.doorsLabel`.
  3. `message.caption` does **not** contain either agenda item's own formatted time
     (`formatDateTimeInTimezone(new Date("2026-11-05T21:00:00Z"), ...)` for the workshop
     item, and the afterparty item's own formatted time) — this is the "no OTHER agenda
     item's time leaks" half of AC8, distinct from merely "no doors line," and not
     directly asserted by name in BACKEND-DEV's own AC8 case (its own case asserts
     `.not.toContain(catalog.reminder3h.doorsLabel)` only — confirmed by reading the
     committed case directly, lines ~477 onward). This spec's version closes that gap by
     asserting the two non-doors items' own times are absent too, not just the doors
     label string.
- **Failure mode this catches:** a `findDoorsAgendaItem` or caption-composition bug that
  falls back to "the first agenda item" or "the last agenda item" instead of genuinely
  filtering on `kind === "doors"` — such a bug would pass a check that only asserts the
  doors *label* is absent (since a fallback item has no `"doors"` label to render this
  incorrect label with) but would fail this spec's additional "no other item's own time
  appears anywhere" assertion, because the fallback item's time would still leak into the
  caption under some other line.

## Forged-callback non-authorization — committed regression coverage for the property
SECURITY-REVIEWER verified ad hoc

**Why this belongs here as a permanent test, not just a Step 2c finding:** per
`handoffs/WF02-REQ-026/step-02c-security-reviewer.json`, SECURITY-REVIEWER wrote 3
adversarial tests in a scratch file, ran them, and deleted them — "not committed." This
requirement introduces a brand-new authorization surface (`reminder24h:confirm`/`:decline`
callbacks keyed by a `registrationId` embedded in `callback_data`), and per this run's
task brief this deserves the same permanent coverage AC1/AC3/the race case got in
REQ-025's own spec, not a one-off manual verification that leaves no trace for the next
regression.

**New committed test file:** `apps/bot/src/handlers/reminder24h.forgery.test.ts`, modeled
on `reminder24h.test.ts`'s own `beforeAll`/`beforeEach`/`dbAvailable`-skip discipline and
`makeTestBot()` helper (same real grammY dispatch pattern), with its own `nextTgId =
990_000_000` counter and its own `seedChapter`/`seedVenue`/`seedPublishedEvent` helpers

```ts
describe("reminder24h:confirm/:decline -- forged callback naming another user's registrationId", () => {
  it("an attacker with no registration of their own cannot reconfirm a victim's registration", async (t) => {
    if (!dbAvailable) { t.skip(); return; }
    const chapterId = await seedChapter();
    const eventId = await seedPublishedEvent(chapterId);
    const victimTgId = nextTgId++;
    const victim = await resolveOrCreateUser(db, { tgId: BigInt(victimTgId), tgUsername: "victim1", lang: "ru" });
    const inserted = await db.insert(registrations)
      .values({ eventId, userId: victim.id, admission: "admitted", source: "direct" })
      .returning({ id: registrations.id });
    const victimRegistrationId = inserted[0]?.id;
    if (victimRegistrationId === undefined) throw new Error("fixture insert returned no row");

    const attackerTgId = nextTgId++;
    await resolveOrCreateUser(db, { tgId: BigInt(attackerTgId), tgUsername: "attacker1", lang: "ru" });
    // Attacker has NO registration row of their own at all.

    const { bot, captured } = makeTestBot();
    await bot.handleUpdate(callbackUpdate(attackerTgId, `reminder24h:confirm:${victimRegistrationId}`) as never);

    const catalog = getCatalog("ru");
    expect(textOf(captured[1])).toBe(catalog.withdraw.refusedNotFound);

    const victimRow = (await db.select().from(registrations).where(eq(registrations.id, victimRegistrationId)))[0];
    expect(victimRow?.admission).toBe("admitted");
    expect(victimRow?.reconfirmedAt).toBeNull();

    const auditRows = await db.select().from(auditLog).where(eq(auditLog.entityId, victimRegistrationId));
    expect(auditRows.filter((r) => r.action === "registration.reconfirm")).toHaveLength(0);
  });

  it("an attacker WITH their own separate registration cannot decline (withdraw) a victim's registration", async (t) => {
    if (!dbAvailable) { t.skip(); return; }
    const chapterId = await seedChapter();
    const eventId = await seedPublishedEvent(chapterId, 5);
    const victimTgId = nextTgId++;
    const victim = await resolveOrCreateUser(db, { tgId: BigInt(victimTgId), tgUsername: "victim2", lang: "ru" });
    const victimRow = await db.insert(registrations)
      .values({ eventId, userId: victim.id, admission: "admitted", source: "direct" })
      .returning({ id: registrations.id });
    const victimRegistrationId = victimRow[0]?.id;
    if (victimRegistrationId === undefined) throw new Error("fixture insert returned no row");

    const attackerTgId = nextTgId++;
    const attacker = await resolveOrCreateUser(db, { tgId: BigInt(attackerTgId), tgUsername: "attacker2", lang: "ru" });
    const attackerRowInsert = await db.insert(registrations)
      .values({ eventId, userId: attacker.id, admission: "admitted", source: "direct" })
      .returning({ id: registrations.id });
    const attackerRegistrationId = attackerRowInsert[0]?.id;
    if (attackerRegistrationId === undefined) throw new Error("fixture insert returned no row");

    const { bot, captured } = makeTestBot();
    // Attacker forges a decline naming the VICTIM's registrationId, not their own.
    await bot.handleUpdate(callbackUpdate(attackerTgId, `reminder24h:decline:${victimRegistrationId}`) as never);

    const catalog = getCatalog("ru");
    expect(textOf(captured[1])).toBe(catalog.withdraw.refusedNotFound);

    const victimAfter = (await db.select().from(registrations).where(eq(registrations.id, victimRegistrationId)))[0];
    expect(victimAfter?.admission).toBe("admitted"); // seat NOT freed

    const attackerAfter = (await db.select().from(registrations).where(eq(registrations.id, attackerRegistrationId)))[0];
    expect(attackerAfter?.admission).toBe("admitted"); // attacker's own row untouched -- no silent redirect

    const auditRows = await db.select().from(auditLog).where(eq(auditLog.entityId, victimRegistrationId));
    expect(auditRows.filter((r) => r.action === "registration.withdraw")).toHaveLength(0);
  });
});
```

**Pass conditions (both cases):** the reply is the non-disclosing `refusedNotFound`
string in both cases (never a distinct "not yours" message that would confirm the id's
existence to the attacker); the victim's row is completely unaffected in every field
checked; zero audit rows are written for the victim's registration id; in the second
case, the attacker's own separate registration is also unaffected (rules out a bug that
silently substitutes "the caller's own registration" when the named id doesn't match,
which would be a different, still-wrong behavior that a coarser assertion could miss).

**Failure mode this catches:** `decideReconfirmOutcome`/`decideWithdrawOutcome`'s
`ownerUserId !== actingUserId` check being skipped, inverted, or reading `ownerUserId`
from stale/cached data instead of a fresh `SELECT ... FOR UPDATE` inside the same
transaction — any of these would let an attacker who merely knows or guesses another
user's `registrationId` (observable, for example, if a registration id ever leaked into
a URL, log line, or shared screenshot) reconfirm or withdraw on that user's behalf.
