**What is NOT yet independently re-parameterized, and what this spec closes, per this
project's established convention (REQ-019 through REQ-023's precedent — every spec adds
its own independently-designed cases rather than merely re-pointing at BACKEND-DEV's
coverage):**

- **AC1's cross-leakage check has only ever been scanned against 5 profile fields
  (name/company/phone/email split into first/last) and only ever with a 2-user, 1-row-
  each fixture.** The `profiles` table (`apps/bot/src/db/schema.ts` lines 97-129) holds
  9 more nullable fields BACKEND-DEV's own fixture never populates or scans for:
  `position`, `isStudent`, `experienceLevel`, `linksGithub`, `linksLinkedin`, `linksSite`,
  `publicBio`, plus `users.tgUsername`. This spec's AC1 case populates and scans for all
  of these, uses a 3-user fixture (a secret user with data spread across TWO
  registrations — one admitted, one waitlisted — rather than one), and adds a third user
  with zero registrations of their own to confirm their `/my` reply is the empty-state,
  not a leaked view of anyone else's rows.
- **AC2's position-recompute has only ever been exercised via a capacity-0 event where
  the person ahead voluntarily withdraws from the waitlist directly** — no admitted seat
  ever existed, so REQ-023's auto-promotion path was structurally never involved in
  recomputing the viewer's position. This spec's AC2 case uses a materially different
  mechanism: a capacity-1 event where the SEAT-HOLDER withdraws, triggering REQ-023's
  real auto-promotion of the earliest waitlisted candidate (who is ahead of the viewer);
  the viewer's position must still recompute correctly (from 2 to 1) even though the
  person who left the front of the queue did so by being *promoted*, not by withdrawing
  from the waitlist themselves — a different code path (`promoteFromWaitlistIfEligible`)
  than the one BACKEND-DEV's own AC2 case exercises.
- **AC3 has never been exercised with more than one admitted row in the same `/my`
  reply** — BACKEND-DEV's AC3/AC4/AC5 fixture has exactly one admitted registration. A
  QR-token mix-up bug (e.g. the wrong row's `qrToken` accidentally reused across rows,
  or a closure-capture bug in a loop) could not be caught by a single-admitted-row
  fixture. This spec's AC3 case gives one user TWO admitted registrations (two different
  events, two distinct tokens generated the same way real registrations get them — via
  `registerForEvent`, not hand-picked repeated-character strings) and confirms each
  photo's own decoded content matches ITS OWN row's token, never the other row's.
- **AC4 has only ever exercised 3 of the 5 `AdmissionState` values** (`withdrawn`,
  `rejected`, `waitlisted`) — the 5th value, `requested` (a registration pending
  organizer approval, `apps/bot/src/db/schema.ts` line 178's enum), has never been
  included in any `/my` fixture. This spec's AC4 case adds a `requested` row alongside
  the other three non-admitted states in one fixture and confirms zero photo sends
  across all four.
- **The empty-registrations case (a user with zero registrations calling `/my`) has never
  been exercised anywhere in this codebase** — neither `my.test.ts` nor any other test
  file dispatches `/my` for a user with no rows. Per this run's own task brief, this is a
  genuine coverage gap, not busywork: `handlers/my.ts` step 4 has a distinct code path
  (`rows.length === 0` → `catalog.my.emptyState`, return) that is never reached by any
  existing test, and a regression there (e.g. throwing on an empty array, or falling
  through to the header-plus-zero-rows shape instead) would go undetected today. This
  spec adds AC-empty below.

**`tg_id` range:** `1000000800`+ — distinct from REQ-019 (`1000000200`+), REQ-020
(`1000000300`+), REQ-021 (`1000000400`+), REQ-022 (`1000000500`+), REQ-023
