# Test spec — REQ-033 (`invite_codes` table, `registrations.invite_code_id` FK closure, code generator)

## Scope test result (WF-02 Step 3, run first)

**Split verdict, stated explicitly rather than picking one path for the whole
requirement:**

- **Code generator (AC6, AC7) — NO further spec needed.** `generateInviteCode()`
  (`apps/bot/src/domain/inviteCode.ts`) is pure TypeScript with zero DB/handler
  dependency, and `apps/bot/src/domain/inviteCode.test.ts` already exercises exactly
  what AC6/AC7 ask for: a 10,000-code zero-collision run (AC6), a 1000-code
  every-character-in-alphabet run (AC7), an exact-alphabet-string assertion, and a
  runtime `Math.random`-not-called check (AC6's CSPRNG-source requirement). These are
  automated tests, not a manual checklist, and this project's QA guide
  (`docs/guides/qa_testing_guide.md` §7) treats automated coverage as superior to a
  manual spec once it exists — TEST-RUNNER's job for AC6/AC7 is to run `npm test`
  (specifically this file) and quote the real pass/fail output, not to re-derive a
  parallel manual procedure for a property already mechanically checked on every run.
- **Design artefact content (AC8) — NO further spec needed.** AC8 asks whether
  `docs/agents/design/REQ-033.md` states three things in prose (the composition
  reasoning, the legal-combination list, the FR-4 open question routed to REQ-038).
  This was already gated by CODE-DESIGN-VALIDATOR at Step 1b, which is the correct and
  sufficient gate for design-artefact *content* (WF-02 Step 1b checklist item "no
  TBD/deferral language," "every acceptance criterion maps to a concrete design
  element"). A grep-based confirmation case is included below anyway (mirroring
  REQ-011's AC7 case), since it costs nothing and gives TEST-RUNNER something
  mechanical to point at rather than "trust CODE-DESIGN-VALIDATOR's earlier PASS."
- **Migration/schema behavior (AC1-AC5, AC9) — SPEC WARRANTED, written below.** These
  acceptance criteria are explicitly properties of *the migration applied to a real
  Postgres instance* — unique-constraint enforcement, FK enforcement (both the new
  `invite_codes` FKs and the closed `registrations.invite_code_id` FK), and
  `ON DELETE RESTRICT` behavior. None of these can be verified by reading
  `schema.ts` or the `.sql` file alone (the requirement's own AC2 text says so
  explicitly: "Reading the schema is not sufficient; the duplicate insert must be
  attempted"). BACKEND-DEV already ran these checks manually once against a scratch
  Postgres (Step 2 handoff `result.summary`), but per `core-directives.md`'s "Every
  producing step has a validating step," TEST-RUNNER and RELEASE-VALIDATOR must be
  able to independently re-derive the same verdict, not trust that report — hence this
  spec, so they have an exact, mechanically-followable procedure to repeat rather than
  re-inventing one under time pressure or silently accepting BACKEND-DEV's word.

**Why this is not the "no user-visible surface, skip straight to RELEASE-VALIDATOR"
path stated in WF-02 Step 3's scope test:** that path is for a requirement whose
*only* artifacts are narrative `.md` files with nothing to run a check against. Here,
`apps/bot/drizzle/0007_sturdy_network.sql` is a real, applyable migration with
constraints that either hold or don't when real rows are inserted against them — a
concrete, repeatable, judgment-free thing to verify, exactly like REQ-010/REQ-011
before it (both of which the workflow already treats as warranting a test-spec,
per `docs/agents/test-specs/REQ-010.md` and `REQ-011.md`). There is no Telegram
handler and no bot-UI surface, so no *manual checklist against the running bot* is
written — but "manual checklist against a rendered screen" and "verification kind:
scripted docker/psql checklist" are not the same thing; WF-02 Step 3 explicitly
allows the latter's shape via the `qa_testing_guide.md`/REQ-010/REQ-011 precedent, and
this spec follows that precedent rather than diverging from it.

**Verification kind: scripted docker/psql checklist** — same shape as
`docs/agents/test-specs/REQ-011.md`, not a Vitest integration test (no reusable
spin-up-Postgres-in-CI fixture exists yet in this repo, per REQ-011's spec; building
one here would be inventing test infrastructure off-handedly, the same reason REQ-011
declined to).

This migration (`0007_sturdy_network.sql`) is additive on top of every prior migration
(0000–0006), so all seven files must be applied in order before AC1 runs.

## AC1 — `invite_codes` table shape: UUID PK, created/updated timestamps, all seven data columns

> "The migration creates an invite_codes table with a UUID primary key,
> created/updated timestamps, and columns for event_id, code, issued_to_user_id,
> grants_companion_of, max_uses, used_count and expires_at — verified by applying the
> migration to a scratch Postgres database and pasting the resulting schema into the
> verification report (PRD 5)."

Steps:
```bash
docker exec req033-pg-verify psql -U postgres -d verify -c '\d+ invite_codes'
```

Expected — the pasted output must show all of:
- `id` — `uuid`, `not null`, default `gen_random_uuid()`, listed as
  `"invite_codes_pkey" PRIMARY KEY, btree (id)`.
- `event_id` — `uuid`, `not null`.
- `code` — `text`, `not null`.
- `issued_to_user_id` — `uuid`, nullable (no `not null`).
- `grants_companion_of` — `uuid`, nullable.
- `max_uses` — `integer`, `not null`.
- `used_count` — `integer`, `not null`, default `0`.
- `expires_at` — `timestamp with time zone`, nullable.
- `created_at` — `timestamp with time zone`, `not null`, default `now()`.
- `updated_at` — `timestamp with time zone`, `not null`, default `now()`.
- Foreign-key list includes `invite_codes_event_id_events_id_fk`,
  `invite_codes_issued_to_user_id_users_id_fk`,
  `invite_codes_grants_companion_of_users_id_fk`, each `ON DELETE RESTRICT`.
- Index list includes `"invite_codes_code_unique" UNIQUE, btree (code)`.

This case fails if any column is missing, has the wrong type/nullability/default, or if
any of the three FKs or the unique index is absent or has a different delete rule.

## AC2 — `invite_codes.code` UNIQUE constraint is enforced

> "invite_codes.code carries a UNIQUE constraint that is actually enforced: verified
> by inserting the same code value twice against the scratch database and confirming
> the second insert fails with a unique-violation error. Reading the schema is not
> sufficient; the duplicate insert must be attempted."

Steps:
```bash
docker exec req033-pg-verify psql -U postgres -d verify -c "INSERT INTO invite_codes (event_id, code, max_uses) VALUES ('$EVENT_ID', 'CODE1TESTDUPLICATEVALUEAA', 5) RETURNING id;"
docker exec req033-pg-verify psql -U postgres -d verify -c "INSERT INTO invite_codes (event_id, code, max_uses) VALUES ('$EVENT_ID', 'CODE1TESTDUPLICATEVALUEAA', 5);"
```

Expected:
- First insert → `INSERT 0 1`, one UUID returned. Record as `$BULK_CODE_ID`.
- Second insert (same `code`, different row) → fails with:
  ```
  ERROR:  duplicate key value violates unique constraint "invite_codes_code_unique"
  DETAIL:  Key (code)=(CODE1TESTDUPLICATEVALUEAA) already exists.
  ```

This case fails if the second insert succeeds, or fails under a different constraint
name.

## AC3 — `issued_to_user_id`/`grants_companion_of` nullable FKs to `users.id`

> "invite_codes.issued_to_user_id and invite_codes.grants_companion_of are both
> nullable and both reference users.id, verified by inserting a bulk code supplying
> neither (must succeed) and a code whose issued_to_user_id names a non-existent user
> id (must fail on the foreign key) — both cases run (PRD 5)."

Steps:
```bash
docker exec req033-pg-verify psql -U postgres -d verify -c "INSERT INTO invite_codes (event_id, code, issued_to_user_id, grants_companion_of, max_uses) VALUES ('$EVENT_ID', 'BULKCODENONEITHERCOLB', NULL, NULL, 10) RETURNING id;"
```
Expected: `INSERT 0 1` — the bulk shape (neither column set) succeeds. Record the
returned id as `$BULK_CODE_ID_2` (independent of AC2's row).

```bash
docker exec req033-pg-verify psql -U postgres -d verify -c "INSERT INTO invite_codes (event_id, code, issued_to_user_id, max_uses) VALUES ('$EVENT_ID', 'PERSONALCODEBADUSERC', '00000000-0000-0000-0000-000000000000', 1);"
```
Expected: fails with:
```
ERROR:  insert or update on table "invite_codes" violates foreign key constraint "invite_codes_issued_to_user_id_users_id_fk"
DETAIL:  Key (issued_to_user_id)=(00000000-0000-0000-0000-000000000000) is not present in table "users".
```

As a companion positive/negative pair for `grants_companion_of` (not separately named
in the AC text but the same column-pair claim, verified the same way):
```bash
docker exec req033-pg-verify psql -U postgres -d verify -c "INSERT INTO invite_codes (event_id, code, grants_companion_of, max_uses) VALUES ('$EVENT_ID', 'COMPANIONBADUSERCODE', '00000000-0000-0000-0000-000000000000', 1);"
```
Expected: fails the same way, naming `invite_codes_grants_companion_of_users_id_fk`.

This case fails if the neither-set bulk insert fails, if either bad-FK insert
succeeds, or if either bad-FK insert fails under a different constraint name.

## AC4 — `registrations.invite_code_id` is a real FK to `invite_codes.id`

> "registrations.invite_code_id is a real FOREIGN KEY to invite_codes.id after this
> migration, verified by attempting to insert a registration whose invite_code_id
> names a non-existent invite_codes row and confirming it FAILS — an insert that
> succeeds proves the FK was not added and is a FAIL of this criterion (REQ-011.md §11
> open question 3, closed here)."

Steps:
```bash
docker exec req033-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, invite_code_id) VALUES ('$EVENT_ID', '$USER_ID', 'self', '00000000-0000-0000-0000-000000000000');"
```

Expected: fails with:
```
ERROR:  insert or update on table "registrations" violates foreign key constraint "registrations_invite_code_id_invite_codes_id_fk"
DETAIL:  Key (invite_code_id)=(00000000-0000-0000-0000-000000000000) is not present in table "invite_codes".
```

This is the load-bearing negative case for the whole requirement: if this insert
**succeeds**, the FK was never actually added (the column is still a plain UUID) and
this criterion — and by extension the requirement's core purpose — is a FAIL,
regardless of what AC1's `\d+` output showed (a `\d+` listing can be misread; an
actual rejected insert cannot).

As positive confirmation the FK accepts a real `invite_codes` row, reuse `$BULK_CODE_ID`
from AC2:
```bash
docker exec req033-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, invite_code_id) VALUES ('$EVENT_ID', '$USER_ID', 'self', '$BULK_CODE_ID') RETURNING id;"
```
Expected: `INSERT 0 1`, one UUID returned. Record as `$REG_ID` — needed by AC5.

This case fails if the bad-id insert succeeds, or if the real-id insert fails.

## AC5 — Deleting a referenced `invite_codes` row is refused (RESTRICT)

> "Deleting an invite_codes row that a registration references is refused by the
> database, verified by constructing exactly that pair and attempting the delete (the
> restrict posture this requirement's design states)."

Uses the exact pair from AC4: `$BULK_CODE_ID` (an `invite_codes` row) referenced by
`$REG_ID` (a `registrations` row).

Steps:
```bash
docker exec req033-pg-verify psql -U postgres -d verify -c "DELETE FROM invite_codes WHERE id = '$BULK_CODE_ID';"
```

Expected: fails with:
```
ERROR:  update or delete on table "invite_codes" violates foreign key constraint "registrations_invite_code_id_invite_codes_id_fk" on table "registrations"
DETAIL:  Key (id)=($BULK_CODE_ID) is still referenced from table "registrations".
```

As positive confirmation the row still exists afterward (the delete was refused, not
silently no-op'd for some other reason):
```bash
docker exec req033-pg-verify psql -U postgres -d verify -c "SELECT id FROM invite_codes WHERE id = '$BULK_CODE_ID';"
```
Expected: one row returned, matching `$BULK_CODE_ID`.

This case fails if the delete succeeds, or if the row is absent from the follow-up
`SELECT` (which would indicate a cascade-delete or cascade-null happened instead of a
refusal).
