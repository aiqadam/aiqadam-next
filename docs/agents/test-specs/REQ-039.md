**On AC3's wording (SECURITY-REVIEWER's note, `handoffs/WF02-REQ-039/step-02c-security-reviewer.json`):**
GitHub issue #71's AC3 literally reads "ZERO new `users` rows, ZERO new `profiles` rows, ZERO new
`registrations` rows." Taken completely literally this does not hold, because the PRE-EXISTING
(REQ-014, unrelated to this requirement) `/start` handler's `resolveOrCreateUser` unconditionally
inserts a bare `users` row (`tg_id`/`tg_username`/`lang` only, no PII, `consent_pd_at` still null)
for every brand-new Telegram contact, before `hasConsented` is even evaluated — this is not a write
this requirement introduces and is identical across every `/start` entry point (REQ-038's own
`redeem.db.test.ts` AC9 case already treats this the same way, asserting on `profiles`/
`registrations` counts and `consentPdAt`, never on "zero users rows"). Verifying AC3's actual
security-critical substance therefore means: **zero new `profiles` rows, zero new `registrations`
rows, and the baseline `users` row (if any) carries no PII beyond its REQ-014 shape** — checked
below by asserting `consentPdAt`/`chapterId` stay null and no name/phone/company exists anywhere
for that guest (there is nowhere on `users` to even put such a value — confirmed by reading
`schema.ts`'s `users` table definition, which has no name/phone/company column at all; the only
place such data could land is `profiles`, whose row count is asserted zero). This is not a weakened
check — it verifies the exact property AC3 is protecting (S1, STORY-DETAILS B8's "storing anything
before consent" refusal), just scoped to the tables the property is actually about.

// Drives one brand-new guest through the full flow: /start i_<code>, consent
// tap, field reply, confirm tap. Returns the captured bot messages and the
// invite code id for follow-up assertions.
async function runFullCompanionFlow(
  bot: Bot,
  captured: Captured[],
  tgId: number,
  code: string,
  fields: { name: string; company: string; phone: string },
): Promise<{ inviteCodeId: string }> {
  await bot.handleUpdate(commandUpdate(tgId, `/start i_${code}`) as never); // consent prompt
  await bot.handleUpdate(consentAgreeCallbackUpdate(tgId, `i_${code}`) as never); // -> field prompt
  const fieldPromptText = textOf(lastSendOrEdit(captured));

  const codeRow = await db
    .select({ id: schema.inviteCodes.id })
    .from(schema.inviteCodes)
    .where(eq(schema.inviteCodes.code, code));
  const inviteCodeId = codeRow[0]!.id;

  await bot.handleUpdate(
    replyUpdate(tgId, `${fields.name} | ${fields.company} | ${fields.phone}`, fieldPromptText) as never,
  ); // -> confirm message
  const confirmText = textOf(lastSendOrEdit(captured));

  await bot.handleUpdate(companionConfirmCallbackUpdate(tgId, inviteCodeId, confirmText) as never); // -> the write

  return { inviteCodeId };
}
