### AC2a — 3-row ordering, checked before AND after the flip

  const eventId = /* seedPublishedEvent(chapterId, { capacity: 0 }) */;

  right, not just the delta), the after-state is exactly `{null, 1, 2}`, and Q's
  `updated_at` is unchanged down to the millisecond. A run where the before-state is
  wrong (would mean the base ranking itself is broken, not just the flip-response), where
  R's position fails to also shift 3→2 (would mean only the immediately-adjacent row
  updates, revealing a hidden off-by-one instead of a true re-derivation from scratch), or
  where Q's `updated_at` changed at all, is a FAIL — the last of these is the exact
  regression AC2 exists to catch: any write to a row whose own registration state never
  changed.

### AC2b — the `created_at`/`id` tie-break (design §2.3), not exercised by any committed test

**Order-independence is checked as 3 loop iterations inside this one script invocation
(one process, run once) — NOT by re-invoking the whole script 3 times as separate
`npx tsx` processes.** Re-invoking the whole script as separate processes was this AC's
original design, but it is mechanically unsafe: this script's fixtures (AC2a's chapter,
AC2c's chapter, and this case's own rows) use fixed, non-varying identifiers, and
`apps/bot/src/db/schema.ts`'s `chapters_code_unique` (line 54) and `users_tg_id_unique`
(line 94) would reject run 2 and run 3 as duplicates of what run 1 already committed —
crashing on a real constraint violation instead of exercising order-independence. Running
the 3 repetitions as loop iterations inside one process sidesteps this entirely: each
iteration seeds its own fresh chapter/event/pair-of-users via a script-local counter (the
same idiom `registration.db.test.ts` lines 52–54/56–83 already establishes with
`chapterSeq`/`userSeq`/`tgSeq`), so within-process uniqueness is trivial and no
cross-process uniqueness strategy is ever needed:

- Same script, continuing after AC2a. Declare one script-local counter, then loop 3
  times, each iteration seeding a wholly fresh chapter/event/two-users fixture and
  independently re-checking the tie-break:
  ```ts
  let tieIterSeq = 0; // script-local counter, mirrors registration.db.test.ts's chapterSeq/tgSeq idiom

  const tieResults: { lowerIdPosition: number | null; higherIdPosition: number | null }[] = [];
  for (let iter = 0; iter < 3; iter++) {
    tieIterSeq += 1;
    const chapterIdN = /* seedChapter(`r21a2-tie-${tieIterSeq}`) */; // e.g. "r21a2-tie-1", "r21a2-tie-2", "r21a2-tie-3"
    const eventIdN = /* seedPublishedEvent(chapterIdN, { capacity: 0 }) */;
    const userS = /* seedUser() */; // tg_id derived from this script's own counter, e.g. 1000000450 + tieIterSeq*2
    const userT = /* seedUser() */; // tg_id = the above + 1
    const tieInstant = new Date("2026-11-02T00:00:00.000Z"); // same literal instant every iteration -- the tie itself never changes, only the fixture identities around it
    const [rowS, rowT] = await db.insert(registrations).values([
      { eventId: eventIdN, userId: userS, admission: "waitlisted", source: "direct", createdAt: tieInstant },
      { eventId: eventIdN, userId: userT, admission: "waitlisted", source: "direct", createdAt: tieInstant },
    ]).returning({ id: registrations.id });
    // Sort the two returned ids lexicographically to know, independently of insertion
    // order, which one the tie-break rule (§2.3: lower id is "ahead") predicts as position 1.
    const [lowerIdRow, higherIdRow] = [rowS, rowT].sort((a, b) => (a.id < b.id ? -1 : 1));
    const result = {
      lowerIdPosition: await getWaitlistPosition(db, eventIdN, lowerIdRow.id),
      higherIdPosition: await getWaitlistPosition(db, eventIdN, higherIdRow.id),
    };
    console.log(`tie-break iter ${iter}`, result);
    tieResults.push(result);
  }
  console.log("tie-break all 3 iterations", tieResults);
  ```
- Expected: all 3 entries of `tieResults` read exactly `{ lowerIdPosition: 1,
  higherIdPosition: 2 }` — regardless of which of `rowS`/`rowT` happened to be inserted
  first, the row with the lexicographically lower `id` value is the one
  `getWaitlistPosition` reports as ahead, per design §2.3's explicit, arbitrary-but-fixed
  rule. Each iteration seeds a brand-new, otherwise-empty event, so Postgres's physical
  row-return order for that iteration's 2-row `INSERT ... VALUES (...), (...)` is free to
  vary iteration to iteration (nothing pins it) — exactly the source of nondeterminism
  this case must prove the tie-break is immune to, now exercised 3 independent times
  without any cross-process state to collide on.
- Pass conditions: all 3 loop iterations produce `{ lowerIdPosition: 1, higherIdPosition:
  2 }` — the tie-break must depend only on the `id` comparison, never on insertion or scan
  order, and this must hold on every one of the 3 independently-seeded iterations, not
  just the first. A run where any iteration has either row reading `null`, both rows
  reading the same position, or the reported "ahead" row is NOT the lower-`id` one, is a
  FAIL — this is the exact regression this case exists to catch: a `created_at`-only
  comparison that returns a non-deterministic or duplicate position when two rows tie,
  breaking §2.4's "same set of waitlisted rows always yields the same positions on
  repeated reads" guarantee.
