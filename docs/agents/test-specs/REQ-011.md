# Test spec — REQ-011 (Bot data model and migration: Venue, Event, Registration, EventStaff, AuditLog)

## Verification kind: scripted docker/psql checklist (not a Vitest integration test)

**Call:** same shape as `docs/agents/test-specs/REQ-010.md` — exact `docker run`/`psql`
commands with exact expected output, not a Vitest test file spinning up its own Postgres.

**Reasoning (unchanged from REQ-010, not re-litigated):** every acceptance criterion here
is a property of *the migration applied to a real Postgres* (unique-constraint behavior,
enum rejection, JSONB path-query behavior, `\d+` schema shape) — decision
`0006-test-framework-vitest.md`'s driving cases are clock-dependent bot *logic* made
testable in-process via fake timers; nothing here is that. No reusable
spin-up-Postgres-in-CI fixture exists yet in this repo (REQ-012, still pending per
`docs/agents/requirements.yaml`, is what will eventually wire a persistent runtime
connection/migration runner — its scope is not a reusable ephemeral test fixture either).
Building that fixture inside this one data-model requirement's test design would be
inventing test infrastructure off-handedly, which REQ-010's spec already declined to do
for the same reason; this spec follows that precedent rather than diverging.

This migration is additive on top of REQ-010's `chapters`/`users`/`profiles` (design §9.6),
so both migration files must be applied in order.

## AC1 — UUID primary keys and created/updated timestamps on all five tables

> "The migration creates venues, events, registrations, event_staff and audit_log with
> UUID primary keys and created/updated timestamps, verified by applying it to a scratch
> Postgres database and pasting the resulting schema into the verification report."

Steps:
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c '\d+ venues'
docker exec req011-pg-verify psql -U postgres -d verify -c '\d+ events'
docker exec req011-pg-verify psql -U postgres -d verify -c '\d+ registrations'
docker exec req011-pg-verify psql -U postgres -d verify -c '\d+ event_staff'
docker exec req011-pg-verify psql -U postgres -d verify -c '\d+ audit_log'
```

Expected (all five tables):
- An `id` column: type `uuid`, `not null`, default `gen_random_uuid()`, listed as the
  table's `"<table>_pkey" PRIMARY KEY, btree (id)` index.
- A `created_at` column: type `timestamp with time zone`, `not null`, default `now()`.
- An `updated_at` column: type `timestamp with time zone`, `not null`, default `now()`.

This case fails if any of the five tables' `\d+` output is missing any of the three
properties above on any of the three columns.

## AC2 — `UNIQUE(event_id, user_id)` on `registrations` is enforced

> "A UNIQUE constraint on registrations(event_id, user_id) exists and is enforced,
> verified by inserting the same (event_id, user_id) pair twice against the scratch
> database and confirming the second insert fails with a unique-violation error (PRD
> 12.1) — reading the schema is not sufficient; the duplicate insert must actually be
> attempted."

Steps:
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source) VALUES ('$EVENT_ID', '$USER_ID', 'self');"
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source) VALUES ('$EVENT_ID', '$USER_ID', 'self');"
```

Expected:
- First insert → `INSERT 0 1`.
- Second insert → fails with:
  ```
  ERROR:  duplicate key value violates unique constraint "uq_registrations_event_user"
  DETAIL:  Key (event_id, user_id)=($EVENT_ID, $USER_ID) already exists.
  ```
  (constraint name grepped from `apps/bot/drizzle/0001_tired_annihilus.sql` line 90:
  `CREATE UNIQUE INDEX "uq_registrations_event_user" ON "registrations" USING btree
  ("event_id","user_id")`.)

This case fails if the second insert succeeds, or if it errors under a different
constraint name than `uq_registrations_event_user`.

## AC3 — `registrations.qr_token` is UNIQUE and nullable

> "registrations.qr_token is UNIQUE and nullable, verified by inserting two registrations
> with NULL qr_token (both succeed) and two with the same non-null token (second fails)."

Steps (each insert uses a distinct `user_id` to avoid colliding with AC2's
`uq_registrations_event_user` constraint — seed two more users first):
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (555000222) RETURNING id;"
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (555000333) RETURNING id;"
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (555000444) RETURNING id;"
```
Expected: all three `INSERT 0 1`, each returning a UUID — record as `$USER_ID_2`,
`$USER_ID_3`, `$USER_ID_4`.

```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, qr_token) VALUES ('$EVENT_ID', '$USER_ID_2', 'self', NULL);"
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, qr_token) VALUES ('$EVENT_ID', '$USER_ID_3', 'self', NULL);"
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, qr_token) VALUES ('$EVENT_ID', '$USER_ID_4', 'self', 'tok_abc123');"
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (555000555) RETURNING id;"
```
Expected: first three all `INSERT 0 1`; the fourth (a fresh user, `$USER_ID_5`) returns
a UUID.
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, qr_token) VALUES ('$EVENT_ID', '$USER_ID_5', 'self', 'tok_abc123');"
```

Expected:
- Both NULL-`qr_token` inserts → `INSERT 0 1` each (Postgres's standard
  multiple-NULLs-distinct unique-index behavior, same mechanism REQ-010 used for
  `users.tg_id`).
- First non-null `tok_abc123` insert → `INSERT 0 1`.
- Second non-null `tok_abc123` insert (different `user_id`, so `uq_registrations_event_user`
  does not also fire) → fails with:
  ```
  ERROR:  duplicate key value violates unique constraint "registrations_qr_token_unique"
  DETAIL:  Key (qr_token)=(tok_abc123) already exists.
  ```
  (constraint name grepped from `apps/bot/drizzle/0001_tired_annihilus.sql` line 91:
  `CREATE UNIQUE INDEX "registrations_qr_token_unique" ON "registrations" USING btree
  ("qr_token")`.)

This case fails if either NULL insert errors, if the duplicate non-null insert succeeds,
or if it errors under a different constraint name.

## AC4 — `admission` enum accepts exactly the five PRD 6 values, rejects a sixth

> "The registrations.admission enum/check accepts exactly the five PRD 6 values
> (requested, waitlisted, admitted, rejected, withdrawn) and rejects a sixth — verified by
> attempting an insert with admission='checked_in' and confirming it fails, proving
> attendance was not modelled as an admission state (PRD 6)."

Steps (fresh user to avoid the AC2/AC3 unique constraints):
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (555000666) RETURNING id;"
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, admission) VALUES ('$EVENT_ID', '$USER_ID_6', 'self', 'checked_in');"
```
(`$USER_ID_6` is the UUID returned by the first command above.)

Expected: the insert fails with:
```
ERROR:  invalid input value for enum admission: "checked_in"
```
(exact wording as produced by Postgres 16 for an unrecognized value against the native
`admission` ENUM type created by `apps/bot/drizzle/0001_tired_annihilus.sql` line 1:
`CREATE TYPE "public"."admission" AS ENUM('requested', 'waitlisted', 'admitted',
'rejected', 'withdrawn')`.)

As positive confirmation the five real values are accepted, also run:
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, admission) VALUES ('$EVENT_ID', '$USER_ID_6', 'self', 'withdrawn');"
```
Expected: `INSERT 0 1`.

This case fails if the `'checked_in'` insert succeeds, or if it fails with any error
other than an enum-input-value rejection (e.g. a generic type-cast error would still
indicate the enum is doing its job, but the exact message above is what TEST-RUNNER
should see against this migration's real enum name — a different enum name in the error
text is itself a regression signal worth flagging even if the insert still fails).

## AC5 — No column for a PRD 5 computed-never-stored value; `no_show_reason` is present and distinct

> "No column named no_show, waitlist_position, seats_taken, registration_open or finished
> exists in any table created by this migration, verified by grepping the migration for
> each name (PRD 5 computed-never-stored); the stored column no_show_reason is present and
> is explicitly distinguished from the derived no_show in the design artefact."

**Forbidden-name check** (run from the repo root, not inside the container):
```bash
grep -inE "no_show[^_]|no_show$|waitlist_position|seats_taken|registration_open|finished" apps/bot/drizzle/0001_tired_annihilus.sql
```
Expected: no output, exit code `1` (grep's "no match" exit code). Note the pattern
`no_show[^_]|no_show$` is deliberately written so it matches a bare `no_show` column
but does NOT match `no_show_reason` — these are two different things and this check must
not conflate them (see the separate positive check below).

**`no_show_reason` positive check** (a SEPARATE check — this column DOES exist and its
presence is correct, not a violation of the forbidden-name grep above):
```bash
grep -n "no_show_reason" apps/bot/drizzle/0001_tired_annihilus.sql
docker exec req011-pg-verify psql -U postgres -d verify -c '\d+ registrations' 
```
Expected: the grep prints exactly one match, line 58: `"no_show_reason" text,`. The `\d+
registrations` output lists `no_show_reason` as a `text`, nullable column. Also confirm
the design artefact keeps the two concepts distinct:
```bash
grep -n "derived.*no_show\|no_show.*derived" docs/agents/design/REQ-011.md
```
Expected: at least one match — the design's §5 states `no_show_reason` "is a real stored
column and is not part of this table — it is listed here only to repeat, once more, that
it must never be confused with the derived `no_show` boolean above, which has no column
anywhere."

This case fails if the forbidden-name grep produces any output (exit code `0`), if the
`no_show_reason` grep produces zero matches, or if `\d+ registrations` does not list
`no_show_reason` as a real column.

## AC6 — `agenda[]` doors-item query, and no `doors_at` column

> "An agenda[] item's shape supports identifying a doors item programmatically: storing an
> event whose agenda holds a doors item PLUS at least one non-doors item (networking,
> close), a single database query returns the doors item's time and only that item —
> WITHOUT the application loading the whole agenda and scanning it in TypeScript, which is
> the free-text outcome this constraint exists to prevent. Verified by exhibiting the
> actual query and its result. NO doors_at or equivalently-named column may exist on the
> events table (grep the migration to confirm), per PRD 5 de-duplication."

Steps — insert a second event carrying a 3-item agenda (doors + 2 non-doors), matching
the design doc §3's own worked example exactly:
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO events (chapter_id, title, description, format, venue_id, starts_at, ends_at, capacity, agenda) VALUES ('$CHAPTER_ID', 'Agenda Test Event', 'A test event with agenda', 'meetup', '$VENUE_ID', '2026-10-01T15:00:00Z', '2026-10-01T19:00:00Z', 100, '[{\"kind\":\"doors\",\"at\":\"2026-10-01T15:00:00Z\",\"label\":\"Doors open\"},{\"kind\":\"networking\",\"at\":\"2026-10-01T15:30:00Z\",\"label\":\"Networking\"},{\"kind\":\"close\",\"at\":\"2026-10-01T19:00:00Z\",\"label\":\"Doors close\"}]') RETURNING id;"
```
Expected: `INSERT 0 1`, one UUID returned. Record it as `$AGENDA_EVENT_ID`.

Run BOTH JSONB queries from `docs/agents/design/REQ-011.md` §3, substituting
`$AGENDA_EVENT_ID` for `$1`:

**Query 1 (`jsonb_path_query_first`):**
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "SELECT jsonb_path_query_first(agenda, '\$[*] ? (@.kind == \"doors\").at') FROM events WHERE id = '$AGENDA_EVENT_ID';"
```
Expected output (exactly one row, one column):
```
 jsonb_path_query_first
-------------------------
 "2026-10-01T15:00:00Z"
(1 row)
```

**Query 2 (`jsonb_array_elements` + `@>`/`->>`):**
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "SELECT elem->>'at' AS doors_at FROM events, jsonb_array_elements(agenda) AS elem WHERE events.id = '$AGENDA_EVENT_ID' AND elem @> '{\"kind\":\"doors\"}'::jsonb;"
```
Expected output (exactly one row, one column):
```
       doors_at
-----------------------
 2026-10-01T15:00:00Z
(1 row)
```

Both queries must return exactly one row containing only the doors item's `at` value
(`2026-10-01T15:00:00Z`) — neither the networking item's `2026-10-01T15:30:00Z`, nor the
close item's `2026-10-01T19:00:00Z`, nor the full array, may appear in either result.

**No `doors_at` column check:**
```bash
grep -inE "doors_at" apps/bot/drizzle/0001_tired_annihilus.sql
```
Expected: no output, exit code `1`.

This case fails if either query returns zero rows, more than one row, or a value other
than `2026-10-01T15:00:00Z`; or if the `doors_at` grep produces any output.

## Additional invariant case — S6 CHECK constraint (not one of the 7 literal ACs)

**Why this case exists even though it is not a numbered acceptance criterion:**
SECURITY-REVIEWER already found and verified that `apps/bot/src/db/schema.ts` and
`apps/bot/drizzle/0001_tired_annihilus.sql` (line 61) implement
`CONSTRAINT "chk_registrations_checked_in_only_if_admitted" CHECK ("registrations"."checked_in_at"
IS NULL OR "registrations"."admission" = 'admitted')` — a real, DB-level enforcement of
S6 ("attendance is not an admission state; `checked_in_at` may not be set on a
registration that is waitlisted, withdrawn, requested, or rejected"). This is a genuine
invariant this migration adds, distinct from AC4 (which only tests that `admission`
itself rejects a sixth enum value, not that `checked_in_at` and `admission` are kept
consistent with each other). Without a precise case for it here, a future migration could
silently drop this CHECK and nothing in the 7 literal ACs would catch the regression.

Steps (fresh user to avoid earlier unique constraints):
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO users (tg_id) VALUES (555000777) RETURNING id;"
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, admission, checked_in_at) VALUES ('$EVENT_ID', '$USER_ID_7', 'self', 'requested', now());"
```
(`$USER_ID_7` is the UUID returned by the first command.)

Expected: the second insert fails with:
```
ERROR:  new row for relation "registrations" violates check constraint "chk_registrations_checked_in_only_if_admitted"
```

As positive confirmation the same `checked_in_at` value IS accepted once `admission` is
`'admitted'`:
```bash
docker exec req011-pg-verify psql -U postgres -d verify -c "INSERT INTO registrations (event_id, user_id, source, admission, checked_in_at) VALUES ('$EVENT_ID', '$USER_ID_7', 'self', 'admitted', now());"
```
Expected: `INSERT 0 1`.

This case fails if the first (`requested` + non-null `checked_in_at`) insert succeeds, if
it fails under any constraint name other than `chk_registrations_checked_in_only_if_admitted`,
or if the second (`admitted` + non-null `checked_in_at`) insert is rejected.
