# REQ-040 — Named invitation list with derived outreach status and account linking

**Role:** CODE-DESIGNER (design only — no implementation code; BACKEND-DEV implements
this artefact). **DATA-DESIGNER follow-up required** — this requirement needs a new
table; §3 states exactly what is deferred and why it is not designed here.

**Composes, does not reimplement:** REQ-010's nullable-`tg_id` `users` row (§1),
REQ-037's `issuePersonalInviteCode` (§4), REQ-020/028/029's registration/check-in state
(§2). No second code generator, no second "guest" table, no parallel identity concept.

---

## 0. Re-verified against the live schema/domain code

- `apps/bot/src/db/schema.ts`'s `users` table: `tgId` is nullable, `users_tg_id_unique`
  is a plain unique index (Postgres treats multiple `NULL`s as distinct under a unique
  index — REQ-010's own proven property, unchanged). Confirmed no new column is needed
  on `users` itself for this requirement.
- `apps/bot/src/domain/inviteCode.ts`: `issuePersonalInviteCode`, `redeemInviteCode`,
  `validateInviteCodeForRedemption`, `getInviteCodeByCode` read exactly as REQ-037/038/039
  left them — reused unchanged (§4, §5).
- `apps/bot/src/handlers/start.ts`'s `makeStartHandler`: **load-bearing finding** for this
  design. `resolveOrCreateUser` is called unconditionally, keyed on `tg_id`, at the very
  top of the handler, *before* `parseStartPayload` is even evaluated. This means that
  today, a personal invite code issued to a pre-created (`tg_id NULL`) row is
  **unreachable by its intended redeemer**: the first-ever `/start` from that real person
  creates a *brand-new* `users` row keyed on their own `tg_id` (not the pre-created row),
  and `redeemInviteCode`'s `validateInviteCodeForRedemption` then refuses with
  `"not-yours"` because `issuedToUserId` (the pre-created row's id) never equals
  `redeemerUserId` (the new row's id). **This is exactly the gap PRD FR-17 and REQ-014's
  deferred note describe, and §2 below is this requirement's resolution of it — not a
  pre-existing bug report, but the reason this requirement exists at all.**

## 1. Pre-created guest — no schema change, reused mechanism

Adding a never-contacted guest to a list creates exactly one `users` row via a plain
`INSERT` — `tg_id`, `tg_username`, `lang`, `chapter_id`, `consent_pd_at` all left at their
schema defaults/`NULL` (identical shape to REQ-010's proof, not a variant of it). No
`profiles` row is written by this action (§3's business-card fields live on the new
list-entry table itself, not `profiles` — reasoning in §3.4).

`createNamedGuestUser(db, tx): Promise<{ id: string }>` — a thin, one-purpose wrapper
that performs exactly this `INSERT` and nothing else. Not `resolveOrCreateUser` (which is
keyed on `tg_id`, always required there) — this is a distinct creation path with no
`tg_id` input at all, so it is its own function, called only from the list-entry "add"
flow (§4.1), inside the same transaction as the list-entry `INSERT` and the audit write.

## 2. Account linking on first contact — resolution

### 2.1 The two readings and why code-based matching is the only one that composes

STORY-DETAILS F9 states the match is "by the code." `invite_codes.issued_to_user_id`
already points at the pre-created row (REQ-037), so redemption is what must special-case
identity resolution — not `/start` in general, and not every deep link, only the
`i_<code>` personal-invite payload.

### 2.2 New pre-`resolveOrCreateUser` identity-resolution step

A new domain function, `resolvePersonalCodeIdentity`, runs **before**
`resolveOrCreateUser` is called, and **only** when `parseStartPayload` returns
`kind: "invite"` — every other payload kind (`event`, `checkin`, `none`) is completely
unaffected; `resolveOrCreateUser` runs exactly as it does today for them.

```
resolvePersonalCodeIdentity(
  db: DbClient["db"],
  rawCode: string,
  callerTgId: bigint,
  callerTgUsername: string | null,
  callerLang: BotLang | null,
): Promise<
  | { kind: "not-applicable" }               // code unknown, or not a personal code
  | { kind: "linked"; userId: string }        // pre-created row just linked to this tgId
  | { kind: "collision-relinked"; userId: string } // see §2.4
>
```

**Rule table** (no comparison written as code — stated as the decision each branch makes):

| Condition on the normalized code | Condition on `issuedToUserId`'s own row (call it **A**) | Condition on any row already holding `callerTgId` (call it **B**) | Outcome |
|---|---|---|---|
| Code not found, or found but `issuedToUserId` is `null` (bulk/companion shape) | — | — | `not-applicable` — caller falls through to the unmodified `resolveOrCreateUser` flow |
| Personal code found | Target row **A** not found (defensive; FK guarantees this in practice) | — | `not-applicable` |
| Personal code found | **A**.`tgId` is already non-null (already linked, or the code targets an existing member, REQ-037's ordinary case) | — | `not-applicable` — `resolveOrCreateUser` resolves the caller's own row exactly as today; if that row is not **A**, `validateInviteCodeForRedemption`'s existing `"not-yours"` refusal correctly applies (the code was issued to a specific, different, already-real person) |
| Personal code found | **A**.`tgId` is `null` | No row **B** holds `callerTgId` | `linked` — see §2.3 |
| Personal code found | **A**.`tgId` is `null` | Row **B** holds `callerTgId` and **B**.id ≠ **A**.id | `collision-relinked` — see §2.4 |

### 2.3 The normal case — link, don't create

An atomic `UPDATE users SET tg_id = $callerTgId, tg_username = $callerTgUsername,
lang = $callerLang WHERE id = $A.id AND tg_id IS NULL`, returning the updated row.

- Writing `tg_id`/`tg_username`/`lang` here is the **same category of write** REQ-014
  already permits before consent (§2.4 of that design: "the User row itself is not gated
  behind consent... the minimal Telegram-native fields"). This UPDATE differs from
  `resolveOrCreateUser`'s existing INSERT-based creation only in *which* row it targets
  (an existing placeholder by `id`, not a fresh row by `tg_id`) — it introduces no new S1
  exposure.
- `WHERE ... AND tg_id IS NULL` is the concurrency guard: if two near-simultaneous taps
  somehow race (should not happen in practice — the same code, tapped by the same real
  person, twice), the second UPDATE affects zero rows. The caller re-reads: if the row's
  `tg_id` now equals `callerTgId`, the flow is idempotent and proceeds as `linked` anyway;
  otherwise treat as `not-applicable` and let `resolveOrCreateUser` + the existing
  `"not-yours"` refusal handle it safely.
- The caller (`makeStartHandler`) **skips calling `resolveOrCreateUser`** for this
  request and proceeds directly with `A.id`. The very next read, `getFlowUserByTgId(db,
  callerTgId)`, now correctly resolves row **A** (its `tg_id` was just set), so no new
  "resolve by id" helper is needed — the existing tg_id-keyed read is reused unchanged.
- **AC6 traced exactly:** the pre-created row's `id` is unchanged (an `UPDATE`, never a
  second `INSERT`), and the `users` table row count is unchanged (no new row created) —
  both are the literal, structural consequence of this being an `UPDATE ... WHERE id =`
  statement, not an assertion.

### 2.4 The hard case — existing separate account, resolved

**Resolution: relink the list entry to the existing account; the pre-created row is
retired as a permanently inert, unreachable orphan. Never a data merge across
`profiles`/`registrations`/`invite_codes`/`audit_log`, and never a refusal.**

Reasoning, traced against the three candidates the requirement names:

- **Refusal** is rejected: it would defeat this requirement's entire purpose for exactly
  the population it exists to serve — a VIP who has used the bot before (e.g. attended a
  past event under their own account) is the *most* likely collision case, and refusing
  their own pre-arranged personal code the one time it matters is a worse outcome than any
  bookkeeping cost.
- **A full data merge** (reassigning every FK — `registrations.userId`,
  `registrations.checkedInBy`, `registrations.invitedByUserId`, `invite_codes.
  issuedToUserId`, `invite_codes.grantsCompanionOf`, `eventStaff.userId`,
  `auditLog.actorUserId`, `profiles.userId` — from **B** onto **A**, or **A** onto **B**,
  resolving unique-constraint collisions such as two `profiles` rows or two
  `registrations` rows for the same event) is rejected as disproportionate: no
  requirement or existing code in this repository performs a cross-table identity merge,
  it would require inventing conflict-resolution rules this requirement's ACs never ask
  for, and it is far riskier than the alternative below for the same outcome.
- **The chosen resolution** only touches data *this requirement itself introduces* — the
  list-entry row(s) — never `registrations`/`profiles`/other identity-bearing tables:
  1. The redemption proceeds exactly as an ordinary `/start` from a returning user: no
     new row for **B** (it already exists), `resolveOrCreateUser` resolves **B**
     unchanged, and `redeemInviteCode` runs with `redeemerUserId = B.id`. For this to
     pass `validateInviteCodeForRedemption`'s `"not-yours"` check, the identity-resolution
     step returns `collision-relinked` and the caller substitutes `B.id` as the
     *effective* `issuedToUserId` for this one redemption (this is the one place this
     design diverges from "reuse `redeemInviteCode` unmodified": `redeemInviteCode`
     itself does not need to change — it is called with `redeemerUserId = B.id` and the
     precheck against `issuedToUserId` succeeds because the identity-resolution step,
     immediately before this call, **repoints `A`'s outstanding personal invite code(s)
     to `issuedToUserId = B.id`** in the same transaction the list entries are repointed
     in (below) — i.e. the code itself is corrected to name the real, now-known identity,
     the same way the list entry is).
  2. **Every** `invite_list_entries` row (DATA-DESIGNER's table, §3) whose `user_id = A.id`
     — across *all* events, not only the one being redeemed — is repointed to
     `user_id = B.id`, in the same transaction. Scoping to "all of A's entries" (not just
     the current event's) is deliberate: **A** is being permanently retired as an
     identity; leaving any other list referencing **A** unrepointed would silently break
     that list's own `registered`/`attended` derivation the same way this one would have.
  3. Row **A** itself is left in `users`, permanently `tg_id = NULL`, holding no
     reachable data once step 2 completes (its list entries and invite codes have been
     repointed away from it) — never deleted (other rows, e.g. an `audit_log` row for the
     original "add" action, may still name `A.id` as `entity_id`/appear in a payload, and
     `audit_log` is never rewritten). It is inert history, not a second live identity: no
     future `/start` can ever resolve to it again (its `tg_id` never becomes non-null),
     and it is no longer the target of any list entry or invite code. **This satisfies
     FR-17's "nobody is duplicated" as "no two rows are ever both reachable as the same
     person going forward," not as "the losing row is deleted."**
  4. One additional `AuditLog` row is written for this repointing, action
     `invite_list.entry_relinked`, `entity: "invite_list_entry"`, payload
     `{ fromUserId: A.id, toUserId: B.id, eventId }` per repointed entry — distinct from
     the add/remove audit actions (§5), so AC11's "adding and removing... exactly one row
     each" is not conflated with this separate, rarer event.
- **AC7 traced exactly:** before redemption, two live rows exist for one real person
  (**A**, pre-created, and **B**, their own prior account). After redemption, exactly one
  is reachable (`B`, via `tg_id`); `A` is retired. This is a stated, traced resolution —
  not silence.

### 2.5 Why this pre-check runs ahead of the consent gate

`resolvePersonalCodeIdentity` reads `invite_codes` and `users` rows unrelated to the
caller's own submitted data, and its only writes are the same category of minimal
identity fields REQ-014 §2.4 already established as ungated (§2.3), plus, in the collision
branch, a repoint of organizer-owned bookkeeping rows the caller never supplied data
into. No Profile write, no phone/email, nothing the caller told the bot about themselves.
Running it before the consent prompt (which needs a resolved `users.id` to check
`consent_pd_at` against in the first place) is structurally required, not a loosening of
S1 — S1 governs storing what a person tells the bot about *themselves*, which this step
never does.

## 3. Deferred to DATA-DESIGNER — new table

**Not designed here** (schema shape is DATA-DESIGNER's territory per this role's
constraint). What is being deferred, concretely:

### 3.1 Table needed

A new table, tentatively `invite_list_entries`, holding at minimum:

- `event_id` — FK `events.id`, `NOT NULL`.
- `user_id` — FK `users.id`, `NOT NULL` (points at the pre-created row at add-time;
  §2.4's collision path is the only thing that ever repoints it after creation).
- `invite_code_id` — FK `invite_codes.id`, **nullable** (issuing a code is a separate
  step from adding the entry, per STORY-DETAILS F9 — an entry can exist with no code yet).
- `added_by` — FK `users.id`, `NOT NULL` (the organizer who added the entry).
- `added_at` — `timestamptz`, `NOT NULL` (this codebase's convention is
  `createdAt`/`updatedAt` on every table — DATA-DESIGNER decides whether `added_at`
  duplicates or is simply `created_at` under this table's own name for that pair).
- `opened_at` — **nullable `timestamptz`** — §3.2 below states why this column exists
  and justifies it against PRD 5.
- Guest business-card fields for display before any real `Profile` exists — `name`,
  `company`, `position` (§3.4) — exact nullability/typing left to DATA-DESIGNER, matching
  `profiles`' own precedent of nullable optional fields.

**Recommendation, not a mandate:** a `UNIQUE(event_id, user_id)` index, mirroring
`registrations`' own `uq_registrations_event_user` precedent — the same person should not
appear twice on the same event's list. DATA-DESIGNER should also decide add/remove
semantics (hard `DELETE` on remove vs. a `removed_at`/`active` marker) — `audit_log`
already preserves the historical fact of every add/remove regardless of which the
schema chooses (§5), so this is a data-shape choice, not a correctness one.

### 3.2 `opened` — resolution: (a), a stored `opened_at`

**Chosen over (b) (derive from `tg_id` becoming non-null).** Reasoning:

- Reading (b) collapses `opened` and `registered` into the *same instant* for exactly the
  population this requirement exists to serve: §2.3's linking UPDATE sets `tg_id` at
  redemption time, which is the same moment admission is decided. A VIP who has never
  used the bot before would show `opened` and `registered` flipping together, destroying
  the funnel's diagnostic value (an organizer cannot see "opened, hasn't registered yet"
  — exactly the state that would prompt a follow-up nudge) for the flagship case
  (Uzcard/SAP/EPAM/etc. from RE-EVALUATION R5) this requirement was written for.
- Reading (b) is also **still true before this invitation existed** for anyone who has
  ever used the bot for something unrelated — a weak, misleading signal the issue text
  itself flags.
- **Justification against PRD 5's computed-not-stored discipline, stated explicitly (per
  the requirement's own instruction):** `opened_at` is not a case of storing a value that
  could instead be read off other tables — a deep-link tap that does not lead to a
  registration leaves **no other trace anywhere in this schema** (no `registrations` row,
  no `invite_codes.used_count` increment — the code is only consumed on a *successful*
  redemption, per `redeemInviteCode`'s step 9). This is the same category of genuinely
  unrecordable-otherwise event REQ-011/REQ-033 already accepted stored columns for
  (`invite_codes.used_count` itself, `registrations.no_show_reason`) — a fact with no
  other row to derive it from, not a convenience cache of something joinable.
- **Write site (traced, not left implicit):** written inside `resolveInviteDeepLink`
  (`apps/bot/src/handlers/start.ts`), at the exact point that function already performs
  its own `getInviteCodeByCode` read for companion-shape detection (today, line ~234) —
  i.e. **after** the consent gate, the same gate `used_count`'s eventual increment already
  waits behind. One `UPDATE invite_list_entries SET opened_at = $now WHERE invite_code_id
  = $codeRow.id AND opened_at IS NULL` (the `AND opened_at IS NULL` guard is the
  first-open-only rule — never overwritten on a repeat tap). Matched by `invite_code_id`,
  not `user_id` — precise even after §2.4's collision repoint, and correct for the
  ordinary case where a `user_id` could in principle appear on more than one list.
  A companion/bulk code, or a personal code with no matching list entry at all (an entry
  was never added — issuing a code is optional and separate from listing, §3.1), simply
  matches zero rows — a no-op, not an error.
- Distinct from `registered`: opened is recorded the moment consent is accepted and the
  code resolves, strictly before `decideRegistrationOutcome` runs — a guest who taps the
  link, consents, but abandons before finishing (e.g. the companion field-collection
  reply, or simply closes the chat) is `opened` and not `registered`, preserving the
  four-state funnel's value exactly as intended.

### 3.3 `registered`/`attended` — derivation query shape (DATA-DESIGNER confirms, not
invents)

No column, mirroring REQ-028/032's existing pattern exactly:

```
registered  := EXISTS registrations WHERE user_id = entry.user_id
                                       AND event_id = entry.event_id
                                       AND admission IN ('admitted', 'waitlisted', 'requested')
                                       -- exact admitted-vs-live-admission set is
                                       -- REQ-028's own live-counter definition, reused
                                       -- unchanged, not redefined here
attended    := registered AND that registration's checked_in_at IS NOT NULL
```

This is the same `registrations` JOIN shape `listInviteCodeRedeemers`
(`domain/inviteCode.ts`) already performs for a different purpose — reused as a query
pattern, not a new derivation rule. **AC4's before/after `updated_at` comparison on the
list-entry row holds structurally**: this query never issues an `UPDATE` against
`invite_list_entries` — it is a plain `SELECT ... LEFT JOIN registrations`.

### 3.4 Business-card fields — why not `profiles`, and the S1 boundary this draws

Organizer-supplied `name`/`company`/`position` for a person who has **never interacted
with the bot at all** does not fit the walk-in precedent
(`domain/profile.ts`'s `createWalkinProfile`, called only after `createWalkinUser` stamps
`consent_pd_at` at the same moment — a verbal, in-person consent asserted at the door).
There is no equivalent assertion available for someone who has never been contacted.

**Resolution:** these fields live on `invite_list_entries` itself (§3.1), not on
`profiles`, and are explicitly **not** gated by S1's `consent_pd_at` framework — reasoning:
S1 concerns data a person gives *to the bot/organization through it*; here the organizer
is recording information they already independently possess (a business card, a known
contact) on their **own** organizer-side list, structurally no different from an
organizer's private spreadsheet the bot is replacing (RE-EVALUATION R5's own framing).
This also cleanly satisfies S3's "never phone/email" for this surface: the list-entry
table's schema simply never has phone/email columns to begin with, so there is no
runtime filter that could be bypassed (§4.2's "structural exclusion" pattern, same
discipline `listInviteCodeRedeemers` already uses).

Once the guest actually registers (redeems the code, and — per REQ-019's existing
onboarding — completes a real, consent-gated `profiles` row), **the list's rendering
should prefer `profiles` data over the entry's own organizer-entered snapshot** wherever
a `profiles` row now exists (more authoritative, and it is the person's own, consented
data) — stated here as the display-precedence rule §4.2's query composes, not invented at
render time.

**This is flagged as a genuine open question, not silently resolved**, in one respect:
whether S1/SECURITY-REVIEWER accepts "the organizer's own independent knowledge, stored
on the organizer's own list, is out of S1's scope" as a durable principle, or wants it
named as a formal S1 carve-out in `security-invariants.md` itself. This design proceeds
on the stated reasoning above; §7 open questions restates it for SECURITY-REVIEWER's
explicit sign-off at Step 2c.

## 4. Handler surface (organizer-only, S2/S3)

All four commands/callbacks below open with the identical S2 check
`requireOrganizerForChapter(db, BigInt(tgId), event.chapterId)` (same call this file's
precedent, `organizerRequests.ts`/`inviteCodes.ts`, already establishes on every handler
entry) — `member` and `EventStaff`-only callers refused, an organizer of a different
chapter refused for this event, re-checked on every callback exactly as
`organizerRequests.ts`'s multi-step flows already do (design §6.2 precedent there).

### 4.1 `/invite_list_add <event_id> <name> | <company> | <position>`

Pipe-delimited remainder, mirroring `parseCompanionFieldsMessage`'s established
convention. `name` required (usage-message refusal if blank, same "collect, don't
half-apply" discipline `validateEventCreateInput`/`parseInvitePersonalArgs` already use);
`company`/`position` optional, `""` meaning "not given" — same convention
`createWalkinProfile`'s `company` field already uses.

Steps (one transaction): event resolve → S2 → `createNamedGuestUser` (§1) → INSERT
`invite_list_entries` row (`user_id` = the just-created row, `added_by` = actor,
`invite_code_id` = `NULL`, `opened_at` = `NULL`, business-card fields as parsed) → exactly
one `writeAuditLog` call, action `invite_list.add`, `entity: "invite_list_entry"`,
`entityId` = the new entry's id, payload `{ eventId, userId, name, company, position }`
(never phone/email — none are ever collected by this command in the first place, §3.4).

Reply: confirmation text plus the created guest's internal `user_id` (needed so the
organizer can, if they prefer, use REQ-037's raw `/invite_personal <event_id> <user_id>`
directly) — but see §4.3 for the composed one-step alternative.

### 4.2 `/invite_list <event_id>` — the S3-safe list view

Read-only. One query: `invite_list_entries` for `event_id`, `LEFT JOIN profiles ON
profiles.user_id = invite_list_entries.user_id`, `LEFT JOIN registrations ON
registrations.user_id = invite_list_entries.user_id AND registrations.event_id =
invite_list_entries.event_id`.

**Select clause — the exact S3-safe set, structurally excluding phone/email (never a
runtime filter):**

```
name        := profiles.firstName/lastName if the profiles row exists and holds them,
               else invite_list_entries.name (display-precedence rule, §3.4)
company     := profiles.company if present, else invite_list_entries.company
position    := profiles.position if present, else invite_list_entries.position
status      := derived per the table below — never a column
```

| `invite_list_entries` row exists | `opened_at` | matching `registrations` row | `checked_in_at` | Status shown |
|---|---|---|---|---|
| yes | `NULL` | none | — | **invited** |
| yes | non-null | none | — | **opened** |
| yes | — | exists, live admission (§3.3) | `NULL` | **registered** |
| yes | — | exists, live admission | non-null | **attended** |

No phone, no email, no other `profiles` column is ever named in the select clause of this
query — the same structural-exclusion discipline `listInviteCodeRedeemers` and
`getCompanionDisplayData` already establish in `domain/inviteCode.ts` (§0's re-verified
precedent).

Each rendered entry carries two inline actions: **Remove** (§4.4) and, only when
`invite_code_id IS NULL`, **Issue code** (§4.3) — never a "Send" action (§6).

### 4.3 `invite_list:issue:<entryId>` callback — composes REQ-037, does not reimplement it

S2 re-checked. Reads the entry's `user_id`, calls `issuePersonalInviteCode(db,
actorUserId, eventId, entry.userId, expiresAt, at)` **unchanged** (REQ-037's own function,
§0), then `UPDATE invite_list_entries SET invite_code_id = $result.id WHERE id =
$entryId` in the same transaction. `writeAuditLog` is **not** duplicated here —
`issuePersonalInviteCode` already writes its own `invite_code.issue` row (S8, one row per
issue, unchanged); this callback's own bookkeeping write (`invite_code_id` on the entry)
is not itself a status change requiring a second audit row, since "an invite code was
issued" is already the fact `invite_code.issue`'s row records.

Reply shows the code and the `?start=i_<code>` link **to the organizer**, identical
composition to `inviteCodes.ts`'s existing `buildIssuedReply` (§0) — reused, not
reinvented.

### 4.4 `invite_list:remove:<entryId>` → `invite_list:remove:confirm:<entryId>`

Two-step confirm, mirroring `organizerRequests.ts`'s existing reject-with-confirm shape
(§0 precedent) rather than a single destructive tap. S2 re-checked on **both** steps. The
confirm step performs the removal (DATA-DESIGNER's chosen mechanism, §3.1) and exactly
one `writeAuditLog` call, action `invite_list.remove`, `entity: "invite_list_entry"`,
`entityId` = the entry's id, payload `{ eventId, userId }`, in the same transaction as the
removal write — same "insert/delete plus audit in one transaction" discipline every
existing mutation in this codebase already follows (§0's `writeAuditLog` header comment).

**Removal never deletes the underlying `users` row** — only the list entry. The
pre-created identity (linked or not) persists exactly as REQ-010 intends; only the
organizer's list membership is retracted.

## 6. No "send" action — the exact constraint (AC9)

No handler, callback, or scheduled job introduced by this design ever calls a message-send
API (`ctx.reply`/`ctx.replyWith*`/a `NotificationSender` call) **targeting the list
entry's own `user_id`** — every reply in §4 is sent to `ctx` (the acting **organizer's**
own chat), never composed toward the guest. §4.2's list view and §4.3's issued-code reply
are both organizer-facing displays of a code/link **for the organizer to share
themselves** (by DM, email, or in person, per STORY-DETAILS F9's own restated refusal) —
structurally identical to `inviteCodes.ts`'s existing `buildIssuedReply`, which this

## 7. No engagement score — the exact constraint (AC10)

This design defines exactly four derived/stored facts for a list entry: `added_at`
(stored, §3.1), `opened_at` (stored, justified §3.2), `registered`/`attended` (derived,
§3.3). **No field anywhere in this design — stored or derived — counts messages, replies,
group membership, group message frequency, or any other activity signal.** PRD FR-4/
RE-EVALUATION R4's "active in the group stays a human judgement, supported by the
invitation list, not replaced by it" is honored structurally: this list's only job is the
four-state outreach funnel named by PRD FR-17, nothing broader. BACKEND-DEV's
implementation must introduce no column, cache, or computed field beyond exactly these
four; TEST-DESIGNER's `git grep` check (AC10) is the enforcement mechanism, not this
design step.
