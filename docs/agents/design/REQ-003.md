# REQ-003 — Add English (`en`) locale to the i18n mechanism, design

Status: design for WF-02 Step 1. Scope: make `en` a recognized, routable locale
alongside `ru`/`uz` with a fully-keyed placeholder message catalog. Translation content
is explicitly out of scope — REQ-004 (`depends_on` this requirement) replaces the
placeholders with real English copy. See handoff
`handoffs/WF02-REQ003-REQ004/step-01-code-designer.json` for full requirement text.

## 0. Current state verified directly (not taken on faith from the handoff)

- `src/i18n/routing.ts` (6 lines): `defineRouting({ locales: ["ru", "uz"], defaultLocale:
  "ru" })`. Confirmed — two-entry tuple, `ru` first/default.
- `src/i18n/request.ts` (15 lines): `getRequestConfig` resolves `locale` via
  `hasLocale(routing.locales, requested) ? requested : routing.defaultLocale`, then
  loads `(await import(\`../../messages/${locale}.json\`)).default`. This is fully
  generic over `routing.locales` — it does not enumerate `"ru"`/`"uz"` anywhere.
  **Confirms the requirement text's claim: no change needed.** Adding `"en"` to
  `routing.locales` is sufficient for this file to resolve and load
  `messages/en.json` automatically; an unrecognized locale still falls back to
  `defaultLocale` ("ru"), unaffected by adding a third valid locale.
- `src/components/landing/LocaleSwitcher.tsx` (26 lines): a Client Component that maps
  over `routing.locales` directly (`routing.locales.map((locale) => ...)`), rendering
  one `<Link>` per entry with `href={pathname}`, `locale={locale}`,
  `className={locale === activeLocale ? "on" : undefined}`, and visible text
  `{locale.toUpperCase()}`. No hardcoded `"ru"`/`"uz"` literals, no per-locale branches,
  no fixed-length destructuring. **Confirms the requirement text's claim: no change
  needed.** A third entry in `routing.locales` produces a third `<Link>` (`EN`)
  automatically, with the same active-state and href logic as the existing two.
  - CSS check: `.lang` (`src/app/globals.css` line 48) is
    `display:flex;gap:2px;font-family:var(--mono);font-size:11px;color:var(--muted);...`
    — a flex row with a small gap, not a fixed-width or two-child-assuming layout. `.lang
    a` (line 50) and `.lang .on` (line 51) are per-link/per-state rules with no
    child-count assumption. A third `<a>` flows into the same flex row with no layout
    change required. No new CSS needed.
- `src/app/[locale]/layout.tsx` (77 lines): `RootLayout` calls
  `hasLocale(routing.locales, locale)` and calls `notFound()` if false — generic over
  `routing.locales`, no `"ru"`/`"uz"` literal. `generateMetadata` reads
  `t("title")`/`t("description")`/`t("ogLocale")` from the `Metadata` namespace via
  `getTranslations({ locale, namespace: "Metadata" })` — also generic, driven entirely by
  whatever locale is resolved and whatever `messages/<locale>.json` contains.
  `<html lang={locale} ...>` sets `lang` dynamically from the resolved `locale` string.
  **Confirms the requirement text's claim: no change needed.** Once `en` is a valid
  locale and `messages/en.json` exists with a `Metadata` namespace, this file handles it
  identically to `ru`/`uz` — `lang="en"` renders correctly, `notFound()` is not
  triggered, `generateMetadata` reads `Metadata.title`/`Metadata.description`/
  `Metadata.ogLocale` from the new catalog with no code change.
- `messages/ru.json`: 177 leaf keys under 11 top-level namespaces (`Metadata`, `Nav`,
  `Hero`, `Band`, `Creed`, `Metrics`, `Doors`, `Events`, `MapSection`, `Streams`,
  `Partners`, `Team`, `Footer` — 13 namespaces, verified by direct read). Verified by
  script: `messages/uz.json` has exactly the same 177 leaf keys in the same nested
  structure (key-set equality checked programmatically, not by inspection alone).
- No other file in `src/` references `"ru"`/`"uz"` as a literal locale list — the search
  surface for this requirement is exactly the four files above plus the new catalog.

**Net finding: every file the requirement text names as needing no change is confirmed
correct by direct reading.** This requirement's only concrete deliverables are (a) a
one-entry array addition in `src/i18n/routing.ts` and (b) a new file,
`messages/en.json`.

## 2. `src/i18n/routing.ts` — exact change

Structural shape (types/fields, not implementation):

```
locales: readonly ["ru", "uz", "en"]   // "en" appended after "uz"
defaultLocale: "ru"                     // unchanged
```

This is the only edit to this file. `defaultLocale` stays `"ru"` — no requirement source
(neither the GitHub issue nor REQ-001a nor the design system readme) states a reason to
change the site's entry locale; the requirement only asks for an English version to
exist as an additional, selectable locale.

## 3. `messages/en.json` — content shape

Exact same nested shape as `messages/ru.json`: 13 top-level namespaces (`Metadata`,
`Nav`, `Hero`, `Band`, `Creed`, `Metrics`, `Doors`, `Events`, `MapSection`, `Streams`,
`Partners`, `Team`, `Footer`), same key names at every level, same 177 total leaf keys,
same nesting depth (all namespaces are flat string maps — no arrays, no further nesting
below the namespace level, matching `ru.json`'s actual shape as read in §0).

Per requirement text, every leaf value is the **Russian source string duplicated
verbatim** as a placeholder — not an empty string, not a `TODO` marker, not a machine
translation. This matches the same placeholder convention REQ-001a used for
`messages/uz.json` (design doc `docs/agents/design/REQ-001a.md` §2: "every key
populated with the Russian source string duplicated verbatim as a placeholder").

One field needs a deliberate exception to pure verbatim-duplication, by the same logic
REQ-001a already applied to `uz.json`'s `ogLocale` field (see design precedent, §2 of
that doc): `Metadata.ogLocale` is a locale-format code consumed by
`src/app/[locale]/layout.tsx`'s `generateMetadata` as the OpenGraph `locale` field, not
translatable prose. `ru.json` has `"ogLocale": "ru_RU"`; `uz.json` has `"ogLocale":
"uz_UZ"`. Following that established pattern, `en.json`'s `ogLocale` should be
`"en_US"` (the standard OpenGraph/HTTP locale-code form for English) rather than a
duplicate of `"ru_RU"` — duplicating `ru_RU` here would emit an incorrect OpenGraph
locale tag on the English pages regardless of translation-content being out of scope,
exactly as REQ-001a reasoned for `uz_UZ`. This is flagged as an open question (§5)
because, unlike REQ-001a where the requirement text named the target value explicitly,
REQ-003's requirement text does not name `en_US` — it is this design's inference from
the existing two-catalog pattern, not a dictated value.

All other 176 leaf keys: Russian source string, character-for-character identical to
`messages/ru.json`'s value at the same key path. No translation, no transliteration, no
partial rewording — REQ-004 replaces these.

## 4. Design-token / responsive / theme considerations

None apply. This requirement touches no visual, layout, or interactive code:

- No new CSS class or token — `.lang`/`.lang a`/`.lang .on` are reused unchanged (§0),
  no new declaration is added or needed.
- No new component, so no new token consumption site.
- No responsive behavior changes — the switcher's flex-row layout already accommodates
  a variable number of children (§0); a third link does not require a breakpoint change.
- No theme-specific behavior — the reused classes already resolve through
  `var(--primary)`/`var(--muted)`/`var(--border)` per existing dark/light token
  definitions in `docs/Design system for AI agents/tokens/tokens.css`; nothing new is
  introduced that would need separate light/dark verification beyond confirming the
  existing switcher still renders correctly with three links in both themes (a
  verification-step concern, not a design decision).

## 5. Open questions (not silently resolved)

1. **`messages/en.json`'s `Metadata.ogLocale` placeholder value.** This design proposes
   `"en_US"` (§3), following the `ru_RU`/`uz_UZ` pattern REQ-001a established, rather
   than the Russian-string-verbatim rule that applies to every other key. The
   requirement text does not name this value explicitly (unlike REQ-001a, where
   `uz_UZ` was stated directly) — CODE-DESIGN-VALIDATOR should confirm `en_US` is the
   correct inferred value, or that FRONTEND-DEV should instead follow the literal
   verbatim-duplication rule for this key too (i.e. `"ru_RU"` unchanged) if the
   `ogLocale`-exception precedent is judged not to carry over automatically.
2. **Locale switcher visible-label order.** `LocaleSwitcher.tsx` renders links in
   `routing.locales` array order (§0) — appending `"en"` after `"uz"` places `EN` as the
   third/rightmost link (`RU · UZ · EN`). No source states a required visual order for
   three locales; this design accepts array order as the de facto display order since
   changing it would require either a routing.ts entry-order decision (which the
   requirement text already makes: "after uz") or a LocaleSwitcher.tsx code change
   (which §0 established is unneeded). Flagged only so REVIEWER/FRONTEND-DEV don't
   independently "fix" the order under the assumption it needs sorting or a different
   convention.
3. **`generateStaticParams` for `[locale]`, if one exists.** Not found in
   `src/app/[locale]/layout.tsx` as read in §0 (none is defined there), so this is
   inherited as a non-issue from REQ-001a's own open question 4 — no static-params list
   exists today that would need `"en"` added to it. Noted only for completeness; no
   action implied.
