# REQ-024 — `/my` registrations view with live status, computed waitlist position and the QR pass

**Requirement:** PRD 14 build-order step 3 (closing it), PRD 8's `/my`, STORY-DETAILS
C2's "QR always retrievable from `/my`, never the only copy." `depends_on: REQ-023`.

**Surface:** `apps/bot/**` (bot requirement). No design tokens apply — Telegram text/
button copy only, same as every other bot design in this pipeline (REQ-017/018/020/021/
022/023).

**No schema change.** Checked `apps/bot/src/db/schema.ts` directly: `registrations`
already has every column this design needs to read — `admission`, `qr_token`,
`event_id`, `user_id`, `checked_in_at`, `created_at`; `events` already has `title`,
`starts_at`, `ends_at`, `chapter_id`; `chapters` already has `timezone`. **No `ALTER
TABLE`, no new column, no new index — `DATA-DESIGNER` is not dispatched for this run**,
same precedent as REQ-017/020/021/022/023.

## 0. The three design decisions (resolved)

### 0.1 QR library recommendation

**Recommend adding `qrcode` (npm, `https://www.npmjs.com/package/qrcode`) to
`apps/bot/package.json` dependencies.** Checked `apps/bot/package.json` directly: no QR
generation dependency exists today (only `grammy`, `drizzle-orm`, `pg`). Reasoning:

- **Maintenance/adoption.** `qrcode` is the de facto standard pure-JS QR encoder in the
  Node ecosystem — long-lived, widely depended upon, no abandoned-package risk.
- **Output format compatibility.** Its `toBuffer(text, { type: "png" }, callback)` /
  promise form returns a PNG-encoded `Buffer` directly in memory — exactly the shape
  grammY's `InputFile` accepts (`new InputFile(buffer)`) for `ctx.replyWithPhoto`, with
  no intermediate file write and no second encoding step.
- **No native-binary/build-step complications.** It is pure JavaScript (no
  native addon, no `node-gyp`, no platform-specific binary) — it installs and runs
  identically wherever this bot already runs, with zero Dockerfile/deploy impact
  (`docs/guides/deploy_guide.md` is unaffected).
- Adding it is normal implementation work per this project's standing operating rules
  (a project dependency, not a system-wide install) — BACKEND-DEV adds it to
  `apps/bot/package.json` when building this requirement.

### 0.2 Withdraw-action wiring: reuse REQ-022's callback pattern directly, unchanged

**`/my`'s row-level withdraw action is one inline button per eligible row whose
`callback_data` is literally `withdraw:confirm:<registrationId>`** — the exact string
shape `handlers/withdraw.ts`'s `WITHDRAW_CONFIRM_PATTERN` already matches, handled by
the exact same `makeWithdrawConfirmCallbackHandler` already registered in `index.ts`
(REQ-022). **No new callback pattern, no new callback handler, no change to
`withdraw.ts` at all.**

This differs slightly from `/withdraw <event_id>`'s own flow (which first shows a
confirm/cancel *prompt*, §4.1 step 7 of REQ-022's design, before either callback fires)
— `/my`'s row already displays the event, its date/time, and its current status as
context, so a single "Withdraw" button *is* the confirmation surface; a second
confirm/cancel pair stacked underneath it would be redundant. Tapping it invokes
withdrawal immediately (same effect as tapping "Yes, withdraw" from `/withdraw`); not
tapping it is the cancellation — no `withdraw:cancel:<id>` button is shown per row (that
pattern remains used only by the standalone `/withdraw` command's own prompt, unchanged).

**Eligibility for showing the button is computed by calling the existing, unchanged,
pure `decideWithdrawOutcome`** (`domain/registration.ts`, REQ-022 §2.1) per row, with
`registrationExists: true`, `ownerUserId: actingUser.id`, `actingUserId: actingUser.id`,
`admission: row.admission`, `checkedInAt: row.checkedInAt` — the button is shown iff the
result's `kind` is `"withdrawn"` (REQ-022's own name for "this call is eligible to
succeed", not to be confused with the *display* admission state `"withdrawn"`, a
pre-existing but harmless naming overlap already present in that type). Since `/my`'s
own query (§1) never returns any other user's row, `ownerUserId` and `actingUserId` are
always equal here by construction — `decideWithdrawOutcome`'s `"not-owner"` branch can
never fire from this call site, mirroring the exact same reasoning `/withdraw`'s own
command handler already documents (REQ-022 §4.1 step 5) for its own eligibility check.
**No new predicate is introduced — this is the same function, called for the same
purpose (deciding whether to show the actionable UI), a second time.**

### 0.3 Privacy-discipline mechanism (S3)

**The `/my` list query accepts exactly one caller-derived input — the acting user's own
internal `id` — and it is never taken from anything the caller supplies.** Concretely:

1. The handler resolves `actingUser` via the existing `resolveActingUser(db,
   BigInt(ctx.from.id))` (`domain/eventAuthorization.ts`) — the same function every other
   mutation/read handler in this codebase already uses to turn a Telegram id into an
   internal user id, role, and chapter id. `ctx.from.id` is Telegram's own
   cryptographically-authenticated sender id for the update; the handler never reads any
   user/registration identifier out of message text, command arguments, or
   `callback_data` for this query.
2. `getMyRegistrations(db, actingUser.id)` (§1 below) issues exactly one `WHERE
   registrations.user_id = <actingUser.id>` clause — `actingUser.id` is a value produced
   in step 1 from the Telegram-authenticated sender, never a parameter accepted from any
   other source. **The function's own signature makes this structural, not
   conventional: it takes a single `userId: string` parameter and has no `eventId`,
   `registrationId`, or any other caller-suppliable identifier anywhere in its
   parameter list** — there is no argument through which a second user's id could enter
   this query even by mistake.
3. Every row's rendering (§2) uses only fields already present on that same row (the
   row's own `eventTitle`, `admission`, `qrToken`, etc.) — no per-row lookup by a
   caller-suppliable id occurs anywhere downstream of step 2, so there is no second
   query in the whole `/my` path that could be pointed at another user's data.

This is the same "resolve the acting identity first, then scope every read/write to it,
never accept an alternate identity from the caller" discipline `security-invariants.md`
S2/S3 already establish and every prior bot requirement's design already follows (most
directly: `/withdraw`'s `getRegistrationForEventAndUser(db, eventId, actingUser.id)`,
REQ-022 §4.1 step 4, and `withdrawRegistration`'s own `ownerUserId !== actingUserId`
check, REQ-022 §2.1) — restated here for the specific shape S3 names as the easiest to
get wrong: a **list** view.

## 1. New domain read: `getMyRegistrations` (`domain/registration.ts`)

```
export interface MyRegistrationListItem {
  registrationId: string;
  eventId: string;
  eventTitle: string;
  admission: AdmissionState;
  checkedInAt: Date | null;
  qrToken: string | null;
  startsAt: Date;
  endsAt: Date;
  chapterTimezone: string;
}

export async function getMyRegistrations(
  db: DbClient["db"],
  userId: string,
): Promise<MyRegistrationListItem[]>;
```

One `SELECT`, joining `registrations` to `events` (`registrations.event_id =
events.id`) and `events` to `chapters` (`events.chapter_id = chapters.id`) — the same
two-join shape `getEventByIdWithChapterTimezone` (REQ-017 §2.2) already uses, applied
here per-registration instead of per-event. `WHERE registrations.user_id = userId` is
the **only** filter (§0.3) — every admission state is returned, deliberately no
`admission IN (...)` filter, since AC4/the requirement's closing bullet require
withdrawn and rejected rows to keep showing, not disappear. Ordered by
`registrations.created_at DESC` (most recently registered first) — no acceptance
criterion specifies an ordering, and this is the simplest one that needs no extra join
or derived value; stated explicitly here so `BACKEND-DEV` does not have to guess it.

**Reused unchanged, called per row by the handler, never by this function itself** (this
function performs no per-row I/O beyond the one `SELECT` above):
- `getWaitlistPosition(db, eventId, registrationId)` (`domain/registration.ts`,
  REQ-021 §2) — called only for rows where `admission === "waitlisted"`; it already
  re-reads live state on every call and is never cached (REQ-021's own §2's stated
  contract), which is exactly AC2's requirement.
- `decideWithdrawOutcome(...)` (`domain/registration.ts`, REQ-022 §2.1) — called per row
  as described in §0.2, to decide whether to render the withdraw button.
- `formatDateTimeInTimezone(date, chapterTimezone, lang)` (`i18n/formatTimeInTimezone.ts`,
  REQ-017) — called twice per row (`startsAt`, `endsAt`), same as every other
  chapter-local date/time rendering in this codebase (`buildEventCardContent`,
  `listUpcomingPublishedEvents`'s call site, `sendPromotionNotification`).

## 2. New shared QR-image renderer: `domain/qr.ts`

**This is the single function this requirement introduces and REQ-026 must call — not
duplicated inline in the `/my` handler (AC5).**

```
export interface CheckInQrInput {
  botUsername: string;
  qrToken: string;
}

export async function renderCheckInQrPng(input: CheckInQrInput): Promise<Buffer>;
```

Placed in its own module, `apps/bot/src/domain/qr.ts`, alongside (not inside)
`domain/registration.ts` — it has no dependency on `DbClient`, performs no I/O, and its
only purpose is pure encoding, so it does not belong in a module whose other exports all
take a `db` handle. Framework-free (decisions/0004): no `grammy` import in this module —
its return type is a plain `Buffer`, and the handler (§3) is the one place that wraps it
in grammY's `InputFile` for `ctx.replyWithPhoto`.

**What it does, stated in prose (no branching, so nothing here is a disallowed
comparison/predicate one-liner — this is pure data composition and a single library
call):**

1. Composes the deep-link text as exactly this template, with no additional characters
   before, after, or between the pieces:

   | Piece | Value |
   |---|---|
   | Literal prefix | `https://t.me/` |
   | `botUsername` | the input parameter, verbatim |
   | Literal | `?start=ci_` |
   | `qrToken` | the input parameter, verbatim |

   Result: `https://t.me/<botUsername>?start=ci_<qrToken>` — this is what makes AC3 true:
   decoding the produced image yields exactly this string, which **contains** the
   substring `?start=ci_<that registration's qr_token>` the acceptance criterion names.
2. Passes that composed string to the `qrcode` package's PNG-buffer generation entry
   point (`QRCode.toBuffer(text, { type: "png" })`, per §0.1) and returns the resulting
   `Buffer` directly — no intermediate file, no disk write, no caching; a fresh buffer is
   produced on every call.

`botUsername` is an explicit parameter, not resolved inside this module (keeping it
framework-free) — the caller (`/my`'s handler, and later REQ-026's) supplies it from
grammY's own bot-identity accessor (`ctx.me.username`, populated once the bot has
started polling, which is true for every handler invocation in this codebase — no
handler ever runs before `bot.start()` has completed its own `getMe()` call).

**Explicit scope boundary, named rather than silently assumed:** this requirement builds
only the **encoding** side (turning a `qr_token` into a scannable image). Decoding a
scanned `?start=ci_<token>` deep link at check-in time — extending `parseStartPayload`
(`domain/event.ts` §6.2) with a `ci_` branch, and whatever the staff-facing check-in flow
does with it — is `/checkin`'s own future scope (`handlers/checkin.ts`'s header comment
already names this as REQ-028/029, unchanged by this design). Nothing in this
requirement reads or interprets a `ci_` payload; it only ever produces one.

## 3. Handler: `handlers/my.ts` — `/my` command

```
export function makeMyCommandHandler(db: DbClient["db"]);
```

Registered in `index.ts` as `bot.command("my", makeMyCommandHandler(db))`, alongside the
other id-less, non-organizer-gated read commands (`/events`'s own registration site,
REQ-017).

Steps (prose — no acceptance criterion in scope asks for branching logic finer than
what's already stated by the reused functions above, so nothing here restates a
comparison as code):

1. Resolve `tgId` from `ctx.from.id`; if absent (defensive, unreachable via Telegram),
   return with no reply, same guard every other handler in this codebase already opens
   with.
2. Resolve `actingUser` via `resolveActingUser(db, BigInt(tgId))` (§0.3 step 1). If
   `null`, reply with the existing `catalog.profile.startFirst` string (same reused key
   `/withdraw`'s command handler already uses for the identical case) and return.
3. Call `getMyRegistrations(db, actingUser.id)` (§0.3 step 2, §1).
4. **Empty list** → reply with a new catalog string, `catalog.my.emptyState` (§4) — a
   concrete CTA per this codebase's own "no dead ends" precedent (`events.followCityInvite`,
   REQ-017 §4.3), pointing at `/events` to find something to register for. Return.
5. **Non-empty list** → for each row, in the order returned by step 3:
   a. Resolve `dateTimeText` via two `formatDateTimeInTimezone` calls (§1).
   b. Resolve the status label via the existing `STATUS_CATALOG_KEY` mapping
      (`handlers/registration.ts`, REQ-020 §7.2 — this map already covers all five
      `AdmissionState` values via `catalog.registration.status*`; it needs to be
      **exported** from `registration.ts` for `my.ts` to import and reuse it, rather
      than a second copy being written — a one-line export addition, not a new mapping).
   c. If `admission === "waitlisted"`: call `getWaitlistPosition(db, eventId,
      registrationId)` (§1) and include the resulting position line using the exact same
      conditional-line-inclusion shape `composeRegistrationReply`'s `"waitlisted"` branch
      already establishes (REQ-020 §7.2: the position line is included only when a
      non-null position was obtained, omitted entirely otherwise — REQ-021 §6 open
      question 3's own precedent for "position unexpectedly null").
   d. Compose the row's text as: status label line, event title, `dateTimeText`, the
      optional waitlist-position line (step c). One `ctx.reply` (or one
      `ctx.replyWithPhoto`, per step f) per row — **not** one giant concatenated
      message — so each row can carry its own inline keyboard (the withdraw button)
      and, where applicable, its own photo.
   e. Attach the withdraw button (§0.2) as that row's `reply_markup` `InlineKeyboard`
      when `decideWithdrawOutcome(...)` (§0.2) returns `{ kind: "withdrawn" }` for this
      row; no keyboard otherwise.
   f. **QR gate (AC3, AC4):** if and only if `admission === "admitted"` **and**
      `qrToken !== null` (defensive — every row that reaches `"admitted"` always has a
      `qr_token` set, per REQ-020 §3.2 step 8 and REQ-023 §3 step 5, but the row's own
      type keeps `qrToken` nullable, so this is a guard, not an assumption, same
      no-speculation discipline this codebase's other reads already apply): call
      `renderCheckInQrPng({ botUsername: ctx.me.username, qrToken })` (§2) and send the
      resulting buffer via `ctx.replyWithPhoto(new InputFile(buffer), { caption: <the
      row's composed text from step d> })` instead of a plain `ctx.reply` — same
      "photo-with-caption vs. plain text" branch `handlers/start.ts`'s own event-card
      send already establishes (REQ-017 §3.5) for a `coverFileId`. For every other
      admission state, plain `ctx.reply(text, { reply_markup })`.

**Why per-row messages, not one combined message:** a QR image can only be attached as
a photo message's own content — grammY has no way to embed an inline image inside a
single text reply alongside other rows' plain text — and each row's withdraw button must
carry that row's own `registrationId` in its `callback_data`, which requires its own
`reply_markup`. One message per row is therefore the only shape that can satisfy AC3 and
AC5 simultaneously; stated explicitly since it is a structural constraint, not a
stylistic choice.

## 4. New i18n catalog section: `Catalog.my`

```
my: {
  header: string;           // e.g. "Your registrations:" -- one reply sent before the
                              // per-row messages (step 5's preamble), so an empty list
                              // (step 4) and a non-empty list are visually distinct
  emptyState: string;        // e.g. "You have no registrations yet. Check /events to
                              // find one." -- the concrete CTA, per REQ-017's
                              // followCityInvite precedent
  withdrawButton: string;    // e.g. "Withdraw" -- the single per-row button (§0.2)
}
```

Composed message shape per row (§3 step 5d): `[catalog.registration[statusKey],
eventTitle, dateTimeText, <optional waitlistPositionLine>].join("\n")` — reusing
`catalog.registration.*` status keys directly rather than introducing a second, parallel
set of status strings under `catalog.my`. Final wording owned by `CONTENT-BA`
(decisions/0002), same placeholder/minimal-functional-copy precedent every prior bot
design in this pipeline follows.

`STATUS_CATALOG_KEY` (`handlers/registration.ts`) needs an `export` keyword added to its
existing declaration — the only cross-file change to that file this design requires; no
existing export, type, or behavior of `registration.ts` changes.

## 5. Open questions (not silently resolved)

1. **Pagination / very long lists.** No acceptance criterion in scope bounds how many
   registrations a single user may have, and this design sends one Telegram message per
   row with no page/limit. Left unaddressed here — if a future requirement's acceptance
   criteria demand it, that requirement should add a limit/cursor to `getMyRegistrations`
   rather than this one inventing a pagination scheme no AC asks for.
2. **`ci_` deep-link consumption at check-in time** (§2's closing paragraph) is
   explicitly out of scope — `/checkin`'s own header comment already names this as
   REQ-028/029's future job.
3. **Send-failure UX for an individual row** (e.g. `ctx.replyWithPhoto` failing for one
   row while others succeed) is not specified by any acceptance criterion in scope; this
   design does not add per-row retry or partial-failure surfacing, matching the same
   "let the framework's own promise-rejection behavior apply" precedent REQ-023 §6.2
   step 3 already states for its own send.

## 6. Acceptance criteria → design element map

| AC | Design element |
|---|---|
| AC1 — user A's `/my` returns only user A's rows, no other user's name/company/phone/email anywhere | §0.3: `getMyRegistrations`'s sole `userId` parameter, sourced only from `resolveActingUser(db, BigInt(ctx.from.id))`, filters `WHERE registrations.user_id = userId`; the function's own signature has no second, caller-suppliable identifier through which another user's id could enter. Row rendering (§3 step 5) uses only fields already on that row — no per-row lookup by a caller-suppliable id exists anywhere in the path, so no other user's Profile fields (name/company/phone/email) can surface even indirectly |
| AC2 — waitlisted row's position is computed live: capture, withdraw the person ahead, re-invoke `/my`, position decreases, no write to the viewer's own row | §1/§3 step 5c: `getWaitlistPosition` (REQ-021, reused unchanged) performs one fresh `SELECT ... count` against live state on every call, never cached; `/my`'s own `getMyRegistrations` performs no write of any kind (a plain `SELECT`), so re-invoking `/my` after another registration's withdrawal changes only the *computed* position, never a stored column on the viewer's row |
| AC3 — an admitted row's QR image, decoded by an actual decoder, contains exactly `?start=ci_<that registration's qr_token>` | §2: `renderCheckInQrPng`'s exact template (`https://t.me/<botUsername>?start=ci_<qrToken>`) encoded via the `qrcode` package's PNG buffer, sent via `ctx.replyWithPhoto` (§3 step 5f) — the decoded image content is the literal string, verifiable only by decoding the produced PNG, not by inspecting the encoder's input |
| AC4 — waitlisted/withdrawn/rejected rows show no QR image | §3 step 5f's gate: QR rendering is attempted **if and only if** `admission === "admitted"` (and `qrToken !== null`) — every other admission value (`waitlisted`, `withdrawn`, `rejected`, `requested`) falls through to the plain-text `ctx.reply` branch, never calling `renderCheckInQrPng` |
| AC5 — the QR renderer is a single shared function under `apps/bot` REQ-026 can call, not duplicated inline | §2: `renderCheckInQrPng` is exported from its own module, `apps/bot/src/domain/qr.ts`, with no `db`/`ctx` dependency — `/my`'s handler is one caller; REQ-026's future T-3h message handler is designed to be a second caller of the same export, never a second implementation |
