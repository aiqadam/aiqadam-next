# REQ-011 — Bot data model and migration: Venue, Event, Registration, EventStaff, AuditLog

**Role:** DATA-DESIGNER (design only — no implementation code, no migration SQL/TS;
BACKEND-DEV writes both per this artefact, per `.claude/agents/data-designer.md`).

**Scope:** exactly five entities — `Venue`, `Event`, `Registration`, `EventStaff`,
`AuditLog`. No other table, column, or state is introduced. Derived from PRD 5 (data
model), PRD 6 (state machines), PRD 12 (invariants), `security-invariants.md`
S2/S4/S6/S7/S8/S11, `decisions/0005-orm-drizzle.md` (Drizzle ORM + Drizzle Kit, plain
`.sql` migrations), and `decisions/0006` (time-dependent predicates take the evaluation
time as an explicit application parameter, never SQL `now()` inside the query). Builds
directly on REQ-010's `chapters`/`users`/`profiles` tables (`docs/agents/design/REQ-010.md`)
— every FK to a person resolves to `users.id`, never `users.tg_id` (§5.1 of that artefact,
restated here as binding on this slice too).

As with REQ-010, this requirement is pure schema/migration design — no handler,

## 1. Entity: `venues`

| Field | Type | Nullable | Why |
|---|---|---|---|
| `id` | UUID (PK, default gen) | No | Stable internal identity, preamble rule. |
| `chapter_id` | UUID FK → `chapters.id` | No | A venue belongs to exactly one chapter (PRD 5 lists it first); every event/venue-scoped query (organizer scoping, S2) needs this to filter. Required because a venue with no chapter cannot be shown in any chapter-scoped venue picker — it would be unusable the moment it exists. |
| `name` | text | No | The venue must be identifiable in any UI that lists it (event creation, event card). No stated use case for an unnamed venue. |
| `address` | text | No | PRD 5 lists it; used to render "where" on the event card — a venue without a human-readable address fails that use immediately. |
| `lat` | numeric (double precision) | **Yes** | Used only for map links / distance display, both optional enhancements over the address. A venue can be fully usable (name + address shown) with no coordinates on file, e.g. entered before someone looks up the exact pin. |
| `lon` | numeric (double precision) | **Yes** | Same reasoning as `lat`; the two are always set or unset together at the application level, but neither blocks the other at the DB level — no requirement demands enforcing that pairing as a DB constraint. |
| `yandex_url` | text | **Yes** | A map-deep-link convenience for one region's users. Nothing in scope requires it to render the venue at all (address text already does). |
| `google_url` | text | **Yes** | Same reasoning, for the other map provider. |
| `capacity` | integer | No | PRD 5 lists it, and it is the physical ceiling an event's own `capacity` (see §2) is checked against by whoever creates an event at this venue. A venue whose capacity is unknown cannot be safely used to host an event, so this is required at venue-creation time, not deferred. |
| `notes` | text | **Yes** | Explicitly nullable per this requirement's field list — free-form organizer notes (parking, entry code, etc.) that no flow requires to finish creating or using a venue. |
| `created_at` | timestamptz, default now() | No | Preamble rule. |
| `updated_at` | timestamptz, default now(), updated on write | No | Preamble rule. |

**Keys / uniqueness:** `id` PK. No uniqueness constraint on `(chapter_id, name)` — nothing
in PRD 5 or the requirement text asks for one, and two venues with the same name in the
same chapter (e.g. a renamed hall re-added) is not excluded by any stated rule. Not adding
one, per the "don't invent a business rule" boundary.

**Cascade on `chapter_id`:** `ON DELETE RESTRICT`, matching REQ-010's `users.chapter_id`
reasoning — chapters are not deleted in normal operation; silently orphaning or
cascade-deleting venues on a chapter delete is a worse default than refusing until venues
are reassigned.

## 2. Entity: `events`

| Field | Type | Nullable | Why |
|---|---|---|---|
| `id` | UUID (PK, default gen) | No | Preamble rule. |
| `chapter_id` | UUID FK → `chapters.id` | No | Listed directly on `Event` in PRD 5's own field list (not merely derivable via `venue_id`) — see §6 open question 1 for the redundancy this creates and why it is kept rather than removed. Required: every chapter-scoped query (an organizer sees only their chapter's events, S2) needs this without a join through `venue_id`, and `venue_id` itself is nullable (an event's venue can be TBD), so `chapter_id` cannot be derived when `venue_id` is null. |
| `title` | text | No | An event with no title cannot be shown in any list, card, or announcement — required by construction. |
| `description` | text | No | PRD 5 lists it as a field an event card renders; unlike `Venue.notes` there is no stated "optional extra" framing for it, so it is treated as required content for a usable event listing. |
| `format` | enum (`meetup`\|`fail_stories`\|`workshop`\|`hackathon`) — **Postgres native `ENUM` type** | No | See rationale below. Every event has exactly one format; it drives card iconography/labeling per PRD 5. |
| `venue_id` | UUID FK → `venues.id` | **Yes** | An event can be announced ("save the date") before a venue is confirmed — no stated requirement forces a venue to exist at event-creation time, and forcing one would block that legitimate draft state. Once set, the venue must belong to a real row (FK). |
| `starts_at` | timestamptz | No | The one fact that makes an event schedulable/orderable at all; every later time-dependent predicate (`finished`, reminders) needs it. No draft state is described that omits a start time. |
| `ends_at` | timestamptz | No | Needed for `finished`/`no_show` derivations (§4) and for check-in window rules (S4's "token remains valid after the event ends" negative case). Required for the same reason as `starts_at`. |
| `registration_closes_at` | timestamptz | **Yes** | `registration_open` derivation (§4) needs a closing time to compare against, but some events may accept registration until the event itself starts (no separate cutoff) — a null value is the natural way to express "no earlier cutoff than the event start" rather than forcing every event creator to duplicate `starts_at` into this field. |
| `capacity` | integer | No | S7 states `seats_taken = count(admission='admitted')` and that it "exceeds `capacity` only via an explicit organizer override" — the comparison is meaningless without a capacity value on file, so every event must have one from creation. |
| `requires_invite` | boolean, default `false` | No (has default) | PRD 5 lists it as a gate on the registration flow; every event is determinately invite-gated or not — no requirement describes a "not yet decided" middle state, and a default of `false` (open by default) is the least-surprising creation-time value. |
| `requires_approval` | boolean, default `false` | No (has default) | Same reasoning — determines whether `admission` starts at `requested` pending organizer action or can go straight to `admitted`. Default `false` (auto-admit) is the least-surprising default absent a stated reason to gate by default. |
| `status` | enum (`draft`\|`published`\|`cancelled`) — **Postgres native `ENUM` type** | No | Every event has exactly one lifecycle state (PRD 5); `draft` is the natural creation-time default so an event can be built up before being made visible. Default `draft`. |
| `cover_file_id` | text (Telegram file_id) | **Yes** | A cosmetic card image. No flow requires an event to have cover art to be created, published, or registered for. |
| `agenda` | **JSONB**, array of items | **Yes** | See §3 — the doors-item-query design. Nullable because an event can exist (even be published) before its non-talk agenda items are finalized; no requirement forces `agenda` to be populated at creation. When present, holds ONLY non-talk items (doors, networking, close) — the talk lineup lives in its own entity elsewhere (out of this requirement's scope) and is never duplicated here, per PRD 5. |
| `created_at` | timestamptz, default now() | No | Preamble rule. |
| `updated_at` | timestamptz, default now(), updated on write | No | Preamble rule. |

**Why `format` and `status` are Postgres native `ENUM` types, not `CHECK` constraints or
plain text:**

- Both are small, closed, rarely-changing value sets (4 and 3 members respectively) that
  PRD 5 states exhaustively — a native `ENUM` documents the exact legal set directly in
  `\d+ events` output, which matters for the exportability goal (`decisions/0005`
  rationale #1: a future absorbing team reading the schema cold should see the legal
  values without hunting for a separate `CHECK` clause).
- A `CHECK (format IN (...))` constraint is functionally equivalent and would also satisfy
  every acceptance criterion here; the reason `ENUM` is chosen over `CHECK` for these two
  fields (unlike REQ-010, which left enum-shaped fields as `text` + app-level check) is
  that `format`/`status` are structural to *this* requirement's design challenge — the
  `agenda` JSONB design in §3 already asks whoever reads this table's DDL to reason
  precisely about typed, closed value sets, and using native `ENUM` here keeps that same
  precision consistent within the same table. This is DATA-DESIGNER's stated preference. It
  is **not binding on BACKEND-DEV as the only legal implementation** — per REQ-010 §7's own
  disclaimer, a `CHECK` constraint achieves the same acceptance criteria (rejecting a sixth
  format/status value) and remains an acceptable implementation choice if a native `ENUM`'s
  Drizzle Kit migration ergonomics (adding a new label later, e.g. a future fifth format,
  requires `ALTER TYPE ... ADD VALUE`, which cannot run inside the same transaction as other
  DDL in older Postgres) make `CHECK` preferable at implementation time. State whichever is
  chosen in the migration's own commit message.
- `Registration.admission` (§3) and `EventStaff`/`AuditLog` fields are evaluated the same
  way below, each with its own call.

**Keys / uniqueness:** `id` PK. No additional uniqueness constraint — nothing requires
title/venue/date uniqueness.

**Cascades:** `chapter_id` → `ON DELETE RESTRICT` (same reasoning as `venues.chapter_id`).
`venue_id` → `ON DELETE RESTRICT` (a venue with a past or future event scheduled against it
should not be silently deletable; forces reassignment first).

## 3. The `agenda[]` doors-item query — concrete shape and proof

**The constraint:** `agenda` must hold only non-talk items (doors, networking, close —
never the talk lineup), and a single SQL query must return **just** the doors item's time,
without the application loading the whole array and scanning it in TypeScript. PRD 5
forbids a separate `doors_at` column, so this JSONB structure is the only place the doors
time can live, and it must be queryable in place.

### Shape

`events.agenda` is a `JSONB` column holding a **JSON array of objects**, each with at
least:

```
{ "kind": "doors" | "networking" | "close" | <other non-talk label>,
  "at":   "<ISO-8601 timestamp string>",
  "label": "<human-readable text shown on the event card>" }
```

- `kind` is a **typed discriminator** — a small closed-ish string tag, analogous in spirit
  to `format`/`status` above but kept as a JSON string (not a Postgres enum) because it
  lives inside a JSONB value, not as its own column; Postgres enums cannot type-constrain
  values nested inside JSONB. Every item MUST carry `kind`; exactly one item per event may
  carry `kind: "doors"` (an application-level invariant — Postgres JSONB has no native
  "at most one array element matching X" constraint short of a `CHECK` using
  `jsonb_path_query_array` length-1 assertion, which is possible but adds complexity for a
  cardinality rule better enforced where the agenda is written, i.e. in application code
  that builds/replaces the array atomically on every write. Flagged as an implementation
  choice, not mandated here — see §6 open question 2 for the trade-off.)
- `at` is the item's TIME (ISO-8601 string, parseable to `timestamptz`) — satisfies "each
  agenda item carries at minimum a TIME and a LABEL" from the requirement text.
- `label` is the item's LABEL (free text, e.g. "Doors open", "Networking & coffee").
- `kind` never takes the value `"talk"` and no field on any item duplicates a talk's own
  title/speaker — those live entirely in the (out-of-scope) talk/lineup entity. This is a
  data-entry/application-level rule, not something the JSONB column shape alone can forbid
  (JSONB accepts any object shape); it is stated here as the binding rule for whoever
  writes to `agenda` (BACKEND-DEV, and any future organizer-facing agenda editor).

### The query — extracting only the doors item's time, in one query

Using Postgres's `jsonb_path_query_first` (available since PG 12), given an `events` row
identified by `$1`:

```sql
SELECT jsonb_path_query_first(agenda, '$[*] ? (@.kind == "doors").at')
FROM events
WHERE id = $1;
```

- `jsonb_path_query_first(target, jsonpath)` evaluates the SQLJSON path `$[*] ? (@.kind ==
  "doors").at` against the `agenda` array: `$[*]` iterates every array element, `?
  (@.kind == "doors")` is a **filter** that keeps only elements whose `kind` field equals
  the string `"doors"`, and `.at` then projects just that element's `at` member. The
  function returns the **first** match as a single `jsonb` scalar (the doors item's `at`
  string) — not the whole array, not the whole object, and never anything routed through
  TypeScript array-scanning. If no doors item exists, it returns SQL `NULL`.
- An equivalent, more conventional-looking form using the `@>` containment operator plus
  `->>`/`->` for anyone who prefers operator syntax over `jsonpath` (both are legitimate;
  `jsonb_path_query_first` is the one that most directly satisfies "single query, only
  that item" without a subquery unnest):

```sql
SELECT elem->>'at' AS doors_at
FROM events, jsonb_array_elements(agenda) AS elem
WHERE events.id = $1
  AND elem @> '{"kind":"doors"}'::jsonb;
```

  Here `jsonb_array_elements(agenda)` unnests the array server-side (still inside
  Postgres, not the application), `elem @> '{"kind":"doors"}'` is the JSONB **containment**
  operator selecting only the element that contains that key/value pair, and `elem->>'at'`
  extracts `at` as text (`->>`) rather than as a JSONB value (`->`). Both forms return
  exactly the doors item's time and nothing else, computed entirely inside Postgres.
- **This satisfies REQ-011's own AC6 literally**: "storing an event whose agenda holds a
  doors item PLUS at least one non-doors item (networking, close), a single database query
  returns the doors item's time and only that item." Given
  `agenda = [{"kind":"doors","at":"2026-10-01T15:00:00Z","label":"Doors open"},
  {"kind":"networking","at":"2026-10-01T15:30:00Z","label":"Networking"},
  {"kind":"close","at":"2026-10-01T19:00:00Z","label":"Doors close"}]`, either query above
  returns exactly `"2026-10-01T15:00:00Z"` — not the networking or close items, and not the
  array.
- **Consumer:** REQ-026's T-3h reminder job runs this query (or its Drizzle equivalent —
  Drizzle exposes raw `sql` template fragments for exactly this kind of JSONB path
  expression) with the evaluation time supplied by the application per `decisions/0006`;
  the query itself has no time-dependence, so that rule does not additionally constrain
  this specific query — it constrains whatever comparison REQ-026 makes against the
  returned `at` value afterward (e.g. `WHERE $evaluation_time BETWEEN $doors_at - interval
  '3 hours' AND $doors_at`, with `$evaluation_time` and `$doors_at` both passed in, never
  `now()`).
- **Indexing note (not required by any AC, stated for completeness):** if this lookup runs
  frequently across many events, a Postgres **GIN index** on `agenda` (`CREATE INDEX ...
  ON events USING GIN (agenda jsonb_path_ops)`) would accelerate the containment/path query
  at scale. Given PRD 1's stated load (~1,000 users, ~10 events/year, 0.06 rps), this index
  is very unlikely to be needed — flagged as a non-recommendation, so a future reader does
  not mistake its absence for an oversight.

## 4. Entity: `registrations`

| Field | Type | Nullable | Why |
|---|---|---|---|
| `id` | UUID (PK, default gen) | No | Preamble rule. |
| `event_id` | UUID FK → `events.id` | No | A registration with no event is meaningless — required by construction. |
| `user_id` | UUID FK → `users.id` | No | Same — a registration must belong to exactly one identified person, keyed on the stable internal id, never `tg_id` (REQ-010 §5.1, restated as binding here). |
| `admission` | enum (`requested`\|`waitlisted`\|`admitted`\|`rejected`\|`withdrawn`) — **Postgres native `ENUM` type** | No | PRD 6's exact five-value state machine. Native `ENUM` chosen over `CHECK`/text for the same reason as `events.format`/`status` (§2) — this is the single most safety-critical closed set in the whole schema (S2/S6/S7 all key off it), so making an invalid sixth value structurally unrepresentable is worth the `ALTER TYPE` migration cost of ever adding a value (which PRD 6 gives no indication will ever be needed — the five values are exhaustive by design). Every registration has a determinate admission state from creation (default `requested`, the natural entry point before any organizer or auto-admit decision is made). **Attendance (`checked_in_at`) is never a sixth value here** — see the dedicated row below and S6. |
| `checked_in_at` | timestamptz | **Yes** | S6: "Attendance is not an admission state; it is a timestamp, and it may not be set on a registration that is waitlisted, withdrawn, requested, or rejected." Nullable because most registrations are never checked in (or not yet); the "may only be set while admission='admitted'" rule is an application-level write-time invariant (checked at the point of writing `checked_in_at`, e.g. as part of the same transaction that verifies `admission`), not a column-level one — Postgres has no direct way to make a nullable timestamp's non-null-ness conditional on a sibling column's *current* value without a trigger or a `CHECK` referencing both columns. A `CHECK (checked_in_at IS NULL OR admission = 'admitted')` constraint **is possible and is recommended** as a belt-and-suspenders enforcement of S6 directly in the database — flagged as a recommendation in §6 rather than mandated, since REQ-011's own acceptance criteria test S6 by insert/attempt, not by asserting a specific constraint mechanism. |
| `checked_in_by` | UUID FK → `users.id` | **Yes** | Records which staff member performed the check-in (S8's audit trail, S5's staff-only check-in). Nullable because most registrations have no check-in at all; must be a `users.id`, consistent with S2's `EventStaff` being keyed on `users.id`. |
| `check_in_method` | enum (`qr`\|`manual`) | **Yes** | Nullable for the same reason as `checked_in_at` — meaningless until a check-in has actually happened. A native `ENUM`/`CHECK` here is a minor closed set (2 values); either implementation is fine, DATA-DESIGNER expresses no preference. |
| `reconfirmed_at` | timestamptz | **Yes** | PRD 5 lists it (a pre-event reconfirmation nudge, e.g. "will you still attend?"); nullable because most registrations are never reconfirmed or the feature simply hasn't fired yet for this row. |
| `invited_by_user_id` | UUID FK → `users.id` | **Yes** | Only populated when the registration originated from a personal invite (`source`, below); a self-registered attendee has no inviter. Nullable FK to `users.id`, never `tg_id`. |
| `source` | text | No | PRD 5 lists it (how the registration was created — e.g. self, invite, organizer-added); every registration is created through *some* path, so this is determinate from creation. Kept as free text rather than an enum here because no requirement text enumerates its exact closed value set (unlike `admission`, which PRD 6 states exhaustively) — inventing that enumeration would be adding a business rule this requirement doesn't ask for. Flagged in §6. |
| `invite_code_id` | **UUID, nullable, no FK constraint** | **Yes** | See §6 open question 3 — no `InviteCode` table exists in this requirement's scope, so there is nothing to reference. Stored as a plain nullable UUID column now; a later requirement that introduces `InviteCode` should add the FK constraint via an `ALTER TABLE` migration rather than this artefact inventing that table now. |
| `qr_token` | text, **UNIQUE**, nullable | **Yes** | S4: "≥128 bits from a cryptographically secure source." Nullable because a registration that never reaches an admitted/checkable state (e.g. `rejected`) may never need one; generated only when a token is actually issued. UNIQUE is a real DB constraint (mirrors AC3's exact test: two NULLs both succeed via Postgres's standard multiple-NULLs-distinct behavior — same reasoning as REQ-010 §2's `users.tg_id` — one duplicate non-null value fails). |
| `no_show_reason` | text | **Yes** | **A real stored column**, explicitly distinct from the *derived* `no_show` boolean (§5), which has no column anywhere. PRD 5 lists `no_show_reason` on `Registration`; it records an organizer's free-text note about *why* someone didn't show (illness, no-show without notice, etc.) — information no formula can derive, unlike the boolean fact of non-attendance itself. Nullable because most registrations never need one (attended, or the event hasn't happened yet). |
| `created_at` | timestamptz, default now() | No | Preamble rule, **and load-bearing**: waitlist position is computed by ranking `created_at` among `waitlisted` rows for an event (§5) — this column must be non-null (guaranteed by `DEFAULT now()` + `NOT NULL`) and is the literal ordering key that ranking query uses. |
| `updated_at` | timestamptz, default now(), updated on write | No | Preamble rule. |

**Keys / uniqueness:**

- `id` PK.
- **`UNIQUE (event_id, user_id)`** — a real database constraint (PRD 12.1: "exactly one
  Registration per (event_id, user_id)"). This is the load-bearing constraint the
  requirement calls out by name; it is expressed directly as a table-level unique
  constraint, not application-checked.
- **`UNIQUE (qr_token)`** — see row above; a plain unique constraint (Postgres's
  multiple-NULLs-distinct default gives exactly the "two NULLs succeed, one duplicate
  non-null fails" behavior REQ-011's AC3 tests, the same mechanism REQ-010 used for
  `users.tg_id`).
- **Index for waitlist ranking:** a composite index on `(event_id, admission, created_at)`
  (or, narrower, a **partial index** `ON registrations (event_id, created_at) WHERE
  admission = 'waitlisted'`) is specified so "waitlist position is computed by ranking
  `created_at` among waitlisted rows" (the requirement's own words) runs efficiently rather
  than via a full table scan. The partial-index form is the tighter fit — it indexes
  exactly the rows the ranking query filters on — and is DATA-DESIGNER's recommended shape;
  a plain composite index on all three columns is an acceptable substitute. Either
  satisfies the requirement's own text ("must be non-null and indexed for that query");
  which exact form BACKEND-DEV generates is an implementation choice, stated here so it is
  not silently skipped.

**Cascades:** `event_id` → `ON DELETE RESTRICT` (an event with registrations against it is
never a candidate for hard deletion under any stated flow — `cancelled` is the status for
"called off," never a row delete, per the one-word-per-concept rule). `user_id` →
`ON DELETE RESTRICT` (mirrors REQ-010 §5.3's reasoning: S13 anonymizes a `User` in place
rather than hard-deleting the row, so `Registration` rows should never need to survive a
`User` row's disappearance — if that assumption is ever wrong, it is S13's anonymization
routine's job to say so, not this artefact's). `checked_in_by` / `invited_by_user_id` →
`ON DELETE RESTRICT` for the same reason.

## 5. What is NOT stored, and its exact derivation (binding)

None of the following gets a column, in this migration or any future one touching these
tables. Every derivation below takes the evaluation time as an **explicit application
parameter**, never SQL `now()`/`current_timestamp` inline, per `decisions/0006`.

| Value | Derivation (pseudocode) | Notes |
|---|---|---|
| `no_show` | `admission = 'admitted' AND checked_in_at IS NULL AND $evaluation_time > ends_at` | Evaluated per-registration, joined to the registration's `events.ends_at`. `$evaluation_time` is supplied by the caller (e.g. the reminder/reporting job's own clock reading), never `now()` in the query text. |
| `waitlist_position` | `RANK() OVER (PARTITION BY event_id ORDER BY created_at ASC)` computed over rows `WHERE admission = 'waitlisted'` for the target `event_id`, or equivalently `SELECT count(*) FROM registrations WHERE event_id = $1 AND admission = 'waitlisted' AND created_at < $2.created_at` for one row's position. Not time-dependent (no `$evaluation_time` needed) — it depends only on other rows' `created_at`, which is why the index in §4 exists. |
| `seats_taken` | `SELECT count(*) FROM registrations WHERE event_id = $1 AND admission = 'admitted'` | Verbatim S7 formula. Not time-dependent. |
| `registration_open` | `$evaluation_time <= COALESCE(registration_closes_at, starts_at)` (and, if capacity is also a gating factor for "open," additionally `seats_taken < capacity` — PRD 5/6 do not fully specify whether capacity alone closes registration or only triggers waitlisting; this artefact states the time-window half concretely and flags the capacity interaction as an open question, §6.4, rather than inventing the exact combined rule). | `$evaluation_time` supplied by the caller. |
| `finished` | `ends_at < $evaluation_time` | Verbatim from the requirement text; `$evaluation_time` supplied by the caller. |

`no_show_reason` (§4) is a **real stored column** and is not part of this table — it is
listed here only to repeat, once more, that it must never be confused with the *derived*
`no_show` boolean above, which has no column anywhere.

## 6. Entity: `event_staff`

| Field | Type | Nullable | Why |
|---|---|---|---|
| `id` | UUID (PK, default gen) | No | Preamble rule — kept even though `(event_id, user_id)` could itself serve as a composite PK, for consistency with every other table in this schema having a single surrogate UUID identity (matches REQ-010's pattern for `profiles`, which also has both a 1:1 unique FK and its own `id`). |
| `event_id` | UUID FK → `events.id` | No | S2: `EventStaff(event_id, user_id)` grants check-in rights **for that one event and nothing else**. A row with no event is meaningless. |
| `user_id` | UUID FK → `users.id` | No | Same — the staff member, keyed on `users.id`, never `tg_id`. |
| `created_at` | timestamptz, default now() | No | Preamble rule. |
| `updated_at` | timestamptz, default now(), updated on write | No | Preamble rule. |

**Explicit statement (S2):** an `event_staff` row grants check-in rights for **exactly the
one `event_id` on that row** — nothing else. A person staffing two events needs two
`event_staff` rows. Staff have no rights on any screen other than check-in for their
assigned event(s); this table carries no `role`/`scope` column, because the entity's whole
meaning per S2 is "check-in rights for one event," not a general staffing/role concept —
adding a scope field would silently widen what this table is capable of granting beyond
what the requirement asks for.

**Keys / uniqueness:** `id` PK, plus **`UNIQUE (event_id, user_id)`** — a person cannot be
staffed twice for the same event (a duplicate row would be meaningless and could confuse
any "is this person staff for this event" check into false negatives/positives depending
on which row a query happens to read). This mirrors the `registrations` UNIQUE pattern and
is a straightforward corollary of "grants rights for exactly one event," not an invented
extra rule.

**Cascades:** `event_id` → `ON DELETE RESTRICT`, `user_id` → `ON DELETE RESTRICT` (same
reasoning as `registrations`).

## 7. Entity: `audit_log`

| Field | Type | Nullable | Why |
|---|---|---|---|
| `id` | UUID (PK, default gen) | No | Preamble rule. |
| `actor_user_id` | UUID FK → `users.id` | **Yes** | S8 requires "actor, action, entity, entity id, payload, timestamp" on every status-change row, and S5 additionally requires a row for "scanner is not staff" refusals and other system-initiated events. Nullable because a genuinely **system-initiated** action (e.g. an automated auto-promotion-from-waitlist job running on a schedule, or a scheduled reminder/notification send with no human actor) has no human to attribute — forcing a non-null `actor_user_id` would require inventing a fake "system" user row purely to satisfy a NOT NULL constraint, which manufactures a business concept (a system pseudo-user) this requirement does not ask for. When an actor exists, the column is populated and resolves to `users.id`, never `tg_id`. |
| `action` | text | No | Every audit row exists because *something* happened; an audit row describing no action is meaningless. Free text (not an enum) because PRD 5/12 do not enumerate a fixed closed set of audit actions — new action strings will be added by future requirements as new status-change paths are built, and constraining this to a Postgres `ENUM` now would require an `ALTER TYPE` for every new audit-worthy action forever. Flagged as a deliberate choice, not an oversight. |
| `entity` | text | No | Identifies which table/kind of thing the action was about (e.g. `"registration"`, `"event"`). Required for the same reason as `action` — an audit row with no subject is not auditable. Free text for the same forward-compatibility reason. |
| `entity_id` | UUID | No | The specific row's id within `entity`. Deliberately **not a foreign key** to any specific table — `audit_log` spans multiple entity types (`registrations`, `events`, ...), and a single column cannot carry a FK to more than one target table; polymorphic references are conventionally left unconstrained at the DB level (or handled with a check-per-entity-type pattern that this requirement does not ask for). Required — an audit row about nothing identifiable fails S8's own field list. |
| `payload` | **JSONB** | **Yes** | S8's "payload" field — holds whatever structured detail is relevant to the specific action (e.g. old/new `admission` values for a status change). Nullable because some audit-worthy actions may have no extra detail beyond action/entity/entity_id (e.g. a bare "export requested" event with nothing more to capture). **See the explicit S11 limitation stated below** — this is the field most at risk of becoming a PII leak. |
| `at` | timestamptz, default now() | No | The literal timestamp S8 requires. `DEFAULT now()` at write time is appropriate here (unlike a *predicate* evaluated later against a supplied clock — decisions/0006's rule is about time-dependent *queries*, not about a row recording *when it was written*, which is exactly what a database default timestamp is for). |
| `created_at` | timestamptz, default now() | No | Preamble rule — kept distinct from `at` even though they will typically be identical, because `at` is the semantically meaningful "when did the audited event happen" field per S8, while `created_at` is this schema's own structural convention applied uniformly to every table. Keeping both avoids overloading `at` with two meanings (audit semantics vs. schema convention) that could diverge if a future backfill/import ever writes audit rows after the fact. |
| `updated_at` | timestamptz, default now(), updated on write | No | Preamble rule. An audit row is expected to be write-once in practice (no requirement describes editing an audit row after creation — doing so would undermine its purpose as a record), but the column is kept for schema-wide consistency; nothing in this design implies audit rows are ever actually updated. |

**Explicit statement (S11) — a design-time limitation, stated honestly:**
`AuditLog.payload` **must never carry plaintext phone or email**. This is a rule for
whoever writes audit rows later (every future requirement that calls the audit-writing
code path — S8's own negative case: "a status changed through a bulk/admin path that
bypasses the audit-writing code path used by the normal path"), not something this
column's type can enforce by itself. **JSONB has no schema, so Postgres cannot reject a
payload merely for containing a phone number or email address** — that would require
either a `CHECK` constraint with a regex over the JSON text (fragile, false-positive-prone,
and easily defeated by encoding/formatting variation — not recommended) or, better,
discipline enforced at the point audit rows are constructed in application code (never
pass a whole profile/request object as `payload`; pass only the specific fields the audit
entry needs — ids, enum values, timestamps — never `phone`/`email`). SECURITY-REVIEWER is
named in `security-invariants.md`'s header as the party who verifies this at review time,
per S11's own negative case ("`an AuditLog.payload` that captures a full profile diff
including the phone"). This artefact states the limitation rather than claiming a schema
fix that does not exist.

**Keys / uniqueness:** `id` PK. No uniqueness constraint — audit rows are, by nature,
append-only and not deduplicated (S8: "One row — not zero, not one per retry" is an
application-level idempotency concern about *how many times the write path runs*, not a DB
uniqueness constraint on the row's content, since two genuinely distinct actions could
otherwise have identical action/entity/entity_id/payload/at values, e.g. two different
"admission changed" events for two different retries — the fix for S8 is application-level
idempotency at the call site, not a DB constraint here).

**Cascades:** `actor_user_id` → `ON DELETE RESTRICT` (same reasoning as elsewhere — never
allow a hard-deleted user to silently blank out or cascade-remove historical audit rows,
per S13's "aggregate counts intact" spirit extended to audit history). No FK on
`entity_id` (see above — polymorphic, unconstrained by design).

## 9. Migration and reversibility

A single Drizzle Kit-generated `.sql` file (per `decisions/0005`, committed under
`apps/bot/`, e.g. `apps/bot/drizzle/0001_<slug>.sql`) that:

1. Creates the enum types (`event_format`, `event_status`, `admission`,
   `check_in_method`) if native `ENUM` is the chosen implementation (§2/§4).
2. `CREATE TABLE venues (...)`, then `CREATE TABLE events (...)` (depends on `venues` and
   `chapters`), then `CREATE TABLE registrations (...)` (depends on `events`/`users`), then
   `CREATE TABLE event_staff (...)` (depends on `events`/`users`), then
   `CREATE TABLE audit_log (...)` (depends on `users` only) — in that dependency order.
3. Includes `UNIQUE (event_id, user_id)` on `registrations`, `UNIQUE (qr_token)` on
   `registrations`, `UNIQUE (event_id, user_id)` on `event_staff`, and the recommended
   partial index for waitlist ranking on `registrations`.
4. Contains no `no_show`, `waitlist_position`, `seats_taken`, `registration_open`, or
   `finished` column or table anywhere (AC5 — grep-checkable negative).
5. Is purely additive (five new tables, referencing REQ-010's existing three, no existing
   table altered) — **it is reversible**: `DROP TABLE audit_log; DROP TABLE event_staff;
   DROP TABLE registrations; DROP TABLE events; DROP TABLE venues;` (respecting FK
   dependency order, reverse of creation), then dropping the enum types if native `ENUM`
   was used, undoes it cleanly with no data-loss ambiguity, since nothing existed in these
   tables before this migration.
6. Per `decisions/0005`'s own consequence section: this migration touches no column
   carrying personal data or attendance history from an *existing* table (REQ-010's tables
   are untouched), so the "SECURITY-REVIEWER sign-off for a migration dropping/rewriting
   PII" trigger in that decision does not apply to this migration itself — it is purely
   additive. Any *later* migration that alters `registrations`/`audit_log` after real data
   exists in them would trigger that review.

## 11. Open questions (not resolved by invention)

1. **`events.chapter_id` redundancy with `venue_id → venues.chapter_id`.** PRD 5 lists
   `chapter_id` directly on `Event`, and `Venue` also carries its own `chapter_id`. When
   `venue_id` is set, the two *should* agree (an event's chapter and its venue's chapter
   should match), but nothing in this requirement's text states that as an enforced rule,
   and `venue_id` is nullable (a venue-less draft event still needs a `chapter_id` to be
   chapter-scoped at all). This artefact keeps both columns as PRD 5 literally lists them
   and does **not** add a `CHECK`/trigger enforcing `events.chapter_id = venues.chapter_id`
   when a venue is set — that would be inventing a consistency rule the requirement text
   does not state. Flagged for REQ-VALIDATOR/CODE-DESIGN-VALIDATOR to confirm whether such
   a constraint is wanted, or whether cross-chapter venue-borrowing is intentionally
   allowed.
2. **Enforcing "at most one `doors`-kind item per `agenda` array" at the DB level.** §3
   notes this is currently an application-level invariant (enforced by whatever writes the
   array atomically), not a DB `CHECK`. A `CHECK` using `jsonb_path_query_array(agenda,
   '$[*] ? (@.kind == "doors")')` and asserting array length ≤ 1 is possible but adds
   complexity current acceptance criteria do not demand (they demand the query return the
   right thing given a well-formed agenda, not that malformed agenda be rejected at write
   time). Flagged as a hardening option, not mandated.
3. **`registrations.invite_code_id`'s exact shape absent an `InviteCode` table.** Per the
   requirement text's own framing, this is stored now as a bare nullable UUID column with
   **no FK constraint** (§4, §8), since no `InviteCode` table exists in this requirement's
   scope. When a future requirement introduces `InviteCode` (S4 already anticipates its
   token needing the same ≥128-bit unguessability bar as `qr_token`), that requirement
   should add the FK via `ALTER TABLE registrations ADD CONSTRAINT ... FOREIGN KEY
   (invite_code_id) REFERENCES invite_codes(id)`. This artefact does not create a stub
   `InviteCode` table now — doing so would be adding an entity this requirement's scope
   list does not include.
4. **`registrations.source`'s value set.** Left as free text (§4) because PRD 5/12 do not
   enumerate its exact closed set of values in the material available to this run. If a
   fixed set (e.g. `self | invite | organizer_added`) is intended, that should be stated by
   whichever requirement first writes distinguishable `source` values, and could then
   become an enum/`CHECK` in a follow-up migration.
5. **`registration_open`'s interaction with capacity.** §5 states the time-window half of
   this derivation concretely (`$evaluation_time <= COALESCE(registration_closes_at,
   starts_at)`) but flags that PRD 5/6 do not fully specify whether reaching `capacity`
   alone also closes registration (as opposed to triggering waitlisting while registration
   itself stays "open" in the time-window sense). Not resolved here — the *time-window*
   half of the predicate is what this requirement's acceptance criteria actually ask
   DATA-DESIGNER to specify, and it is specified without inventing the capacity
   interaction.
6. **`checked_in_at`/`admission='admitted'` consistency as a DB-level `CHECK`.** §4
   recommends `CHECK (checked_in_at IS NULL OR admission = 'admitted')` as a
   belt-and-suspenders enforcement of S6 directly in the database, but does not mandate it,
   since REQ-011's acceptance criteria test S6's behavior via insert/attempt rather than
   naming a specific constraint mechanism. BACKEND-DEV/REVIEWER should confirm whether to
   include it.
7. **`format`/`status`/`admission` as native `ENUM` vs. `CHECK`.** §2/§4 state
   DATA-DESIGNER's preference (native `ENUM`, for `admission` especially) but explicitly
   leave the final choice to BACKEND-DEV given Drizzle Kit's `ALTER TYPE` migration
   ergonomics trade-off — either satisfies the stated acceptance criteria.

## 12. Summary for the handoff

Five tables (`venues`, `events`, `registrations`, `event_staff`, `audit_log`), UUID PKs,
`created_at`/`updated_at` on each, extending REQ-010's `chapters`/`users`/`profiles`. Every
person-referencing FK resolves to `users.id`, never `tg_id`. `registrations` carries the
PRD 12.1 `UNIQUE(event_id, user_id)` as a real DB constraint, a `UNIQUE(qr_token)` mirroring
REQ-010's nullable-unique pattern, and a `created_at`-based index recommendation for
waitlist ranking. The five-value `admission` enum has no attendance state —
`checked_in_at` stays a separate nullable timestamp per S6. `no_show_reason` is a real
stored column, sharply distinguished from the *derived, columnless* `no_show` boolean;
`waitlist_position`, `seats_taken`, `registration_open`, and `finished` are likewise all
given exact derivation expressions and no columns, every time-dependent one parameterized
by an explicit `$evaluation_time` per decisions/0006. `events.agenda` is a nullable JSONB
array of `{kind, at, label}` objects holding only non-talk items; §3 proves, with two
concrete SQL forms (`jsonb_path_query_first` and `jsonb_array_elements` + `@>`/`->>`), that
the doors item's time alone is extractable in one query with no application-side array
scanning, and that no `doors_at` column exists anywhere. `event_staff` grants check-in
rights for exactly one event per row (S2), enforced by `UNIQUE(event_id, user_id)`.
`audit_log.actor_user_id` is nullable for genuine system-initiated actions; `payload`'s
S11 plaintext-phone/email prohibition is stated explicitly as an application-level
discipline this JSONB column's type cannot itself enforce. Seven open questions are
flagged (§11) rather than resolved by invention.
