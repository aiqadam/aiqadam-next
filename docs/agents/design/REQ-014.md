## 1. New i18n catalog keys

Extends `apps/bot/src/i18n/types.ts`'s `Catalog` interface (nested-by-feature, per
REQ-013 §1.2's established convention) with three new top-level flows and one new key
under `start`:

```
interface Catalog {
  start: {
    greeting: string;            // unchanged, REQ-013
    noActiveChapters: string;    // NEW — zero-active-chapters edge case, §2.3
  };
  chapter: {                     // NEW
    prompt: string;              // shown only when >=2 active chapters exist
  };
  consent: {                     // NEW
    prompt: string;              // includes the placeholder wording + "(v1)" tag, §2.4
    agree: string;                // button label, sentence case
  };
  help: {                        // NEW
    body: string;                // §4
  };
  lang: { ... }                  // unchanged, REQ-013
}
```

`ru.ts`/`en.ts` both gain these four leaves; `catalogs.test.ts`'s existing key-parity and
non-empty-string assertions (REQ-013 §4) extend to them automatically since they iterate
the whole flattened object — no new test file, no new CI wiring needed, matching
REQ-013's established mechanism.

**Content shape for the four new leaves — all placeholder/provisional, stated explicitly
per this requirement's own instruction not to invent legal-sounding or fabricated
copy:**

| Key | RU | EN |
|---|---|---|
| `start.noActiveChapters` | Отделения пока недоступны. | No chapters are available yet. |
| `chapter.prompt` | Выберите отделение. | Choose your chapter. |
| `consent.prompt` | Бот AI Qadam Events сохраняет ваш Telegram ID, имя пользователя и язык интерфейса для регистрации на мероприятия и связи с вами. Эта формулировка предварительная (v1) и будет заменена после согласования с ответственным лицом. | The AI Qadam Events bot stores your Telegram ID, username and interface language to handle event registration and to reach you about it. This wording is a provisional placeholder (v1), pending review by the product owner. |
| `consent.agree` | Согласен | I agree |
| `help.body` | Этот бот ведёт сообщество AI Qadam. По вопросам обращайтесь к организаторам вашего отделения. (Плейсхолдер: точные контакты и ссылка на сообщество ещё не определены.) | This bot is run by the AI Qadam community. For questions, contact the organizers of your chapter. (Placeholder: exact contact details and the community link are not yet defined.) |

Tone check against the design system's content-fundamentals section (the only part of it
applicable to a bot, per REQ-013 §0's precedent note): no exclamation marks, no slogans,
no emoji, sentence case, factual register. `Chapter` used as the verbatim domain term in
English per the vocabulary table; the Russian translation is the natural equivalent, same
pattern REQ-013 used.

**Why `help.body` names its own placeholder status inline, unlike `consent.prompt`'s
"(v1)" tag which is the ONLY marker there:** PRD 8's actual contact channel/link is not
present anywhere in this repository (checked: no PRD document, no existing constant, no
prior requirement's design artefact states one) — inventing a plausible-looking
`t.me/...` URL would be worse than an honest gap, since a fabricated link that happens to
resolve to something else is actively misleading, whereas a short bracketed note is
merely unfinished. `consent.prompt` does not need the same inline caveat because AC4
already requires and verifies an explicit version identifier as its own marker of
provisionality — adding a second parenthetical there would be redundant. **This is a
design choice made to avoid fabricating unverifiable contact information — flagged
explicitly in §5's open questions, not silently resolved.**

## 2. `/start` handler flow

### 2.1 Entry: resolve tg_id, guard

Same guard as the REQ-013 stub: `const tgId = ctx.from?.id; if (tgId === undefined) return;`.

### 2.2 Resolve-or-create the User row

New domain function, `apps/bot/src/domain/user.ts` (extending the existing file):

```
resolveOrCreateUser(
  db: DbClient["db"],
  input: { tgId: bigint; tgUsername: string | null; lang: BotLang | null },
): Promise<{ id: string; tgUsername: string | null; lang: string | null;
             chapterId: string | null; consentPdAt: Date | null }>
```

Behavior: SELECT the full row by `tg_id`. If found, return it unchanged (no
column is overwritten on a repeat `/start` — see §3.5, this function never re-writes
`tg_username`/`lang` on an existing row, only reads it). If not found, create it holding
**only** `tg_id`, `tg_username`, `lang` — no other column is set beyond schema defaults
(`role` defaults to `member`, `chapter_id`/`consent_pd_at` stay NULL, matching AC1's "NO
profiles row" framing extended to "no other users column either").

**Concurrency note (design-level, not implementation):** the SELECT-then-INSERT
described in the requirement text must not be a naive read-then-write racing against
`users_tg_id_unique` — two near-simultaneous `/start` taps from the same account (a
double-tap, or Telegram redelivering an update) must not crash on the unique-index
violation or produce two rows. The create-if-missing step must be atomic against that
index (e.g. an upsert-shaped statement that no-ops or returns the existing row on
conflict, rather than a plain `INSERT` following a separate `SELECT`). The exact
statement shape is BACKEND-DEV's implementation choice; the design requirement is only
that this be atomic, not that any given SQL form be used.

**What `lang` is on a brand-new user — resolved, not left to guesswork:**
grammY's `ctx.from` exposes Telegram's `User.language_code` (an optional IETF tag
Telegram itself infers from the client's settings). This handler maps it through the
**same** `ru`/`en` recognition `resolveLang` already uses (i.e., set `lang` to `"ru"` if
`language_code` starts with `"ru"`, `"en"` if it starts with `"en"`, otherwise leave it
`null`) — it does **not** invent a second validation routine; it is a thin reuse of the
same two-value recognition `isBotLang` already performs internally.

**Why NULL rather than always defaulting to `"ru"` when `language_code` is unrecognized:**
`resolveLang`'s three-step fallback chain (own lang → chapter default → `"ru"`) is
already the single source of truth for what language to *display*, and it already
handles a NULL `users.lang` correctly. Writing a forced `"ru"` into storage at creation
time for, say, a Kazakh-client user (`language_code = "kk"`) would silently bake a
guessed value into a column that later logic (a chapter with `default_lang = "en"`, or a
future `/lang` call) should be free to override via the *read-time* fallback chain
instead. Storing `NULL` for "Telegram didn't tell us a bot-supported language" defers to
the resolution logic that already exists and is already tested (REQ-013), rather than
duplicating a fallback decision at write time. This is a design decision, not an
invented one — it follows directly from not wanting two different places (write-time
guess, read-time fallback) to disagree about what "unknown" means.

### 2.3 Chapter assignment

Query (per `REQ-014-schema.md` §4): `SELECT id FROM chapters WHERE active = true LIMIT 2`.

Only performed when `resolveOrCreateUser` returned `chapterId: null` — an already-assigned
user is never re-queried or re-asked (chapter is changeable later only via `/profile`,
REQ-019's scope, per this requirement's own description).

- **0 rows — the flagged edge case, resolved here:** no chapter exists to assign. The
  handler sends `getCatalog(lang).start.noActiveChapters` and leaves `users.chapter_id`
  NULL. It does **not** fabricate a chapter, does **not** hold the user in a blocked/retry
  loop, and does **not** treat this as an error. The `/start` flow continues immediately
  to the consent step (§2.4) — chapter presence and consent are independent gates; nothing
  about consent depends on a chapter being assigned. **Reasoning for why this is
  engineering discipline, not invented product policy:** the requirement's own acceptance
  criteria describe two states (one active, two-or-more active) and are silent on zero;
  "do nothing harmful and don't block the rest of the flow when the deployment is
  mid-configuration" is the same category of defensive default this codebase already
  applies elsewhere (e.g. `resolveLang`'s final `"ru"` fallback for an unrecognized
  `chapterDefaultLang`, REQ-013 §1.3) — a safe no-op for an unspecified input, not a new
  business rule about which chapters should exist or how they should be created. It
  invents no chapter, assigns no default, and changes no schema-level meaning of
  `active`. If chapters are later created/activated, nothing in this design prevents a
  human operator or a future requirement from backfilling `chapter_id` for
  already-created users — this design only guarantees `/start` itself doesn't break or
  stall today.
- **Exactly 1 row:** assign silently. `UPDATE users SET chapter_id = $1 WHERE id = $2`
  (keyed on `users.id`, never `tg_id` — see §6). No message is sent about this step; the
  user proceeds straight to §2.4 with no visible interruption, matching AC2's "WITHOUT
  prompting."
- **2 rows (meaning "two or more"):** ask once. A **second** query — distinct from the
  `LIMIT 2` branch-signal query, and not a contradiction of `REQ-014-schema.md` §4's
  recommendation, which only concerns the three-way branch decision — fetches the full
  option set: `SELECT id, name FROM chapters WHERE active = true ORDER BY name`. The
  handler replies with `getCatalog(lang).chapter.prompt` and an inline keyboard with one
  button per row, label = that chapter's `name` (a data value, not a catalog string —
  exempt from the i18n mechanism for the same reason REQ-013 §2.2 exempted the two fixed
  language-name button labels: chapter names are content, not translated UI copy),
  `callback_data: "chapter:<chapter.id>"`. The flow pauses here; completion happens in
  the callback handler, §2.5.

### 2.4 Consent prompt

Sent immediately after §2.3 resolves (silent-assign, zero-chapter, or — for the
multi-chapter branch — after the chapter callback in §2.5 completes), **only if**
`consentPdAt` is still null on the resolved user row. Reply with
`getCatalog(lang).consent.prompt` (the placeholder wording, carrying its "(v1)" tag
inline per §1's table) and an inline keyboard with exactly one button:
`getCatalog(lang).consent.agree` label, `callback_data: "consent:agree"`. The version
tag is **not** read from the callback payload when the tap is handled (see §2.5's
security note) — it is a single module-level constant (e.g.
`CONSENT_WORDING_VERSION = "v1"`) defined alongside the catalog content, so the server
always records the version it actually knows itself to be showing, not whatever a client
round-trips back.

**Confirmation, per the requirement's own instruction (structurally trivial, not
merely asserted):** because this requirement writes no `Profile` row anywhere in its
scope — no handler, domain function, or code path introduced here ever inserts into
`profiles` — "no phone/email value exists until consent is accepted" is true by
construction: there is no code path capable of writing one either way. The `users` row
itself (holding only `tg_id`, `tg_username`, `lang`, and later `chapter_id`) is
explicitly *not* gated behind consent by the requirement's own description ("A User row
created at /start holds only what Telegram supplies... no Profile row and no phone/email
may be written before consent_pd_at is set") — this is the requirement text's own
resolution of the apparent tension with S1, not something this design resolves on its
own, and it's restated here so it isn't mistaken for an unaddressed conflict.

### 2.5 Consent callback handler

`bot.callbackQuery("consent:agree", handler)`. Steps:

1. Resolve the tapping user via `tg_id = ctx.from.id` (the same entry-point pattern as
   every command/callback handler — see §6 for why this doesn't violate AC5).
2. If no such user row exists (should not happen in the normal flow, but a stale/forwarded
   callback is possible), answer the callback query and reply with a fixed catalog
   fallback — reuse `getCatalog(resolveLang(null, null)).start.greeting` context is wrong
   here; instead this is the one case genuinely uncovered by any AC, so the handler
   simply answers the callback with no further reply text change, matching REQ-013 §2.3's
   established pattern of never leaving a tap silently unanswered
   (`ctx.answerCallbackQuery()` is always called).
3. `UPDATE users SET consent_pd_at = now(), <version column> = CONSENT_WORDING_VERSION
   WHERE id = $1` — **the `<version column>` does not exist in the current schema.** See
   §5, item 1 — this is flagged as a genuine schema gap, not resolved by this design.
4. Answer the callback query, then reply with the localized `start.greeting` — consent
   acceptance is the last gate; once it clears, `/start`'s job is done.

**Security note on why the version is a server-side constant, not trusted client input:**
if the version identifier were taken from `callback_data` (e.g. `"consent:agree:v1"`),
a client could in principle round-trip an arbitrary string, and a value with
audit/compliance significance ("which wording was this person actually shown and did
they agree to it") should not be attacker-influenced. Reading it from the same
server-side constant that rendered the prompt avoids that, at the acceptable cost of a
narrow edge case noted in §5 item 3 (a stale prompt sent under an older version, tapped
after a version bump, would record the *current* version rather than the one actually
displayed) — negligible at this project's deployment cadence and scale (PRD §11's
~1,000-user, single-chapter-pair scope), and strictly safer than trusting the client.

### 2.6 Chapter callback handler

`bot.callbackQuery(/^chapter:(.+)$/, handler)`:

1. Resolve the tapping user via `tg_id` (same entry pattern, §6).
2. Extract the chapter id from the match. **Validate it against the currently active
   chapter set** (re-run the "list active chapters" query, or check the tapped id is a
   member of it) before writing — a stale keyboard (a chapter deactivated between prompt
   and tap) or a tampered `callback_data` value must not silently assign a user to a
   nonexistent or now-inactive chapter. If invalid, answer the callback query and inform
   the user to re-run `/start` (no dedicated catalog key proposed for this rare
   corrective path — flagged in §5 as a minor open item rather than inventing one
   unasked-for).
3. If valid: `UPDATE users SET chapter_id = $1 WHERE id = $2` (keyed on `users.id`).
4. Answer the callback query, then proceed directly into §2.4 (consent prompt), exactly
   as the silent-assignment and zero-chapter branches do — the chapter step and the
   consent step are two sequential, independently-gated stages of the same overall
   `/start` flow, not two different flows.

### 2.7 Why a callback-query two-step, not the `conversations` plugin

**Recommendation: plain `bot.callbackQuery` handlers (grammY core, no new dependency),
not the `conversations` plugin.** Argued explicitly, since decision 0004 requires a real
plugin addition to be flagged rather than added silently:

- This is a **single, one-time, one-shot decision point** ("which of these N chapters"),
  not a multi-step form with several sequential fields the way REQ-019's `/profile` form
  is (decision 0004 §1 itself distinguishes exactly this: the conversations plugin earns
  its cost for *dialogue position across many steps*, not a single tap). There is nothing
  here resembling "which step is the user on" state that would need a storage adapter —
  the entire "conversation" is: bot asks, user taps, bot proceeds. All the state that
  matters (has this user got a `chapter_id` yet? a `consent_pd_at`?) is already sitting in
  the `users` row itself, so **the database is the state store**, not an in-memory or
  persisted conversation session.
- PRD §11's small-scale/simplicity bias (cited by decision 0004 itself as a reason
  Telegraf's serverless-friendliness doesn't matter here, but the same bias cuts against
  *any* unneeded dependency) favors not adding a plugin, its storage-adapter
  configuration burden (decision 0004's own correction: "the default storage backend is
  an in-memory Map... it is not free"), and its associated SECURITY-REVIEWER/REVIEWER
  surface, for a problem two `bot.callbackQuery` registrations already solve completely.
- The callback-query approach is exactly the shape REQ-013 already established and
  shipped for `/lang` (prompt with inline keyboard now, handle the tap in a separate
  `callbackQuery` handler later) — reusing an already-reviewed, already-working pattern
  is lower risk than introducing a new plugin's first real usage on the same
  first-contact path that creates every future user.
- **Restart-safety is free here, unlike the conversations plugin's default:** because
  every intermediate fact (`chapter_id`, `consent_pd_at`) is written straight to the
  `users` row rather than held in a plugin's session, a process restart between the
  chapter prompt and the tap loses nothing — the user just taps the (still-valid) button
  whenever the process comes back, and the callback handler resolves fresh state from the
  database. A conversations-plugin implementation would need exactly this same
  database-write discipline anyway to avoid decision 0004's flagged "restart-safe
  dialogue position, not restart-safe domain data" gap — so it would buy nothing over the
  callback-query approach for this specific one-shot interaction.

**If a future step needs to be reversed:** should REQ-019 or a later requirement
introduce a genuinely multi-step bot form, that is precisely decision 0004's stated
trigger ("plugins are added when a requirement needs them") — not a retroactive argument
for changing this requirement's flow.

**No dependency addition required for this requirement.** `InlineKeyboard` and
`bot.callbackQuery` are `grammy` core exports already used by REQ-013's `/lang` handler.

### 2.8 Combined flow, top to bottom

```
/start received
 -> resolve tgId, guard on undefined
 -> resolveOrCreateUser(tgId, tgUsername, mappedLang)     [SELECT or atomic create]
 -> if chapterId is null:
      query active chapters (LIMIT 2)
        0    -> send start.noActiveChapters; continue (chapter_id stays null)
        1    -> UPDATE users.chapter_id silently; continue
        2+   -> send chapter.prompt + keyboard; STOP (resumes in chapter callback)
 -> if consentPdAt is null:
      send consent.prompt + agree keyboard; STOP (resumes in consent callback)
 -> else: send start.greeting (fully onboarded, or just finished onboarding)

chapter callback (chapter:<id>)
 -> resolve user by tgId
 -> validate <id> is currently active
 -> UPDATE users.chapter_id
 -> if consentPdAt is null: send consent.prompt + agree keyboard
 -> else: send start.greeting

consent callback (consent:agree)
 -> resolve user by tgId
 -> UPDATE consent_pd_at = now(), <version column: SCHEMA GAP, §5>
 -> send start.greeting
```

This makes `/start` naturally **idempotent and resumable** without any new persisted
"which step" state: every invocation (fresh command or callback tap) recomputes what's
still missing directly from the `users` row's own columns (`chapter_id`, `consent_pd_at`)
rather than trusting an in-memory or session-held position — consistent with §2.7's
argument that the database already is the state machine.

## 3. Repeat `/start` behavior (not explicitly required by an AC, stated for completeness)

- **Fully onboarded user** (`chapterId` set or zero-chapter-case already shown,
  `consentPdAt` set) sends `/start` again: `resolveOrCreateUser` returns the existing row
  unchanged, both gates are already satisfied, so the flow falls through directly to
  `start.greeting` in the caller's resolved language (`resolveLang(user.lang,
  chapter?.defaultLang)`) — the same reply shape the REQ-013 stub already produced for a
  known user, now reached via the real creation path instead of a read-only lookup.
- **Partially onboarded user** (e.g. tapped away before finishing consent) sends
  `/start` again: the flow re-evaluates from the top and re-shows whichever prompt is
  still outstanding — this is a natural consequence of §2.8's stateless recomputation, not
  a separate code path.

## 4. `/help` handler

`bot.command("help", handler)`. Steps: resolve the caller's language exactly as `/lang`
already does (`getUserWithChapterByTgId` + `resolveLang` — the existing REQ-013 read-only
helper is sufficient here since `/help` neither creates nor mutates anything), then reply
with `getCatalog(lang).help.body` — **the entire visible response is one catalog lookup,
no string concatenation, no inline literal appended.** This satisfies AC6's "no hardcoded
string literals in the handler" literally: the handler body contains zero user-facing
string constants of its own.

**Content is a provisional placeholder** (§1's table) pending real contact/community-link
information from the product owner, per §5 item 2 below — the mechanism (catalog-sourced,
localized, no hardcoded literal) is what this requirement's AC6 actually tests, and the
mechanism is complete regardless of the copy's final wording.

## 5. Open questions (not silently resolved)

1. **Consent wording version column — genuine schema gap, escalated to DATA-DESIGNER,
   not invented here.** AC3 requires that accepting consent "records the consent wording
   version," verified by "reading the row back." `docs/agents/design/REQ-014-schema.md`
   and the current `apps/bot/src/db/schema.ts` define `users.consent_pd_at` as a bare
   timestamp with **no companion column** for which wording version was shown. A
   timestamp alone cannot answer "which version was this" if the wording is ever revised
   later — inferring the version from "whatever the code constant said at read time"
   would be wrong for anyone who consented under an earlier version after a later revision
   ships, and is not what AC3's "reading the row back" literally describes (reading a
   *stored* value, not re-deriving one from current code state). **This design does not
   invent a column** — per this role's constraint, schema shape is DATA-DESIGNER's
   territory. A follow-up to DATA-DESIGNER is required before BACKEND-DEV can satisfy AC3
   as literally worded: most likely a new `users.consent_pd_version` (or similarly named)
   text/varchar column, NOT NULL only once consent exists (i.e., nullable, matching
   `consent_pd_at`'s own nullability, both null until acceptance). This is named as a
   concrete recommendation for DATA-DESIGNER to evaluate, not a decision this artefact is
   entitled to make.
2. **`/help`'s actual contact information and community link.** Not present anywhere in
   this repository (checked: no PRD document file, no prior design artefact, no existing
   constant). §1's placeholder copy is honest about being unfinished rather than
   fabricating a plausible-looking link. Whoever holds the real PRD 8 content (the product
   owner, or a future CONTENT-BA pass per decisions/0002's precedent, mirroring how
   REQ-013's minimal seed copy was later meant to receive a real CONTENT-BA pass) needs to
   supply it.
3. **Consent version drift on a stale prompt.** §2.5's security note: if the consent
   wording version constant is bumped between a prompt being sent and the user tapping
   "I agree," the recorded version will be the *current* one, not the one literally
   displayed in that specific message. Judged negligible at this project's scale and
   deployment cadence (PRD §11), but noted rather than silently ignored — a future
   requirement revising consent wording should re-examine this if it ever matters (e.g. by
   also stamping a `consent_prompt_sent_at`/message-id correlation, which nothing today
   requires).
4. **Chapter-callback validation-failure copy.** §2.6 step 2 (tapping a chapter that
   became inactive between prompt and tap) has no dedicated catalog string proposed —
   deliberately, since no acceptance criterion or requirement text describes this rare
   race, and inventing a full recovery UX for it would be scope creep. Flagged as a minor
   gap rather than silently handled with an unlocalized literal; a future pass may want a
   dedicated `chapter.staleSelection` key.
5. **Zero-active-chapters resolution — stated explicitly per this artefact's mandate to
   resolve or flag it:** resolved in §2.3 as a safe no-op (inform, don't assign, don't
   block, continue the flow) rather than an invented product rule about default chapters
   or auto-retry behavior. This is a defensive default for an unspecified input, in the
   same category as `resolveLang`'s existing fallback discipline — not a business decision
   about chapter lifecycle, which remains `REQ-014-schema.md` §7 open question 1's
   territory (whether a chapter should ever be *creatable* inactive) and is not reopened
   here.

## 6. `tg_id`-never-a-business-key discipline (AC5)

Every write and every domain-table join in this design resolves through `users.id` /
`chapters.id`:

- `resolveOrCreateUser`'s SELECT/create-if-missing step — keyed on `tg_id`. **This is the
  allowed exception** ("the single initial lookup-by-tg_id at /start's entry"), and by the
  same reasoning REQ-013 already established for `/lang`'s command handler and its
  callback handler (`docs/agents/design/REQ-013.md` §2.2/§2.3, both resolving via
  `tg_id = ctx.from.id`): **every** handler entry point — a command or a callback query —
  necessarily identifies the tapping/messaging Telegram account via `tg_id` before it can
  do anything else, because that is the only identifier Telegram's update payload
  supplies. Read this AC as "no `tg_id` in a join or FK between domain tables, and no
  `tg_id` used anywhere past the point a handler has resolved `users.id`" — not literally
  "one call site in the entire codebase" — which is the reading REQ-013's own precedent
  already relies on (its `/lang` and callback handlers each perform their own `tg_id`
  lookup, and that design was not treated as an AC5-equivalent violation). This is stated
  explicitly here as a confirmed interpretation rather than a silent assumption.
- Chapter assignment write (`UPDATE users SET chapter_id = ...`) — keyed on `users.id`.
- Consent write (`UPDATE users SET consent_pd_at = ... WHERE id = ...`) — keyed on
  `users.id`.
- Chapter listing/validation queries (`SELECT ... FROM chapters WHERE active = true`) —
  no reference to `users` or `tg_id` at all.
- `getUserWithChapterByTgId`'s `LEFT JOIN chapters ON users.chapter_id = chapters.id`
  (reused, unchanged) — the join itself is `users.chapter_id = chapters.id`, both internal
  `id` columns; `tg_id` only appears in the outer `WHERE`, exactly the allowed entry-point
  shape.

No new code introduced by this design touches `tg_id` as a foreign key or as a join
predicate between two domain tables.

## 7. Acceptance criteria mapping

| AC | Design element |
