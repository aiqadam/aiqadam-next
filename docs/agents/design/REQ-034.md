# REQ-034 — Registration into `requested` for an approval-gated event, with the decision-pending confirmation

**Requirement:** GitHub issue #66. Second requirement of Release 2 (`depends_on: REQ-033`,
already merged — `InviteCode` data model, unrelated to this requirement's own tables).
Implements USER-STORIES B6 ("Ask for a seat at a curated event") and PRD FR-4's
`requires_invite=false, requires_approval=true` row. Replaces REQ-020's deliberate
placeholder refusal (`{ kind: "requires-approval" }`) with the real behaviour: create the
registration as `admission = 'requested'` instead of refusing.

**Surface:** `apps/bot/**` (bot requirement).

**No schema change — confirmed independently, not taken on the issue's word.** Read
`apps/bot/src/db/schema.ts` directly (lines 188–194): `admission` is already
`pgEnum("admission", ["requested", "waitlisted", "admitted", "rejected", "withdrawn"])`.
Read `apps/bot/src/domain/registration.ts` line 25–30: `AdmissionState` already includes
`"requested"`. `events.registrationClosesAt` (schema.ts line 232) is already
`timestamp("registration_closes_at", { withTimezone: true })` with **no** `.notNull()` —
nullable, exactly as the requirement assumes. `events.startsAt` (line 230) is `NOT NULL`.
**`DATA-DESIGNER` is not needed for this run** — same precedent as REQ-020/021/022/023/024.

**Files this design expects to change:**
- `apps/bot/src/domain/registration.ts` (existing) — `decideRegistrationOutcome`'s
  `requiresApproval` branch (§1), `RegistrationOutcome`'s union (§1), `registerForEvent`'s
  writing-outcome set and audit-log action mapping (§2)
- `apps/bot/src/handlers/registration.ts` (existing) — the post-outcome event-data fetch
  gate, the new `"requested"` reply branch, and the removal of the now-unreachable
  `"requires-approval"` branch (§3)
- `apps/bot/src/i18n/types.ts`, `en.ts`, `ru.ts` — new `Catalog.registration` keys, removal
  of the now-dead `refusedRequiresApproval` key (§4)
- No change to `apps/bot/src/handlers/my.ts`, `apps/bot/src/handlers/start.ts`'s event-card
  send, or any i18n `my.*`/`events.*` keys — see §0.2/§0.3 for why.

## 0. Reuse decisions and scope boundaries, stated up front

### 0.1 This is a domain-logic change, not a handler-only change — traced precisely

Tracing `registerForEvent`'s current body (`domain/registration.ts` lines 117–256):

1. `decideRegistrationOutcome` (§2.2 of that file, lines 56–82) is a pure first-match-wins
   table. Its `requiresApproval` branch (line 75–77) currently returns
   `{ kind: "requires-approval" }` **before** the `seatsLeft > 0` check (line 78) is ever
   reached.
2. `registerForEvent`'s own step 7 (line 189) treats every outcome **other than**
   `"admitted"`/`"waitlisted"` as non-writing: `if (outcome.kind !== "admitted" &&
   outcome.kind !== "waitlisted") { return outcome; }` — no row is created, no audit row is
   written, for `"requires-approval"` today.

**The fix changes both the pure decision function's return value and the transactional
function's writing-outcome set** — this is squarely domain logic, not a rendering choice:

- `decideRegistrationOutcome`'s `requiresApproval` branch changes its return value from
  `{ kind: "requires-approval" }` to `{ kind: "requested" }`. Nothing else in the
  first-match-wins table's order changes — `requiresApproval` is still checked exactly
  where it is today (after `requiresInvite`, before the `seatsLeft` check), so **AC7's
  "an event with `requires_approval=false` is unaffected" holds structurally**: that
  branch is unreached whenever `requiresApproval` is `false`, exactly as today.
- `RegistrationOutcome`'s union (line 42–51) drops the `{ kind: "requires-approval" }`
  member and gains `{ kind: "requested" }`.
- `registerForEvent`'s step 7 condition becomes: an outcome is a **writing** outcome iff
  its `kind` is `"admitted"`, `"waitlisted"`, or `"requested"`; every other kind
  (`"not-found"`, `"already-registered"`, `"event-cancelled"`, `"event-finished"`,
  `"registration-closed"`, `"requires-invite"`) returns unchanged, exactly as today.
- The `qrToken` line (line 196) — `outcome.kind === "admitted" ? generateQrToken() :
  null` — needs **no change at all**. `"requested"` already falls into the `null` branch
  of this existing ternary, the same way `"waitlisted"` already does today. This is what
  makes AC5 (`qr_token IS NULL` on a requested row) true by the **existing** code's own
  shape, not a new guard this design adds.
- The `INSERT`/`UPDATE`'s `admission: outcome.kind` (lines 208/221) also needs **no
  change** — it already writes whatever `outcome.kind` is, and `"requested"` is now a
  legal member of that writing set.
- The audit-log `action` mapping (line 243) gains a third branch: `"requested"` maps to
  a new action string, `"registration.request"` (§2 below) — the existing ternary between
  `"registration.admit"`/`"registration.waitlist"` becomes a three-way mapping.

The **handler-level** part of the change is separate and additive: `handlers/registration.ts`
needs a new reply branch for the `"requested"` outcome kind (§3), because the outcome kind
itself is new. Both halves are in scope for this requirement — stating this explicitly
because REQ-issue text described only the "creates a row" outcome, and a design that only
touched the handler would leave `decideRegistrationOutcome` still returning a refusal.

### 0.2 Zero capacity check on this path — traced precisely, not just asserted

`registerForEvent` computes `seatsLeft` (line 172, `computeSeatsLeft(event.capacity,
admittedCount)`) **unconditionally**, before calling `decideRegistrationOutcome` — this is
existing, unchanged behaviour (every outcome needs `seatsLeft` computed because
`decideRegistrationOutcome`'s input shape requires it). Computing the number is not itself
a check. The **check** is the `if (input.seatsLeft > 0)` comparison inside
`decideRegistrationOutcome` (line 78) — and with the `requiresApproval` branch (line 75)
unchanged in its position (still before line 78), a `requiresApproval = true` event's
request **never reaches line 78 at all**. `seatsLeft`'s computed value plays no role
whatsoever in what `decideRegistrationOutcome` returns for a requiresApproval event,
whether it is `5` or `-3` (over capacity). No new comparison against `seatsLeft` or
`capacity` is added anywhere on this path. This is what makes AC4 (a request at/over
capacity still succeeds as `"requested"`) true structurally, and it is also why S7/PRD
12.2's `seats_taken = count(admission = 'admitted')` is preserved unchanged — a
`"requested"` row is never counted by `countAdmittedRegistrations` (used by `seatsLeft`'s
own computation, `domain/event.ts`), so it can never itself consume a seat.

### 0.3 `/my` and the event card need NO changes — traced, not assumed

Checked `handlers/my.ts` and `handlers/registration.ts` directly:

- `handlers/registration.ts`'s `STATUS_CATALOG_KEY` (line 21–27, exported since REQ-024)
  **already** maps `requested: "statusRequested"`, and `apps/bot/src/i18n/en.ts`/`ru.ts`
  **already** define `statusRequested` (`"requested"` / `"запрошено"`). This map was built
  for the `AdmissionState` union, which has included `"requested"` since REQ-011 — it was
  never missing a case.
- `handlers/my.ts`'s row-rendering (`composeRowText`, line 30–42) uses this same map
  unconditionally for every row regardless of admission value, and its QR gate (line 108)
  is `row.admission === "admitted" && row.qrToken !== null` — `"requested"` rows
  structurally take the plain-text branch (line 115–119), never the photo branch. **No
  line of `my.ts` changes.**
- `handlers/registration.ts`'s `composeRegistrationReply`'s `"already-registered"` branch
  (line 137–145) already renders `STATUS_CATALOG_KEY[outcome.admission]` for **any**
  `AdmissionState`, including `"requested"` — this is what already satisfies AC3
  ("requesting twice shows the person's CURRENT pending status") with **zero** change to
  that branch. The `UNIQUE(event_id, user_id)` index (REQ-011) plus
  `decideRegistrationOutcome`'s existing first check (`existingAdmission !== null` →
  `"already-registered"`, line 60–62, unchanged) together make the "exactly one row"
  half of AC3 true, exactly as they already do for every other admission state.
- The event card (`handlers/start.ts`'s `resolveEventDeepLink`, lines 160–182) renders a
  Register button **unconditionally** — it does not read or display the viewer's own
  admission state at all, for any admission value, today. Nothing about this requirement
  changes that; the issue's mention of "/events (REQ-017)" rendering `requested` plainly
  is satisfied by the **already-registered reply branch** above, not by the card itself.

Consequence: **§0.3's three points above are pre-existing correctness, not new design
elements this requirement adds.** They are listed here because AC3/AC5's "verified by...
/my" wording could otherwise be misread as requiring a `my.ts` change.

### 0.4 The confirmation is a direct, synchronous reply — NOT `sendLedgeredNotification`, and no new `NotificationKind`

The issue text says this send "goes through REQ-025's ledger... the same distinction
REQ-018's description drew." Read `docs/agents/design/REQ-018.md` (§0, its own stated
reasoning, lines 409–415) and `domain/notification.ts` (§S9's docstring, lines 12–26) to
check this claim rather than following it uncritically:

- `sendLedgeredNotification`'s entire reason to exist is **idempotency across retries of
  a send that could otherwise be re-triggered** — a scheduled job re-running after a
  restart, a reminder batch re-selecting the same row, a promotion notification fired a
  second time by a re-run of `promoteFromWaitlistIfEligible`. S9's own stated negative
  case is exactly this: "the scheduler restarted mid-batch."
- REQ-020's **existing** `registerForEvent` → `composeRegistrationReply` path — which
  already produces the `"admitted"` and `"waitlisted"` confirmations today — is a
  **direct, synchronous `ctx.reply` inside the same callback handler invocation that
  performed the write**, called exactly once, in response to exactly one Telegram
  `callback_query` update. It is never re-run by a scheduler, never re-selected by a
  batch job, and carries no retry path of its own — grammY delivers each `callback_query`
  update exactly once to this handler. There is nothing here for `sendLedgeredNotification`
  to deduplicate **against**: a second delivery of the same reply would require Telegram
  itself re-delivering the same `callback_query`, which grammY's own update handling
  already treats as a distinct concern unrelated to this design (no other registration
  outcome branch — `"admitted"`, `"waitlisted"`, `"already-registered"` — uses the ledger
  either).
- **Conclusion: the `"requested"` confirmation reuses the exact same
  `composeRegistrationReply` → `ctx.reply` path the `"admitted"`/`"waitlisted"` branches
  already use, inside `makeRegisterCallbackHandler`.** It is a new `switch` branch in an
  **existing** direct-reply function, not a new ledgered send. **No new `NotificationKind`
  is added** — `notification.ts`'s closed union (lines 15–26) is untouched by this
  requirement.
- This reading is independent of REQ-018's now-superseded reasoning (REQ-018's own
  comment said its direct send was provisional "until REQ-025 lands" — REQ-025 has since
  shipped, so that specific justification no longer applies to REQ-018's case). It does
  not change this requirement's answer: REQ-034's send was never conditioned on the
  ledger not existing — it is a synchronous reply to the tapper's own action, the same
  category REQ-020's already-shipped `"admitted"`/`"waitlisted"` replies fall into, and
  the ledger's own purpose (dedup across independent re-runs) simply does not describe
  this call site.

## 1. `decideRegistrationOutcome` — the outcome-kind change

**Current signature and behaviour, unchanged except for the one branch below:**

```
export type AdmissionState =
  | "requested"
  | "waitlisted"
  | "admitted"
  | "rejected"
  | "withdrawn";

export interface RegistrationDecisionInput {
  existingAdmission: AdmissionState | null;
  eventStatus: "draft" | "published" | "cancelled";
  requiresInvite: boolean;
  requiresApproval: boolean;
  registrationClosesAt: Date | null;
  endsAt: Date;
  seatsLeft: number;
}

export type RegistrationOutcome =
  | { kind: "not-found" }
  | { kind: "already-registered"; admission: AdmissionState }
  | { kind: "event-cancelled" }
  | { kind: "event-finished" }
  | { kind: "registration-closed" }
  | { kind: "requires-invite" }
  | { kind: "requested" }              // CHANGED — was { kind: "requires-approval" }
  | { kind: "admitted" }
  | { kind: "waitlisted" };

export function decideRegistrationOutcome(
  input: RegistrationDecisionInput,
  evaluationTime: Date,
): RegistrationOutcome;
```

**The first-match-wins table, stated exactly (only row 6 changes; rows 1–5 and 7–8 are
unchanged, same order as today):**

| # | Condition | Result |
|---|---|---|
| 1 | `existingAdmission !== null` | `{ kind: "already-registered", admission: existingAdmission }` |
| 2 | `eventStatus === "cancelled"` | `{ kind: "event-cancelled" }` |
| 3 | `isFinished(endsAt, evaluationTime)` | `{ kind: "event-finished" }` |
| 4 | `!isRegistrationOpen(registrationClosesAt, evaluationTime)` | `{ kind: "registration-closed" }` |
| 5 | `requiresInvite` | `{ kind: "requires-invite" }` |
| 6 | `requiresApproval` | **`{ kind: "requested" }`** ← the only changed row |
| 7 | `seatsLeft > 0` | `{ kind: "admitted" }` |
| 8 | (else) | `{ kind: "waitlisted" }` |

Row 6 still sits between rows 5 and 7 exactly as today — this is why row 7's `seatsLeft`
comparison is structurally unreachable whenever `requiresApproval` is true (§0.2), and why
AC7 (an unaffected `requires_approval=false` event) holds: rows 1–5 and 7–8 are byte-for-
byte the same table entries the current, shipped REQ-020/021 code already implements.

written inside the same transaction as the one `INSERT`/`UPDATE`, both committing or
rolling back together (AC6).

|---|---|

| `event.registrationClosesAt === null` | `null` |

### 3.3 `composeRegistrationReply` — the new `"requested"` branch, and the removed `"requires-approval"` branch

**Signature:**

```
function composeRegistrationReply(
  outcome: Awaited<ReturnType<typeof registerForEvent>>,
  catalog: ReturnType<typeof getCatalog>,
  eventTitle: string,
  dateTimeText: string,
  waitlistPosition: number | null = null,
  registrationClosesAtText: string | null = null,   // ADDED
): string;
```

The `switch (outcome.kind)` (line 121–158) changes as follows:

- **Removed:** the `case "requires-approval":` branch (line 154–155) — this `kind` can no
  longer be produced by `decideRegistrationOutcome` (§1), so the branch is dead and TS's
  own exhaustiveness check over the narrowed `RegistrationOutcome` union requires its
  removal (leaving it in place would be a type error against the new union, not a style
  choice).
- **Added**, in its place, a new `case "requested":` branch. Composition rule, stated as a
  table (mirrors the existing `"waitlisted"` branch's own conditional-line shape, lines
  126–136):

  | Line | Always included? | Content |
  |---|---|---|
  | 1 | Yes | `catalog.registration.requestedPrefix` |
  | 2 | Yes | `eventTitle` |
  | 3 | Yes | `dateTimeText` |
  | 4 | Only if `registrationClosesAtText !== null` | `` `${catalog.registration.requestedDecisionByPrefix} ${registrationClosesAtText}` `` |
  | 4′ (else) | Only if `registrationClosesAtText === null` | `catalog.registration.requestedDecisionByFallback` |
  | 5 | Yes | `catalog.registration.requestedWhatNext` |

  Lines joined with `"\n"`, same as every other branch in this function.

This table is exactly what makes AC2 true: when `registration_closes_at` is non-null, line
4 states the exact chapter-local rendering of that column (via the same
`formatDateTimeInTimezone` call every other date in this codebase already uses — no new
formatting logic); when it is null, line 4′'s fixed fallback string fires instead, and
line 3 (`dateTimeText`, already always present) already states the event's start/end time
in chapter-local time — so the fallback branch is "phrased in terms of the event start"
by virtue of that line already being on the message, without repeating the date a second
time in different wording.

## 7. Summary for the design gate

- **No schema change** (confirmed directly against `schema.ts`, §"No schema change" above)
  — `DATA-DESIGNER` is **not** dispatched for this run.
- **Domain-logic change**: `decideRegistrationOutcome`'s `requiresApproval` branch and
  `registerForEvent`'s writing-outcome set + audit-action mapping (§1–§2), both in

  gate, and a removed now-dead `"requires-approval"` branch, all in
  `apps/bot/src/handlers/registration.ts` (§3).
- **i18n change**: four new `registration.*` keys, one removed, across `types.ts`/`en.ts`/
  `ru.ts` (§4).
- **No change** to `apps/bot/src/handlers/my.ts`, `apps/bot/src/handlers/start.ts`'s
