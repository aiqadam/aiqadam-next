## 0. Reuse decision: generalize `venueAuthorization.ts` or add a parallel module?

**Decision: add a parallel `domain/eventAuthorization.ts`, not a generalization of
`venueAuthorization.ts`.**

Reasoning:
- REQ-015's `checkOrganizerForChapter`/`requireOrganizerForChapter` predicate is already
  entity-agnostic in its logic (it takes a `targetChapterId` string and an `ActingUser`,
  and never reads or writes anything venue-specific) — the only entity-specific thing
  about `venueAuthorization.ts` is its *filename* and its own doc comments, which say
  "venue-mutation handler" throughout.
- Two honest options: (a) rename/move the predicate into a shared, entity-neutral module
  (e.g. `domain/chapterAuthorization.ts`) and have both `venue.ts` and `event.ts`'s
  handlers import from it, touching REQ-015's already-shipped, already-merged files; or
  (b) duplicate the same ~30-line predicate into a new `domain/eventAuthorization.ts`
  with identical logic, at the cost of two copies of the same rule that must stay in sync
  by hand.
- This design picks **(b)**, scoped narrowly: REQ-016's own acceptance criteria (AC8) ask
  only that "a member invoking the publish handler directly is refused" using the same
  authorization discipline as REQ-015 — they do not ask for a refactor of REQ-015's
  already-merged, already-audited files. Editing `venueAuthorization.ts` is out of this
  requirement's stated scope (core-directives.md's "Unblock-Everything" scope boundary:
  a defect/improvement noticed but not blocking this requirement is filed, not fixed
  here), and renaming a file REQ-015's own REVIEWER/SECURITY-REVIEWER already signed off
  on carries a non-zero risk of a silent regression for a purely cosmetic gain.
- The duplication cost is small and bounded: the predicate is ~10 lines of pure logic
  with a stable, already-decided shape (PRD 3's role definitions do not change per
  entity). If a **third** entity needing the identical chapter-scoped check appears
  later, that is the trigger to extract a shared module — two occurrences is not yet a
  pattern that pays for the refactor risk; three would be. This is flagged as an open
  question (§11.1) rather than resolved by silently picking one file layout forever.

`domain/eventAuthorization.ts` exports the identical shape to `venueAuthorization.ts`
(`ActingUser`, `AuthorizationResult`, `resolveActingUser`, `checkOrganizerForChapter`,
`requireOrganizerForChapter`), byte-for-byte the same logic, so a future extraction is a
pure move with no behavior change to verify.

## 1. Authorization (AC8, S2)

Identical predicate and call discipline to REQ-015 §1, reused per §0's decision:

```
// apps/bot/src/domain/eventAuthorization.ts
interface ActingUser { id: string; role: "member" | "organizer" | "owner"; chapterId: string | null; }
type AuthorizationResult =
  | { ok: true; user: ActingUser }
  | { ok: false; reason: "no-user" | "not-organizer" | "wrong-chapter" };

function resolveActingUser(db, tgId: bigint): Promise<ActingUser | null>;
function checkOrganizerForChapter(user, targetChapterId): AuthorizationResult;
function requireOrganizerForChapter(db, tgId, targetChapterId): Promise<AuthorizationResult>;
```

Called as the **first** statement of every event-mutation handler (create, edit,
publish, cancel), before any parsing of the mutation's own field text, any read of the
event row beyond what's needed to resolve `targetChapterId`, or any reply. Same ordering
rule as REQ-015 §4 for update/delete: for edit/publish/cancel, the event row is read
*first* only to discover `targetChapterId = event.chapterId` (required — an event's
chapter never comes from caller input), then the authorization check runs before any
further parsing or mutation.

**AC8 mapping** ("a member invoking the publish handler directly is refused, no side
effect"): identical proof shape to REQ-015 AC1 — `checkOrganizerForChapter` step 2
(`role === "member"`) returns `ok: false` before `publishEvent`/`createEvent`/etc. is
ever reachable, so a refused call writes zero `events` rows and zero `audit_log` rows.

**Refusal reply:** one generic catalog string (`event.notAuthorized`), reason never
disclosed to the caller. No audit row on an authorization refusal — same reasoning as
REQ-015 §1's closing note (S8 requires a row on a *status change*; a refused attempt
changes nothing). Carried forward as the same open question already flagged in REQ-015
§9.1, not re-opened here as a new one.

## 2. Event creation (draft) — AC-mapped to the requirement's general scope

### 2.1 Command shape

Same decision as REQ-015 §2.1 for the identical reasons (PRD 11 simplicity bias,
decisions/0004's "no plugin added preemptively," no restart-safety requirement stated for
event drafts): **a single command carrying structured multi-line text**, no
`conversations`-plugin multi-step flow.

`/event_new` with no further text replies with a usage template (`event.createUsage`).
To create, the organizer sends `/event_new` followed by `label: value` lines:

```
/event_new
title: LLM Engineering in Production
description: A practitioner's walkthrough of...
format: meetup
venue: <venue-id>            (omit only for an event with no venue — see §3.3's finding)
starts: 2026-10-01T18:00:00+05:00
ends: 2026-10-01T20:30:00+05:00
registration_closes: 2026-10-01T12:00:00+05:00   (optional)
capacity: 60
requires_invite: false        (optional, default false)
requires_approval: false      (optional, default false)
cover_file_id: <file-id>      (optional)
chapter: <chapter-id>         (optional — same override semantics as REQ-015 §2.5)
```

`agenda[]` is **not** settable through `/event_new`'s inline fields — it is a structured
array, not a scalar `label: value` pair, and PRD 5 states the talk lineup is never
duplicated into it, so there's nothing agenda-shaped an organizer would type at creation
time in most cases anyway. Agenda items are added/edited via a separate
`/event_agenda <event-id>` sub-flow (§7), consistent with venue's own precedent of
`/venue_edit` handling structured multi-line changes separately from creation.

`parseEventFields(text: string): Record<string, string>` — identical implementation to
REQ-015's `parseVenueFields` (split on newline, split each line on the first `:`,
case-insensitive labels, unknown labels ignored). This is the same framework-free,
no-DB, directly-unit-testable shape; whether it is literally the same exported function
reused from `domain/venue.ts` or a byte-identical copy in `domain/event.ts` is an
implementation choice with no observable behavior difference — this design states the
logic once and leaves the file-organization call to BACKEND-DEV, since (unlike §0's
authorization predicate) it carries no per-call state or entity coupling that would make
reuse risky.

### 2.2 Field set — draft-time (all PRD-5 fields editable, but NOT all required at
### creation; publish is what enforces "required")

Per the requirement text ("all PRD-5 fields editable") and the acceptance criteria's own
framing (AC1 tests **publish-time** required-field refusal, not creation-time refusal),
**event creation as a `draft` has no required-field validation beyond what the database
schema itself enforces as `NOT NULL`.** This is a deliberate, stated design choice, not
an oversight:

- `events.title`, `events.description`, `events.format`, `events.starts_at`,
  `events.ends_at`, `events.capacity` are `NOT NULL` at the schema level (schema.ts lines
  194–205) — so `createEvent` must supply *some* value for each of these regardless of
  what "required for publish" ends up meaning, or the `INSERT` itself fails.
- `venue_id`, `registration_closes_at`, `cover_file_id`, `agenda` are nullable at the
  schema level — a draft is explicitly allowed to omit them, and STORY-DETAILS A1
  ("Draft and cancelled events never appear to a member") plus the requirement's own
  framing ("Organizer creates an Event as `draft` — invisible to members") support a
  draft being an incomplete, in-progress record an organizer is still filling in.
- Because the DB's own `NOT NULL` columns already force `title`/`description`/`format`/
  `starts_at`/`ends_at`/`capacity` to be present on *any* insert (draft or not),
  `validateEventCreateInput` mirrors REQ-015's `validateVenueCreateInput` shape and
  treats exactly those six as "required to create at all," collecting every missing one
  into a single `missing: string[]` (same "name every missing field" discipline as
  REQ-015 §2.3) — this is a data-integrity floor, not the publish gate. It is a distinct,
  smaller list from §3's publish-required-field list (§3.2 explains the difference:
  publish additionally requires `venue_id` for a venue-requiring event, which creation
  does not).

| Field | Required to create a draft at all? | Reason |
|---|---|---|
| `title` | yes | DB `NOT NULL` |
| `description` | yes | DB `NOT NULL` |
| `format` | yes, must be one of `meetup`\|`fail_stories`\|`workshop`\|`hackathon` | DB `NOT NULL` enum |
| `starts_at` | yes, must parse as a valid ISO 8601 timestamp | DB `NOT NULL` |
| `ends_at` | yes, must parse as a valid ISO 8601 timestamp, and must be after `starts_at` | DB `NOT NULL`; the after-check is a basic sanity floor this design adds because an event ending before it starts is not a "field missing" case §3 is built to name, it's a malformed pair — refused at creation with a dedicated message, not folded into the publish-required-fields mechanism |
| `capacity` | yes, must parse as a positive integer | DB `NOT NULL` |
| `venue_id` | no | nullable column; §3.3 addresses whether publish requires it |
| `registration_closes_at` | no | nullable column |
| `requires_invite` | no (defaults `false`) | DB default |
| `requires_approval` | no (defaults `false`) | DB default |
| `cover_file_id` | no | nullable column |
| `agenda` | no (empty/`null` at creation; edited via §7) | nullable column |

`createEvent(db, actorUserId, targetChapterId, input, at)`: one `INSERT INTO events (...,
status: 'draft')` + one `AuditLog` row (`action: "event.create"`), one transaction — same
shape as REQ-015 §2.6's `createVenue`.

## 3. Publish transition (draft → published) — AC1, AC2

### 3.1 General "collect all missing required fields" mechanism (not hardcoded to three)

A dedicated function, run only on a publish attempt (never on create/edit), that
re-checks the **full** publish-required set against the event's **current, already-
stored** row (not the caller's latest edit payload — publish takes no field arguments of
its own, it operates on whatever the event currently holds):

```
// domain/event.ts

// Pure predicate over an already-loaded row — no I/O, unit-testable without a DB.
function findMissingPublishFields(event: EventRecord): string[];
```

**General mechanism over a declared list, stated exactly so it cannot be reinterpreted**
— not an `if/if/if` hardcoded to exactly the three fields the acceptance criteria happen
to test. The list of publish-required fields and each one's exact "missing/invalid"
condition:

| Key (name used in the refusal) | Missing/invalid when |
|---|---|
| `title` | blank or whitespace-only (`isBlank(e.title)`) |
| `starts_at` | `null` |
| `ends_at` | `null` |
| `capacity` | `null`, zero, or negative |
| `venue` | `venue_id` is `null` (§3.3 — every format needs a venue today) |

`findMissingPublishFields` evaluates every row above against the given event and
returns the list of keys whose condition is true, in the table's order. The check is
declarative over this list, not a sequence of independent `if` statements — the AC's own
wording ("each missing field," tested by removing title/starts_at/capacity
*individually*) is satisfied by a list-driven check that would equally refuse-and-name a
missing `venue` or a corrupted `ends_at`/`capacity` without needing new control flow
added for every future field PRD 5 might add. Adding a new publish-required field later
means adding one row to this table (and its corresponding condition), not writing new
control flow.

Since `title`/`starts_at`/`ends_at`/`capacity` are already `NOT NULL` at the DB level
(§2.2), a *currently-stored* draft can never actually be missing them once creation
succeeded — so in practice only `venue` (nullable) is ever the field that fires this
check on a real row today. This is stated explicitly rather than treated as suspicious:
the mechanism is general (it would correctly catch a future nullable-at-creation field),
and the acceptance criteria's "missing title/starts_at/capacity" cases are constructed as
raw fixture rows directly against the table (same technique the acceptance criteria
themselves specify: "verified by attempting publication with title, starts_at and
capacity each individually absent" — this is only reachable by writing a row that
bypasses `createEvent`'s own validation, e.g. a direct fixture `INSERT` with
`title: null`, which the schema's `NOT NULL` would itself reject at the DB layer unless
the fixture inserts through a path that doesn't enforce it, OR — see §3.1a below — the
column is genuinely nullable and the AC's premise needs re-reading).

### 3.1a Resolving the AC1/schema tension for `title`/`starts_at`/`capacity`

**Open tension, named rather than silently smoothed over:** AC1 asks to verify refusal
"with title, starts_at and capacity each individually absent," but all three are `NOT
NULL` in the current schema (schema.ts lines 194, 200, 205) — a row with any of them
`null` cannot exist in the table at all, so "constructing that state" as literally a
stored row is impossible without a schema change this design is not authorized to make
(DATA-DESIGNER's territory, and the schema addendum, §16-016-schema.md, does not propose
loosening these constraints).

**Resolution: `findMissingPublishFields` still checks all three** (§3.1's declared
list), so the *mechanism* is correct and general regardless of which fields are
currently reachable — this is not a wasted check, because a title of empty string `""`
(as opposed to SQL `NULL`) is very much constructible without any schema change
(`isBlank` catches it), and a `capacity` of `0` is likewise constructible today (the DB
only forbids `NULL`, not `0` or negative — `capacity integer NOT NULL` has no `CHECK
capacity > 0`). **Re-reading AC1's "individually absent" as "individually
absent-or-invalid"** — blank title, non-positive capacity — makes every one of the
three cases genuinely constructible today without a schema change, and is the reading
this design adopts: `isMissing` for `title` treats `""`/whitespace-only as missing (not
only SQL `NULL`), and for `capacity` treats `<= 0` as missing, not only `NULL`.
`starts_at`/`ends_at` remain checked as `=== null`, which cannot occur through
`createEvent` (schema `NOT NULL`) but is retained in the general list for defense in
depth and because TEST-DESIGNER may still choose to construct it via a raw fixture
`INSERT` bypassing the app layer entirely (Postgres itself would reject a literal `NULL`
insert against a `NOT NULL` column, so this specific sub-case is genuinely untestable
against the real schema — flagged as an open question, §11.2, for TEST-DESIGNER/
TEST-DESIGN-VALIDATOR to resolve when writing the concrete verification case: either
they use `""`/`0`-style invalid-not-missing values for `title`/`capacity` per this
section's reading, or they escalate that AC1's `starts_at` sub-case is untestable as
literally worded and needs the same "absent-or-invalid" reframing applied to it too —
e.g. a `starts_at` far enough in the past to be nonsensical is NOT what AC1 asks for, so
there may be no constructible negative case for `starts_at` specifically without a
schema change, and that gap should be raised rather than silently faked).

### 3.2 Refusal message (AC1)

`event.publishRefusedMissingFields` + the field-name list, same "name every missing
field" composition pattern as REQ-015's `missingFieldsPrefix`:

```
publish refused. Missing/invalid: title, capacity
```

No partial-publish: if `findMissingPublishFields` returns any entries, `publishEvent`
returns `{ ok: false, missing: string[] }` and performs **no** `UPDATE` and **no**
`AuditLog` write — same "refusal writes nothing" discipline as every other check in this
design.

### 3.3 Offline/online format investigation (AC2)

**Finding, stated rather than invented:** `eventFormat` (schema.ts lines 145–150) is
`pgEnum("event_format", ["meetup", "fail_stories", "workshop", "hackathon"])`. **There is
no `online` value in this enum, and no other column or convention in the current schema
distinguishes an "online" event from an "offline" one.** `git grep -n "online"
apps/bot/src` (domain code) returns nothing — "online" appears only in the **design
system's** copy vocabulary (`docs/Design system for AI agents/readme.md`'s `EventCard`
"4 states: upcoming · live · past · online" and the `ONLINE` status-label example), which
is a **card-rendering concept for REQ-017's future UI**, not a stored `Event` fact this
requirement's schema currently models at all.

**Resolution adopted by this design: every event, of every current format value,
requires a `venue_id` to publish.** AC2's phrasing ("Publishing an **offline** event
whose `venue_id` is null is refused") is read as: since the schema has no mechanism today
to mark an event as *not* requiring a venue, **"offline" is simply the only kind of event
this schema can currently express**, and the qualifier "offline" in the AC's wording
describes every event in the current format enum, not a subset — `venue` is therefore
included, unconditionally, in `PUBLISH_REQUIRED_FIELDS` (§3.1), with no format-based
branching. This is the position stated in the CODE-DESIGNER brief's own framing
("reconsider... making 'offline' the only kind, and venue_id effectively always
required"), confirmed by reading the schema.

**What this design explicitly does NOT do:** it does not invent an `online` format
value, an `is_online` boolean column, or any other schema element to make the
online/offline distinction real. If a future requirement needs a genuinely venue-less
"online meetup" format, that requires (a) a requirement adding `online` (or similar) to
the `eventFormat` enum or an equivalent flag — DATA-DESIGNER's decision — and (b) a
follow-up change to `PUBLISH_REQUIRED_FIELDS` to branch on it. Flagged as an open
question, §11.3.

### 3.4 Capacity floor (AC3)

**General mechanism, correct today (0 admitted rows) and correct once REQ-020 exists:**

```
// domain/event.ts
async function countAdmittedRegistrations(
  db: DbClient["db"],
  eventId: string,
): Promise<number> {
  // SELECT count(*) FROM registrations
  // WHERE registrations.event_id = $eventId
  //   AND registrations.admission = 'admitted'
}
```

Called from **two** call sites, both before any write:

1. **Publish** — `publishEvent` calls `countAdmittedRegistrations` and compares against
   the event's *current, already-stored* `capacity` (publish does not change capacity
   itself, so this is really "is the currently-stored capacity still >= admitted count,"
   which can only fail if capacity was somehow lowered below admitted count through some
   other path — defense in depth, since §3.4's edit-time check below is what's actually
   supposed to prevent that state from ever being reached). Genuinely, under this
   design's own edit-time gate, this publish-time re-check can never fire in practice —
   stated the same way §3.1 states the `NOT NULL` fields can't really be "missing" post-
   creation: it's a general, always-run safety re-check, not dead code removed for being
   currently unreachable via the normal edit path.
2. **Any capacity edit** (via `/event_edit`, §5) — whenever the edit payload contains a
   `capacity` field, `validateEventUpdateInput` runs this sequence before any write:
   1. Parse the supplied `capacity` value as an integer.
   2. If it does not parse as an integer, or parses to zero or a negative number, treat
      `capacity` as an invalid field the same way §2.2's create-time table does (named in
      the refusal, same "name every missing/invalid field" discipline) — stop here, no
      further step runs, no write occurs.
   3. Otherwise, call `countAdmittedRegistrations(db, eventId)` (the same function as
      call site 1 above) to get the current admitted count.
   4. If the parsed, valid `capacity` value is less than that admitted count, refuse with
      a `capacityFloorViolation` result carrying both numbers (the proposed capacity and
      the admitted count) — stop here, no write occurs.
   5. Otherwise, the parsed value is accepted into the update's change set as `capacity`,
      and the field is recorded among the changed fields for the audit payload (§8).

**Refusal message (AC3):** `event.capacityBelowAdmittedFloor` — e.g. "Capacity cannot be
set below N admitted registrations" with `N = admittedCount` interpolated. **No write of
any kind occurs on this path** — not to `events.capacity`, and critically, per AC3's own
wording ("no admitted registration is altered"), **this mechanism never touches the
`registrations` table at all**, in either direction — it only reads a `count(*)`. There
is no code path in this design that could alter a `registrations` row's `admission`
value as a side effect of a capacity edit; the read-only count query is the entire
mechanism, so "no admitted registration is altered" holds by construction (nothing here
writes to that table), not merely by the test not having found a bug.

**Why this is correct today with 0 real admitted rows and correct once REQ-020 ships:**
`countAdmittedRegistrations` is a plain, unconditional `COUNT` against the real
`registrations` table with no assumption baked in about whether any rows currently
exist — it returns `0` today only because REQ-020 (the requirement that actually creates
`registrations` rows) hasn't shipped, which makes every capacity value pass the floor
check today (since `proposed >= 0` is always true), but the query does not need to change
at all once REQ-020 exists and starts inserting real `admitted` rows — the same query
then naturally starts returning nonzero counts and correctly refusing. **Testable now**
via the same fixture-row technique REQ-014/REQ-015 used: TEST-DESIGNER's verification
case inserts raw `registrations` rows directly (`INSERT INTO registrations (event_id,
user_id, admission, source, ...) VALUES (..., 'admitted', ...)`, bypassing any handler,
exactly as AC3's own wording specifies — "constructing exactly that state... by
inserting raw registrations fixture rows directly").

## 4. Editing (AC-general; no post-publish field restriction invented)

`/event_edit <event-id>` with no further lines → current field values as a copy-editable
template (`formatEventDump`, mirroring REQ-015 `formatVenueDump`) + usage instructions.
`/event_edit <event-id>` + `label: value` lines → partial update of **only the supplied
fields**, at **any status** (draft, published, or cancelled) — the requirement's own text
does not say editing is restricted post-publish, and this design does not invent such a
restriction. The **one** place a "some fields behave differently depending on what's
already true" rule is genuinely implied by the acceptance criteria is AC6/AC7's agenda
validation, which is a **value-shape** check (does this replacement agenda array satisfy
the doors/ends_at rules), not a **status-gated** check (whether the event is
draft/published/cancelled) — so it applies identically regardless of the event's current
status, which is exactly what "refused at edit time" (not "refused at edit time only
pre-publish") means: the validation runs on every edit that touches `agenda`, full stop.

Editable fields: `title, description, format, venue_id, starts_at, ends_at,
registration_closes_at, capacity, requires_invite, requires_approval, cover_file_id,
agenda[]` — every PRD-5 Event field except `chapter_id` (never editable through this
command, same "moving between chapters is out of scope" precedent as REQ-015 §4) and
`status` (status changes only through the dedicated `/event_publish`/`/event_cancel`
commands, §5/§6 — never as a plain field value inside `/event_edit`'s `label: value`
lines, so a crafted `status: published` line in an edit payload is simply an unknown
label, ignored per `parseEventFields`'s forward-compatible "unknown labels ignored"
rule, never a transition bypass).

Authorization: `targetChapterId` = the existing event row's `chapterId`, read before the
authorization check (§1). Validation (`validateEventUpdateInput`) mirrors REQ-015 §4
step 3's partial-update shape: only supplied fields are checked/changed; `title`,
`description`, `format`, `starts_at`, `ends_at`, `capacity` cannot be cleared to blank
(present-but-blank refused, naming the field) since they stay `NOT NULL`; `venue_id`,
`registration_closes_at`, `cover_file_id` may be explicitly cleared (empty value ⇒
`null`). `capacity`'s floor check (§3.4) applies whenever `capacity` is present in the
edit payload, regardless of the event's status. `agenda` edits go through §7's
validation whenever `agenda` is present in the edit payload — but see §7's note on
`/event_edit` vs. the dedicated `/event_agenda` sub-flow.

`updateEvent(db, actorUserId, eventId, chapterId, changes, changedFields, at)`: one
`UPDATE` + one `AuditLog` row (`action: "event.update"`), one transaction — same shape as
REQ-015 §4's `updateVenue`. **Audit-on-update scope decision:** AC8 only explicitly
requires an audit row for draft-create, publish, and cancel — it does not name update.
This design **does** still write one on every successful update anyway, reasoning from
S8's general principle ("every status change writes exactly one AuditLog row... PRD
§12.7") generalized the same way REQ-015 already generalized it to non-status field
edits (`venue.update` is not a status change either, and REQ-015 audits it) — REQ-015's
own precedent, already reviewed and merged, is the controlling analogy, not a fresh
invention. Stated explicitly as a scope decision rather than silently assumed (§11.4).

## 5. Publish/Cancel command wiring

`/event_publish <event-id>`:
1. `event = getEventById(db, eventId)`. `null` → "not found", stop, no audit row.
2. `requireOrganizerForChapter(db, tgId, event.chapterId)`. Refused → stop, no audit row.
3. If `event.status !== "draft"` → refuse with `event.publishRefusedNotDraft` (a
   published event cannot be re-published; a cancelled event cannot be published —
   PRD's status machine has no `cancelled → published` or `published → published`
   transition; this is a state-machine guard, not one of AC1/AC2's field-validation
   refusals, and produces no audit row since nothing changed).
4. `findMissingPublishFields(event)` (§3.1) + capacity floor re-check (§3.4 site 1). Any
   failure → refuse naming the fields/floor violation, stop, no audit row.
5. All checks pass → `publishEvent(db, actorUserId, eventId, chapterId, at)`: one
   `UPDATE events SET status = 'published'` + one `AuditLog` row (`action:
   "event.publish"`), one transaction.

`/event_cancel <event-id>`:
1. `event = getEventById(db, eventId)`. `null` → "not found", stop.
2. `requireOrganizerForChapter(db, tgId, event.chapterId)`. Refused → stop.
3. If `event.status !== "published"` → refuse with `event.cancelRefusedNotPublished`
   (only a published event can be cancelled — cancelling a draft is "delete/leave it as
   draft," not this transition; cancelling an already-cancelled event is a no-op refusal,
   not a second cancellation).
4. `cancelEvent(db, actorUserId, eventId, chapterId, at)`: one `UPDATE events SET status
   = 'cancelled'` + one `AuditLog` row (`action: "event.cancel"`), one transaction.

**Explicit scope boundary (stated per the task's flagged tension #2): `cancelEvent`
performs the state transition and its audit row ONLY.** It does not read the
`registrations` table, does not compose or send any message to any registrant, and does
not call anything notification-shaped. Sending a cancellation notice to every
non-withdrawn registrant (PRD 6) is REQ-027's scope, per the requirement's own
description. This design deliberately leaves that gap visible rather than stubbing in a
placeholder notification call that would need to be found and wired to REQ-025's
send-once ledger later — there is nothing here for REQ-027 to "replace," only a clean
call site (`cancelEvent`'s transaction, once it commits) for REQ-027 to hook into by
adding its own call after this function returns, from the handler or a scheduled job,
whichever REQ-025/027's own design decides.

## 6. Deep-link resolution (AC4, AC5)

### 6.1 Mechanism: grammY's existing `/start` payload, not a new command

Telegram's deep-link convention (`https://t.me/<bot>?start=<payload>`) delivers the
payload as plain text after `/start` in the message the bot receives — i.e. the user's
client sends literally `/start e_<id>` or `/start e_<id>__linkedin` as the message text.
grammY's `bot.command("start", handler)` (already registered, `index.ts` line 47)
already receives this via `ctx.match`, exactly the same mechanism the existing `/start`
handler uses today for its own argument-free case (`matchText(ctx)` pattern already used
by `handlers/venue.ts`). **No new command registration and no deep-link plugin is
needed** — this is extending the existing `makeStartHandler` (or a thin wrapper it
delegates to) to branch on whether `ctx.match` matches the `e_` payload shape, not adding
a second bot-level command handler that would race with the existing one for the same
`/start` trigger.

### 6.2 Payload grammar

```
e_<event-id>                  — plain deep link, no channel
e_<event-id>__<channel>       — channel-suffixed deep link
```

`parseStartPayload(raw: string): { kind: "none" } | { kind: "event"; eventId: string;
channel: string | null }` (framework-free, in `domain/event.ts`):
1. `raw.trim()` is empty → `{ kind: "none" }` (ordinary `/start`, REQ-014's existing flow
   runs unchanged — this design does not touch that path at all).
2. Does not start with `e_` → `{ kind: "none" }` (forward-compatible: a future payload
   prefix, e.g. for a different deep-link kind, is simply not this design's concern and
   falls through to ordinary `/start` handling rather than erroring).
3. Starts with `e_` → split the remainder on the **first** `__` occurrence. Left part is
   `eventId`; if a `__` was found, right part is `channel` (kept as opaque text, not
   validated against a closed vocabulary — same "free text, PRD doesn't enumerate it"
   reasoning as `registrations.source` and `users.pending_source`, REQ-016-schema.md §3);
   if no `__` was found, `channel: null`.

### 6.3 Resolution logic

```
1. payload = parseStartPayload(matchText(ctx))
2. if payload.kind === "none": run the existing REQ-014 /start flow unchanged, return.
3. event = getEventById(db, payload.eventId)
4. if event === null:
     reply with the same "plain explanation" as step 5 below (an unknown/deleted event
     id is indistinguishable, from the caller's perspective, from a draft/cancelled one —
     neither should leak whether the id ever existed at all, consistent with not
     disclosing internal state to an unauthenticated deep-link opener)
5. if event.status !== "published":
     reply: event.deepLinkNotAvailable (the "plain explanation") — e.g. "This event
     isn't open yet." — followed immediately by the §6.4 stub/placeholder reference to
     the upcoming list (never the event card).
6. if event.status === "published":
     if payload.channel !== null:
       setPendingSource(db, userId, payload.channel)   -- AC5, see §6.5
     reply with the §6.4 placeholder-card reference (never a silent dead end, never the
     full REQ-017 card).
7. In every branch, the acting user's row must exist first (resolveOrCreateUser, same
   call REQ-014's /start already makes unconditionally at its own top) — a deep link is
   still someone's first-ever contact with the bot, so user creation happens before step
   3, using the identical resolve-or-create call the plain-/start path already uses.
```

### 6.4 AC4's forward-dependency — resolution (flagged tension #1)

**This design's own scope for AC4 is limited to exactly two things, stated explicitly
per the task's instruction, not silently expanded to build REQ-017's UI:**

**(a) Deep-link resolution behavior — built and tested now.** Opening
`?start=e_<draft-id>` (or a cancelled/finished id) yields the plain-explanation branch
(§6.3 step 5), never the event card. This is fully testable today: TEST-DESIGNER can
open the deep link against a fixture draft event and assert the reply is the plain
explanation, not a card-shaped message. The "upcoming list" reference in that same
reply is a **stub/placeholder line** — a single catalog string,
`event.deepLinkSeeUpcoming` (e.g. "See what's coming up with /events" — a plain text
pointer to a future command, not a rendered list), since `/events` and any list
rendering is REQ-017's entire scope and does not exist in this codebase yet
(`git grep -n "events\.command\|/events\b"` returns nothing under `apps/bot/src`). This
design does **not** build a minimal inline substitute list (e.g. querying and dumping
raw published-event rows as text) — inventing even a minimal version of REQ-017's list
here would pre-empt that requirement's own design (soonest-first ordering, chapter
timezone display, seat-count computation are all explicitly REQ-017's stated scope per
`requirements.yaml`), so the reply names the future command rather than rendering
anything list-shaped.

**(b) The published-event branch's rendering — explicitly deferred, real work still
done.** `?start=e_<published-id>` resolves per §6.3 step 6: the state check (is it
published?) and the `pending_source` write (AC5) are REQ-016's real, testable work.
What the reply *shows* for a published event is a **minimal placeholder** — one catalog
string with the event's title and start time only (`event.deepLinkPublishedPlaceholder`,
composed from two fields the handler already has in hand from `getEventById`, not a
formatted `EventCard`-shaped rendering with venue/seats/badges/etc.) — not the full card
REQ-017 will build. This is a deliberate, named choice: REQ-016's handler's real job for
this branch is the state check + `pending_source` write; the reply text is a thin,
honest placeholder so the deep link is never a dead end (per STORY-DETAILS A2's own
wording, "never a silent dead end") while explicitly not building REQ-017's card twice.

**(c) The "underlying query/data model doesn't expose draft events to a hypothetical
list query" half of AC4 — documented as a note for REQ-17, not built.** The correct
"upcoming events for members" query, for whenever REQ-017 builds `/events`, is:

```
SELECT * FROM events
WHERE events.chapter_id = $chapterId
  AND events.status = 'published'
  AND events.ends_at > $evaluationTime   -- "unfinished": ends_at, not starts_at, is the
                                           -- correct not-yet-over bound (an event that
                                           -- has started but not yet ended is still
                                           -- "upcoming"/ongoing, not past)
ORDER BY events.starts_at ASC
```

This design does not implement this query, does not create the `/events` command, and
does not create any list-rendering component. It states the filter (`status =
'published' AND not past`) as the correctness property REQ-017's own design must
preserve, satisfying AC4's "ensuring the underlying query/data model doesn't expose
draft events" half without building the query's caller. Nothing about `events`'s current
schema (status column, starts_at/ends_at columns) needs to change to make this query
possible — it is a read against columns REQ-011 already created.

## 7. Agenda validation (AC6, AC7)

### 7.1 Where it runs

Whenever `agenda[]` is written — both from `/event_edit`'s `agenda` field (if BACKEND-DEV
wires a structured agenda syntax into the same multi-line parser) and from a dedicated
`/event_agenda <event-id>` sub-flow (§2.1's note) if that turns out to be the more usable
shape — **the validation function itself is a single, reusable predicate**, called
regardless of which command path assembles the candidate array, so there is exactly one
place this rule can be gotten wrong, not two parallel implementations:

```
// domain/event.ts
interface AgendaItem { kind: string; at: string /* ISO timestamp */; label: string; }

type AgendaValidation =
  | { ok: true }
  | { ok: false; reason: "doors-after-start"; item: AgendaItem }
  | { ok: false; reason: "item-after-end"; item: AgendaItem }
  | { ok: false; reason: "multiple-doors" };

// Pure predicate over the full candidate replacement array — no I/O,
// unit-testable without a DB.
function validateAgenda(
  candidateAgenda: AgendaItem[],
  startsAt: Date,
  endsAt: Date,
): AgendaValidation;
```

`validateAgenda` logic, stated exactly so it cannot be reinterpreted:

1. Count the items in `candidateAgenda` whose `kind === "doors"`. If there is more than
   one, refuse with `{ ok: false, reason: "multiple-doors" }` — this check runs first,
   independently of every item's timing, so a second doors item is refused even if its
   own time would otherwise be valid.
2. Otherwise, walk `candidateAgenda` in order and, for each item:
   - If `item.kind === "doors"` and `item.at` is later than `startsAt`, refuse with
     `{ ok: false, reason: "doors-after-start", item }` and stop.
   - If `item.at` is later than `endsAt` (checked for **every** item, doors included),
     refuse with `{ ok: false, reason: "item-after-end", item }` and stop.
3. If no item triggers either refusal, return `{ ok: true }`.

**Exact bounds, read carefully from AC6's own wording, no invented lower bound:**
- A `doors` item's `at` must be `<= starts_at` — "later than starts_at is refused" means
  the boundary case `at === starts_at` is **allowed** (only strictly-later is refused).
- **Every** agenda item's `at` (doors included — the `ends_at` check runs for every item,
  not only non-doors ones, since AC6 says "any agenda item later than ends_at is
  refused" without excluding doors) must be `<= ends_at`.
- **No lower bound whatsoever** — an item timestamped hours or days before `starts_at` is
  not refused by this function. AC6's own text states this explicitly ("NO lower bound...
  an all-day workshop may legitimately have an early setup item") — this design does not
  add one.
- At most one `kind: "doors"` item total (AC7) — checked independently of the time
  bounds, so a second doors item is refused even if its own time would otherwise be
  valid.

Both refusal reasons carry the **offending item** so the handler's reply can name it
(AC6: "a message naming the offending item" — e.g. its `label` and/or its position in
the array) — `validateAgenda` returns the item, the catalog-string composition (which
field of the item to echo) is the handler's/CONTENT-BA's copy decision, not this
function's concern.

### 7.2 Atomicity — the whole array is validated and replaced together

Consistent with REQ-016-schema.md §6's already-established reading (REQ-011's own
decision, restated as still correct): `agenda` is a single JSONB column, replaced as a
whole on every write. `validateAgenda` receives the **full proposed replacement array**
(not a diff against the stored one), so "at most one doors item" and both time bounds
are checked against the array as it would exist **after** the edit, not merely against
the item(s) being newly added — appending a second doors item to an agenda that already
has one is refused by the same check that would refuse creating two at once, because
both cases produce the same final candidate array shape.

On `ok: false`, no write to `events.agenda` occurs, and the event is left unchanged
(AC6/AC7's own verification instruction: "confirming the event is left unchanged").

## 11. Open questions (not silently resolved)

1. **Duplicated authorization predicate vs. a shared module (§0).** This design adds a
   parallel `domain/eventAuthorization.ts` with logic identical to REQ-015's
   `domain/venueAuthorization.ts`, rather than extracting a shared
   `domain/chapterAuthorization.ts`. Reasoned as acceptable at two occurrences; flagged
   for whoever adds a third chapter-scoped-authorization entity to actually do the
   extraction then, rather than adding a third copy.

2. **`starts_at`'s "individually absent" sub-case may be untestable as literally worded
   (§3.1a).** `starts_at` is `NOT NULL` at the schema level with no non-null "invalid"
   sentinel value analogous to blank-string `title` or non-positive `capacity` — there
   may be no way to construct a stored row with a genuinely "missing" `starts_at` without
   a schema change. TEST-DESIGNER/TEST-DESIGN-VALIDATOR must resolve whether this
   sub-case is covered by the general mechanism being demonstrably correct in code (unit
   test on `findMissingPublishFields` with a raw object literal, not a real DB row) or
   whether AC1 itself needs a wording correction — not silently skipped either way.

3. **Whether an `online`/venue-less event format is ever wanted (§3.3).** This design
   finds no such distinction in the current schema and treats every event as
   venue-requiring. If a future requirement wants a genuinely venue-less online format,
   that requires new requirement text plus a DATA-DESIGNER-owned enum/flag change and a
   follow-up to `PUBLISH_REQUIRED_FIELDS`.

4. **Auditing `event.update` beyond what AC8 explicitly asks (§4).** This design audits
   every successful update, reasoning by analogy to REQ-015's already-merged
   `venue.update` precedent, even though REQ-016's AC8 only names draft-create/publish/
   cancel. Flagged so REVIEWER/SECURITY-REVIEWER can confirm this generalization is
   wanted, not merely assumed twice now.

5. **`/event_edit` vs. a dedicated `/event_agenda` sub-flow for agenda edits (§7.1).**
   This design states the validation function once, reusable from either call site, but
   leaves the actual command-surface shape (agenda as one more `label: value`-style
   field with some serialized-array syntax, vs. a separate command/sub-flow with its own
   line-per-item syntax) to BACKEND-DEV, since PRD/AC text does not specify the input
   syntax for a JSON array inside a plain-text Telegram message and this is a UX/parsing
   decision with no behavior-correctness stake either way, as long as `validateAgenda` is
   the single function both paths call before any write.

6. **Refusal audit rows for authorization/state-machine refusals.** Same open question
   already carried forward from REQ-015 §9.1, restated here rather than re-litigated: no
   audit row is written on an authorization refusal or a status-machine guard refusal
   (e.g. publishing an already-published event) — only on an actual field/floor/agenda
   validation refusal would a row also not be written, consistently. Flag for
   SECURITY-REVIEWER per the same precedent.

7. **Exact copy for every new catalog string (§9).** Placeholder/functional text only;
   CONTENT-BA owns final wording per decisions/0002, unchanged precedent from REQ-013/
   014/015.
