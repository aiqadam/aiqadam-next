# REQ-022 — Withdraw from a registration and free the seat

**Requirement:** USER-STORIES B5 ("Change my mind"), PRD 8 (destructive-action
confirmation). `depends_on: REQ-021`. Sequenced before REQ-023 (auto-promotion) because
auto-promotion has no trigger until a withdrawal exists.

**Surface:** `apps/bot/**` (bot requirement). No design tokens apply — Telegram text/
button copy only, same as every other bot design in this pipeline (REQ-018/020/021).

**No schema change.** `apps/bot/src/db/schema.ts`'s `registrations` table already has
every column this design needs: `admission` (the `admission` pgEnum already includes
`'withdrawn'`, REQ-011), `checked_in_at` (nullable timestamp, confirmed present at line
256, with the existing CHECK `chk_registrations_checked_in_only_if_admitted` already
enforcing "checked-in only while admitted" at the DB level — belt-and-suspenders for this
requirement's own refusal rule), `created_at`/`updated_at`, and the
`uq_registrations_event_user` unique index this design's row-reuse mechanism (§3) relies
on. No `ALTER TABLE`, no new column, no new enum value, no new index. **`DATA-DESIGNER` is
not dispatched for this run** — same precedent as REQ-017/REQ-020/REQ-021.

---

## 0. Resolving the `/my`-doesn't-exist-yet scoping issue (stated explicitly)

The requirement text says withdrawal happens "from `/my`" — but `/my` is REQ-024, two
requirements after this one, and does not exist in this codebase yet.

**Decision: build a standalone `/withdraw <event_id>` command now** that implements the
full withdraw domain logic (§2) and the full two-step confirmation UX (§4), with an
explicit note that REQ-024's `/my` will later become the primary (likely only)
user-facing entry point, and this standalone command may be superseded or kept as a
secondary path once `/my` exists.

Reasoning:

1. **This is the exact shape of gap REQ-018 and REQ-021 already hit and resolved the same
   way.** REQ-018 built `/checkin <event_id>` before any registration list existed to link
   from; REQ-021's own design (§0) named the identical "the referencing feature doesn't
   exist yet" problem for a different requirement and chose to build the real mechanism
   now rather than invent a stub. Building the full domain logic behind a minimal,
   ID-parameterized command is this project's established move, not a new one.
2. **The domain logic (§2) and the confirmation UX (§4) are the actual deliverable of this
   requirement** — the acceptance criteria test admission-state transitions, refusal
   rules, row-reuse, and audit rows, not the discoverability of the entry point. A
   `/withdraw <event_id>` command exercises every one of them exactly as a "Withdraw"
   button inside `/my`'s future registration list would, differing only in how the
   `event_id`/`registration_id` reaches the handler (a typed command argument today, a
   callback_data payload attached to a list row once `/my` exists).
3. **Command-with-id-argument is this codebase's own precedent for "the referencing
   surface doesn't exist yet,"** not an invented pattern: `/checkin <event_id>`
   (`handlers/checkin.ts`) is exactly this shape — a raw id typed by the caller, parsed via
   `ctx.match`, with a "no id given" usage message. §4.1 follows it directly.
4. **When `/my` (REQ-024) ships**, its own design should point its list row's "Withdraw"
   button at the same `withdraw:confirm:<registrationId>`/`withdraw:cancel:<registrationId>`
   callback pair this design defines (§4.2) — the confirmation step and the domain call are
   reused unchanged; only the *first* message (today `/withdraw`'s reply, later a list row)
   changes. That is a design decision for REQ-024 to state explicitly when it is designed,
   not something this document can bind in advance — flagged here as a forward note, not
   asserted as already decided.

## 1. What already exists vs. what this design adds

Reused completely unchanged:
- `registrations` schema (REQ-011), including the `admission` enum's existing
  `'withdrawn'` member and the `checked_in_at` column/CHECK.
- `resolveActingUser` (`domain/eventAuthorization.ts`, REQ-016) — resolves `ctx.from.id`
  to the acting `users.id`. Withdrawal needs no organizer/staff check (any member may
  withdraw their own registration), so only `resolveActingUser` is reused, never
  `checkOrganizerForChapter`/`requireOrganizerForChapter`.
- `writeAuditLog` (`domain/auditLog.ts`, REQ-015).
- `computeSeatsLeft` (`domain/event.ts`, REQ-017) — confirmed already correct for this
  requirement with **no change**: it counts only rows where `admission = 'admitted'`
  (§7 of REQ-017's own design), so the moment a row's `admission` flips away from
  `'admitted'` to `'withdrawn'`, that row stops being counted on the very next call — the
  same "recomputed fresh, nothing cached" property REQ-021 §2.4 already established for
  waitlist position. This is a proof of absence, not a new design element: no interface
  gains a `seatsLeft` field, no value is stored, `computeSeatsLeft`'s two-integer
  subtraction signature is untouched.

New in this design:
- `domain/registration.ts` gains `decideWithdrawOutcome` (pure decision, §2.1) and
  `withdrawRegistration` (the transactional write, §2.2).
- `domain/registration.ts`'s existing `registerForEvent` needs one targeted change to
  support row-reuse on re-registration (§3) — **not** a rewrite; `decideRegistrationOutcome`
  itself stays completely unchanged (§3.3).
- `handlers/registration.ts` (or a new `handlers/withdraw.ts` — open question, §6.1) gains
  the `/withdraw` command handler and the two confirm/cancel callback handlers (§4).
- `i18n/types.ts`/`ru.ts`/`en.ts` gain a new `withdraw` catalog section (§5).

## 2. The withdraw domain logic

### 2.1 `decideWithdrawOutcome` — pure decision, no I/O

```
export interface WithdrawDecisionInput {
  registrationExists: boolean;
  ownerUserId: string | null;      // the registration row's own user_id; null if registrationExists is false
  actingUserId: string;
  admission: AdmissionState | null; // null if registrationExists is false
  checkedInAt: Date | null;
}

export type WithdrawOutcome =
  | { kind: "not-found" }
  | { kind: "not-owner" }
  | { kind: "checked-in" }
  | { kind: "not-eligible"; admission: AdmissionState }
  | { kind: "withdrawn" };

export function decideWithdrawOutcome(input: WithdrawDecisionInput): WithdrawOutcome;
```

The rule, stated as an ordered table (first match wins — same convention
`decideRegistrationOutcome`, REQ-020 §2.2, already established; described here in prose,
never as executable branching, per this role's zero-implementation-code rule):

| # | Condition | Result |
|---|---|---|
| 1 | `registrationExists` is `false` | `{ kind: "not-found" }` |
| 2 | `ownerUserId !== actingUserId` | `{ kind: "not-owner" }` — S2-shaped authorization: a person may withdraw only their own registration, never one looked up by someone else's supplied id |
| 3 | `checkedInAt` is non-null | `{ kind: "checked-in" }` — the requirement's own refusal rule, stated verbatim: "they were there; history is not editable." Checked **before** the admission-eligibility row below, since a checked-in row is always `admission = 'admitted'` (the schema's own CHECK enforces this), so this ordering never masks a distinct case |
| 4 | `admission` is not one of `'requested'`, `'waitlisted'`, `'admitted'` (i.e. it is already `'rejected'` or `'withdrawn'`) | `{ kind: "not-eligible", admission }` — re-withdrawing an already-withdrawn row, or withdrawing a rejected one, is refused as a no-op rather than silently accepted or erroring |
| 5 | Otherwise (`admission` is `'requested'`, `'waitlisted'`, or `'admitted'`, not checked in, owned by the acting user) | `{ kind: "withdrawn" }` |

Row 5 is the only outcome the caller (`withdrawRegistration`, §2.2) treats as
write-worthy; rows 1–4 are refusals the caller returns unchanged, with **zero** write and
**zero** audit-log call — mirroring `registerForEvent`'s own "every non-writing outcome
returns unchanged" discipline (REQ-020 §3.2 step 7).

### 2.2 `withdrawRegistration` — the transactional write (AC2, AC3, AC5)

```
export async function withdrawRegistration(
  db: DbClient["db"],
  registrationId: string,
  actingUserId: string,
  at: Date,
): Promise<WithdrawOutcome>;
```

Steps, in one `db.transaction`:

1. `SELECT id, user_id, admission, checked_in_at FROM registrations WHERE id =
   registrationId FOR UPDATE` (row lock, same discipline `registerForEvent` §3.2 step 2
   already uses on `events` — here it is the `registrations` row itself that must not be
   concurrently mutated between the read and the write, e.g. by a simultaneous check-in).
2. Build the `WithdrawDecisionInput` from the row found (or `registrationExists: false`
   if no row matched) and call `decideWithdrawOutcome` (§2.1, pure — no I/O inside it).
3. If the outcome's `kind` is anything other than `"withdrawn"`: return it unchanged. No
   write, no audit row (AC1's dismiss-path and AC3's refusal-path both land here — AC3
   specifically hits row 3 above).
4. Otherwise: `UPDATE registrations SET admission = 'withdrawn' WHERE id = registrationId`
   — **only the `admission` column changes**. `checked_in_at`/`checked_in_by`/
   `check_in_method`/`created_at` are left untouched (row 3 of §2.1 already guarantees
   `checked_in_at` was null before this point, so there is nothing to clear).
5. `writeAuditLog(tx, { actorUserId: actingUserId, action: "registration.withdraw",
   entity: "registration", entityId: registrationId, payload: { eventId: <the row's
   event_id, read in step 1> }, at })` — exactly one row, inside the same transaction as
   step 4, same "exactly-once, same transaction, atomic" discipline `writeAuditLog`'s own
   header comment requires and every existing mutation function in this codebase already
   follows (S8).
6. Return `{ kind: "withdrawn" }`.

This satisfies **AC5** (exactly one audit_log row per withdrawal) by construction: there
is exactly one `writeAuditLog` call in this function, reached only once, only on the one
writing branch, inside the same transaction as the one `UPDATE`.

This satisfies **AC2** (seats-left increases by exactly one at next read) without this
function doing anything about seats itself: the moment step 4's `UPDATE` commits, the row
is no longer counted by `countAdmittedRegistrations`/`computeSeatsLeft` on the very next
call — the seat-freeing is REQ-023's later consumption point, and this requirement's job
(per its own scope note) is only to make that state transition happen, immediately and
durably. No new "seats freed" event, flag, or table is introduced — the `admission` column
transition **is** the signal REQ-023 will read (a proof-of-absence, restated from §1's
`computeSeatsLeft` note, not a new mechanism).

### 2.3 Why `checked_in_at` is read from the row, not trusted from an earlier read

Step 1's `FOR UPDATE` read happens fresh inside the withdraw transaction, not reused from
whatever data populated the confirmation prompt (§4.2) — closing the race where a person
gets checked in during the window between seeing the confirmation prompt and tapping
"Yes." This mirrors `registerForEvent`'s own `FOR UPDATE` discipline (REQ-020 §3.2 step
2) applied to the row this requirement mutates instead of the row that one does.

## 3. Re-registration reuses the existing row (AC4) — and the change `registerForEvent` needs

**Checked `registerForEvent`'s current insert logic (`domain/registration.ts` lines
109–216) directly, per this task's instruction. It does NOT already handle row-reuse and
DOES need a targeted modification** — stated explicitly, not left to BACKEND-DEV to
discover:

**Today:** step 3 of `registerForEvent`'s transaction reads only `admission` from any
existing `(event_id, user_id)` row and passes it straight into
`decideRegistrationOutcome` as `existingAdmission`. That function's row 1 (REQ-020 §2.2)
returns `{ kind: "already-registered", admission }` whenever `existingAdmission !== null`
— and a `'withdrawn'` row's `admission` **is** non-null, so today a withdrawn person who
tries to register again gets told they are "already registered (withdrawn)" and nothing
is written. Then, separately, even if that branch were bypassed, step 8's write path
calls `.insert(registrations).values(...)` unconditionally — which would violate
`uq_registrations_event_user` for a second row with the same `(event_id, user_id)` pair
even if it somehow ran. Both of these are the concrete reasons a change is required, not
assumed.

**The two changes, precisely scoped:**

1. **Step 3's read** (today: `SELECT admission FROM registrations WHERE event_id = ... AND
   user_id = ... LIMIT 1`) additionally selects `id`. Call the result
   `existingRegistrationId` (`string | null`) and `existingAdmission` (`AdmissionState |
   null`), same as today.

2. **The value passed to `decideRegistrationOutcome` changes, the function itself does
   not.** `decideRegistrationOutcome` (REQ-020 §2.2) stays byte-for-byte unchanged — its
   row 1 continues to mean exactly "a non-null existing admission blocks re-registration."
   What changes is what `registerForEvent` computes as the `existingAdmission` value it
   passes in: when the found row's actual `admission` is `'withdrawn'`, `registerForEvent`
   passes `null` instead (i.e., a withdrawn row is treated, for the purposes of *deciding*
   the new outcome, as if no registration exists yet — which is exactly the product
   intent: withdrawal must let the person register again from scratch). Every other
   existing admission value (`'requested'`, `'waitlisted'`, `'admitted'`, `'rejected'`) is
   passed through unchanged, preserving `decideRegistrationOutcome`'s existing
   "already-registered" behavior for all four of those exactly as today.

3. **Step 8's write** (today: unconditional `INSERT`) branches on whether
   `existingRegistrationId` is non-null (which, given change 2, can only be true when the
   pre-existing row's admission was `'withdrawn'` — every other non-null case already
   returned `"already-registered"` before step 8 is ever reached, so this is the only case
   step 8 will ever see a non-null `existingRegistrationId`):
   - If `existingRegistrationId` is non-null: `UPDATE registrations SET admission =
     outcome.kind, source = source, qr_token = qrToken WHERE id = existingRegistrationId`
     — the **same row**, same `id`, same `created_at`. `RETURNING id` still yields
     `existingRegistrationId` itself.
   - Otherwise (no prior row at all): `INSERT` exactly as today.

   Every other step (pending-source clearing, the `writeAuditLog` call, the returned
   `RegisterForEventResult` shape) is unchanged — `registration.admit`/
   `registration.waitlist` are written exactly as they are today, satisfying S8 for the
   re-registration path too (one audit row, same transaction as the write).

### 3.1 Why `created_at` is provably preserved

`created_at` is a column this `UPDATE` statement never names in its `SET` clause (change
3 above lists exactly three columns: `admission`, `source`, `qr_token`) — Postgres leaves
every unnamed column untouched by an `UPDATE`. There is no read-modify-write of
`created_at` anywhere in this design that could accidentally reset it, and no `ON
CONFLICT ... DO UPDATE` upsert pattern is introduced (which would risk a
default-re-evaluation footgun) — the row-reuse path is a plain, explicit `UPDATE` against
an `id` already known from step 1's read, never an insert-shaped statement of any kind.
This directly satisfies **AC4**: same primary key (`id` unchanged, confirmed above),
same `created_at` (never in the `SET` clause), and never a second `INSERT` (the branch
that would `INSERT` is only reached when `existingRegistrationId` is null).

### 3.2 Interaction with the waitlist ordering this preserves

Because `created_at` is preserved, a person who withdraws from the waitlist and later
re-registers while the event is still full does **not** get a fresh, later `created_at` —
they re-enter at their **original** waitlist position ordering (`getWaitlistPosition`,
REQ-021, ranks purely by `created_at`/`id`, both unchanged by this design). This is a
consequence of the row-reuse mechanism, not a new decision this design is making — flagged
here because it is a real, observable behavior difference from "delete and re-insert"
(which would have given a person who withdraws-then-rejoins a fresh, later place in line)
worth stating explicitly rather than leaving implicit.

### 3.3 Reuse decisions, restated for `CODE-DESIGN-VALIDATOR`

- `decideRegistrationOutcome` (`domain/registration.ts`, REQ-020) — **signature and body
  completely unchanged**. Only its caller's computed input changes (§3 point 2).
- `RegistrationOutcome`, `RegisterForEventResult`, `AdmissionState` — unchanged.
- `generateQrToken`, `resolveRegistrationSource`, `clearPendingSource`,
  `getPendingSource` — unchanged, called exactly as today from `registerForEvent`.
- `getWaitlistPosition` (REQ-021) — unchanged; §3.2 above is a consequence of its
  existing, unmodified ranking rule, not a change to it.

## 4. The confirmation UX (AC1)

No existing "confirm/cancel before a destructive action" pattern exists anywhere in
`apps/bot/src/handlers/*.ts` (checked directly, per this task's instruction — every
existing command either acts immediately on valid input or refuses immediately on
invalid/unauthorized input; nothing in this codebase today shows a prompt and waits for a
second, distinct tap before writing). This design introduces the pattern fresh, following
this codebase's own established building blocks (`InlineKeyboard`, a
`<domain>:<action>:<param>` callback_data convention already used by `chapter:<id>`,
`consent:agree(:<payload>)`, `profile:student:(yes|no)`, `register:<eventId>`) rather than
inventing new mechanics.

### 4.1 Entry point — `/withdraw <event_id>` command

Same argument-parsing shape as `/checkin <event_id>` (`handlers/checkin.ts`, REQ-018):
`ctx.match` trimmed to a string.

1. `tgId` missing → return (defensive, unreachable via Telegram).
2. Argument blank → reply `catalog.withdraw.usageNoId`, return.
3. Resolve acting user via `resolveActingUser` (`domain/eventAuthorization.ts`). `null` →
   reply `catalog.profile.startFirst` (same phrasing `registration.ts`'s handler already
   uses for the equivalent case), return.
4. Look up the registration for `(event_id, actingUser.id)` — a new read function,
   `getRegistrationForEventAndUser(db, eventId, userId): Promise<{ id, admission,
   checkedInAt } | null>`, a plain `SELECT ... WHERE event_id = ... AND user_id = ...
   LIMIT 1`, no lock (this is the display-only read; the authoritative, lock-taking read
   happens later, inside `withdrawRegistration` itself at confirm time, per §2.3).
5. Call `decideWithdrawOutcome` (§2.1) against that read (with `registrationExists`/
   `ownerUserId` set accordingly — `ownerUserId` here is always `actingUser.id` by
   construction of the query, so row 2 ("not-owner") can never fire from this entry point;
   it exists in `decideWithdrawOutcome` for the callback path, §4.2, where the id is
   attacker-suppliable).
6. If the outcome is `"not-found"`/`"not-eligible"`/`"checked-in"`: reply the matching
   catalog string (§5) immediately — **no confirmation shown for a refusal that is already
   certain**, since presenting "are you sure?" for an action that will be refused anyway
   would be a confusing UX, not a security concern (the authoritative check still runs
   again at confirm time regardless, §2.3).
7. If the outcome is `"withdrawn"` (i.e., eligible): reply with the confirmation prompt —
   `catalog.withdraw.confirmPrompt` plus the event's title (fetched via the existing
   `getEventById`) — and an `InlineKeyboard` with two buttons:
   `catalog.withdraw.confirmButton` → `withdraw:confirm:<registrationId>`,
   `catalog.withdraw.cancelButton` → `withdraw:cancel:<registrationId>`.

### 4.2 `withdraw:confirm:<registrationId>` callback (AC1's confirm path, AC2, AC3, AC5)

Pattern: `/^withdraw:confirm:(.+)$/`, registered in `index.ts` alongside the other
`bot.callbackQuery(...)` lines.

1. Resolve `tgId` → `actingUser` via `resolveActingUser` exactly as §4.1 step 3. `null` →
   `ctx.answerCallbackQuery()`, reply `profile.startFirst`, return.
2. Call `withdrawRegistration(db, registrationId, actingUser.id, new Date())` (§2.2) —
   this is the single authoritative check-and-write; it re-derives ownership,
   check-in-status, and eligibility fresh (§2.3), independent of whatever §4.1 displayed.
3. `ctx.answerCallbackQuery()`.
4. Reply per outcome: `"withdrawn"` → `catalog.withdraw.confirmedReply`; `"not-owner"` →
   a generic refusal (never disclosing whose registration it actually was — same
   non-disclosure discipline `resolveActingUser`'s callers already follow elsewhere in
   this codebase, e.g. `checkin.ts`'s "one generic string" comment); `"checked-in"` →
   `catalog.withdraw.refusedCheckedIn`; `"not-eligible"` → `catalog.withdraw.refusedNotEligible`;
   `"not-found"` → `catalog.withdraw.refusedNotFound`.

### 4.3 `withdraw:cancel:<registrationId>` callback (AC1's dismiss path)

Pattern: `/^withdraw:cancel:(.+)$/`.

1. `ctx.answerCallbackQuery()`.
2. Reply `catalog.withdraw.cancelledReply`.
3. **No domain call of any kind** — this handler never touches `registrations`,
   `withdrawRegistration`, or `writeAuditLog`. This is what makes **AC1**'s dismissal path
   ("dismissing leaves admission unchanged") true by construction: there is no code path
   from this callback to any write.

### 4.4 Why `registrationId`, not `eventId`, is the callback payload

`/withdraw <event_id>`'s own lookup (§4.1 step 4) already resolves a `registrationId`
before ever showing the prompt, so carrying it forward avoids a second, redundant
`(event_id, user_id)` lookup inside the callback and keeps the callback_data payload a
single opaque id (well under Telegram's 64-byte `callback_data` limit, same concern
`start.ts`'s own header comments already flag for its event-id-bearing callbacks).

## 5. i18n catalog additions

New `Catalog.withdraw` section (`i18n/types.ts`, mirrored placeholder copy in `ru.ts`/
`en.ts`, decisions/0002 — final wording owned by `CONTENT-BA`):

```
withdraw: {
  usageNoId: string;        // "/withdraw <event_id>" reminder when no argument given
  confirmPrompt: string;    // prefix shown before the event title, e.g. "Withdraw from this event?"
  confirmButton: string;    // e.g. "Yes, withdraw"
  cancelButton: string;     // e.g. "No, keep my spot"

  cancelledReply: string;   // shown after dismissing the prompt
  refusedCheckedIn: string; // "they were there; history is not editable" (S8/AC3's copy)
  refusedNotEligible: string; // already withdrawn or was rejected
  refusedNotFound: string;  // no such registration
}
```

No key needs Markdown/HTML formatting beyond this catalog's existing plain-string
convention (every other bot catalog section is a flat string map — `registration`,
`checkin`, `profile` all follow the same shape, confirmed by reading `i18n/types.ts`
directly).

## 6. Open questions (not silently resolved)

1. **New file vs. extending `handlers/registration.ts`.** This design doesn't mandate
   `handlers/withdraw.ts` vs. adding the three new handlers to the existing
   `handlers/registration.ts` — both are consistent with this codebase's existing
   granularity (`handlers/checkin.ts` is its own file for one command;
   `handlers/registration.ts` already holds one command's-worth of logic plus its
   callback). Left to `BACKEND-DEV`'s judgment; either satisfies every acceptance
   criterion identically. Whichever is chosen, `getRegistrationForEventAndUser` (§4.1
   step 4) belongs in `domain/registration.ts` regardless, next to `withdrawRegistration`.
2. **`/my` (REQ-024) is not designed yet**, so §0 point 4's forward note (REQ-024 pointing
   its list row's button at this design's `withdraw:confirm`/`withdraw:cancel` callbacks)
   is a recommendation for that future design to consider, not a binding decision this
   document can make on REQ-024's behalf.
3. **Exact refusal copy for `refusedCheckedIn`** should echo the requirement's own stated
   reasoning ("they were there; history is not editable") closely enough that a person
   understands *why*, without this design drafting the final wording itself (CONTENT-BA's
   call, decisions/0002).
4. **Whether the `/withdraw` command should validate that `event_id` is even a
   syntactically plausible UUID before querying** — this design leaves that to whatever
   convention `BACKEND-DEV` already applies elsewhere for id-shaped command arguments
   (`checkin.ts` performs no such pre-validation, relying on the DB lookup's `null` result
   instead); no acceptance criterion here depends on the distinction between "malformed id"
   and "well-formed but nonexistent id," both already collapse to `decideWithdrawOutcome`'s
   `"not-found"` row.

## 7. Acceptance criteria → design element map

| AC | Design element |
|---|---|
| AC1 — confirmation required; dismissing leaves admission unchanged | §4: `/withdraw` shows the prompt (§4.1 step 7) only for an eligible registration; `withdraw:confirm` (§4.2) performs the write, `withdraw:cancel` (§4.3) performs **no** domain call at all — dismissal is a no-write path by construction |
| AC2 — withdrawing from admitted → `admission='withdrawn'`, seats-left +1 at next read | §2.2 step 4 (the one-column `UPDATE`) for the state change; §1's restated `computeSeatsLeft` proof-of-absence (unchanged, counts only `'admitted'` rows, so the freed seat is visible on the very next call with no code change) |
| AC3 — a registration with non-null `checked_in_at` is refused, row unchanged | §2.1 row 3 (`decideWithdrawOutcome`'s `"checked-in"` outcome, checked before eligibility) + §2.2 step 3 (every non-`"withdrawn"` outcome returns with zero write) |
| AC4 — re-registering after withdrawal UPDATEs the existing row, same PK, same `created_at`, never a new INSERT | §3's two changes to `registerForEvent` (existingAdmission normalization + the UPDATE-vs-INSERT branch) and §3.1's proof that `created_at` is never in the `UPDATE`'s `SET` clause |
| AC5 — each withdrawal writes exactly one `audit_log` row | §2.2 step 5 — exactly one `writeAuditLog` call, reached only on the one writing branch, same transaction as the `UPDATE` (S8) |
