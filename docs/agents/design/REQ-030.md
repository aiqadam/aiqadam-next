## 1. The interaction pattern, decided explicitly

### 1.1 Why a genuinely new interaction shape is needed here, and why it is still stateless

REQ-019 §0.1 and REQ-028 §1.2 both rejected multi-message conversational state for a
structural reason specific to this codebase: no session/conversation mechanism exists
anywhere in `apps/bot/src` (confirmed again by the same `git grep -n
"session\|conversation" apps/bot/src` REQ-028 §1.2 already ran), and both an in-memory
`Map` (S9's own forbidden "idempotency enforced by an in-memory set a restart clears"
pattern, generalized) and a new DB column for transient UI state were rejected as
disproportionate or unsafe.

This requirement cannot reuse either precedent's own resolution, though:
- REQ-019's resumability trick (derive "what's next" from **already-persisted** partial
  rows) is unavailable **by construction**: S1 forbids writing anything — including a
  first partial row — before consent is confirmed, so there is nothing in the database
  yet to derive resumability from during the one part of this flow (data entry →
  consent) that most needs it.
- REQ-028's "stateless command with a free-text remainder" resolves a single round trip
  (one command, one reply) with no confirm/cancel step. This flow needs a **second**
  round trip — a deliberate confirm tap — precisely because AC1 requires an abandon-able
  point *between* data entry and storage, which a single-shot command has no room for.

**Decision: the single command captures all three fields in one message (per the task's
own suggested shape), and the confirm/cancel/override steps that follow carry their state
in the CONTENT OF THE BOT'S OWN MESSAGE, not in `callback_data`, not in memory, and not in
a new DB column.** Concretely:

```
/walkin <event_id> <name>|<company>|<phone>
```

The bot's reply to this command is a **canonically formatted** confirmation message (§7)
containing the collected `name`/`company`/`phone` as fixed, machine-parseable labeled
lines plus the consent statement, with Confirm/Cancel inline buttons. `callback_data`
carries only `eventId` (well inside the Bot API's 64-byte cap, unlike carrying all three
free-text fields would be — see §1.2). Tapping Confirm re-parses the **same message's own
text** (`ctx.callbackQuery.message.text`) back into `name`/`company`/`phone` using the
identical label format the reply was rendered in, then performs the write.

This is stateless in the same sense REQ-028's pattern is: the "state" being read back is
not held anywhere the bot's own process or database owns — it is the literal content of a
Telegram message that Telegram's own infrastructure hands back verbatim as part of every
`callback_query` update, indefinitely, independent of bot process restarts. There is
nothing to lose on a restart because there is nothing the bot itself is holding — the
carrier is the message Telegram already delivered and is still displaying to the
organizer, which is also, not incidentally, the exact same content the organizer already
visually confirmed matches what they typed. **Abandoning the flow (AC1) is simply never
tapping Confirm** — no timeout, no cleanup job, no stored draft to expire, because no
draft was ever stored anywhere.

### 1.2 Rejected alternative: encode the fields directly in `callback_data`

Considered and rejected on a hard technical constraint, not preference: `callback_data`
is capped at 64 bytes (Telegram Bot API, already load-bearing for REQ-028 §1.4/REQ-029
§6.2's own designs). `"walkin:confirm:".length` (15) plus a UUID `eventId` (36) already
consumes 51 of the 64 bytes available, leaving no room for a name, company, and phone
number encoded alongside it. Re-parsing the message's own text (§1.1) sidesteps this
limit entirely, since message *text* has no such cap.

### 1.3 The override step reuses the identical mechanism — no `callback_data`-carried id

When capacity is full, the confirm tap does not write a placeholder registration row just
to have something to hand an id to a second callback (which would need its own
dismiss-deletes-the-row bookkeeping to keep AC3's "dismissing creates no registration"
true). Instead the override-offer message (§7.2) is rendered with the **same** canonical
`name`/`company`/`phone` lines, and the override tap re-runs the **same** write function
(§6) a second time with one flag flipped (`overrideConfirmed: true`). Because the
person-matching rule (§3) makes "resolve or create the `User`/`Profile` row" idempotent
(a second call finds the just-created row by phone and reuses it, §6.2), re-running the
same resolve step at the override tap is safe and does not create a second `User`/
`Profile`. See §6.1 for why this also means capacity is always re-evaluated fresh at
write time, never trusted from the first tap.

```
export interface ParsedWalkinArgs {

  name: string;
  company: string; // "" when the door didn't collect one — see Open Question 1

  | { ok: false; reason: "usage" };
```

Rule, stated exactly (no comparison written as executable code):

| Step | Check | Result |
|---|---|---|
| 1 | `text`, trimmed, is empty, or contains no whitespace after the first token | `{ ok: false, reason: "usage" }` |
| 2 | Split on the first run of whitespace into `eventId` (first token) and `remainder` (everything after, trimmed) | — |
| 3 | `remainder` split on `"\|"` does not yield **exactly** 3 segments | `{ ok: false, reason: "usage" }` |
| 4 | Exactly 3 segments | `{ ok: true, args: { eventId, name: segment1.trim(), company: segment2.trim(), phone: segment3.trim() } }` |

```
export type WalkinFieldValidation =
  | { ok: true }
  | { ok: false; reason: "missing-name" | "missing-phone" };

export function validateWalkinFields(args: ParsedWalkinArgs): WalkinFieldValidation;
```

Rule: `isNonBlank(args.name)` false → `{ ok: false, reason: "missing-name" }`;
`isNonBlank(args.phone)` false → `{ ok: false, reason: "missing-phone" }` (checked after

requirement — an empty string is a legitimate "no company given" value (§ Open Question

unchanged, never re-implemented here.

## 3. The person-matching rule — by phone, normalized to digits-only

### 3.1 Why phone, and why not `tg_id`

`tg_id` is `NULL` for anyone who has never opened the bot (PRD 5, `db/schema.ts`'s own
comment) — the exact case a door walk-in usually is. Phone is the only field the door
collects that a returning person's existing profile might already carry (name is
free-text and unindexed; company is not identifying). This design therefore matches
strictly on `profiles.phone`.

### 3.2 Normalization rule (stated as prose, not as executable logic)

```
export function normalizePhoneForMatching(phone: string): string;
```

**Rule:** the output is `phone` with every character that is not one of the ten digits
`0`–`9` removed, preserving the order of the remaining digits. Nothing else is
canonicalized — no country-code insertion, no leading-zero/leading-plus rewriting, no
length check.

**Why nothing cleverer:** AI Qadam's chapters span multiple countries (Uzbekistan,
Kazakhstan, Kyrgyzstan, Tajikistan — design-system readme's "Products represented"), each
with its own national dialing convention, and this codebase has no existing phone-parsing
library or convention to build on (`profiles.phone`'s own field rule, REQ-019 §2.3, is
"no format rule — any non-blank value is accepted as-is"). Inventing a country-aware
canonicalization scheme here would be new logic well beyond this requirement's scope, and
would fail silently for whichever country's convention it got wrong. A digit-strip is the
one normalization every representation of the same number literally shares, at the cost
of not resolving representations that omit or vary the country code.

### 3.3 Tradeoffs, stated explicitly (not silently assumed)

| | |
|---|---|
| **False negative** (same person, no match found) | Two representations of the same physical number that don't strip to the same digit string — most commonly, one has a country code and the other doesn't (`"87051234567"` vs. `"+77051234567"` vs. `"7051234567"`). This design does **not** attempt to resolve these — a mismatch here silently creates a second `User`/`Profile` pair for the same real person. Accepted as the cheaper failure mode: a duplicate profile is a nuisance an organizer can notice and merge manually later; it does not corrupt any acceptance criterion this requirement states. |
| **False positive** (different people, wrongly matched) | Two different people whose digit-stripped phone numbers are identical — requires literal phone number reuse (a recycled SIM, a shared landline reused by a new owner). Rare, and the digit-strip rule does not make this more likely than any other phone-based matching scheme would; not specific to this normalization choice. |
| **Match only succeeds against a profile row that already has a non-null `phone`** | A person who has a `Profile` but skipped the phone field (REQ-019's `phoneSkipped`) is **never** matched here, however identical their `name`/`company` might look — matching is phone-only, never name-based (name collisions across a community of hundreds are far likelier than phone collisions). |

### 3.4 The lookup

```
// domain/user.ts — addition
export async function getUserIdByPhone(
  db: DbClient["db"],
  normalizedPhone: string,
): Promise<string | null>;
```

Query shape: one `SELECT users.id FROM users JOIN profiles ON profiles.user_id = users.id
WHERE profiles.phone IS NOT NULL AND <the DB-side digit-strip of profiles.phone> =
$normalizedPhone LIMIT 1` (the digit-strip on the stored side is a declarative SQL
expression — e.g. `regexp_replace(profiles.phone, '[^0-9]', '', 'g')` — evaluated by
Postgres, not an application-level comparison function). Returns the first match's
`users.id`, or `null`.

**Open question, named rather than resolved:** `profiles.phone` carries no index (checked:
`db/schema.ts`'s only index on `profiles` is `profiles_user_id_unique`). If more than one
row's normalized phone matches, this query returns whichever row Postgres returns first
for an unordered `LIMIT 1` — not a specified "most recent" or "first ever" row, the same
open-endedness `getUserByTgUsername` (`domain/user.ts` §6.3, REQ-018) already leaves for
its own unindexed lookup. Not exercised by any acceptance criterion; an index is a
performance concern this design does not need to resolve for a per-event, low-volume
lookup.

## 4. Reused unchanged, restated for this flow's authorization gate

`domain/eventAuthorization.ts`'s `requireOrganizerForChapter` (REQ-016) — **not**
`eventStaffAuthorization.ts`'s `requireEventStaffForEvent` (REQ-018/028/029's check-in
gate). This is the AC6/S2-critical choice: `EventStaff` grants check-in rights "for that
one event and nothing else" (S2) — admitting a walk-in, like REQ-029's organizer override
(§4.3 of that design), is a decision about *who gets a seat*, not merely *whether someone
already admitted has arrived*. `requireOrganizerForChapter` is called against the target
event's `chapterId` at **three** separate points in this flow (§8): the initial command,
the confirm tap, and the override tap — never only at the first of the three, mirroring
REQ-028 §3.3's "the tap is the action, re-authorize on the action" discipline.

## 5. The pure decision (`domain/walkin.ts`)

```
export interface WalkinDecisionInput {
  eventStatus: "draft" | "published" | "cancelled";
  endsAt: Date | null;
  capacity: number | null;
  existingRegistration: {
    admission: AdmissionState;
    checkedInAt: Date | null;
  } | null;
  seatsLeft: number; // capacity - admittedCount, computed BEFORE this walk-in's own effect
  overrideConfirmed: boolean;
}

export type WalkinDecisionOutcome =
  | { kind: "event-not-ready" }             // endsAt or capacity is null — defensive, see note
  | { kind: "event-cancelled" }
  | { kind: "event-finished" }
  | { kind: "already-checked-in" }
  | { kind: "check-in-existing-admitted" }
  | { kind: "admit-and-check-in" }
  | { kind: "needs-override-confirmation" };

export function decideWalkinOutcome(
  input: WalkinDecisionInput,
  evaluationTime: Date,
): WalkinDecisionOutcome;
```

First-match-wins table, stated exactly (same convention `decideRegistrationOutcome`/
`decideCheckinToggleOutcome`/`decideQrCheckinOutcome`/`decideOverrideOutcome` already use
in this codebase):

| Step | Condition | Result |
|---|---|---|
| 1 | `endsAt === null` or `capacity === null` | `{ kind: "event-not-ready" }` |
| 2 | `eventStatus === "cancelled"` | `{ kind: "event-cancelled" }` |
| 3 | `isFinished(endsAt, evaluationTime)` | `{ kind: "event-finished" }` |
| 4 | `existingRegistration !== null` AND `existingRegistration.admission === "admitted"` AND `existingRegistration.checkedInAt !== null` | `{ kind: "already-checked-in" }` |
| 5 | `existingRegistration !== null` AND `existingRegistration.admission === "admitted"` AND `existingRegistration.checkedInAt === null` | `{ kind: "check-in-existing-admitted" }` |
| 6 | (`existingRegistration === null` OR its `admission !== "admitted"`) AND (`seatsLeft > 0` OR `overrideConfirmed === true`) | `{ kind: "admit-and-check-in" }` |
| 7 | (`existingRegistration === null` OR its `admission !== "admitted"`) AND `seatsLeft <= 0` AND `overrideConfirmed === false` | `{ kind: "needs-override-confirmation" }` |

Step 1 is defensive/unreachable for any `published` event (`findMissingPublishFields`,
`domain/event.ts`, already requires both non-null before publish is allowed) — stated
explicitly rather than left as an implicit type-widening, following this codebase's own
convention of naming defensive branches (REQ-016/018/029's `endsAt === null` checks).

**Why steps 4–5 (an existing `admitted` registration) never need the override:** that
person is already counted inside `admittedCount`/`seatsLeft` before this walk-in ran — no
new seat is being consumed, so no capacity question arises. Step 5's outcome is simply
"check them in," the same one-column write REQ-028's manual toggle already performs for
an admitted-but-not-yet-checked-in attendee, reused as the same *shape* here (not the same
function — REQ-028's `toggleCheckIn` also handles undo, which this flow never does; a walk-in
add never removes an attendance mark).

**Why an existing `waitlisted`/`requested`/`withdrawn`/`rejected` registration is treated
identically to "no registration at all"** (step 6/7's shared condition): admitting any of
these past normal rules is exactly the same "admit past capacity/waitlist rules" decision
REQ-029 §4's `decideOverrideOutcome` already reasons about for the QR-refusal path — this
design applies the identical reasoning to the door, not a different one, per the
requirement text's own pointer ("reuse the S7 override precedent ... or design a
walk-in-specific variant" — this is the variant, sharing REQ-029's reasoning while
differing in its write shape, §6).

## 6. The transactional write (`domain/walkin.ts`)

### 6.1 Why capacity is re-evaluated fresh on every call, never trusted from an earlier tap

```
export async function commitWalkin(
  db: DbClient["db"],
  eventId: string,
  organizerUserId: string,
  args: { name: string; company: string; phone: string },
  overrideConfirmed: boolean,
  at: Date,
): Promise<
  WalkinDecisionOutcome & { auditAction?: string }
>;
```

Called **twice** across the flow's lifetime in the ordinary over-capacity case (§1.3): once
from the confirm tap (`overrideConfirmed: false`), and, only if that call returns
`"needs-override-confirmation"`, a second time from the override tap
(`overrideConfirmed: true`). Each call opens its **own** transaction with a **fresh**
locked read — never a value carried over from the first call — the identical discipline
`toggleCheckIn`/`performQrCheckIn`/`overrideAdmitAndCheckIn` (REQ-028/029) already
establish for "the check and the write must be atomic, not read-then-write" (S7's negative
case). A seat that opened up (a cancellation) or closed (a concurrent admission) between
the two taps is picked up correctly because nothing about admittedCount/seatsLeft is ever
read outside this function's own transaction.

### 6.2 Sequence, stated exactly

1. `db.transaction`: `SELECT id, status, ends_at, capacity, chapter_id FROM events WHERE
   id = $eventId FOR UPDATE` — locked, mirroring `registerForEvent`'s own event-row lock
   (REQ-020 §3.2 step 2). Not found → `{ kind: "event-not-ready" }` (a defensive
   not-found branch; the caller has already resolved this event once at the command step,
   §8, so a mid-flow deletion is the only way this is reached).
2. `normalizedPhone = normalizePhoneForMatching(args.phone)` (§3.2); `matchedUserId =
   getUserIdByPhone(tx, normalizedPhone)` (§3.4), run against the same transaction (`tx`)
   so a phone match created by a concurrent, near-simultaneous walk-in add is visible
   consistently — though a genuine race here is extremely unlikely at door volume and no
   acceptance criterion exercises it.
3. **Resolve or create the person**, stated as a table (no branch written as executable
   logic beyond the two named calls):

   | `matchedUserId` | Action |
   |---|---|
   | non-null | `userId = matchedUserId`. **No write to `users` or `profiles`** — the existing profile (guaranteed to exist, §3.3) is left exactly as it is; the door-supplied `name`/`company` are used only for this flow's own confirmation/success copy, never written over the existing row (§ Open Question 2). |
   | `null` | `userId = createWalkinUser(tx, { chapterId: event.chapterId, consentPdAt: at }).id` (§6.3) — the **only** point in this entire flow where a new `User` row is written, and it happens with `consentPdAt` already set on the very same `INSERT`, never in a separate later write (S1: nothing is stored **before** consent — here, nothing about this specific new person is stored **without** consent already attached to the same statement that creates their first row). Then `createWalkinProfile(tx, { userId, name: args.name, company: args.company, phone: args.phone })` (§6.4). |

4. `existingRegRows = SELECT id, admission, checked_in_at FROM registrations WHERE
   event_id = $eventId AND user_id = $userId LIMIT 1 FOR UPDATE` (locked — `uq_registrations_event_user`
   guarantees at most one row).
5. `admittedCount = countAdmittedRegistrations(tx, eventId)` (existing, `domain/event.ts`,
   reused unchanged) — counted **before** this walk-in's own effect, same convention
   `registerForEvent` already uses. `seatsLeft = computeSeatsLeft(event.capacity,
   admittedCount)` (existing, reused unchanged).
6. `outcome = decideWalkinOutcome({ eventStatus: event.status, endsAt: event.endsAt,
   capacity: event.capacity, existingRegistration: existingRegRows[0] ?? null, seatsLeft,
   overrideConfirmed }, at)` (§5).
7. `"event-not-ready"` / `"event-cancelled"` / `"event-finished"` / `"already-checked-in"` /
   `"needs-override-confirmation"` → **no write to `registrations`**, return the outcome
   as-is. (For `"needs-override-confirmation"` specifically: this is the branch that
   leaves the transaction opened at step 3 still committing the `User`/`Profile`
   resolve/create — see § Open Question 3 for why that is a deliberate choice, not an
   oversight.)
8. `"check-in-existing-admitted"` → `UPDATE registrations SET checked_in_at = $at,
   checked_in_by = $organizerUserId, check_in_method = 'manual' WHERE id =
   $existingRegRows[0].id`, then **exactly one** `writeAuditLog(tx, { actorUserId:
   organizerUserId, action: "registration.checkin", entity: "registration", entityId:
   existingRegRows[0].id, payload: { eventId, source: "walkin" }, at })` — reuses the
   identical action name REQ-028/029 already use for an ordinary check-in, since this
   *is* an ordinary check-in of an already-admitted person (S8).
9. `"admit-and-check-in"` → insert-if-absent / update-if-present against
   `uq_registrations_event_user` (mirrors `registerForEvent`'s REQ-022 reuse pattern,
   §3.2 point 3 of that design): `admission = 'admitted'`, `checked_in_at = $at`,
   `checked_in_by = $organizerUserId`, `check_in_method = 'manual'`, `qr_token =
   generateQrToken()` (existing, reused unchanged), `source = 'walkin'` (insert case
   only — an update reuses the row's existing `source`, matching REQ-022's own
   `set` clause discipline of not touching columns outside what's changing). Then
   **exactly one** `writeAuditLog` call, action chosen by this table (not a branch
   written as code):

   | `seatsLeft` at this write | `overrideConfirmed` | `action` |
   |---|---|---|
   | `> 0` | (either) | `"registration.walkin_admit"` |
   | `<= 0` | `true` | `"registration.walkin_override_admit"` |

   payload `{ eventId, previousAdmission: existingRegRows[0]?.admission ?? null, source:
   "walkin" }` in both cases — the `previousAdmission` field is what makes the override
   row's payload distinguishable from an ordinary admit's when read back, mirroring
   REQ-029 §4.2's identical field.
10. Return the outcome with `auditAction` attached (the handler, §8, uses it only to
    decide which success copy to show — "admitted" vs. "admitted via override" — never to
    decide whether to write anything, which is already fully decided by this point).

**Why this satisfies AC3's "exactly one audit_log row" for the override specifically:**
one `UPDATE`/`INSERT`, one `writeAuditLog` call, one transaction — the same discipline
every other mutation in `registration.ts` already follows (REQ-020/022/028/029). The
override tap's own call to `commitWalkin` (`overrideConfirmed: true`) either lands on
step 9 (writing exactly one row, if capacity is still genuinely full) or, if a seat freed
up between taps, on the ordinary `seatsLeft > 0` branch of the same step 9 — either way,
exactly one audit row from that one tap, never zero, never two.

```
  db: DbClient["db"],
  input: CreateWalkinProfileInput,
): Promise<void>;
```

`INSERT INTO profiles (user_id, first_name, company, phone) VALUES ($userId, $name,
$company === "" ? NULL : $company, $phone)` — every other column
(`last_name`/`position`/`is_student`/`experience_level`, the five `*Skipped` flags,
`public_bio`/`photo_file_id`/`publish_consent`) is left at its column default/`NULL`,
exactly the same "partially filled, resumable-later" row shape REQ-019's own form
produces for someone mid-onboarding — no new null-handling rule invented. The whole
door-collected `name` string is stored into `first_name` as-is; `last_name` stays `NULL`.
This is a deliberate simplification (the door collects one free-text name field, not
first/last separately) stated here rather than silently splitting on whitespace, which
would mis-split any name with a middle name, a single-word name, or a non-Latin-script
name with different conventions (§ Open Question 5).

## 7. The two canonical messages (`domain/walkin.ts`)

### 7.1 Render/re-parse pair — the mechanism §1.1 depends on

```
export interface WalkinMessageFields {
  eventTitle: string;
  name: string;
  company: string; // "" allowed
  phone: string;
}

export function formatWalkinConfirmMessage(
  fields: WalkinMessageFields,
  lang: BotLang,
): string;

export function formatWalkinOverrideMessage(
  fields: WalkinMessageFields,
  admittedCount: number,
  capacity: number,
  lang: BotLang,
): string;

export type ParseWalkinMessageResult =
  | { ok: true; fields: { name: string; company: string; phone: string } }
  | { ok: false };

export function parseWalkinMessageFields(messageText: string): ParseWalkinMessageResult;
```

**Canonical format, shared by both render functions** — four fixed-prefix lines,
in this exact order, each other line in the message free-form (catalog copy, consent
statement, capacity numbers):

```
Event: <eventTitle>
Name: <name>
Company: <company, or the literal placeholder "—" when "">
Phone: <phone>
```

`parseWalkinMessageFields`'s rule: split `messageText` on newlines; find the first line
starting with the exact literal prefix `"Name: "`, the first starting with `"Company: "`,
the first starting with `"Phone: "`; each line's value is everything after its prefix. Any
of the three not found → `{ ok: false }` (the tap's handler, §8, treats this exactly like
a stale/corrupted message — refuse, no write, ask the organizer to re-run `/walkin`). A
parsed `Company:` value equal to the literal placeholder `"—"` is converted back to `""`.
The `Event:` line is **not** parsed back into a value used by any write — it exists only
for the organizer's own visual confirmation of which event they're adding to, and as a
defensive human-readable cross-check against a stale message (§ Open Question 6); the
authoritative `eventId` for every write always comes from the tapped button's
`callback_data`, never from re-parsed text.

### 7.2 What's rendered where

- **Confirm message** (§8.2, sent by the `/walkin` command): `formatWalkinConfirmMessage`
  plus the catalog's consent statement (`walkin.consentStatement`, §9) plus Confirm/Cancel
  buttons.
- **Override-offer message** (§8.3, sent when `commitWalkin` returns
  `"needs-override-confirmation"`): `formatWalkinOverrideMessage`, additionally showing
  `admittedCount`/`capacity` (`walkin.overridePrompt`, interpolated), plus
  Confirm-override/Dismiss buttons. Uses the **same** three labeled lines so the override
  tap can re-parse `name`/`company`/`phone` exactly like the confirm tap does (§1.3).

## 8. Handlers (`apps/bot/src/handlers/walkin.ts`)

### 8.1 `/walkin <event_id> <name>|<company>|<phone>`

```
export function makeWalkinCommandHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence:
1. `tgId = ctx.from?.id`; `undefined` → return.
2. `lang = resolveLangForTg(db, tgId)`.
3. `parsed = parseWalkinArgs(matchText(ctx))` (§2); `!ok` → reply `walkin.usage`, return.
4. `event = getEventById(db, parsed.args.eventId)`; `null` → reply `walkin.eventNotFound`,
   return.
5. `event.chapterId` is always present (`events.chapterId` is `NOT NULL`, §0) —
   `authResult = requireOrganizerForChapter(db, BigInt(tgId), event.chapterId)` (§4).
   `!ok` → reply `walkin.notAuthorized`, return. **This is AC6's negative case** —
   constructed by invoking this handler with a `tgId` resolving to `role: "member"` or an
   organizer of a *different* chapter; no `EventStaff` row is consulted anywhere in this
   flow at all (§4).
6. `fieldsValid = validateWalkinFields(parsed.args)` (§2); `!ok` → reply
   `walkin.missingName` / `walkin.missingPhone` by `reason`, return.
7. Reply with `formatWalkinConfirmMessage({ eventTitle: event.title, name:
   parsed.args.name, company: parsed.args.company, phone: parsed.args.phone }, lang)` +
   `walkin.consentStatement`, with an inline keyboard: Confirm
   (`callback_data = "walkin:confirm:" + event.id`), Cancel
   (`callback_data = "walkin:cancel"`). **No write of any kind happens in this handler** —
   this is what makes AC1 structurally true for the "abandoned at the consent step"
   case: nothing between here and a Confirm tap ever calls `commitWalkin`.

### 8.2 `walkin:confirm:<eventId>` callback

```
export const WALKIN_CONFIRM_PATTERN = /^walkin:confirm:(.+)$/;

export function makeWalkinConfirmCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence:
1. Extract `eventId` from `WALKIN_CONFIRM_PATTERN`; no match → `ctx.answerCallbackQuery()`,
   return (defensive, unreachable).
2. `tgId = ctx.from?.id`; `undefined` → `ctx.answerCallbackQuery()`, return.
3. `event = getEventById(db, eventId)`; `null` → `ctx.answerCallbackQuery({ text:
   walkin.eventNotFound, show_alert: true })`, return.
4. **Re-authorization (S2, mirrors REQ-028 §3.3/REQ-029 §4.3):**
   `authResult = requireOrganizerForChapter(db, BigInt(tgId), event.chapterId)`. `!ok` →
   `ctx.answerCallbackQuery({ text: walkin.notAuthorized, show_alert: true })`, **no
   write**, return.
5. `parsed = parseWalkinMessageFields(ctx.callbackQuery.message?.text ?? "")` (§7.1);
   `!ok` → `ctx.answerCallbackQuery({ text: walkin.staleMessage, show_alert: true })`, no
   write, return.
6. `outcome = commitWalkin(db, eventId, authResult.user.id, parsed.fields, false, new
   Date())` (§6).
7. `outcome.kind === "event-not-ready" | "event-cancelled" | "event-finished"` →
   `ctx.answerCallbackQuery({ text: <matching catalog key>, show_alert: true })`, no
   further action.
8. `outcome.kind === "already-checked-in"` → `ctx.editMessageText(walkin.alreadyCheckedIn)`
   (no keyboard).
9. `outcome.kind === "check-in-existing-admitted"` or `"admit-and-check-in"` →
   `ctx.editMessageText(walkin.success, { ... })` — success copy interpolated with
   `parsed.fields.name`/`parsed.fields.company` (never phone — AC5, §10), no keyboard.
10. `outcome.kind === "needs-override-confirmation"` → `admittedCount =
    countAdmittedRegistrations(db, eventId)` (a plain post-transaction read for display
    only — the authoritative count that decided the outcome was already read fresh
    inside `commitWalkin`'s own transaction, step 5 of §6.2) → `ctx.editMessageText(
    formatWalkinOverrideMessage({ eventTitle: event.title, ...parsed.fields },
    admittedCount, event.capacity ?? 0, lang), { reply_markup: <Confirm-override
    (callback_data = "walkin:override:" + eventId) / Dismiss
    (callback_data = "walkin:cancel") buttons> })`. **This is AC3's confirmation
    step** — reached only when `commitWalkin` itself determined `seatsLeft <= 0` inside
    its own locked transaction, not from any value computed earlier in this handler.

### 8.3 `walkin:override:<eventId>` callback

```
export const WALKIN_OVERRIDE_PATTERN = /^walkin:override:(.+)$/;

export function makeWalkinOverrideCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Identical to §8.2 steps 1–5, then:

6. `outcome = commitWalkin(db, eventId, authResult.user.id, parsed.fields, true, new
   Date())` (§6) — **the only difference from §8.2's call is `overrideConfirmed: true`**.
7. Same outcome handling as §8.2 steps 7–9 (an "event-not-ready"/cancelled/finished
   refusal, an "already-checked-in" report, or a success edit) — `"needs-override-confirmation"`
   is structurally unreachable here (`overrideConfirmed: true` makes step 6 of §5's table
   always satisfied once steps 1–5 are cleared), so this handler defines no branch for it.

**This is AC3's "confirming writes exactly one audit_log row" and "dismissing creates no
registration"**: confirming reaches step 9 of §6.2 (one `UPDATE`/`INSERT` + one
`writeAuditLog`, §6.2's table); dismissing means the organizer taps the Dismiss button
instead (§8.4) — `commitWalkin` is never called at all on that path, so the registration
table is never touched (the `User`/`Profile` rows created at the first confirm tap, if
any, remain — § Open Question 3 — but **no** registration row is created either then or
ever, satisfying the AC's literal wording).

### 8.4 `walkin:cancel` callback

```
export function makeWalkinCancelCallbackHandler() {
  return async (ctx: Context): Promise<void> => {
    await ctx.answerCallbackQuery();
    await ctx.editMessageText(getCatalog(<lang>).walkin.cancelled);
  };
}
```

No `db` parameter — this handler never reads or writes anything. Used for **both** the
initial Cancel button (§8.1) and the override step's Dismiss button (§8.2 step 10) — both
mean exactly the same thing ("do not create anything from this message"), so one shared
handler and one shared `callback_data` string (`"walkin:cancel"`) is used for both,
rather than two parallel no-op handlers.

## 10. S11 — the PII redaction rule this design commits to (AC5)

**No function anywhere in `domain/walkin.ts`, `domain/user.ts`'s new additions,
`domain/profile.ts`'s new addition, or `handlers/walkin.ts` interpolates the raw `phone`
value into: a log message (`msg` string or a `LogFields` value under any key other than
the literal key `phone`, which `log.ts`'s existing `REDACTED_KEYS` set already strips —
REQ-012 §5, pre-existing, unchanged by this requirement) or a `writeAuditLog` payload.**
Every `writeAuditLog` call in §6.2 (steps 8 and 9) passes a payload of exactly `{ eventId,
previousAdmission, source }` (or `{ eventId, source }`) — `phone` is never a key in either
shape, structurally, not by omission after the fact.

**Where phone IS shown, and why that is not this invariant's negative case:** the confirm
message (§7.2, §8.1 step 7) and its stale-message/re-parse round trip (§8.2 step 5) do
carry the raw phone in plain message text, replied privately into the **same** chat the
organizer just typed it into. This is the identical class of exception REQ-019 §2.5
already establishes for `formatProfileDump` ("this is the OWNER's own data shown back to
themselves ... never a log line, error message, or audit payload") — here the same
non-third-party reasoning applies to the organizer who supplied the value one message
earlier in the same conversation, not a log line, not an audit payload, and not shown to
anyone other than the person who typed it. **The concrete negative case AC5 asks for**
(phone entered, then grepped out of process logs and every audit row) is satisfied because
no `log.*` call in this design's handlers ever receives the phone value as an argument at
all — every log-worthy event in this flow (a refusal, a stale-message parse failure, a
successful commit) is logged, if at all, keyed only by `eventId`/`userId`/`outcome.kind`,
never by the free-text fields from the message.

## 12. Open questions (not silently resolved)

1. **Whether `company` is a required door field.** The requirement text lists "name,
   company, phone" as the door's "minimal field set," which reads as all three required;
   this design treats only `name` and `phone` as non-blank-required (§2), since phone is
   the matching key and name is needed for any confirmation/success copy, while company
   has no such structural necessity and organizers at a real door may not always get a
   clean answer to "where do you work." If product intends `company` to be a hard
   requirement, `validateWalkinFields`'s table gains one more row — a small change, but
   named here rather than silently assumed.
2. **A phone match never updates the existing profile's `name`/`company` with the
   door-supplied values (§6.2 step 3).** If the existing profile has a blank `company` and
   the door capture supplies one, this design leaves the blank as-is rather than filling
   it in. No acceptance criterion requires an update either way; leaving the existing row
   untouched avoids silently overwriting data the person may have entered more carefully
   themselves via `/profile`.
3. **A `"needs-override-confirmation"` outcome leaves a freshly created `User`/`Profile`
   committed even if the organizer then taps Dismiss (§6.2 step 7, §8.3).** AC3's own
   wording only forbids a **registration** row surviving a dismissed override, which this
   design satisfies exactly; whether an organizer walking away from an at-capacity add
   should also roll back the just-created `User`/`Profile` (via a compensating delete on
   Dismiss) is not asked for by any acceptance criterion and is not added here — inventing
   a rollback path for data whose consent has already been validly given is a bigger,
   separate behavioral decision this design does not make unilaterally.
4. **`createWalkinUser` defaults the new person's `chapterId` to the event's own chapter
   (§6.3).** Reasonable but not tested by any acceptance criterion; flagged in case
   product wants a walk-in's chapter left unset until they interact with the bot directly.
5. **The whole door-collected `name` string is stored into `profiles.first_name`, with
   `last_name` left `NULL` (§6.4).** No first/last split is attempted. If a future
   requirement wants the walk-in's later `/profile` view to show a conventional two-field
   name, that requirement's own design is responsible for reconciling a single-field name
   already on file — not solved here.
6. **The `Event:` line in the canonical message (§7.1) is never cross-checked against the
   tapped button's `eventId`.** It exists purely for the organizer's own visual
   confirmation. A theoretical tamper scenario (a forwarded/edited message showing one
   event's title but a button pointing at a different event's id) is not defended against
   beyond Telegram's own guarantee that only the bot can edit its own messages — flagged
   as a residual gap rather than silently assumed closed, though no acceptance criterion
   exercises it and no ordinary user action can produce it (a forward carries a fresh,
   button-less copy of the message; only the original message's own buttons still work).
