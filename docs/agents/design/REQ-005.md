# REQ-005 — Add Kazakh (`kk`) locale to the i18n mechanism, design

Status: design for WF-02 Step 1. Scope: make `kk` a recognized, routable locale
alongside `ru`/`uz`/`en` with a fully-keyed placeholder message catalog. Translation
content is explicitly out of scope — REQ-006 (`depends_on` this requirement) replaces
the placeholders with real Kazakh copy. See handoff
`handoffs/WF02-REQ005-REQ006/step-01-code-designer.json` for full requirement text.

This design mirrors `docs/agents/design/REQ-003.md`'s structure exactly (REQ-003 added
`en` as the third locale, following the same mechanism REQ-001a used for `uz`). Unlike
REQ-003, every value this requirement needs — including the `Metadata.ogLocale`
placeholder — is stated explicitly in the requirement text, so this design has no open
questions.

## 2. `src/i18n/routing.ts` — exact change

Structural shape (types/fields, not implementation):

```
locales: readonly ["ru", "uz", "en", "kk"]   // "kk" appended after "en"
defaultLocale: "ru"                           // unchanged
```

This is the only edit to this file. `defaultLocale` stays `"ru"` — the requirement text
states no source gives a reason to change the site's entry locale; the requirement only
asks for a Kazakh version to exist as an additional, selectable locale. `"kk"` is the
ISO 639-1 language code (distinct from `"KZ"`, the ISO 3166-1 country code, which is used
only inside the region-tagged `ogLocale` value `kk_KZ` — see §3).

## 3. `messages/kk.json` — content shape

Exact same nested shape as `messages/ru.json`: 13 top-level namespaces (`Metadata`,
`Nav`, `Hero`, `Band`, `Creed`, `Metrics`, `Doors`, `Events`, `MapSection`, `Streams`,
`Partners`, `Team`, `Footer`), same key names at every level, same 177 total leaf keys,
same nesting depth (all namespaces are flat string maps — no arrays, no further nesting
below the namespace level, matching `ru.json`'s actual shape as verified in §0).

Per requirement text, every leaf value is the **Russian source string duplicated
verbatim** as a placeholder — not an empty string, not a `TODO` marker, not a machine
translation. This is the same placeholder convention REQ-001a used for `messages/uz.json`
and REQ-003 used for `messages/en.json`.

`Metadata.ogLocale` is the one deliberate exception to pure verbatim-duplication, and
unlike REQ-003 (which had to infer `en_US` and flag it as an open question), **this
requirement's text states the placeholder value explicitly**: `"ru_RU"` — i.e., for this
locale only, `ogLocale` is *not* set to a `kk_KZ`-style value yet. The real `kk_KZ` value
is explicitly deferred to REQ-006 along with the rest of the translation content. This
matches `Metadata.title`/`Metadata.description`, which also get the verbatim Russian
string — `ogLocale` here simply isn't special-cased the way REQ-003/REQ-001a special-cased
their locales' `ogLocale`, per this requirement's own explicit instruction. **This value
is settled by the requirement text, not an inference — no open question.**

Concrete shape:

```
{
  "Metadata": {
    "title": "<ru.json Metadata.title verbatim>",
    "description": "<ru.json Metadata.description verbatim>",
    "ogLocale": "ru_RU"
  },
  "Nav": { ... 1:1 verbatim copy of ru.json's Nav keys/values ... },
  "Hero": { ... },
  "Band": { ... },
  "Creed": { ... },
  "Metrics": { ... },
  "Doors": { ... },
  "Events": { ... },
  "MapSection": { ... },
  "Streams": { ... },
  "Partners": { ... },
  "Team": { ... },
  "Footer": { ... }
}
```

All 177 leaf keys (including `Metadata.ogLocale`): Russian source string,
character-for-character identical to `messages/ru.json`'s value at the same key path. No
translation, no transliteration, no partial rewording — REQ-006 replaces these,
including the eventual real `kk_KZ` `ogLocale` value.

## 4. Design-token / responsive / theme considerations

None apply. This requirement touches no visual, layout, or interactive code:

- No new CSS class or token — `.lang`/`.lang a`/`.lang .on` are reused unchanged (§0),
  no new declaration is added or needed.
- No new component, so no new token consumption site.
- No responsive behavior changes — the switcher's flex-row layout already accommodates
  a variable number of children (§0); a fourth link does not require a breakpoint
  change.
- No theme-specific behavior — the reused classes already resolve through
  `var(--primary)`/`var(--muted)`/`var(--border)` per existing dark/light token
  definitions in `docs/Design system for AI agents/tokens/tokens.css`; nothing new is
  introduced that would need separate light/dark verification beyond confirming the
  existing switcher still renders correctly with four links in both themes (a
  verification-step concern, not a design decision).

## 5. Open questions

None. Every value this requirement needs is settled by the requirement text itself:

- Locale code: `"kk"` (ISO 639-1), stated explicitly in the requirement text, with the
  `kk` vs. `KZ` distinction stated explicitly too.
- `defaultLocale`: stays `"ru"`, stated explicitly.
- `messages/kk.json` content rule: Russian source string verbatim for every key,
  **including** `Metadata.ogLocale` seeded as the literal placeholder `"ru_RU"` (not an
  inferred `kk_KZ`-style value the way REQ-003 had to infer `en_US`) — stated explicitly
  in the requirement text.
- The three "no code change" files (`request.ts`, `LocaleSwitcher.tsx`, `layout.tsx`)
  are independently re-verified in §0 by direct reading today, not copied from REQ-003's
  doc without re-checking.

This is a deliberate contrast with REQ-003's design doc, which carried one open question
about the `ogLocale` placeholder value because the requirement text didn't name it. Here
the requirement text does name it, so there is nothing left to flag as open.
