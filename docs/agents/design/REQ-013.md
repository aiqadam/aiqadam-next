# REQ-013 — Bot i18n scaffold with RU and EN catalogs and the /lang command

**Role:** CODE-DESIGNER (design only — no implementation code; BACKEND-DEV implements
this artefact). No DATA-DESIGNER output: this requirement adds no column and no table —
`users.lang` and `chapters.default_lang` already exist from REQ-010's migration. It reads
those two columns; it does not alter their shape.

**Design-system note (stated once, up front):** `docs/Design system for AI agents/` is a
*visual* system — OKLCH color tokens, spacing, typography, Lucide icons, CSS component
classes — built for rendered HTML surfaces (`apps/web`). A Telegram bot has no HTML, no
CSS, and no icon rendering; none of that system's tokens apply here. The parts of the
design system that DO apply to a bot's text are the content-fundamentals section only —
voice (functional, operator-facing, no exclamation marks, no slogans, no emoji),
casing (sentence case for anything button-like), and domain vocabulary (verbatim English
terms: Event, Chapter, Talk, Speaker, CFP, Agenda, Check-in, Going, Watching). Every seed
string in §5 below follows those rules. `frontend_developer_guide.md` likewise governs
`apps/web`/`src`/`public` and has no bot-specific content — nothing in it applies to this
requirement's `apps/bot/**` scope beyond that same voice/tone material, which lives in
the design system readme, not that guide.

## 1. Message catalog mechanism

### 1.1 File shape

```
apps/bot/src/i18n/
  types.ts        Catalog shape (the TypeScript type every locale catalog must satisfy)
  ru.ts           export const ru: Catalog = { ... }
  en.ts           export const en: Catalog = { ... }
  catalog.ts       export const catalogs: Record<BotLang, Catalog> = { ru, en };
                    export type BotLang = "ru" | "en";
  resolveLang.ts   pure resolution function, §1.3
  catalogs.test.ts Vitest key-parity check, §4
```

Plain TypeScript modules, **not JSON**. Rationale: `apps/web/messages/*.json` is read at
request time by `next-intl`'s dynamic `import()` — a mechanism this requirement
deliberately does not adopt (REQ-013's own description: no shared package, no reuse of
the site's catalogs, and `next-intl` is not and must not become a dependency of
`apps/bot`). A plain `.ts` module exporting a `const` object gets the same "flat file
per locale" shape the site uses, but also gets TypeScript's own structural checking for
free: declaring `ru`/`en` as `satisfies Catalog` (or as `Catalog` directly) makes a
missing or extra key a **compile error** in `npm run build -w apps/bot`, on top of the
runtime parity check in §4 — belt and suspenders, and consistent with this workspace's
existing style (`config.ts`, `log.ts` are plain typed TS modules, not JSON/YAML config).

### 1.2 Key structure: nested by feature

```ts
// apps/bot/src/i18n/types.ts
export interface Catalog {
  start: {
    greeting: string;
  };
  lang: {
    prompt: string;
    confirmed: string;
  };
}
```

Two levels: top-level key = the command/flow the string belongs to (`start`, `lang`),
second level = the specific string within that flow. This mirrors the site's own
`messages/*.json` nesting convention (`Metadata.title`, etc.) without sharing any actual
file — same *pattern*, independent *content*. Flat (single-level) was considered and
rejected: with only two flows today the difference is cosmetic, but every later bot
requirement (REQ-014 onward) adds its own flow-scoped strings, and starting nested avoids
a later rename/restructure once the catalog has 30+ keys across a dozen commands.

`Catalog` is the single source of truth for what keys must exist; `ru.ts` and `en.ts`
both declare their export `satisfies Catalog` (or as `: Catalog`) so TypeScript itself
rejects a locale file missing a key or misspelling one, in addition to §4's runtime
check.

### 1.3 Resolution function

```ts
// apps/bot/src/i18n/resolveLang.ts
export type BotLang = "ru" | "en";

export function resolveLang(
  userLang: string | null | undefined,
  chapterDefaultLang: string | null | undefined,
): BotLang;
```

Pure, synchronous, no I/O — same shape discipline as `config.ts`'s `loadConfig` (a
function of its inputs only, fully unit-testable without a database or a bot instance).
Logic, in order:

1. If `userLang` is exactly `"ru"` or `"en"` (case-sensitive, matching `users.lang`'s
   stored values per PRD 5's `lang(ru|en)`), return it.
2. Else if `chapterDefaultLang` is exactly `"ru"` or `"en"`, return it. **Note:**
   `chapters.default_lang` is a free-text column (REQ-010's schema places no CHECK/enum
   constraint on it — see `apps/bot/src/db/schema.ts`'s `defaultLang: text(...)`), and
   PRD 5's `Chapter.default_lang` is not stated to be drawn from the same `ru|en` set as
   `User.lang` — a chapter could plausibly hold `"uz"` there for other purposes. This
   function does not assume `chapterDefaultLang` is always a valid bot locale; an
   unrecognized value falls through to step 3 exactly like a missing one. This is the
   concrete reading of the requirement's own phrase "to ru when neither resolves" — 
   "neither resolves" covers both "chapter has no default_lang" and "chapter's
   default_lang isn't a bot-supported locale."
3. Else return `"ru"` (the fixed final fallback, per the requirement text — never
   configurable, never derived from `BotConfig.defaultChapterCode` or any other source).

`getCatalog(lang: BotLang): Catalog` (a one-line lookup into `catalogs`, §1.1) is the
companion function every handler calls after resolving a lang: `getCatalog(resolveLang(
user.lang, chapter?.defaultLang)).start.greeting`, etc.

**Domain-logic placement (decisions/0004):** `resolveLang` and `getCatalog` are
framework-free — no `Context`, no grammY import anywhere in `i18n/`. Handlers call them;
they never inline the ru/en branching themselves. This also happens to be exactly what
makes AC4 testable as a pure unit test (§3 below).

## 2. The `/lang` command

### 2.1 Registration

`bot.command("lang", handler)` — grammY core, no plugin (matches REQ-009's "no grammY
plugins at this stage" boundary; `InlineKeyboard` is exported by the `grammy` package
itself, not a separate plugin package).

### 2.2 Interaction: inline keyboard, two buttons

Chosen over a text-based `/lang ru` / `/lang en` sub-argument scheme because it removes
any parsing/typo surface (an unrecognized argument, wrong case, extra whitespace) for a
closed two-option choice, and keeps the confirmation step atomic (one tap = one
unambiguous selection) rather than requiring the user to type a language code correctly
in the language they may not yet be able to read comfortably.

- On `/lang`: the handler resolves the user's **current** language (`resolveLang`, §1.3,
  reading the caller's `users` row by `tg_id` — the same lookup shape as §3.2 below) and
  replies with `catalog.lang.prompt` (in that current language) plus an inline keyboard
  of exactly two buttons:
  - Button 1: label `"Русский"` (fixed, native-script language name — not itself a
    catalog key; a language's own name is not something that gets "translated" per
    locale, it is always displayed in its own script), `callback_data: "lang:ru"`.
  - Button 2: label `"English"`, `callback_data: "lang:en"`.
- `bot.callbackQuery(/^lang:(ru|en)$/, handler)` handles the tap: extracts the chosen
  `BotLang` from the match, calls the persistence function (§2.3), answers the callback
  query (grammY's `ctx.answerCallbackQuery()`, required by Telegram's API contract for
  every callback), and replies (or edits the prompt message) with `catalog.lang.
  confirmed` **read from the newly-chosen language's catalog**, not the pre-selection
  one — this is the literal mechanism behind AC3's "the confirmation message itself
  arrives in the newly selected language."

### 2.3 Persistence

A framework-free module, e.g. `apps/bot/src/domain/setUserLang.ts`:

```ts
export async function setUserLang(
  db: DbClient["db"],
  tgId: bigint,
  lang: BotLang,
): Promise<void>;
```

A single `UPDATE users SET lang = $1 WHERE tg_id = $2` (via Drizzle's query builder
against the already-existing `users` table/`tgId`/`lang` columns — no schema change).
Called from the `callbackQuery` handler with the `db` handle constructed once in
`index.ts` (REQ-012's `createDbClient`, already wired and currently unused —
`apps/bot/src/index.ts`'s `void pool;` line is replaced by actually passing `db` into
the bot's handlers, e.g. via `bot.use` middleware attaching it to `ctx`, or a closure —
BACKEND-DEV's call on the exact wiring shape; this design fixes only that the write goes
through this one framework-free function, never an inline query inside the handler
body, per decisions/0004).

**No-User-row case:** if the `UPDATE` affects zero rows (no `users` row exists for this
`tg_id` — the expected state for anyone who has never sent a stub-`/start`, see §3),
`setUserLang` reports that (e.g. a boolean return or a thrown typed error) and the
`/lang` handler replies with a short functional message stating the choice could not be
saved because no profile exists yet, instead of silently no-op'ing. This does **not**
create a `users` row — that remains REQ-014's exclusive scope (see §3's framing). Flagged
as open question 1 below since the requirement text does not explicitly cover this case.

## 3. The `/start` forward-dependency: resolution

**Chosen: option (a) — a minimal placeholder `/start` stub, explicitly a throwaway
REQ-013-only artefact that REQ-014 replaces wholesale.**

### 3.1 Why not option (b)

AC2 says "receives **/start and /lang** responses" (plural, both commands, naming
`/start` explicitly, not "the resolution function"). AC4 says "verified... by
**sending /start**" and explicitly rules out evidence that doesn't involve sending it
("a test run where User.lang was already set... is not evidence" — this sentence is
about *which row state* was exercised, not about *whether a live send occurred*, but it
is written entirely in terms of sending the command, never in terms of calling a
function). Both criteria are worded as live-bot, live-command checks, matching AC2's own
"verified against a live bot instance." An argument that "the resolution function IS the
thing being tested" would require rewriting what these two acceptance criteria literally
say TEST-DESIGNER/RELEASE-VALIDATOR must verify — and `core-directives.md`'s Instruction
Precedence places a `docs/agents/decisions/` record above everything else, but there is
no such record permitting AC text to be reinterpreted away from its literal wording by
CODE-DESIGNER. Silently narrowing "/start" to "the resolveLang unit test" would be
exactly the kind of unresolved ambiguity CODE-DESIGNER must not resolve alone. So option
(b) is rejected as insufficient on its own — **though the pure-function unit test from
§1.3 is still written and still valuable, in addition to, not instead of, a live
`/start` send.**

### 3.2 The stub itself

`bot.command("start", handler)`, registered alongside the existing `bot.command("health"
, ...)` in `index.ts`. Behavior, in full — nothing more:

1. Look up a `users` row by `tg_id = ctx.from.id` (`SELECT ... FROM users LEFT JOIN
   chapters ON users.chapter_id = chapters.id WHERE users.tg_id = $1`) — **read-only**,
   via a framework-free query function (e.g. `apps/bot/src/domain/user.ts`'s
   `getUserWithChapterByTgId(db, tgId): Promise<{ lang: string | null; chapterDefaultLang:
   string | null } | null>`).
2. If a row is found: `resolveLang(row.lang, row.chapterDefaultLang)`, then reply with
   `getCatalog(lang).start.greeting`.
3. If no row is found (the common case for anyone who has never been pre-created by an
   organizer and has never had a `users` row written by any other flow — i.e. everyone,
   until REQ-014 ships): reply with `catalog.ru.start.greeting` (the fixed `"ru"`
   fallback — no user, no chapter, nothing to resolve against; step 3 of §1.3's own
   fallback chain applied to the "no data at all" case).

**What this stub explicitly does NOT do**, so REQ-014 is not silently narrowed or
pre-empted:
- No `INSERT`/`UPSERT` into `users` — it never creates a row, under any input.
- No consent prompt, no `consent_pd_at` read or write.
- No chapter-assignment logic (single-active-chapter auto-assign, multi-chapter
  ask-once) — this stub never assigns or changes `chapter_id`.
- No deep-link (`?start=e_<event_id>`) payload handling.

**Consequence for REQ-014:** its own `/start` handler **replaces this stub's entire
`bot.command("start", ...)` registration**, not extends it — REQ-014 is expected to
delete this stub's body and write its own from scratch (creation, consent, chapter
assignment, THEN localized reply), reusing only `resolveLang`/`getCatalog`/the
`getUserWithChapterByTgId` query helper from this requirement's `i18n`/`domain` modules.
This is stated explicitly here so BACKEND-DEV on REQ-014 does not try to preserve or
incrementally build on the stub's lookup-only shape.

### 3.3 How AC2 and AC4 are actually verified against this stub

Both criteria require a **pre-existing** `users` (and, for AC4, `chapters`) row, since
the stub never creates one. The verification report inserts that row state directly
against the scratch/QA Postgres database (`psql`/a one-off script) **before** sending
`/start` — exactly the same style REQ-010's own acceptance criteria used ("verified by
inserting rows directly," "constructing exactly that row state"). Concretely:

- **AC2 (en/ru live responses):** insert one `users` row with `lang = 'en'`, `tg_id =
  <test account A>`; insert a second with `lang = 'ru'`, `tg_id = <test account B>`.
  Send `/start` and `/lang` from each account; paste the two accounts' received message
  text into the verification report.
- **AC4 (fallback):** insert a `chapters` row with `default_lang = 'en'`; insert a
  `users` row with `lang = NULL`, `chapter_id` pointing at that chapter, `tg_id = <test
  account C>`. Send `/start` from account C; the reply must be `catalog.en.start.
  greeting`. AC4's own text — "a test run where User.lang was already set... is not
  evidence" — is satisfied by this row explicitly having `lang = NULL`.

This is the concrete meaning of AC2/AC4's "sending /start": a live command against a
live bot process and a live (test-seeded) database row, using the stub above — not a
call to `resolveLang` in isolation. The `resolveLang` unit test (§1.3, run under
Vitest/`npm test`) is additional, cheaper coverage of the same fallback *logic*, not a
substitute for this live check.

## 4. Key-set parity check

**Shape:** a Vitest test, `apps/bot/src/i18n/catalogs.test.ts` — not a bespoke
standalone script. Rationale: decisions/0006 already wires Vitest at the repo root into
`.github/workflows/ci-cd.yml`'s `build` job (`npm test`, unconditionally gating the
build), and REQ-009 already established that a failing test fails CI. Adding a second,
parallel "run this extra script" step would duplicate infrastructure that already exists
and already gates — folding the parity check into `npm test` is strictly simpler and
satisfies "invoked in the verification report" (the report quotes `npm test`'s own
output) without a new CI step. This mirrors REQ-005's site-side key-parity checks in
*spirit* (a script that fails on any key-set mismatch) while using this workspace's own
existing test runner rather than a hand-rolled diff script, since one is now available
here and wasn't necessarily at REQ-005's time.

**What it asserts:**
1. A recursive key-extraction helper (e.g. flattening `ru`/`en` into dotted-path key
   lists: `"start.greeting"`, `"lang.prompt"`, `"lang.confirmed"`) applied to both
   catalogs.
2. `expect(flatten(en)).toEqual(flatten(ru))` (or the reverse) — a real assertion against
   the two actual catalog objects, not a placeholder. This is exactly the shape
   `backend_dev_guide.md` requires ("never `expect(true).toBe(true)`").
3. A second assertion that every leaf value is a non-empty string (catches an
   accidentally-blank seed value, not just a missing key).

**Where it's wired:** nowhere new — `npm test` at the repo root already runs every
`*.test.ts` file under both workspaces (Vitest's default discovery), so this file is
picked up automatically the moment it's committed; `.github/workflows/ci-cd.yml`'s
existing `Test` step (`npm test`) already gates on it. No new CI step, no new npm script.

**Additional compile-time layer:** §1.1/§1.2 already noted `ru.ts`/`en.ts` declaring
`satisfies Catalog` catches a missing/extra/misnamed key at `npm run build -w apps/bot`
time too — the Vitest check is the requirement's literal "runnable script... exits
non-zero," the `satisfies` typing is a second, earlier tripwire for the same class of
defect.

## 5. Seed content

**Confirming the requirement's own reading:** the requirement's description states this
mechanism "seeds it only with the strings the /start and /lang flows themselves need"
and separately states decisions/0002 "gives CONTENT-BA ownership of message catalog COPY
... any later bot copy pass is CONTENT-BA's, exactly as for the site." Read together,
this requirement (owner: BACKEND-DEV, not CONTENT-BA) is explicitly the mechanism-plus-
minimal-functional-seed step, structurally identical to REQ-001a's precedent (which
seeded `messages/ru.json`/`uz.json` with only `layout.tsx`'s own strings, written by
FRONTEND-DEV, with CONTENT-BA's real translation pass deferred to REQ-002). No CONTENT-BA
involvement is needed for this requirement's four seed strings — they are short,
functional, infrastructure-proving copy, not a copy pass over a real conversational
surface. A future requirement that writes the bot's actual conversational copy at scale
(greetings with real personalization, event-flow strings, error copy, etc.) should route
through CONTENT-BA per decisions/0002's consequence note, the same way REQ-002 followed
REQ-001a. This reading is confirmed, not silently assumed — flagged here per the task's
own instruction to state it explicitly.

**Closed key list (exactly four leaf keys, both locales):**

| Key | RU | EN |
|---|---|---|
| `start.greeting` | Это бот AI Qadam Events. | This is the AI Qadam Events bot. |
| `lang.prompt` | Выберите язык интерфейса. | Choose your interface language. |
| `lang.confirmed` | Язык интерфейса: русский. | Interface language: English. |

(`lang.confirmed` is deliberately not parameterized/templated — each locale's own value
already states its own language name in that language, so `catalog.en.lang.confirmed`
reads correctly as a whole sentence without needing the button-label constants from
§2.2 interpolated in.)

Tone check against the design system's content-fundamentals section: no exclamation
marks, no slogans, no emoji, sentence case throughout, no domain-vocabulary terms
present in this particular seed (none of Event/Chapter/Talk/etc. appear in a greeting or
a language prompt, so the verbatim-English rule has nothing to apply to here).

The two button labels (`"Русский"`, `"English"`, §2.2) are **not** catalog keys — they
are fixed, locale-independent literals (a language's own name in its own script), a
deliberate design choice stated explicitly rather than left ambiguous.

## 7. Confirmations

- **No `apps/web/messages/*.json` changes.** Nothing in this design touches
  `apps/web/**`. `apps/bot`'s catalogs are entirely new files under `apps/bot/src/i18n/`.
- **No shared i18n package.** `packages/` is not created or touched — matches
  decisions/0003's "only when a second consumer exists" rule and this requirement's own
  stated decision that the site's 177 marketing-copy keys and the bot's four

## 8. Open questions

1. **`/lang` called with no existing `users` row.** §2.3 proposes replying with a
   functional "nothing to save yet" message and NOT creating a row (since creation is
   REQ-014's scope). The requirement text does not cover this case explicitly. If
   REQ-014 lands and merges before REQ-013 in practice (their `depends_on` only requires
   REQ-012, so ordering between REQ-013/REQ-014 is not fixed), this case may become rare
   in practice but the mechanism must still handle it correctly on its own for whichever
   order actually ships. Confirm this handling is acceptable rather than, say, silently
   ignoring the tap with no reply at all (which this design rejects — a no-op response
   to a button press is a worse UX than a short explanation, and violates the tone
   guide's "no cheerful non-answer" spirit for empty/edge states, even though that guide
   line is written about visual empty states, not chat).
2. **`chapters.default_lang`'s actual value domain.** REQ-010's schema leaves it as
   unconstrained `text`. This design's `resolveLang` treats any value outside
   `{"ru","en"}` as non-resolving (falls through to `"ru"`) rather than throwing or
   logging a warning. If a later requirement wants a CHECK constraint restricting
   `default_lang` to a fixed set, or wants unrecognized values to be logged as a data
   inconsistency, that is a DATA-DESIGNER/BACKEND-DEV decision outside this
   requirement's scope — flagged, not resolved here.
3. **Whether a `users`-row lookup by `tg_id` inside a stub `/start` needs
   SECURITY-REVIEWER's explicit sign-off as "touching personal data."** The stub only
   *reads* `lang`/`chapter_id`-derived data (no PII value is ever echoed back — the
   reply is one of two fixed catalog strings, never `tg_username`, phone, or email), but
   WF-02 Step 2c runs SECURITY-REVIEWER unconditionally for every `apps/bot/**`
   requirement regardless of how security-irrelevant it looks (per
   `backend_dev_guide.md` §1, citing REQ-009's own precedent) — so this is already
   covered procedurally, not actually left open; noted here only so BACKEND-DEV doesn't
   mistake the stub's minimalism for an exemption from that gate.
