## 1. Command surface — one command family, three sub-commands

**Resolution of design question 1:** three separate commands, not one command with a
type parameter. Rationale: this codebase's existing convention (`venue_new`/`venue_edit`/
`venue_delete`, `event_new`/`event_edit`/`event_publish`/`event_cancel`,
`staff_add`/`staff_remove`) is always "one verb per command," never a single command
branching on a first-token type discriminator — and the three shapes take genuinely
different required arguments (PERSONAL needs a target user id, BULK needs a use count,
COMPANION needs a host user id), so a shared command would need the same
kind-then-branch parsing REQ-033 §2 explicitly rejected for the *data* shape. Matching
that precedent at the command layer keeps the two consistent.

### 1.1 `/invite_personal <event_id> <user_id> [expires_at]`

Issues a PERSONAL code: `issuedToUserId = <user_id>`, `grantsCompanionOf = null`,
`maxUses = 1`.

- `<event_id>`, `<user_id>`: required, first two whitespace-separated tokens (same
  first-token parsing convention `parseCheckinCommandArgs`/`parseRequestsCommandArgs`
  already use for `<event_id> [rest]`, extended here to a second required token before
  the optional remainder).
- `[expires_at]`: optional third token, an ISO-8601 timestamp. Absent → `expiresAt`
  defaults to the event's `startsAt` (§1.4). Present → overrides.
- `<user_id>` names an existing `users.id` row (never a `tg_id` — REQ-010 §5.1, restated
  binding here). The row's `tgId` MAY be null (design question 3, resolved below): this
  command performs a plain "does a `users` row with this id exist" lookup and proceeds
  regardless of whether `tgId` is null. Creating that pre-arrival row when it does not
  yet exist is REQ-040's scope, not this command's — a `<user_id>` naming no row is
  refused (`invitePersonal.userNotFound`), never auto-created here.

### 1.2 `/invite_bulk <event_id> <max_uses> [expires_at]`

Issues a BULK code: `issuedToUserId = null`, `grantsCompanionOf = null`,
`maxUses = <max_uses>`.

- `<max_uses>`: required, a positive integer, parsed the same way
  `validateEventCreateInput`'s `capacity` field is (`Number.isInteger(parsed) &&
  parsed > 0`) — reused as a stated parsing RULE, not copied code: "not a positive
  integer" refuses with `invalidMaxUses`, naming the field.
- `[expires_at]`: same optional-third-token shape as §1.1.

### 1.3 `/invite_companion <event_id> <host_user_id> [expires_at]`

Issues a COMPANION code: `issuedToUserId = null`, `grantsCompanionOf = <host_user_id>`,
`maxUses = 1`.

**Resolution of design questions 2/3 from REQ-033 §6 (points 2 and 3), routed here for
this requirement to close:**

- **Cardinality (REQ-033 §6 point 2):** this issuing flow always produces `maxUses = 1`
  for a COMPANION code — there is no command-line argument for it, unlike `/invite_bulk`.
  A "bulk companion" shape (`grantsCompanionOf` non-null, `maxUses > 1`) is simply never
  produced by any command this design defines; REQ-033's open DB-level question is
  resolved at the issuing-flow level by never offering the combination, not by a new
  constraint.
- **`issued_to_user_id` alongside `grants_companion_of` (REQ-033 §6 point 3):** this
  flow's `/invite_companion` never sets `issuedToUserId` — it is always `null` for a code
  issued through this command. The "personal companion code" combination REQ-033 §2
  states is legal at the DB level is not produced by any command in this design; if a
  future requirement wants it, it adds its own command rather than overloading this one.
  Stated explicitly, not silently resolved: this is a scope choice by this requirement's
  issuing flow, not a claim that the combination is illegal.
- `<host_user_id>`: same "must name an existing `users.id` row, `tgId` may be null"
  handling as §1.1's `<user_id>`.

### 1.4 Expiry default (design question 5 confirmation — no new field)

All three commands share one rule, stated once: **`expiresAt` defaults to the named
event's `startsAt`** when the optional third argument is absent; supplying an explicit
ISO-8601 timestamp overrides it. This reads `events.startsAt` (already selected by
`getEventById`) — no new column, no new query. If the supplied override fails to parse
as a date, the command refuses naming `invalidExpiresAt`, the same "collect and report,
don't half-apply" discipline `validateEventCreateInput`/`validateEventUpdateInput` use.

### 1.5 Shared parse/validate shape (types only)

```
IssueInviteCodeInput =
  | { kind: "personal"; eventId: string; targetUserId: string; expiresAt: Date | null }
  | { kind: "bulk"; eventId: string; maxUses: number; expiresAt: Date | null }
  | { kind: "companion"; eventId: string; hostUserId: string; expiresAt: Date | null }

IssueInviteCodeValidation =
  | { ok: true; value: IssueInviteCodeInput }
  | { ok: false; missing: string[] }   // field names, same convention as
                                        // EventCreateValidation's `missing` list
```

Three parse functions (`parseInvitePersonalArgs`, `parseInviteBulkArgs`,
`parseInviteCompanionArgs`), one per command, each producing its own branch of
`IssueInviteCodeInput` — mirrors `parseEventFields`/`validateEventCreateInput`'s split
between raw tokenizing and typed validation, kept as three functions rather than one
kind-branching function per §1's own "three commands, not one branching command"
resolution.

## 2. Refusal conditions and their exact check order (design question 3)

Traced against `apps/bot/src/domain/event.ts`'s existing helpers — no new predicate is
added; the requirement's refusal rule is expressed entirely as calls to
`getEventById` (already returns `status`) and `isFinished(endsAt, evaluationTime)`
(already exists, `event.ts:755-757`).

**Every one of the three issuing commands runs this exact sequence, in this exact
order, before any `invite_codes` row is created:**

1. **Resolve `<event_id>` via `getEventById`.** Not found → refuse
   (`invitePersonal.eventNotFound` / equivalent per command), no row created.
2. **Authorization (§3) — `requireOrganizerForChapter` against the event's own
   `chapterId`.** Not authorized → refuse (`notAuthorized`), no row created. Checked
   *before* the two refusal conditions below, matching every existing handler's ordering
   (`organizerRequests.ts` §6.1 step 4/§6.3 step 1: auth is checked immediately after the
   event is resolved, before any further business-rule check).
3. **Cancelled event: `event.status === "cancelled"`.** Refuse
   (`invitePersonal.eventCancelled`), no row created. `status` is already selected by
   `getEventById` — no new read.
4. **Finished event: `isFinished(event.endsAt, evaluationTime)`.** Refuse
   (`invitePersonal.eventFinished`), no row created. `evaluationTime` is the
   caller-supplied clock value (`decisions/0006` — never `new Date()` buried inside a
   domain function; the handler passes `new Date()` at the call site, same pattern
   `organizerRequests.ts` uses throughout).
5. **No `requires_invite`/`requires_approval` gate of any kind.** Explicitly NOT a
   refusal condition — restated per the handoff's instruction and STORY-DETAILS F4/
   DESIGN-REVIEW F9: issuing succeeds on an OPEN event exactly as it does on a gated one.
   Nothing in this design reads `requiresInvite` or `requiresApproval` at issuing time.
6. **Per-command argument validation** (§1's `IssueInviteCodeValidation`, and for
   PERSONAL/COMPANION, the target/host `users.id` existence check) — runs as part of
   parsing, reported as its own refusal (`missing`/`userNotFound`), independent of the
   event-state checks above; either order between "parse the command's own arguments"
   and "resolve+check the event" is acceptable since both must pass before a row is
   created, but this design fixes event-resolution-and-authorization-first (steps 1-2)
   since that is the existing codebase's uniform ordering (`organizerRequests.ts` never
   validates a reply's business content before re-running `requireOrganizerForChapter`).

**Why cancelled is checked before finished, not the reverse:** no requirement text states
an ordering preference between the two refusal reasons; this design picks
cancelled-then-finished because `status` is already in hand from `getEventById`'s same
result object (zero extra cost) while `isFinished` needs the extra `evaluationTime`
comparison — cheapest, already-available check first. This is a plumbing choice with no
behavioral consequence (both routes end in the identical "no row created" outcome) and is
named here rather than left for BACKEND-DEV to invent silently.

## 3. Authorization (S2)

Identical shape to `organizerRequests.ts`: `requireOrganizerForChapter(db, tgId,
event.chapterId)` called on **every** command handler (`/invite_personal`,
`/invite_bulk`, `/invite_companion`), immediately after the event is resolved (§2 step
2), before any row is written. `EventStaff` is not `organizer`/`owner` and is refused by
`checkOrganizerForChapter`'s existing `"not-organizer"` branch unchanged — no new
authorization logic. An organizer of chapter A naming a chapter B event is refused by the
existing `"wrong-chapter"` branch, same as every other event-mutation handler.

**Negative case this design must hold under** (S2's explicit instruction): a `member`
invoking any of the three commands directly is refused before any row exists; an
`EventStaff` member for the named event is likewise refused (staff carries no
`organizer`/`owner` role and gets exactly the `"not-organizer"` outcome); an organizer of
a different chapter than the event's is refused via `"wrong-chapter"`. All three cases
are provable against `requireOrganizerForChapter`'s existing, already-tested branches —
this design adds no new branch to that function.

## 4. Usage visibility — the redeemer-list query (design question 2, AC6/AC7)

**Resolution: a read-only JOIN against `registrations`, S3-safe field selection, no
write to `invite_codes` on read (design question 6).**

### 4.1 List view: codes issued for an event

`/invite_codes <event_id>` — same authorization (§3) and event-resolution ordering as
§2. Lists every `invite_codes` row for that event with its `usedCount`/`maxUses` and a
tappable row per code (mirrors `renderRequestsListMessage`'s one-row-per-item,
inline-keyboard-driven shape from `organizerRequests.ts`).

```
InviteCodeListItem = {
  inviteCodeId: string
  code: string             // the raw stored value, for display/copy
  shape: "personal" | "bulk" | "companion"   // derived label only, see §4.3 —
                                              // never a stored discriminator (REQ-033 §2)
  usedCount: number
  maxUses: number
  expiresAt: Date | null
}
```

Query: a plain `SELECT` on `invite_codes` filtered by `eventId`, ordered by
`createdAt` — no join needed for this list (every field it shows is a native
`invite_codes` column). This is the query design question 6 asks be confirmed read-only:
it is a `SELECT`, touches no other row, and in particular never issues an `UPDATE` to
`invite_codes.updated_at`.

### 4.2 Detail view: who used this code

Tapping a code (`invite:open:<inviteCodeId>` callback, same `entity:action:id` pattern
`organizerRequests.ts` uses for `req:open:<id>`) opens the redeemer list for that one
code.

```
InviteCodeRedeemer = {
  registrationId: string
  displayName: string      // deriveCheckinDisplayName(firstName, lastName, tgUsername,
                            // noNameFallback) — the SAME derivation table
                            // organizerRequests.ts/checkin.ts already use, not a new one
  company: string | null
}

InviteCodeDetail = {
  inviteCodeId: string
  code: string
  shape: "personal" | "bulk" | "companion"
  usedCount: number
  maxUses: number
  expiresAt: Date | null
  redeemers: InviteCodeRedeemer[]
}
```

**Query shape (AC7's exact requirement):**

```
SELECT registrations.id            AS registrationId,
       profiles.first_name         AS firstName,
       profiles.last_name          AS lastName,
       users.tg_username           AS tgUsername,
       profiles.company            AS company
FROM registrations
LEFT JOIN profiles ON profiles.user_id = registrations.user_id
INNER JOIN users    ON users.id = registrations.user_id
WHERE registrations.invite_code_id = <inviteCodeId>
ORDER BY registrations.created_at ASC
```

— structurally identical to `listPendingRequestsForOrganizer`'s own
select-then-map shape (`registration.ts:1597-1637`): a plain multi-table `SELECT`
followed by an in-memory `.map()` that calls `deriveCheckinDisplayName`. **No
`profiles.phone` and no `profiles.email` column ever appears in this select clause** —
the same structural exclusion `listPendingRequestsForOrganizer`/
`listAdmittedRegistrantsForCheckin` already rely on for S3, not a runtime filter that
could be bypassed. This satisfies AC6's "contains NO phone number and NO email" by
construction: the column is never selected, so it cannot leak through any downstream
formatting bug either.

**Why this is read-only (design question 6):** the query above is a `SELECT` against
`registrations`/`profiles`/`users`. It never issues an `UPDATE`/`INSERT`/`DELETE`
against `invite_codes`, so `invite_codes.updated_at` is untouched by reading this view —
AC7's "no write to the invite_codes row when reading redeemer list, confirmed by
comparing updated_at before/after" holds structurally, not by a discipline that could be
forgotten: there is no write statement in this query at all. `usedCount` itself is read
directly off the `invite_codes` row already fetched for the list view (§4.1); the
redeemer identities are read separately via the join above — the two are composed by the
handler into one `InviteCodeDetail`, not fetched by a single combined query, since
`usedCount` needs no join and forcing one would be a wasted `GROUP BY`.

### 4.3 Deriving the `shape` label (design element, not a stored value)

Restates REQ-033 §2's composition table as a **pure, columnless label function** — no
new column, just a display-time reading of the three existing fields:

| `issuedToUserId` | `grantsCompanionOf` | `maxUses` | `shape` label |
|---|---|---|---|
| non-null | null | (any) | `"personal"` |
| null | non-null | (any) | `"companion"` |
| null | null | `1` | `"personal"` (a personal code issued via a since-changed flow, or `max_uses=1` with no target — treated as the PERSONAL reading per REQ-033 §2's own table, since BULK is defined as `N > 1`) |
| null | null | `> 1` | `"bulk"` |

This table is a lookup the design specifies exactly (four exhaustive row patterns, no
ambiguity left to the implementer); BACKEND-DEV writes it as a single pure function with
no I/O, following `findDoorsAgendaItem`/`buildSeatsLine`'s existing precedent for a
small stated-table-as-function in this codebase — this design does not write that
function's body, only the table it must implement.

## 5. Shareable link — organizer-only, bot-never-sends (design question 4)

**Stated as a genuine design decision, not an implementation footnote**, per the
handoff's explicit instruction:

**Decision: the bot never sends the issued code or its deep link to the invitee (the
named `issuedToUserId`/`grantsCompanionOf` user). The organizer is shown both forms and
shares them personally (DM, email, in person, poster, etc.).**

**Reasoning:** Telegram's Bot API does not allow a bot to initiate a conversation with a
user who has never pressed Start on that bot (`sendMessage` to such a `chat_id` fails —
the bot has no open conversation to write into). A PERSONAL code's entire premise (§1.1)
is that it may be issued to a user whose `tgId` is null — i.e., a person who has,
structurally, never started the bot. There is therefore no Telegram delivery channel
available at the moment of issuing for exactly the case this requirement's own AC3
requires to work. This is a platform constraint the design must accept, not a product
choice to route around (e.g., by queuing the send until the user later starts the bot) —
no requirement text describes such a queued-send mechanism, and inventing one here would
be exactly the kind of unrequested behavior the pipeline's scope discipline forbids.

**What the design specifies instead:**

- Both commands' success reply to the organizer shows: the bare `code` value (for typing
  — story B7) and the full deep link `https://t.me/<bot_username>?start=i_<code>` (for
  sharing — the `i_` prefix per PRD 8, parsed by REQ-038's redemption handler, not this
  requirement's scope to parse).
- `<bot_username>` is already resolved once at process start (`index.ts:140`,
  `bot.botInfo.username`) and passed to handlers exactly as `handlers/event.ts`'s T-3h
  QR-code job already does for its own deep links — reused, not re-fetched.
- The reply text states, in the organizer's own language, that the organizer is
  responsible for sending this link/code to the invitee themselves (content shape,
  §7 below) — making the platform constraint visible to the organizer rather than
  silent.
- **`git grep` verifiable negative (AC9):** no call site in this requirement's handler
  file sends a message to `issuedToUserId`/`grantsCompanionOf`'s `tgId` at issuing time —
  the only `ctx.reply`/`sender.send`-shaped call in the issuing flow targets the acting
  organizer (the same chat the command was issued from), never a second recipient.

## 6. Audit logging (S8)

**Exactly one `AuditLog` row per successful issue**, written inside the same transaction
as the `invite_codes` insert — same "insert + `writeAuditLog` in one `db.transaction`"
shape `createEvent`/`publishEvent`/`cancelEvent` already use (`event.ts:559-605`,
`639-659`, `666-686`).

```
action: "invite_code.issue"
entity: "invite_code"
entityId: <the new invite_codes row's id>
actorUserId: <the issuing organizer's users.id, from requireOrganizerForChapter's result>
payload: { eventId, shape: "personal" | "bulk" | "companion", maxUses,
           issuedToUserId: string | null, grantsCompanionOf: string | null }
at: <evaluation time supplied by the handler, decisions/0006>
```

No phone/email in the payload (S11) — the payload above carries only ids and the
issuing parameters, never a resolved name/company/phone/email. On any refusal (§2), the
transaction never opens and no `AuditLog` row is written — matching S8's "never on a
refusal" discipline every existing mutation function in this codebase already follows.

One domain function per command (`issuePersonalInviteCode`, `issueBulkInviteCode`,
`issueCompanionInviteCode`), each performing exactly one `invite_codes` INSERT plus
exactly one `writeAuditLog` call in one transaction — mirrors `createEvent`'s shape,
kept as three functions rather than one branching function for the same reason §1
gives for the command layer (the three shapes have different required inputs).

## 10. Open questions (not silently resolved)

1. **Command naming for the three sub-commands** (`invite_personal`/`invite_bulk`/
   `invite_companion` vs. some other verb choice) follows this codebase's existing
   `<entity>_<verb>` convention but the exact verb words are BACKEND-DEV's/
   CONTENT-BA's to finalize alongside the catalog copy in §7 — not a behavioral question,
   a naming one.
2. **`(event_id, issued_to_user_id)` re-issuance** (REQ-033 §6 point 4: whether issuing a
   second personal code to the same person for the same event should revoke/expire the
   first, or simply coexist) is **not resolved by this design** — no stated requirement
   text asks for revocation, and REQ-033 explicitly left this open. This design's
   `/invite_personal` performs a plain INSERT with no existence check against prior codes
   for the same `(event_id, issued_to_user_id)` pair; multiple personal codes for the same
   person on the same event will coexist, each independently usable up to its own
   `maxUses`. If this turns out to be unwanted, it is a new acceptance criterion for a
   future requirement, not an invented constraint here.
3. **Exact grouping/formatting of the 26-character code in the success reply** (REQ-033
   §4's "hyphens or spacing... a presentation-layer concern for whichever requirement
   renders the code") is not fixed by this design beyond stating that `issuedReply` (§7)
   shows the raw `code` value; whether it is chunked (e.g. `XXXX-XXXX-...`) for
   readability is a CONTENT-BA/BACKEND-DEV copy decision with no behavioral consequence,
   left open per REQ-033's own note.
4. **Whether `/invite_codes` (the list command) should also expose issuing shortcuts
   inline** (e.g. a "issue new code" button on the list view) is not requested by any
   acceptance criterion in scope and is not added — flagged so a future requirement does
   not have to reverse-engineer why it is absent.
