**Requirement:** third slice of PRD 14 build-order step 3, USER-STORIES/STORY-DETAILS
B3 ("Join the waitlist when it's full"), PRD FR-6's waitlist half, PRD 13 acceptance
criterion 3. depends_on: REQ-020.

**Surface:** `apps/bot/**` (bot requirement).

**No schema change.** Checked `apps/bot/src/db/schema.ts` line-by-line: `registrations`
already has every column this design reads (`event_id`, `admission`, `created_at`, `id`)
and already carries `registrations_waitlist_order_idx` — a partial index on
`(event_id, created_at) WHERE admission = 'waitlisted'`, whose own header comment in the
schema file (line ~288) states it exists specifically "for the waitlist-ranking query
(REQ-011.md §4)." That index was built in anticipation of exactly this requirement and
needs no change. No new column, table, enum value, or index is proposed anywhere in this
document — **`DATA-DESIGNER` is not dispatched for this run**, same precedent as
REQ-017/REQ-020 (confirmed explicitly in §7).

**Files this design expects:**
- `apps/bot/src/domain/registration.ts` (existing, REQ-020) — gains one new exported
  function, `getWaitlistPosition` (§2). No existing export in this file changes shape.
- `apps/bot/src/handlers/registration.ts` (existing, REQ-020) — the `waitlisted` branch
  of `composeRegistrationReply` gains a position line and a "what happens next" line
  (§3); the handler's own body gains one additional read call.
- `apps/bot/src/i18n/types.ts`, `ru.ts`, `en.ts` — two new keys under the existing
  `Catalog.registration` object (§4).

Nothing else changes. `decideRegistrationOutcome` and `registerForEvent`
(`domain/registration.ts`, REQ-020) are **reused completely unchanged** — this

## 0. Resolving the AC2/REQ-022 scoping issue (stated explicitly, not silently)

AC2's own text says: *"With three waitlisted people, withdrawing the first one causes
the second person's displayed position to change from 2 to 1 on their NEXT READ with no
write to their registrations row."* "Withdrawing" names a state transition
(`admission: 'waitlisted' → 'withdrawn'`) that today has no producing feature —
`REQ-022` ("Withdraw from a registration and free the seat") is not yet built, and per
`docs/agents/requirements.yaml` it `depends_on: [REQ-021]`, i.e. it comes *after* this
one, not before.

**Chosen resolution: option (b) — design the position query to be provably correct by
construction, and let AC2 be verified by directly manipulating the `admission` column
via test SQL rather than needing a real withdraw feature.**

Reasoning:

1. **The property AC2 actually tests is a property of the query, not of withdrawal.**
   Read the AC's own wording again: the observable claim is "no write to the *second*
   person's row, yet their displayed position changes." Nothing about that claim depends
   on *how* the first person's row stopped being `'waitlisted'` — it only depends on
   `getWaitlistPosition` (§2) re-deriving its answer from the live value of
   `registrations.admission` on every call, with no cached or stored intermediate. The
   query design in §2 is stated precisely enough (an exact `WHERE`/tie-break rule) that
   its correctness does not depend on which code path flipped the first row's
   `admission` value — a direct SQL `UPDATE registrations SET admission = 'withdrawn'
   WHERE id = ...` in a test exercises exactly the same code path (`getWaitlistPosition`
   re-reading `registrations`) as a real withdraw feature would, because that function
   takes no input describing *why* a row is no longer `'waitlisted'` — only that it
   isn't.
2. **Building an internal-only withdraw primitive (option (a)) risks inventing behavior
   REQ-022 hasn't designed yet.** REQ-022's own scope note (`requirements.yaml`) already
   states it must confirm-first (destructive-action gate, PRD 8), free the seat
   immediately for an admitted registration, and kill future notifications — a real
   feature surface with its own audit-log action, its own confirmation UX, and its own
   interaction with REQ-023's auto-promotion trigger. A "minimal internal-only" version
   built here would either (a) duplicate a subset of that surface, creating two places
   that can set `admission = 'withdrawn'` with different side effects (audit log written
   once here, differently there), or (b) be so stripped down (a bare `UPDATE` with no
   audit trail) that it doesn't resemble what REQ-022 will actually build — either way it
   is scope invention this role is supposed to flag, not silently produce (per
   `.claude/agents/code-designer.md`'s "don't silently resolve an ambiguity" rule).
3. **This mirrors an already-accepted precedent in this exact pipeline.**
   `docs/agents/design/REQ-019.md` §8's open question 3 hit the identical shape of
   problem — an AC's own stated verification method (running the live registration flow)
   couldn't literally execute because REQ-020 didn't exist yet — and resolved it by
   naming an interim substitute verification method rather than building a stand-in
   version of the missing feature. Option (b) here is the same move: name the substitute
   test action (a direct SQL state flip) precisely enough that `TEST-DESIGNER` can write
   a runnable case, without this design inventing withdraw-shaped product behavior.

**Concretely, for `TEST-DESIGNER`:** AC2's verification case should (1) create three
`registrations` rows for one at-capacity event with `admission = 'waitlisted'` and
strictly increasing `created_at` values, (2) read the *second* row's position via
`getWaitlistPosition` and confirm it is `2`, (3) directly `UPDATE` the *first* row's
`admission` to any non-`'waitlisted'` value (`'withdrawn'` reads most naturally, but
`'admitted'` or `'rejected'` exercise exactly the same query path and are equally valid
substitutes) via a raw test-fixture SQL statement — **not** via any application-level
function, since none exists yet — (4) capture the second row's `updated_at` before and
after step 3, asserting it is byte-for-byte unchanged, (5) call `getWaitlistPosition`
for the second row again and confirm it now reads `1`. This is a real, literal,
runnable test today; it needs nothing from REQ-022.

## 2. The position-computation query (AC1, AC2, AC3)

### 2.1 Signature

```
export async function getWaitlistPosition(
  db: DbClient["db"],
  eventId: string,
  registrationId: string,
): Promise<number | null>;
```

### 2.2 The rule, stated in prose (never as executable branching)

1. Read the target row's own `created_at` and `admission` from `registrations` by
   `id = registrationId` (a single `SELECT ... LIMIT 1`). If no row is found (defensive
   — the row was just inserted by the caller in the common path, so this is unreachable
   in practice, same discipline as REQ-020's `insertedRow === undefined` guard): the
   function's result is `null`.
2. If the found row's `admission` is anything other than `'waitlisted'` (defensive — by
   the time this function is called the row could in principle have already moved on,
   e.g. a future auto-promotion race; no requirement in scope actually produces this
   today, but the function does not assume it can't happen): the function's result is
   `null`. A position is only ever a meaningful answer for a row that is currently
   waitlisted.
3. Otherwise, count the rows in `registrations` where `event_id` equals the given
   `eventId`, `admission` equals `'waitlisted'`, and the row is **strictly ahead** of the
   target row in waitlist order — "ahead" meaning: `created_at` is earlier than the
   target row's `created_at`, OR `created_at` is exactly equal to the target row's
   `created_at` AND that row's `id` is less than the target row's `id` (the tie-break,
   §2.3). This is one `SELECT count(*)`-shaped query, filtered by `event_id`, `admission`,
   and the ahead-of condition above — no join, no subquery beyond the one already-read
   `created_at`/`id` pair from step 1.
4. The function's result is that count **plus one** (a 1-based position — the person
   with nobody ahead of them is position 1, never position 0).

This is the same relationship a `ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY
created_at ASC, id ASC)` window, restricted to `admission = 'waitlisted'` rows and
evaluated for one specific row, would produce — expressed here as a plain count-ahead
query instead of a window function because Drizzle's query-builder surface expresses
`eq`/`lt`/`and`/`or` filters directly and typedly (`db.select({ count: ... }).from(
registrations).where(and(eq(...), eq(...), or(lt(...), and(eq(...), lt(...)))))`,
composed from the same builder methods REQ-020's design already relies on), matching
this codebase's established "no raw SQL escape hatch" discipline (REQ-020 §1.2, restated
here rather than reintroduced as a fresh choice). The existing partial index
`registrations_waitlist_order_idx` on `(event_id, created_at) WHERE admission =
'waitlisted'` directly supports this filter shape — an index built, per its own schema
comment, for exactly this query.

### 2.3 The tie-break, named explicitly

Two waitlisted rows for the same event sharing an identical `created_at` is a genuine
edge case at Postgres's `timestamptz` precision (microseconds), not an expected
occurrence — but nothing in the requirement or PRD states what should happen if it did,
so this design states its own fixed answer rather than leaving `BACKEND-DEV` to invent
one ad hoc: whichever row has the lower `id` is treated as "ahead." `id` is a `uuid`
primary key with no ordering meaning of its own beyond "some fixed value," so this
tie-break carries no semantic claim (it does not mean "created first" or "requested
first") — it exists only to make the ranking a **total order**, so that the same set of
waitlisted rows always yields the same positions on repeated reads, per §2.4.

### 2.4 Why this satisfies "computed, never stored, recomputed at every read" (PRD 5, PRD 13 criterion 8, AC2, AC3)

`getWaitlistPosition` performs its `SELECT count(*)` fresh, from the current state of
the `registrations` table, on every single call — there is no parameter, return value,
or side effect anywhere in this design that carries a position value from one call to
the next. No interface in this codebase (`RegistrationOutcome`, `RegisterForEventResult`,
`EventRecord`, or any new type introduced here) gains a `position` or `rank` field —
the *only* place a position value ever exists is as this function's own return value, for
the duration of the one request handling it. This is what makes AC2's "no write to the
second row, but a changed displayed value" true by construction: the second row's own
columns are never involved in producing *anyone's* position (only its `created_at`/`id`
are read, never written), and the *first* row leaving `'waitlisted'` (by whatever means)
changes what step 3's `WHERE admission = 'waitlisted'` filter matches on the very next
call — automatically, with no renumbering step, no migration, no batch job. There is
exactly one function in this codebase capable of producing a waitlist position
(`getWaitlistPosition` itself), so AC3's `git grep` (for any column/cache/persisted
field) has nothing to find: the position is a query expression over `created_at` (and,
for the tie-break, `id`), never a stored value anywhere.

## 3. Wiring into the confirmation message (AC1)

### 3.1 Handler change — `apps/bot/src/handlers/registration.ts`

`makeRegisterCallbackHandler`'s existing body (REQ-020) already produces an `outcome`
whose `registrationId` is populated for `kind === "waitlisted"` (REQ-020 §3.2 step 8g,
unconditional — unchanged). This design adds, only inside the existing `if (outcome.kind
=== "admitted" || outcome.kind === "waitlisted" || outcome.kind === "already-registered")`
block that already fetches display data (REQ-020's `eventTitle`/`dateTimeText` fetch):
when `outcome.kind === "waitlisted"`, one additional call, `await getWaitlistPosition(db,
eventId, outcome.registrationId)`, whose result (`number | null`) is threaded into
`composeRegistrationReply` as a new parameter, `waitlistPosition`.

If that call's result is `null` (§2.2 step 1/2's defensive cases): the reply is composed
exactly as if the parameter were simply not shown — no "position: unknown" placeholder
text, no error surfaced to the user (see §6 open question 3 for why this specific choice
is flagged rather than asserted as obviously correct).

### 3.2 `composeRegistrationReply`'s `waitlisted` case, extended

Today (REQ-020): `[catalog.registration.waitlistedPrefix, eventTitle, dateTimeText]
.join("\n")`.

This design's replacement, stated as an ordered content list (not code): when
`waitlistPosition` is a number, the joined lines are — `waitlistedPrefix`, `eventTitle`,
`dateTimeText`, a position line built from `waitlistedPositionPrefix` followed by the
numeric position (same "prefix string + interpolated value" convention
`handlers/event.ts` already uses throughout, e.g. `capacityBelowAdmittedFloor`), then
`waitlistedWhatNext` (§4). When `waitlistPosition` is `null`, the position line is
omitted entirely and the other four lines are unchanged.

## 5. AC4 — unbounded waitlist (no new design element; a proof of absence)

AC4 asks that the waitlist accept an unbounded number of registrations — at least 5
waitlisted past capacity, no refusal. This is already true of `decideRegistrationOutcome`
(REQ-020 §2.2, unchanged): row 8, the `waitlisted` outcome, is the unconditional
fallback reached whenever none of rows 1–7 matched — there is no row anywhere in that
table, and no code added anywhere by this design, that counts existing `waitlisted` rows
against any ceiling before producing another one. `getWaitlistPosition` (§2) is a
**read-only** function called only after a waitlisted row has already been written — it
participates in no capacity or admission decision, so it cannot itself introduce a cap.
This AC is verified by constructing the scenario (register 5+ people past capacity) and
observing zero refusals — there is no new design element to point to beyond "this
design adds no capacity check anywhere," stated explicitly here rather than left
implicit.

## 6. Open questions (not silently resolved)

1. **AC2/REQ-022 scoping — resolved at §0 as option (b).** Restated here for
   completeness: this design does not build any withdraw primitive, real or internal-only;
   AC2 is verified by a direct SQL state flip in the test fixture, named precisely in §0's
   closing paragraph for `TEST-DESIGNER`.
2. **`waitlistedWhatNext`'s exact wording risks overpromising a mechanism
   (auto-promotion) that REQ-023 has not yet built.** This design does not draft the
   literal copy (per `.claude/agents/code-designer.md`'s scope — content wording is
   `CONTENT-BA`'s call), but flags that the safest placeholder avoids a specific
   guarantee ("you'll move up automatically as seats open" is safer than "we'll notify
   you within X minutes," since no requirement in scope states a timing bound).
3. **Whether a `null` position (§2.2's defensive cases, §3.1) should render any fallback
   text at all, versus silently omitting the line.** This design chooses silent omission
   (§3.1) reasoning that inventing an error-shaped message for a case no current
   requirement can actually produce is scope beyond what was asked — but this is a
   judgment call, not a certainty, and is named here rather than asserted as the only
   correct choice.
4. **The tie-break rule (§2.3) is this design's own arbitrary but explicit choice** —
   nothing in the requirement or PRD states what should happen when two waitlisted rows
   share an identical `created_at`; `id` ascending is stated so `BACKEND-DEV` does not
   need to invent one, not because it is provably the only correct choice.
