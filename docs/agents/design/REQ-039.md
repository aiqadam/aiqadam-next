## 1. Design question 4 — schema change

**Answered: none.** `invited_by_user_id` is a nullable `uuid` FK to `users.id`
(`onDelete: "restrict"`), already present on `registrations` before this requirement.
This design's own `git grep`-checkable acceptance criterion (issue AC2) is satisfied by
construction: nothing in §2–§6 below adds a column, a table, or a second attribution
field. The companion mechanic and referral attribution are the same write
(`invited_by_user_id = grantsCompanionOf`), exactly as DESIGN-REVIEW F10 requires.

## 2. Design question 2 — where a companion code is distinguished from personal/bulk

**Distinguishing point:** inside `handlers/start.ts`'s `resolveInviteDeepLink`, **after**
the existing consent gate (`hasConsented` check, unchanged position) and **before** the
existing unconditional call to `redeemInviteCode`.

Current shape (REQ-038, unchanged lines 195-210 of `resolveInviteDeepLink`):

```
if (!hasConsented) { show consent prompt, encode payload, STOP }
→ outcome = await redeemInviteCode(...)   // unconditional today
```

New shape — one lookup and one branch inserted between those two steps:

```
if (!hasConsented) { show consent prompt, encode payload, STOP }        // unchanged
codeRow = await getInviteCodeByCode(db, normalizeInviteCode(code))       // read-only,
                                                                           // no PII,
                                                                           // already an
                                                                           // exported
                                                                           // function
if (codeRow !== null && codeRow.grantsCompanionOf !== null
    && <no existing registration for this event/user — see Open Question 2>) {
  → route to the companion field-collection flow (§4), NOT redeemInviteCode directly
} else {
  → outcome = await redeemInviteCode(...)   // REQ-038's unchanged path — includes
                                              // personal codes, bulk codes, AND a
                                              // companion code redeemed by someone who
                                              // already completed the reduced form on
                                              // an earlier attempt (§5's idempotent
                                              // profile check)
}
```

`getInviteCodeByCode` is the exact function `redeemInviteCode` itself already calls at
its own step 2 — this is the same read, reused, not a new query shape. Reading it one
step earlier (in the handler, before the transaction) writes nothing and discloses
nothing beyond what any caller possessing the exact code string already could via the
five-check table's own distinct refusal messages (REQ-038 §3.2's info-leakage
resolution, unchanged reasoning applies here since this is a read, not a new leak
surface).

**Why the branch sits here and not inside `redeemInviteCode`:** `redeemInviteCode` is a
pure transactional decision function reused by BOTH the `i_<code>` deep link and the
typed `/redeem` command (`handlers/registration.ts`). Whether to run the reduced-field
collection UI is a **handler-level, conversational** concern (asking questions, showing
a confirm message, waiting for a reply) — exactly the same division of labor
`resolveEventDeepLink`/`resolveInviteDeepLink` already draw between "handler sequences
replies" and "domain function performs the one write." `redeemInviteCode` itself is
still extended (§5) to accept and persist the already-collected fields, but it does not
decide whether to collect them.

## 3. Design question 1 — collecting name/phone/company before consent, write only after consent + confirm

**Resolution: reuse REQ-030's message-text-carrier mechanism, single combined
consent+confirm tap, no DB draft row of any kind.** Concretely:

### 3.1 Ordering (the security-critical property)

1. Guest opens the `i_<code>` deep link. `makeStartHandler` runs its existing,
   unconditional `resolveOrCreateUser` (bare `tgId`/`tgUsername`/`lang` row — no PII,
   no consent-gated field, pre-existing platform behavior unchanged by this
   requirement, identical for every `/start` including REQ-038's own personal/bulk
   redemption path).
2. `payload.kind === "invite"` → `resolveInviteDeepLink` runs. `hasConsented` is false
   for a guest the bot has never seen (`flowUser.consentPdAt === null`). The **existing,
   unmodified** consent prompt (`consent.prompt` / `buildConsentKeyboard`) is shown —
   the same generic "Store my data" prompt every other flow uses, not a
   companion-specific one. This is "the consent step" AC3 refers to. **Nothing about
   this specific companion code has been read or acted on yet** — the handler does not
   even know it is a companion code at this point (§2's lookup runs later, after
   `hasConsented` is confirmed true).
3. Guest abandons here (never taps "I agree") → per AC3, zero new `users`/`profiles`/
   `registrations` rows exist beyond the bare `users` row from step 1 — that row is
   pre-existing platform behavior, not a write this requirement introduces, and it
   carries no PII the guest has not already implicitly exposed by opening Telegram
   (their own `tg_id`).
4. Guest taps "I agree" → `consent:agree` callback fires → `recordConsent` sets
   `consent_pd_at` (unchanged mechanism) → the deferred deep-link payload resumes with
   `hasConsented: true` → **now**, and only now, §2's lookup runs and the companion
   branch is taken.
5. The companion field-collection conversation (§3.2) begins. **No DB write of any
   kind happens during this conversation** — see §3.2's carrier mechanism. If the guest
   abandons anywhere in this conversation, zero `profiles`/`registrations` rows exist
   (a `users` row already exists from step 1/consent, unchanged from step 3 — consent
   itself is a legitimate, already-given write at this point, not a violation).
6. The conversation ends with one combined "Confirm & register" tap that is the single
   write trigger (§3.3): Profile row + Registration row (`invited_by_user_id` set) +
   `invite_codes.used_count` increment + one `AuditLog` row, all in the **existing**
   `redeemInviteCode` transaction, extended per §5.

### 3.2 Field collection — the carrier

Reuses `domain/walkin.ts`'s proven shape (`parseWalkinMessageFields` /
`formatWalkinConfirmMessage`), adapted from "one organizer-typed command line" to "one
guest-typed reply," for the reason given in §3.3:

- The bot sends one prompt asking for all three fields in a single reply, using the
  same `|`-delimited convention `parseWalkinArgs`'s remainder-parsing already
  establishes (`Name | Company | Phone`, company segment may be blank).
- The guest's plain-text reply is parsed with a **new, structurally identical** sibling
  to `parseWalkinMessageFields`/`validateWalkinFields` — same three-segment split, same
  `isNonBlank` check on name and phone, company optional. Placed in `domain/walkin.ts`
  alongside the existing functions it mirrors (a rename/relocate of nothing existing;
  new pure functions only), or exported from `domain/inviteCode.ts` if CODE-DESIGN-VALIDATOR
  or BACKEND-DEV judges the invite-code module the more natural home — **left as Open
  Question 3**, since both placements are equally correct and the requirement does not
  say which.
- On a parse/validation failure, the bot re-prompts (same message, no write) — no
  different from `parseWalkinArgs`'s existing usage-error branch.
- On success, the bot renders the **confirm message** — the same
  `formatWalkinConfirmMessage` shape (canonical `Name:`/`Company:`/`Phone:` lines,
  followed by the consent-adjacent copy) with one inline button. **No DB write yet.**
  This message's own text is the state carrier for the next step — nothing is held in
  memory or in a DB row between this reply and the button tap.

### 3.3 Why this reuses REQ-030's mechanism rather than REQ-019's write-as-you-go

REQ-019's `advanceOnboarding`/`determineNextProfileField` pattern writes each answered
field into a **real, partially-filled `profiles` row** as soon as it is answered,
resuming later sessions from wherever the row was left. That is safe there because (a)
consent already precedes the very first question by construction, and (b) the person is
building their **own, ongoing** account — an incomplete row sitting in the database
between sessions is exactly the intended, reviewed behavior.

REQ-039's guest is not doing that. They are a stranger completing a **single,
self-contained** action (redeem this one companion code) who may never interact with
the bot again either way. Two things follow, and both are why this design uses the
message-carrier pattern instead:

1. **No half-registered stranger.** If field-by-field writes were used and the guest
   answered "name" then closed the chat, a Profile row for them would sit in the
   database attached to no completed registration and no confirmed consent to that
   specific companion registration — exactly the "partial-form draft" AC3 and the
   issue text both name as the failure mode, even though `consent_pd_at` is technically
   already true by that point. The message-carrier pattern makes this structurally
   impossible: there is nothing to have "half-written," because nothing is written
   until the single final tap.
2. **One atomic unit, matching AC1's own shape.** AC1 requires the registration row to
   carry `invited_by_user_id` and `invite_code_id` together, in the same row, from the
   moment it is created. Building the Profile row incrementally and the Registration
   row separately (as REQ-019's pattern would, since it has no registration-writing
   step at all) would require reconciling two independently-timed writes; the
   message-carrier + single-transaction approach (§5) makes them one write by
   construction, the same discipline `redeemInviteCode` already uses for the
   registration+`used_count`+`AuditLog` triple.

This distinction is stated here explicitly per this run's brief, precisely so
BACKEND-DEV does not import `advanceOnboarding`/`determineNextProfileField` or add a
"pending companion fields" column to `users`/`profiles` by analogy to REQ-019.

## 4. The confirm tap — what it does

The confirm message's inline button is a **fixed** `callback_data` (e.g.
`companion_confirm:<inviteCodeId>` or reuse of the existing `consent:agree` pattern with
a new payload prefix — the exact string is an Open Question, §Open Questions below,
since it is a naming/wiring detail with no behavioral consequence CODE-DESIGNER should
guess at). It carries **no field values** — the carrier is the message text (§3.2), not
the callback payload, exactly like REQ-030's own `invite:open:<id>`-style callbacks
carry only an id, never PII, in `callback_data`.

The callback handler:

1. Re-parses the tapped message's own text with the new `parseCompanion...Fields`
   function (§3.2) to recover `name`/`company`/`phone`. A message whose text no longer
   parses (edited, or a stale/forwarded tap) is refused with no write — same discipline
   `parseWalkinMessageFields`'s `{ ok: false }` branch already establishes.
2. Calls the extended `redeemInviteCode` (§5) with those three fields.
3. Sends the guest their own result via the **unchanged** `composeRegistrationReply`
   (§0 table) — identical to REQ-038's existing reply for every other outcome kind
   (`admitted`/`waitlisted`/`requested`/every refusal). No new outcome kind is
   introduced by this requirement — a companion code's five-check refusals render
   exactly like a personal code's.
4. On an admitting/waitlisting/requesting outcome (i.e. a registration row was
   actually created — mirrors `redeemInviteCode`'s own existing "writing outcomes"
   set), sends the host their notification (§6).

## 5. `redeemInviteCode` — the extension

**Not a parallel function.** Three additions to the existing function
(`apps/bot/src/domain/inviteCode.ts`), each a minimal, backward-compatible delta:

1. **New optional parameter**, added after the existing `evaluationTime: Date`:
   `companionProfile: { name: string; company: string; phone: string } | null`. Every
   existing caller (the typed `/redeem` command, REQ-038's own non-companion deep-link
   path) passes `null` — zero behavior change for them.
2. **Locked `codeRows` SELECT (step 5, unchanged position) gains one column**:
   `grantsCompanionOf: inviteCodes.grantsCompanionOf`, alongside the five columns
   already selected there. This is the field this requirement's whole attribution
   mechanic reads — read from the **locked** row (not the earlier unlocked `precheck`),
   matching this function's own existing "never trust the pre-tx read for the actual
   decision" discipline stated in its header comment.
3. **The registrations insert/update (step 10, unchanged position) gains one field**:
   `invitedByUserId: codeRow.grantsCompanionOf`. For a personal or bulk code
   `grantsCompanionOf` is always `null` (per REQ-033/REQ-037's issuing functions,
   `issuePersonalInviteCode`/`issueBulkInviteCode` both hard-code `grantsCompanionOf:
   null`), so this is a no-op for every existing, already-shipped call site — **AC1 is
   satisfied by this one field, with zero new branching in the decision logic** (no new
   `if`, no new outcome kind, no touch to `validateInviteCodeForRedemption` or
   `decideRegistrationOutcome` at all).
4. **When `companionProfile !== null`**, immediately before the registrations
   insert/update within the SAME transaction: reuse `createWalkinProfile`'s exact input
   shape (`{ userId: redeemerUserId, name: companionProfile.name, company:
   companionProfile.company, phone: companionProfile.phone }`) to insert the Profile
   row. This is `domain/profile.ts`'s existing function, called from a second call
   site — not a new function, not a new field mapping. See Open Question 1 for the one
   case this does not by itself cover (an existing Profile row for this guest).

Every other line of `redeemInviteCode` — the five-check validation call, the seats/
capacity read, `decideRegistrationOutcome`, the `used_count` increment, the single
`AuditLog` write — is **untouched**. This directly satisfies design questions 5 and 6:

- **Capacity/waitlist (question 5):** `decideRegistrationOutcome` is called with the
  same `seatsLeft`/`inviteSatisfied: true` shape REQ-038 already uses for every code
  kind. A companion code redeemed against a full event produces `outcome.kind ===
  "waitlisted"` through the exact same branch a personal/bulk code would — no
  companion-specific capacity path exists anywhere in this design.
- **One-use enforcement (question 6):** unchanged `validateInviteCodeForRedemption`'s
  `usedCount >= maxUses` row. A companion code's `maxUses` is set once, at issue time,
  by REQ-037's `issueCompanionInviteCode` (already shipped, defaults to `1`,
  organizer-overridable via that command's existing parameters) — this requirement
  reads that value, never writes it, never adds a second check.

## 6. Design question 3 — host notification

**New `NotificationKind`: `"companion_registered"`.** Added to the closed union in
`domain/notification.ts` (currently ending `"registration_auto_declined"`) — a
one-line addition, same convention the file's own comments describe for future
extensions (`notification_ledger.kind` is `text`, no migration).

Sent from the companion confirm-callback handler (§4 step 4), modeled directly on
`handlers/organizerRequests.ts`'s `sendApprovalNotification`/`sendRejectionNotification`
pair (§0 table):

```
sendLedgeredNotification({
  db, sender,
  registrationId: <the guest's newly-created registration id>,
  kind: "companion_registered",
  classification: "transactional",   // PRD 9 / S10 — always sent, ignores broadcast_opt_in
  userId: <hostUserId — i.e. the code's grantsCompanionOf value>,
  composeMessage: (lang) => {
    // catalog text carrying exactly two data values: the guest's display name and
    // company. Mirrors sendApprovalNotification's own "look up display data, compose,
    // return { kind: "text", text }" shape.
  },
})
```

**Content — S3-bounded, exactly per the issue's own instruction:** the composed text
carries the guest's **name and company only**. It structurally cannot carry phone or
email, because the `composeMessage` closure for this kind never reads `profiles.phone`
or `profiles.email` at all — the same "never a runtime filter that could be bypassed"
discipline `listInviteCodeRedeemers`'s comment already states for the identical S3
concern (its SELECT clause structurally excludes those two columns). AC7/S11 are
satisfied the same way: the composing function has no code path that touches the phone
value, so it cannot appear in the sent text, a log line, or (since
`sendLedgeredNotification`'s own ledger INSERT carries no `payload` column at all —
confirmed by re-reading `domain/notification.ts`: the `notificationLedger.values` call
inserts only `registrationId`/`kind`) an audit payload either.

**Idempotency:** `(registrationId, kind)` — the guest's registration id, `kind:
"companion_registered"` — the same unique-index mechanism every other kind already
relies on (§0 table). A retry of the confirm tap (e.g. a double-tap) cannot double-send
to the host, mirroring S9 unchanged.

**Guest's own message:** unchanged — the direct, synchronous
`composeRegistrationReply` reply (§4 step 3), the same mechanism REQ-038 already uses
for every redemption outcome, not a ledgered send. This satisfies "the guest gets their
own admission result" without inventing a second notification path for someone who is,
at that moment, actively in the chat.

## Open questions (not silently resolved)

1. **A companion guest who already has a Profile row** (a returning bot user, already
   onboarded via REQ-019, redeeming a companion code for a different event). `profiles`
   has a unique index on `user_id` (`profiles_user_id_unique`) — a second
   `createWalkinProfile`-shaped INSERT for this user would violate it. The requirement
   text does not address this case. Two directions are equally defensible and neither
   is chosen here: (a) skip the reduced-field conversation entirely when a Profile
   already exists and redeem immediately (treating this as "close enough" to a normal
   REQ-038 redemption, just with `invited_by_user_id` set), or (b) still show the
   fields (pre-filled from the existing profile?) and perform an UPDATE instead of an
   INSERT on confirm. This must be resolved before BACKEND-DEV can implement §5 point 4
   for this branch.
2. **Re-redemption by the same already-registered guest.** If the guest taps "Confirm &
   register" twice (network retry, double-tap), the second call reaches
   `redeemInviteCode` with an existing registration for `(eventId, redeemerUserId)` —
   the existing `existingAdmission`/`existingRegistrationId` logic (unchanged, §5)
   already handles this the same way REQ-038 always has. Not a new case, noted only for
   completeness — no open question here, listed to distinguish it from #1.
3. **Exact placement of the new parse/validate/format functions** (§3.2) —
   `domain/walkin.ts` (co-located with the pattern they mirror) vs. `domain/inviteCode.ts`
   (co-located with the feature they serve). Either is structurally correct; not
   resolved here.
4. **Exact `callback_data` string / prefix for the confirm button** (§4) and the exact
   catalog copy for the field-collection prompt, the confirm message's trailing
   copy, and the host notification text — content/wiring details with no behavioral
   consequence, left for BACKEND-DEV/CONTENT-BA, not invented here.
5. **Whether the companion's short-form prompt states the event title/host name** (so
   the guest knows what they're agreeing to attend and whose invitation this is) — the
   requirement's "Conversation" reference (USER-STORIES B8) is not available in this
   repository to check verbatim; the design assumes yes (the confirm message can carry
   an `Event:` line the same way `formatWalkinConfirmMessage` already does) but the
   exact copy is not specified here.
