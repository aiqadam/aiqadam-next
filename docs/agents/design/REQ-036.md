## 0. Reuse decisions, stated up front

### 0.1 Scheduling mechanism — the existing runner, unchanged

Both jobs are `ScheduledJobDefinition` values (`scheduler/runner.ts`, unchanged interface)
passed into the SAME `startScheduledJobs([...])` array `apps/bot/src/index.ts` already
builds for the reminder/feedback/no-show jobs. No new scheduling primitive, no new
dependency (decisions/0004, PRD 1's "do not add infrastructure").

### 0.2 Notification delivery — both new sends reuse `sendLedgeredNotification` completely unchanged

Both the urgency notice and the auto-decline notice are single-recipient sends: the
urgency notice's recipient is one organizer (§2.2's deterministic choice), the
auto-decline notice's recipient is the registrant. Neither needs a new send primitive,
a fan-out helper, or any change to `domain/notification.ts` beyond the two new
`NotificationKind` literals (§1) — the same "one-line addition, not a migration" pattern
REQ-026/031/032 already used for their own new kinds (`notification_ledger.kind` is
`text`).

This is a deliberate design choice over a "notify every organizer of the chapter"
fan-out, traced in §2.2.

### 0.3 Both sends go through the ledger; the auto-decline's state write is a SEPARATE, independently-self-guarding mechanism

Stated up front because the issue text and this artefact's own mandate require it not be
conflated (§3.4 gives the full trace):

- **Mechanism 1 — the notification-send guard**: `notification_ledger`'s
  `UNIQUE(registration_id, kind)`, exercised by `sendLedgeredNotification`'s existing
  step 4 (an INSERT, unique-violation caught as `skipped-already-sent`). This guards
  **whether a message goes out**, for each of the two new kinds independently.
- **Mechanism 2 — the state-transition guard**: `decideRejectionOutcome`'s existing
  `admission !== "requested"` branch (`domain/registration.ts`, REQ-035, reused
  **unchanged** — see §3.3). This guards **whether the row transitions**, and is a plain
  SQL `WHERE`/first-match-wins predicate with no relationship to the ledger table at all.

A row already moved to `'rejected'` can never match a `WHERE admission = 'requested'`
selection filter again — that is Mechanism 2, and it holds regardless of whether
Mechanism 1's ledger row exists. A message already recorded in `notification_ledger`
can never be re-sent under the same `(registration_id, kind)` — that is Mechanism 1, and
it holds regardless of what `registrations.admission` currently is. **These are two
independent structures on two independent tables; neither substitutes for the other.**

## 2. Urgency, at T-48h before `starts_at`

**Mechanism, stated concretely per the issue's own instruction: BOTH.** (1) a push
notification to one organizer (§2.1–§2.3), and (2) a marker on REQ-035's existing
`/requests` list, computed fresh on every render (§2.4) — never dependent on whether the
push notification succeeded, reached anyone, or was ever attempted. Choosing "both"
means a chapter's second (or Nth) organizer, who does not receive the push (§2.2 traces
why only one organizer is pushed), still sees the urgency marker the next time they open
the list themselves — the two mechanisms cover each other's gap.

### 2.1 Selection — `selectRegistrationsForUrgencyNotice`

```
export interface UrgentRequestCandidate {
  registrationId: string;
  eventId: string;
  chapterId: string;
}

export async function selectRegistrationsForUrgencyNotice(
  db: DbClient["db"],
  evaluationTime: Date,
): Promise<UrgentRequestCandidate[]>;
```

**Selection condition, stated as a table** (same convention `noShowJobs.ts`'s own
docstring table uses):

| Clause | Condition |
|---|---|
| Admission | `registrations.admission = 'requested'` |
| Event status | `events.status = 'published'` |
| Trigger instant reached | `events.startsAt - 48 hours <= evaluationTime` |
| Not stale (catch-up window) | `events.startsAt - 48 hours > evaluationTime - CATCH_UP_WINDOW_MS` |

`CATCH_UP_WINDOW_MS` is a module constant, same reasoning `noShowJobs.ts`/
`feedbackJobs.ts` already state for their own identical constant: "a generous multiple of
the job's own polling interval, comfortably covering any realistic scheduler downtime
without letting the backward-looking query grow unbounded." Recommended value: 2 hours,
matching the existing precedent exactly (no AC requires a different value).

Joined `registrations` → `events` (same shape as `noShowJobs.ts`'s own join). `chapterId`
is `events.chapterId`, selected here so §2.2 does not need a second round-trip per
candidate.

**Why no separate "already past registration close" exclusion is needed, confirmed not
assumed:** if `registrationClosesAt` (or, per §3.1, the `endsAt` fallback) has already
passed by the time T-48h arrives, the auto-decline job (§3) will already have moved that
row out of `'requested'` before this query ever runs — the `admission = 'requested'`
clause above excludes it by construction, the same way §0.3's Mechanism 2 always excludes
an already-decided row. No redundant, confusing "still urgent" notice can fire for an
event whose registration already closed.

### 2.2 Recipient — `getPrimaryOrganizerIdForChapter`, ONE organizer, deterministic — traced against the fan-out alternative

```
export async function getPrimaryOrganizerIdForChapter(
  db: DbClient["db"],
  chapterId: string,
): Promise<string | null>;
```

**Query**: `SELECT id FROM users WHERE role = 'organizer' AND chapter_id = $1 ORDER BY id
ASC LIMIT 1`. Returns `null` when no organizer is currently assigned to that chapter
(§7 open question 1 names this edge case explicitly).

**Why one organizer, not every organizer of the chapter — traced:** `users.role` has no
uniqueness constraint against `chapter_id` (confirmed: no `uniqueIndex` on `(role,
chapter_id)` anywhere in `schema.ts`), so a chapter can genuinely have more than one
organizer. `sendLedgeredNotification`'s idempotency key is `(registration_id, kind)`
**with no recipient column at all** — calling it once per organizer for the SAME
`registrationId`/`kind` pair would let only the FIRST organizer's call win the ledger
INSERT; every subsequent organizer's call would immediately return
`skipped-already-sent` and that organizer would never be pushed. Building a genuine
fan-out (a new send primitive keyed differently, or a new ledger column) is exactly the
kind of schema/mechanism change this run is not scoped to invent silently. Given no AC
requires every organizer of a chapter to receive the push (AC1 only requires the requests
be surfaced "to that event's organizers," and the marker in §2.4 independently reaches
**any** organizer who opens the list, regardless of chapter organizer count), this design
resolves the tension by pushing to exactly one deterministically-chosen organizer and
relying on §2.4's marker to cover the rest. `ORDER BY id ASC` is an arbitrary but stable
tie-break with no AC pinning a specific choice — the same "simplest deterministic order"
convention `getWaitlistPosition`/`getMyRegistrations` already establish for their own
unpinned orderings.

### 2.3 Compose — at-send-time recheck, same discipline as every other job in this codebase

```
async function composeUrgencyNotice(
  db: DbClient["db"],
  registrationId: string,
  eventId: string,
  lang: BotLang,
): Promise<ComposedMessage>;
```

Rule table (first-match-wins, same shape `composeNoShowReasonRequest`/
`composeFeedbackNpsPrompt` already use):

| # | Recheck | Failing result |
|---|---|---|
| 1 | Registration still exists and `admission === 'requested'` | `{ kind: "skip" }` |
| 2 | Event still exists and `status === 'published'` | `{ kind: "skip" }` |
| 3 | (else) | `{ kind: "text", text: <urgency message>, buttons: undefined }` |

A `"skip"` result still leaves the already-inserted ledger row consumed (§0.3
Mechanism 1) — the same accepted convention `sendLedgeredNotification`'s own step 5
already documents.

### 2.4 The list marker — `isRequestUrgent`, `PendingRequestListItem.isUrgent`

New pure predicate, `domain/event.ts`, alongside `isRegistrationOpen`/`isFinished`/
`isAutoPromotionHalted` (same file, same "evaluation time is an explicit parameter"
discipline, decisions/0006):

```
export function isRequestUrgent(startsAt: Date, evaluationTime: Date): boolean;
```

**Rule, stated in prose (not executable code, per this role's constraint):** `true` when
48 hours or fewer remain before `startsAt` (i.e. `evaluationTime` is at or past the T-48h
instant), `false` otherwise — the exact same boundary rule `isAutoPromotionHalted`
already states for its own T-24h window, only with a 48-hour threshold and applied to a
request's urgency rather than auto-promotion. This mirrors `isAutoPromotionHalted`'s
signature and doc-comment shape precisely, so a later reader can compare them side by
side.

`listPendingRequestsForOrganizer`'s existing return type (`domain/registration.ts`,
REQ-035 §1) gains one additive field:

```
export interface PendingRequestListItem {
  // ...all existing fields, unchanged...
  isUrgent: boolean;  // computed via isRequestUrgent(event.startsAt, evaluationTime)
}
```

`listPendingRequestsForOrganizer` gains one new parameter, `evaluationTime: Date`
(decisions/0006 — never `SQL now()` inside the read), threaded in by its handler caller
the same way every other evaluation-time-consuming read in this codebase already is.
`renderRequestsListMessage` (the existing rendering function `organizerRequests.ts`
already has, REQ-035 §6.1 step 5) is extended to prefix a fixed marker string
(`catalog.organizerRequests.urgentMarker`, §5) onto a row when `isUrgent` is `true` — a
plain per-row text prefix, no new button, no new callback, no new command. This marker is
**computed fresh on every render** — it never reads the ledger, never depends on whether
the push notification in §2.2/§2.3 was ever sent, attempted, or delivered, and is visible
to every organizer who opens `/requests`, not only the one chosen in §2.2.

### 2.5 The job — `makeUrgencyNoticeJob`

```
export function makeUrgencyNoticeJob(
  db: DbClient["db"],
  sender: NotificationSender,
  intervalMs: number,
): ScheduledJobDefinition;
```

Run body, stated as steps (mirrors `makeNoShowReasonRequestJob`'s shape exactly):

1. `candidates = selectRegistrationsForUrgencyNotice(db, evaluationTime)` (§2.1).
2. For each candidate: `organizerId = getPrimaryOrganizerIdForChapter(db,
   candidate.chapterId)` (§2.2). If `null`, skip this candidate entirely — no
   `sendLedgeredNotification` call, no ledger row (§7 open question 1).
3. Otherwise: `sendLedgeredNotification({ db, sender, registrationId:
   candidate.registrationId, kind: "pending_request_urgent", classification:
   "transactional", userId: organizerId, composeMessage: (lang) =>
   composeUrgencyNotice(db, candidate.registrationId, candidate.eventId, lang) })`.

Recommended `intervalMs`: 5 minutes, matching the existing jobs' polling cadence (no AC
requires a different value).

**Why re-selecting the same candidate on every subsequent tick is safe and does not
re-notify:** once step 3 succeeds once for a given `registrationId`, every later tick's
attempt to INSERT the same `(registrationId, "pending_request_urgent")` ledger row hits
the unique-violation branch and returns `skipped-already-sent` immediately — the query in
§2.1 has no need to itself suppress already-notified rows, because the ledger already
does, structurally, the same way every other repeating job in this codebase already
relies on (`sendLedgeredNotification`'s own AC1/AC2, REQ-025).

## 3. Auto-decline, at `registration_closes_at`

### 3.1 `registration_closes_at IS NULL` — resolved as an `ends_at` fallback, reasoned explicitly

**Decision: when `registrationClosesAt` is `NULL`, the auto-decline job uses `endsAt` as
the effective close instant for that event instead.** No column is added (the issue's own
explicit prohibition) — this is a choice of *which existing column* the job's selection
query keys on for that one event, made once per candidate row at query time, not a stored
value.

**Reasoning, not silently assumed:** STORY-DETAILS B6's own text is "nobody waits past
the event" — stated as the member-side guarantee this requirement exists to satisfy, not
merely "nobody waits past whatever `registration_closes_at` happens to say." An event
configured with no explicit registration close has, definitionally, no earlier "close"
moment than its own end — but it still has an end, and a request still sitting at
`'requested'` after the event has already finished is squarely the "hangs forever" failure
JOURNEY-AUDIT J3 names. The alternative named in the issue text — "no auto-decline at all,
with the urgency flag as the only backstop" — was considered and rejected: it would leave
such a request in `'requested'` permanently (the urgency notice, §2, fires once at T-48h
and is not itself a resolution), directly contradicting "nobody waits past the event."
The `ends_at` fallback is the smaller deviation from the requirement's own stated intent,
uses an existing, always-`NOT NULL` column (`events.endsAt`, `schema.ts` line 231), and
requires no new predicate beyond substituting which timestamp is compared — the same
substitution `isRegistrationOpen`'s own existing `NULL`-means-"no deadline" convention
already establishes for a different purpose (registration acceptance, not decline), read
here as: absence of an explicit close means the event's own boundary governs instead, at
both ends of this requirement's timeline (registration never explicitly closes → the event
ending is what finally closes the window on an undecided request).

### 3.2 Selection — `selectRegistrationsForAutoDecline`

```
export interface AutoDeclineCandidate {
  registrationId: string;
  eventId: string;
}

export async function selectRegistrationsForAutoDecline(
  db: DbClient["db"],
  evaluationTime: Date,
): Promise<AutoDeclineCandidate[]>;
```

**Selection condition, stated as a table:**

| Clause | Condition |
|---|---|
| Admission | `registrations.admission = 'requested'` |
| Event status | `events.status = 'published'` |
| Close instant reached (§3.1) | `(events.registrationClosesAt IS NOT NULL AND events.registrationClosesAt <= evaluationTime) OR (events.registrationClosesAt IS NULL AND events.endsAt <= evaluationTime)` |
| Not stale (catch-up window) | the relevant close instant (whichever branch above matched) `> evaluationTime - CATCH_UP_WINDOW_MS` |

Same `CATCH_UP_WINDOW_MS` reasoning and recommended value as §2.1 (2 hours) — kept as its
own module constant in this job's own file, not shared with `urgencyJobs.ts`'s constant,
matching this codebase's existing convention of each scheduler file owning its own
identically-reasoned constant (`noShowJobs.ts` and `feedbackJobs.ts` each define their
own `CATCH_UP_WINDOW_MS` rather than importing a shared one).

**No re-derivation of `admission='requested'` as a "not yet decided" business rule beyond
what already exists:** this is the exact same admission-state test §0.3 Mechanism 2 and
§2.1 both already rely on — one predicate, reused by reading, not reinvented per query.

### 3.3 The write — `autoDeclineRequest`, reusing `decideRejectionOutcome` unchanged, a NEW writer for the system-actor case

**`decideRejectionOutcome` (REQ-035 §4.1, `domain/registration.ts`) is reused
completely unchanged** — no new pure decision function is introduced. Its existing table
already is exactly what this case needs:

| # | Condition | Result |
|---|---|---|
| 1 | `!registrationExists` | `{ kind: "not-found" }` |
| 2 | `admission !== "requested"` | `{ kind: "not-requested", admission }` |
| 3 | (else) | `{ kind: "reject" }` |

Row 2 is §0.3's Mechanism 2 stated once more in the concrete function that implements it:
a row already `'admitted'`, `'rejected'`, or `'withdrawn'` (by an organizer's own decision,
or by a PRIOR run of this very job) is refused here, with no write and no audit row —
structurally, not by a separate "already declined" check this design would otherwise have
to invent.

**Why a NEW writer, not a call to REQ-035's existing `rejectRequest`:** `rejectRequest`'s
signature takes `organizerUserId: string` (non-nullable) and unconditionally writes
`actorUserId: organizerUserId` and `action: "registration.reject"` with the organizer's
free-text `reason` in the audit payload. This job has no organizer and no free-text
reason — S8/AC6 require `actorUserId = NULL` for a "genuinely system-initiated action,"
which `rejectRequest`'s signature cannot express (it has no branch that omits the
organizer id). Rather than adding an optional/nullable parameter to `rejectRequest` that
would change an already-merged, already-tested function's contract, this design adds a
narrow, dedicated writer with its own signature and its own audit action string — the
same "distinct action per branch" discipline REQ-035 §0.2 already established for
`approve` vs. `approve_override` (two audit action strings distinguishing two
circumstances of the same underlying transition), applied here to distinguish a human
decision from a system one.

```
export async function autoDeclineRequest(
  db: DbClient["db"],
  registrationId: string,
  at: Date,
): Promise<RejectionOutcome & { eventId?: string; userId?: string }>;
```

**Steps, inside one `db.transaction`** (identical shape to `rejectRequest`'s own steps,
REQ-035 §4.2, minus the organizer/reason parameters):

1. `SELECT id, eventId, userId, admission FROM registrations WHERE id = $1 FOR UPDATE`.
2. `decideRejectionOutcome` (pure, unchanged, above).
3. `not-found` / `not-requested` → return unchanged: no write, no audit row (mirrors
   every other non-writing branch in this file, and is Mechanism 2 in action — this is
   exactly what makes a duplicate job tick for an already-declined row a no-op).
4. `reject` → `UPDATE registrations SET admission = 'rejected' WHERE id = $1` — only this
   one column, same as `rejectRequest` (`noShowReason` untouched, a different, unrelated
   concept per REQ-032).
5. `writeAuditLog(tx, { actorUserId: null, action: "registration.auto_decline", entity:
   "registration", entityId: registrationId, payload: { eventId }, at })` — **exactly one
   row** (AC6), **`actorUserId: null`** (AC6, S8, the schema comment this requirement's
   own description cites), same transaction as the `UPDATE`. `payload` carries no
   `reason` field (unlike `rejectRequest`'s payload) — there is no organizer-authored
   text to capture; the fixed, honest explanation lives only in the notification text
   (§3.5), not in the audit trail, matching REQ-035 §Open-Question-1's own precedent that
   no AC requires a stored, queryable reason beyond the audit action name itself.

Return shape mirrors `rejectRequest`'s: the outcome plus `eventId`/`userId` for the
caller to compose and send the notification **outside this transaction** — same
write-commits-first-then-notify separation `approveRequest`/`rejectRequest`/
`promoteFromWaitlistIfEligible` all already use.

### 3.4 The two mechanisms, traced through this specific function (restating §0.3 concretely)

- **Mechanism 2 (state)**: `autoDeclineRequest`'s own step 2/3 above. A row already
  `'rejected'` (whether by an organizer's `rejectRequest` or a PRIOR tick of this same
  job) returns `not-requested` here — no second `UPDATE`, no second audit row. This holds
  with **zero involvement of `notification_ledger`.**
- **Mechanism 1 (send)**: applied by the CALLER, after `autoDeclineRequest` returns
  `{ kind: "reject" }`, via `sendLedgeredNotification({ ..., kind:
  "registration_auto_declined", ... })` (§3.6 step 3). Its own step-4 INSERT into
  `notification_ledger` is what prevents a second message for a registration whose
  `sendLedgeredNotification` call is somehow invoked twice for the same tick (e.g. a
  duplicated job run in the overlap-guard's own narrow race, per `runner.ts`'s own
  documented "skip, don't queue" discipline) — but by the time a SECOND job tick runs,
  Mechanism 2 has already excluded the row from re-selection (§3.2's `admission =
  'requested'` clause), so Mechanism 1 is very rarely even reached twice in practice; it
  exists as its own independent backstop regardless.

### 3.5 The notification — honest, blame-free, reuses `deepLinkSeeUpcoming` unchanged

```
async function composeAutoDeclineNotice(
  eventId: string,
  lang: BotLang,
): Promise<ComposedMessage>;
```

Text = `catalog.autoDecline.notification` (interpolated with `{event}`, the event's
title, resolved the same way every other composed message in this codebase resolves it)
followed by `catalog.event.deepLinkSeeUpcoming` — the **exact existing string** REQ-035
§0.4 already reuses unchanged for its own reject flow's onward path, and REQ-027 before

**Wording constraint (STORY-DETAILS B6's "honest message," this requirement's own

before registration closed and that registration is now closed — it never says or implies
the person was judged, reviewed, or found lacking, because no such review happened. Same
tone class as REQ-014's consent copy and REQ-032's no-show copy: sentence case, no
exclamation marks, no slogans, no emoji, factual register.

### 3.6 The job — `makeAutoDeclineJob`

```
export function makeAutoDeclineJob(
  db: DbClient["db"],
  sender: NotificationSender,
  intervalMs: number,
): ScheduledJobDefinition;
```

Run body, stated as steps:

1. `candidates = selectRegistrationsForAutoDecline(db, evaluationTime)` (§3.2).
2. For each candidate: `outcome = autoDeclineRequest(db, candidate.registrationId,
   evaluationTime)` (§3.3, transactional, commits or no-ops before this step returns).
3. If `outcome.kind !== "reject"` (i.e. `not-found`/`not-requested` — the row was already
   decided by an organizer or a prior tick between selection and this write, Mechanism
   2 in action): move to the next candidate, no notification call at all — no ledger row
   is written for a registration whose state never actually transitioned here.
4. If `outcome.kind === "reject"`: `sendLedgeredNotification({ db, sender,
   registrationId: candidate.registrationId, kind: "registration_auto_declined",
   classification: "transactional", userId: outcome.userId, composeMessage: (lang) =>
   composeAutoDeclineNotice(outcome.eventId ?? candidate.eventId, lang) })`.

Recommended `intervalMs`: 5 minutes, same reasoning as §2.5.

## 4. Restart-safety (AC4) — traced through a kill-mid-batch scenario

**Scenario, matching AC4's own construction:** three pending requests on one event, all
past `registration_closes_at`. The job selects all three candidates in step 1. The process
completes candidate 1 fully (state write commits, `sendLedgeredNotification` commits its
ledger row and successfully calls `sender.send`), then is **killed** while about to start
candidate 2 (i.e. between candidates, the ordinary "mid-batch" reading of the AC's own
wording — §7 open question 3 names the narrower single-candidate torn-write case
separately, since it is not what a multi-candidate batch test constructs).

- **Candidate 1** (fully completed before the kill): on restart, the job's immediate
  first tick (`runner.ts`'s existing "run once immediately" behavior) re-runs
  `selectRegistrationsForAutoDecline`. Candidate 1's row is now `admission = 'rejected'`
  — excluded by the `WHERE admission = 'requested'` clause (Mechanism 2). It is never
  re-selected, so `autoDeclineRequest` is never called again for it, so no second audit
  row, no second `UPDATE`. Even if it somehow WERE re-selected, `sendLedgeredNotification`'s
  ledger INSERT for `(candidate1.registrationId, "registration_auto_declined")` would hit
  the unique violation and skip (Mechanism 1) — two independent backstops, either one
  alone already sufficient.
- **Candidates 2 and 3** (never started before the kill): both rows are still
  `admission = 'requested'` (nothing wrote to them) and neither has a
  `notification_ledger` row for `"registration_auto_declined"` (nothing inserted one).
  Both are re-selected by the restarted job's first tick, both transition exactly once,
  both are notified exactly once.

**Total across both runs: 3 transitions, 3 sends — the same as if the process had never
been killed.** No further transitions occur on any LATER tick, because by then all three
rows are `'rejected'` and Mechanism 2 excludes them permanently. This is the literal
count AC4 requires, produced by the SAME two independent, already-existing mechanisms
(§0.3) working together — no new restart-recovery logic of any kind was added to make
this hold; it falls out of `WHERE admission = 'requested'` plus the ledger's unique index,
exactly as REQ-025 §7/REQ-032 §3 already rely on for every prior scheduled job in this
codebase.

## 7. Open questions (not silently resolved)

1. **A chapter with zero assigned organizers at T-48h.** `getPrimaryOrganizerIdForChapter`
   (§2.2) returns `null`; the design's own step 2 (§2.5) skips the push entirely for that
   candidate — no error, no retry loop, no ledger row written (so if an organizer is
   assigned to that chapter LATER, before the event starts, this design does not
   automatically catch them up with a late push; the list marker (§2.4), being computed
   fresh on every render, WOULD immediately show the request as urgent to that
   newly-assigned organizer the first time they open `/requests`). Judged acceptable
   because the marker mechanism has no such gap; flagged rather than silently accepted as
   "won't happen."
2. **The exact placement of `getPrimaryOrganizerIdForChapter`** — `domain/registration.ts`
   (co-located with the other REQ-035/REQ-036 registration-flow functions this file
   already holds) or `domain/event.ts` (co-located with the other chapter/event-timing
   predicates this design adds, §2.4) — either is consistent with this codebase's
   existing file-organization conventions; BACKEND-DEV's plumbing choice, no behavioral
   consequence either way.
3. **The narrow single-candidate "torn write" window** — `autoDeclineRequest` commits
   the state transition (§3.3) BEFORE the caller invokes `sendLedgeredNotification`
   (§3.6 step 4). A crash occurring in exactly that gap (state committed, notification
   never attempted) would leave that one registrant permanently un-notified: on the next
   tick the row is already `'rejected'` (Mechanism 2 excludes it from re-selection) and no
   ledger row was ever created for it (so there is no "already sent, but let's confirm
   delivery" trace either). This is the SAME class of risk `approveRequest`/
   `rejectRequest` (REQ-035 §5) already accept for their own write-commits-then-notify
   sequencing in the synchronous handler path — not a new risk this design introduces,
   but stated explicitly here rather than silently assumed away, since AC4's own
   restart-safety test (traced in §4) exercises the between-candidates case, not this
   narrower within-a-single-candidate window. No AC in this requirement's list requires
   closing this gap, and doing so would require a mechanism (e.g. an outbox/two-phase
   write) nothing else in this codebase uses.
4. **Whether `urgentMarker`'s exact placement/format in the rendered list (prefix vs.
   suffix, plain-text tag vs. some other visual treatment)** is left to BACKEND-DEV's
   implementation of `renderRequestsListMessage` — no AC pins an exact rendered format,
   only that the urgency be "concretely" surfaced and checkable, which a fixed,
   catalog-sourced marker string satisfies regardless of exact placement.
