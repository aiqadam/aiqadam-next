# REQ-018 — EventStaff assignment by organizers and the staff-only check-in surface gate

**Requirement:** implements USER-STORIES F7 ("Put volunteers on the door") and F8
("Know I'm on the door"), plus PRD 3's EventStaff definition. depends_on: REQ-016.
Establishes security-invariants.md S2's EventStaff authorization surface before any
actual check-in feature exists (REQ-028/REQ-029).

**Surface:** `apps/bot/**` (bot requirement).

**Schema:** **no change.** `event_staff` already exists (`db/schema.ts`, added under
REQ-011's original schema pass): `id`, `event_id`, `user_id`, `created_at`, `updated_at`,
unique index `uq_event_staff_event_user(event_id, user_id)`. See §1 for why this is
sufficient as-is — in particular, why removal does not need a `removed_at`/`revoked_at`
column.

**Files this design expects:**
- `apps/bot/src/domain/eventStaff.ts` (new) — parsing, CRUD, and the plain read
  `getEventStaffRow` (§2)
- `apps/bot/src/domain/eventStaffAuthorization.ts` (new) — the check-in authorization

  `getUserByTgUsername` (§2.1)
- `apps/bot/src/domain/event.ts` (existing, REQ-016/017) — reused unchanged
  (`getEventById`, `isFinished`)
- `apps/bot/src/domain/eventAuthorization.ts` (existing, REQ-016) — reused unchanged
  (`requireOrganizerForChapter`) for the assign/remove commands' own organizer gate

- `apps/bot/src/handlers/checkin.ts` (new) — the minimal `/checkin` authorization-stub
  handler (§4.3, and the explicit REQ-028/029 scope boundary in §0.3)

- `apps/bot/src/index.ts` — registers `/staff_add`, `/staff_remove`, `/checkin`

## 0. Reuse decisions and scope boundaries, stated up front

### 0.1 Assign/remove is an organizer-only, chapter-scoped mutation — no new authorization module for it

Adding or removing a person as EventStaff is an organizer action on an event, exactly
the same authorization shape as `/event_publish`/`/event_cancel`: fetch the event first
(to learn its `chapterId`), then call **the existing**
`requireOrganizerForChapter(db, tgId, event.chapterId)` from `domain/eventAuthorization.ts`
— unchanged, not copied, not extended. No new module is needed for this half of the
requirement; it is exactly REQ-016's established pattern applied to a new target entity.

### 0.2 The check-in gate IS a new authorization module, and it is a genuinely different predicate

`checkOrganizerForChapter` answers "does this user's `role`/`chapterId` authorize acting
on this chapter." EventStaff authorization answers a structurally different question:
"does an `event_staff` row exist for this exact `(event_id, user_id)` pair, and has the
event not yet ended." There is no role short-circuit — being `organizer` or `owner`
grants **no** check-in rights by itself (PRD 3: rights are "for that one event, nothing
else," not a role). This is why §3 is a new file, `eventStaffAuthorization.ts`, rather
than an extra branch bolted onto `eventAuthorization.ts`: the two predicates check
different tables against different rules, and conflating them would risk exactly the
"role check present on the menu but wrong on the handler" defect S2 names. It still
follows the project's stated convention of a parallel copy for the `ActingUser`/
`resolveActingUser` scaffolding (§3.1) rather than a shared refactor — REQ-016/017's own
precedent for `eventAuthorization.ts` vs `venueAuthorization.ts`.

### 0.3 The check-in handler's scope boundary — resolving the task's own scoping question

**Resolution: `/checkin <event_id>` is an authorization-only stub.** Its entire job is
(a) run the EventStaff gate from §3, and (b) on success, acknowledge that the caller is
authorized for that one event. It performs **no** check-in business logic:

- It does not parse or accept a `qr_token`.
- It does not read or write `registrations.checked_in_at`,
  `registrations.check_in_method`, or `registrations.checked_in_by`.
- It does not implement any of security-invariants.md S5's or S6's rules (duplicate
  check-in detection, waitlisted/withdrawn refusal, the `admission = 'admitted'` CHECK
  interaction) — those rules describe the real check-in flow, which is REQ-028/029's
  scope, not this requirement's.
- Consequently, **S5's "scanner is not staff → refuse and write an AuditLog row" is not
  implemented by this stub.** None of REQ-018's own acceptance criteria (AC1-AC6) ask
  for an audit row on a check-in refusal — AC5 counts only assignment/removal audit
  rows. Flagged explicitly in §6.1 rather than silently adding (or silently omitting
  without saying so) an audit write that REQ-028/029's own design should decide on when
  it builds the real scanning flow on top of this gate.

This is a deliberate scoping decision, not an oversight — stated here per the task's own
instruction so it reads as intentional to CODE-DESIGN-VALIDATOR and to whoever reads this
file when REQ-028/029 starts.

### 0.4 Assigning EventStaff never touches `users.role`

`addEventStaff` (§2.2) writes only to the `event_staff` table. It never reads or writes
`users.role`. This is the concrete reason AC2 holds "for free": an EventStaff member's
`role` stays whatever it already was (`member`, by default) both before and after
assignment, so **every existing organizer-only handler already refuses them** — no new
check is added to `checkOrganizerForChapter`, and none is needed. Stated explicitly so a
reviewer doesn't go looking for a change to `eventAuthorization.ts` that was deliberately
not made.

### 0.5 No speaker read anywhere in this design

No function in `eventStaff.ts`, `eventStaffAuthorization.ts`, `handlers/staff.ts`, or
`handlers/checkin.ts` reads a "speaker" flag or any Talk-derived status — none of these
files have any reason to touch the (still-nonexistent, per REQ-017 §3.2) Talk entity at
all. AC6's `git grep -n "speaker" apps/bot/src` gate is satisfied by this design simply
containing no such reference; there is nothing to design around, and nothing new to
break the invariant this requirement exists to protect.

## 1. Why no schema change — removal is a hard delete, audit trail lives in `audit_log`

**Decision: removal is a real `DELETE FROM event_staff WHERE id = ...`, not a
`revoked_at`/`removed_at` soft-delete column.**

Reasoning:

- **Direct precedent already in this codebase.** `domain/venue.ts`'s `deleteVenue`
  (REQ-015 §5 step 4) hard-deletes the `venues` row and relies entirely on `audit_log`
  (`action: "venue.delete"`, `entityId: venueId`, a snapshot payload captured before the
  delete) for the historical record. `event_staff` needs exactly the same shape: a
  removal is a state change the requirement's own S8 obligation already covers via a
  dedicated `audit_log` row — a second, in-table historical marker would duplicate that
  record for no behavioral gain.
- **What "rights expire" actually needs is time-based, not row-based.** STORY-DETAILS
  F7's "rights that outlive the event" refusal and AC3 ("after `ends_at` has passed...
  refuses") are both about comparing `evaluationTime` against the **event's** `ends_at`
  — not about a flag on the `event_staff` row. A soft-delete column would only be
  needed if "removed" and "expired" had to be distinguished in the row itself; nothing
  in this requirement's acceptance criteria asks for that distinction (removal and
  expiry both simply mean "the person can no longer check in," and both are already
  fully explained by two independent, already-available facts: whether the row exists,
  and whether `evaluationTime > event.ends_at`).
- **A hard delete keeps re-assignment trivial.** `uq_event_staff_event_user` means a
  removed-then-reassigned volunteer for the same event needs the unique index to accept
  a fresh row with the identical `(event_id, user_id)` pair. A soft-delete column would
  force a design choice between relaxing the unique index (e.g. a partial index over
  `revoked_at IS NULL`) or reusing/reviving the old row — genuine complexity this
  requirement's acceptance criteria do not ask for. Hard delete avoids the question
  entirely: a removed pair simply doesn't exist until re-added.

**Consequence for §3's authorization check:** "is this user currently EventStaff for
this event" is answered by **existence of a row** (`getEventStaffRow`, §2.3) — never by
reading a status column on it.

## 2. `domain/eventStaff.ts` (new)

Framework-free (decisions/0004): no grammY import. Follows the same pure-parsing /
I/O-performing split already established in `domain/venue.ts` and `domain/event.ts`.

### 2.1 Parsing the assign/remove command payload

```
// domain/eventStaff.ts
export interface ParsedStaffCommand {
  eventId: string;
  tgUsername: string;
}

export function parseStaffCommandArgs(text: string): ParsedStaffCommand | null;
```

Rule, stated exactly:

| Input | Result |
|---|---|
| Fewer than two non-blank, whitespace-separated tokens | `null` (usage error) |
| Two or more tokens | first token trimmed = `eventId`; second token, trimmed, with one leading `@` stripped if present = `tgUsername`. Any further tokens are ignored. |

No normalization beyond the leading-`@` strip — no case-folding of the username. Flagged
as open question §6.2 (Telegram usernames are conventionally case-insensitive; this
design does not decide whether a case-insensitive match is required, since no
acceptance criterion exercises mixed-case input).

### 2.2 Looking up the target user

Not in this file — added to the existing `domain/user.ts` (§2.1 below), since "resolve a
user by an identifying field" is a general user-lookup concern, not staff-specific, the
same reasoning that already keeps `getFlowUserByTgId`/`getUserWithChapterByTgId` in
`user.ts` rather than in whichever feature's handler first needed them.

```
// domain/user.ts — addition
export interface UserWithTelegram {
  id: string;
  tgId: bigint | null;
  tgUsername: string | null;
}

export async function getUserByTgUsername(
  db: DbClient["db"],
  tgUsername: string,
): Promise<UserWithTelegram | null>;
// SELECT id, tg_id, tg_username FROM users WHERE tg_username = $tgUsername LIMIT 1
```

**Open question, named rather than silently assumed (§6.3):** `users.tg_username` has no
unique index (`db/schema.ts` — only `tg_id` is uniquely indexed). If two rows somehow
share the same `tg_username` (Telegram itself prevents this at the platform level for
live accounts, but this schema does not enforce it), this query returns whichever row
the database happens to return first for an unordered `LIMIT 1` — not a specified
"most recent" or "first ever" row. Not exercised by any acceptance criterion; flagged so
it isn't mistaken for a considered ordering decision later.

`tgId: bigint | null` is read defensively even though every row currently reaching this
lookup was created by `resolveOrCreateUser` (REQ-014 §2.2), which always sets `tgId` and
`tgUsername` together — so a row found by username lookup should, in current practice,
always carry a non-null `tgId`. Typed nullable anyway because the column itself is
nullable (`db/schema.ts`'s own comment: "nullable so an organizer can pre-create a User
row before the person's first `/start`") and no future requirement should be able to
violate this design's safety by assuming otherwise. §4.1/§4.2 state what the handler
does with a null `tgId`.

### 2.3 Reading current staff status

```
// domain/eventStaff.ts
export interface EventStaffRow {
  id: string;
  eventId: string;
  userId: string;
}

export async function getEventStaffRow(
  db: DbClient["db"],
  eventId: string,
  userId: string,
): Promise<EventStaffRow | null>;
// SELECT id, event_id, user_id FROM event_staff
// WHERE event_id = $eventId AND user_id = $userId LIMIT 1
```

Used three ways: (a) the assign handler's "already assigned" pre-check (§4.1), (b) the
remove handler's "not assigned" pre-check and delete-snapshot source (§4.2), (c) the
check-in authorization gate's existence check (§3.2).

### 2.4 Mutations — one write + one `AuditLog` row, one transaction each (S8)

```
// domain/eventStaff.ts
export async function addEventStaff(
  db: DbClient["db"],
  actorUserId: string,
  eventId: string,
  targetUserId: string,
  eventTitle: string,
  at: Date,
): Promise<string>; // returns the new event_staff.id
```

Behavior, stated exactly (same shape as `createVenue`/`createEvent`):
1. `INSERT INTO event_staff (event_id, user_id) VALUES (...) RETURNING id`, inside a
   `db.transaction`.
2. If the insert returns no row: unreachable in practice (guarded, not asserted, per
   this codebase's no-speculation stance — same guard `createEvent`/`resolveOrCreateUser`
   already use).
3. `writeAuditLog(tx, { actorUserId, action: "event_staff.add", entity: "event_staff",
   entityId: <the new row's id>, payload: { eventId, targetUserId, eventTitle }, at })`,
   same transaction.
4. Return the new row's id.

The handler (§4.1) is responsible for calling `getEventStaffRow` FIRST and refusing with
`staff.alreadyAssigned` before ever calling `addEventStaff` — this function itself does
not re-check the unique index's outcome (consistent with `createVenue`/`createEvent`
never re-deriving their own callers' pre-conditions).

```
export async function removeEventStaff(
  db: DbClient["db"],
  actorUserId: string,
  staffRowSnapshot: EventStaffRow,
  eventTitle: string,
  at: Date,
): Promise<void>;
```

Behavior, stated exactly (same shape as `deleteVenue`, §1's own cited precedent —
`staffRowSnapshot` is captured by the caller BEFORE this call, from the same
`getEventStaffRow` read used for the "not assigned" pre-check, since the row no longer
exists to read from afterward):
1. `DELETE FROM event_staff WHERE id = $staffRowSnapshot.id`, inside a `db.transaction`.
2. `writeAuditLog(tx, { actorUserId, action: "event_staff.remove", entity: "event_staff",
   entityId: staffRowSnapshot.id, payload: { eventId: staffRowSnapshot.eventId, userId:
   staffRowSnapshot.userId, eventTitle }, at })`, same transaction.

## 3. `domain/eventStaffAuthorization.ts` (new) — the check-in gate

### 3.1 `ActingUser`/`resolveActingUser` — parallel copy, per project convention

Byte-for-byte the same shape as `venueAuthorization.ts`/`eventAuthorization.ts` (§0.2's
own reasoning for why this stays a copy, not a shared import):

```
export interface ActingUser {
  id: string;
  role: "member" | "organizer" | "owner";
  chapterId: string | null;
}

export async function resolveActingUser(
  db: DbClient["db"],
  tgId: bigint,
): Promise<ActingUser | null>;
// identical query to venueAuthorization.ts's/eventAuthorization.ts's own
// resolveActingUser: SELECT id, role, chapter_id FROM users WHERE tg_id = $tgId LIMIT 1
```

`role` is read here only because `ActingUser`'s shape is copied whole for consistency
with the other two authorization modules — §3.2's predicate never inspects it. Stated
explicitly so a future reader doesn't assume `role` participates in the check-in
decision (it structurally cannot: PRD 3's "for that one event, nothing else").

### 3.2 The predicate — no role short-circuit, existence + expiry only

```
export type CheckInAuthorizationResult =
  | { ok: true }
  | { ok: false; reason: "no-user" | "not-staff-for-event" | "event-ended" };

export function checkEventStaffAuthorization(
  user: ActingUser | null,
  staffRow: EventStaffRow | null,
  eventEndsAt: Date,
  evaluationTime: Date,
): CheckInAuthorizationResult;
```

Rule, stated exactly so it cannot be reinterpreted:

| Step | Condition | Result |
|---|---|---|
| 1 | `user === null` | `{ ok: false, reason: "no-user" }` |
| 2 | `staffRow === null` (no `event_staff` row for this exact `(eventId, user.id)` pair — covers both "never staffed" and "staffed for a different event," §0.2) | `{ ok: false, reason: "not-staff-for-event" }` |
| 3 | `evaluationTime` is strictly after `eventEndsAt` (reuses REQ-017's own `isFinished(eventEndsAt, evaluationTime)` from `domain/event.ts` — not reimplemented here) | `{ ok: false, reason: "event-ended" }` |
| 4 | none of the above | `{ ok: true }` |

**No step ever inspects `user.role`.** An `owner` or `organizer` with no `event_staff`
row for this event is refused at step 2 exactly like a plain `member` would be — this is
the structural reason AC1's negative case (staffed on event 1, calling event 2) and
AC2's negative case (organizer-only surfaces) cannot be confused with each other or with
this predicate: this predicate never grants anything on the strength of a role, and the
organizer-only handlers (§0.1) never grant anything on the strength of an `event_staff`
row.

### 3.3 Composed entry point

```
export async function requireEventStaffForEvent(
  db: DbClient["db"],
  tgId: bigint,
  eventId: string,
  eventEndsAt: Date,
  evaluationTime: Date,
): Promise<CheckInAuthorizationResult>;
```

Behavior: `resolveActingUser(db, tgId)` → `getEventStaffRow(db, eventId, user?.id)` (only
called when `user !== null`; passes `null` straight through to step 2 of §3.2 otherwise)
→ `checkEventStaffAuthorization(user, staffRow, eventEndsAt, evaluationTime)`. This is
the single function `handlers/checkin.ts` calls (§4.3) — no handler ever calls
`checkEventStaffAuthorization` directly, the same "one composed entry point per handler"
discipline `requireOrganizerForChapter` already established.

## 4. Handlers

### 4.1 `/staff_add <event_id> <tg_username>` (`handlers/staff.ts`)

```
export function makeStaffAddHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence, stated exactly (no domain logic in the handler body — decisions/0004; every
step below is a call into `domain/`):

1. `tgId = ctx.from?.id`; `undefined` → return (existing convention, every handler in
   this codebase).
2. `lang = resolveLangForTg(db, tgId)` — the ORGANIZER's own language, for the reply
   text in step 9 (a local copy of the helper every handler file already defines).
3. `parsed = parseStaffCommandArgs(matchText(ctx))`; `null` → reply
   `staff.usageNoArgs`, return.
4. `event = getEventById(db, parsed.eventId)` (reused, unchanged, from `domain/event.ts`);
   `null` → reply `staff.eventNotFound`, return.
5. `authResult = requireOrganizerForChapter(db, BigInt(tgId), event.chapterId)` (reused,
   unchanged, from `domain/eventAuthorization.ts`); `!ok` → reply `staff.notAuthorized`,
   return. **This is the FIRST authorization-relevant check that runs after only the
   minimal parsing needed to know what to authorize against** — same discipline as every
   existing mutation handler in this codebase.
6. `targetUser = getUserByTgUsername(db, parsed.tgUsername)`; `null` → reply
   `staff.userNotFound`, return.
7. `targetUser.tgId === null` → reply `staff.userNotFound` (§2.2's defensive case — the
   organizer sees the same message as "no such user," since from their point of view the
   volunteer needs to `/start` the bot before they can be staffed either way); return.
8. `existing = getEventStaffRow(db, event.id, targetUser.id)`; not `null` → reply
   `staff.alreadyAssigned`, return.
9. `newId = addEventStaff(db, authResult.user.id, event.id, targetUser.id, event.title,
   new Date())`.
10. **Notification send (F8), in the TARGET's own language, not the organizer's:**
    `targetLang = resolveLangForTg(db, Number(targetUser.tgId))`, then
    `ctx.api.sendMessage(Number(targetUser.tgId), getCatalog(targetLang).staff.assignmentNotificationBody.replace("{event}", event.title))`
    (or equivalent string composition — a plain reply-composition concatenation/
    interpolation, the same "compose from a catalog string plus dynamic data" discipline
    `venue.createSuccessPrefix`/`event.publishSuccessPrefix` already use, not a new
    domain function). **Direct, synchronous send at the moment of assignment — not
    queued, not scheduled.** This is a deliberate reasoning point, not an oversight:
    REQ-025's idempotent send ledger does not exist yet, so there is no
    per-`(registration, kind)`-style dedup mechanism (S9) to route this through; a single
    direct API call at the point of assignment has no retry/restart path that could
    duplicate it (unlike a scheduled job, which is exactly what S9 is guarding against).
    When REQ-025 lands, whether this send should move onto its ledger is that
    requirement's own decision, flagged again in §6.4.
    - **If the send throws** (e.g. the volunteer has blocked the bot): caught by the
      handler; the assignment itself is NOT rolled back (the DB write already committed
      in step 9, and a failed *notification* is not grounds to undo a successful
      *authorization grant* — the organizer may need to fix delivery out-of-band, e.g.
      by asking the volunteer to unblock the bot, without re-doing the assignment). The
      organizer's reply (step 11) additionally appends `staff.notificationFailedNote` in
      this case.
11. Reply to the organizer: `staff.addSuccessPrefix` plus the target's `tgUsername` (or,
    per the exception in step 10, that plus `staff.notificationFailedNote`).

### 4.2 `/staff_remove <event_id> <tg_username>` (`handlers/staff.ts`)

Mirrors §4.1 exactly through authorization (steps 1-5 identical, target-user lookup step
6 identical), then:

7. `existing = getEventStaffRow(db, event.id, targetUser.id)`; `null` → reply
   `staff.notAssigned`, return.
8. `removeEventStaff(db, authResult.user.id, existing, event.title, new Date())`.
9. Notification send, same shape as §4.1 step 10 but using
   `staff.removalNotificationBody` — STORY-DETAILS F8's "Removed → told, and the screen
   is gone." **What "the screen is gone" means concretely, restated so it isn't confused
   with a UI element this design would need to build:** once `removeEventStaff` commits,
   the very next `/checkin <event_id>` call this person makes for this event evaluates
   `getEventStaffRow` fresh (§3.2 step 2) and finds no row — refusal is automatic and
   immediate from the next invocation onward. There is no cached permission, no session
   flag, and nothing else for this design to "revoke" beyond the row itself; the removal
   notification is the entire "and the screen is gone" behavior this requirement needs
   to build, not a separate mechanism.
10. Reply to the organizer: `staff.removeSuccessPrefix` (+ `staff.notificationFailedNote`
    on the same send-failure exception as §4.1 step 10).

### 4.3 `/checkin <event_id>` (`handlers/checkin.ts`) — the authorization-only stub (§0.3)

```
export function makeCheckInHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence:

1. `tgId = ctx.from?.id`; `undefined` → return.
2. `lang = resolveLangForTg(db, tgId)`.
3. `eventId = matchText(ctx).trim()`; blank → reply `checkin.usageNoId`, return.
4. `event = getEventById(db, eventId)`; `null` → reply `checkin.notFound`, return (same
   "reveal not-found before authorization" ordering `handlers/venue.ts`'s
   `/venue_edit`/`/venue_delete` and `handlers/event.ts`'s equivalents already use —
   not a new disclosure this requirement introduces).
5. `event.endsAt === null` → reply `checkin.notFound` (defensive/unreachable path:
   `createEvent` enforces `endsAt` `NOT NULL`; same guard style as
   `buildEventCardContent`'s own defensive nullable-field handling in REQ-017 §3.1).
6. `authResult = requireEventStaffForEvent(db, BigInt(tgId), event.id, event.endsAt, new
   Date())`; `!ok` → reply `checkin.notAuthorized` (one generic string — the specific
   `reason` is never disclosed to the caller, same "don't leak which check failed"
   discipline `venue.notAuthorized`/`event.notAuthorized` already follow), return.
7. `ok` → reply `checkin.authorizedStub` (interpolated with `event.title`) — a plain
   acknowledgment that the caller is authorized to check people in for this event.
   **No further action.** No `qr_token` is read, no `registrations` row is read or
   written, no `AuditLog` row is written (§0.3's stated boundary).

## 5. i18n catalog additions

Two new top-level `Catalog` keys, following REQ-015/016/017's established convention
(top-level key = command/flow; placeholder/minimal functional copy per decisions/0002,
final wording owned by CONTENT-BA):

```
staff: {
  notAuthorized: string;
  usageNoArgs: string;
  eventNotFound: string;
  userNotFound: string;
  alreadyAssigned: string;
  notAssigned: string;
  addSuccessPrefix: string;
  removeSuccessPrefix: string;
  notificationFailedNote: string;
  // Sent to the VOLUNTEER, never to the organizer. Written so someone who has
  // never worked the door before can run it unbriefed (F8) — names the event
  // (interpolated), states the role plainly ("you're on the check-in door for
  // this event"), and states what happens at the door in plain steps (greet
  // the guest, ask their name, confirm them in the list — the actual scanning
  // mechanism is REQ-028/029's, not described here since it doesn't exist
  // yet). One static template, one interpolation point (event title) — no
  // per-assignment role variation exists in this requirement's scope (PRD 3
  // names exactly one EventStaff capability, not multiple staff roles).
  assignmentNotificationBody: string;
  // Sent to the VOLUNTEER on removal. States plainly that their check-in
  // access for this one event has ended and why ("the organizer removed you
  // as staff for <event>" / "this event has ended") — STORY-DETAILS F8.
  removalNotificationBody: string;
}
checkin: {
  usageNoId: string;
  notFound: string;
  notAuthorized: string;
  // Interpolated with the event title. States plainly that scanning/check-in
  // recording is not available yet in this build (§0.3's own boundary) so a
  // real user hitting this command mid-rollout is not confused by a
  // does-nothing acknowledgment.
  authorizedStub: string;
}
```

`ru.ts`/`en.ts` gain the matching keys with placeholder copy — same provisional-copy
precedent already used by every `venue.*`/`event.*`/`events.*` key (decisions/0002).
`catalogs.test.ts`'s existing runtime parity check (REQ-013 §4) continues to enforce that
both locale files stay in lock-step with `types.ts` with no code change of its own.

## 6. Open questions (not silently resolved)

1. **S5's "refuse and audit" is not implemented by this requirement's check-in stub
   (§0.3).** None of REQ-018's own acceptance criteria ask for an audit row on a
   check-in refusal (only AC5, which counts assignment/removal rows). REQ-028/029's own
   design, when it builds the real scanning flow on top of `requireEventStaffForEvent`,
   is the place to decide whether a refused `/checkin` attempt should write an
   `audit_log` row — flagged explicitly so it is a conscious decision there, not an
   accidental gap inherited from here.
2. **Username matching has no case-folding (§2.1).** `parseStaffCommandArgs` strips one
   leading `@` and nothing else; `getUserByTgUsername` does an exact-string match. No
   acceptance criterion exercises mixed-case input; flagged in case a real organizer
   types a username with different casing than what was stored.
3. **`users.tg_username` is not uniquely indexed (§2.2).** `getUserByTgUsername`'s
   `LIMIT 1` has no defined ordering if duplicate usernames ever exist in this table.
   Not currently reachable through any shipped write path, but named rather than
   assumed away.
4. **Whether this notification should move onto REQ-025's idempotent send ledger once it
   exists (§4.1 step 10).** This design's reasoning for a direct synchronous send is
   that no restart/retry path exists for a single request-scoped API call, so S9 is not
   at risk today — but REQ-025's own design should make the explicit call on whether
   assignment notifications join its ledger for consistency with every other
   requirement's sends, once that ledger exists.
5. **AC2 names three organizer-only handlers; only two currently exist.** `/venue_new`
   (venue create) and `/event_publish` (event publish) both exist today and are covered
   by this design's reasoning in §0.4 without any code change to either. A "registration
   list" handler does not exist anywhere in this codebase yet (`git grep -n
   "registration.*list\|listRegistrations" apps/bot/src` finds nothing) — it is not this
   requirement's scope to build one. AC2's third case cannot be exercised until whichever
   future requirement adds a registration-list handler exists; that handler's own design
   is responsible for reusing `requireOrganizerForChapter` (§0.1's same reasoning) rather
   than inventing a new authorization path. Flagged here so TEST-DESIGNER/TEST-RUNNER
   know why AC2's third named surface has no handler to call yet, rather than treating it
   as a missed implementation in this run.
