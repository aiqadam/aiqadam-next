## 0. Scope decisions stated up front

### 0.1 Profile capture is folded into the SAME onboarding pipeline `/start` already runs, not a separate flow bolted on afterward

REQ-014's `/start` handler (`handlers/start.ts`) already threads consent → chapter →
greeting through three call sites (`makeStartHandler`'s tail, `makeChapterCallbackHandler`'s
tail, `makeConsentCallbackHandler`'s tail), each ending in `ctx.reply(...start.greeting)`.
AC4 ("a user with an already-complete profile registering for a second event is asked no
profile question") only makes structural sense if "ask the next unanswered onboarding
question" is a single, reusable **progression step**, not a per-command special case —
otherwise every future entry point (the eventual REQ-020 registration flow included) would
need to reimplement "is this person fully onboarded" from scratch. This design therefore:

- Extracts a new `domain/onboarding.ts` module (§3) that answers exactly one question —
  "given this user's current consent/chapter/profile state, what is the next thing to ask,
  if anything" — and performs the single side effect of sending that next prompt.
- **Modifies** `handlers/start.ts`'s three existing greeting tail-points to call this
  module instead of unconditionally sending the greeting (§3.3). This is a real change to
  already-shipped REQ-014 behavior, stated explicitly here exactly the way REQ-016's own
  rework note documented its change to the same file's consent ordering.
- Gives `/profile` (§4.1) the identical entry point: calling the same progression function
  is how `/profile` "skips the form entirely" for an already-complete profile (the
  description's own words) and is how a bare `/profile` from a brand-new user (who never
  ran `/start`) still gets the correct next question rather than a dead end.

### 0.2 "Declining consent" is modeled as "has not yet accepted" — no new Decline button is added

REQ-014's existing consent prompt (`handlers/start.ts`, `consent.prompt` +
`consent.agree`) has exactly one button: **Agree**. Nothing in REQ-014 or REQ-019's own
text asks for a second, explicit "Decline" button, and PRD 10/`security-invariants.md` S1
never describe consent refusal as a distinct recorded event — only as the *absence* of
acceptance. This design reads AC3's "declining" as: **the caller has been shown the
consent prompt and has not tapped Agree.** Concretely: any attempt to progress past the
consent gate (via `/start`, any of its callbacks, or `/profile`) while
`users.consent_pd_at IS NULL` re-shows the same consent prompt — a plain, expected reply,
never an exception — and, by construction (§3.2), no code path ever calls
`domain/profile.ts`'s field-writing function while consent is unset. "Zero profiles rows"
follows automatically: nothing ever attempts a write before this gate opens.

Flagged as an explicit assumption, not silently resolved (§8.2): a dedicated Decline
button is a legitimate alternative reading, and would need its own catalog key/callback if
CONTENT-BA or a future requirement decides the plain "never agreed" reading is
insufficiently explicit for the user.

### 0.3 No `AuditLog` row is written by this requirement

Profile field writes are plain data entry, not an authorization-relevant status
transition (`security-invariants.md` S8 targets state changes like admission/publish/
cancel/check-in — a `Profile` row has no status of that kind). No function in this
design calls `writeAuditLog`. This makes AC5's audit-payload clause satisfied
**vacuously** — there is no payload for this requirement's own code to ever construct —
stated explicitly per this codebase's established convention (REQ-018 §0.3 uses the same
pattern for its own out-of-scope S5 audit write) rather than left for a reader to wonder
whether it was missed. If a future requirement adds an audit trail over profile edits,
that requirement's own design is responsible for applying the same phone/email
redaction rule stated in §6 to whatever payload it constructs.

## 1. Schema dependency — the gap this design cannot design around

Current `profiles` table (`apps/bot/src/db/schema.ts`, REQ-010):

| Column | Nullable today |
|---|---|
| `first_name`, `last_name`, `company`, `position`, `is_student`, `experience_level` | **No** (`NOT NULL`) |
| `phone`, `email`, `links_github`, `links_linkedin`, `links_site`, `public_bio`, `photo_file_id` | Yes |

**The conflict:** PARTIAL WRITES (this requirement's own scope note) requires that "each
answer is written to the Profile row as it arrives" — meaning a `profiles` row must be
insertable after the very first required answer (`first_name` alone) and updatable one
column at a time as each subsequent required answer arrives, well before all six required
columns are known. A `NOT NULL` constraint on five of those six columns (`last_name`,
`company`, `position`, `is_student`, `experience_level`) makes exactly the row shape this
resumability mechanism needs to write — "I have `first_name` and nothing else yet" —
impossible to insert at all.

**What must change:** `last_name`, `company`, `position`, `is_student`, and
`experience_level` must become nullable. §2's resumability derivation (§2.2) treats
"required-but-currently-null" as the well-defined, expected mid-form state — the
`NOT NULL` floor that currently exists is exactly the "no invalid state is
representable" property REQ-010 was written for, but that floor was designed before this
requirement's partial-write rule existed, and the two are now in direct conflict on these
five columns.

**`first_name` — recommend making it nullable too, for uniformity, not because any
acceptance criterion forces it.** `first_name` is always the very first field asked
(fixed order, §2.1), so in practice the only row ever inserted mid-form already has
`first_name` set — a schema that kept `first_name NOT NULL` and relaxed only the other
five would still work for every acceptance criterion as written. This design recommends
relaxing all six uniformly anyway: `isProfileComplete` (§2.3) then reads as one uniform
rule ("all six required columns are non-null") rather than "five null-checked columns plus
one column whose NOT NULL constraint happens to be load-bearing for row-existence
itself," and a future reordering of the required-field sequence (a decision this artefact
does not make and has no reason to anticipate) would not silently require a second schema
change. This is a recommendation for `DATA-DESIGNER`'s own artefact to accept or reject on
its own reasoning — not something this artefact can bind by itself.

**A second, genuinely new piece of state is needed: distinguishing "skipped" from "not
yet reached" for the five optional fields.** `NULL` on `phone`/`email`/`links_github`/
`links_linkedin`/`links_site` already means "no value" — but this requirement needs a
*third* readable state for the optional segment specifically: "the person was asked and
tapped Skip" vs. "the form has not reached this field yet." Both currently read back as
`NULL`; without a way to tell them apart, a restart mid-optional-segment cannot correctly
resume (the derivation in §2.2 would re-ask an already-skipped field, or worse, be unable
to tell "complete because every optional field was explicitly skipped" from "abandoned
before reaching the first optional field" for §2.3's completeness check). AC2 itself
("skipping every optional field still completes the profile") requires *some* durable
record that a skip happened, distinct from "was never asked" — a value derived purely from
existing nullable columns cannot make this distinction. **Recommendation (not binding —
DATA-DESIGNER's call): five boolean flags, one per optional field** (e.g.
`phone_skipped`, `email_skipped`, `links_github_skipped`, `links_linkedin_skipped`,
`links_site_skipped`), `NOT NULL DEFAULT false`, following this schema's own existing
convention for plain per-row booleans (`is_student`, `publish_consent`). A single
combined column (a `jsonb`/`text` array of skipped-field names) is the considered
alternative; this artefact does not pick between the two, since that is exactly the kind
of storage-shape call `DATA-DESIGNER`'s prior artefacts (REQ-014-schema.md,
REQ-016-schema.md) have made for comparable questions.

**No separate "current form step" cursor column is proposed**, deliberately, mirroring
this codebase's established computed-never-stored discipline (REQ-017's
`computeSeatsLeft`/`isRegistrationOpen`, cited explicitly as the pattern this design
follows): §2.2's `determineNextProfileField` derives the next step by walking the fixed
field order and reading already-persisted column state (including the skip flags above) —
there is nothing a separate step-number column would represent that isn't already fully
implied by which columns are null/non-null/skipped. Introducing one would create a second
source of truth that could drift from the actual column state (e.g. a crash between
writing a field and advancing a stored cursor) — the exact class of bug pure derivation
avoids by construction.

**Summary of the schema change this design depends on** (for DATA-DESIGNER's artefact to
formalize): relax `NOT NULL` on the six required `profiles` columns; add a durable
"explicitly skipped" marker for each of the five optional columns (shape — five booleans
vs. one array column — left open). **`CODE-DESIGN-VALIDATOR` should treat this design as
incomplete until a `docs/agents/design/REQ-019-schema.md` exists covering this**, per the
REQ-014/REQ-016 precedent cited above.

**Resolved:** `docs/agents/design/REQ-019-schema.md` (DATA-DESIGNER) now covers both
changes — `NOT NULL` relaxed on all six required columns, and five booleans
(`phone_skipped`, `email_skipped`, `links_github_skipped`, `links_linkedin_skipped`,
`links_site_skipped`, each `NOT NULL DEFAULT false`) chosen over a combined array/JSONB
column. `ProfileRecord`'s field list (§2.2 above) matches that shape exactly.

## 2. `domain/profile.ts` (new)

Framework-free (decisions/0004): no grammY import. Every function here is pure or a
single-purpose DB call, mirroring `domain/venue.ts`/`domain/event.ts`'s established split.

### 2.1 Field order — fixed, matches the requirement's own listed sequence

```
REQUIRED_PROFILE_FIELDS = ["firstName", "lastName", "company", "position", "isStudent", "experienceLevel"]
OPTIONAL_PROFILE_FIELDS = ["phone", "email", "linksGithub", "linksLinkedin", "linksSite"]
```

Both orders are exactly the order the requirement text lists them in. No acceptance
criterion or requirement text motivates a different order for any field, so none is
invented.

```
export type RequiredProfileField = (typeof REQUIRED_PROFILE_FIELDS)[number];
export type OptionalProfileField = (typeof OPTIONAL_PROFILE_FIELDS)[number];
export type ProfileField = RequiredProfileField | OptionalProfileField;
```

### 2.2 Reading current state and deriving the next step — pure, no I/O beyond the read

```
export interface ProfileRecord {
  firstName: string | null;
  lastName: string | null;
  company: string | null;
  position: string | null;
  isStudent: boolean | null;
  experienceLevel: string | null; // "user" | "builder" | "advanced" | "expert"
  phone: string | null;
  email: string | null;
  linksGithub: string | null;
  linksLinkedin: string | null;
  linksSite: string | null;
  phoneSkipped: boolean;
  emailSkipped: boolean;
  linksGithubSkipped: boolean;
  linksLinkedinSkipped: boolean;
  linksSiteSkipped: boolean;
}

export async function getProfileByUserId(
  db: DbClient["db"],
  userId: string,
): Promise<ProfileRecord | null>;
// SELECT <every column above> FROM profiles WHERE user_id = $userId LIMIT 1
```

`ProfileRecord`'s shape depends directly on §1's schema change (the five `*Skipped`
booleans do not exist on `profiles` today) — `getProfileByUserId` cannot be implemented
until that lands.

```
export type ProfileFieldStep = { kind: "field"; field: ProfileField } | { kind: "complete" };

export function determineNextProfileField(
  profile: ProfileRecord | null,
): ProfileFieldStep;
```

Rule, stated exactly (never re-derived differently by a caller):

| Step | Check | Result |
|---|---|---|
| 1 | `profile === null`, or any of `REQUIRED_PROFILE_FIELDS` in fixed order is `null`/`undefined` on it | `{ kind: "field", field: <the first such required field name, in the fixed §2.1 order> }` |
| 2 | All six required fields are non-null, and at least one of `OPTIONAL_PROFILE_FIELDS` in fixed order is BOTH null AND not marked skipped (its matching `<field>Skipped` flag is `false`) | `{ kind: "field", field: <the first such optional field name, in the fixed §2.1 order> }` |
| 3 | All six required fields are non-null, and every optional field is either non-null or marked skipped | `{ kind: "complete" }` |

This function never touches consent or chapter state — those are `domain/onboarding.ts`'s
concern (§3), layered on top. It has no side effects and requires no DB access beyond the
`ProfileRecord` its caller already fetched via `getProfileByUserId`.

```
export function isProfileComplete(profile: ProfileRecord | null): boolean;
// Equivalent to determineNextProfileField(profile).kind === "complete" — a thin,
// separately named predicate purely because callers outside the step-progression flow
// (e.g. a future REQ-020 registration precondition) read it as a yes/no fact, not a
// "what's next" instruction. Never reimplements step 1-3's logic independently.
```

### 2.3 Validation rules — stated as tables, not expressions

```
export function isNonBlank(value: string): boolean;
// Rule: true only if value, after trimming leading/trailing whitespace, has length > 0.
// Applies to every free-text required field (firstName, lastName, company, position) and
// to a typed (non-skipped) answer for phone/linksGithub/linksLinkedin/linksSite.
```

```
export function isValidEmailFormat(value: string): boolean;
// Rule (AC6's "format-validated only if given"): accepts a single conventional
// local-part@domain shape — a non-empty local part, an "@", and a domain containing at
// least one "." with a non-empty label on each side, no internal whitespace anywhere in
// the string. Rejects a blank string, a string with no "@", a string with no "." in the
// domain portion, or any embedded whitespace. The exact expression (regex vs. a
// structured parse) is BACKEND-DEV's implementation choice; this design fixes only the
// acceptance boundary in this table, not a specific expression. Called ONLY when the
// caller has already confirmed the raw answer is non-blank (§4.4 step for the email
// step) — an absent email never reaches this function at all, which is what makes AC6's
// "validated only if supplied" branch structural rather than an extra `if` the handler
// has to remember.
```

```
export function isValidStudentAnswer(value: "yes" | "no" | string): boolean;
// Rule: true only for the exact tokens "yes" or "no" (case-insensitive) — used by the
// text-block edit path (§4.2); the guided step-by-step flow (§4.4) never calls this at
// all, since it collects the answer from a two-button keyboard whose two callback values
// are already exactly "yes"/"no" by construction (§4.5).
```

```
export function isValidExperienceLevelAnswer(value: string): boolean;
// Rule: true only for one of the four literal tokens "user", "builder", "advanced",
// "expert" (case-insensitive) — REQ-010's already-fixed closed set
// (docs/agents/design/REQ-010.md §7, "'user'|'builder'|'advanced'|'expert', app-level enum
// check"). Same split as isValidStudentAnswer: only the text-block edit path (§4.2) calls
// this; the guided flow (§4.4) collects the answer from a four-button keyboard whose
// callback values are already exactly these four tokens.
```

### 2.4 Writing an answer — insert-if-absent, else update-one-column

```
export async function writeRequiredProfileField(
  db: DbClient["db"],
  userId: string,
  field: RequiredProfileField,
  value: string | boolean,
  at: Date,
): Promise<void>;
```

Behavior, stated exactly (mirrors `resolveOrCreateUser`'s insert-or-update shape,
`domain/user.ts` §2.2, adapted to a single named column rather than a fixed set):
1. `INSERT INTO profiles (user_id, <field's column>) VALUES ($userId, $value)
   ON CONFLICT (user_id) DO UPDATE SET <field's column> = $value, updated_at = $at`
   — the existing `profiles_user_id_unique` index (REQ-010) is exactly the conflict
   target this upsert needs; no new index is required.
2. This is the ONLY write path for a required field, used identically whether the row
   does not exist yet (the very first answer, in practice always `firstName`) or already
   exists (every subsequent required answer, and any later edit via §4.2).

```
export async function writeOptionalProfileField(
  db: DbClient["db"],
  userId: string,

  value: string,
  at: Date,

// Same upsert shape as writeRequiredProfileField, additionally clearing that field's
// <field>Skipped flag back to false in the same statement (answering a field after

```

```
export async function markOptionalProfileFieldSkipped(
  db: DbClient["db"],
  userId: string,
  field: OptionalProfileField,

### 2.5 Reading for the view surface

```
export function formatProfileDump(
  profile: ProfileRecord,
  catalog: ReturnType<typeof getCatalog>,
): string;
```
Same composition discipline as `formatVenueDump` (`handlers/venue.ts`): one line per
field, catalog-provided label prefix, a catalog placeholder for "skipped" for a field
whose `*Skipped` flag is true, a catalog placeholder for "not set" for a null,
not-skipped optional field, and the raw stored value otherwise. Includes phone/email as
plain text exactly as stored — this is the OWNER's own data shown back to themselves
(S3's exception: a member reading their own Profile is not the "another person's
Profile" case S3 exists to prevent), so S11's log/error/audit redaction rule (§6) does
NOT apply to this one reply — it is a direct reply to the same person whose data it is,
never a log line, error message, or audit payload.

## 3. `domain/onboarding.ts` (new) — the shared consent → chapter → profile progression engine

Framework-free domain logic (decisions/0004) plus one function that also sends the
prompt, since "what to ask" and "asking it" are the same atomic step in every existing
handler in this codebase's convention (e.g. `assignChapterOrPrompt` already both decides
and replies in one function, `handlers/start.ts`).

### 3.1 The composed step

```
export type OnboardingStep =
  | { kind: "consent-needed" }
  | { kind: "chapter-needed" } // signal only — chapter's own 0/1/2+ branching stays in domain/chapter.ts, reused unchanged
  | { kind: "profile-field"; field: ProfileField }
  | { kind: "ready" };

export function determineOnboardingStep(
  hasConsented: boolean,
  hasChapter: boolean,
  profile: ProfileRecord | null,
): OnboardingStep;
```

Rule, stated exactly:

| Step | Check | Result |
|---|---|---|
| 1 | `!hasConsented` | `{ kind: "consent-needed" }` |
| 2 | `hasConsented && !hasChapter` | `{ kind: "chapter-needed" }` |
| 3 | `hasConsented && hasChapter`, and `determineNextProfileField(profile)` (§2.2) returns a field | `{ kind: "profile-field", field: <that field> }` |
| 4 | all three satisfied | `{ kind: "ready" }` |

This ordering is REQ-014's own already-established order (consent before chapter,
per that requirement's security rework) with profile appended as the natural third
onboarding stage — not a reordering of anything REQ-014 already fixed.

### 3.2 The composed entry point — the ONE function every handler calls

```
export async function advanceOnboarding(
  ctx: Context,
  db: DbClient["db"],
  userId: string,
  hasConsented: boolean,
  hasChapter: boolean,
  lang: BotLang,
): Promise<"prompted" | "ready">;
```

Behavior:
1. `profile = hasConsented && hasChapter ? getProfileByUserId(db, userId) : null` — never
   reads the `profiles` table at all while consent is outstanding (§0.2's "no write
   before the gate opens" guarantee extended to reads: there is nothing to read yet
   either).
2. `step = determineOnboardingStep(hasConsented, hasChapter, profile)`.
3. `"consent-needed"` → send the existing consent prompt (§3.3 reuses
   `handlers/start.ts`'s `buildConsentKeyboard`/`consent.prompt`, exported, not copied)
   → return `"prompted"`.
4. `"chapter-needed"` → **not handled here** — the caller (§3.3) runs
   `assignChapterOrPrompt` (existing, `handlers/start.ts`, unchanged) itself, since that
   function already both decides the 0/1/2+ branch and sends whichever reply, and already
   returns `"stopped" | "continue"` — `advanceOnboarding` is called again by the same
   caller only once chapter assignment resolves to `"continue"` (or was never needed).
   This keeps `domain/chapter.ts`'s existing, already-reviewed branching untouched rather
   than re-expressed inside this new function.
5. `"profile-field"` → send that field's prompt (§4.4's per-field prompt builders) →
   return `"prompted"`.
6. `"ready"` → return `"ready"`, no reply sent — the CALLER decides what "ready" means for
   its own context (greeting, for `/start`'s three call sites; the profile view surface,
   for `/profile` — §3.3/§4.1).

### 3.3 Call sites — one new, three modified

- **New:** `handlers/profile.ts`'s `/profile` command (§4.1) calls `advanceOnboarding`
  first; on `"ready"` it renders the view surface (§2.5) instead of a greeting.
- **Modified — `handlers/start.ts`, three places**, each currently ending
  `await ctx.reply(getCatalog(finalLang).start.greeting);` (or the equivalent early
  return): `makeStartHandler`'s tail, `makeChapterCallbackHandler`'s tail, and
  `makeConsentCallbackHandler`'s tail (its non-deep-link branch only — the deep-link
  branch, §resolveEventDeepLink, is untouched; a deep-link open is its own separate flow
  REQ-016/017 already fully specified and this requirement does not touch it). Each is
  changed to: run its existing consent/chapter logic exactly as today, then call
  `advanceOnboarding`; on `"prompted"`, return (the reply was already sent by
  `advanceOnboarding`); on `"ready"`, send the existing `start.greeting` exactly as
  before. **No behavioral change for any user whose profile is already complete or who
  has not yet reached the profile stage in a way this requirement's own acceptance
  criteria exercise** — the greeting is byte-for-byte the same reply it always was in
  that case.
- `buildConsentKeyboard`, `CONSENT_AGREE_CALLBACK_PATTERN`, and the module-level
  `matchText` helper in `handlers/start.ts` are changed from file-private to `export`ed,
  reused as-is by `handlers/profile.ts` (§4.1) rather than duplicated — these are the
  exact same consent prompt and callback pattern, not a parallel copy, since `/profile`'s
  consent gate is not a "genuinely different predicate" the way REQ-018 §0.2 justified a
  parallel authorization module; it is the identical one-time gate.

## 4. `handlers/profile.ts` (new)

### 4.1 `/profile` (no arguments)

```
export function makeProfileCommandHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence:
1. `tgId = ctx.from?.id`; `undefined` → return (existing convention).
2. `flowUser = getFlowUserByTgId(db, BigInt(tgId))`; `null` → reply
   `profile.startFirst` (new catalog key — a plain "run /start first" nudge; this bare
   command is the only place in this design that can be reached by someone who has never
   run `/start` at all), return.
3. `lang = resolveLang(flowUser.lang, flowUser.chapterDefaultLang)`.
4. `outcome = advanceOnboarding(ctx, db, flowUser.id, flowUser.consentPdAt !== null,
   flowUser.chapterId !== null, lang)`.
5. `"prompted"` → return (§3.2 already sent the next question).
6. `"ready"` → `profile = getProfileByUserId(db, flowUser.id)` (guaranteed non-null by
   `"ready"`'s own definition, §3.1 step 4) → reply
   `formatProfileDump(profile, getCatalog(lang))` followed by `profile.editHint` (a
   static line naming `/profile_edit` and `/profile_chapter`).

### 4.2 `/profile_edit` — text-block partial update (reuses the venue/event CRUD convention)

```
export function makeProfileEditHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
export function parseProfileEditFields(text: string): Record<string, string>;
// Identical shape/behavior to parseVenueFields/parseEventFields (domain/venue.ts §2.2,
# domain/event.ts §2.1) — same file, moved to domain/profile.ts since it is this

Recognized labels and their rule (unrecognized labels ignored, per `parseVenueFields`'s
own forward-compatible precedent; a label simply absent from the text leaves that field
untouched — this is a partial update, not a full replace, unlike venue/event's CREATE):

| Label | Field | Rule |
|---|---|---|
| `first_name` | `firstName` | non-blank (§2.3 `isNonBlank`) |
| `last_name` | `lastName` | non-blank |
| `company` | `company` | non-blank |
| `position` | `position` | non-blank |
| `student` | `isStudent` | exactly `yes`/`no` (§2.3 `isValidStudentAnswer`) |
| `experience` | `experienceLevel` | one of `user`/`builder`/`advanced`/`expert` (§2.3 `isValidExperienceLevelAnswer`) |
| `phone` | `phone` | the literal token `skip` (case-insensitive) marks it skipped (§2.4); any other non-blank value is accepted as-is (no format rule, per this requirement's own scope) |
| `email` | `email` | the literal token `skip` marks it skipped; any other non-blank value must pass `isValidEmailFormat` |
| `github` | `linksGithub` | the literal token `skip` marks it skipped; any other non-blank value accepted as-is |
| `linkedin` | `linksLinkedin` | same as `github` |
| `site` | `linksSite` | same as `github` |

Handler sequence: parse gate identical to §4.1 steps 1-3; `advanceOnboarding`'s "ready"
check first (editing presupposes onboarding is already past the gate — an edit attempt
while `!hasConsented` or profile incomplete replies with whatever `advanceOnboarding`
already sends, exactly like §4.1, rather than a separate "not ready to edit yet"
message); on `"ready"`, parse the command's text, validate, and for every entry in
`updates`: `"skip"` → `markOptionalProfileFieldSkipped`; a required field's value →
`writeRequiredProfileField`; an optional field's value → `writeOptionalProfileField`.
Any label that failed its own rule is reported back in one reply (`profile.editRejectedPrefix`
+ the invalid label names) and **none** of that submission's updates are applied — an
all-or-nothing edit, avoiding a half-applied edit from a single malformed line.

### 4.5 The generic step-answer listeners — the resumability mechanism's read side

Two listeners, registered in `index.ts` (`bot.on("message:text", ...)` and
`bot.on("message:contact", ...)`), each re-deriving state fresh on every incoming
message — **never** trusting anything held in process memory, which is the whole
property AC1 tests.

```
export function makeProfileTextAnswerHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```
Sequence:
1. `text = ctx.message?.text`; `undefined`, blank, or starts with `"/"` → return
   (defers to `bot.command(...)` handlers, which are matched by grammY independent of
   registration order for `/`-prefixed text — this guard exists so this generic listener
   never intercepts a slash command's own argument text).
2. **Phone step's typed-answer branch and its plain-text "Skip" button share this same
   listener** (Telegram sends a tapped reply-keyboard button as an ordinary text
   message identical in shape to typed input) — matched by exact string equality against
   `catalog.profile.skipButton` for the current language, ahead of step 3's general
   handling, so a tap of that specific button is treated as a skip regardless of which
   field is current. This is the one place in this design where a Skip affordance is
   matched by literal button text rather than `callback_data` (§8.4).
3. `flowUser = getFlowUserByTgId(...)`; `null` → return (a `/`-less message from someone
   who never ran `/start` has nothing to answer).
4. `hasConsented`/`hasChapter` from `flowUser`; `profile = getProfileByUserId(...)`.
5. `step = determineOnboardingStep(hasConsented, hasChapter, profile)`; not a
   `"profile-field"` step, or the field it names is not a free-text-capable one
   (`firstName`/`lastName`/`company`/`position`, or `phone`/`linksGithub`/
   `linksLinkedin`/`linksSite` when not already handled by step 2) → return (this
   message is not a profile-step answer; this requirement defines no other meaning for
   an unmatched plain text message).
6. Required field → `isNonBlank(text)`; false → re-send that field's own prompt with a
   leading `profile.invalidAnswerPrefix` line (never echoing the rejected text); true →
   `writeRequiredProfileField(...)`.
7. Optional field (`phone`/`linksGithub`/`linksLinkedin`/`linksSite`) → `isNonBlank(text)`;
   false is impossible to reach meaningfully here since a blank message is filtered at
   step 1 — any non-blank text is accepted as-is → `writeOptionalProfileField(...)`.
   `email` is handled by this same branch except it additionally calls
   `isValidEmailFormat(text)` first; false → re-send the email prompt with
   `profile.invalidEmailFormat` (never echoing the rejected text — **this is AC5's
   concrete "error path"**, §6), no write; true → `writeOptionalProfileField(...)`.
8. After any successful write in steps 6/7: call `advanceOnboarding` again (now that the
   just-answered field is persisted, its own fresh read will move past it) to send the
   next prompt, or, if that call returns `"ready"`, send `profile.completedNotice` (a new
   catalog key marking the guided flow's own completion, distinct from `/profile`'s view
   surface which a returning user reaches deliberately).

```
export function makeProfileContactHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```
Sequence: same resolution as steps 3-5 above, but only ever meaningful when the derived
step names `phone`; any other step → return (a shared-contact message arriving outside
the phone step has nothing defined for it — this requirement does not attempt to guess
intent). On the `phone` step: `contact = ctx.message?.contact`; `undefined` → return;
else `writeOptionalProfileField(db, flowUser.id, "phone", contact.phone_number, new
Date())`, then the same step-8 "advance and prompt next" behavior as the text handler.

```

export function makeProfileSkipCallbackHandler(db: DbClient["db"]) {

}
export function makeProfileStudentCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
export function makeProfileExperienceCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Each follows the identical **derive-current-step-first, then gate the write on it**
discipline §4.5 states for the text/contact listeners — restated here explicitly, in the
same order, so no implementer reads §4.6 as "write first, re-check after":

1. Resolve `flowUser` from `ctx.from?.id` (as §4.1); `null` → answer the callback query,
   no reply, no write, return (mirrors §4.5 step 3 — a callback from someone who never
   ran `/start` has nothing to write against).
2. Answer the callback query (Telegram UX requirement — always happens, regardless of
   what follows; answering is not a write to `profiles` and carries no consent
   implication).
3. `hasConsented`/`hasChapter` from `flowUser`; `profile = getProfileByUserId(...)`
   (identical shape to §4.5 step 4 — this read itself never happens while
   `!hasConsented`, per §3.2 step 1's short-circuit, since a caller with no consent has
   `profile` fixed at `null` by construction rather than by this handler remembering to
   skip the read).
4. `step = determineOnboardingStep(hasConsented, hasChapter, profile)` (§3.1) — computed
   fresh from current DB state on every single callback, exactly once, before any write
   function is named or called. This is the same call §4.5 step 5 makes and is the ONE
   authority for "what is this person currently allowed to answer."
5. **Gate:** the write is called if and only if `step.kind === "profile-field"` AND
   `step.field` equals the specific field this callback names (`"phone"`/`"email"`/etc.
   for skip; `"isStudent"` for student; `"experienceLevel"` for experience). Every other
   outcome — `step.kind` is `"consent-needed"`, `"chapter-needed"`, `"ready"`, or
   `"profile-field"` naming a *different* field than this callback claims to answer — is
   a **no-op**: no write function is called at all, and the handler proceeds straight to
   step 7 below. This is the explicit mechanism (not merely an asserted guarantee) behind
   the "stale/forged callback" case: a `profile:skip:phone`-shaped `callback_data`
   replayed or forged while `consent_pd_at IS NULL` derives `step.kind ===
   "consent-needed"` in step 4, fails this gate, and reaches no write function — the same
   structural impossibility §3.2 step 1 already gives every other path in this design,
   stated here in full rather than left as a one-line aside.
6. Only when step 5's gate passes: call the matching write —
   `markOptionalProfileFieldSkipped` for a skip callback; `writeRequiredProfileField`
   with `isStudent` set from the matched `"yes"`/`"no"` token for the student callback;
   `writeRequiredProfileField` with the matched level string for the experience callback.
7. Re-run `advanceOnboarding` (§4.5 step 8's identical "advance and prompt next, or
   announce completion" behavior) — this re-read is what advances someone whose write
   just landed, and is also what re-prompts (or shows the consent/chapter prompt) someone
   whose callback was no-op'd at step 5, so a stale tap never dead-ends silently.

A callback whose named field does not match the caller's actual current derived step
(e.g. a stale keyboard tapped after the field was already answered another way, while
still fully onboarded) therefore results in no write at all, followed by whatever
`advanceOnboarding` currently derives as next — never an error, and never a write
performed and only discovered stale afterward. This is a direct consequence of step 5's
gate ordering (derive, then compare, then write) rather than a property asserted
independently of the sequence that is supposed to produce it.

## 6. S11 — the PII redaction rule this design commits to (AC5)

**No function anywhere in `domain/profile.ts`, `domain/onboarding.ts`, or
`handlers/profile.ts` interpolates a raw `phone` or `email` value into: a log message
(`msg` string or a `LogFields` value under any key other than the literal keys `phone`/
`email`, which `log.ts`'s existing `REDACTED_KEYS` set already strips — REQ-012 §5,
pre-existing, unchanged by this requirement), an error/validation reply shown to any
user (§4.5 step 6/7's "re-send the prompt, never echoing the rejected text" rule), or a
`writeAuditLog` payload (moot per §0.3 — this requirement calls that function zero
times).**

The concrete negative case AC5 asks for — phone and email entered, then an error path
triggered — is §4.5 step 7's email-format rejection: the submitted (invalid) email string
is used only to call `isValidEmailFormat`, is never written anywhere (the `writeOptional
ProfileField` call is skipped on the `false` branch), never appears in the
`profile.invalidEmailFormat` reply, and is not passed to any `log.*` call this design
defines. If this handler logs the rejection at all (e.g. `log.info("profile field
rejected", { field: "email" })`), the fields object carries only the field NAME, never
the attempted VALUE — stated here as the binding rule for whoever implements it, not left
to be inferred.

| AC | Design element |
|---|---|

## 8. Open questions (not silently resolved)

1. **This design depends on a schema change no `DATA-DESIGNER` artefact has yet
   specified (§1).** ORCH should dispatch `DATA-DESIGNER` for
   `docs/agents/design/REQ-019-schema.md`, per the REQ-014/REQ-016 precedent, before
   `CODE-DESIGN-VALIDATOR` can treat this design as buildable. This artefact states the
   exact requirement (relax `NOT NULL` on six named columns; add a durable
   skip-vs-not-yet-reached marker for five named columns) but does not fix the final DDL
   or the skip-marker's concrete shape (five booleans vs. one array column).
2. **"Declining consent" has no dedicated UI affordance (§0.2)** — modeled as "has not
   yet accepted," re-showing the same one-button consent prompt. A future requirement or
   CONTENT-BA review may prefer an explicit second "Not now" button; not added here since
   nothing in REQ-019's text asks for one and inventing UI beyond what's asked for is
   outside this role's remit.
3. **AC4's own stated verification method ("running the registration flow") cannot
   literally execute — REQ-020 does not exist yet** (depends_on REQ-014/REQ-018 only).
   Interim substitute for `TEST-DESIGNER`: construct a user with a complete profile via
   this design's own `advanceOnboarding`/`/profile` entry points, then invoke
   `/profile` (or `advanceOnboarding` directly) a second time and confirm zero of the
   eleven field prompts are sent and the view surface (§2.5) renders instead. Flagged
   rather than silently substituted without saying so.
4. **The phone step's Skip affordance is matched by literal button text, not
   `callback_data` (§4.4, §4.5 step 2)** — the one asymmetry in this design's otherwise
   uniform callback-based Skip pattern, forced by the Telegram Bot API constraint that
   `request_contact` exists only on `KeyboardButton` (a reply keyboard), which cannot be
   combined with inline callback buttons in the same message. If BACKEND-DEV finds a
   cleaner mechanism within that same API constraint, this design has no objection to an
   equivalent alternative — the acceptance boundary is "one tap skips phone," not the
   specific button type.
5. **No global `bot.catch` handler exists in `apps/bot/src/index.ts` today** (confirmed
   by inspection — `index.ts`'s only `catch` is around `loadConfig` at startup, before
   `bot.start()`). This is a pre-existing gap, not something this requirement's own
   acceptance criteria require fixing (§4.5's validation-rejection paths are controlled,
   expected branches, not uncaught exceptions), so it is not fixed here — flagged for
   ORCH to file as its own issue per `ISSUE_QUEUE.md`, not resolved inside this design.
6. **Whether `/profile_chapter` should re-check consent/profile completeness before
   allowing a chapter change.** This design assumes no additional gate beyond
   `advanceOnboarding`'s existing "ready" check (§4.3) — chapter is treated as
   independent of profile-field state once someone has already reached "ready" once.
   Nothing in REQ-014 or REQ-019's text suggests chapter changes should ever be blocked
   by profile state, so no such rule is added.
