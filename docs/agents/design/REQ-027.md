# REQ-027 — Event cancellation notifies every non-withdrawn registrant, once

**Requirement:** GitHub issue #30, `docs/agents/requirements.yaml` REQ-027. PRD 14
build-order step 4; PRD 6 "Cancelling notifies every non-withdrawn registrant"; PRD 9
(transactional, ignores `broadcast_opt_in`); `security-invariants.md` S9 (idempotent per
`(registration, kind)`), S10 (transactional sends ignore `broadcast_opt_in`), S13
(deletion/anonymization preserves aggregates — the same "don't touch the historical
record" principle this requirement applies to cancellation). `depends_on: REQ-026`.

**Surface:** `apps/bot/**` only (bot requirement). No design tokens apply — same
"no tokens, Telegram messages only" note as REQ-018/020/021/022/023/024/025/026: this
requirement adds no user-visible screen on `apps/web`.

**Content shape:** new catalog keys only, placeholder/minimal functional copy per
`decisions/0002` — final wording owned by `CONTENT-BA`. Named precisely in §4.

## 1. Trigger mechanism — decided

**Synchronous, one-time batch send from the `/event_cancel` handler, right after
`cancelEvent`'s transaction commits.** Not a scheduled/polling job.

Reasoning:

- Cancellation is a one-time organizer action (a command invocation), not a
  time-based condition that needs re-evaluating on an interval — unlike REQ-026's T-24h/
  T-3h reminders, which fire when the clock crosses a threshold and must therefore be
  polled by `scheduler/runner.ts`'s `ScheduledJobDefinition` mechanism. There is no
  "threshold" here: the moment to notify is exactly the moment the organizer's
  `/event_cancel` command succeeds.
- `apps/bot/src/domain/event.ts`'s `cancelEvent` (REQ-016) is a single `db.transaction`
  that does exactly two writes — the `events.status` UPDATE and one `audit_log` INSERT —
  and its own header comment states the explicit scope boundary: "no read of the
  registrations table, no notification composition/send of any kind. REQ-027's scope."
  This requirement does not reopen that transaction or add a third write inside it.
  Reasons:
  1. A cancellation can have dozens of non-withdrawn registrations; sending Telegram
     messages is `NotificationSender` I/O (network calls to the Telegram Bot API), and
     `cancelEvent`'s domain module is deliberately framework-free (no `grammy` import,
     `event.ts`'s own header note) — it has no way to reach a `NotificationSender` even
     if it wanted to.
  2. `sendLedgeredNotification` (REQ-025) does its own atomic ledger INSERT per
     registration and is not itself transactional with any caller-supplied transaction —
     REQ-026's reminder jobs already establish the precedent of calling it in a plain
     `for` loop, **after** the state change that made the registrations eligible has
     already committed, never inside the same DB transaction as that state change.
- `apps/bot/src/handlers/withdraw.ts`'s `makeWithdrawConfirmCallbackHandler` is the
  closest same-file precedent for "call the state-changing domain function, then, only
  once its transaction has returned, synchronously call a notification function before
  replying to the actor" — used there for the single promoted registrant (REQ-023). This
  requirement is the same shape, generalized from one registrant to a list.
- `apps/bot/src/scheduler/reminderJobs.ts`'s `makeReminder24hJob`/`makeReminder3hJob` are
  the closest precedent for "iterate eligible registrations, call
  `sendLedgeredNotification` once per registration in a plain sequential loop" — reused
  directly here, minus the `ScheduledJobDefinition` wrapper (there is no interval; this
  runs exactly once, invoked by the handler).

Net design: one new orchestration function that combines withdraw.ts's "call right after
the domain write commits, before the handler's own reply" placement with
reminderJobs.ts's "select the eligible set, then loop `sendLedgeredNotification` over it"
body — see §2, §3.

## 2. New read: `domain/registration.ts`

```
export interface NonWithdrawnRegistrant {
  registrationId: string;
  userId: string;
}

export async function selectNonWithdrawnRegistrantsForEvent(
  db: DbClient["db"],
  eventId: string,
): Promise<NonWithdrawnRegistrant[]>;
```

**Rule (stated in prose, not code):** a plain, unfiltered-by-time `SELECT` of
`registrations.id` (returned as `registrationId`) and `registrations.userId` from the
`registrations` table, where `registrations.eventId` equals the given `eventId` AND
`registrations.admission` is NOT `'withdrawn'`. No join to `events` and no `startsAt`/
`endsAt` window is applied — unlike `domain/reminders.ts`'s
`selectRegistrationsForReminderWindow`, which filters on the event's timing because a
reminder is only meaningful in a specific window before the event starts. A cancellation
notice is due to every non-withdrawn registrant regardless of how far away the event was,
so this read has no time predicate and needs no `evaluationTime` parameter (a deliberate
difference from `decisions/0006`'s "explicit evaluation time" discipline, which applies
only to functions that compare against the current instant — this one does not).

This is a plain `SELECT`, not `SELECT ... FOR UPDATE`: it is read-only and is not part of
any write transaction (§1's reasoning — the send batch runs entirely after `cancelEvent`'s
transaction has already committed).

Placed in `domain/registration.ts` alongside the file's other registration-set reads
(`getMyRegistrations`, `getWaitlistPosition`), matching that file's existing convention
that any query shaped "rows from `registrations`, filtered/joined" lives here rather than
in `domain/event.ts`.

## 3. New compose + orchestration functions: `handlers/event.ts`

Placed in the same file as `makeEventCancelHandler`, mirroring exactly where
`handlers/withdraw.ts` places its own `sendPromotionNotification` (a compose-and-send
helper that composes a message from already-known event/registration facts and calls
`sendLedgeredNotification`) — not in a `domain/` module, per that established precedent,
and not in `scheduler/`, since nothing here is interval-driven (§1).

```
async function composeCancellationMessage(
  db: DbClient["db"],
  registrationId: string,
  eventTitle: string,
  lang: BotLang,
): Promise<ComposedMessage>;
```

**Rule (stated in prose):** re-fetches the registration's *current* admission via the
already-existing `getRegistrationAdmissionAndEvent(db, registrationId)` (REQ-026,
`domain/registration.ts`) — the same at-send-time freshness recheck
`composeReminder24h`/`composeReminder3h` already perform, called here for the identical
reason: `sendLedgeredNotification` invokes `composeMessage` only *after* its ledger
`INSERT` has committed (REQ-025 §3.1 step 5), so the registration's own admission can, in
principle, have changed between §2's batch selection and this individual send (e.g. the
registrant withdrew in the seconds between). Table of outcomes:

| Condition at send time | Result |
|---|---|
| Registration row not found, or its `admission` equals `'withdrawn'` | `{ kind: "skip" }` — surfaces as `SendOutcome.skipped-stale`; the already-committed ledger row is left in place, same accepted risk REQ-025 §3.2 and REQ-026 already name for their own skip cases. |
| Otherwise | `{ kind: "text", text: <composed message, §4> }` |

No re-check of `events.status` is needed here (unlike the reminder jobs' re-check of
`event.status === "published"`): this batch is only ever invoked once, synchronously,
immediately after `cancelEvent` has already flipped the event to `'cancelled'`, and there
is no "un-cancel" transition anywhere in the state machine (`event.ts`'s
`EventRecord.status` union is `"draft" | "published" | "cancelled"` with no path back) —
so the event's cancelled status cannot become stale between selection and send within the
same invocation.

```
export async function notifyNonWithdrawnRegistrants(
  db: DbClient["db"],
  sender: NotificationSender,
  eventId: string,
  eventTitle: string,
): Promise<void>;
```

**Rule (stated in prose):**

1. Calls `selectNonWithdrawnRegistrantsForEvent(db, eventId)` (§2) exactly once, to get a
   fixed snapshot list of `{ registrationId, userId }` — the list is read once before any
   sends begin, not re-queried mid-loop, so the batch's size is fixed at invocation time
   (this is what makes AC1's "exactly 5 notifications" a property of a single,
   well-defined batch rather than a moving target).
2. For each candidate in that list, in a plain sequential `for...of` loop (same shape as
   `reminderJobs.ts`'s `makeReminder24hJob`/`makeReminder3hJob` `run()` bodies — no
   `Promise.all`/concurrent fan-out), calls `sendLedgeredNotification` once, with the
   following fields:

   | Field | Source |
   |---|---|
   | `db` | the `db` parameter of `notifyNonWithdrawnRegistrants` |
   | `sender` | the `sender` parameter of `notifyNonWithdrawnRegistrants` |
   | `registrationId` | `candidate.registrationId` |
   | `kind` | the literal string `"event_cancelled"` |
   | `classification` | the literal string `"transactional"` |
   | `userId` | `candidate.userId` |
   | `composeMessage` | a function of `lang` that calls `composeCancellationMessage` with `db`, `candidate.registrationId`, the `eventTitle` parameter of `notifyNonWithdrawnRegistrants`, and that `lang` |

3. The per-call `SendOutcome` is not inspected or aggregated — same `Promise<void>`,
   "fire the whole batch, do not act on individual outcomes" contract
   `sendPromotionNotification` already establishes for its single-registrant case. No AC
   requires the handler to branch on send success; AC1/AC2 are properties of the ledger
   and the captured sends, verified externally by TEST-DESIGNER's spec, not by anything
   this function returns.

**`evaluationTime` is deliberately not a parameter of this function or of §2's read** —
see §2's note. Nothing in this requirement's scope compares against the current instant;
the *timing* of "when to run this batch" is entirely the handler's responsibility (it
runs once, right after `cancelEvent` returns), not something this function decides.

`makeWithdrawConfirmCallbackHandler(db, sender)`'s existing shape exactly:

```
export function makeEventCancelHandler(
  db: DbClient["db"],
  sender: NotificationSender,

```

**Call-site ordering inside the handler (prose, not code):** unchanged through the
existing authorization/state checks and the `cancelEvent(...)` call. Immediately after

## 6. AC2's idempotency argument (why cancelling twice, or restarting mid-batch, sends nothing extra)

Structurally identical to REQ-025's own idempotency guarantee (S9), which REQ-026 already
relied on unchanged for its own AC-equivalent, extended here to a batch of many
registrations instead of one:

1. `notification_ledger` carries `uniqueIndex("uq_notification_ledger_registration_kind")
   .on(registrationId, kind)` (schema.ts, unchanged by this requirement — §"Schema change:
   NO" above).
2. `sendLedgeredNotification`'s step 4 is the **only** place a ledger row is ever written,
   and it is a single atomic `INSERT`. A repeat `INSERT` for the same
   `(registrationId, "event_cancelled")` pair hits that unique index and raises Postgres
   error code `23505`, which `sendLedgeredNotification` classifies as
   `{ kind: "skipped-already-sent" }` — no send, no error surfaced to the caller.
3. This guarantee is **per registration**, not per batch-run, and holds regardless of
   *why* the function is invoked twice: an organizer literally re-running `/event_cancel`
   on an already-cancelled event (refused earlier anyway by the existing
   `event.status !== "published"` guard, so this path is actually unreachable through the
   command surface) — or, the case the AC is really naming, a process restart or crash
   mid-batch. Because `notifyNonWithdrawnRegistrants` keeps **no in-memory state of its
   own** (no local "already sent" set, no counter) — the same "idempotency lives entirely
   in the DB constraint, never in memory" property `security-invariants.md` S9 states
   explicitly ("idempotency enforced by an in-memory set that a restart clears" is named
   there as the exact negative case to avoid) — re-running the whole batch (or the
   REQ-027 handler being invoked again by any means, or `notifyNonWithdrawnRegistrants`
   being called a second time over the same `eventId`) reduces every one of its 5 calls to
   `sendLedgeredNotification` to step 4's duplicate-key branch, which sends nothing.
4. This is exactly the same argument REQ-026's own design already made for its two
   scheduled jobs (which restart on every process boot and re-select the same candidates
   until each is no longer eligible) — this requirement adds no new mechanism, only a new
   call site and a new `kind` value flowing through the existing one.

## 7. Acceptance criteria — mapped

| AC | Design element |
|---|---|
| AC1 — 3 admitted + 2 waitlisted + 1 withdrawn → exactly 5 notifications, none to the withdrawn one | §2's `selectNonWithdrawnRegistrantsForEvent` excludes `admission = 'withdrawn'` at the SQL `WHERE` clause — the withdrawn registration is never in the batch list at all. §3's `composeCancellationMessage` re-excludes on the same condition at send time (defense in depth against a race). §3's `notifyNonWithdrawnRegistrants` calls `sendLedgeredNotification` exactly once per list entry — 5 entries, 5 calls, 5 sends (none `skipped-*` under normal conditions since none of the 5 are withdrawn or blocked in the scenario as stated). |
| AC2 — cancelling twice / restarting mid-batch adds no messages, counted across both runs | §6, the full idempotency argument: `uq_notification_ledger_registration_kind`'s uniqueness is what makes a repeat `sendLedgeredNotification` call for the same `(registrationId, "event_cancelled")` pair a guaranteed no-op, with no in-memory state anywhere in this design. |
| AC3 — `broadcast_opt_in=false` registrant still receives the cancellation message | §5's `notifyNonWithdrawnRegistrants` passes `classification: "transactional"` on every call — `sendLedgeredNotification`'s step 3 (the only place `broadcastOptIn` is ever read) is gated on `classification === "marketing"`, so a transactional call never reads or is affected by `broadcastOptIn` at all (matches S10's rule and REQ-025's own AC3 precedent, reused unchanged). |
| AC4 — every `registrations` row for the event still exists with `admission` UNCHANGED after cancellation | Structural, not defended by any new check: no function introduced by this requirement (`selectNonWithdrawnRegistrantsForEvent`, `composeCancellationMessage`, `notifyNonWithdrawnRegistrants`) issues any `UPDATE`/`DELETE` against `registrations` — every one of them is read-only or write-only-to-`notification_ledger`. `cancelEvent` (REQ-016, unchanged by this requirement) only ever `UPDATE`s `events.status` and inserts one `audit_log` row — its header comment's explicit scope boundary ("no read of the registrations table") is preserved, not reopened, by this design. |
| AC5 — message offers the upcoming events list as an onward path | §4: the composed text's third line is the literal existing `catalog.event.deepLinkSeeUpcoming` string, reused unchanged from REQ-017/REQ-016's deep-link-not-available path, not a new or differently-worded string. |

## 8. Open questions

1. **Send-failure-after-ledger-commit risk (accepted, not new).** If `sender.send(...)`
   throws inside `composeCancellationMessage`'s caller after step 4's ledger `INSERT` has
   already committed, `sendLedgeredNotification` returns `{ kind: "failed", error }` and
   the ledger row stays in place — that registrant will never be notified by a retry of
   this batch (the unique-index check will treat them as already sent). This is the same
   accepted, named risk REQ-025 §3.2 and REQ-026 already carry for their own sends,
   restated here rather than re-solved, since no AC in this requirement's scope exercises
   a mid-send network failure.
2. **A withdraw racing with the cancellation batch, landing between §2's `SELECT` and that
   same registrant's `sendLedgeredNotification` call.** §3's at-send-time recheck in
   `composeCancellationMessage` closes this for the common case (the withdraw commits
   before this particular registrant's turn in the loop), but a withdraw that commits
   *after* `getRegistrationAdmissionAndEvent`'s read inside `composeCancellationMessage`
   but *before* the message is actually sent is not caught — the registrant would receive
   a cancellation notice for a registration they had just withdrawn from seconds earlier.
   No AC in this requirement exercises that exact interleaving; named here rather than
   silently resolved, and left as pre-existing residual risk of the same shape REQ-026
   §9 already accepts for its own reminder jobs.
3. **Ordering of the batch relative to the event's other registrants' own concurrent
   actions (e.g. someone registering for the now-cancelled event mid-batch).** Not
   possible through the normal registration path — `registerForEvent`'s own state-machine
   guard refuses registration against a non-`'published'` event, and by the time this
   batch runs `cancelEvent` has already committed `events.status = 'cancelled'` — so this
   is named only to confirm it was considered, not because any gap was found.
4. **Synchronous batch send blocks the bot's single-threaded long-poll loop for large
   registrant counts (accepted for Release-1, not resolved).** `apps/bot/src/index.ts`
   line 195 calls `bot.start()` with no `@grammyjs/runner` concurrent dispatcher wired
   in, so grammy's default long-polling processes one update at a time, sequentially.
   `notifyNonWithdrawnRegistrants` is `await`ed synchronously inside the
   `/event_cancel` handler, **before** the handler's own `ctx.reply(...)` confirmation
   (§5) — so for an event with many non-withdrawn registrants, the organizer's own
   confirmation is delayed, and every other user's bot interaction is held up for the
   same duration, since the single-threaded poll loop cannot process the next update
   until this handler's `await` resolves. The duration is bounded by
   `scheduler/rateLimiter.ts`'s pacing (roughly N/25 seconds for N registrants) but
   otherwise grows unboundedly with N. No repo-local PRD volume/capacity figures for
   Release-1 chapter/event sizes were found to bound how large N can realistically get,
   so this cannot be dismissed as clearly out of range on that basis alone. No AC in
   this requirement exercises event scale, so this is not a blocking gap against any
   AC — this design accepts it as a known Release-1 limitation rather than introducing
   fire-and-forget dispatch or bounded concurrency: PRD 1's explicit "do not add
   infrastructure" stance rules out introducing `@grammyjs/runner` or a job queue for
   this one call site, and fire-and-forget (not `await`ing
   `notifyNonWithdrawnRegistrants` before the organizer's reply) would reorder AC1's
   "notifications sent" guarantee to happen after the handler has already returned,
   with no mechanism in this design to surface a failure of the detached call back to
   the organizer or to any caller — a strictly worse guarantee than the current
   synchronous ordering for no proven volume benefit at Release-1's expected chapter
   sizes. If real Release-1 usage later shows this delay is actually reached in
   practice, the fix belongs in a future requirement (e.g. a bounded-concurrency send
   or a genuine background job), not as a silent addition to this one.
