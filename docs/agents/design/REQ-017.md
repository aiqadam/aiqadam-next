# REQ-017 — Public event card and the `/events` upcoming list with computed seat counts

**Requirement:** third slice of PRD 14 build-order step 2, completing "public event
card." Implements PRD FR-2 (Event card), USER-STORIES A1 ("See what's coming up") and A3
("Know where it is and how to get there"). depends_on: REQ-016.

**Surface:** `apps/bot/**` (bot requirement). **No schema change.** Every field this
design reads already exists: `events.*`, `chapters.timezone`, `venues.*`,
`registrations.admission` (REQ-011/REQ-010 schema, unchanged by this requirement). Step
1b can verify this in one pass: no `db/schema.ts` edit is proposed anywhere in this
document, and every read below is a `SELECT` against an existing column.

**Files this design expects:**
- `apps/bot/src/domain/event.ts` (existing, REQ-016) — extended with the three
  computed-never-stored predicates (§1), the chapter-scoped upcoming-events query (§4),
  and the card-content assembly function (§3)
- `apps/bot/src/domain/venue.ts` (existing, REQ-015) — reused unchanged
  (`getVenueById`) for the card's venue block
- `apps/bot/src/i18n/formatTimeInTimezone.ts` (new) — the chapter-timezone rendering
  mechanism (§2), framework-free, no grammY import
- `apps/bot/src/handlers/event.ts` (existing, REQ-016) — new `/events` handler (§4.2)
- `apps/bot/src/handlers/start.ts` (existing, REQ-016) — the deep-link resolution
  branch for a published event is rewired to call this design's card-rendering function
  instead of REQ-016's placeholder (§6)
- `apps/bot/src/i18n/types.ts`, `ru.ts`, `en.ts` — new `events.*` catalog keys, §7
- `apps/bot/src/index.ts` — registers `/events`

---

## 0. Reuse decisions, stated up front

- **`/events` is a plain, unauthenticated read**, exactly like REQ-015 §3's `/venues`
  (`makeVenuesListHandler`) — scoped to the caller's own `chapterId`, **not** gated by
  `requireOrganizerForChapter`/`checkOrganizerForChapter`. Any member may run it. This
  mirrors `/venues`'s own "§3's own scope note" precedent exactly: listing published data
  back to the person it's published for is not a mutation and carries no organizer-only
  concern.
- **The event card is rendered by one function, called from two places**: (a) REQ-016's
  `/start` deep-link handler (`resolveEventDeepLink` in `handlers/start.ts`, replacing its
  `deepLinkPublishedPlaceholder` line), and (b) nowhere else in this requirement — `/events`
  renders **list rows**, not full cards, per the requirement's own text ("each row
  showing title/date-time/venue/seats," not "each row followed by a full card"). Whether a
  future requirement makes a list row tappable into its own card is explicitly not decided
  here (§8.1).
- **No new authorization module.** Reading `chapters.timezone` and rendering a card needs
  no `ActingUser` resolution beyond what already exists (`resolveActingUser` from
  `domain/eventAuthorization.ts`, reused for `/events`'s own chapter lookup — see §4.2's
  own note on which of the two near-identical `resolveActingUser` exports it calls).

## 1. Computed-never-stored predicates (AC3, AC4)

Three pure functions, no I/O, added to `domain/event.ts` alongside REQ-016's existing
pure predicates (`validateAgenda`, `findMissingPublishFields`) in the same file, same
style. **None of the three may ever be written to a column, cached in a variable that
outlives a single request, or denormalized onto `EventRecord`.**

```
// domain/event.ts

// PRD 5: seats left = capacity - count(admission='admitted'). The admitted count is
// always read fresh via countAdmittedRegistrations (already exists, REQ-016 §3.4) —
// this function is a one-line arithmetic step over that already-fetched number, kept
// separate from the query so the arithmetic itself is unit-testable without a DB.
function computeSeatsLeft(capacity: number, admittedCount: number): number {
  return capacity - admittedCount;
}

// PRD 5: whether registration is currently open. evaluationTime is an explicit
// parameter (decisions/0006) — this function never reads the clock itself. A null
// registrationClosesAt means "no registration deadline configured" -> always open.
function isRegistrationOpen(
  registrationClosesAt: Date | null,
  evaluationTime: Date,
): boolean {
  if (registrationClosesAt === null) {
    return true;
  }
  return evaluationTime.getTime() < registrationClosesAt.getTime();
}

// PRD 5: whether the event itself is over. Same evaluation-time-as-parameter
// discipline. Consistent with REQ-016 §6.4(c)'s already-stated "unfinished" bound:
// ends_at, not starts_at, is the correct not-yet-over bound.
function isFinished(endsAt: Date, evaluationTime: Date): boolean {
  return evaluationTime.getTime() > endsAt.getTime();
}
```

**Seats-left-or-waitlist-open composition** (used identically by both the card and the
list row): given `seatsLeft = computeSeatsLeft(event.capacity, admittedCount)`,

- `seatsLeft > 0` → render the seats-left count (`events.cardSeatsLeft` /
  `events.listRowSeatsLeft`, interpolated with `seatsLeft`).
- `seatsLeft <= 0` → render "waitlist open" (`events.cardWaitlistOpen` /
  `events.listRowWaitlistOpen`). This holds regardless of whether `isRegistrationOpen`
  is true — a full event with registration still open is exactly the waitlist case PRD 5
  describes; whether registration is *closed* on top of being full is not a distinct
  render state this requirement's acceptance criteria ask for (no AC mentions a
  registration-closed row/card state), so `isRegistrationOpen` is exported for future
  requirements (REQ-020's registration flow needs it to refuse a closed-registration
  attempt) but **is not itself rendered** anywhere in this design. Stated explicitly
  rather than silently wired into a card/list state nobody asked for (§8.2).

**AC3/AC4 mapping:** every one of the three functions above takes its inputs as plain
parameters and returns a plain value with no side effect — `git grep -n
"seats_taken\|seats_left\|registration_open\|finished"` across `apps/bot/src` after this
requirement ships must find these three function/parameter *names* only in this file's
pure-function signatures and their call sites' local variables, never a column
definition in `db/schema.ts` or a field on `EventRecord`.

## 2. Chapter-timezone rendering (AC2)

### 2.1 Mechanism

**`Intl.DateTimeFormat` with an explicit `timeZone` option sourced from
`chapters.timezone`.** `chapters.timezone` is a `text` column holding an IANA timezone
name (confirmed against `docs/agents/design/REQ-010.md` §7's schema table: `timezone`
text, "IANA tz name, e.g. `Asia/Tashkent`" — the same convention `docs/agents/design/
REQ-010.md` line 256 states verbatim). **Never** `process.env.TZ`, never
`Date.prototype.toLocaleString()` called without an explicit `timeZone` option (both
would silently fall back to the server's or the runtime's default zone, which is exactly
what AC2 tests against by deliberately mismatching the process's `TZ`).

```
// apps/bot/src/i18n/formatTimeInTimezone.ts — framework-free, no grammY import,
// no I/O (decisions/0004). Pure function: (Date, IANA tz string, BotLang) -> string.

import type { BotLang } from "./catalog.js";

// BotLang -> BCP-47 locale, for Intl's own month-name/weekday-name localization.
// Only "ru"/"en" exist today (catalog.ts); a third BotLang is out of this
// requirement's scope to anticipate.
const INTL_LOCALE: Record<BotLang, string> = { ru: "ru-RU", en: "en-US" };

export function formatDateTimeInTimezone(
  at: Date,
  timezone: string,
  lang: BotLang,
): string {
  return new Intl.DateTimeFormat(INTL_LOCALE[lang], {
    timeZone: timezone,
    year: "numeric",
    month: "short",
    day: "2-digit",
    hour: "2-digit",
    minute: "2-digit",
  }).format(at);
}
```

**Why this satisfies AC2 exactly:** `Intl.DateTimeFormat`'s `timeZone` option converts
the UTC instant stored in the `timestamptz` column (drizzle/`pg` already returns a JS
`Date`, which is always a UTC instant internally — a `Date` object carries no zone of its
own) into wall-clock fields for the *named* zone, independent of `process.env.TZ` or the
V8 default `Intl` locale data's own default zone. Running the process with `TZ=UTC` (or
any zone other than the chapter's) produces byte-identical output to running it with
`TZ` unset, because the function never consults the ambient zone at all — it is supplied
explicitly on every call. This is the literal mechanism AC2's own verification
instruction asks for ("run the check with the process TZ deliberately set to a DIFFERENT
zone... confirming the rendered time is unchanged").

**One function, one call site pattern, reused everywhere a timestamp renders:**
`formatDateTimeInTimezone` is called for `event.startsAt`, `event.endsAt` (only where the
card needs an end time — see §3.2), every `agenda[]` item's `at`, and the `/events` list
row's date/time — always with the **event's chapter's** `timezone`, never the caller's
own chapter (an organizer or member deep-linked from a different chapter's event still
sees that event's own chapter-local time, since the value has no relationship to the
viewer's chapter at all).

### 2.2 Where the chapter timezone comes from, concretely

`EventRecord` (domain/event.ts) does not currently carry the chapter's timezone — only
`chapterId`. Two read shapes are needed and both are plain joins, no new tables:

```
// domain/event.ts — new read, joins events -> chapters for exactly the one column the
// card/list needs beyond what getEventById already returns.
export interface EventWithChapterTimezone extends EventRecord {
  chapterTimezone: string;
}

export async function getEventByIdWithChapterTimezone(
  db: DbClient["db"],
  eventId: string,
): Promise<EventWithChapterTimezone | null>;
// SELECT events.*, chapters.timezone AS chapter_timezone
// FROM events JOIN chapters ON chapters.id = events.chapter_id
// WHERE events.id = $eventId
```

`/events`' own list query (§4.1) selects `chapters.timezone` directly in the same
`SELECT` as the event rows, for the same reason — one join, not a per-row follow-up
query (this project's stated load, PRD 1, makes a naive N+1 harmless in absolute terms,
but a single join is no more code and is the obviously correct shape).

## 3. Event card rendering (AC1, AC5)

### 3.1 Content shape

```
// domain/event.ts — pure assembly, no I/O, no grammY import. Takes every already-
// fetched piece of data as a parameter; the handler is responsible for fetching the
// event, its venue, its chapter timezone, and the admitted count before calling this.
export interface EventCardContent {
  title: string;
  coverFileId: string | null;
  dateTimeText: string;          // formatDateTimeInTimezone(startsAt..endsAt range)
  venueName: string | null;      // null only if venue_id is null (§3.3's own open Q)
  venueAddress: string | null;
  yandexMapUrl: string | null;
  googleMapUrl: string | null;
  agendaLines: { timeText: string; label: string }[]; // one per agenda[] item, in
                                                        // stored array order
  seatsLine: { kind: "seatsLeft"; count: number } | { kind: "waitlistOpen" };
  ctaText: string;               // §3.4 — plain text, not an inline button
}

export function buildEventCardContent(
  event: EventWithChapterTimezone,
  venue: VenueRecord | null,
  admittedCount: number,
  lang: BotLang,
): EventCardContent;
```

`buildEventCardContent` is pure composition over already-fetched rows — it performs no
DB read itself, consistent with the existing split in this file between pure functions
and I/O-performing ones (§4's `validateEventUpdateInput` vs. `updateEvent`).

### 3.2 Field-by-field mapping to PRD FR-2's card elements

| FR-2 element | Source | Design element |
|---|---|---|
| Title | `event.title` | `EventCardContent.title`, rendered verbatim |
| Cover | `event.coverFileId` | §3.5 — sent as a Telegram photo message using the stored `file_id` |
| Date/time in chapter timezone | `event.startsAt`, `event.endsAt`, `chapterTimezone` | `formatDateTimeInTimezone` applied to both; rendered as a range, e.g. `"Oct 1, 2026, 18:00–20:30"` (start and end formatted separately, joined with an en dash — a plain string composition, not a new Intl option) |
| Venue name + address | `venue.name`, `venue.address` | Rendered as two lines under a `events.cardVenueLabel` heading. If `event.venueId` is `null` (schema allows it even though REQ-016 §3.3 established every *publishable* event needs one — a defensive case, not a reachable one for a card only ever rendered for a published event, §6's reuse note), `venueName`/`venueAddress` are both `null` and the card renders no venue block at all rather than an empty label |
| BOTH map links | `venue.yandexUrl`, `venue.googleUrl` | Both are `NOT NULL`-equivalent in practice: REQ-015 §2.3 requires both at venue creation (`validateVenueCreateInput` refuses a venue missing either), so a `VenueRecord` read through `getVenueById` always has both populated for any venue that exists. Rendered as two separate lines/labels (`events.cardMapYandex`, `events.cardMapGoogle`), each the raw URL — no link-shortening, no new component |
| Coordinates-optional rendering (STORY-DETAILS A3) | `venue.lat`, `venue.lon` | **Resolution, stated explicitly because the requirement's own text could be misread as depending on the map links:** `lat`/`lon` are never displayed as their own field anywhere in this card design (no design element reads them at all) — the two map link URLs are stored, static text on the `venues` row (REQ-015), not derived from `lat`/`lon` at render time. So "venue without coordinates renders address text only" is satisfied by construction: the address line renders unconditionally from `venue.address` (`NOT NULL`), and there is no coordinate-derived line that could be present or absent depending on `lat`/`lon` — a venue with `lat`/`lon` both `null` produces byte-identical card output to one with both set. This is the design's answer to the requirement text's "no coordinates" case; it is not a branch in the code, it is the absence of any code path that would have read those two columns |
| Agenda | `event.agenda` (JSONB array) | `agendaLines`, one entry per stored item, in stored array order (no re-sorting — REQ-016 §7.2 already establishes the array is validated/replaced as a whole, and nothing about ordering was ever specified as anything other than array order), each item's `at` formatted via `formatDateTimeInTimezone` |
| Seats left / waitlist open | `event.capacity`, live `countAdmittedRegistrations` | `seatsLine`, per §1's composition rule |
| CTA | — | `ctaText`, §3.4 |
| LINEUP | — | **Absent.** No field in `EventCardContent` represents a talk lineup. Release 3 scope (PRD 5's Talk entity does not exist yet — `git grep -n "talks\b" apps/bot/src` finds nothing), stated here per the requirement's own instruction so the omission reads as deliberate, not an oversight found later |

### 3.3 Venue name/address when `venueId` is null

Not exercised by any acceptance criterion (a card is only ever rendered for a published
event, and REQ-016 §3.3 already established every publishable event has a `venue_id`),
but `buildEventCardContent` handles it defensively — `venue: VenueRecord | null` — rather
than assuming its caller always supplies a non-null venue. This is the same
defense-in-depth posture REQ-016 §3.4 site 1 already uses for `publishEvent`'s
capacity re-check.

### 3.4 The CTA, resolved explicitly (open question named in the task, answered here)

**Resolution: the CTA is plain reply text, not an inline keyboard button.**

Reasoning:
- Registration itself (writing a `registrations` row, admission logic, capacity
  atomicity) is REQ-020's scope, not built by this requirement or any requirement that
  exists yet. An inline button needs a `callback_data` value that some registered
  `bot.callbackQuery(...)` handler resolves — building that button now would create a tap
  target with **no handler wired to it at all**, which either does nothing when tapped
  (Telegram shows a loading spinner that never resolves, or grammY's default "no handler
  matched" behavior — an genuinely broken UI element sitting live in production) or
  requires inventing a stub handler now that REQ-020 would then have to find and replace,
  duplicating the exact "placeholder now, replace later" risk REQ-016 §5's closing note
  already named for cancellation notifications and explicitly avoided.
- This project's own established precedent (REQ-016 §6.4(a)/(b)) is to use a plain
  catalog string that points at a still-unbuilt capability rather than half-build a
  UI-shaped stub for it (`deepLinkSeeUpcoming` names `/events` in plain text rather than
  rendering a fake list). The CTA follows the identical discipline: `events.cardCta`, a
  plain text line telling the reader what to do next (e.g. "Reply here to register — this
  event doesn't accept registrations yet" as functional placeholder copy, CONTENT-BA owns
  final wording per decisions/0002), not an interactive control.
- **What this design explicitly does NOT do:** it does not add a `bot.callbackQuery`
  registration, does not add a `register:<event-id>` callback-data convention, and does
  not reserve UI space for a button REQ-020 would need to fill in. When REQ-020 exists,
  its own design is the right place to decide whether the CTA becomes an
  `InlineKeyboard` button (grammY, already imported elsewhere in this codebase,
  `handlers/start.ts`) wired to a real registration flow — that is a design decision for
  REQ-020 to make with its own acceptance criteria, not one this requirement should
  guess at. Flagged as open question §8.3.

### 3.5 Cover rendering — how `cover_file_id` becomes a Telegram message

**Resolution:** a Telegram Bot API `sendPhoto` call (grammY's `ctx.replyWithPhoto`),
passing the stored `cover_file_id` string directly as the `photo` parameter, with the
card's full text (§3.1's assembled content, composed into one string per §3.6) as the
`caption`. Telegram's Bot API accepts a previously-uploaded `file_id` interchangeably
with a fresh upload or URL for this parameter — no re-upload, no fetch of the file
content by this bot, consistent with `cover_file_id`'s own column comment ("the
file-id," already established as a Telegram file identifier by REQ-011/REQ-016, this
requirement does not change how the value gets there, only how it's consumed at render
time).

**When `event.coverFileId` is `null`:** a plain `ctx.reply` with the same assembled text
as the caption would have been — no photo message sent, no placeholder image, no empty
`sendPhoto` call. This is a straight two-branch choice in the handler (`if coverFileId
!== null: replyWithPhoto(coverFileId, { caption: text }) else: reply(text)`), not a new
domain function — sending a Telegram message is I/O the handler performs directly, the
same layering `handlers/start.ts`/`handlers/event.ts` already use for every `ctx.reply`
call in this codebase.

**Caption length:** Telegram's `sendPhoto` caption is capped at 1024 characters (a
platform limit, not a design choice this document is inventing). A long agenda could
plausibly exceed it. This design does **not** add truncation or a "read more" split —
no acceptance criterion tests caption length, and no fixture data in this codebase's
existing tests approaches that size. Flagged as open question §8.4 rather than silently
truncating agenda content, which would be a silent data-loss risk for exactly the
element (agenda) AC5 tests for completeness.

### 3.6 Text composition order

One newline-joined string, section order matching FR-2's own listed order (title, cover
handled separately per §3.5, date/time, venue+address+both map links, agenda, seats
line, CTA) — the same "compose a template literal / join array, no conditional
reordering" discipline REQ-015/016's own reply-composition functions
(`formatVenueDump`, `formatEventDump`) already use. No new component, no HTML/Markdown
parse mode is introduced (plain text, matching every other bot reply in this codebase —
`parse_mode` is never set anywhere in `handlers/`).

## 4. `/events` upcoming list (AC6)

### 4.1 Query

**Exact filter, using the evaluation-time-as-parameter rule (decisions/0006) — never SQL
`now()`/`current_timestamp` inside the query:**

```
// domain/event.ts
export interface UpcomingEventListItem {
  id: string;
  title: string;
  startsAt: Date;
  endsAt: Date;
  capacity: number;
  venueName: string;
  chapterTimezone: string;
}

export async function listUpcomingPublishedEvents(
  db: DbClient["db"],
  chapterId: string,
  evaluationTime: Date,
): Promise<UpcomingEventListItem[]>;
// SELECT events.id, events.title, events.starts_at, events.ends_at, events.capacity,
//        venues.name AS venue_name, chapters.timezone AS chapter_timezone
// FROM events
// JOIN chapters ON chapters.id = events.chapter_id
// LEFT JOIN venues ON venues.id = events.venue_id
// WHERE events.chapter_id = $chapterId
//   AND events.status = 'published'
//   AND events.ends_at > $evaluationTime
// ORDER BY events.starts_at ASC
```

This is the exact filter REQ-016 §6.4(c) already documented as the correctness property
this requirement must preserve — restated here as the actual implemented query, not a
note for later. `LEFT JOIN venues` (not `JOIN`) because a defensively-possible
`venue_id IS NULL` row (§3.3) must not silently disappear from the list; `venueName`
is typed `string` in `UpcomingEventListItem` on the optimistic assumption every real
published row has one (§3.3's established invariant), but the query itself does not
enforce that with an inner join, since an inner join would make the list actively
mislead ("this chapter has zero upcoming events") if that invariant were ever violated,
rather than merely rendering one venue-less row oddly.

**Per-row seats computation:** `listUpcomingPublishedEvents` does not itself compute
seats — it returns `capacity`. The handler calls `countAdmittedRegistrations(db,
event.id)` per row (§1's composition rule) after the list query returns, same
"query returns raw facts, seats/waitlist is composed at render time" split as the card.
At this project's stated load (PRD 1: peak 0.06 rps) a per-row follow-up query for a list
that is realistically single-digit-to-low-double-digit rows per chapter is not a
performance concern worth a JOIN-based batch count; this is stated explicitly so nobody
reads the per-row query as an oversight (§8.5 names it as an open question anyway, for
the record, per this pipeline's "don't silently resolve" discipline even where the
answer seems obvious).

### 4.2 Handler and row format

```
// handlers/event.ts — new, alongside the existing event_* handlers.
export function makeEventsListHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => {
    // 1. resolveActingUser(db, tgId) from domain/eventAuthorization.ts — reused for
    //    its chapterId lookup only; no authorization check is applied to its result
    //    (§0's scope decision — this is a plain read, not gated by
    //    checkOrganizerForChapter).
    // 2. chapterId = actingUser?.chapterId ?? null. null -> same empty-state reply as
    //    zero rows (§4.3) — a user with no chapter yet has, by definition, no chapter
    //    of published events to show.
    // 3. list = listUpcomingPublishedEvents(db, chapterId, new Date())
    // 4. list.length === 0 -> §4.3's empty state.
    // 5. Otherwise, for each item: admittedCount = countAdmittedRegistrations(db,
    //    item.id); seatsLine = per §1's composition; dateTimeText =
    //    formatDateTimeInTimezone(item.startsAt, item.chapterTimezone, lang) — a
    //    range using item.endsAt the same way the card does (§3.2).
    // 6. Compose one row per item, one reply message (events.listHeader, then one
    //    line per row, newline-joined — same shape as /venues' listHeader/lines
    //    pattern in handlers/venue.ts).
  };
}
```

**Row format**, one line per event, following `/venues`' own `"${name} — ${address}"`
composition precedent, extended with the fields this requirement's own acceptance
criteria name:

```
<title> — <dateTimeText> — <venueName> — <seats-left-or-waitlist-open text>
```

e.g. `LLM Engineering in Production — Oct 1, 2026, 18:00 — Tashkent AI Hub — 12 seats
left` or `... — Waitlist open`.

No per-row interactivity (no inline button, no deep link) — this requirement's
acceptance criteria describe only what each row *shows*, never a tap action. Consistent
with §3.4's CTA resolution: this design does not invent an interaction surface no
acceptance criterion asks for.

### 4.3 Empty state (AC6)

Zero rows (or no chapter) → **one plain informational reply**, `events.followCityInvite`
— an invitation to follow the city, per STORY-DETAILS A1's explicit framing ("an
invitation... NOT an apology"). **No Wishlist row or table is created or referenced.**
`git grep -n "wishlist" apps/bot/src` must return nothing after this requirement ships;
the catalog string itself is static informational text with no persistence side effect
of any kind — the handler's empty-state branch performs no write, exactly like
`/venues`' own `venue.listEmpty` branch performs no write.

### 4.4 Draft/cancelled exclusion — confirming the two call sites independently

Per the task's explicit instruction to confirm this rather than assume it:

- **`/events`'s own query** (§4.1) filters `status = 'published'` directly — a member
  running `/events` can never see a draft or cancelled event's row, by construction of
  the `WHERE` clause, independent of anything the deep-link handler does.
- **The event-card renderer** (`buildEventCardContent`, §3) performs **no status check of
  its own** — it is a pure function over an already-fetched `EventWithChapterTimezone`
  and trusts its caller to have already verified `status === 'published'`. This is a
  deliberate reuse of REQ-016's existing gate: `handlers/start.ts`'s deep-link branch
  (§6.3 step 5) already refuses to reach the published-rendering branch at all for a
  draft/cancelled/finished/unknown event, before this requirement's card function is
  ever called. **Confirmed correct, not merely assumed:** the only call site this
  requirement wires the card function into is that already-gated branch (§6 below); no
  new call site is added anywhere that could reach `buildEventCardContent` with an
  unpublished event. If a future requirement adds a second call site (e.g. an organizer
  preview command for a draft event), that call site is responsible for its own gating —
  `buildEventCardContent` staying gate-free is consistent with this codebase's existing
  split between pure rendering/validation functions (which never gate) and handlers
  (which always gate before calling them), the same split REQ-016 §3.1/§7.1 already
  establish for `findMissingPublishFields`/`validateAgenda`.

## 5. `isFinished` and the deep-link's own draft/cancelled/finished branch

REQ-016 §6.3 step 5's existing check (`event.status !== "published"`) does **not** by
itself exclude a published-but-already-finished event from the deep-link's "available"
branch — REQ-016 never implemented an `isFinished` check because it hadn't been designed
yet. This requirement's `isFinished` (§1) closes that gap: **the deep-link handler's
call site is updated** (§6 below) to additionally treat a published-but-finished event
the same as a draft/cancelled one for rendering purposes — reusing the exact same
`deepLinkNotAvailable` + `deepLinkSeeUpcoming` reply REQ-016 §6.3 step 5 already sends,
now gated on `event.status !== "published" || isFinished(event.endsAt, new Date())`
rather than the status check alone. This is a direct, named fix to a gap REQ-016's own
requirement text left for this requirement (`requirements.yaml`'s REQ-017 description:
"finished is derived from now > ends_at" is listed as this requirement's own scope, and
the deep-link's "unavailable" branch is the one place in the existing codebase a
finished-event check was missing).

## 6. Updating REQ-016's deep-link handler (`handlers/start.ts`)

Two concrete edits to `resolveEventDeepLink` in `apps/bot/src/handlers/start.ts`,

## 8. Open questions (not silently resolved)

1. **Whether a future requirement should make `/events` rows tappable into a full card
   (§0).** This design renders `/events` as plain text rows with no per-row interaction,
   since no acceptance criterion asks for one. If a future requirement wants "tap a row
   to see the card," that is new UI surface (likely an inline keyboard, one button per
   row, `callback_data` carrying the event id) with its own design and its own
   acceptance criteria — not invented here.
2. **`isRegistrationOpen` is exported but not rendered anywhere in this design (§1).**
   It exists because REQ-020 will need it, but no card/list state in this requirement
   distinguishes "full and registration still open" from "full and registration closed."
   Flagged so REQ-020's own design consciously decides whether that distinction needs a
   render-visible state, rather than assuming this requirement already covered it.
3. **The CTA's eventual shape once REQ-020 ships (§3.4).** This design deliberately
   ships the CTA as plain text with no interactive element, reasoning that an
   unwired button is worse than no button. REQ-020's own design is the place to decide
   whether it becomes a real `InlineKeyboard` control.
4. **Cover-photo caption length vs. a long agenda (§3.5).** Telegram's `sendPhoto`
   caption cap (1024 chars) is not handled by any truncation/pagination in this design.
   No fixture or acceptance criterion currently produces a caption anywhere near that
   length, but a future event with many agenda items could. Left for whoever hits it
   first to decide between truncation, a follow-up text message, or dropping the photo
   in favor of a plain (uncapped) text reply for that one render.
5. **Per-row `countAdmittedRegistrations` call vs. a batched count query (§4.1).** Stated
   as a deliberate, load-justified choice (PRD 1's stated peak of 0.06 rps), not an
   oversight — but named explicitly per this pipeline's "don't silently resolve" rule,
   since a batched `GROUP BY event_id` count is the obvious alternative a reviewer might
   otherwise wonder was simply missed.
6. **`event.deepLinkPublishedPlaceholder`'s catalog key becomes dead after §6's edit**,
   and this design does not remove it from `types.ts`/`ru.ts`/`en.ts` — that is a
   separate i18n-parity edit with its own discipline (a removed key must be removed from
   all three files atomically, per REQ-013 §1.2's parity rule), left for whoever
   implements this design or a follow-up cleanup pass to actually perform, not silently
   left half-done here.
