## 0. Schema dependency — stated precisely, DDL left to DATA-DESIGNER

### 0.1 A new `feedback` table (PRD 5's `Feedback` entity, deliberately deferred from REQ-010/011)

Required, per the requirement text and AC2:

| Requirement | Reasoning |
|---|---|
| A column identifying which `Registration` this row belongs to, `NOT NULL`, with a **`UNIQUE`** constraint (or an equivalent unique index) | This single column is the entire mechanism behind AC2 — "attempting a second feedback row for the same registration fails on a database constraint, verified by attempting the duplicate insert directly." The uniqueness must hold at the database level, not merely be enforced by application code, precisely because AC2's own verification method is a raw duplicate `INSERT` that bypasses this design's own write functions entirely. |
| An NPS column, `NOT NULL`, holding an integer 0–10 | PRD FR-8's "NPS 0-10." `NOT NULL` is what makes "skipping NPS does not save a feedback row" true at the schema level (§1.3) — the row cannot exist at all without it. A `CHECK (nps >= 0 AND nps <= 10)` is recommended, mirroring this schema's existing `chk_*` convention (e.g. `chk_registrations_checked_in_only_if_admitted`), but the exact DDL is DATA-DESIGNER's call. |
| A "liked" column (`Feedback.liked`), nullable text | "what worked" — skippable (§1.3), so nullable, no format rule. |
| An "improve" column (`Feedback.improve`), nullable text | "what to improve" — skippable, same shape as `liked`. |
| A "topic votes" column (`Feedback.topic_votes`) | See §0.2 — shape recommended, not bound, exactly like REQ-019's skip-marker recommendation. |
| A durable "explicitly skipped" marker for `liked`, `improve`, and `topic_votes` — three columns or one combined structure | Same reasoning REQ-019 §1 already established for its five optional profile fields: `NULL` alone cannot distinguish "the person tapped past this question" from "the flow has not reached this question yet," and AC3 ("every question except NPS can be skipped and the feedback still saves") needs that distinction to be durable and resumable. **Recommendation (not binding): three booleans** — `liked_skipped`, `improve_skipped`, `topic_votes_skipped`, `NOT NULL DEFAULT false` — following the same per-field-boolean convention REQ-019-schema.md chose over a combined array/JSONB column for its own five skip markers. DATA-DESIGNER may choose differently for the same reasons it was free to choose differently there. |
| `created_at`/`updated_at` timestamps | This schema's universal convention on every table. |

**No "current step" cursor column is proposed**, for the identical reason REQ-019 §1
gives: `determineNextFeedbackField` (§2.2) derives the next step by reading already-
persisted column state, so a separate step-number column would be a second source of
truth that could drift from it.

### 0.2 `Feedback.topic_votes`'s shape — an explicit open question, not silently resolved

**No topic taxonomy exists anywhere in this schema today** — confirmed by inspection of
`apps/bot/src/db/schema.ts`: `events.agenda` is a free-form JSONB array of
`{ kind, at, label }` agenda items (non-talk items only, per its own comment), and no
`topics`/`tags` table or column exists for an event or a talk. The requirement text
supplies no fixed list of topics to vote on either.

Because of this, §3.4 below resolves "topic votes" as a **free-text, self-reported list**
(the respondent types the topics they'd like more of, not a selection from a
system-defined set) rather than an inline multi-select keyboard — a multi-select keyboard
would require a closed list of options that nothing in this codebase currently supplies.
**This is a deliberate design choice stated as an open question in §8**, not an invented
taxonomy: if product wants topic votes tied to the event's actual agenda items in a future
iteration, that is a materially different (and larger) feature this artefact does not
attempt to pre-empt.

Given that, the recommended shape is **an array of strings** (one entry per topic the
respondent typed) — a native Postgres `text[]` is the simplest fit for "an unordered list
of freeform strings with no need for per-item metadata." A `jsonb` column is the
considered alternative if DATA-DESIGNER prefers this schema's more common practice
elsewhere (`events.agenda`, `audit_log.payload` are both `jsonb`) over introducing the
first native array column in this schema. Left open, same as REQ-019's five-booleans-
vs-one-array choice.

### 0.3 A new column on `users`: distinguishing "never asked" from "asked and answered" for the broadcast opt-in

**This is design question 2, resolved as a required schema addition.** `users.
broadcast_opt_in` (existing, `boolean NOT NULL DEFAULT false`) cannot by itself
distinguish "this person has never been asked" from "this person was asked and declined"
— both read back as `false`. AC5 requires exactly this distinction: "the broadcast-opt-in
question is asked once; after the person declines, re-running the whole feedback flow for
a later event does not ask again, and `users.broadcast_opt_in` remains `false`."

**Required addition:** `broadcast_opt_in_asked_at`, a nullable `timestamp with time zone`
on `users`, set together with `broadcast_opt_in` on the exact same write the moment the
question is answered — mirroring this schema's own existing pairing convention for
`consent_pd_at`/`consent_pd_version` (REQ-014-schema.md §10: two columns written together
by the same statement, never one without the other). `NULL` means "never asked";
non-`NULL` means "asked, and `broadcast_opt_in` holds the answer that was given."

**Resolving the second half of design question 2 — does a prior "yes" also block re-
asking, not just a prior "no"?** Yes. The gate this design uses everywhere (§4.1) is
"has `broadcast_opt_in_asked_at` ever been set," never "did the person decline." The
requirement's own wording — "asked once... Declining is remembered and never asked
again" — names the decline case because that is the case STORY-DETAILS D1 is worried
about (nagging someone who already said no), but the mechanism that makes it true is
strictly "was the question ever asked," which necessarily also covers the "already said
yes" case with no separate rule needed. Treating "asked" as the single gate (rather than
"asked and the answer was no") is also the only reading under which the gate stays a
single boolean-shaped timestamp rather than needing to separately remember "yes, don't
ask again" vs. "no, don't ask again" as two different suppressions — there is exactly one
suppression condition, "already asked," regardless of the answer.

## 1. The interaction pattern, decided explicitly (design question 3)

### 1.1 DB-derived resumability (REQ-019's pattern), not message-text-carrier (REQ-030's pattern) — for the multi-step progression itself

The task names both precedents and asks which applies. Read against what actually differs
between them:

- **REQ-030's message-text-carrier trick exists to solve a problem this requirement does
  not have.** REQ-030 needed it because (a) S1 forbids writing anything — including a
  first partial row — before consent is confirmed, so there was nothing in the database
  yet to resume from during the very part of that flow that most needed resuming, and
  (b) `callback_data`'s 64-byte cap left no room to carry three free-text fields through a
  confirm/cancel round trip. Neither condition holds here: every feedback respondent is
  already a known, consented member (they hold an `admitted` registration with a non-null
  `checked_in_at` — S1 is already satisfied for them long before this flow starts), and
  no step of this flow needs to carry more than a single small token (an NPS digit, a
  registration id) through `callback_data`.
- **REQ-019's DB-derived resumability fits directly**, generalized from "six required +
  five optional columns on one singleton-per-user row" down to "one required (NPS) + three
  optional columns on one row keyed by registration." A `Feedback` row can be created the
  instant NPS is answered and updated one column at a time thereafter — exactly
  `writeRequiredProfileField`/`writeOptionalProfileField`'s shape, with only one required
  field instead of six. This also directly produces AC3's persistent-skip property and
  AC2's row-only-on-completion-of-the-required-field property, via the identical mechanism
  REQ-019 already uses (§1.3 below).

### 1.2 A genuinely new wrinkle neither precedent faced: disambiguating **which** flow a free-text reply belongs to

REQ-019's profile form is a singleton per user — there is only ever one profile, so a bare
incoming text message unambiguously belongs to "the" profile flow. **`Feedback` is 1:1
with `Registration`, not with `User`** (PRD 5) — the same person can hold multiple
registrations (different events, possibly close together in time), and this design's own
T+2h/T+24h jobs mean **more than one feedback flow can legitimately be "in progress" for
the same person at once** (e.g. two events ending a day apart). A bare `bot.on
("message:text", ...)` listener like REQ-019's cannot tell which registration's `liked`/
`improve`/`topic_votes` question a plain-text reply is answering.

**Resolution: every free-text-answerable prompt (`liked`, `improve`, `topic_votes`) is
sent with Telegram's `force_reply` reply markup, and carries a fixed, parseable pair of
lines in its own text (§3.1): "Feedback ref: `<registrationId>`" AND "Feedback field:
`<fieldName>`".** Telegram's ForceReply UI makes the user's client automatically set
`reply_to_message` on whatever they type next to point back at that exact prompt message —
this is standard Telegram Bot API behavior, not new application state. The generic text
listener (§6.3) reads `ctx.message.reply_to_message.text`, extracts both the registration
id AND the specific field the REPLIED-TO message was actually asking about from these two
lines (§3.1's render/parse pair — the same class of mechanism REQ-030 §7.1 already
established for its own canonical-message re-parse, applied here to solve a different
problem: not carrying answer data, only disambiguating *which* row, AND *which field of
that row*, a reply belongs to), and proceeds only if BOTH (a) that registration's flow is,
per §2.2's fresh derivation, actually expecting a free-text answer right now, AND (b) the
field that derivation currently names is the SAME field the replied-to message's own
"Feedback field: " line encodes. A reply with no `reply_to_message`, one whose text carries
no "Feedback ref: "/"Feedback field: " lines, or one whose encoded field does not match the
currently-expected field, is treated as a no-op — the first two cases because it is not a
feedback-flow message at all (deferring silently to whatever else `message:text` listener a
message might belong to, REQ-019's own `makeProfileTextAnswerHandler`, most concretely, the
same "return with no side effect on no match" discipline that file already uses — confirmed
by reading its actual implementation, it never calls an explicit `next()`; both listeners
are simply registered on the same event and each independently no-ops on a message it does
not recognize), and the third case (§6.3 step 8, below) because it is a stale reply to an
already-superseded prompt: the respondent replied to an OLDER force_reply message (Telegram
permits replying to any older message, and §6.5 relies on old prompts staying repliable
indefinitely) whose own field is no longer the field the flow is currently waiting on, and
writing the reply's text to the CURRENTLY-expected field instead would silently misattribute
it to the wrong question. This encoded-field recheck at write time is exactly the same
"recheck at write time" pattern this design's own checkin/QR precedents (and §6.1/§6.2's
ownership and step gates) already use for every other stale-tap case — REQ-031 is now
consistent with itself rather than asserting a guarantee (§6.3 step 8) it did not actually
implement.

**Why not the same trick for `nps` or the broadcast-ask question:** both are answered via
inline keyboard taps, whose `callback_data` already carries the registration id directly
and unambiguously (§3.2, §3.3) — no disambiguation problem exists for them, so no
`force_reply`/ref-line mechanism is needed there.

**Why not combine an inline "Skip" button with `force_reply` on the same prompt:** the
Telegram Bot API's `reply_markup` field is a single object of one type — an inline
keyboard and `ForceReply` cannot both be attached to the same message. §3.1 resolves this
by making Skip a **typed reply keyword** (matched case-insensitively against the catalog's
`feedback.skipButton` text) rather than a button, for `liked`/`improve`/`topic_votes` —
this is the same "Skip matched by literal reply text" pattern REQ-019 §4.4/§4.5 already
uses for its own phone-step Skip (chosen there because `request_contact` cannot coexist
with an inline keyboard either), generalized here to every free-text-answerable field
rather than only one.

### 1.3 Exactly when the `Feedback` row is created — traced explicitly (the second half of design question 3)

**On the NPS answer, and only then — never on flow completion, never speculatively
earlier.** Table, stated exactly (mirrors REQ-019 §2.2's convention of a first-match-wins
rule table rather than executable logic):

| Event | Row state after |
|---|---|
| The T+2h (or T+24h) prompt is sent | No `feedback` row exists yet. |
| Respondent taps an NPS button (0–10) | `writeFeedbackNps` (§2.3) performs the **first and only `INSERT`** for this registration — `registration_id`, `nps`; every other column left at its default (`NULL`/`false`). This is the sole path that ever creates a row. |
| Respondent never taps an NPS button (ignores the request entirely, or replies to `liked`/`improve`/`topic_votes` before ever answering NPS — structurally impossible, since those prompts are only ever sent *after* NPS is answered, §2.2) | **No `feedback` row exists at all.** This is exactly AC3's "skipping NPS does not save a feedback row" — made true structurally by there being no Skip affordance of any kind on the NPS step (§3.2 defines only numbered buttons, never a Skip button, and no code path in this design calls any feedback-writing function for `nps` other than a genuine 0–10 tap) and by `liked`/`improve`/`topic_votes` never being reachable before `nps` is non-null (§2.2's own ordering). |
| Respondent answers or skips `liked`/`improve`/`topic_votes` after NPS | `writeFeedbackOptionalField`/`markFeedbackFieldSkipped` (§2.4) **`UPDATE`s the existing row** (guaranteed to exist by the ordering above) — never an `INSERT`, never a second row. |

This also directly answers the task's traced alternative ("does NPS alone create the row
immediately since skipping NPS must not save anything"): yes, exactly that — NPS's answer
is both necessary and sufficient to create the row, and nothing else ever attempts to
create one.

### 1.4 Why `isFinished` is not reused here

REQ-017's `isFinished(endsAt, evaluationTime)` answers "has this event's `ends_at` already
passed" — a plain boolean. This design's own two scheduled jobs (§5) need a **relative**
comparison ("has at least 2 hours / 24 hours elapsed *since* `ends_at`"), which is a
different predicate shape (comparing `evaluationTime` against `endsAt` plus an offset, not
against `endsAt` alone) — reusing `isFinished` and separately checking an elapsed-time
threshold would be two checks doing the work of one. §5.2/§5.3's selection queries state
the actual comparison directly instead.

## 2. `domain/feedback.ts` (new)

Framework-free (decisions/0004): no grammY import. Time-dependent values are passed in as
explicit parameters (decisions/0006) — nothing here calls SQL `now()`/`current_timestamp`.

### 2.1 Field order — fixed, matches PRD FR-8's own listed order (NPS first, always un-skippable)

```
export type FeedbackField = "nps" | "liked" | "improve" | "topicVotes";
export const FEEDBACK_FIELD_ORDER: readonly FeedbackField[] =
```

| 5 | `nps` is non-null and `liked`/`improve`/`topicVotes` are each resolved | `{ kind: "complete" }` |

### 2.3 Writing the NPS answer — the one and only INSERT path (§1.3)

```
export function isValidNpsValue(value: number): boolean;
// Rule: true only if value is an integer and 0 <= value <= 10. The NPS callback (§6.1)
// only ever calls this defensively — the eleven buttons it sends (§3.2) already emit
// exactly these eleven values by construction, so a false result here is unreachable in
// ordinary use, the same "defensive, unreachable in practice" branch convention
// REQ-016/018/029/030 already document explicitly rather than silently.

export async function writeFeedbackNps(
  db: DbClient["db"],
  registrationId: string,
  nps: number,
  at: Date,
): Promise<void>;
// INSERT INTO feedback (registration_id, nps, created_at, updated_at) VALUES
// ($registrationId, $nps, $at, $at) ON CONFLICT (registration_id) DO UPDATE SET
// nps = $nps, updated_at = $at. The ON CONFLICT clause exists only so a person who
// re-taps a DIFFERENT NPS number before answering anything else can correct their
// answer (no acceptance criterion forbids this); it is never what makes AC2's "a second
// row fails on a database constraint" true -- that property comes from the schema's own
// UNIQUE constraint (§0.1) rejecting a raw duplicate INSERT that does not go through
// this upsert at all, which is exactly how AC2 states its own verification method.
```

### 2.4 Writing an optional answer, or marking it skipped — UPDATE only, never INSERT

```
export type FeedbackOptionalField = "liked" | "improve" | "topicVotes";

export async function writeFeedbackOptionalField(
  db: DbClient["db"],
  registrationId: string,
  field: FeedbackOptionalField,
  value: string | string[],
  at: Date,
): Promise<void>;
// UPDATE feedback SET <field's column> = $value, <field>Skipped = false,
// updated_at = $at WHERE registration_id = $registrationId. Clearing the skip flag on a
// direct answer mirrors REQ-019's writeOptionalProfileField (§2.4) — there is no
// "answered AND skipped" state. Reachable, by §2.2's own ordering, only once a row
// already exists (nps answered) — never performs an insert-if-absent, unlike §2.3.

export async function markFeedbackFieldSkipped(
  db: DbClient["db"],
  registrationId: string,
  field: FeedbackOptionalField,
  at: Date,
): Promise<void>;
// UPDATE feedback SET <field>Skipped = true, updated_at = $at WHERE registration_id =
// $registrationId. Never touches the field's own value column -- a skip leaves it NULL,
// distinguished from "not yet reached" purely by this flag, same as REQ-019 §2.4.
```

### 2.7 The composed flow step — layers the broadcast-opt-in ask on top of §2.2

```
export type FeedbackFlowStep =
  | { kind: "feedback-field"; field: FeedbackField }
  | { kind: "broadcast-ask" }
  | { kind: "complete" };

export function determineFeedbackFlowStep(
  feedback: FeedbackRecord | null,
  broadcastOptInAskedAt: Date | null,
): FeedbackFlowStep;
```

Rule, stated exactly:

| Step | Check | Result |
|---|---|---|
| 1 | `determineNextFeedbackField(feedback)` (§2.2) returns a field | `{ kind: "feedback-field", field: <that field> }` |
| 2 | §2.2 returns `"complete"`, and `broadcastOptInAskedAt === null` | `{ kind: "broadcast-ask" }` |
| 3 | §2.2 returns `"complete"`, and `broadcastOptInAskedAt !== null` | `{ kind: "complete" }` |

Step 2/3's gate reads `broadcastOptInAskedAt` from `users` — **a global, per-user value,
never per-registration** — which is exactly what makes AC5's "re-running the whole
feedback flow for a **later event** does not ask again" true structurally: the second
event's own `Feedback` row is a completely separate row (different `registration_id`), but
`determineFeedbackFlowStep` for it reads the SAME `users.broadcast_opt_in_asked_at` value
already set by the first event's flow, so step 2's condition is already false the second
time regardless of which registration is asking.

## 3. The rendered prompts and the ref-line render/parse pair (`domain/feedback.ts`)

### 3.1 Free-text prompts — `force_reply`, plus the disambiguating ref line (§1.2)

```
export function formatFeedbackTextPrompt(
  promptBody: string,
  registrationId: string,
  field: FeedbackOptionalField,
): string;
// Rule: promptBody, then a blank line, then two fixed-prefix lines, in this order:
// "Feedback ref: " + registrationId, then "Feedback field: " + field (the literal
// FeedbackOptionalField value -- "liked" | "improve" | "topicVotes"). Used for the
// liked/improve/topicVotes prompts only -- never for nps or the broadcast-ask (both
// button-driven, §3.2/§3.3, no ref line needed since callback_data already carries the
// registration id, and neither is a sibling of any other text-answerable field so no
// field-disambiguation problem exists for them either). The "Feedback field: " line is
// what §6.3 step 8's stale-reply recheck (§1.2) depends on -- without it, a reply to a
// superseded prompt for one field cannot be told apart from a reply to the current
// prompt for a different field.

export type ParseFeedbackReplyResult =
  | { ok: true; registrationId: string; field: FeedbackOptionalField }
  | { ok: false };

export function parseFeedbackReplyContext(
  repliedToText: string,
): ParseFeedbackReplyResult;
// Rule: split repliedToText on newlines. Find the first line starting with the exact
// literal prefix "Feedback ref: "; its value (everything after the prefix, trimmed) is
// the registrationId. Find the first line starting with the exact literal prefix
// "Feedback field: "; its value, trimmed, must equal exactly one of the three
// FeedbackOptionalField literals ("liked" | "improve" | "topicVotes") to be accepted as
// field. Either line missing, or the field line's value not one of those three exact
// literals -> { ok: false }. Both lines present and the field value valid -> { ok: true,
// registrationId, field }.
```

### 3.2 The NPS prompt — inline keyboard, no Skip button anywhere (§1.3, §2.1)

Eleven buttons, labels `"0"` through `"10"`, `callback_data` =
`"feedback:nps:" + <0-10> + ":" + registrationId` (well inside the 64-byte cap: the
longest instance, `"feedback:nps:10:"` at 16 bytes plus a 36-byte UUID, totals 52 bytes).
Laid out across more than one keyboard row — a row-count/wrapping detail with no
design-system implication (the bot surface has no visual/CSS component, §9).

### 3.3 The broadcast-ask prompt — inline keyboard, two buttons

`callback_data` = `"feedback:broadcast:yes:" + registrationId` /
`"feedback:broadcast:no:" + registrationId` (longest instance: 24 + 36 = 60 bytes, inside
the cap).

### 3.4 Parsing a free-text answer for `topicVotes`

```
export function parseTopicVotes(text: string): string[];
// Rule: split text on newlines and commas; trim each resulting segment; drop any
// segment that is empty after trimming; keep the remaining segments in the order they
// appeared. No de-duplication -- a respondent listing the same topic twice is not
// normalized here.
```

`liked`/`improve` need no parse function of their own — the raw, trimmed reply text is
the stored value (§2.4), identical in shape to REQ-019's optional free-text fields.

```
export function isFeedbackSkipReply(text: string, skipKeyword: string): boolean;
// Rule: true only if text, trimmed, equals skipKeyword, trimmed, case-insensitively.
```

## 5. The two scheduled jobs (`apps/bot/src/scheduler/feedbackJobs.ts`, new)

Reuses `scheduler/runner.ts`'s `ScheduledJobDefinition`/`startScheduledJobs`
infrastructure unchanged (REQ-025/026) — the third and final Release-1 consumer named in
the task. Both jobs call `sendLedgeredNotification` (REQ-025, `domain/notification.ts`,
reused unchanged) with **distinct `NotificationKind`s**, which is the entire mechanism
behind "both sends go through REQ-025's ledger with distinct kinds so neither can
double-send" (requirement text) and AC4's "exactly one reminder, nothing thereafter."

### 5.1 `NotificationKind` — one addition

`domain/notification.ts`'s `NotificationKind` union gains `"feedback_reminder"`
(`"feedback_request"` already exists in the union). A one-line TypeScript change, not a
migration — `notification_ledger.kind` is already `text` (REQ-025-schema.md §2), exactly
the situation that module's own comment already anticipates ("Release-3 will extend this
union... a one-line TypeScript change, not a migration").

### 5.2 Selecting T+2h candidates — `selectRegistrationsForFeedbackRequest`

```
export interface FeedbackJobCandidate {
  registrationId: string;
  userId: string;
}

export async function selectRegistrationsForFeedbackRequest(
  db: DbClient["db"],
  evaluationTime: Date,
): Promise<FeedbackJobCandidate[]>;
```

Selection condition, stated exactly (mirrors `selectRegistrationsForReminderWindow`'s
table-driven style, `domain/reminders.ts`):

| Clause | Condition |
|---|---|
| Only the checked-in | `registrations.checked_in_at IS NOT NULL` — **this single clause is AC1's entire mechanism**: an admitted-but-never-checked-in registration has `checked_in_at IS NULL` and is excluded by construction, never reaching this job's candidate list at all. |
| Only currently-published events | `events.status = 'published'` |
| The event has actually ended | `events.ends_at IS NOT NULL` |
| At least 2 hours have elapsed since it ended | `events.ends_at <= evaluationTime - 2 hours` |
| A bounded catch-up window, not unbounded | `events.ends_at > evaluationTime - 2 hours - CATCH_UP_WINDOW` |

**Why a bounded window, unlike a naive "elapsed >= 2h, no upper bound" reading:** an
unbounded lower-only bound would re-select every checked-in registration from every event
that has ever ended, forever, on every 5-minute tick — the ledger's `UNIQUE
(registration_id, kind)` constraint (REQ-025) would correctly turn every one of those into
a no-op `skipped-already-sent` outcome, but the query itself would grow without bound over
the project's lifetime, doing steadily more wasted work. `CATCH_UP_WINDOW` (an
implementation-chosen constant — a generous multiple of the job's own polling interval,
comfortably covering any realistic scheduler downtime) bounds the query the same way
`selectRegistrationsForReminderWindow`'s own window bounds its forward-looking query,
adapted here to a backward-looking one. **Why no retry concern arises from bounding it:**
`sendLedgeredNotification`'s own design (REQ-025 §3.2) already commits the ledger row
before attempting the actual send and never rolls it back on a send failure — an accepted,
named under-sending risk this design inherits unchanged, not one it introduces. There is
therefore no legitimate "the send failed, please retry later" case a wider window would
need to cover; a candidate outside `CATCH_UP_WINDOW` is one this system already gave up on
by design, the same way `selectRegistrationsForReminderWindow` does for its own forward
window.

### 5.3 Selecting T+24h candidates — `selectRegistrationsForFeedbackReminder`

```
export async function selectRegistrationsForFeedbackReminder(
  db: DbClient["db"],
  evaluationTime: Date,
): Promise<FeedbackJobCandidate[]>;
```

Identical shape to §5.2, with two differences stated exactly:

| Clause | §5.2 (request) | §5.3 (reminder) |
|---|---|---|
| Elapsed time | `ends_at <= evaluationTime - 2 hours` (and the matching catch-up lower bound) | `ends_at <= evaluationTime - 24 hours` (and the matching catch-up lower bound) |
| Feedback state | *(no clause)* | **`NOT EXISTS` a `feedback` row for this `registration_id`** |

**The `NOT EXISTS` clause is a deliberate design decision, named explicitly rather than
left implicit.** No acceptance criterion's literal wording forces it — AC4 only tests "a
person who ignores the request" — but "ignores" is read here as "never engaged with NPS at
all" (§1.3: a `feedback` row exists if and only if NPS was answered), and reminding someone
who already engaged would contradict the requirement's own "keep it short"/respect-the-
respondent framing (STORY-DETAILS D1) without being asked for by anything. This clause is
what makes that reading concrete: anyone whose `feedback` row already exists — whether
fully complete or only NPS-answered — is excluded from ever receiving the T+24h reminder,
because they did not ignore the request.

### 5.4 T+2h job — `makeFeedbackRequestJob`

```
export function makeFeedbackRequestJob(
  db: DbClient["db"],
  sender: NotificationSender,
  intervalMs: number,
): ScheduledJobDefinition;
```

`run(evaluationTime)`: for each `selectRegistrationsForFeedbackRequest` candidate, call
`sendLedgeredNotification({ kind: "feedback_request", classification: "transactional", registrationId, userId, composeMessage })` — **`classification: "transactional"`** is what
satisfies **AC7** ("the feedback request reaches a user with `broadcast_opt_in = false`")
structurally: `sendLedgeredNotification`'s own §3 step 3 (REQ-025, `domain/notification.ts`,
already read verbatim above) only ever consults `broadcastOptIn` for a `"marketing"` send —
a transactional send's code path never reads that flag at all, exactly mirroring how
REQ-026's own T-24h/T-3h reminders are already classified.

`composeMessage(resolvedLang)` (a new function in `domain/feedback.ts`), stated exactly:

1. `context = getRegistrationFeedbackContext(db, registrationId)` (§2.5); `context ===
   null`, `context.admission !== "admitted"`, or `context.checkedInAt === null` →
   `{ kind: "skip" }` — the at-send-time recheck this codebase's existing jobs already
   perform (REQ-026 §5.1/§5.2's own composeReminder24h/composeReminder3h re-verify
   `admission === "admitted"` before sending, even though the selection query already
   filtered on it), covering the gap between selection and the actual send.
2. `event = getEventById(db, context.eventId)` (existing, reused unchanged); `event ===
   null` or `event.status !== "published"` → `{ kind: "skip" }`.
3. `feedback = getFeedbackByRegistrationId(db, registrationId)` (§2.2); `feedback !==
   null` → `{ kind: "skip" }` — **this scheduled job's only job is to START the flow**; if
   a `feedback` row already exists (NPS already answered through some other path before
   this job ran — a race, not an expected case), there is nothing for this specific send
   to do. §5.5 states the identical recheck for the reminder job.
4. Otherwise: `{ kind: "text", text: <catalog.feedback.npsPrompt>, buttons: <the eleven
   NPS buttons, §3.2> }`.

This composed message is **always** the NPS prompt, never `liked`/`improve`/
`topicVotes`/broadcast-ask — by construction (step 3 above), since a fresh send only
reaches this compose function when no `feedback` row exists yet, and §2.2's own ordering
makes `nps` the only field `determineNextFeedbackField` can name for a `null` row.
**This is also why `ComposedMessage`'s existing `{ kind: "text"; text; buttons? }` shape
(REQ-025/026, `domain/notification.ts`) needs no `force_reply` variant added to it for
this requirement**: every prompt this design ever routes through the ledger is
button-driven (NPS here; Yes/No only ever sent interactively, never by a scheduled job,
§5.6); the `force_reply` prompts (§3.1) are sent directly by the interactive handlers via
`ctx.reply` (§6), never through `sendLedgeredNotification` — there is no scheduler-driven
double-send risk for them to begin with, since they only ever fire synchronously in
response to the respondent's own preceding action.

### 5.5 T+24h job — `makeFeedbackReminderJob`

```
export function makeFeedbackReminderJob(
  db: DbClient["db"],
  sender: NotificationSender,
  intervalMs: number,
): ScheduledJobDefinition;
```

Identical shape to §5.4, three differences: selects via `selectRegistrationsForFeedbackReminder`
(§5.3); sends with `kind: "feedback_reminder"` (§5.1); its own `composeMessage`'s step 3
recheck (a `feedback` row now exists — the person answered between selection and send) is
not merely defensive here the way §5.4's is — it is the exact same clause §5.3's query
already applies, re-verified at send time for the identical reason REQ-026's existing jobs
re-verify their own selection predicates. Its rendered text is `catalog.
feedback.reminderPrefix` prepended to the same NPS prompt body, with the same eleven
buttons — a nudge, not a different question.

### 5.6 Why the broadcast-ask question is never sent by either scheduled job

Both jobs' compose functions only ever render the NPS step (§5.4 step 4/§5.5). The
broadcast-ask question is reachable only via `advanceFeedbackFlow` (§6.4), called
synchronously from inside the interactive handlers once a respondent has actually engaged
— there is no scenario in which a scheduled, unattended job should be the one to ask "may
we message you about future events?" out of nowhere; STORY-DETAILS D1 places this question
"at the end" of an active exchange, not as its own separate broadcast.

Same `intervalMs` (300000 = 5 minutes) as the existing REQ-026 jobs — no acceptance

## 6. `handlers/feedback.ts` (new)

Every handler below follows the identical **derive-current-step-first, then gate the
write on it** discipline REQ-019 §4.6 and REQ-030 §8.2–§8.3 already establish: resolve the
tapping/replying person, re-derive `FeedbackFlowStep` fresh from the database, and only
then decide whether to write anything. A stale tap/reply (naming a field that is not the
one currently expected) is always a no-op, never an error.

### 6.1 `feedback:nps:<0-10>:<registrationId>` callback

```
export const FEEDBACK_NPS_PATTERN = /^feedback:nps:(\d{1,2}):(.+)$/;

export function makeFeedbackNpsCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence:
1. Extract `npsStr`/`registrationId` from the pattern; no match → `ctx.
   answerCallbackQuery()`, return (defensive, unreachable).
2. `isValidNpsValue(Number(npsStr))` false → `ctx.answerCallbackQuery()`, return
   (defensive, unreachable — §2.3).
3. `tgId = ctx.from?.id`; `undefined` → `ctx.answerCallbackQuery()`, return.
4. `flowUser = getFlowUserByTgId(db, BigInt(tgId))` (REQ-014, reused unchanged); `null` →
   `ctx.answerCallbackQuery()`, return.
5. `context = getRegistrationFeedbackContext(db, registrationId)` (§2.5); `context ===
   null` → `ctx.answerCallbackQuery({ text: feedback.staleMessage, show_alert: true })`,
   return.
6. **Ownership check (S3):** `context.userId !== flowUser.id` → `ctx.answerCallbackQuery
   ({ text: feedback.notYourFeedback, show_alert: true })`, **no write**, return. This is
   the concrete negative case for "a member's own feedback answer is never writable by
   anyone else" — a forwarded or otherwise leaked button tapped by a different Telegram
   user resolves to a different `flowUser.id` than `context.userId` and is refused here,
   before any read of `feedback`/`users` state is even attempted.
7. `ctx.answerCallbackQuery()` (Telegram UX requirement, always happens once ownership is
   confirmed).
8. `feedback = getFeedbackByRegistrationId(db, registrationId)` (§2.2); `userState =
   getUserFeedbackStateById(db, flowUser.id)` (§2.6); `step = determineFeedbackFlowStep
   (feedback, userState?.broadcastOptInAskedAt ?? null)` (§2.7) — computed fresh, before
   any write function is named.
9. **Gate:** the write is called if and only if `step.kind === "feedback-field"` AND
   `step.field === "nps"`. Any other outcome is a no-op — no write function is called —
   and the handler proceeds straight to step 11.
10. Only when step 9's gate passes: `writeFeedbackNps(db, registrationId, Number(npsStr),
    new Date())` (§2.3).
11. `advanceFeedbackFlow(ctx, db, registrationId, flowUser.id, lang)` (§6.4) — sends the
    next prompt (or the completion notice), whether or not step 9's gate passed, so a
    stale tap never dead-ends silently (identical discipline to REQ-019 §4.6 step 7).

### 6.2 `feedback:broadcast:<yes|no>:<registrationId>` callback

```
export const FEEDBACK_BROADCAST_PATTERN = /^feedback:broadcast:(yes|no):(.+)$/;

export function makeFeedbackBroadcastCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Identical to §6.1 steps 1–8 (extracting `answerToken`/`registrationId` instead of
`npsStr`; no `isValidNpsValue`-equivalent check needed — the pattern itself only ever
matches the literal tokens `yes`/`no`), then:

9. **Gate:** write called if and only if `step.kind === "broadcast-ask"`. Any other
   outcome (including a stale re-tap after the question was already answered once — the
   exact case AC5 needs refused, not double-processed) is a no-op.
10. Only when the gate passes: `writeBroadcastOptInAnswer(db, flowUser.id, answerToken ===
    "yes", new Date())` (§2.6).
11. `advanceFeedbackFlow(ctx, db, registrationId, flowUser.id, lang)`.

**This is the concrete mechanism behind AC5's "does not ask again":** a stale
`feedback:broadcast:*` tap arriving after `broadcast_opt_in_asked_at` is already set
re-derives `step.kind === "complete"` at step 8 (never `"broadcast-ask"` again, per §2.7's
own rule table), fails step 9's gate, and writes nothing — the SAME structural
impossibility REQ-019 §4.6/REQ-030 §8.3 already give every other "answer this exactly
once" case in this codebase, not a separately asserted guarantee.

### 6.3 The generic reply-to-message text listener

```
export function makeFeedbackTextReplyHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence:
1. `text = ctx.message?.text`; `undefined`, blank, or starts with `"/"` → return.
2. `repliedToText = ctx.message?.reply_to_message?.text`; `undefined` → return — **not a
   feedback-flow message**, deferring silently to any other `message:text` listener
   (§1.2).
3. `parsed = parseFeedbackReplyContext(repliedToText)` (§3.1); `!ok` → return — a reply to
   some other bot message, not a feedback prompt.
4. `tgId = ctx.from?.id`; `undefined` → return.
5. `flowUser = getFlowUserByTgId(db, BigInt(tgId))`; `null` → return.
6. `context = getRegistrationFeedbackContext(db, parsed.registrationId)` (§2.5);
   `context === null` OR `context.userId !== flowUser.id` → return — **the same S3
   ownership gate as §6.1 step 6**, silent here (not an alert) since this is a passive
   listener reacting to an incoming message, not a command the sender explicitly invoked;
   mirrors REQ-019 §4.5's "no other meaning defined for an unmatched message" convention.
7. `feedback = getFeedbackByRegistrationId(db, parsed.registrationId)` (§2.2); `userState
   = getUserFeedbackStateById(db, flowUser.id)`; `step = determineFeedbackFlowStep
   (feedback, userState?.broadcastOptInAskedAt ?? null)` (§2.7) — fresh, as every other
   handler in this design.
8. **Field-match gate (§1.2's fix):** `step.kind !== "feedback-field"`, or `step.field
   === "nps"`, or `step.field !== parsed.field` → return, a no-op. The first two clauses
   are unchanged from before this rework (`nps` is never text-answerable, §2.1/§3.2); the
   third clause is the fix itself — it is what actually makes "a stale reply to an
   already-superseded prompt is silently ignored" TRUE, including the specific case that
   was previously unhandled: a reply to an OLD, already-answered prompt for one field
   (e.g. `liked`, encoded in that prompt's own "Feedback field: " line, §3.1) arriving
   after the flow has already moved on to a DIFFERENT, currently-expected sibling field
   (e.g. `improve`) is caught HERE, because `parsed.field` (`"liked"`, from the message
   actually replied to) does not equal `step.field` (`"improve"`, the fresh derivation) —
   and is therefore a no-op rather than being silently written to the wrong field. Every
   other stale-tap case in this design (§6.1 step 9, §6.2 step 9) already uses this same
   "derive fresh, gate the write on an exact match, no-op on mismatch" shape; this closes
   the one case (a stale reply naming a *different but still-valid* text-answerable
   field) that §6.1/§6.2's own gates have no equivalent of, since neither of those two
   handlers has more than one sibling field competing for the same step.
9. `lang` resolved for `flowUser` (as every other handler).
10. `isFeedbackSkipReply(text, getCatalog(lang).feedback.skipButton)` (§4) → `true` →
    `markFeedbackFieldSkipped(db, parsed.registrationId, step.field, new Date())`.
11. Otherwise (any other non-blank text — blank was already filtered at step 1):
    `value = step.field === "topicVotes" ? parseTopicVotes(text) : text.trim()` (§3.4);
    `writeFeedbackOptionalField(db, parsed.registrationId, step.field, value, new
    Date())` (§2.4). (Step 8's gate already established `step.field === parsed.field`, so
    `step.field` and `parsed.field` are interchangeable here — `step.field` is used for
    consistency with §6.1/§6.2's own "write using the freshly-derived step" convention.)
12. `advanceFeedbackFlow(ctx, db, parsed.registrationId, flowUser.id, lang)` (§6.4).

### 6.4 `advanceFeedbackFlow` — the shared "send the next prompt, or announce completion" step

```
export async function advanceFeedbackFlow(
  ctx: Context,
  db: DbClient["db"],
  registrationId: string,
  userId: string,
  lang: BotLang,
): Promise<"prompted" | "complete">;
```

Sequence:
1. `feedback = getFeedbackByRegistrationId(db, registrationId)` (§2.2); `userState =
   getUserFeedbackStateById(db, userId)` (§2.6).
2. `step = determineFeedbackFlowStep(feedback, userState?.broadcastOptInAskedAt ?? null)`
   (§2.7).
3. `step.kind === "feedback-field"` → send that field's own prompt (§3.2 for `nps`, §3.1's
   `force_reply` shape for `liked`/`improve`/`topicVotes` — `formatFeedbackTextPrompt`
   called with `step.field` as its own `field` argument, so the ref line's "Feedback
   field: " value always matches the field the prompt currently being sent is actually
   for) via `ctx.reply(...)` → return `"prompted"`.
4. `step.kind === "broadcast-ask"` → `ctx.reply(catalog.feedback.broadcastAskPrompt, {
   reply_markup: <the two buttons, §3.3> })` → return `"prompted"`.
5. `step.kind === "complete"` → `ctx.reply(catalog.feedback.completedNotice)` → return
   `"complete"`.

Called from every write path in §6.1/§6.2/§6.3, always as the final step, whether or not
that path's own gate actually wrote anything — the same "re-advance regardless" discipline
REQ-019 §4.5 step 8/§4.6 step 7 already establish.

### 6.5 No `/feedback` command — a stated scope boundary, not an oversight

This flow is entirely bot-initiated (§5) and entirely resumable through the prompts
already sent (§1.2/§3.1's `force_reply` messages remain repliable indefinitely — Telegram
does not expire them). No acceptance criterion asks for a way to manually (re)start or
inspect a feedback flow on demand, so none is added. A respondent who partially completes
a flow (answers NPS, then never replies to `liked`) and receives no reminder (§5.3
excludes them, having already engaged) can still complete it at any later time simply by
scrolling back and replying to their own last unanswered prompt — no expiry, no lost
state, by the same "the carrier is the Telegram message itself" property REQ-030 §1.1
already relies on.

## 10. Open questions (not silently resolved)

1. **This design depends on a schema change no `DATA-DESIGNER` artefact has yet
   specified (§0).** ORCH should dispatch `DATA-DESIGNER` for
   `docs/agents/design/REQ-031-schema.md` — a new `feedback` table (registration-scoped,
   unique, NPS `NOT NULL`, three optional columns, a skip marker per optional column) plus
   one new nullable `users.broadcast_opt_in_asked_at` column — before `CODE-DESIGN-
   VALIDATOR` can treat this design as buildable.
2. **`Feedback.topic_votes`'s concrete shape is left open in two dimensions** (§0.2):
   the storage type (`text[]` recommended vs. `jsonb`, DATA-DESIGNER's call) and, more
   fundamentally, **whether "topics" should ever be tied to a real taxonomy** (e.g. the
   event's own agenda item labels) rather than free self-reported text. Nothing in this
   codebase currently supplies such a taxonomy, so this design resolves it as free text —
   flagged as a product decision a future requirement may revisit, not concluded here.
3. **The `CATCH_UP_WINDOW` constant (§5.2/§5.3) is named but not sized** — an
   implementation choice for `BACKEND-DEV`, following the same "a generous multiple of the
   job's own polling interval" reasoning `selectRegistrationsForReminderWindow` already
   uses for its own forward window, not fixed here as a specific number.
4. **Whether `writeFeedbackNps`'s `ON CONFLICT` re-answer path (§2.3) should be reachable
   at all** — this design allows a respondent to change a previously given NPS number by
   tapping a different button before answering anything else, since nothing forbids it;
   whether the NPS keyboard should instead be removed/disabled after the first tap (making
   the number final) is a UX call no acceptance criterion decides either way.
5. **The T+24h reminder's exclusion of anyone with an existing `feedback` row (§5.3) is
   this design's own reading of "ignores the request," not literally forced by AC4's
   wording** — named explicitly in §5.3 rather than silently assumed, since a stricter
   reading (remind everyone who has not reached `"complete"`, even if they answered NPS)
   is a legitimate alternative this design did not choose.
