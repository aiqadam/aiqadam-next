# REQ-009 Design — `apps/bot` workspace skeleton (grammY, Drizzle, Vitest)

**Requirement:** REQ-009
**Decisions this implements:** `docs/agents/decisions/0004-telegram-framework-grammy.md`
(grammY), `docs/agents/decisions/0005-orm-drizzle.md` (Drizzle ORM + Drizzle Kit),
`docs/agents/decisions/0006-test-framework-vitest.md` (Vitest at repo root). None of the
three is re-litigated here — this document only fixes the exact files/shapes that
implement them.
**Design type:** INFRA/SKELETON (workspace scaffold), not a UI/component requirement.
**Surface:** `apps/bot/**` — bot requirement per WF-02 Step 0.9. Step 2c
(SECURITY-REVIEWER) runs after Step 2b; this design does not contradict
`docs/agents/instructions/security-invariants.md` (checked explicitly in §8).

## 0. Why this design artefact looks different from a normal one

REQ-009 introduces no UI component, prop, content shape, design token, or
responsive/theme behavior — the usual CODE-DESIGNER template sections for those are N/A
and are stated as such, not omitted. `docs/guides/frontend_developer_guide.md` (read per
Step 1's instructions) is written for `apps/web` only and has nothing bot-specific to
carry over beyond the general "design before code, don't freelance structure" discipline.
**No `docs/guides/backend_developer_guide.md` exists yet.** Its absence is flagged as a
gap for ORCH/DOC-UPDATER (see §9.1) rather than worked around silently — BACKEND-DEV has
no role-specific guide analogous to the frontend one for anything beyond this design
artefact and the role file itself.

What this artefact specifies instead:

1. Exact new files under `apps/bot/` and at repo root, with their required shape.
2. Exact pinned dependency versions and which `package.json` declares each.
3. How root `lint`/`build` cover both workspaces without touching `ci-cd.yml`'s existing
   invocations.
4. Vitest wiring: root config, the one real assertion, and the test-file convention.
5. The exact `ci-cd.yml` diff.
6. Acceptance-criteria mapping and explicit open questions.

- Import the recommended flat configs from `"typescript-eslint"` (the package added in

- `globalIgnores(["dist/**", "node_modules/**"])`.
- No project-specific rule overrides required by this requirement — a bare
  recommended-config setup that lints `src/**/*.ts` (including `*.test.ts`).

### 2.4 `apps/bot/src/config.ts` — framework-free env-var validation module

**This is the one piece of "logic" REQ-009 produces, and it is deliberately NOT written
inside `src/index.ts`'s top level or inside any grammY handler**, per decision 0004's
binding consequence ("domain logic lives in framework-free modules that handlers call,
never inside grammY handler bodies") and because it is the only unit small enough to
carry REQ-009's one real Vitest assertion (decision 0006's consequence for REQ-009).

Shape (types/signature only, no implementation):

```
export interface BotConfig {
  botToken: string;
  databaseUrl: string;
}

export function loadConfig(env: NodeJS.ProcessEnv): BotConfig
```

Behavior in prose:
- Reads `env.BOT_TOKEN` and `env.DATABASE_URL` (see §6 for the exact-name decision).
- If either is absent or empty, **throws** an `Error` whose message names exactly which
  variable(s) are missing (e.g. `"Missing required environment variable(s): BOT_TOKEN"`)
  — it does not call `process.exit` itself, so it stays a plain, synchronously testable
  function with no process side effect.
- Never includes the *value* of either variable anywhere in the thrown message, in
  keeping with `security-invariants.md` S11 (see §8) — only the variable *name* is ever
  named.
- If both are present, returns `{ botToken: env.BOT_TOKEN, databaseUrl: env.DATABASE_URL }`
  unchanged (no transformation, trimming, or validation of the token/URL's *shape* — that
  is out of REQ-009's scope; only presence is checked).

### 2.5 `apps/bot/src/index.ts`

Prose/pseudocode only, no implementation:

1. Import `Bot` from `"grammy"` and `loadConfig` from `"./config.js"` (NodeNext ESM
   resolution requires the `.js` extension on relative specifiers even though the source
   file is `.ts` — a mechanical consequence of §2.2's module settings, not a design
   choice needing its own justification).
2. Call `loadConfig(process.env)` inside a `try`/`catch` at the top level.
   - On failure: `console.error(<the caught error's message>)` to stderr, then
     `process.exit(1)`. The error message (from §2.4) already names only the missing
     variable's name, never a value — nothing else is logged in this branch.
   - On success: proceed with `{ botToken, databaseUrl }` in scope.
3. Construct `const bot = new Bot(botToken)`.
4. Register exactly one handler: `bot.command("health", ctx => ctx.reply("ok"))` — the
   "health/liveness path" the requirement's scope line permits beyond "no handlers." See
   §6 for why this is a grammY command rather than an HTTP endpoint, stated as a decision
   with rationale rather than left open.
5. Log a single startup line via `console.log` confirming the process is starting —
   content is limited to a static string (e.g. `"bot starting"`) plus non-secret
   metadata if any (nothing from `botToken`/`databaseUrl` ever appears here, satisfying
   S11 even on the success path, not just the failure path).
6. Call `bot.start()` (long polling — decision 0004's "single long-running process"
   framing; no webhook server is introduced, matching decision 0003's deployment shape
   and REQ-009's "no handlers beyond health/liveness" boundary).
7. `databaseUrl` is threaded through to `index.ts`'s scope but **not connected to** in
   this requirement — REQ-009 explicitly forbids schema/handlers, and there is no
   Drizzle table to query yet. It is validated for *presence* only (§2.4) so that
   REQ-010's `DATA-DESIGNER`/`BACKEND-DEV` work has a config module to import rather than
   inventing env-var handling per-requirement. No `drizzle-orm`/`pg` client is
   instantiated in `index.ts` by this requirement — doing so would need a schema to
   query against, which does not exist until REQ-010.

## 3. Root-level wiring

### 3.1 `package.json` (repo root) — script changes

Current scripts (§1) each delegate to `apps/web` only via `-w apps/web`. Required
change — extend each of `lint`/`build` to also run against `apps/bot`, using the same
`-w <workspace>` delegation mechanism REQ-007 already established (no turborepo/nx/custom
script — see REQ-007's design §3, same reasoning applies here):

- `"lint"`: `"npm run lint -w apps/web -w apps/bot"`
- `"build"`: `"npm run build -w apps/web -w apps/bot"`
- `"dev"` and `"start"`: **unchanged** — the requirement's scope line only names `lint`
  and `build` as needing to cover both workspaces; `dev`/`start` staying `apps/web`-only
  is not a gap this requirement is asked to close (a bot "dev" workflow is explicitly
  deferred, §6).
- New script: `"test"`: `"vitest run"` — runs once, at the repo root, against both
  workspaces' test files (§5). Not scoped with `-w` because Vitest is a root-level
  devDependency (§3.2), not per-workspace — this mirrors decision 0006's "one runner, not
  one per workspace."

This satisfies the requirement's "root-level scripts so `npm run lint`/`npm run build` at
repo root cover BOTH workspaces, without editing `ci-cd.yml`'s existing invocations" —
`ci-cd.yml` already runs bare `npm run lint`/`npm run build` (§1), so extending what those
scripts *do* at the root `package.json` level changes their coverage without touching the
workflow file for those two steps. The workflow file changes only to add the new `npm
test` step (§4).

### 3.2 `package.json` (repo root) — new dependency

- `"devDependencies"`: `{ "vitest": "5.0.0" }` (npm registry `dist-tags.latest`, checked
  2026-09-06 — decision 0006's exact-pinned runner, declared at the root per that
  decision's explicit "at the repo root, covering both workspaces" scope, not inside
  either workspace's own `package.json`).

`"workspaces"` stays `["apps/*"]` — `apps/bot` is picked up automatically as soon as the
directory and its `package.json` exist; no change needed there.

## 4. CI wiring — exact `ci-cd.yml` diff

**File:** `.github/workflows/ci-cd.yml`, `build` job (lines 19-36 as read on this
branch). Insert a `Test` step between the existing `Lint` and `Build` steps:

```yaml
      - name: Lint
        run: npm run lint
      - name: Test
        run: npm test
      - name: Build
        run: npm run build
```

Rationale for the position (lint → test → build, before the Docker verification build):
cheapest/fastest checks fail first, and `npm test` here runs Vitest directly against
TypeScript source (`vitest` transpiles on the fly — no `dist/` or Next build output is a
prerequisite), so it does not need to wait for `npm run build` to have run first. No
other line in `ci-cd.yml` changes — `deploy-qa`, `deploy-prod`, and the Docker build step
are untouched, matching REQ-009's scope (no Dockerfile/deploy change; §1's Docker
out-of-scope note applies identically to CI's deploy jobs).

## 5. Vitest wiring

### 5.1 `vitest.config.ts` (repo root, new file)

Shape (prose, not implementation):
- `defineConfig` from `"vitest/config"`.
- `test.environment`: `"node"` — everything testable today (`apps/bot`'s config module)
  is plain Node logic; no DOM/jsdom environment is needed yet. If `apps/web` later wants
  component tests needing a DOM, that is a config change for whichever requirement adds
  the first such test, not this one (flagged, §6).
- `test.include`: left at Vitest's own default (`**/*.{test,spec}.?(c|m)[jt]s?(x)`,
  excluding `node_modules`) — sufficient to find `apps/bot/src/**/*.test.ts` without
  needing a repo-specific glob, and automatically extends to `apps/web` whenever a test
  file appears there. No Vitest "workspaces"/"projects" feature is configured — decision
  0006 calls for **one** runner/config, not one per package.

### 5.2 The one real assertion

**File:** `apps/bot/src/config.test.ts`, colocated next to `config.ts` (§5.3 fixes this
as the repo-wide convention). Targets `loadConfig` (§2.4) directly — no grammY, no
process spawning, no mocking of `process.exit` needed, because `loadConfig` is a pure
function that throws rather than exiting.

Required assertions (at minimum — TEST-DESIGNER expands this at Step 3, this is the
skeleton's own minimum per decision 0006's "Consequence for REQ-009"):
1. `loadConfig({ BOT_TOKEN: "t", DATABASE_URL: "d" })` returns
   `{ botToken: "t", databaseUrl: "d" }` — a real assertion against real behavior, not
   `expect(true).toBe(true)`.
2. `loadConfig({})` (or an object missing one of the two keys) throws, and the thrown
   error's message contains the missing variable's name.

### 5.3 Test-file convention (repo-wide, going forward)

**Colocated `*.test.ts` files next to the module they test** (e.g. `config.ts` +
`config.test.ts` in the same directory), matching Vitest's default include glob with zero
extra configuration. This applies to both workspaces from now on — `apps/web` gets the
same convention the day it adds its first test, rather than a second convention being
invented later.

## 6. Decisions made here (not left open) and their rationale

| Question REQ-009's text leaves unstated | Decision | Why |
|---|---|---|
| Exact env var names | `BOT_TOKEN`, `DATABASE_URL` | `DATABASE_URL` is the de facto standard consumed directly by `pg`/`drizzle-kit` connection-string parsing; `BOT_TOKEN` is short and unambiguous in a single-bot process with no other token in play. |
| `pg` vs `postgres` driver (decision 0005 left this open as "an implementation detail") | `pg` (`node-postgres`) | Longest-established Node Postgres driver, most widely documented Drizzle adapter (`drizzle-orm/node-postgres`), mature `@types/pg`. `postgres` (porsager) is a reasonable alternative but not chosen here; reversing this later touches only the driver import and connection setup, not the schema. |
| Shape of the "health/liveness path" | A grammY `bot.command("health")` handler replying `"ok"`, plus a non-secret startup log line | The bot is a single long-polling process (decision 0004 rationale 4), not a web server — adding an HTTP listener here would be inventing infrastructure REQ-009's "no handlers beyond health/liveness" line does not ask for, and the repo's one HTTP `/health` convention (`apps/web/src/app/health/route.ts`, per `deploy_guide.md`) is not extended to the bot by any requirement in scope. A Telegram-native command handler proves the handler pipeline itself is wired and responsive, which is what a liveness check for this kind of process actually needs. |
| TypeScript module resolution | `module`/`moduleResolution`: `"NodeNext"`, `"type": "module"` | Unlike `apps/web` (bundled by Next, `moduleResolution: "bundler"`), `apps/bot`'s compiled output runs directly under `node`, so it needs real Node ESM resolution semantics. |
| Whether `drizzle-kit` is a `dependency` or `devDependency` | `devDependency` | It is a CLI/build-time migration-generation tool, never imported at runtime by `src/index.ts`; the acceptance criterion's "depends on" wording does not require `"dependencies"` specifically. |

## 8. Security-invariants check (informational — Step 2c is the real gate)

This design does not contradict `security-invariants.md`. The only applicable item at
skeleton stage is **S11 (PII/credentials never in plaintext logs)**:
- `loadConfig`'s thrown error names only variable *names*, never values (§2.4).
- `index.ts`'s failure branch logs only that caught message (§2.5 step 2).
- `index.ts`'s success branch logs a static string with no secret interpolation (§2.5
  step 5).
- No literal token, password, or connection string appears in any file this design adds
  — every credential comes from `process.env` (§2.4), satisfying REQ-009's own
  acceptance criterion 6 (`git grep` finds no committed secret).

S1-S10, S12-S14 are N/A at this stage (no consent flow, no roles, no tokens beyond the
bot's own credential, no check-in, no exports, no deletion, no publication exist yet) —
stated explicitly per this file's own "silent skip is a FAIL" rule, for
SECURITY-REVIEWER's Step 2c to re-derive independently rather than trust this line.

## 9. Open questions (not resolved here — flag for CODE-DESIGN-VALIDATOR / ORCH)

1. **No `docs/guides/backend_developer_guide.md` exists.** `docs/guides/` currently has
   `frontend_developer_guide.md`, `qa_testing_guide.md`, `deploy_guide.md`,
   `content_ba_guide.md` — nothing for BACKEND-DEV. `AGENTS.md`'s standing rule is that
   the agent system must be extended with a new guide when a genuinely new domain of work
   arrives; `apps/bot` is exactly that. This design does not author that guide (out of
   CODE-DESIGNER's remit) but flags its absence so ORCH can route its creation
   (presumably to DOC-UPDATER or a dedicated pass) before or alongside REQ-010, rather
   than BACKEND-DEV improvising conventions per-requirement with nothing written down.
2. **Whether a `drizzle.config.ts` belongs in this requirement or REQ-010's.** `drizzle-kit`
   is added as a dependency here (§2.1) but REQ-009 explicitly forbids any database
   schema, and `drizzle-kit`'s config normally points at a schema file path that does not
   exist until REQ-010. This design does **not** add a `drizzle.config.ts` — creating one
   now would reference a schema that isn't there yet. If CODE-DESIGN-VALIDATOR or
   REQ-010's `DATA-DESIGNER` believes the config file itself (with an empty/placeholder
   schema path) belongs to the skeleton, that is a rework note, not something this design
   silently assumed either way.
3. **Whether a bot "dev" workflow (hot-reload, `tsx`, or Node's `--experimental-strip-types`)
   is needed before REQ-010 lands.** This design deliberately adds no `dev` script and no
   extra dependency for one (§2.1) — `build` + `start` are sufficient for the acceptance
   criteria's "starting apps/bot" checks. If BACKEND-DEV finds iterating via full `tsc`
   builds too slow once real logic arrives, that is a tooling addition for whichever
   requirement first feels the pain, not invented preemptively here.
4. **`vitest.config.ts`'s `test.environment` staying `"node"` project-wide.** Correct for
   everything testable today. The first `apps/web` test that needs a DOM (jsdom/happy-dom)
   will need either a per-file environment override (Vitest supports a
   `// @vitest-environment jsdom` docblock) or a config change — not decided here since no
   such test exists yet.
