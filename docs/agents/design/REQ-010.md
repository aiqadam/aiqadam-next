# REQ-010 — Bot data model and initial migration: Chapter, User, Profile

**Role:** DATA-DESIGNER (design only — no implementation code, no migration SQL/TS;
BACKEND-DEV writes both per this artefact, per `.claude/agents/data-designer.md`).

**Scope:** exactly three entities — `Chapter`, `User`, `Profile`. No other table, column,
or state is introduced. Derived from PRD 5 (data model), PRD 10 (privacy),
`security-invariants.md` S1/S11/S13, `decisions/0005-orm-drizzle.md` (Drizzle ORM +
Drizzle Kit, plain `.sql` migrations), and `decisions/0006` (time-dependent predicates
take the clock as an explicit parameter — noted here because it constrains anything this
schema is later queried by, even though this requirement adds no such query itself).

## 1. Entity: `chapters`

| Field | Type | Nullable | Why |
|---|---|---|---|
| `id` | UUID (PK, default gen) | No | Stable internal identity; PRD 1 "UUID keys, no Telegram-only assumptions". |
| `code` | text/varchar, `uz` \| `kz` | No | REQ-014's chapter-assignment logic and every chapter-scoped query (organizer scoping, S2) need a short stable code to reference a chapter without a display name; PRD 5 lists it first. |
| `name` | text | No | Displayed to users during chapter selection (REQ-014's "asked once, briefly" prompt) and in organizer/owner screens. Every chapter needs a human-readable name to be usable at all — required by construction, not a hardening choice. |
| `timezone` | text (IANA tz name, e.g. `Asia/Tashkent`) | No | Every later time-dependent computation (event start/end display, T-3h reminder in REQ-026, `registration_open`) is chapter-local. Without it, no event under this chapter can render a correct local time. Required because it is used the moment the first Event exists (REQ-011). |
| `default_lang` | text, `ru` \| `en` | No | REQ-013's acceptance criteria explicitly test "a User with `lang` NULL whose chapter has `default_lang` 'en' receives English" — this is a named consumer, so the field is required, not speculative. |
| `created_at` | timestamptz, default now() | No | PRD 5 preamble: every entity carries created/updated timestamps. |
| `updated_at` | timestamptz, default now(), updated on write | No | Same. |

**Keys / uniqueness:** `id` PK. `code` should be UNIQUE — two chapters cannot share the
same `uz`/`kz` code without breaking REQ-014's "exactly one active chapter" logic and any
future chapter-scoped lookup by code. *(Open question — see §6: the requirement text does
not literally ask for this constraint, so it is flagged rather than silently added beyond
scope; recommended but not mandated by this artefact's authority alone.)*

**No `active` column is in REQ-010's scope.** REQ-014 refers to "one active chapter" /
"two active chapters" as a state the /start flow reads, but REQ-010's own scope list for
`Chapter` is exactly `code - name - timezone - default_lang` — no `active`/`status` field.
Adding one now would exceed this requirement's explicit entity-field list. **Flagged as an
open question (§6)**, not resolved here: REQ-014 (or an earlier gap-filling requirement)
must state where "active" is decided before it can be implemented; DATA-DESIGNER does not
invent it.

## 2. Entity: `users`

| Field | Type | Nullable | Why |
|---|---|---|---|
| `id` | UUID (PK, default gen) | No | The one and only business key for this entity — see §5. |
| `tg_id` | bigint (Telegram user ids exceed 32-bit int range) | **Yes** | PRD 5's closing rule: an organizer can pre-create a `User` row for a person who has never opened the bot (no Telegram identity to record yet); it links on first `/start`. Never a business key — see §5. |
| `tg_username` | text | Yes | Telegram usernames are themselves optional/mutable at the platform level, and pre-created users have none. Never used as a key. |
| `lang` | text, `ru` \| `en` | Yes | REQ-013's fallback rule requires `lang` to be able to be NULL so the chapter's `default_lang` fallback branch is reachable; forcing a value at row-creation would make that branch untestable and would force a choice before the user has made one. |
| `role` | text, `member` \| `organizer` \| `owner` | No | S2 authorization is defined entirely in terms of this field ("Roles mean what you may do"). Every row must have a determinate role for every authorization check to be well-defined; default `member` at creation. |
| `chapter_id` | UUID (FK → `chapters.id`) | **Yes** | See §5.2 — a `User` row can exist before chapter assignment (organizer pre-creation with no chapter decided yet; the moment between `/start` creating the row and the "asked once" chapter prompt being answered, per REQ-014). Required once assignment happens, but not at row-creation time. |
| `broadcast_opt_in` | boolean, default `false` | No (has default) | S1: "message me" consent, its own column, default off. A user who never touches this setting must read back `false`, never NULL — NOT NULL + DEFAULT FALSE makes "unset" and "declined" the same safe state, which is exactly what S10's opt-in-only marketing rule needs. |
| `consent_pd_at` | timestamptz | **Yes** — until set | S1: "store my data" consent. Nullable because it starts unset (a `User` row created at `/start` per REQ-014 holds only what Telegram supplies, before consent); becomes non-null the instant consent is recorded. This is the literal gate AC3 of REQ-014 and S1 test against — a nullable timestamp column, not a boolean, so *when* consent was given is itself recorded (needed for any future audit or wording-version reasoning). |
| `blocked` | boolean, default `false` | No (has default) | S10: "`blocked` users are skipped in both [transactional and marketing] cases." A tri-state (null = unknown) would make that skip-check ambiguous; every user must be determinately blocked or not. |
| `created_at` | timestamptz, default now() | No | Preamble rule. |
| `updated_at` | timestamptz, default now(), updated on write | No | Preamble rule. |

**Keys / uniqueness — `tg_id`:**

- `tg_id` carries a **UNIQUE constraint** implemented as a standard Postgres unique
  index/constraint (`UNIQUE (tg_id)` — no partial-index workaround needed).
- **Why a plain unique constraint already gives AC2's exact behavior:** standard Postgres
  unique indexes treat each `NULL` as **distinct from every other `NULL`** (this is
  Postgres's default; it differs from some other RDBMSes and from what a naive reading of
  "unique" might suggest). Concretely: inserting two `users` rows both with `tg_id = NULL`
  **succeeds** for both — Postgres never considers a NULL a duplicate of another NULL for
  uniqueness purposes — while inserting two rows with the **same non-null** `tg_id` value
  is rejected. This is exactly the AC2 requirement ("two inserts of users with NULL tg_id
  (both must succeed)... one duplicate non-null tg_id insert (must fail)"), and it is the
  *out-of-the-box* behavior of `UNIQUE (tg_id)` in Postgres — no `NULLS NOT DISTINCT` (the
  PG15+ opt-in that would make NULLs collide) and no partial unique index is needed or
  wanted here. BACKEND-DEV should not add `NULLS NOT DISTINCT` — doing so would break
  AC2's first case.
- `id` is the PK.

**Cascade on `chapter_id`:** if a chapter row is ever deleted (not a case any current
requirement performs — chapters are not designed to be deleted in normal operation), the
FK should be `ON DELETE RESTRICT` rather than `CASCADE`: silently orphaning or
cascade-deleting users because their chapter row was removed is a far more destructive
default than refusing the chapter deletion until users are reassigned. This is a design
recommendation, not a currently-exercised path (no requirement deletes a chapter).

## 3. Entity: `profiles`

| Field | Type | Nullable | Why |
|---|---|---|---|
| `id` | UUID (PK, default gen) | No | Own identity, independent of `user_id`, per the preamble rule (every entity gets a UUID PK — a 1:1 relationship is still a distinct row with its own key, not a `users` column, because PRD 5 lists it as its own entity). |
| `user_id` | UUID (FK → `users.id`, UNIQUE) | No | The 1:1 link. NOT NULL because a `Profile` row's entire reason to exist is to describe one `User`; an orphaned profile is meaningless. UNIQUE enforces the "1:1" part — see §5.3. |
| `first_name` | text | No | PRD 5 lists this as a required field, and AC3 names it explicitly among "the PRD 5 required fields" a minimal insert must supply. |
| `last_name` | text | No | Same — AC3 names it explicitly. |
| `phone` | text | **Yes** | PRD 5's optionality rule, explicit in the requirement text: "phone... NULLABLE at the database level. A NOT NULL constraint... is a defect." No stated requirement forces every profile to carry a phone number at creation. |
| `email` | text | **Yes** | Same rule, same reasoning. |
| `company` | text | No | AC3 names it among the required-field set a minimal profile insert must supply. |
| `position` | text | No | Same — AC3 names it explicitly. |
| `is_student` | boolean | No | AC3 names it among the required fields; a determinate true/false is needed the moment any student-specific logic (if ever added) reads it — no NULL "unknown" state is asked for. |
| `experience_level` | text, `user` \| `builder` \| `advanced` \| `expert` | No | AC3 names it explicitly among the required fields for a minimal insert. |
| `links_github` | text | **Yes** | PRD 5: "links{github,linkedin,site} (all nullable)". No requirement makes any social link mandatory to finish a profile. |
| `links_linkedin` | text | **Yes** | Same. |
| `links_site` | text | **Yes** | Same. |
| `public_bio` | text | **Yes** | PRD 5 explicit nullable list; also gated for *display* by `publish_consent` (S14) regardless of whether it is filled in. |
| `photo_file_id` | text (Telegram file_id) | **Yes** | PRD 5 explicit nullable list; a person may never upload a photo and must still be able to finish. |
| `publish_consent` | boolean, default `false` | No (has default) | S1 / S14: "publish me" consent, its own column, **default off**. Gates whether anything about this person (including the above optional fields) is ever shown publicly (lineup, etc.) — "Speaker TBA" is the fallback per S14 when this is false, regardless of what data exists. |
| `created_at` | timestamptz, default now() | No | Preamble rule. |
| `updated_at` | timestamptz, default now(), updated on write | No | Preamble rule. |

**Why `links` are three flat columns, not a JSON/array column:** PRD 5 names three fixed,
known keys (github, linkedin, site) — not an open-ended list. Three named nullable text
columns keep each independently nullable (as required) and keep the schema
plain-SQL-readable for the exportability goal (`decisions/0005`'s rationale #1) — a JSONB
blob would hide per-field nullability/typing from a plain schema read and from any future
absorbing system that doesn't share this project's JSON key conventions. If a future
requirement needs an open-ended list of links, that is a new decision, not implied here.

**Keys / uniqueness:** `id` PK; `user_id` UNIQUE + NOT NULL + FK → `users.id` enforces the
1:1 relationship at the database level — Postgres will reject a second `profiles` row for
the same `user_id`.

## 4. What is NOT stored, and where the computation lives (binding, not just for REQ-010)

None of the following ever gets a column, in this migration or in any future one that
touches these three tables:

| Value | Why it stays computed | Where it will live, when a consumer exists |
|---|---|---|
| `no_show` | Derivable from `Registration.admission` + whether `checked_in_at` was ever set, evaluated relative to an event's end. Storing it duplicates state that can silently drift from the source of truth. | A query/view over `Registration`, added by whichever requirement first needs it (REQ-011 territory), taking the evaluation time as an explicit parameter — never SQL `now()` inline (`decisions/0006`). |
| `waitlist_position` | A rank, not a fact — it changes as other rows change state without this row being touched. | A query ordering waitlisted `Registration` rows by e.g. creation order, computed on read. |
| `seats_taken` | `security-invariants.md` S7 states this explicitly as a formula: `count(admission = 'admitted')`. | A `COUNT` query against `Registration`, scoped by `event_id`. |
| `registration_open` | A boolean derived from comparing `now` to `Event.registration_closes_at` (and possibly capacity). | A predicate function taking the evaluation time as an explicit input parameter, not a stored flag. |
| `finished` | Derived from comparing `now` to `Event.ends_at`. | Same shape as `registration_open` — a time-parameterized predicate, never a column. |

None of these five entities exist in REQ-010's scope in the first place (they belong to
`Event`/`Registration`, REQ-011's territory) — this table is recorded here because
DATA-DESIGNER's role file states the rule must be held explicitly and on record from the
first schema slice, not deferred until the tables that could tempt a column actually
exist.

## 5. Binding relationship/business-key rules

### 5.1 `tg_id` is never a business key

**`tg_id` is never a business key; every later lookup resolves to `User.id`.** `tg_id` is
only ever used as (a) the lookup key `/start` uses to find-or-create the matching `User`
row on first contact, and (b) informational display. No foreign key in this schema, or any
schema this requirement anticipates, references `users.tg_id`. `Profile.user_id` (and
every later entity's user references — `Registration.user_id`, `EventStaff.user_id`,
`AuditLog.actor_user_id`, etc., all out of REQ-010's scope but bound by this same rule)
points at `users.id`. This satisfies AC6 directly and is the same sentence this
requirement's acceptance criterion 6 and `decisions/0005`'s consequence section both state.

### 5.2 `Chapter` ↔ `User`: `chapter_id` is nullable

`users.chapter_id` is a nullable FK, not a required one. Reasoning, cross-checked against
REQ-014 (which is not yet implemented but whose description is the concrete evidence for
this call, since REQ-010's own text does not resolve it directly):

- REQ-014 states a `User` row is created at `/start` holding "only what Telegram supplies
  (tg_id, tg_username, lang)" — before consent, and by extension before any chapter
  assignment has necessarily happened (assignment is either silent, for exactly one active
  chapter, or requires an extra prompt-and-answer round trip for multiple chapters).
- REQ-014 also explicitly requires that an organizer-pre-created `User` (NULL `tg_id`) be
  constructible without inventing an assignment ahead of time.
- Therefore a `User` row can validly exist, for at least a brief window, with no chapter
  decided. A NOT NULL constraint would force inventing a default chapter or a sentinel
  value, which is worse than a nullable column with no chapter chosen yet.

This is stated as DATA-DESIGNER's own reasoning from the cited REQ-014 context, not
invented as a business rule from nothing — flagged as confirmed-by-cross-reference rather
than by REQ-010's own text alone.

### 5.3 `Profile` ↔ `User`: 1:1, and cascade on deletion (open question)

`profiles.user_id` is UNIQUE + NOT NULL + FK, giving the 1:1 relationship.

**Cascade behavior on `User` deletion/anonymization is an open question — not resolved by
this artefact.** `security-invariants.md` S13 says deletion **anonymizes**, it does not
hard-delete: "`/profile → delete my data` anonymizes the person while keeping aggregate
counts intact... an 'anonymization' that leaves the phone, email, or `tg_username`
recoverable" is explicitly named as the failure case. That implies the `User` row itself is
never hard-deleted by the product's own "delete my data" flow — its PII columns
(`tg_username`, and the `Profile` row's `phone`/`email`/`first_name`/`last_name`/etc.) are
overwritten/nulled in place, while the row and its `id` persist so `Registration`/
`AuditLog` foreign keys and aggregate counts keep resolving. Under that reading, **there is
no ordinary product path that deletes a `User` row at all**, so `ON DELETE CASCADE` on
`profiles.user_id` would only ever fire from a manual/administrative hard delete outside
the normal flow.

This requirement does not implement the anonymization flow (that is a later requirement's
scope) and REQ-010's field list does not include the columns an anonymization routine would
touch beyond what's already specified. What is flagged here, explicitly, as **open rather
than invented**:

1. Whether `profiles.user_id`'s FK should be `ON DELETE RESTRICT` (refuse any hard delete
   of a `User` that still has a `Profile`, forcing anonymization-in-place as the only path)
   or `ON DELETE CASCADE` (remove the `Profile` row if a `User` row is ever hard-deleted).
   **Recommendation, not a decision:** `ON DELETE RESTRICT` is the safer default given S13's
   explicit rejection of cascading hard deletes that "retroactively alter a past event's
   published figures" — but the actual anonymization mechanism (which columns get
   overwritten, by what routine, under what requirement) is not designed here and should be
   confirmed by whichever requirement implements `/profile → delete my data`.
2. This artefact does **not** design an anonymization routine, a "deleted" sentinel state,
   or any new column to support it — none of that is in REQ-010's three-entity, listed-field
   scope, and inventing one here would violate the "don't add a field/state the requirement
   doesn't call for" rule.

## 6. Open questions (not resolved by invention)

1. **`chapters.code` uniqueness.** Recommended (`UNIQUE (code)`) but not explicitly
   demanded by REQ-010's acceptance criteria; flagged so a validator/reviewer can confirm
   or explicitly waive it rather than it being silently assumed.
2. **`chapters.active`/status.** REQ-014 talks about "one active chapter" vs. "two active
   chapters" as an existing predicate, but `Chapter`'s field list in REQ-010's own scope
   (`code - name - timezone - default_lang`) has no such column. This gap must be closed by
   REQ-014 or an earlier gap-filling requirement — DATA-DESIGNER is not adding an
   unrequested field to close it now.
3. **Cascade/anonymization mechanism for `User`/`Profile` on "delete my data" (S13).**
   See §5.3 — the FK cascade direction is recommended (`RESTRICT`), not decided, and the
   anonymization routine itself is out of REQ-010's scope entirely.
4. **`users.role` default and creation path.** REQ-010's field list requires `role` NOT
   NULL; this artefact assumes a `member` default at row creation (the least-privileged
   role, consistent with S2's default-deny posture) since no requirement text states an
   explicit default. Flagged so BACKEND-DEV/REVIEWER can confirm `DEFAULT 'member'` matches
   intent before the migration is generated.

## 7. Drizzle schema shape (pseudocode — not implementation)

Table/column shapes only, illustrating types and constraints for BACKEND-DEV to translate
into actual `drizzle-orm/pg-core` definitions and generate via `drizzle-kit`. This is
deliberately not valid TypeScript/Drizzle syntax.

```
table chapters:
  id            uuid          PRIMARY KEY DEFAULT gen_random_uuid()
  code          text          NOT NULL UNIQUE            -- 'uz' | 'kz', app-level enum check
  name          text          NOT NULL
  timezone      text          NOT NULL                   -- IANA tz name
  default_lang  text          NOT NULL                   -- 'ru' | 'en', app-level enum check
  created_at    timestamptz   NOT NULL DEFAULT now()
  updated_at    timestamptz   NOT NULL DEFAULT now()      -- app or trigger sets on update

table users:
  id                 uuid        PRIMARY KEY DEFAULT gen_random_uuid()
  tg_id              bigint      NULL UNIQUE              -- plain UNIQUE; Postgres allows multiple NULLs
  tg_username        text        NULL
  lang               text        NULL                     -- 'ru' | 'en', app-level enum check
  role               text        NOT NULL DEFAULT 'member' -- 'member' | 'organizer' | 'owner'
  chapter_id         uuid        NULL REFERENCES chapters(id) ON DELETE RESTRICT
  broadcast_opt_in   boolean     NOT NULL DEFAULT false
  consent_pd_at      timestamptz NULL
  blocked            boolean     NOT NULL DEFAULT false
  created_at         timestamptz NOT NULL DEFAULT now()
  updated_at         timestamptz NOT NULL DEFAULT now()

table profiles:
  id                 uuid        PRIMARY KEY DEFAULT gen_random_uuid()
  user_id            uuid        NOT NULL UNIQUE REFERENCES users(id) ON DELETE RESTRICT  -- see open question 5.3
  first_name         text        NOT NULL
  last_name          text        NOT NULL
  phone              text        NULL
  email              text        NULL
  company            text        NOT NULL
  position           text        NOT NULL
  is_student         boolean     NOT NULL
  experience_level   text        NOT NULL                 -- 'user'|'builder'|'advanced'|'expert', app-level enum check
  links_github       text        NULL
  links_linkedin     text        NULL
  links_site         text        NULL
  public_bio         text        NULL
  photo_file_id      text        NULL
  publish_consent    boolean     NOT NULL DEFAULT false
  created_at         timestamptz NOT NULL DEFAULT now()
  updated_at         timestamptz NOT NULL DEFAULT now()
```

Enum-like fields (`chapters.code`, `chapters.default_lang`, `users.lang`, `users.role`,
`profiles.experience_level`) are shown as `text` above; whether BACKEND-DEV expresses them
as a Postgres `ENUM` type, a `CHECK` constraint, or an application-level union type is an
implementation choice this artefact does not mandate — either satisfies REQ-010's
acceptance criteria as written, provided invalid values are rejected somewhere before
storage.

## 8. What the generated migration file should contain (prose)

A single Drizzle Kit-generated `.sql` file (per `decisions/0005`, committed under
`apps/bot/`, e.g. `apps/bot/drizzle/0000_<slug>.sql` or wherever BACKEND-DEV's Drizzle
config points its migrations directory) that:

1. `CREATE TABLE chapters (...)` with the columns, types, defaults and `UNIQUE (code)`
   constraint from §7.
2. `CREATE TABLE users (...)` with the columns/types/defaults from §7, including
   `UNIQUE (tg_id)` as a plain unique constraint (not `NULLS NOT DISTINCT`) and the FK to
   `chapters(id)` with `ON DELETE RESTRICT`.
3. `CREATE TABLE profiles (...)` with the columns/types/defaults from §7, including
   `UNIQUE (user_id)` and the FK to `users(id)` (cascade direction per open question 5.3 —
   `RESTRICT` recommended pending confirmation).
4. No `no_show`, `waitlist_position`, `seats_taken`, `registration_open`, or `finished`
   column or table anywhere in the file (AC5 — this is a grep-checkable negative).
5. This is a purely additive migration (three new tables, no existing table altered) —
   **it is reversible**: a corresponding `DROP TABLE profiles; DROP TABLE users; DROP TABLE
   chapters;` (profiles first, respecting the FK) undoes it cleanly with no data-loss
   ambiguity, since nothing existed in these tables before this migration. Drizzle Kit's
   default down-migration generation (or a hand-written down script, per BACKEND-DEV's
   Drizzle config) should reflect this drop order.

## 10. Summary for the handoff

Three tables (`chapters`, `users`, `profiles`), UUID PKs, `created_at`/`updated_at` on
each. `users.tg_id` is a nullable, uniquely-constrained bigint (Postgres's native
multiple-NULLs-distinct behavior gives AC2 for free). Three consents live in their
PRD-specified, never-conflated homes. `chapter_id` is a nullable FK on `users` (reasoned
from REQ-014's /start flow, not invented). `profiles` is 1:1 with `users` via a unique FK.
No computed value gets a column. Four open questions are flagged (§6) rather than resolved
by invention: `chapters.code` uniqueness, `chapters.active` (missing from REQ-010's own
field list but referenced by REQ-014), the deletion/anonymization cascade mechanism for
S13, and `users.role`'s default value.
