# REQ-033 — InviteCode data model, `registrations.invite_code_id` FK closure, and code generator

**Role:** DATA-DESIGNER (design only — no implementation code, no migration SQL/TS;
BACKEND-DEV writes both per this artefact, per `.claude/agents/data-designer.md`).

**Scope:** exactly one new entity (`InviteCode`), one FK closure on an existing column
(`registrations.invite_code_id`), and one generator design (code *values*, not the
issuing/redemption flow). No handler, no domain logic, no issuing/redemption code — those
are REQ-037 (issuing), REQ-038 (redemption + eligibility), REQ-039 (companion), REQ-040
(invitation list). Derived from PRD 5 (data model), PRD FR-4/FR-5 (invite gating and code
shapes), story B7 ("by typing it" or by deep link), `security-invariants.md` S4 (token
unguessability bar, explicitly extended to `InviteCode` values), and `decisions/0006`
(time-dependent predicates take the evaluation time as an explicit parameter — noted
because `expires_at` will be read against a caller-supplied clock by REQ-038, not by any
query this artefact defines). Builds directly on REQ-010's `users` table and REQ-011's
`events`/`registrations` tables — every FK to a person resolves to `users.id`, never
`users.tg_id` (REQ-010 §5.1, restated as binding here).

**Follows the REQ-010/REQ-011 precedent, not REQ-025/REQ-031's:** `InviteCode` serves four
separate downstream flows (issuing, redemption, companion, invitation list), so it is
drafted as its own DATA-DESIGNER-owned schema requirement rather than carried inline by
whichever BACKEND-DEV requirement happens to touch it first — exactly the reasoning
REQ-011 §9.3 anticipated when it deferred `registrations.invite_code_id`'s FK to "a future
requirement."

## 1. Entity: `invite_codes`

| Field | Type | Nullable | Why |
|---|---|---|---|
| `id` | UUID (PK, default gen) | No | Preamble rule (every entity gets a UUID PK, PRD 5 preamble) — the stable internal identity `registrations.invite_code_id` points to. |
| `event_id` | UUID FK → `events.id` | No | PRD 5 lists it first; an invite code with no event is meaningless — it exists to gate registration for exactly one event, and every downstream flow (REQ-037 issuing, REQ-038 redemption) scopes its query by event. Required by construction. |
| `code` | text | No | The human-typeable/deep-linkable value itself (§4). Every row's entire reason to exist is to carry this value — required by construction, and UNIQUE (see "Keys / uniqueness" below). |
| `issued_to_user_id` | UUID FK → `users.id` | **Yes** | PRD 5 lists it as nullable. Null is the BULK-code shape (§2): a code not tied to any one named recipient, shared with many people, redeemable up to `max_uses` times. Non-null is the PERSONAL-code shape: issued to one specific pre-identified person. Never `users.tg_id` — resolves to `users.id` per REQ-010 §5.1. |
| `grants_companion_of` | UUID FK → `users.id` | **Yes** | PRD 5 lists it as nullable. Non-null marks the COMPANION-code shape (§2): redeeming this code registers the redeemer as the named user's companion/plus-one, not as an independent invitee in their own right. Null means the code carries no companion relationship. Never `users.tg_id`, same reasoning. |
| `max_uses` | integer | No | Every code has a determinate use ceiling from creation — REQ-038's redemption check (`used_count < max_uses`) is meaningless against a null ceiling. PERSONAL and COMPANION codes are the `max_uses = 1` case; BULK codes set it higher. No stated flow creates a code with an undecided ceiling. |
| `used_count` | integer, default `0` | No (has default) | **A real stored counter, not a violation of the computed-never-stored rule** — see the dedicated note below. Every code starts at zero uses; NOT NULL + DEFAULT 0 keeps "never redeemed" and "explicitly zero" the same determinate state, which is what REQ-038's `used_count < max_uses` comparison needs to be well-defined from the moment a code is created. |
| `expires_at` | timestamptz | **Yes** | PRD 5 lists it as a field, and S4's negative case ("a code accepted past `expires_at`") presupposes it can gate redemption — but nothing in this requirement's scope states every code must have an expiry (an organizer may intend a code to remain valid indefinitely, e.g. until the event itself closes registration). Nullable = no additional expiry beyond whatever else gates redemption (event's own `registration_closes_at`/`starts_at`, read by REQ-038); non-null is a code-specific cutoff, evaluated by REQ-038 against a caller-supplied `$evaluation_time`, never SQL `now()` inline (`decisions/0006`). |
| `created_at` | timestamptz, default now() | No | Preamble rule. |
| `updated_at` | timestamptz, default now(), updated on write | No | Preamble rule — and load-bearing here specifically: `used_count` increments are writes to this row, so `updated_at` doubles as "last redeemed at" for free, though no requirement in this artefact's scope names that as a required read path. |

### Why `used_count` is a stored column, not a violation of the computed-not-stored rule

PRD 5's computed-never-stored rule (restated in REQ-010 §4 and REQ-011 §5) names exactly
five values that must never get a column: `no_show`, `waitlist_position`, `seats_taken`,
`registration_open`, `finished`. `used_count` is not on that list — PRD 5 lists it as an
`InviteCode` **field**, in the same breath as `max_uses` and `expires_at`, not as a derived
report value. Unlike `seats_taken` (`count(admission='admitted')` over `registrations`,
recomputable from source-of-truth rows at any time with no independent write path),
`used_count` requires an atomic increment coupled to the *act* of redemption itself — a
concurrent-redemption race (two people redeeming the last remaining use of a bulk code at
the same instant) must be resolved by a single atomic `UPDATE ... SET used_count =
used_count + 1 WHERE used_count < max_uses` (or equivalent row-locking read-then-write)
inside the same transaction that creates the `Registration` row, not by recounting
`Registration` rows after the fact (nothing on `Registration` even names *which* invite
code redemption consumed a use once `invite_code_id` is set, versus counting redemptions
generally). This makes `used_count` a genuine source-of-truth counter, not a cache of a
derivable fact. **The atomicity mechanism itself (row lock vs. `CHECK`-guarded UPDATE vs.
serializable transaction) is REQ-038's problem to design, not this requirement's** — this
artefact states only that the column is legitimately stored and states why, per the
handoff's explicit instruction.

### Keys / uniqueness

- `id` PK.
- **`code` carries a UNIQUE constraint** — a real database constraint, not
  application-checked. Two rows sharing the same `code` value would make redemption
  ambiguous (which row does `?start=i_<code>` or a typed code resolve to?); PRD FR-5's
  code-based redemption flow presupposes a code identifies exactly one row. Enforced with a
  plain `UNIQUE (code)` (no nullability question here — `code` is NOT NULL, so Postgres's
  multiple-NULLs-distinct behavior, relevant to REQ-010's `tg_id` and REQ-011's `qr_token`,
  does not apply to this column).
- No uniqueness constraint on `(event_id, issued_to_user_id)` or any other combination —
  nothing in this requirement's scope states an event may issue at most one personal code
  per person; an organizer re-issuing a replacement code for the same person is not
  excluded by any stated rule. Not adding one, per the "don't invent a business rule"
  boundary (flagged in §6 as an open question for whoever designs issuing, REQ-037, to
  confirm is not needed).

### Cascades

- `event_id` → `ON DELETE RESTRICT` — matches every other event-scoped FK in REQ-011
  (`registrations.event_id`, `event_staff.event_id`): an event with invite codes issued
  against it is never a candidate for hard deletion under any stated flow (`cancelled` is
  the status for "called off," never a row delete, per the one-word-per-concept rule).
- `issued_to_user_id` → `ON DELETE RESTRICT` — mirrors REQ-010 §5.3's reasoning: S13
  anonymizes a `User` in place rather than hard-deleting the row, so an `InviteCode` row
  should never need to survive a `User` row's disappearance under the normal product flow.
- `grants_companion_of` → `ON DELETE RESTRICT`, same reasoning.

## 2. The three code shapes are compositions, not a `type` enum

Per the handoff's explicit instruction and PRD FR-5/story F4: PERSONAL, BULK, and COMPANION
are **not** a fourth discriminator column. They are named readings of the same five columns
(`issued_to_user_id`, `grants_companion_of`, `max_uses`, plus `used_count`/`expires_at`
common to all three), exactly as DESIGN-REVIEW.md's own reasoning treats
`requires_invite`/`requires_approval` as two independent booleans rather than one access
enum — "compositions, not special cases."

| Shape | `issued_to_user_id` | `grants_companion_of` | `max_uses` | Meaning |
|---|---|---|---|---|
| **PERSONAL** | non-null (the named recipient) | null | `1` | Issued to one specific pre-identified person; redeemable exactly once, by that flow's own logic (REQ-038 decides whether redemption is further restricted to that exact person or merely single-use — not this artefact's call, see §6). |
| **BULK** | null | null | `N` (> 1, organizer-chosen) | Not tied to any named recipient; shared with many people (e.g. printed on a poster, posted in a channel); redeemable up to `N` times by up to `N` distinct redeemers. |
| **COMPANION** | null or non-null (see below) | non-null (the user being companioned) | `1` | Redeeming this code registers the redeemer as `grants_companion_of`'s companion/plus-one rather than as an independent invitee. `issued_to_user_id` may additionally be set if the companion code is issued to a specific named plus-one; this artefact does not resolve whether that combination is required or merely permitted — flagged in §6. |

**Legal combinations, stated explicitly:**

- `issued_to_user_id` non-null AND `grants_companion_of` non-null: **legal** — a personal
  companion code issued to one specific named plus-one. Both PERSONAL and COMPANION
  readings apply simultaneously; this is not a conflict because they describe orthogonal
  facts (who was it issued to vs. does redeeming it create a companion relationship), not
  mutually exclusive states.
- `issued_to_user_id` null AND `grants_companion_of` non-null: **legal** — an
  un-targeted companion code (e.g. "bring your plus-one," handed to the primary registrant
  to pass along, redeemer identity not known in advance).
- `issued_to_user_id` non-null AND `grants_companion_of` null: **legal** — the plain
  PERSONAL shape.
- `issued_to_user_id` null AND `grants_companion_of` null: **legal** — the plain BULK
  shape (this is also the only legal state when `max_uses > 1`, see below).
- **`grants_companion_of` non-null AND `max_uses > 1`: this artefact does NOT forbid it at
  the database level** (no `CHECK` constraint is specified), but it is very likely not a
  legal *business* combination — a companion relationship names one specific person to be
  companioned, and it is unclear what "companion of X, redeemable 5 times" would mean
  (five different redeemers all becoming X's companion?). This tension is **not resolved
  here**: PRD FR-5/story F4 do not state whether COMPANION codes are always `max_uses = 1`
  by construction or whether a bulk-companion shape is intentionally allowed. Flagged in
  §6 for REQ-037 (issuing) to resolve — REQ-037 controls what combinations its own issuing
  flow ever *produces*, which is a tighter and more appropriate gate than a DB `CHECK`
  guessed at here.
- **`issued_to_user_id` and `grants_companion_of` both non-null and equal (a user granted
  as their own companion): not forbidden at the DB level** (both are independently
  nullable FKs to the same table with no cross-column constraint), and not a case this
  artefact can rule out as meaningless without inventing a business rule — flagged in §6
  for REQ-037/REQ-039 to guard against at the point a code is issued, if it turns out to be
  nonsensical.

No DB-level `CHECK` constraint enforces any of the above legality statements — consistent
with REQ-011 §3's precedent for the `agenda` doors-item cardinality rule (an
application-level invariant enforced by the code that *writes* the row, not by a
cross-column `CHECK`, because the acceptance criteria in scope test insert/behavior, not a
specific enforcement mechanism). This is stated as DATA-DESIGNER's design-time reasoning
for REQ-037/REQ-038/REQ-039 to build against consistently — the whole point of drafting
this table centrally rather than letting three requirements race to define it.

## 3. `registrations.invite_code_id` — closing the FK

**Before this migration:** `registrations.inviteCodeId` is `uuid("invite_code_id")`, a
plain nullable UUID column, no `.references(...)`, per REQ-011 §11 open question 3 (quoted
in "Verified current state" above).

**After this migration:** `registrations.invite_code_id` becomes a real foreign key —

```
invite_code_id   uuid   NULL   REFERENCES invite_codes(id) ON DELETE RESTRICT
```

- **Still nullable** — unchanged from REQ-011's design. Most registrations are not
  invite-gated at all (`requires_invite = false` is the default per REQ-011 §2), so most
  `registrations` rows legitimately have no invite code to reference. This requirement adds
  the FK constraint; it does not change the column's nullability, and nothing in this
  requirement's scope asks it to.
- **`ON DELETE RESTRICT`**, matching every other person/event reference on `registrations`
  (`event_id`, `user_id`, `checked_in_by`, `invited_by_user_id` — REQ-011 §4 "Cascades").
  A redeemed invite code is history: it is the record of *how* a specific registration came
  to exist, and REQ-011 §5's `no_show`/audit-adjacent reasoning already establishes that
  this schema never lets a past registration's provenance be silently invalidated by
  deleting the row it points to. Deleting an `invite_codes` row that a live `registrations`
  row references must fail, not cascade-null the reference and not cascade-delete the
  registration.
- This is an `ALTER TABLE` migration against an **existing** table
  (`ALTER TABLE registrations ADD CONSTRAINT ... FOREIGN KEY (invite_code_id) REFERENCES
  invite_codes(id) ON DELETE RESTRICT`), run *after* `CREATE TABLE invite_codes` in the same
  migration file (dependency order) or as its own follow-up statement in the same file —
  either is acceptable, BACKEND-DEV's choice. Because `invite_code_id` is currently
  entirely NULL in any existing data (no `InviteCode` table has ever existed to populate it
  from), adding the constraint cannot fail against pre-existing rows.

## 4. Code value generator — CSPRNG, typeable alphabet, stated entropy

### The tension, stated explicitly (per the handoff's instruction)

S4 sets the same unguessability bar for `InviteCode` values as for `qr_token`: "**≥128
bits** from a cryptographically secure source... never `Math.random`, never a sequential
id, never a hash of the user id." `generateQrToken()`'s precedent — 32 bytes of
`crypto.randomBytes`, hex-encoded — hits that bar exactly (256 bits) but produces a
64-character lowercase-hex string, which satisfies "cryptographically secure" while failing
"typeable": no human types a 64-character hex string from a printed poster or a
verbally-read code, and hex mixes visually similar characters research shows people
mistype easily (e.g. `0`/`o` when hand-transcribed, even though hex has no letter `o`
formally — the deeper issue is simply that 64 characters is too long to type reliably at
all). Story B7 requires redemption "by typing it" as an alternative to the `?start=i_<code>`
deep link, so the *value itself*, not just the delivery mechanism, must be short enough to
type without error while still meeting S4's entropy floor. These two pull against each
other: more entropy needs more characters; typeability needs fewer.

### Resolution: a 32-symbol alphabet, 26 characters, CSPRNG-drawn

**Alphabet (32 symbols, visually-ambiguous characters excluded):**

```
23456789ABCDEFGHJKLMNPQRSTUVWXYZ
```

- Digits `2`–`9` (8 symbols) — `0` and `1` excluded (confusable with letters `O`/`I`
  and, for `1`, with lowercase `l` in some fonts).
- Uppercase `A`–`Z` minus `I` and `O` (24 symbols) — `I` excluded as confusable with `1`,
  `O` excluded as confusable with `0`.
- Total: 8 + 24 = **32**, already an exact power of two (`log2(32) = 5` bits/character) —
  no further exclusion is needed to round the count. `0`, `O`, `1`, `I` are the
  non-negotiable exclusions per the ambiguity rule this requirement states; this artefact
  does not additionally exclude `L`/`Q`/`S`/`5`/etc., since 32 is already reached and every
  further exclusion would move the alphabet off a clean power of two, breaking the exact
  `log2` arithmetic below for no stated benefit. If BACKEND-DEV judges another character
  visually ambiguous enough to also exclude (a font/UX call outside this artefact's
  authority), the alphabet size should be dropped by two (to 30) or kept at a power of two
  by finding a compensating swap, so the entropy arithmetic stays exact.
- Case: **uppercase only** — a code that is case-sensitive but delivered/typed in mixed
  case invites transcription errors from a source (poster, screen) that itself may not
  preserve case cues clearly; fixing the alphabet to one case removes that failure mode
  entirely. If the redemption handler (REQ-038's scope) additionally normalizes user input
  to uppercase before comparison, that is a redemption-flow robustness choice, not
  something this artefact mandates — the *stored* value is uppercase-only by construction
  either way.

**Length and entropy:**

- Alphabet size: 32 symbols → `log2(32) = 5` bits of entropy per character (exact, since
  32 = 2⁵).
- S4's floor: ≥128 bits.
- Minimum length to clear the floor: `128 / 5 = 25.6` → **26 characters** (the smallest
  integer length whose total entropy is ≥ 128 bits).
- Resulting entropy: `26 × 5 = 130 bits` — **≥ 128 bits, satisfying S4** with a 2-bit
  margin from rounding up to a whole character.

**26 characters is long for a human to type in one unbroken run.** This artefact states,
rather than silently resolving, that display formatting (e.g. grouping as
`XXXX-XXXX-XXXX-XXXX-XXXX-XXXX`, five groups of four plus one group of six, or similar) is
a presentation-layer concern for whichever requirement renders the code to a user
(REQ-037's issuing message, REQ-040's invitation list) — hyphens or spacing are not part of
the **stored** `code` value and must be stripped/normalized by REQ-038's redemption handler
before comparison, exactly as the deep-link form `?start=i_<code>` would need the raw
26-character value with no separators embedded in the payload. This artefact does not
mandate a specific grouping; it states that the 26-character/130-bit value is what is
generated, stored, and compared, and that any human-facing chunking is display-only.

**Generator shape (design-level pseudocode — not implementation):**

```
CODE_ALPHABET = "23456789ABCDEFGHJKLMNPQRSTUVWXYZ"   // 32 symbols, 5 bits/char
CODE_LENGTH = 26                                       // 26 × 5 = 130 bits ≥ S4's 128-bit floor

function generateInviteCode() -> string:
  bytes = crypto.randomBytes(CODE_LENGTH)   // one CSPRNG call, cryptographically secure
  return map each byte -> CODE_ALPHABET[byte % 32]   // 32 divides 256 evenly: no modulo bias
```

- **Cryptographically secure source:** `crypto.randomBytes`, the same primitive
  `generateQrToken()` already uses — never `Math.random`, never a sequential id, never a
  hash of a user id (S4's exact negative-case list). BACKEND-DEV implements this as its own
  function (e.g. `generateInviteCode()` alongside `generateQrToken()` in
  `apps/bot/src/domain/`), not a modification of `generateQrToken()` itself — the two
  outputs serve different purposes (`qr_token` is machine-scanned only, never typed;
  `code` is typed-or-scanned) and should stay independently named and independently
  callable, per this requirement's "no domain logic" scope boundary — this artefact
  specifies the shape; BACKEND-DEV's REQ-037 writes the actual function.
- **No modulo bias:** mapping each raw byte (0-255) to `byte % 32` is unbiased specifically
  because 32 evenly divides 256 (256 / 32 = 8 exactly) — every alphabet symbol is equally
  likely regardless of which byte value maps to it. This is a real correctness property
  worth stating explicitly: it is *not* generally safe to take `randomByte % N` for an
  arbitrary `N` (it biases toward lower symbol indices when `N` does not evenly divide
  256), which is exactly why the alphabet size was kept at a clean power of two above,
  rather than an odd size like 30 or 31.
- **Collision handling:** at 130 bits of entropy the birthday-bound collision probability
  across any realistic volume of codes this product will ever issue (PRD 1's ~1,000
  users, ~10 events/year) is negligible enough that no uniqueness-retry loop is required
  for the *entropy* to hold — the `UNIQUE (code)` DB constraint (§1) is nonetheless the
  actual correctness backstop or a retry-on-conflict, exactly as `qr_token`'s own `UNIQUE`
  constraint (REQ-011 §4) is the backstop for its 256-bit space. This artefact does not
  mandate a specific retry mechanism (single insert-and-catch-unique-violation vs.
  check-then-insert) — an implementation choice for REQ-037.

## 5. What is NOT stored, and where the computation lives (binding, restated)

No column named `no_show`, `waitlist_position`, `seats_taken`, `registration_open`, or
`finished` is added by this migration — none of the five apply to `InviteCode` in the
first place, and this table adds no new instance of any of them. Restated here per this
requirement's own field-list discipline; REQ-010 §4 and REQ-011 §5 remain the binding
statements of the rule and its derivations for the entities those requirements own.

`used_count` is the one field in this migration that could plausibly be mistaken for a
violation of that rule — see the dedicated note in §1, which states explicitly why it is a
legitimate stored counter, not a derived report value with an improperly-added column.

## 6. Open questions (not resolved by invention)

1. **FR-4 "configurable per event" eligibility rule — explicitly UNRESOLVED here, routed
   to REQ-038.** PRD FR-4's `requires_invite=true, requires_approval=false` row states
   "Valid code → admitted; no code → offer wishlist," and FR-4 further states "a user who
   has `checked_in_at` on any past event satisfies `requires_invite` without a code
   (eligibility rule, **configurable per event**)." "Configurable per event" implies an
   `Event`-level flag or setting that PRD 5's `Event` entity (as designed in REQ-011 §2)
   does not list. **This requirement does not add such a column.** Inventing an unlisted
   `Event` field to resolve this ambiguity is exactly what the pipeline's own closing rule
   forbids (mirrors REQ-026's doors-time precedent: read what exists, do not add a field to
   make an ambiguous requirement text convenient). **REQ-038 (redemption + eligibility) owns
   this question** and must state, when it is drafted, either (a) a new `Event`-level flag
   with its own decision record justifying the addition, or (b) that the "past
   `checked_in_at` satisfies `requires_invite`" rule applies uniformly to every
   `requires_invite` event with no per-event override. This artefact records the question
   so REQ-038 cannot inherit it silently, per this requirement's explicit instruction.
2. **PERSONAL/COMPANION `max_uses` cardinality.** §2 flags that a companion code
   (`grants_companion_of` non-null) combined with `max_uses > 1` is not forbidden at the
   DB level and is not obviously meaningful as a business rule. Routed to REQ-037 (issuing)
   to state what combinations its own issuing flow ever produces.
3. **Whether `issued_to_user_id` is required, forbidden, or optional when
   `grants_companion_of` is set.** §2 states both legal combinations exist at the DB level
   without asserting which one(s) REQ-037's issuing flow should actually offer. Routed to
   REQ-037.
4. **`(event_id, issued_to_user_id)` uniqueness for personal codes.** §1 "Keys /
   uniqueness" notes no constraint prevents an event from having two personal codes issued
   to the same person (e.g. a replacement code). Not resolved here — routed to REQ-037 to
   confirm whether re-issuance should revoke/expire the prior code or simply coexist.
5. **Exact excluded-character set for the typeable alphabet (cosmetic).** §4's alphabet
   already excludes only `0/O` and `1/I` as the non-negotiable ambiguity exclusions — 32
   symbols is reached without excluding `L`, so `L` remains in the alphabet. §4 flags `Q`
   as an optional further exclusion BACKEND-DEV could make, at the cost of moving off a
   clean power of two (32 → 30) unless compensated by a swap. This is a cosmetic decision
   for BACKEND-DEV to finalize; the entropy arithmetic in §4 holds for any 32-symbol,
   power-of-two alphabet with the non-negotiable `0/O/1/I` exclusions applied.
6. **Redemption-time case/format normalization** (stripping display hyphens, uppercasing
   user-typed input before comparison) is explicitly REQ-038's concern, not this
   artefact's — noted in §4 so REQ-038 does not have to rediscover it.

```

  id                    uuid         PRIMARY KEY DEFAULT gen_random_uuid()
  event_id              uuid         NOT NULL REFERENCES events(id) ON DELETE RESTRICT
  code                  text         NOT NULL UNIQUE       -- 26 chars, 32-symbol typeable alphabet, see §4
  issued_to_user_id     uuid         NULL REFERENCES users(id) ON DELETE RESTRICT
  grants_companion_of   uuid         NULL REFERENCES users(id) ON DELETE RESTRICT
  max_uses              integer      NOT NULL
  used_count            integer      NOT NULL DEFAULT 0    -- real stored counter, see §1 note; atomic increment is REQ-038's problem
  expires_at            timestamptz  NULL
  created_at            timestamptz  NOT NULL DEFAULT now()
  updated_at            timestamptz  NOT NULL DEFAULT now()

-- ALTER on the existing registrations table:
alter table registrations:
  invite_code_id   uuid   NULL   -- unchanged nullability
    ADD CONSTRAINT FOREIGN KEY (invite_code_id) REFERENCES invite_codes(id) ON DELETE RESTRICT
```

## 8. Migration and reversibility

A single Drizzle Kit-generated `.sql` file (per `decisions/0005`, committed under
`apps/bot/`, e.g. `apps/bot/drizzle/000N_<slug>.sql`) that:

1. `CREATE TABLE invite_codes (...)` with the columns/types/defaults from §7, including
   `UNIQUE (code)` and the three FKs (`event_id`, `issued_to_user_id`,
   `grants_companion_of`), all `ON DELETE RESTRICT`.
2. `ALTER TABLE registrations ADD CONSTRAINT ... FOREIGN KEY (invite_code_id) REFERENCES
   invite_codes(id) ON DELETE RESTRICT` — run after step 1 in the same file, since the FK
   target must exist first.
3. Contains no `no_show`, `waitlist_position`, `seats_taken`, `registration_open`, or
   `finished` column or table anywhere (§5 — grep-checkable negative, per the migration
   acceptance criterion).
4. **Reversibility:** step 2's `ALTER TABLE ... ADD CONSTRAINT` is reversible by `ALTER
   TABLE registrations DROP CONSTRAINT ...` (Drizzle Kit names the constraint
   deterministically); step 1's `CREATE TABLE` is reversible by `DROP TABLE invite_codes`,
   which must run **after** the constraint from step 2 is dropped (FK dependency order,
   reverse of creation). Because `invite_code_id` has never had any non-null data (no
   `InviteCode` table has ever existed to populate it), this down-migration is fully
   data-loss-free on `registrations` — dropping the FK constraint alone does not touch any
   row's data, and the column reverts to exactly its pre-migration shape (plain nullable
   UUID, no FK). Dropping `invite_codes` loses only rows created after this migration, which
   is the expected, unambiguous down-migration outcome for a newly-added table.
5. Per `decisions/0005`'s consequence section: step 2 alters an **existing** table
   (`registrations`) that may carry real registration data by the time this migration runs
   in a live environment, but it adds a constraint rather than dropping or rewriting any
   existing column's data — no PII column is dropped or rewritten, and every existing
   `invite_code_id` value is NULL (per "Verified current state" above), so the ADD
   CONSTRAINT cannot fail against or alter any existing row's content. This artefact's own
   read is that this does not trigger the "SECURITY-REVIEWER sign-off for a migration
   dropping/rewriting PII" gate that decision names, but flags the question for
   SECURITY-REVIEWER/RELEASE-VALIDATOR to confirm rather than asserting it unilaterally,
   since `registrations` is a PII-adjacent table even though this specific column is not
   itself PII.

## 10. Summary for the handoff

One new table, `invite_codes` (UUID PK, `created_at`/`updated_at`, `event_id` FK,
`code` UNIQUE, `issued_to_user_id`/`grants_companion_of` both nullable FKs to `users.id`,
`max_uses`, `used_count` DEFAULT 0, `expires_at` nullable), all FKs `ON DELETE RESTRICT`.
PERSONAL/BULK/COMPANION are compositions of `issued_to_user_id`/`grants_companion_of`/
`max_uses` (§2), not a `type` enum — legal combinations stated explicitly, with two
cardinality questions (companion + `max_uses > 1`; `issued_to_user_id` required-or-not
alongside `grants_companion_of`) routed to REQ-037 rather than resolved here.
`registrations.invite_code_id` gains a real `ON DELETE RESTRICT` foreign key to
`invite_codes.id`, closing REQ-011 §11 open question 3, with no change to its nullability.
The code generator uses `crypto.randomBytes` (never `Math.random`), a 32-symbol alphabet
excluding `0/O/1/I` (visually ambiguous characters; `L` is not excluded — 32 symbols is
already reached without it), at 26 characters for exactly
`26 × 5 = 130` bits of entropy — ≥ S4's 128-bit floor — resolving the CSPRNG-vs-typeable
tension explicitly rather than picking one bar at the expense of the other. `used_count` is
confirmed as a legitimate stored counter, not a computed-value violation (§1), with its
atomicity left to REQ-038. FR-4's "configurable per event" eligibility rule is recorded as
explicitly unresolved and routed to REQ-038 (§6 point 1), not decided by invention here.
