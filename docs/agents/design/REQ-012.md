# REQ-012 — Bot config loading, Postgres connection and migration runner wired into apps/bot startup

**Role:** CODE-DESIGNER (design only — no implementation code; BACKEND-DEV implements
this artefact). No DATA-DESIGNER output is needed for this requirement: it introduces no
new stored entity or column, only infra/config wiring around the schema REQ-010/REQ-011
already designed and migrated (as generated `.sql` files under `apps/bot/drizzle/`).

**Scope:** extend `apps/bot/src/config.ts` (REQ-009's `loadConfig`) with two more fields;
add a pooled Postgres client; add a migration-runner npm script; add a local dev
docker-compose file under `apps/bot/`; extend REQ-009's no-secrets-logged pattern to a
small structured-logging helper. Builds on `docs/agents/decisions/0005-orm-drizzle.md`
(Drizzle ORM + Drizzle Kit, plain `.sql` migrations), `docs/guides/backend_dev_guide.md`
(pure `loadConfig`, S11), and `security-invariants.md` S11.

---

## 1. Extended config module (`apps/bot/src/config.ts`)

Current shape (REQ-009): `loadConfig(env)` returns `{ botToken, databaseUrl }`, is a pure
function (no I/O, no `process.exit`), throws an `Error` naming only the missing
variable(s) by name when `BOT_TOKEN` or `DATABASE_URL` is absent/empty. This requirement
extends it — same purity and same throw contract — never replaces it.

### 1.1 New fields

| Field | Env var | Required | Literal default allowed? | Validation |
|---|---|---|---|---|
| `botToken` | `BOT_TOKEN` | Yes (unchanged from REQ-009) | **No** (requirement text: "No literal defaults for the token or the database URL") | Present and non-empty, else name it in the missing list. |
| `databaseUrl` | `DATABASE_URL` | Yes (unchanged from REQ-009) | **No** | Present and non-empty, else name it in the missing list. |
| `logLevel` | `LOG_LEVEL` | No | **Yes** — the requirement's "no literal defaults" sentence names only the token and the database URL; it does not extend that prohibition to log level or default chapter code, and the description's parallel sentence ("log level and the default chapter code... validates them at startup") treats validation and defaulting as compatible for these two. Default: `"info"`. | If present, must be one of a fixed closed set: `"debug" \| "info" \| "warn" \| "error"`. An unrecognized value (e.g. `LOG_LEVEL=verbose`) is a validation failure — added to the same `missing`-style diagnostic list, but reported as "invalid value for LOG_LEVEL" rather than "missing", since the variable IS present. See open question 1 on whether "validates them at startup" for this field must reject bad values or may silently fall back — this design chooses **reject**, stated explicitly rather than assumed. |
| `defaultChapterCode` | `DEFAULT_CHAPTER_CODE` | No | **Yes** — same reasoning as `logLevel`. No default value is asserted by this design (see open question 2): the field is typed `string \| undefined`, and if unset, code that needs "the" default chapter (later requirements — /start with no chapter context, per PRD 5's `Chapter.code (uz\|kz)`) must handle the unset case itself. This module does not invent a fallback chapter code, because there is no stated business rule for what an unconfigured deployment's default chapter should be. |

### 1.2 Return shape

```
interface BotConfig {
  botToken: string;
  databaseUrl: string;
  logLevel: "debug" | "info" | "warn" | "error";
  defaultChapterCode: string | undefined;
}
```

`logLevel` is always populated (falls back to `"info"` when `LOG_LEVEL` is unset).
`defaultChapterCode` is `undefined` when `DEFAULT_CHAPTER_CODE` is unset — no literal
chapter-code default is invented (there is no canonical "first" chapter stated anywhere
in PRD 5 or PRD 1).

### 1.3 Validation / exit behavior

- `loadConfig` itself stays pure and throw-based, exactly as REQ-009 established: it
  collects every problem (missing `BOT_TOKEN`/`DATABASE_URL`, invalid `LOG_LEVEL`) into
  one list and throws a single `Error` whose message names every offending variable —
  never a value. `defaultChapterCode` cannot itself cause a validation failure (any
  string, or absence, is legal at this layer — later requirements validate it against
  the `chapters` table, since `loadConfig` has no database access and must stay pure per
  §1 of `backend_dev_guide.md`).
- `index.ts`'s existing `try { loadConfig(...) } catch { console.error(message); exit(1) }`
  pattern is unchanged in shape — it already satisfies "exits non-zero naming any missing
  variable" for the two new checks the same way it does for the original two, with no new
  branching needed in `index.ts` itself beyond passing the now-larger config through.

## 2. Postgres connection pooling

### 2.1 Library

`pg`'s own `Pool` (from the already-pinned dependency `pg@8.23.0` — REQ-009 selected
`pg` as the Postgres driver; no new dependency is added here). Drizzle's
`drizzle-orm/node-postgres` adapter (already present as `drizzle-orm@0.45.2`) wraps a
`pg.Pool` instance directly — this is the standard integration point for the
already-chosen ORM/driver pair, requiring no additional package.

### 2.2 Pool configuration and its justification

| Option | Value | Justification |
|---|---|---|
| `max` | **5** | PRD 1's stated load: ~1,000 users, ~10 events/year, peak throughput 0.06 requests/second, database under 50MB, and PRD 1's own explicit conclusion "one Postgres and one bot process are sufficient — do not add infrastructure." At 0.06 rps peak, the bot is handling roughly one request every 17 seconds at its *busiest* stated moment; a single Node event loop plus grammY's own concurrency (which does not run truly parallel DB calls per update under long polling in the way a multi-worker HTTP server would) will never hold more than a handful of connections open at once. A pool of 5 gives headroom for a burst (e.g. several admins clicking buttons around event-open time) without approaching Postgres's own default `max_connections` (100), and comfortably clears this requirement's own bar ("single-digit... a pool max of 20 or more fails this criterion absent a written load argument"). |
| `min` / `idleTimeoutMillis` | Left at `pg.Pool`'s own defaults (no `min`, 10s idle timeout) | Nothing in PRD 1 asks for warm-pool pre-allocation; at 0.06 rps peak, idle connections closing after 10s and reopening on demand costs nothing perceptible and avoids holding open connections against a database this small for no benefit. |
| `connectionTimeoutMillis` | 5000 (5s) | Fails fast rather than hanging indefinitely if Postgres is unreachable at startup — matters for the "exits non-zero" behavior this requirement's AC 2 tests, so a bad `DATABASE_URL` (wrong host/port) surfaces as a prompt failure, not a silent hang. Not itself a load-driven number — stated here as an explicit choice rather than left implicit. |
| `ssl` | Not configured in this design (left `undefined`/unset, i.e. no TLS negotiated) | Open question 3 — see below. |

### 2.3 Where the pool is constructed

A small module, e.g. `apps/bot/src/db/client.ts`, exporting a function that takes the
already-validated `databaseUrl` string (from `BotConfig`) and returns a `{ pool, db }`
pair: `pool = new Pool({ connectionString: databaseUrl, max: 5, connectionTimeoutMillis: 5000 })`,
`db = drizzle(pool, { schema })`. This module does no env reading itself — it receives
`databaseUrl` as a parameter, keeping `config.ts` the single place environment variables
are read (mirrors REQ-009's `index.ts` boundary: config module reads env, everything else
receives values). `index.ts` calls this after `loadConfig` succeeds, before `bot.start()`.

## 3. Migration runner

### 3.1 Command

`npm run migrate -w apps/bot`, backed by `apps/bot/package.json`'s new script:
`"migrate": "drizzle-kit migrate"`. Verified directly against the pinned
`drizzle-kit@0.31.10` binary's own `--help` output in this workspace: it exposes a
`migrate` subcommand (alongside `generate`, `introspect`, `push`, `studio`, `up`, `check`,
`drop`, `export`) that reads the same `drizzle.config.ts` already committed at
`apps/bot/drizzle.config.ts` (schema path `./src/db/schema.ts`, migrations directory
`./drizzle`, `dbCredentials.url` from `process.env.DATABASE_URL`). No custom script using
`drizzle-orm/node-postgres/migrator`'s `migrate()` helper is needed — `drizzle-kit migrate`
IS the tool's own built-in application of exactly the generated `.sql` files already
committed under `apps/bot/drizzle/` (`0000_tough_lilith.sql`, `0001_tired_annihilus.sql`
from REQ-010/REQ-011), so introducing a second, hand-rolled runner alongside it would
duplicate what the pinned tool already does.

### 3.2 Idempotency

`drizzle-kit migrate` tracks applied migrations in a dedicated tracking table it creates
and manages itself in the target database (schema `drizzle`, table
`__drizzle_migrations`, recording each applied migration's hash and timestamp). On every
invocation it reads that table, compares it against the migration files under
`apps/bot/drizzle/`, and applies only the ones not yet recorded. Re-running the identical
command against an already-migrated database therefore finds zero unapplied migrations
and exits 0 having changed nothing — this is the tool's own built-in behavior, not
something this design adds on top, and it is exactly what AC 1 requires ("running the SAME
command a second time... exits 0 and applies nothing further").

### 3.3 "Reports which migrations it applied"

`drizzle-kit migrate`'s own CLI output lists each migration file it applies during that
run (and prints nothing to apply when there is nothing pending). This design relies on
that native output directly — BACKEND-DEV's verification report captures the actual
stdout of both runs (empty-DB run showing the two files applied; second run showing none)
as the evidence AC 1 asks for. No wrapper script is introduced solely to reformat this
output; doing so would be scope the requirement text does not ask for ("reports which
migrations it applied" is satisfied by the tool's existing behavior, observed and quoted
in the verification report — not a new feature to build).

### 3.4 Secrets during migration

`drizzle.config.ts` already reads `DATABASE_URL` directly from `process.env` (REQ-009-era
file, unchanged by this requirement) — this design does not route the migration runner's
DB credential through `config.ts`'s `loadConfig`, since `drizzle-kit` is a separate CLI
process with its own config file, not code that imports `apps/bot/src/`. This is a
pre-existing seam, not one this requirement introduces; it is noted here for
completeness because REQ-012 is the requirement that first actually runs migrations
against a real database.

## 4. Local dev docker-compose

**Location:** `apps/bot/docker-compose.yml` (not `docker-compose.dev.yml` — this is the
only compose file under `apps/bot/`, so no `.dev` qualifier is needed to disambiguate it
from anything else in that directory; `deploy/docker-compose.qa.yml` and
`deploy/docker-compose.prod.yml` remain the only compose files under `deploy/`,
untouched, per AC 4).

**Shape** (prose, not a code block — BACKEND-DEV writes the actual YAML):

- Exactly one service, `postgres`, image `postgres:16-alpine` (matches the "Postgres"
  driver/dialect already pinned; 16 is a current stable major, `-alpine` keeps the image
  small — consistent with PRD 11's minimal-footprint stance even for a dev-only tool).
- Environment: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` set to fixed
  **non-secret, dev-only** literal values (e.g. `bot`/`bot`/`bot`) — acceptable here
  specifically because this file only ever provisions a local/CI throwaway database, never
  a real credential; S11 governs values that reach logs/exports, not a disposable local
  dev password that is never real production data.
- Port mapping: host `55432 -> container 5432`. Chosen to avoid colliding with a
  developer's own locally-installed Postgres (default port 5432) and with
  `deploy/docker-compose.*.yml`'s `3120` (an HTTP port on an unrelated service, no
  collision risk there regardless, but flagged as checked). `apps/bot/.env`-style local
  config would then set `DATABASE_URL=postgres://bot:bot@localhost:55432/bot` — this
  design does not commit an actual `.env` file (never commit secrets/URLs — though this
  one is a fixed dev-only value, the file itself is still not part of this design's
  deliverable list per the requirement's scope).
- A named volume (e.g. `bot_pg_data`) so data survives `docker compose stop`/`start`
  across a dev session, but is trivially destroyable (`docker compose down -v`) when a
  clean slate is wanted for migration-runner testing.
- No other service (no pgAdmin, no bot container itself) — the requirement asks only for
  "a local development docker-compose... bringing up a Postgres instance," not a full dev
  stack; adding more would be scope beyond what was asked.

## 5. Structured logging

**Approach:** no new logging library/dependency. A small wrapper module, e.g.
`apps/bot/src/log.ts`, exporting leveled functions (`debug`/`info`/`warn`/`error`) that:

- Compare the message's level against `BotConfig.logLevel` (from §1) and no-op below
  threshold — the only place `logLevel` is consumed.
- Accept a message string and an optional plain-object `fields` argument, and print via
  `console.log`/`console.error` a single JSON line (`{ level, msg, ...fields, time }`) —
  "structured" here means machine-parseable one-line JSON, not a hierarchical or
  multi-line format, which is the appropriate ceiling for PRD 11's small-scale, one-process
  deployment (no log aggregation pipeline exists to justify a heavier structured-logging
  library like `pino`, and adding one would be exactly the kind of infrastructure PRD 1
  says this project doesn't need).
- **Never accept `databaseUrl`, `botToken`, `phone`, or `email` as a field name** — this is
  enforced by convention (a code-review / REVIEWER checklist item, since a generic logger
  cannot statically know a caller won't pass a secret under an unexpected key) and by
  construction: every call site in this requirement's own scope (config validation
  failure, pool connect/error events, migration-adjacent log lines) only ever has access
  to variable *names*, not their values, matching REQ-009's existing pattern in
  `config.ts`'s thrown `Error` message. The wrapper itself performs one mechanical guard as
  defense in depth: before serializing `fields`, it drops (does not print) any key
  literally named `databaseUrl`, `connectionString`, `botToken`, `token`, `phone`, or
  `email`, replacing the value with the string `"[redacted]"` — this catches an accidental
  future call site passing one of these keys without requiring every caller to remember
  the rule perfectly.
- `console.log("bot starting")` (REQ-009's existing line in `index.ts`) either stays as a
  plain line or is replaced with `log.info("bot starting")` — BACKEND-DEV's call, since
  both satisfy the same requirement; no design preference is stated because nothing in
  scope depends on which.

## 7. Open questions

1. **Does `LOG_LEVEL` validation reject an unrecognized value, or silently fall back to
   `"info"`?** This design chose **reject** (treated as a validation failure alongside the
   missing-variable checks) because the requirement text says config fields are
   "validated at startup," and silently swallowing a typo'd `LOG_LEVEL` value would hide a
   misconfiguration rather than surface it. Not explicitly stated in the requirement text
   either way — flagging so BACKEND-DEV/CODE-DESIGN-VALIDATOR can confirm or override this
   reading rather than it being silently assumed correct.
2. **Should `DEFAULT_CHAPTER_CODE` have a literal fallback value (e.g. `"uz"`, matching
   PRD 5's `Chapter.code (uz\|kz)` first-listed value) instead of being left unset when
   absent?** This design deliberately does NOT invent one — no requirement or PRD text
   states which chapter is "the" default when none is configured, and REQ-010's own design
   states chapters are looked up by code, not ordinally. If a later requirement (e.g. the
   `/start` flow) needs a concrete fallback chapter when `DEFAULT_CHAPTER_CODE` is unset,
   that decision belongs to that requirement, not to this config-loading slice.
3. **TLS (`ssl` option) for the Postgres connection.** This design leaves it unset
   (no TLS negotiated) because no requirement or decision record states the target
   deployment's Postgres is reachable only over TLS, and PRD 11 describes "one small
   server" (plausibly a same-host or same-private-network Postgres). If the actual
   deployment target requires `sslmode=require` (e.g. a managed Postgres service reached
   over a public network), that is an operational fact BACKEND-DEV or ORCH must supply
   before implementation — this design does not guess it, and `pg.Pool` also honors
   `?sslmode=` query parameters embedded directly in `DATABASE_URL` itself as a
   configuration-free alternative if that turns out to be the actual requirement.
4. **Fixed dev-only credentials in `apps/bot/docker-compose.yml`.** §4 proposes literal
   non-secret values (`bot`/`bot`/`bot`) for local Postgres. If REVIEWER/SECURITY-REVIEWER
   wants even a dev-only compose file to avoid ANY literal credential (e.g. requiring an
   `.env` file read via `env_file:` instead), that is a stricter bar than this design
   assumes S11 requires — flagged rather than silently decided either way.
