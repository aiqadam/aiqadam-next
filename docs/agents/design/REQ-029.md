## 1. The deep-link grammar and dispatch point

### 1.1 Extending `parseStartPayload` (`domain/event.ts`)

`StartPayload`'s union gains one member:

```
export type StartPayload =
  | { kind: "none" }
  | { kind: "event"; eventId: string; channel: string | null }
  | { kind: "checkin"; qrToken: string };   // NEW
```

Grammar, stated as a table (the existing function's `e_`/`e_<id>__<channel>` branches are
unchanged — this is an additional, mutually exclusive prefix check that must run before
the `e_` check, since `ci_` and `e_` share no overlap but both must be checked against the
same raw trimmed string):

| Raw payload (trimmed) | Result |
|---|---|
| empty string | `{ kind: "none" }` (unchanged) |
| starts with `"ci_"` | `{ kind: "checkin", qrToken: <everything after "ci_"> }` |
| starts with `"e_"` | unchanged existing `event` branch |
| anything else | `{ kind: "none" }` (unchanged) |

No validation of the token's shape (length, hex charset) happens in this parse step — an
empty or malformed `qrToken` is simply a token that will not be found by §2.1's lookup and
therefore falls into the existing "unknown token" refusal (§3.1), exactly the same
treatment REQ-016's `e_` branch gives a malformed event id. No new validation branch is
needed here.

### 1.2 Dispatch in `makeStartHandler` (`handlers/start.ts`)

Placed as a **second branch alongside** the existing `payload.kind === "event"` check
(§6.3's existing REQ-016 dispatch), evaluated in the same place, on the same
already-resolved `flowUser` (the scanner's own row, created/loaded by the same
`resolveOrCreateUser`/`getFlowUserByTgId` calls that already run unconditionally at the
top of `makeStartHandler` before any payload branch):

| `payload.kind` | Handler called |
|---|---|
| `"event"` | `resolveEventDeepLink(...)` — unchanged, REQ-016 |
| `"checkin"` | **NEW** `resolveCheckinQrDeepLink(ctx, db, flowUser.id, lang, payload.qrToken)` (§6.1) |
| `"none"` | falls through to the existing onboarding flow, unchanged |

**Why no consent gate for this branch (unlike `"event"`'s branch):** the `"event"`
branch's consent gate exists because a published-event deep link may *write*
`users.pending_source` for the tapping user (§6.5, REQ-016) — that is data about the
person running `/start`. The check-in flow writes nothing about the scanner beyond what
`checked_in_by` (a foreign key to their existing `users.id` row, already created with no
extra consent requirement anywhere else in this codebase — the same is true of every
`EventStaff`/organizer action today, e.g. REQ-028's manual check-in never consent-gates
the staff member performing it) records on someone else's registration. No new PII about
the scanner is collected or stored. **This is a deliberate design decision, stated
explicitly rather than silently assumed**, following the precedent every existing
staff/organizer-facing write in this codebase already sets (REQ-018/020/028's staff
actions are never consent-gated on the actor).

**Why the scanner is resolved via `ctx.from.id`, never via the token:** `flowUser.id`
(the acting/scanning user) comes from the ordinary `resolveOrCreateUser(db, { tgId:
BigInt(tgId), ... })` call already at the top of `makeStartHandler` — the same mechanism
every other `/start` branch uses. The `qr_token` never identifies the scanner; it
identifies the registration being scanned (S4). These are two structurally different
people and the design keeps their resolution paths structurally separate: scanner via
`ctx.from.id` → `flowUser.id`; attendee via `qr_token` → `registrations.id` (§2.1).

## 2. Reads

### 2.1 Resolving the token to a registration + everything the flow needs

```
// domain/registration.ts — addition
export interface QrCheckinLookup {
  registrationId: string;
  eventId: string;
  eventTitle: string;
  eventEndsAt: Date;
  eventChapterId: string;
  attendeeUserId: string;
  admission: AdmissionState;
  checkedInAt: Date | null;
  checkedInBy: string | null;
  qrToken: string;
  displayName: string;
  company: string | null;
}

export async function getRegistrationByQrTokenForCheckin(
  db: DbClient["db"],
  qrToken: string,
  lang: BotLang,
): Promise<QrCheckinLookup | null>;
```

Query shape: one `SELECT` joining `registrations` → `events` (for `endsAt`/`title`/
`chapterId`, needed by §5's authorization call) → `profiles` (`LEFT JOIN`, same
nullability as REQ-028 §2.1) → `users` (for `tgUsername`, the same display-name fallback
source), filtered on `registrations.qr_token = $qrToken`. Returns `null` when no row
matches — this is what makes AC4's "unknown token" refusal structural, not a caught
exception.

**Never selects `profiles.phone`/`profiles.email`** — same structural guarantee AC3
already established for REQ-028's list query and AC5 requires here: those two columns are
simply absent from this query's `select` clause.

`displayName` is derived by the **same table** REQ-028 §2.1 already defines
(firstName+lastName / firstName alone / lastName alone / `@tgUsername` / fixed
`noNameFallback`). This design reuses that table's existing implementation,
`deriveCheckinDisplayName`, by **exporting** it (currently file-private in
`registration.ts`) rather than re-deriving the same rule a second time — a plumbing
change (adding the `export` keyword to an existing, unchanged function), not new logic.

**This one lookup is deliberately unlocked** (a plain `SELECT`, no `FOR UPDATE`) — it
exists only to (a) decide "unknown token" immediately, and (b) obtain `eventId`/
`eventEndsAt`/`eventChapterId` so §5's authorization gate can run before anything else.
The authoritative, write-time-safe read happens again, locked, inside §3.2's transaction
— exactly the same two-phase shape (`toggleCheckIn`'s design) REQ-028 §3.2 already
establishes, for the same reason: authorization must be checked before the transaction
opens (it needs `eventId`, which this unlocked read supplies), but the actual admission
decision must be re-read fresh, inside the lock, immediately before any write.

## 3. The QR-specific decision: a NEW function, not a reuse of REQ-028's toggle

### 3.1 Why `decideCheckinToggleOutcome` (REQ-028) cannot be reused as-is

`decideCheckinToggleOutcome`'s outcome union is `not-found | refused-not-admitted |
check-in | undo`. Three structural mismatches with this requirement's refusal table rule
out reusing it unchanged:

1. **QR must never undo a check-in.** Re-scanning an already-checked-in attendee's token
   must **report** the existing check-in (AC2: "report WHEN and BY WHOM. NEVER a
   duplicate write") — `decideCheckinToggleOutcome`'s 4th branch (`checkedInAt !== null`
   → `"undo"`) would silently *clear* `checked_in_at` on a second scan, which is exactly
   the behavior AC2 forbids for this flow (manual check-in's toggle-off is a deliberate,
   different UX for a different surface — a staff member correcting a mistaken tap on a
   list they are looking at — not appropriate for "the same physical person walked past
   the door scanner a second time").
2. **The refusal reason must be reportable per-state**, not just carried opaquely. AC3
   requires "a refusal STATING THAT SPECIFIC REASON" for waitlisted vs. requested vs.
   withdrawn — `decideCheckinToggleOutcome`'s `refused-not-admitted` already carries
   `admission`, so the *data* is there, but the QR flow additionally needs the override
   offer attached to that same outcome (§3.1's own table below), which REQ-028's manual
   list flow has no concept of at all (manual check-in is staff-only; overriding a
   non-admitted attendee into checked-in is a new, organizer-only transition, §4).
3. **The write differs**: `check_in_method` must be `'qr'` here, never `'manual'`
   (`toggleCheckIn`'s hardcoded literal). Two different, independently correct constant
   check-in methods cannot share one write function without threading a method parameter
   through it — at which point it is no longer meaningfully "the same function," and
   `toggleCheckIn`'s existence and REQ-028's own acceptance criteria must not be
   disturbed by adding QR-only concerns to it.

**Decision: a new, parallel pure decision function, matching this file's own established
`decide*`/`*Registration`-or-`*CheckIn` naming and shape convention** (row-lock read →
pure decide → conditional write → exactly one audit row, same skeleton
`toggleCheckIn`/`withdrawRegistration`/`reconfirmRegistration` already use) — not a
divergent style, just a distinct outcome table because the actual business rule is
distinct.

### 3.2 The pure decision table

```
// domain/registration.ts — addition
export interface QrCheckinDecisionInput {
  registrationExists: boolean;
  admission: AdmissionState | null;
  checkedInAt: Date | null;
}

export type QrCheckinOutcome =
  | { kind: "unknown-token" }
  | { kind: "already-checked-in" }
  | { kind: "refused-not-admitted"; admission: AdmissionState }
  | { kind: "check-in" };

export function decideQrCheckinOutcome(
  input: QrCheckinDecisionInput,
): QrCheckinOutcome;
```

First-match-wins table, stated exactly (no comparison written as code — see the note
below the table):

| Step | Condition | Result |
|---|---|---|
| 1 | `!registrationExists` | `{ kind: "unknown-token" }` |
| 2 | `admission !== "admitted"` | `{ kind: "refused-not-admitted", admission }` |
| 3 | `checkedInAt !== null` | `{ kind: "already-checked-in" }` |
| 4 | none of the above (`admission === "admitted"` and `checkedInAt === null`) | `{ kind: "check-in" }` |

Note the ordering difference from `decideCheckinToggleOutcome`: step 2 checks `admission`
*before* `checkedInAt`, same relative order as REQ-028's table, but step 3/4's outcomes
diverge (report vs. undo) exactly as reasoned in §3.1.

**Per-`admission` refusal copy** (AC3's "specific reason"), a table, not a branch written
as code — the handler (§6.1) selects the catalog string by `admission` value on the
`refused-not-admitted` outcome:

| `admission` | Catalog key |
|---|---|
| `"waitlisted"` | `checkinQr.refusedWaitlisted` |
| `"requested"` | `checkinQr.refusedRequested` |
| `"withdrawn"` | `checkinQr.refusedWithdrawn` |
| `"rejected"` | `checkinQr.refusedRejected` |

Every one of these four also attaches the override offer (§4) — see Open Question 1 for
why `"rejected"` is included even though no acceptance criterion tests it directly.

### 3.3 The transactional write, including the token-currency recheck (S4)

```
// domain/registration.ts — addition
export async function performQrCheckIn(
  db: DbClient["db"],
  registrationId: string,
  qrToken: string,
  staffUserId: string,
  at: Date,
): Promise<QrCheckinOutcome & { eventId?: string; checkedInAt?: Date; checkedInByDisplayName?: string }>;
```

Sequence, stated exactly (mirrors `toggleCheckIn`'s shape — row lock, fresh read, pure
decide, conditional write, one audit row):

1. Open `db.transaction`. `SELECT id, event_id, admission, checked_in_at, checked_in_by,
   qr_token FROM registrations WHERE id = $registrationId FOR UPDATE` — a **fresh,
   locked** read, never reusing §2.1's unlocked snapshot.
2. **S4's token-currency check, load-bearing and distinct from REQ-028's precedent** (no
   equivalent exists there, since the manual flow never carries a token at all): the
   locked row's `qr_token` must **still equal** the `qrToken` this call was invoked with.
   If it does not — the registration was re-issued a new token in between (e.g. the
   attendee withdrew and re-registered, `registerForEvent` §3.2 step 8 generates a fresh
   `qrToken` for a newly admitted outcome) — the row is treated **exactly as
   `"unknown-token"`**, even though a row with this `id` still exists. This is what makes
   "a `qr_token` authorizes exactly one thing" (S4) true at the instant of the write, not
   just at the instant `getRegistrationByQrTokenForCheckin` (§2.1) first resolved it —
   closing the gap where a stale printed/screenshotted QR code could keep working through
   an id-based re-lookup even after its own token was superseded.
3. `decideQrCheckinOutcome({ registrationExists: row !== undefined, admission:
   row?.admission ?? null, checkedInAt: row?.checkedInAt ?? null })` — only reached once
   step 2's token-currency check passes; step 2's failure short-circuits to
   `"unknown-token"` before this call.
4. `"unknown-token"` or `"refused-not-admitted"` → **no write, no audit row**, return the
   outcome as-is (mirrors REQ-028 §3.2 step 3's identical no-write-on-refusal discipline).
5. `"already-checked-in"` → **no write** (AC2's "NEVER a duplicate write" — this is the
   entire reason this outcome is distinguished from `"check-in"` rather than collapsed
   into it). The caller (§6.1) separately calls `getCheckinActorDisplayName` (§2.2) using
   the locked row's own `checked_in_by`/`checked_in_at` to build the report — no audit row
   (reporting an existing state is not itself a status change, S8).
6. `"check-in"` → `UPDATE registrations SET checked_in_at = $at, checked_in_by =
   $staffUserId, check_in_method = 'qr' WHERE id = $registrationId`, then
   `writeAuditLog(tx, { actorUserId: staffUserId, action: "registration.checkin", entity:
   "registration", entityId: registrationId, payload: { eventId: row.eventId, method:
   "qr" }, at })` — same transaction (S8), same `"registration.checkin"` action string
   REQ-028's manual path already uses (this is the same underlying event — "a check-in
   happened" — the `method` payload field and the `check_in_method` column both already
   distinguish qr from manual; no reason to fork the audit action name).
7. Return the outcome, with `eventId`/`checkedInAt`/`checkedInByDisplayName` attached as
   applicable (the handler needs these to compose the success/report screen without a
   second round trip).

**Why this satisfies AC2's "BYTE-FOR-BYTE unchanged" on a repeat scan:** step 5 performs
no `UPDATE` at all on the `"already-checked-in"` branch — there is no write for the value
to differ across. The DB `CHECK` constraint (§0) remains a second, independent backstop
exactly as REQ-028 §0 already establishes for the manual path.

## 4. The organizer override

### 4.1 The pure decision

```
// domain/registration.ts — addition
export interface OverrideDecisionInput {
  registrationExists: boolean;
  admission: AdmissionState | null;
}

export type OverrideOutcome =
  | { kind: "not-found" }
  | { kind: "already-admitted"; admission: AdmissionState }
  | { kind: "override-admit" };

export function decideOverrideOutcome(
  input: OverrideDecisionInput,
): OverrideOutcome;
```

First-match-wins table:

| Step | Condition | Result |
|---|---|---|
| 1 | `!registrationExists` | `{ kind: "not-found" }` |
| 2 | `admission === "admitted"` | `{ kind: "already-admitted", admission }` |
| 3 | none of the above (`admission` is `requested`/`waitlisted`/`withdrawn`/`rejected`) | `{ kind: "override-admit" }` |

Step 2 is defensive/unreachable in the intended flow (the override button, §6.2, is only
ever shown on a `"refused-not-admitted"` outcome, §3.2) but is stated explicitly rather
than assumed, following this codebase's own convention of naming defensive branches
(e.g. `event.ts`'s `endsAt === null` checks) rather than leaving them implicit.

**Deliberately, no capacity/`seatsLeft` check appears anywhere in this table.** S7 states
the property this transition exists to satisfy: "`seats_taken` exceeds `capacity` **only**
via an explicit organizer override that writes an `AuditLog` row" — this transition *is*
that explicit override, so re-running `decideRegistrationOutcome`'s capacity gate here
would contradict the very invariant it is designed to satisfy. `registerForEvent`
(REQ-020) is therefore **not** reused or called by this path — it exists to enforce the
capacity gate this transition is explicitly allowed to bypass, so reusing it would either
force a capacity check the requirement forbids on this path or require it to grow a
bypass parameter it has no other caller for.

### 4.2 The transactional write

```
// domain/registration.ts — addition
export async function overrideAdmitAndCheckIn(
  db: DbClient["db"],
  registrationId: string,
  organizerUserId: string,
  at: Date,
): Promise<OverrideOutcome & { eventId?: string }>;
```

Sequence, same skeleton as §3.3:

1. `db.transaction`: `SELECT id, event_id, admission FROM registrations WHERE id =
   $registrationId FOR UPDATE` — fresh, locked.
2. `decideOverrideOutcome({ registrationExists: row !== undefined, admission:
   row?.admission ?? null })`.
3. `"not-found"` or `"already-admitted"` → no write, no audit row.
4. `"override-admit"` → **one** `UPDATE registrations SET admission = 'admitted',
   checked_in_at = $at, checked_in_by = $organizerUserId, check_in_method = 'manual'
   WHERE id = $registrationId` (both the admission change and the check-in happen in this
   single `UPDATE` — "admitting and checking in a previously-refused attendee" is one
   move, per the requirement's own wording, not two separate writes), then **exactly one**
   `writeAuditLog(tx, { actorUserId: organizerUserId, action:
   "registration.override_admit_checkin", entity: "registration", entityId:
   registrationId, payload: { eventId: row.eventId, previousAdmission: row.admission },
   at })` — satisfying AC6's "exactly one audit_log row" by construction (one `UPDATE`,
   one `writeAuditLog` call, one transaction, same discipline every other mutation
   function in this file already follows).
5. Return the outcome with `eventId` attached.

`check_in_method` is set to `'manual'` here, not `'qr'` — the override is an organizer's
administrative act performed by tapping a button in a chat, not a camera scan of the
attendee's own code (see §4.3/§6.2: the tapping user is re-authorized as organizer at the
moment of the tap, structurally distinct from the original QR scan that produced the
refusal).

### 4.3 The override's OWN authorization — organizer, not EventStaff

**This must be a stricter, separate authorization check from `requireEventStaffForEvent`,
reasoned explicitly:**

- S2 states `EventStaff` grants "check-in rights for that one event and nothing else."
  Admitting a waitlisted/requested/withdrawn/rejected attendee **overrides the capacity
  and waitlist rules** `registerForEvent`/`promoteFromWaitlistIfEligible` otherwise
  enforce — a decision about *who gets a seat*, not merely *whether someone already
  admitted has arrived*. That is squarely an organizer-level decision (PRD 12.2's
  "logged-override principle" frames it as a deliberate, accountable exception, not a
  routine door action), and REQ-030's own design (walk-in registration, same
  build-order step) independently arrives at the same organizer-only framing for the
  structurally identical "admit past normal rules" action.
- **Reused unchanged:** `domain/eventAuthorization.ts`'s `requireOrganizerForChapter`
  (REQ-016) — the exact same function every event-mutation handler already calls, applied
  here against the refused registration's **event's `chapterId`** (available from §2.1's
  `eventChapterId`, or re-fetched via `getEventById` inside the override callback handler
  — §6.2's choice, not gated by this design). No new authorization module is written.
- **The tapping user, not the original scanner, is who gets checked.** The override
  button (§6.2) is shown to whoever received the refusal reply — typically the same
  volunteer who scanned the token, who is `EventStaff` but very possibly **not** an
  organizer. Tapping the button re-runs `requireOrganizerForChapter` against **the
  tapper's own `ctx.from.id`** at the moment of the tap. A staff volunteer without
  organizer rights tapping it is refused (`checkinQr.overrideNotAuthorized`) exactly as
  any other organizer-only action in this codebase already refuses a non-organizer — see
  Open Question 2 for the resulting real-world workflow implication.

## 5. Extending `requireEventStaffForEvent` so AC1's audit row names the registration

### 5.1 Why an unchanged reuse is not sufficient here

`requireEventStaffForEvent`/`buildCheckinRefusalAudit` (REQ-018, reused unchanged by
REQ-028) already write an audit row on every authorization failure — but with `entity:
"event"` and `entityId: eventId`. REQ-018/028's own callers have no specific registration
in play at authorization time (`/checkin <event_id>` authorizes against an event, full
stop). **This requirement's AC1 explicitly requires the row to name "the actor, the
action AND THE REGISTRATION"** — a stronger, specific requirement this codebase's existing
audit shape does not meet as-is for this call site.

### 5.2 The extension — backward-compatible, additive only

Both functions gain **one new optional parameter**, defaulting to today's exact behavior
when omitted (every existing call site — REQ-028's `/checkin`, toggle, and page-turn
handlers — passes nothing and is therefore byte-for-byte unaffected):

```
// domain/eventStaffAuthorization.ts — signature changes only
export function buildCheckinRefusalAudit(
  user: ActingUser | null,
  eventId: string,
  reason: Extract<CheckInAuthorizationResult, { ok: false }>["reason"],
  registrationId?: string,          // NEW, optional
): Omit<WriteAuditLogInput, "at">;

export async function requireEventStaffForEvent(
  db: DbClient["db"],
  tgId: bigint,
  eventId: string,
  eventEndsAt: Date,
  evaluationTime: Date,
  registrationId?: string,          // NEW, optional
): Promise<CheckInAuthorizationResult>;
```

`buildCheckinRefusalAudit`'s output, as a table (not a branch written as code):

| `registrationId` argument | `entity` | `entityId` |
|---|---|---|
| omitted (`undefined`) — every existing REQ-018/028 call site | `"event"` (unchanged) | `eventId` (unchanged) |
| provided — this requirement's `resolveCheckinQrDeepLink` (§6.1) call only | `"registration"` | `registrationId` |

`payload` stays `{ reason }` in both cases — unchanged shape, no new field. `actorUserId`
and `action` ("checkin.refused") are already exactly what AC1 asks for ("actor" and
"action"); only the entity identification needed to shift to satisfy "the registration."

This is the **only** modification anywhere in this requirement to an existing, previously
reviewed file — flagged explicitly per `core-directives.md`'s Unblock-Everything scope
(this is not incidental scope creep; AC1 cannot be satisfied without it, since it is the
one and only place this codebase writes a refusal audit row for a non-staff scanner).

## 6. Handlers

### 6.1 `resolveCheckinQrDeepLink` (`handlers/checkinQr.ts`, new file)

```
export async function resolveCheckinQrDeepLink(
  ctx: Context,
  db: DbClient["db"],
  scannerUserId: string,
  lang: BotLang,
  qrToken: string,
): Promise<void>;
```

Sequence:

1. `lookup = getRegistrationByQrTokenForCheckin(db, qrToken, lang)` (§2.1).
2. `lookup === null` → reply `checkinQr.unknownToken` (AC4's unknown-token refusal), return.
3. `tgId = ctx.from?.id`; `undefined` → return (defensive, mirrors every other handler's
   own top-of-function guard in this codebase).
4. `authResult = requireEventStaffForEvent(db, BigInt(tgId), lookup.eventId,
   lookup.eventEndsAt, new Date(), lookup.registrationId)` (§5's extended call, supplying
   `registrationId` so any refusal audit names this registration).
5. `!authResult.ok` → reply by `authResult.reason`:
   | `reason` | Catalog key |
   |---|---|
   | `"no-user"` / `"not-staff-for-event"` | `checkinQr.notStaff` (AC1's refusal; the audit row was already written inside step 4's call, per §5) |
   | `"event-ended"` | `checkinQr.eventEnded` (AC4's second refusal case — S4's "token doesn't outlive the event") |

   Return in either case — no further processing.
6. Scanner is authorized. `outcome = performQrCheckIn(db, lookup.registrationId,
   qrToken, <the scanner's own users.id — resolved via the same
   `resolveActingUser`/`eventStaffAuthorization.ts` lookup `authResult` already implies;
   this handler resolves it once, not duplicated>, new Date())` (§3.3).
7. `outcome.kind === "unknown-token"` → reply `checkinQr.unknownToken` (the token-currency
   recheck, §3.3 step 2, found the token superseded between §2.1's read and this write —
   same copy as step 2's unknown-token case, since to the scanner this is
   indistinguishable from "never a valid token").
8. `outcome.kind === "refused-not-admitted"` → reply with the admission-specific catalog
   key from §3.2's table, **with an inline keyboard** offering the override:
   `InlineKeyboard().text(catalog.checkinQr.overrideButtonLabel,
   "checkin:override:" + lookup.registrationId)` (AC3's "offer organizer override").
9. `outcome.kind === "already-checked-in"` → `actorName =
   getCheckinActorDisplayName(db, outcome's checked_in_by, lang)` (§2.2); reply
   `checkinQr.alreadyCheckedIn` interpolated with the existing `checked_in_at` and
   `actorName` (AC2's "report WHEN and BY WHOM").
10. `outcome.kind === "check-in"` → reply the success screen: `lookup.displayName`,
    `lookup.company`, and `countCheckedIn(db, lookup.eventId)` (REQ-028's existing counter,
    reused unchanged) — composed as `checkinQr.successHeader` (AC5: name, company, live
    counter, **never** phone/email — this handler never reads or has access to those two
    columns at all, per §2.1's structural exclusion).

### 6.2 `checkin:override:<registrationId>` callback (`handlers/checkinQr.ts`)

```
export const CHECKIN_OVERRIDE_PATTERN = /^checkin:override:(.+)$/;

export function makeCheckinOverrideCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence:

1. Extract `registrationId` from `CHECKIN_OVERRIDE_PATTERN`; no match →
   `ctx.answerCallbackQuery()`, return (defensive, unreachable).
2. `tgId = ctx.from?.id`; `undefined` → `ctx.answerCallbackQuery()`, return.
3. Resolve the registration's `eventId`/`chapterId` (a plain, unlocked read — reuses
   `getEventIdForRegistration` (REQ-023, existing) then `getEventById` (existing) for
   `chapterId`, the same two-step shape REQ-028's toggle callback §4.2 step 3 already
   uses for its own re-authorization read).
4. `authResult = requireOrganizerForChapter(db, BigInt(tgId), event.chapterId)` (§4.3,
   reused unchanged). `!ok` → `ctx.answerCallbackQuery({ text:
   checkinQr.overrideNotAuthorized, show_alert: true })`, no write, return.
5. `outcome = overrideAdmitAndCheckIn(db, registrationId, authResult.user.id, new
   Date())` (§4.2).
6. `outcome.kind === "not-found"` or `"already-admitted"` → `ctx.answerCallbackQuery({
   text: checkinQr.overrideNotApplicable, show_alert: true })`, no further action
   (defensive; unreachable in the intended flow per §4.1).
7. `outcome.kind === "override-admit"` → `ctx.answerCallbackQuery()`, then
   `ctx.editMessageText` (or a follow-up `ctx.reply`, BACKEND-DEV's choice — no acceptance
   criterion pins the exact message-editing mechanic here, unlike REQ-028's in-place list
   edit) showing `checkinQr.overrideSuccess` with the same name/company/counter shape as
   §6.1 step 10's success screen (S3 applies identically here — no phone/email).

## 8. No Mini App, no WebApp, no custom client (AC7)

Nothing in this design adds, imports, or references:
- Telegram's `web_app` inline-keyboard button field, or any `sendInvoice`/`WebApp`-family
  grammY API,
- a `bot.on("message:web_app_data")` (or any `web_app_data`) handler,
- any bespoke scanning client, camera API, or hardware-scanner integration.

The **only** new entry point is the `ci_` branch of `parseStartPayload` (§1.1), reached
exclusively through the ordinary `/start ci_<qr_token>` deep link Telegram itself
generates when a plain phone camera (any camera app, not a bot-hosted one) reads
`renderCheckInQrPng`'s existing `https://t.me/<bot>?start=ci_<qrToken>` URL (`domain/qr.ts`,
REQ-024 — reused unchanged, no change needed to that file at all). `git grep -i "web_app\|
webapp\|mini.?app" apps/bot/src` finding nothing is therefore expected to hold after this
requirement ships, exactly as it holds today.

## 9. Open questions (not silently resolved)

1. **Whether `"rejected"` registrations get the override offer.** The requirement's
   acceptance criteria test waitlisted/requested/withdrawn explicitly and do not mention
   `rejected`. This design includes `rejected` in the same `refused-not-admitted` bucket
   with its own specific reason string and the same override offer (§3.2/§7), reasoning
   that it is structurally identical (a non-admitted attendee an organizer might still
   choose to let in) — but no acceptance criterion confirms this is the wanted behavior
   for that specific state. If product wants `rejected` treated differently (e.g. no
   override offered at all, since a `rejected` outcome may represent a deliberate
   organizer decision rather than a capacity/timing artifact), that is a follow-up
   requirement, not resolved here by inventing a distinct code path this design's own ACs
   do not ask for.
2. **The override's real-world workflow when the scanner is not an organizer.** §4.3
   deliberately makes the override tap re-authorize as organizer at the moment of the tap
   — meaning a plain `EventStaff` volunteer who scans and gets refused, then taps
   "Override" themselves, will simply see `overrideNotAuthorized` a second time. The
   practical path (an actual organizer either standing nearby with their own phone, or
   the refusal message being visible in a shared staff group chat where an organizer can
   tap it) is not specified by any acceptance criterion or PRD passage this design was
   given, and is left as a UX/operational question, not a code question — no requirement
   line asks this design to route the refusal to a specific organizer or notify one.
3. **Message-editing mechanic for the override's success screen (§6.2 step 7).** Whether
   the override result replaces the refusal message in place (`editMessageText`) or is
   sent as a new reply is left to BACKEND-DEV — no acceptance criterion distinguishes
   between the two, only that "an organizer override ... writes exactly one audit_log
   row" (AC6), which §4.2 already guarantees independent of how the reply is rendered.
4. **Whether a `checked_in_by` scanner needs to be re-resolved as a `users.id` inside
   `resolveCheckinQrDeepLink` (§6.1 step 6) via a dedicated call, or whether
   `eventStaffAuthorization.ts`'s existing `resolveActingUser` (already exported, REQ-018)
   is called a second time for this purpose** — both are one-line, existing-function
   reuses; this design does not mandate which, only that the value passed to
   `performQrCheckIn`'s `staffUserId` parameter is the scanner's own `users.id`, resolved
   via `ctx.from.id`, never derived from the token.
