## 1. The Telegram interaction pattern, decided explicitly

### 1.1 Why not a native "search box"

Telegram has no form/search-input widget analogous to a web `<input type="search">`.
Every interactive surface this codebase has built so far is either (a) a slash command
with arguments (`/checkin <event_id>`, `/staff_add <event_id> <tg_username>`) or (b) an
inline keyboard button whose `callback_data` is parsed by a regex-matched handler
(`withdraw:confirm:<id>`, `chapter:<id>`). Neither is a native "type into a box" input.

### 1.2 Rejected option: a follow-up free-text message as the search query

The task's own read-first note suggests this as the likely shape: render the list, then
treat the staff member's next plain-text message as a search query. **Decided against**,
stated explicitly rather than silently built, for a structural reason specific to this
codebase, not just style preference:

- This would require tracking **per-user, per-conversation "awaiting a search query for
  event X" state** across two separate Telegram updates (the list render and the later
  text message). No session/conversation-state mechanism exists anywhere in this
  codebase today (confirmed: no `session`, `conversation`, or `ctx.session` outside a
  single unrelated test file — `git grep -n "session\|conversation" apps/bot/src`).
- The two structurally available ways to hold that state are both worse than the
  alternative below:
  - **In-memory** (a `Map` keyed by `tgId` inside the process) — this is **exactly the
    negative case `security-invariants.md` S9 names as unacceptable** for a different
    but structurally identical reason ("idempotency enforced by an in-memory set that a
    restart clears"): a bot process restart mid-shift would silently drop "staff member
    is mid-search," leaving their next ordinary message (which could be anything —
    another command, small talk) misinterpreted as a search query, or the reverse.
  - **DB-backed** (a new `pending_checkin_search` column or table) — a genuine schema
    change requiring a DATA-DESIGNER pass for a feature no acceptance criterion asks for
    by name, plus a new expiry/cleanup policy this requirement's ACs do not specify
    (how long does "awaiting search" stay armed? what clears it if the staff member never
    sends a follow-up?).
- Neither cost is justified by any acceptance criterion — AC6 asks only that "search
  narrows list by name," not that the search be triggered by a bare follow-up message.

### 1.3 Decided pattern: the search query is a command argument

`/checkin <event_id>` gains an **optional second argument**, the search text, consuming
the *remainder* of the command text (not a single token — attendee names contain spaces):

| Input | Behavior |
|---|---|
| `/checkin <event_id>` | Full alphabetical admitted list, paginated (§1.4) |
| `/checkin <event_id> <query text>` | List filtered to admitted attendees whose display name contains `<query text>` (case-insensitive substring match), unpaginated up to a result cap (§1.4) |

This is stateless (works identically after a restart), requires no new column, and
matches this codebase's own established convention for "a command plus a free-text
remainder" (`matchText(ctx)` is already how `/event_new`'s whole body and
`/staff_add`'s username are read). It **is** the search box for this platform: the staff
member re-issues the command with a name fragment appended, same physical action as
retyping a query into a search field and pressing enter. Telegram's own UI makes this
low-friction — the previous `/checkin <event_id>...` message is one tap away in message
history to edit-and-resend.

**Open question, named rather than silently resolved:** this is less discoverable than a
persistent search box would be — a staff member unfamiliar with the convention has to be
told about it. §1.6 states the on-screen hint this design adds to mitigate that; whether
product wants richer, in-chat guided search later is left to a future requirement.

### 1.4 List rendering, pagination, and the search result cap

A single Telegram message with one inline-keyboard button per attendee is the only
native way to show a tappable list. Two constraints shape this:

- **`callback_data` is capped at 64 bytes** by the Telegram Bot API. A UUID is 36
  characters. `checkin:toggle:<registrationId>` alone is `"checkin:toggle:".length` (15)
  `+ 36 = 51` bytes — already most of the budget. **No second UUID (e.g. `eventId`) can
  also ride in the toggle button's `callback_data`** — see §4.2 for how the toggle
  handler recovers `eventId` without it.
- A long admitted list cannot all be rendered as buttons on one screen usably.

Decided shape:

| View | Pagination mechanism | Result cap |
|---|---|---|
| Full list (no query) | `PAGE_SIZE = 10` rows per page; a page row of ◀/▶ buttons with `callback_data = "checkin:page:<eventId>:<pageNumber>"` (`"checkin:page:".length` (13) `+ 36 + 1 + digits` — comfortably under 64 bytes since `eventId` is the only UUID this callback carries) | none — every admitted attendee is reachable via paging |
| Search results (`<query text>` present) | none — rendered as a single page | `SEARCH_RESULT_LIMIT = 20` matches; if more than 20 admitted attendees match, show the first 20 (alphabetically) plus a truncation note (§1.6) naming the count not shown, asking the staff member to refine the query |

`PAGE_SIZE`/`SEARCH_RESULT_LIMIT` are design constants (`apps/bot/src/handlers/checkin.ts`
or a shared constant, BACKEND-DEV's choice) — no acceptance criterion pins an exact
number; 10/20 are chosen only so AC6's "≥10 attendees, exactly one match" scenario is
comfortably inside both.

The query text is **never encoded into any `callback_data`** — the search view has no
pagination buttons, sidestepping the 64-byte budget question entirely for that view.

### 1.5 Reconstructing the current view after a toggle, without threading page/query through `callback_data`

The toggle button's `callback_data` carries **only** `registrationId` (§1.4). After a
successful toggle, the handler does **not** re-fetch and re-render the whole list from
scratch (which would require knowing the original page number or search query it can no
longer see). Instead (§4.2): it edits the **existing** message's inline keyboard in
place — replacing the one button whose `callback_data` matches the tapped
`registrationId` with an updated label (checked-in glyph flips) — and edits the message's
header text in place to reflect the freshly recomputed live counter (§2.2). Grammy's
`ctx.callbackQuery.message.reply_markup` exposes the message's current keyboard for this
in-place mutation; no other button on the keyboard is touched, so whatever page or search
result the staff member was looking at stays exactly as it was, just with one row's
checkmark and the header counter updated.

### 1.6 New copy needed for the interaction pattern

- A short hint line appended to the list message's footer telling staff how to search:
  restates the `/checkin <event_id> <name>` pattern (§5 `checkin.searchHint`).
- A truncation note for `SEARCH_RESULT_LIMIT` overflow (§5 `checkin.searchTruncatedNote`,
  interpolated with the not-shown count).
- An empty-state line for zero admitted attendees and a separate one for zero search
  matches (§5 `checkin.listEmpty` / `checkin.searchNoMatches`).

## 2. Reads: the list and the live counter

### 2.1 The admitted-attendee list

```
// domain/registration.ts — addition
export interface CheckinListItem {
  registrationId: string;
  userId: string;
  displayName: string;
  company: string | null;
  checkedInAt: Date | null;
}

export async function listAdmittedRegistrantsForCheckin(
  db: DbClient["db"],
  eventId: string,
): Promise<CheckinListItem[]>;
```

Query shape: one `SELECT` joining `registrations` to `profiles` (via `profiles.userId =
registrations.userId`, a `LEFT JOIN` since a `profiles` row is not guaranteed to exist
for every user — mirrors `getMyRegistrations`'s existing join style, REQ-024 §1),
filtered to `registrations.eventId = $eventId AND registrations.admission = 'admitted'`.
Selects `registrations.id`, `registrations.userId`, `registrations.checkedInAt`,
`profiles.firstName`, `profiles.lastName`, `profiles.company`, and — for the display-name
fallback rule below — `users.tgUsername` (joined via `users.id = registrations.userId`).
**Never selects `profiles.phone` or `profiles.email`** — this is what makes AC3
structurally true: those two columns are simply absent from this query's `select`
clause, not filtered out after the fact.

**`displayName` derivation rule** (computed in application code from the three raw
fields above, stated as a table rather than as executable logic per this role's
prohibition on writing the comparison itself):

| `firstName` | `lastName` | Result |
|---|---|---|
| present | present | `"<firstName> <lastName>"` |
| present | absent | `firstName` alone |
| absent | present | `lastName` alone |
| absent | absent, `tgUsername` present | `"@<tgUsername>"` |
| absent, absent, `tgUsername` absent | — | the fixed placeholder string `checkin.noNameFallback` (§5) |

`tgUsername` is used as a fallback identifier (not phone/email) — permitted by S3, which
names phone/email specifically, and matches "enough to greet them properly" better than
an anonymous placeholder when it's the only identifying fact on file.

**Ordering rule** (again a table, not code): rows are ordered by `lastName` ascending
(nulls last), then by `firstName` ascending (nulls last), then by `registrationId`
ascending as the final, always-defined tie-break — giving a total, stable order
regardless of how many rows share a blank name. This ordering is computed by the SQL
`ORDER BY` clause itself (a declarative clause, not an executable comparison function),
consistent with how `getWaitlistPosition`'s existing `ORDER BY asc(...), asc(...)`
tie-break is expressed elsewhere in this file.

This single read serves **all three** of: the full list (§1.4), the search filter
(applied afterward in application code — see below — not as a second query), and the
alphabetical ordering AC5/AC6 need. Filtering for `<query text>` is a **plain
case-insensitive substring containment check** of `displayName` against the query,
performed as a filter over this function's already-fetched array — not a second SQL
query with `ILIKE` — since the admitted list for one event is bounded by that event's own
`capacity` (never the full user table), the same "fetch once, filter/derive in memory"
shape `getMyRegistrations`/`selectNonWithdrawnRegistrantsForEvent` already use for
comparably small, per-event/per-user result sets.

### 2.2 The live counter

```
// domain/registration.ts — addition
export async function countCheckedIn(
  db: DbClient["db"],
  eventId: string,
): Promise<number>;
```

`SELECT count(*) FROM registrations WHERE event_id = $eventId AND checked_in_at IS NOT
NULL` — computed fresh on **every** render (the initial list, every page turn, every
search, and every post-toggle header re-render, §1.5). No column, cache, or in-memory
counter anywhere stores this value between reads (AC4). Filtering by `admission =
'admitted'` in addition to `checked_in_at IS NOT NULL` is deliberately **not** added:
`chk_registrations_checked_in_only_if_admitted` (§0) already makes the two conditions
equivalent in the live table, so the extra predicate would be redundant, not
protective — a `checked_in_at IS NOT NULL` row cannot have any other `admission` value.

The total shown alongside it (`"<N> / <M> checked in"`) is `M = ` the length of
`listAdmittedRegistrantsForCheckin`'s result for the same event — no separate `count(*)`
query needed for the denominator, since that array is already being fetched for the list
itself on every one of these same render paths.

## 3. The toggle: the write-time recheck (AC1's crux)

### 3.1 The pure decision

```
// domain/registration.ts — addition
export interface CheckinToggleDecisionInput {
  registrationExists: boolean;
  admission: AdmissionState | null;
  checkedInAt: Date | null;
}

export type CheckinToggleOutcome =
  | { kind: "not-found" }
  | { kind: "refused-not-admitted"; admission: AdmissionState }
  | { kind: "check-in" }
  | { kind: "undo" };

export function decideCheckinToggleOutcome(
  input: CheckinToggleDecisionInput,
): CheckinToggleOutcome;
```

Rule, stated exactly, first-match-wins (same convention `decideWithdrawOutcome`/
`decideReconfirmOutcome` already establish in this same file):

| Step | Condition | Result |
|---|---|---|
| 1 | `!registrationExists` | `{ kind: "not-found" }` |
| 2 | `admission !== "admitted"` | `{ kind: "refused-not-admitted", admission }` |
| 3 | `checkedInAt === null` | `{ kind: "check-in" }` |
| 4 | `checkedInAt !== null` | `{ kind: "undo" }` |

This is a pure function — no I/O, no clock read — exactly the same
decide-then-write split `decideWithdrawOutcome`/`withdrawRegistration` already use.

### 3.2 The transactional write — why this is genuinely a write-time check, not a stale render-time one

```
// domain/registration.ts — addition
export async function toggleCheckIn(
  db: DbClient["db"],
  registrationId: string,
  staffUserId: string,
  at: Date,
): Promise<CheckinToggleOutcome & { eventId?: string }>;
```

Sequence, stated exactly (mirrors `withdrawRegistration`'s/`reconfirmRegistration`'s
existing shape in this file — row lock, fresh read, pure decide, conditional write, one
audit row):

1. Open `db.transaction`. `SELECT id, event_id, admission, checked_in_at FROM
   registrations WHERE id = $registrationId FOR UPDATE` — a **fresh, locked** read
   performed *inside this call*, never reusing any value the callback's own
   `callback_data` or the caller passed in. This is the load-bearing property: the
   callback that invokes this function carries **only** `registrationId` (§1.4) — it is
   structurally incapable of also carrying a stale `admission` snapshot, because no
   `admission` value is ever encoded anywhere in the button that triggers this call. The
   only way this function can learn `admission` is this fresh `SELECT`.
2. `decideCheckinToggleOutcome({ registrationExists: row !== undefined, admission:
   row?.admission ?? null, checkedInAt: row?.checkedInAt ?? null })`.
3. `"not-found"` or `"refused-not-admitted"` → **no write, no audit row**, return the
   outcome as-is. This is AC1's refusal path: an admission changed to `withdrawn`
   directly in the DB between the list being rendered and the toggle being pressed is
   picked up here, inside the same transaction as the row lock, before any write is
   attempted — not detected after the fact by inspecting a failed write.
4. `"check-in"` → `UPDATE registrations SET checked_in_at = $at, checked_in_by =
   $staffUserId, check_in_method = 'manual' WHERE id = $registrationId`, then
   `writeAuditLog(tx, { actorUserId: staffUserId, action: "registration.checkin", entity:
   "registration", entityId: registrationId, payload: { eventId: row.eventId }, at })`,
   same transaction (S8).
5. `"undo"` → `UPDATE registrations SET checked_in_at = NULL WHERE id =
   $registrationId` — **only** `checked_in_at` is cleared, exactly matching the
   requirement's own wording ("tapping again UNDOES it (clears `checked_in_at`)");
   `checked_in_by`/`check_in_method` are left as whatever the most recent check-in wrote
   (they carry no meaning while `checked_in_at` is null and are unconditionally
   overwritten by the next check-in, step 4) — then `writeAuditLog(tx, { actorUserId:
   staffUserId, action: "registration.checkin_undo", entity: "registration", entityId:
   registrationId, payload: { eventId: row.eventId }, at })`, same transaction (S8).
6. Return the outcome, with `eventId: row.eventId` attached on every branch where `row`
   exists — the handler (§4.2) needs this to re-authorize and to recompute the counter,
   without a second round-trip query.

**Why this is provably a write-time check and not a re-labeled render-time one:** the
row lock (`FOR UPDATE`) and the fresh `SELECT` happen *after* the callback has already
been received — i.e., after whatever time elapsed between the list render and the tap —
and *before* the `UPDATE`, inside one transaction. There is no code path in this design
that decides `"check-in"`/`"undo"` from any value read earlier than this `SELECT`. The
DB `CHECK` constraint (§0) is a second, independent backstop: even a hypothetical future
bug that skipped step 2's decision entirely would still have the `UPDATE` rejected by
Postgres if `admission` were not `'admitted'` at commit time — the constraint and this
transactional recheck defend the same property from two different layers.

### 3.3 Re-authorization at toggle time (S2, defense in depth)

`requireEventStaffForEvent` (REQ-018, reused unchanged) is called again by the toggle
**callback** handler, not only by the original `/checkin` command (§4.2 step 3) — a
staff member removed from `event_staff` (`/staff_remove`, REQ-018) between the list
render and a later tap must be refused on the tap itself, not only on their next `/checkin`
invocation. This mirrors S2's "authorization is checked on the action" framing literally:
the toggle *is* the action; the list render is not.

## 4. Handlers (`apps/bot/src/handlers/checkin.ts`)

### 4.1 `/checkin <event_id> [query text]` — rewritten from REQ-018's stub

```
export function makeCheckInHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence (steps 1–6 are **unchanged** from REQ-018's existing stub — same authorization
gate, same not-found/not-authorized replies, same event-endsAt defensive check; only
step 7 changes):

1. `tgId = ctx.from?.id`; `undefined` → return.
2. `lang = resolveLangForTg(db, tgId)`.
3. Parse `matchText(ctx)`: split on the first run of whitespace into `eventId` (first
   token, trimmed) and `query` (the remainder, trimmed; empty string → `null`) — a new
   parse rule (first-token-plus-remainder, not first-two-tokens), needed because a
   search query may itself contain spaces (a full name). Blank `eventId` → reply
   `checkin.usageNoId`, return (unchanged trigger, REQ-018).
4. `event = getEventById(db, eventId)`; `null` → reply `checkin.notFound`, return
   (unchanged, REQ-018).
5. `event.endsAt === null` → reply `checkin.notFound` (unchanged defensive path, REQ-018).
6. `authResult = requireEventStaffForEvent(db, BigInt(tgId), event.id, event.endsAt, new
   Date())`; `!ok` → reply `checkin.notAuthorized` (unchanged, REQ-018), return.
7. **New:** `ok` → render the check-in list (§4.4) at page 0, filtered by `query` if
   present, and `ctx.reply(text, { reply_markup: keyboard })`.

### 4.2 `checkin:toggle:<registrationId>` callback

```
export const CHECKIN_TOGGLE_PATTERN = /^checkin:toggle:(.+)$/;

export function makeCheckinToggleCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence:

1. Extract `registrationId` from `CHECKIN_TOGGLE_PATTERN.exec(ctx.callbackQuery?.data ??
   "")`; no match → `ctx.answerCallbackQuery()`, return (defensive, unreachable).
2. `tgId = ctx.from?.id`; `undefined` → `ctx.answerCallbackQuery()`, return.
3. **Re-authorization (§3.3):** a lightweight, unlocked read of the registration's
   `eventId` (reuses `getRegistrationForEventAndUser`'s sibling shape, or a new
   one-column `SELECT event_id FROM registrations WHERE id = $registrationId` — either
   is acceptable; the design does not mandate which existing/new one-column read
   function is reused, only that it is read-only and separate from §3.2's own locked
   read) → `getEventById(db, eventId)` for `endsAt` → `requireEventStaffForEvent(db,
   BigInt(tgId), eventId, event.endsAt, new Date())`. `!ok` (or the registration/event no
   longer resolvable) → `ctx.answerCallbackQuery({ text: checkin.notAuthorized, show_alert:
   true })`, no list mutation, return.
4. `outcome = toggleCheckIn(db, registrationId, authResult.user.id, new Date())`.
5. `outcome.kind === "not-found"` or `"refused-not-admitted"` → **AC1's stated refusal**:
   `ctx.answerCallbackQuery({ text: checkin.refusedNotAdmitted, show_alert: true })` — a
   Telegram alert popup shown only to the tapping staff member, naming the refusal
   plainly. **No message edit** — the stale row's button is deliberately left as it was
   (still showing the old, no-longer-accurate checked-in glyph for that one attendee)
   until the next full render, rather than this handler attempting to recompute a label
   for a row whose current admission it does not otherwise need to know for any other
   purpose. Named explicitly as a deliberate simplification, not silently decided: see
   §6 open question 1.
6. `outcome.kind === "check-in"` or `"undo"` → recompute this one attendee's row label
   (§4.4's per-row rule, re-run for this `registrationId` alone using the already-known
   new `checkedInAt` value — `at` on check-in, `null` on undo — no extra `SELECT` needed
   for this row) and the header text's live counter (`countCheckedIn` — one fresh query,
   §2.2), then:
   - `ctx.answerCallbackQuery()` (no alert — a silent, successful toggle).
   - Read the current keyboard from `ctx.callbackQuery.message.reply_markup` (§1.5),
     replace the one button whose `callback_data === "checkin:toggle:" + registrationId`
     with the recomputed label, leaving every other button (including any page/nothing
     controls) untouched.
   - `ctx.editMessageText(newHeaderText, { reply_markup: updatedKeyboard })` — a single
     call updates both the header line (new counter) and the keyboard (new checkmark) in
     place.

### 4.3 `checkin:page:<eventId>:<pageNumber>` callback

### 4.4 Shared rendering: `renderCheckinListMessage`

Not a handler itself — a shared composition step both §4.1 and §4.3 call.

```
export interface CheckinListView {
  text: string;
  keyboard: InlineKeyboard; // grammy
}

export function renderCheckinListMessage(
  eventTitle: string,
  items: CheckinListItem[], // already filtered/paginated by the caller
  checkedInCount: number,
  totalAdmitted: number,
  page: { current: number; total: number } | null, // null for a search view (§1.4)

```

Composition, stated exactly:

- **Header line(s):** `checkin.listHeader` (interpolated with `eventTitle`,

  <totalAdmitted> checked in"`, exact wording owned by CONTENT-BA per decisions/0002).
  If `items.length === 0`: replace the list body with `checkin.listEmpty` (no query) or
  `checkin.searchNoMatches` (a query was given) — no keyboard rows for attendees in this
  case, only a page/back control if applicable.
- **One keyboard row per item**, button text = a fixed prefix glyph
  (`checkin.checkedInGlyph` if `checkedInAt !== null`, `checkin.notCheckedInGlyph`

  buttons render plain text only, so this is the platform's substitute for a design-system
  icon here, see §7) followed by `"<displayName> — <company>"` (company omitted, along
  with the dash, when `company` is `null`), `callback_data =
  "checkin:toggle:" + registrationId`.
- **Pagination row** (only when `page !== null`): ◀ button (`callback_data =
  "checkin:page:<eventId>:<page.current - 1>"`, omitted at page 0) and ▶ button
  (omitted at the last page), with a non-interactive middle label
  (`checkin.pageIndicator`, interpolated `"<page.current + 1> / <page.total>"`) — grammy
  represents a non-interactive label as a button whose `callback_data` is a fixed
  no-op string the bot never registers a listener for (same "label-only button" pattern
  this codebase has not needed before now; no existing precedent to point to — flagged as
  new, not copied).
- **Truncation note** (only when `truncatedCount !== null && truncatedCount > 0`):
  `checkin.searchTruncatedNote` interpolated with `truncatedCount`, appended after the
  keyboard rows as a final non-interactive line in the message text (not a button).
- **Search hint footer** (every render, both views): `checkin.searchHint` (§1.6),
  restating the `/checkin <event_id> <name>` pattern.

## 6. Open questions (not silently resolved)

1. **A stale row's button label is not corrected until the next full render (§4.2 step
   5).** When a toggle is refused because admission changed underneath it, this design
   deliberately leaves that one attendee's keyboard button showing its old (possibly now
   wrong) checked-in glyph rather than recomputing and pushing a corrected label for a
   row the handler otherwise has no reason to re-fetch. No acceptance criterion requires
   the stale button's *label* to self-correct — only that the *write* be refused (AC1) —
   but a staff member could be confused by a button that still looks tappable-and-green
   for someone who is actually withdrawn. Left as a UX gap for a future requirement to
   resolve (e.g. periodic full re-render), not resolved here since resolving it would
   mean designing an auto-refresh mechanism no AC asks for.
2. **The "no-op label button" for the page indicator (§4.4) has no precedent in this
   codebase.** Stated as new rather than presented as an established pattern — if
   BACKEND-DEV or REVIEWER finds a cleaner grammy idiom for a non-interactive middle
   label, that is an implementation-level choice this design does not need to gate on.
3. **Discoverability of the search-by-re-issuing-the-command pattern (§1.3).** The
   footer hint (§1.6) is this design's only mitigation; whether a friendlier mechanism
   (e.g. a dedicated `/checkin_search` alias, or eventually genuine session-backed
   free-text search once this codebase has a session mechanism for other reasons) is
   worth building is left to product/a future requirement, not decided here.
4. **Re-authorization on every page turn (§4.3) adds one authorization round-trip per
   page tap that REQ-018's original single-shot `/checkin` command did not need.** This
   is a deliberate S2 choice ("checked on the action"), not an oversight — flagged in
   case a future performance concern wants it relaxed (e.g. only re-checking at first
   page load, not every subsequent page), which no acceptance criterion currently asks
   for either way.

## 7. No new design-system token or component

The bot surface has no visual/CSS component (unchanged reasoning already stated in
REQ-016.md §9/REQ-017.md §7/REQ-018.md §8) — Telegram inline keyboard buttons render
plain text only, so §4.4's "checked-in glyph" is a plain Unicode character chosen at
copy/localization time (§5), not a Lucide icon or any other design-system asset. No
token, spacing value, or component class from `docs/Design system for AI agents/` is
referenced anywhere in this design, because none could apply to a Telegram chat surface.

## 8. Acceptance criteria → design element map

| AC | Design element |
|---|---|
| AC1 — admission changes to `withdrawn` directly in DB between render and a stale toggle press → no check-in written, stated refusal | §3.2 steps 1–3 (fresh, locked `SELECT` inside the toggle's own transaction — the callback carries only `registrationId`, never a snapshot of `admission`, so there is nothing stale to trust); §0's DB `CHECK` constraint as a second, independent layer; §4.2 step 5 (`checkin.refusedNotAdmitted` alert, no write) |
| AC2 — tap admitted attendee sets `checked_in_at`/`checked_in_by`/`check_in_method='manual'`; tap again clears `checked_in_at`; each writes exactly one `audit_log` row | §3.2 step 4 (`"check-in"` branch's `UPDATE` + one `writeAuditLog` call, one transaction) and step 5 (`"undo"` branch's `UPDATE` clearing only `checked_in_at` + one `writeAuditLog` call, one transaction) — S8's "exactly one row, same transaction as the write" shape, identical to `withdrawRegistration`/`reconfirmRegistration`'s already-established pattern in this file |
| AC3 — rendered list contains no phone/email for any attendee | §2.1's `listAdmittedRegistrantsForCheckin` `SELECT` clause structurally never names `profiles.phone`/`profiles.email` — nothing to filter out because it is never fetched |
| AC4 — live counter = `count(checked_in_at IS NOT NULL)` at every read, increments by exactly one when set directly in DB, no write to `events` | §2.2's `countCheckedIn`: one `SELECT count(*)` against `registrations`, re-run on every render path (§4.1, §4.2 step 6, §4.3) with no cache/column/in-memory counter anywhere; nothing in this design ever writes to the `events` table |
| AC5 — list shows only `admission = 'admitted'`; waitlisted/withdrawn don't appear | §2.1's `WHERE registrations.admission = 'admitted'` clause — the only filter in the query, applied at the SQL layer, not as a post-fetch client-side filter |
| AC6 — search narrows list by name (≥10 attendees, query matching exactly one) | §1.3's command-argument search pattern; §2.1's `displayName` substring filter (case-insensitive); §1.4's `SEARCH_RESULT_LIMIT = 20` comfortably exceeds a ≥10-attendee test fixture, so the single matching name is the only row rendered |
