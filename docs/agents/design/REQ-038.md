# REQ-038 — Invite code redemption via `i_` deep link or typed code, with the full validation table and past-attendee eligibility

**Requirement:** GitHub issue #70. Sixth requirement of Release 2 (`depends_on: REQ-037,
REQ-035`, both merged). Implements USER-STORIES B7 ("Use my invitation") and PRD FR-4's
two `requires_invite=true` rows. Replaces REQ-020's deliberate placeholder refusal
(`{ kind: "requires-invite" }`) with the real behaviour — exactly the same class of change
REQ-034 already made for `requires-approval`.

**Surface:** `apps/bot/**` (bot requirement).

**No schema change — confirmed independently, not taken on the issue's word.** `apps/bot/src/db/schema.ts`
already has everything this requirement writes: `invite_codes.used_count` (line 352,
REQ-033, explicitly documented there as "a real stored counter... its atomic increment is
REQ-038's problem, not this file's"), `registrations.invite_code_id` (line 281, REQ-033's
FK, still nullable). Nothing in this design adds a column to `events`, `users`, or any
other table — see §2.4's explicit resolution of the routed-here open question, which
depends on this fact. **`DATA-DESIGNER` is not needed for this run.**

**Files this design expects to change:**
- `apps/bot/src/domain/registration.ts` (existing) — `RegistrationDecisionInput`/
  `decideRegistrationOutcome`'s `requiresInvite` branch (§1), a new
  `hasPastCheckIn` read (§2), a new transactional entry point built on
  `registerForEvent`'s existing shape (§3)
- `apps/bot/src/domain/inviteCode.ts` (existing) — a new by-code-string read
  (`getInviteCodeByCode`), a new pure validation-table function
  `validateInviteCodeForRedemption` (§3.2)
- `apps/bot/src/domain/event.ts` (existing) — `parseStartPayload`'s `StartPayload` union
  gains an `"invite"` member (§4.1)
- `apps/bot/src/handlers/start.ts` (existing) — `i_` dispatch alongside `ci_`/`e_`, and the
  `consent:agree` callback's payload-resume branch (§4.2/§4.3)
- `apps/bot/src/handlers/registration.ts` (existing) — new command handler for `/redeem`,
  new reply branches for the five invite-code refusals, extended `requires-invite` reply
  (§5)
- `apps/bot/src/i18n/types.ts`, `en.ts`, `ru.ts` — new `Catalog.registration` keys (§6)
- `apps/bot/src/index.ts` (existing) — one new `bot.command("redeem", ...)` registration

## 0. Reuse decisions, stated up front

1. **One redemption function, two entry points**, per decisions/0004. Both the `i_<code>`
   deep link and the typed `/redeem` command resolve to the same transactional function
   (§3.1) — neither entry point contains its own copy of the validation table or the
   atomic-increment logic.
2. **The plain (no-code) registration path is barely touched.** `decideRegistrationOutcome`
   gains exactly one new boolean input (`inviteSatisfied`) and one `&&` term on its
   existing `requiresInvite` branch (§1) — every other branch, and every other outcome
   kind, is unchanged. `registerForEvent`'s existing shape (event lock → existingAdmission
   → admittedCount → decide → write) is the template the new code-redemption function
   reuses, not a parallel reinvention.
3. **The two-phase lock discipline already established by `performQrCheckIn`/
   `getRegistrationByQrTokenForCheckin`** (REQ-029 §2.1/§3.3 — an unlocked pre-check to
   fail fast on "unknown", then an authoritative locked recheck inside the write
   transaction) is reused verbatim for invite-code lookup (§3.1).
4. **The onward path is REQ-035's existing offramp, unchanged.** Every stated refusal in
   this design appends `catalog.event.deepLinkSeeUpcoming` exactly as
   `composeRegistrationReply`'s existing `event-cancelled`/`event-finished`/
   `registration-closed` cases already do (`handlers/registration.ts` lines 161-166). No
   Wishlist table, migration, or row anywhere in this design.
5. **The consent-deferred-resume mechanism already established for `e_` deep links**
   (`handlers/start.ts`'s `resolveEventDeepLink`/`buildConsentAgreeCallbackData`/
   `makeConsentCallbackHandler`, REQ-016's security rework) is reused for `i_` unchanged in
   shape — a not-yet-consented redeemer sees the ordinary consent prompt first, with the
   invite payload carried in the `consent:agree` callback's `callback_data`, and the
   redemption itself runs only once `consent_pd_at` is non-null. This is what makes S1 hold
   for this requirement: **no code lookup, no `invite_codes`/`registrations` write, and no
   profile write happens before consent** — nothing about the redemption even runs until
   consent is recorded.

## 1. `decideRegistrationOutcome` — the one-line gate change, stated as a table

### 1.1 `RegistrationDecisionInput` — one new field

```
export interface RegistrationDecisionInput {
  existingAdmission: AdmissionState | null;
  eventStatus: "draft" | "published" | "cancelled";
  requiresInvite: boolean;
  requiresApproval: boolean;
  registrationClosesAt: Date | null;
  endsAt: Date;
  seatsLeft: number;
  inviteSatisfied: boolean; // NEW — see §1.2
}
```

`inviteSatisfied` is `true` when the invite gate is already cleared by *some* means —
either a code that passed §3.2's validation table, or past-attendee eligibility (§2). It
is computed by the caller, outside this pure function, exactly the same discipline
`seatsLeft`/`existingAdmission`/every other field on this interface already follows
(decisions/0006 — this function performs no I/O and reads no clock itself).

**Economy note (not a correctness requirement, stated so BACKEND-DEV doesn't over-query):**
when `requiresInvite` is `false`, this field is never inspected by the table below — a
caller registering for a non-invite event may pass `false` unconditionally rather than
running the past-attendee-eligibility query needlessly.

### 1.2 The first-match-wins table — updated, stated in full (not as a diff)

| Order | Condition | Result |
|---|---|---|
| 1 | `existingAdmission !== null` | `already-registered` (admission: existingAdmission) |
| 2 | `eventStatus === "cancelled"` | `event-cancelled` |
| 3 | `isFinished(endsAt, evaluationTime)` | `event-finished` |
| 4 | `!isRegistrationOpen(registrationClosesAt, evaluationTime)` | `registration-closed` |
| 5 | `requiresInvite === true` AND `inviteSatisfied === false` | `requires-invite` |
| 6 | `requiresApproval === true` | `requested` |
| 7 | `seatsLeft > 0` | `admitted` |
| 8 | (none of the above) | `waitlisted` |

Only row 5 changed (gained the `AND inviteSatisfied === false` term); rows 1-4 and 6-8 are
byte-for-byte what `apps/bot/src/domain/registration.ts` lines 62-83 already do today.
`RegistrationOutcome`'s union (line 44-53) is **unchanged** — no new member. This directly
answers design question 5: **yes, this reuses `decideRegistrationOutcome`'s existing
`admitted`/`waitlisted`/`requested` branches exactly; nothing new is invented for the
"code buys past the gate, not past capacity" behaviour (PRD 12.2, S7).** A valid code that
clears row 5 falls straight into rows 6-8, which are completely unaware a code was ever
involved.

## 2. Past-attendee eligibility — a derived, never-stored query

### 2.1 `hasPastCheckIn`

```
export function hasPastCheckIn(db: DbClient["db"], userId: string): Promise<boolean>;
```

**Rule, stated in prose (not as executable code):** returns `true` if and only if at least
one row in `registrations` exists where `user_id = userId` AND `checked_in_at IS NOT
NULL`. No join to `events`, no additional `endsAt < evaluationTime` filter, no
`evaluationTime` parameter at all.

**Why no extra "past" filter is needed — stated, not assumed:** `checked_in_at` is only
ever set by `toggleCheckIn`/`performQrCheckIn` (REQ-028/REQ-029), and both of those run
only against an event that is already underway (a check-in screen exists only for a
published event that hasn't been withdrawn from). A non-null `checked_in_at` is therefore
structurally evidence of a past attendance already — re-deriving "past" from `endsAt`
would be redundant, not more correct. This is the exact query PRD FR-4/story B7's third
Confirmation calls for: **a query over `registrations`, never a stored `is_returning`
flag or cached boolean** — no new column anywhere, satisfying the AC's own `git grep`
check.

### 2.2 Where it's called

Only from the plain (no-code) registration entry point (`handlers/registration.ts`'s
`register:<eventId>` callback, unchanged trigger), and only when the target event's
`requiresInvite` is `true` (§1.1's economy note). The result becomes
`inviteSatisfied` on `RegistrationDecisionInput` directly — no code involved, no
`invite_codes` row touched, no `used_count` change. A past-attendee's admission proceeds
straight to rows 6-8 of §1.2's table exactly like a valid-code redemption would.

## 3. The redemption path — one transactional function, one pure validation table

### 3.1 The transactional entry point

```
export type InviteRedemptionOutcome =
  | RegisterForEventResult
  | { kind: "invite-code-not-found" }
  | { kind: "invite-code-expired" }
  | { kind: "invite-code-spent" }
  | { kind: "invite-code-wrong-event" }
  | { kind: "invite-code-not-yours" };

export function redeemInviteCode(
  db: DbClient["db"],
  redeemerUserId: string,
  rawCode: string,
  explicitEventId: string | null,
  evaluationTime: Date,
): Promise<InviteRedemptionOutcome>;
```

`explicitEventId` is `null` for the `i_<code>` deep-link entry point (§4.1 — the target
event is the code's own `event_id`, there is no independent expectation to check against)
and non-null for the typed `/redeem <event_id> <code>` entry point (§5.1). This single
parameter is what makes "two entry points, one decision function" concrete: both call
sites invoke this exact function, differing only in what they pass for
`explicitEventId`.

**Step sequence, stated in full (mirrors `performQrCheckIn`'s two-phase discipline,
REQ-029 §3.3, and `registerForEvent`'s existing lock-then-decide shape, REQ-020 §3.2):**

1. **Normalize** `rawCode`: trim, then uppercase (invite codes are generated exclusively
   from `INVITE_CODE_ALPHABET`'s uppercase-only characters, REQ-033 §4 — this is a stated
   design decision, not a silent one: without it, a code copy-pasted in lowercase by some
   Telegram client would fail lookup even though it is the correct code).
2. **Unlocked pre-check** (fast fail, no transaction open yet): look up `invite_codes` by
   the normalized code string. Not found → return `{ kind: "invite-code-not-found" }`
   immediately. This is the "unknown code" refusal, and it is deliberately cheap — it
   never touches `events` or opens a transaction, mirroring
   `getRegistrationByQrTokenForCheckin`'s identical "resolve to unknown fast" role.
3. **Resolve the target event id**: `targetEventId = explicitEventId ?? codeRow.eventId`.
4. **Open the transaction.** Lock the `events` row for `targetEventId` `FOR UPDATE` —
   identical to `registerForEvent`'s existing step 2. Not found → return
   `{ kind: "not-found" }` (the exact same `RegisterForEventResult` member the `e_`
   deep-link's unknown/draft/cancelled/finished handling already produces, §4's reuse).
5. **Lock the `invite_codes` row fresh**, `FOR UPDATE`, by `codeRow.id` — never reuse
   step 2's unlocked read for the actual decision, same "never trust the pre-tx read"
   discipline `performQrCheckIn`'s token-currency recheck already establishes. This is
   the row whose `used_count` is about to be compared and, if the redemption succeeds,
   incremented — locking it here is what makes AC4's concurrency property hold: two
   concurrent redemptions of the same code's last use serialize on this lock, and the
   second one's fresh read sees the first one's already-incremented `used_count`.
6. **Run `validateInviteCodeForRedemption`** (§3.2, pure) against the locked row's current
   fields, `targetEventId`, `redeemerUserId`, and `evaluationTime`. Any non-`ok` result →
   return the matching `invite-code-*` refusal kind. **No write happens, `used_count` is
   untouched**, and the transaction commits or rolls back with no observable effect either
   way (equivalent to a plain read).
7. **`ok`** → proceed with exactly the reads `registerForEvent`'s existing steps 3-4
   already perform on the (already-locked) event: `existingAdmission` for this
   `(eventId, userId)` pair, then `admittedCount` → `seatsLeft`.
8. **Decide** via `decideRegistrationOutcome` (§1.2, unchanged function) with
   `inviteSatisfied: true` (the code just passed §3.2, so the gate is cleared by
   construction).
9. **Non-writing outcomes** (`already-registered`, `event-cancelled`, `event-finished`,
   `registration-closed`) → return unchanged. **The code is NOT consumed** — `used_count`
   is untouched. This is the same "writing outcome" boundary `registerForEvent`'s existing
   step 7 already draws (line 191); redemption inherits it exactly rather than defining a
   second one. Answers a case the issue text doesn't spell out: a valid, unused code
   presented against a cancelled/finished/closed event does not burn a use, since the
   person gained nothing from it.
10. **Writing outcomes** (`admitted`, `waitlisted`, `requested`) → in the same
    transaction:
    - The `registrations` INSERT/UPDATE, identical in every other respect to
      `registerForEvent`'s existing step 8, additionally sets
      `invite_code_id = codeRow.id`.
    - `invite_codes.used_count` is set to the **locked row's own `used_count` value read
      in step 5, plus exactly 1** — the increment and the registration write are the same
      transaction, satisfying AC4/AC1's "increment by exactly one, atomically with the
      registration write."
    - Exactly one `writeAuditLog` call, same action-name mapping
      `registerForEvent` already uses (`registration.admit` /
      `registration.waitlist` / `registration.request`), with `inviteCodeId` added to the
      existing `payload` object (`{ eventId, inviteCodeId }`). **No second, separate
      `invite_code.redeem` audit row is written** — this is a deliberate resolution, not
      an oversight: AC10 requires *exactly* one row per successful redemption, and a
      second row would violate it. Traceability is carried by the single row's payload
      field instead.

### 3.2 `validateInviteCodeForRedemption` — the pure validation table

```
export interface InviteCodeValidationInput {
  expiresAt: Date | null;
  usedCount: number;
  maxUses: number;
  codeEventId: string;
  issuedToUserId: string | null;
  targetEventId: string;
  redeemerUserId: string;
  evaluationTime: Date;
}

export type InviteCodeValidationResult =
  | { ok: true }
  | { ok: false; reason: "expired" | "spent" | "wrong-event" | "not-yours" };

export function validateInviteCodeForRedemption(
  input: InviteCodeValidationInput,
): InviteCodeValidationResult;
```

Pure, no I/O, no clock read (`evaluationTime` is an explicit parameter, decisions/0006) —
same convention as every other `decide*`/`validate*` function in `domain/registration.ts`.
"Not found" is **not** a case of this function — the caller (§3.1 step 2) already
short-circuits before this function is ever reached, so it always receives a real,
locked row's fields.

**The table, in the exact order the requirement states it (existence → expiry →
uses-remain → event-match → identity-match), stated in full:**

| Order | Condition | Result |
|---|---|---|
| 1 | `expiresAt !== null` AND `evaluationTime >= expiresAt` | `{ ok: false, reason: "expired" }` |
| 2 | `usedCount >= maxUses` | `{ ok: false, reason: "spent" }` |
| 3 | `codeEventId !== targetEventId` | `{ ok: false, reason: "wrong-event" }` |
| 4 | `issuedToUserId !== null` AND `issuedToUserId !== redeemerUserId` | `{ ok: false, reason: "not-yours" }` |
| 5 | (none of the above) | `{ ok: true }` |

Row 1's `expiresAt !== null` guard: `invite_codes.expires_at` is nullable at the schema
level (`schema.ts` line 353), but every issuing function in `inviteCode.ts`
(`issuePersonalInviteCode`/`issueBulkInviteCode`/`issueCompanionInviteCode`) takes
`expiresAt: Date` as a required, non-optional parameter — in practice no row this
requirement will ever read has a null `expires_at`. The null-safe guard is defensive only,
mirroring `isRegistrationOpen`'s identical "null means no deadline" convention
(`event.ts` line 743-751) rather than assuming the column's nullability is dead.

**Design question 1's ordering resolution, stated explicitly (not left implicit):**

The requirement's own text states the check order (existence, expiry, uses-remain,
event-match, identity-match) and this design follows it literally — **existence is
handled entirely outside this function** (§3.1 step 2, "not found" fails before the
transaction even opens), so this function's first four rows are exactly the remaining
four checks in the stated order. Reordering was considered and rejected: putting
identity-match before uses-remain would mean a spent personal code redeemed by the wrong
person reports "not yours" instead of "spent" — a marginally different user experience,
but the requirement fixes the order explicitly, so this design does not second-guess it.

**Design question 1's info-leakage sub-question, resolved explicitly:** does giving a
personal-code-redeemed-by-someone-else a *distinct* message from "unknown code" leak that
the code string is real? This design's answer is **no, and the two messages are
deliberately distinct** (§6 — five separate catalog keys, one per `InviteCodeValidationResult`
reason plus not-found), for two reasons: (1) the requirement's own acceptance criteria and
STORY-DETAILS text explicitly call for "each ... their own stated reason" across all five
cases including this one — merging them would contradict the requirement, not just this
design's own preference; (2) codes carry ≥128 bits of CSPRNG entropy (S4, REQ-033 §4 — 26
characters × 5 bits = 130 bits). Reaching the `not-yours` branch at all requires already
possessing the exact code string, which is computationally infeasible to have obtained by
guessing — anyone who reaches this branch already has the string through some other means
(a forwarded message, a screenshot), the same threat model REQ-037's "personal code"
concept already accepts as its baseline. A distinct message therefore discloses nothing an
attacker didn't already have. This reasoning is written down here specifically so
SECURITY-REVIEWER can check it rather than re-derive it from nothing.

## 4. The `i_` deep-link entry point

### 4.1 `parseStartPayload` — one new `StartPayload` member

```
export type StartPayload =
  | { kind: "none" }
  | { kind: "event"; eventId: string; channel: string | null }
  | { kind: "checkin"; qrToken: string }
  | { kind: "invite"; code: string; eventId: string | null }; // NEW
```

**Grammar, reusing the exact `primary__optional` shape `e_<id>__<channel>` already
establishes** (`event.ts` lines 504-513) — code is the primary token, an explicit target
event id is the optional suffix:

| Payload text | Parses to |
|---|---|
| `i_<code>` | `{ kind: "invite", code: <code>, eventId: null }` |
| `i_<code>__<eventId>` | `{ kind: "invite", code: <code>, eventId: <eventId> }` |

The `i_<code>` (no suffix) form is what `?start=i_<code>` deep links always produce — a
deep link never carries an independent event id (design question 5/§3.1 already
establishes `explicitEventId: null` is correct and sufficient for this route: the target
event is the code's own event, always). The `i_<code>__<eventId>` (with suffix) form is
never produced by a raw `?start=` deep link — it exists **only** as the payload shape the
`/redeem` command's consent-deferral (§5.2) re-encodes into `consent:agree`'s
`callback_data`, exactly mirroring how `e_<id>__<channel>` already serves both the direct
deep-link case (no channel) and would carry one when present.

The `ci_`/`e_` checks (lines 498-513) are unchanged; the new `i_` check is added
alongside them (order among the three prefix checks does not affect correctness — `ci_`,
`e_`, and `i_` share no overlapping prefix — but is placed directly after the existing
`ci_` check, before `e_`, for the same "readability only" reason the file's own comment
already gives for `ci_` vs `e_`'s ordering).

### 4.2 `resolveInviteDeepLink` — mirrors `resolveEventDeepLink`'s shape exactly

```
async function resolveInviteDeepLink(
  ctx: Context,
  db: DbClient["db"],
  userId: string,
  lang: BotLang,
  code: string,
  explicitEventId: string | null,
  hasConsented: boolean,
): Promise<void>;
```

**Step sequence, mirroring `resolveEventDeepLink` (§6.3's existing structure,
`handlers/start.ts` lines 107-183) point for point:**

1. **Consent gate first** (S1, §0 point 5): if `!hasConsented`, reply with the ordinary
   consent prompt, `reply_markup: buildConsentKeyboard(lang, payloadText)` where
   `payloadText` is `i_<code>` or `i_<code>__<explicitEventId>` per §4.1's grammar. Return
   — resumes in the `consent:agree` callback (§4.3). **No `invite_codes` read, no
   `registrations` write, nothing at all happens before this returns.**
2. **Consented** → call `redeemInviteCode(db, userId, code, explicitEventId, new
   Date())` (§3.1).
3. **Compose and send the reply** using the same outcome-to-message mapping §5.3 defines
   for `/redeem` — this is deliberately the identical composition function, not a second
   copy, since the deep-link and typed-command routes converge on the exact same
   `InviteRedemptionOutcome` union.

### 4.3 `makeConsentCallbackHandler` — one new sibling branch

The existing branch (`handlers/start.ts` lines 603-621) checks
`payload.kind === "event"` and calls `resolveEventDeepLink(..., true)`. This design adds
a sibling `else if (payload.kind === "invite")` branch calling
`resolveInviteDeepLink(ctx, db, flowUser.id, lang, payload.code, payload.eventId, true)`
— same position in the function, same "already consented" `true` argument, same "this
already sent the caller's reply, no separate ordinary greeting" trade-off the `event`
branch's own comment documents. No other line of `makeConsentCallbackHandler` changes.

## 5. The `/redeem` command entry point

### 5.1 Command shape and parsing

`/redeem <event_id> <code>` — a member-facing (not organizer-gated) command, following
the exact `<event_id> <second-token>` parse convention `splitInviteArgs`
(`inviteCode.ts` lines 71-82) already establishes for `/invite_personal`/`/invite_bulk`/
`/invite_companion`. This design reuses that parsing shape rather than inventing a new
one; the "second token" here is the code itself rather than a user id or a max-uses count.

**Why a two-argument command, not a bare `/redeem <code>` or free text — this ambiguity
is explicitly resolved, not left to BACKEND-DEV's judgment:** the requirement's own AC
requires a constructible "code redeemed for the wrong event" refusal (AC3), which is only
meaningful if the redeemer's *intended* target event is knowable independently of the
code's own `event_id`. Two mechanisms were considered:

1. **A stateful "reply to this message" flow** (the `force_reply` + fixed ref-line prefix
   mechanism `organizerRequests.ts`'s `REJECT_REF_LINE_PREFIX`/`parseRejectReplyContext`
   and `noShow.ts` already establish) — the requires-invite refusal message would embed a
   hidden `eventId` marker line, and a plain-text reply to it would recover the target
   event. Rejected: it adds a second free-text listener + parsing contract for no benefit
   over option 2, and "reply to this specific message" is a real UX than a member has to
   discover, versus a documented command.
2. **A two-token command, `/redeem <event_id> <code>`** — no new state, no new listener,
   directly consistent with the `/invite_personal <event_id> <user_id>` family this same
   requirement's dependency (REQ-037) already established as the codebase's idiom for
   "act on a specific event, by id, in one message." **Chosen.**

**Usage error:** either token missing (or the second is empty) → reply with
`catalog.registration.redeemUsage` (§6), no lookup attempted, no transaction opened —
same "collect and report before ever touching the DB" discipline
`parseInvitePersonalArgs`/`parseInviteBulkArgs` already use for their own arg validation
(a pure parse step, no I/O).

### 5.2 Consent gate

Before calling `redeemInviteCode`, the handler checks `flowUser.consentPdAt === null`
exactly as `makeStartHandler`'s own top-level check already does (`start.ts` lines
426-431) for the ordinary flow. Not yet consented → the ordinary consent prompt, with
`payloadText = "i_" + code + "__" + eventId` (§4.1's with-suffix grammar) carried into
`consent:agree`'s `callback_data` via the existing `buildConsentAgreeCallbackData`
helper (`start.ts` lines 275-300 — already byte-budget-aware, already truncates the
free-text tail rather than the primary id when the 64-byte Telegram limit is tight; here
the "primary" the truncation logic must never truncate is `code`, and the truncatable tail
is the optional `eventId` suffix, the same role `channel` already plays for `e_` links —
BACKEND-DEV extends this existing truncation branch rather than writing a second one).
Already consented → proceeds directly to §5.3.

### 5.3 The command handler and its reply composition

```
export function makeRedeemCommandHandler(db: DbClient["db"]): (ctx: Context) => Promise<void>;
```

Once past parsing (§5.1) and consent (§5.2): resolve the acting user (same
`resolveActingUser`/`getFlowUserByTgId` pattern every other member command already uses,
`handlers/registration.ts` lines 51-64), call
`redeemInviteCode(db, actingUser.id, code, eventId, new Date())`, then compose the reply.

**Reply composition — one function, reused by both entry points (§4.2 point 3):**

| `InviteRedemptionOutcome.kind` | Reply |
|---|---|
| `admitted` / `waitlisted` / `requested` / `already-registered` / `not-found` / `event-cancelled` / `event-finished` / `registration-closed` | **Identical, byte-for-byte, to `composeRegistrationReply`'s existing handling of that same kind** (`handlers/registration.ts` lines 136-183) — this design does not fork a second copy of that switch; BACKEND-DEV extends the existing function (it already takes an `outcome` of the union this redemption path also produces) rather than duplicating it. |
| `invite-code-not-found` | `catalog.registration.refusedInviteCodeNotFound` + `catalog.event.deepLinkSeeUpcoming` |
| `invite-code-expired` | `catalog.registration.refusedInviteCodeExpired` + `catalog.event.deepLinkSeeUpcoming` |
| `invite-code-spent` | `catalog.registration.refusedInviteCodeSpent` + `catalog.event.deepLinkSeeUpcoming` |
| `invite-code-wrong-event` | `catalog.registration.refusedInviteCodeWrongEvent` + `catalog.event.deepLinkSeeUpcoming` |
| `invite-code-not-yours` | `catalog.registration.refusedInviteCodeNotYours` + `catalog.event.deepLinkSeeUpcoming` |

Every one of the five new refusals appends the same onward-path line every other refusal
in this file already appends (§0 point 4) — no new onward-path mechanism.

### 5.4 The plain (no-code) `requires-invite` refusal — extended, not replaced

`composeRegistrationReply`'s existing `"requires-invite"` case (line 167-168, currently
`return catalog.registration.refusedRequiresInvite;` with **no** onward path — the
REQ-020 placeholder this requirement replaces) becomes:

`catalog.registration.refusedRequiresInvite` + `catalog.registration.refusedRequiresInviteHint`
+ `catalog.event.deepLinkSeeUpcoming`

`refusedRequiresInviteHint` is the new line telling a redeemer with a code how to use it
(names `/redeem`, §6). This is reachable only when `hasPastCheckIn` (§2) returned `false`
— a past attendee never reaches this branch at all, since `inviteSatisfied` was already
`true` for them at the `decideRegistrationOutcome` call.

### 5.5 `bot.command` registration

One new line in `apps/bot/src/index.ts`, alongside the existing `invite_personal`/
`invite_bulk`/`invite_companion` block (lines 332-334) or immediately after it:
`bot.command("redeem", makeRedeemCommandHandler(db));` — no callback-query or
`message:text` listener is added (§5.1 point 2's resolution: no free-text/reply-to state).

## 7. Open questions (not silently resolved)

1. **Companion codes (`grants_companion_of` non-null) get no special redemption
   behaviour in this design.** REQ-037 issues them (`maxUses: 1`, `issuedToUserId: null`),
   but nothing in this requirement's own text asks redemption to do anything with
   `grants_companion_of` beyond what §3.2's table already does for any non-personal code
   (exists/expiry/uses-remain/event-match — identity-match never applies, since
   `issuedToUserId` is null for a companion code). Whether a companion's registration
   should be linked back to its host (`invited_by_user_id`, already a column on
   `registrations`, currently unused by any REQ-033-037 write path) is left unresolved
   here — not invented, not silently wired up. Flagged for a future requirement if the
   product actually needs it.
2. **Whether `/redeem`'s `<event_id>` argument should accept anything other than the raw
   UUID** (a short code, a title fragment) is out of scope — every other `<event_id>`
   -taking command in this codebase (`/invite_personal`, `/walkin`, `/requests`) takes the
   raw id, and this design follows that precedent without inventing a friendlier lookup.
3. **Rate limiting/lockout for repeated failed redemption attempts** is not addressed —
   the 130-bit entropy floor (S4) is this codebase's existing defense against guessing,
   and no other command in this codebase currently rate-limits failed attempts either.
   Flagged rather than silently assumed sufficient forever.

**AC8's resolution, stated here explicitly (also referenced above):** FR-4 calls
past-attendee eligibility "configurable per event," but PRD 5's `Event` entity lists no
such flag, and inventing one is exactly what PRD's closing rule and this issue's own text
forbid doing silently. **This design takes resolution (a): the rule applies uniformly to
every `requires_invite` event** (§2 — `hasPastCheckIn` takes no event-scoping parameter
at all, deliberately; it is a property of the user, not of the event). "Configurable per
event" is explicitly deferred, not implemented, until a real product need for per-event
variation appears — at which point it becomes its own requirement with its own
`docs/agents/decisions/` record (per option (b) the issue offers), not a column added
here. **No column is added to `events`, `users`, or any other table by this design** —
confirmed by this document containing zero `ALTER TABLE`/new-column mentions anywhere
above, and by the "No schema change" paragraph at the top of this document.
