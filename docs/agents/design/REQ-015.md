# REQ-015 — Venue CRUD for organizers, chapter-scoped

**Requirement:** Organizer-only creation, listing, editing and deletion of Venues,
scoped to the organizer's own chapter. Every mutation writes an `AuditLog` row.
depends_on: REQ-014.

**Surface:** `apps/bot/**` (bot requirement). No `apps/web` change. No schema change —
`venues` and `audit_log` already exist from REQ-011 with every field this requirement
needs (design doc `docs/agents/design/REQ-011.md`, table in
`apps/bot/src/db/schema.ts` lines 168-187 for `venues`, 304-326 for `audit_log`).

**Files this design expects:**
- `apps/bot/src/domain/venueAuthorization.ts` (new) — §1
- `apps/bot/src/domain/venue.ts` (new) — §2, §3, §4, §5, §6
- `apps/bot/src/domain/auditLog.ts` (new) — §6, reused by later requirements
- `apps/bot/src/handlers/venue.ts` (new) — §3/§4/§5 command wiring
- `apps/bot/src/i18n/types.ts`, `ru.ts`, `en.ts` — new `venue.*` catalog keys, §9
- `apps/bot/src/index.ts` — registers the three new commands

## 1. Authorization check (AC1, AC2 — S2)

A single, reusable, framework-free predicate, called as the FIRST statement of every
venue-mutation handler, before any parsing, any DB read of the venue row, or any reply:

```
// apps/bot/src/domain/venueAuthorization.ts

interface ActingUser {
  id: string;
  role: "member" | "organizer" | "owner";
  chapterId: string | null;
}

type AuthorizationResult =
  | { ok: true; user: ActingUser }
  | { ok: false; reason: "no-user" | "not-organizer" | "wrong-chapter" };

// Resolves ctx.from.id -> users.id/role/chapter_id. Same discipline as
// REQ-013/014's getFlowUserByTgId: tg_id is used only in this one lookup's
// WHERE clause; every later reference is user.id.
function resolveActingUser(db, tgId: bigint): Promise<ActingUser | null>;

// Pure predicate over already-resolved data — no I/O, unit-testable without a DB.
function checkOrganizerForChapter(
  user: ActingUser | null,
  targetChapterId: string,
): AuthorizationResult;

// Composed entry point every handler calls first.
function requireOrganizerForChapter(
  db,
  tgId: bigint,
  targetChapterId: string,
): Promise<AuthorizationResult>;
```

`checkOrganizerForChapter` logic, stated exactly so it cannot be reinterpreted:

1. `user === null` → `{ ok: false, reason: "no-user" }` (no `users` row for this
   `tg_id` at all — a `member`'s or a stranger's tap resolves here if they've never
   been given a role).
2. `user.role === "member"` → `{ ok: false, reason: "not-organizer" }`.
3. `user.role === "owner"` → `{ ok: true, user }` — owner acts on every chapter (PRD 3:
   owner = "all chapters + role assignment"), so no chapter-match check applies.
4. `user.role === "organizer"` → `{ ok: true, user }` only if
   `user.chapterId === targetChapterId`; otherwise `{ ok: false, reason:
   "wrong-chapter" }`.

**AC1 mapping** ("member invoking the handler directly is refused, no side effect"):
step 2 above. Because this check runs before any venue row is read or written, and the
handler's reply/DB-write code paths are only reachable through the `{ ok: true }`
branch, a refused call produces **zero** venue rows and **zero** `audit_log` rows — the
authorization check and the mutation are not two independently-callable steps a caller
could invoke out of order.

**AC2 mapping** ("organizer of chapter A acting on chapter B is refused"): step 4
above, restated as the reason cross-chapter access needs no separate code path —
`user.chapterId` is read from the DB, never taken from caller input, so an organizer's
own `chapterId` is fixed regardless of what `targetChapterId` a crafted call supplies.
`targetChapterId` itself is resolved differently for create vs. edit/delete — see §2
and §4 — but the predicate above is identical in every caller.

**Refusal reply.** On any `ok: false`, the handler sends one catalog string
(`venue.notAuthorized`, a single generic message — reason is not disclosed to the
caller, only used internally/in the audit trail if ever logged) and returns
immediately. No `AuditLog` row is written for an authorization refusal (S8 only
requires a row on a **status change**; a refused attempt changes nothing — this
mirrors S5's contrast, where check-in refusals for a non-staff scanner ARE logged
because S5 states that explicitly. REQ-015's own S2/S8 text does not ask for a refusal
audit row, so this design does not invent one — flagged as an open question in §9 in
case SECURITY-REVIEWER wants it added).

## 2. Venue creation flow (AC3)

### 2.1 Command shape — decision

**Chosen: a single command carrying structured multi-line text, no multi-step
conversation state.** Rationale:

- PRD 11's simplicity bias plus decision 0004's "plugins added only when a requirement
  needs them" rule: a multi-step conversation would need the `conversations` plugin
  (not yet a dependency — REQ-009 deliberately added none). Venue creation has no
  restart-safety requirement analogous to FR-3's profile form (no PRD text says a
  half-finished venue draft must survive a bot restart), so there is nothing here that
  needs cross-message state at all.
- A single message is trivially restart-safe by construction: it either arrives and is
  processed in one handler invocation, or it doesn't arrive — there is no partial state
  to lose, because none is ever created.

### 2.2 Command and parsing

`/venue_new` with no further text replies with a usage template (catalog string
`venue.createUsage`) showing the exact field syntax. To actually create, the organizer
sends `/venue_new` followed on subsequent lines by `label: value` pairs:

```
/venue_new
name: Coworking Ilon
address: Tashkent, Chilanzar, 12
yandex: https://yandex.uz/maps/-/CCU...
google: https://maps.google.com/?q=...
capacity: 40
lat: 41.311
lon: 69.240
notes: entrance from the yard
chapter: <chapter-id>   (optional — see §2.5)
```

`parseVenueFields(text: string): Record<string, string>` (framework-free, in
`domain/venue.ts`) splits the text after the command on newlines, and each line on the
**first** `:` character, trimming both sides. Unknown labels are ignored (forward
compatible); labels are case-insensitive. This function has no DB access and is
directly unit-testable.

### 2.3 Required vs. optional (AC3)

| Field | Required at creation? | Refusal on missing |
|---|---|---|
| `name` | yes | names `name` |
| `address` | yes | names `address` |
| `yandex` → `yandexUrl` | yes (PRD FR-2 / story A3) | names `yandex` |
| `google` → `googleUrl` | yes (PRD FR-2 / story A3) | names `google` |
| `capacity` | yes, must parse as a positive integer | names `capacity` |
| `lat` | no | — |
| `lon` | no | — |
| `notes` | no | — |

Validation function `validateVenueCreateInput(fields): { ok: true; value: VenueInput }
| { ok: false; missing: string[] }` checks required fields in a fixed order and
collects **every** missing field into `missing` (not just the first), so the refusal
message can name all of them at once — the requirement's own text ("refused with a
message naming the missing field") is satisfied by naming exactly the field(s) that are
actually absent, singular or plural.

`lat`/`lon`: if either is present, both must parse as numbers (a lat with no lon, or an
unparseable value, is a normal-shaped validation error naming that field — not a
"coordinates missing" case). If both are absent, creation proceeds and the reply
includes the completion nudge (§2.4).

### 2.4 Completion nudge (AC3)

When `lat`/`lon` are both absent on a successful create, the confirmation reply appends
a second catalog string, `venue.completeNudge` ("Add coordinates later with
`/venue_edit <id>` so the map link renders precisely" — exact copy is CONTENT-BA's, not
invented here). This is plain reply composition in the handler — no domain logic,
no separate state to track ("nudged already?" is not a stored flag; the nudge is
re-derived every time from `lat === null`, so `/venue_edit` re-editing a
still-coordinate-less venue would, per this design, show the nudge again on its own
confirmation — see the edit flow, §4).

### 2.5 Target chapter for creation

`chapter` is an **optional** field. If absent, the target chapter is the actor's own
`chapterId` (from `resolveActingUser`) — this is the only path a normal organizer ever
takes, and it is definitionally same-chapter, so AC2's cross-chapter case cannot arise
through it. If present, its value is used as `targetChapterId` for the
`requireOrganizerForChapter` call — this is what makes AC2's negative case
constructible at all for *creation* (an owner legitimately uses this to create a venue
in a chapter that is not their own — owners have no "own chapter" — while an organizer
attempting the same by supplying a foreign `chapter` value is caught by
`checkOrganizerForChapter` step 4). This mirrors AC1's own framing: the negative case is
proven by constructing the handler call directly with the crafted field, the same way
AC1 is proven by invoking the handler with a `member`'s `tg_id`, not through any menu
that would normally offer a chapter picker to an organizer.

### 2.6 Creation write (single transaction — see §6)

`createVenue(db, actorUserId, input, at)`:
1. `INSERT INTO venues (...) VALUES (...) RETURNING id`.
2. Write one `AuditLog` row, `action: "venue.create"` (§6).
Both statements run inside one `db.transaction(...)` so they cannot partially apply.

## 3. Listing

`/venues` lists the caller's own chapter's venues (owner: their own chapter only too —
listing is not a cross-chapter admin view in this requirement's scope; PRD text does
not ask for one). `listVenuesForChapter(db, chapterId): { id, name, address }[]`, a
plain read scoped by `chapterId` — no authorization check needed beyond "must resolve
to *some* chapterId" since listing is not a mutation and S2's negative case is
stated for mutations; a `member` typing `/venues` sees their own chapter's list, which
is not a privacy concern (venue name/address is not personal data). This is a
deliberate scope note, not silently assumed — flagged in §9.

## 4. Venue editing (AC2 continued)

`/venue_edit <venue-id>` with no further lines replies with the venue's current field
values (as a usage template it can be copy-edited from) plus usage instructions.
`/venue_edit <venue-id>` followed by `label: value` lines updates **only the supplied
fields** (partial update — same `parseVenueFields` as creation). Editable fields: all of
`name, address, yandex, google, capacity, lat, lon, notes` (PRD 5's Venue fields minus
`chapter_id`, which is never editable through this command — moving a venue to a
different chapter is out of this requirement's scope, not assumed).

Authorization: `targetChapterId` is the **existing venue row's** `chapterId`, read by
`getVenueById(db, venueId)` before the authorization check runs. Order of operations:

1. `venue = getVenueById(db, venueId)`. If `null`, reply "not found", stop (no audit
   row — nothing existed to change).
2. `requireOrganizerForChapter(db, tgId, venue.chapterId)`. If `ok: false`, refuse, stop.
3. Parse + validate the partial update (same required-field rule does NOT re-apply to
   fields not being changed — a field already `NOT NULL` in the row, like `yandexUrl`,
   is simply left alone if omitted from this edit; an edit CAN clear an optional field
   by supplying an explicit empty value, e.g. `notes:`, but cannot clear `yandexUrl`
   or `googleUrl` to empty since those stay required post-creation too — validated the
   same way as create, but only for whichever of the two keys is present in the edit's
   field set).
4. `updateVenue(db, actorUserId, venueId, changedFields, at)` — one `UPDATE` plus one
   `AuditLog` row (`action: "venue.update"`), one transaction (§6).

This reuses `checkOrganizerForChapter` from §1 unchanged, satisfying AC2's "confirm the
design's authorization check naturally covers this" requirement — edit's
`targetChapterId` is simply sourced from the venue row instead of an optional input
field, and the same predicate refuses an organizer of chapter A whose `chapterId` does
not match chapter B's venue.

## 5. Venue deletion with future-event refusal (AC4)

`/venue_delete <venue-id>`:

1. `venue = getVenueById(db, venueId)`. `null` → "not found", stop.
2. `requireOrganizerForChapter(db, tgId, venue.chapterId)`. Refused → stop, no audit row.
3. **Future-event check** (decision 0006 — evaluation time is an explicit parameter,
   never SQL `now()`):

```
// domain/venue.ts
function hasFutureEventReference(
  db,
  venueId: string,
  evaluationTime: Date,
): Promise<boolean> {
  // SELECT 1 FROM events
  // WHERE events.venue_id = $venueId
  //   AND events.starts_at > $evaluationTime
  // LIMIT 1
}
```

   The handler supplies `evaluationTime = new Date()` at call time (same pattern as
   `recordConsent`'s `at` parameter in `domain/consent.ts`) — the query itself never
   reads the clock. If any row is found, refuse with catalog string
   `venue.deleteRefusedFutureEvent`, naming the reason ("this venue has an upcoming
   event scheduled") — no ids or titles are echoed (not PII, but unnecessary detail;
   PRD text only requires "the reason", not an event listing). No audit row: the
   venue was not deleted.
4. No future reference → `deleteVenue(db, actorUserId, venueId, venueSnapshot, at)`:
   `DELETE FROM venues WHERE id = $1`, plus one `AuditLog` row (`action:
   "venue.delete"`), one transaction (§6). `venueSnapshot` (name, address) is captured
   BEFORE the delete for the audit payload, since the row will no longer exist to read
   from afterward.

**Why the query is safe against a past-event-only reference:** `events.venue_id`
references `venues.id` with `onDelete: "restrict"` (schema.ts line 197-199) — Postgres
itself would refuse a `DELETE` while ANY event (past or future) still references the
venue, not just future ones. This is a genuine tension the design must state rather
than paper over: the FK's `restrict` behavior is stricter than PRD's stated rule
("deleting a venue attached to an **upcoming** event is refused" implies a venue
attached only to **past** events should be deletable). Two ways to reconcile this,
named as an open question in §9 rather than picked silently, since choosing between
them touches the schema (DATA-DESIGNER's territory, not this artefact's to decide):
(a) nullify `events.venue_id` for past events before the venue delete is allowed
(requires an explicit, deliberate mutation to Event rows this requirement's scope does
not otherwise touch), or (b) leave the FK as `restrict` and let a past-events-only
delete attempt fail at the database level with a foreign-key-violation error, which
this handler would need to catch and translate into a user-facing message distinct from
the future-event refusal. **Until Event CRUD (REQ-016) exists, no event row can ever be
created at all** (REQ-016 is still `pending`), so no venue can be referenced by any
event yet — this scenario is entirely unreachable in REQ-015's own runtime and is not a
gap REQ-015 must close; it must be closed before REQ-016 or REQ-018+ close enough of the
gap. Flagged for REQ-016's design to resolve, since REQ-016 is what would first create a
row that makes this reachable.

## 6. AuditLog write (AC5, S8)

`domain/auditLog.ts`, reused by every later requirement that writes audit rows, not just
this one:

```
interface WriteAuditLogInput {
  actorUserId: string;       // never null here — every venue mutation has an authenticated actor
  action: string;            // "venue.create" | "venue.update" | "venue.delete"
  entity: "venue";
  entityId: string;          // the venue's id
  payload: Record<string, unknown> | null;
  at: Date;                  // caller-supplied evaluation time, not defaultNow() —
                              // stated for consistency with decision 0006's rule, though
                              // 0006 itself exempts audit timestamps; using an explicit
                              // `at` here still lets a test control and assert the exact
                              // stored value, matching recordConsent's own pattern.
}

function writeAuditLog(db, input: WriteAuditLogInput): Promise<void>;
```

**Exactly-once discipline.** `writeAuditLog` is never called directly by a handler.
It is called exactly once, from inside each of `createVenue`, `updateVenue`,
`deleteVenue` — in the SAME `db.transaction(...)` as the row mutation itself. This is
the mechanism that satisfies "exactly one row... never on a refused/failed attempt,
never twice" (AC5):

- **Never on refusal:** the authorization check (§1) and the future-event check (§5)
  both `return` before `createVenue`/`updateVenue`/`deleteVenue` is ever called — there
  is no code path from a refusal into the function that contains the audit write.
- **Never twice:** the audit write lives inside the same function and the same
  transaction as the mutation it documents — there is exactly one call site per
  successful operation, not a separate "then also log it" step a handler could call
  twice (e.g. once on the happy path and once in a retry branch) or a caller could skip.
- **Atomicity:** if the audit insert fails, the transaction rolls back the venue
  mutation too — never a venue changed with zero audit rows, per S8's negative case
  ("a status changed through a path that bypasses the audit-writing code path").

Payload shape per action (no PII per S11 — venue data carries none, but kept minimal
regardless):

| action | payload |
|---|---|
| `venue.create` | `{ chapterId, name }` |
| `venue.update` | `{ chapterId, changedFields: string[] }` (field **names** only, not old/new values — avoids ever growing into a diff payload that could later carry something sensitive if a future field is added, matching S11's caution about `AuditLog.payload` scope) |
| `venue.delete` | `{ chapterId, name }` (captured pre-delete, §5 step 4) |

## 7. "Editing affects future events; past events keep what they had" — resolution

**Choosing option (a).** REQ-015's own scope is venue CRUD only. No Event
creation/editing handler exists yet — REQ-016 (`title: Event CRUD...`) is still
`status: pending` in `docs/agents/requirements.yaml`, and no code under `apps/bot/src`
reads or writes an `events` row today (`git grep -n "events\." apps/bot/src` returns
only `schema.ts`'s own table definition). There is therefore no "what an event shows for
its venue" behavior in existence yet for this requirement to preserve, break, or make
testable — a venue's `UPDATE` cannot retroactively rewrite anything Event-related
because nothing Event-related currently reads venue data at all.

What REQ-015 CAN truthfully claim, and does: a venue `UPDATE` only ever writes the
`venues` row identified by its own `id` (§4's `updateVenue`) — it performs no write to
`events`, `registrations`, or any other table, so there is no code path in THIS
requirement's scope that could rewrite a past event's stored venue details even if such
details existed. This is trivially true precisely because Event CRUD doesn't touch
venues at all yet, exactly as the requirement's own framing anticipated.

**What is deferred, explicitly, to REQ-016's design (not implemented or decided here):**
whether an Event's "venue as shown" is a **live foreign-key reference** to
`venues.id` (read fresh at render time — meaning an edited venue's new address WOULD
appear on a past event's rendering unless REQ-016 does something to prevent it) or a
**point-in-time snapshot** taken at Event creation/publish time (requiring a new
column/table on the `events` side — e.g. a `venue_snapshot` JSONB column, or a
join-table-with-timestamp — which is squarely DATA-DESIGNER's decision, not this
artefact's to invent). REQ-015 adds NO schema, NO column, and NO snapshot mechanism for
this. This is stated here as a **handoff note for REQ-016's design step**: "past events
keep what they had" (STORY-DETAILS F2) becomes a real, testable property only once an
Event row exists that can be checked before and after a venue edit — REQ-016 is the
first point where that check is even constructible, and its design artefact must state
explicitly which of the two mechanisms above it uses, per this requirement's same
instruction extended forward rather than resolved twice.

## 8. Acceptance criteria → design element map

| AC | Design element |
|---|---|
| AC1 — member invoking handler directly is refused, no venue created | §1 `checkOrganizerForChapter` step 2 (`role === "member"` → refused before any DB write); §1 "no side effect" note; §2.6/§4/§5 show the mutation functions are only reachable past an `ok: true` check |
| AC2 — organizer of chapter A vs. chapter B refused | §1 step 4 (`chapterId` mismatch); §2.5 (create's optional `chapter` field is what makes the case constructible for creation); §4 step 1-2 (edit's `targetChapterId` sourced from the existing venue row) |
| AC3 — missing yandex/google refused naming the field; missing lat/lon succeeds + nudges | §2.3 required-field table + `validateVenueCreateInput`; §2.4 completion nudge |
| AC4 — delete refused when referenced by a future event, reason stated | §5 `hasFutureEventReference` query (evaluation-time parameterized per decision 0006); refusal copy `venue.deleteRefusedFutureEvent` |
| AC5 — exactly one audit_log row per successful create/edit/delete | §6 `writeAuditLog`, called exactly once per mutation function, same transaction, never on a refused path |

## 9. Open questions (not silently resolved)

1. **Refusal audit rows.** S5 explicitly requires an audit row when check-in refuses an
   unauthorized scanner; REQ-015's own S2/S8 text does not ask for one on an
   authorization refusal for venue mutations. This design does NOT write one on refusal.
   Flag for SECURITY-REVIEWER: should an unauthorized venue-mutation attempt also be
   audited the way S5's negative case is, even though REQ-015's acceptance criteria only
   count rows on SUCCESS ("Each successful venue create/edit/delete writes exactly one
   audit_log row")? If yes, that is an ADDITIONAL row type this design does not specify
   and would need a follow-up.
2. **Past-events-only deletion vs. the `restrict` FK.** §5's tension between PRD's
   "upcoming event" wording and the schema's `onDelete: "restrict"` FK, which restricts
   on ANY referencing event. Unreachable today (no Event rows can exist until REQ-016
   ships) but must be resolved before a venue with only past-event references can ever
   actually be deleted. Named for REQ-016 or a follow-up, not decided here.
3. **Snapshot vs. live-reference for "past events keep what they had."** §7 — explicitly
   deferred to REQ-016's design, per the instructions given for this run. Not a gap in
   REQ-015; a dependency direction stated so it is not silently dropped.
4. **Command-based creation UX.** The structured multi-line `/venue_new` format (§2.2)
   is functional but not polished — no inline-keyboard step-by-step alternative was
   designed, matching PRD 11's simplicity bias and decision 0004's "no plugin added
   preemptively" rule. Whether this is good enough UX long-term, or whether a future
   requirement should add the `conversations` plugin for a friendlier step-by-step
   flow, is left open — not a defect of this requirement's own acceptance criteria,
   none of which test UX polish.
5. **`/venues` listing's authorization scope.** §3 — listing is not gated by
   `requireOrganizerForChapter` (venue name/address is not personal data, and no
   acceptance criterion tests listing authorization). If a later requirement decides
   listing should be organizer-only too, that is a new/changed acceptance criterion,
   not an oversight in this one.
6. **Clearing an optional field via edit.** §4 step 3 allows `notes:` (empty value) to
   clear an existing note. Whether the parser should distinguish "field omitted" (leave
   alone) from "field present but empty" (clear it) needs an explicit convention
   agreed by whoever writes the catalog copy/usage template — this design states the
   rule but the exact empty-value syntax (`notes:` vs. a literal `notes: -`) is left to
   BACKEND-DEV/CONTENT-BA to settle when writing the usage-template copy, since it's a
   copy/UX detail, not a behavior this artefact needs to lock down further.
