# REQ-007 Design — Monorepo layout: move the site into `apps/web`

**Requirement:** REQ-007
**Decision this implements:** `docs/agents/decisions/0003-events-bot-subproject.md`,
section "Layout: the site moves to `apps/web`".
**Design type:** STRUCTURAL (file-move + workspace config). Not a UI/component
requirement.

## 0. Why this design artefact looks different from a normal one

REQ-007 introduces no new UI component, prop, content shape, design token, or
responsive/theme behavior. Per the requirement text and the CODE-DESIGNER role, the
usual template sections for those do not apply here and are addressed explicitly below
(marked N/A) rather than left blank. What this artefact specifies instead, to give
CODE-DESIGN-VALIDATOR and FRONTEND-DEV something concrete to check against, is:

1. The exact list of root paths that move, and where each lands.
2. The exact required shape (fields/values, not literal JSON-as-code) of the new root
   `package.json`.
3. The exact required shape of `apps/web/package.json` (the moved, unchanged current
   root `package.json`).
4. The explicit out-of-scope boundary.

|---|---|---|
| 1 | `src/` | `apps/web/src/` |
| 2 | `messages/` | `apps/web/messages/` |
| 3 | `public/` | `apps/web/public/` |
| 4 | `next.config.ts` | `apps/web/next.config.ts` |

Command shape (illustrative of the operation, not literal implementation instructions
for FRONTEND-DEV to copy verbatim — FRONTEND-DEV determines exact invocation, this row

```
mkdir apps apps/web   (or git handles directory creation implicitly)
git mv src apps/web/src
git mv messages apps/web/messages
git mv public apps/web/public
git mv next.config.ts apps/web/next.config.ts
```

`package-lock.json` is **not** moved — it is superseded by a newly regenerated
root-level lockfile (§5). The old lockfile is effectively replaced in place at the root,
not relocated.

## 3. New root `package.json` — required shape

A brand-new file at repo root (the moved-out manifest is gone from root; this is a
distinct file, not an edit of a moved one). Required fields and values:

- `"name"`: a value distinct from `"app"` (which now belongs to `apps/web/package.json`)
  identifying this as the workspace root — e.g. a name describing the monorepo itself.
  Exact string is FRONTEND-DEV's implementation choice; open question flagged in §7.
- `"private"`: `true` (required — decision 0003 and the requirement text both mandate
  this; a workspace root must never be publishable).
- `"workspaces"`: array containing exactly `"apps/*"`. Must not also include
  `"packages/*"` yet — `packages/` does not exist and decision 0003 says it is created
  only when a second consumer exists; adding it prematurely would be inventing scope
  this requirement does not have.
- `"scripts"`: root-level scripts that delegate to the `apps/web` workspace so that the
  existing CI invocations (`npm run lint`, `npm run build` — see `.github/workflows/ci-cd.yml`,
  job `build`, unchanged by this requirement) keep working unchanged from the repo root.
  Required script keys and delegation target:
  - `"dev"` -> delegates to `apps/web`'s `dev` script (e.g. `next dev` invoked via
    `-w apps/web`)
  - `"build"` -> delegates to `apps/web`'s `build` script
  - `"lint"` -> delegates to `apps/web`'s `lint` script
  - `"start"` -> delegates to `apps/web`'s `start` script
  - Delegation mechanism: npm workspaces' `-w <workspace>` flag (e.g.
    `npm run build -w apps/web`), consistent with the requirement text's own example.
    No other delegation mechanism (turborepo, nx, custom shell script) is introduced —
    that would be inventing tooling this requirement does not call for.
- No `"dependencies"` or `"devDependencies"` are required at the root by this
  requirement. The root manifest's job is workspace declaration and script delegation
  only; all actual package dependencies stay declared in `apps/web/package.json`
  (unchanged, per §4). If `npm install` at the root needs any tooling of its own in the
  future (e.g. a shared linter config), that is a separate requirement's concern, not
  this one's.

## 4. `apps/web/package.json` — required shape

This file is the current root `package.json`, moved with **no content changes**. The
requirement text is explicit that name/scripts/dependencies stay as-is. For the
validator's and FRONTEND-DEV's reference, the required (unchanged) content is:

- `"name"`: `"app"`
- `"version"`: `"0.1.0"`
- `"private"`: `true`
- `"scripts"`: `"dev": "next dev"`, `"build": "next build"`, `"start": "next start"`,
  `"lint": "eslint"` — unchanged
- `"dependencies"`: `next` `16.3.2`, `next-intl` `^4.13.7`, `react` `19.2.8`, `react-dom`
  `19.2.8` — unchanged
- `"devDependencies"`: `@types/node` `^20`, `@types/react` `^19`, `@types/react-dom`
  `^19`, `eslint` `^9`, `eslint-config-next` `16.3.2`, `typescript` `^5` — unchanged

No field in this file is added, removed, or edited by this requirement. If any of these
values differ from the moved file at implementation time (e.g. because a dependency was
bumped on `master` after this design was written), FRONTEND-DEV carries the current
values forward unchanged — this design does not freeze version numbers as of this
writing, it freezes the rule "unchanged by the move."

## 5. Lockfile regeneration

After the move and after both `package.json` files are in place, `npm install` is run
at the repo root to regenerate `package-lock.json` at the root so it describes the
workspace tree (root + `apps/web` as a workspace member). This is the only lockfile in
the repo post-move; no separate lockfile is committed under `apps/web/`.

## 5a. Post-move runtime verification (locale routing + /health)

The move must not change what the site serves. Two runtime elements move intact under
`apps/web/src/` and both must be exercised post-move, not just assumed from the file list
in §2:

- **Locale routing structure**: `src/app/[locale]/...` (the entire dynamic-locale route
  tree, including `src/app/[locale]/layout.tsx` which sets `<html lang={locale}>`
  dynamically per REQ-005's verified findings) moves as part of `src/` -> `apps/web/src/`
  (§2, row 1). No file inside it is split out or edited by this requirement.
- **Health check route**: `src/app/health/route.ts` (per decision
  0003-events-bot-subproject.md's "current state" section) likewise moves as part of
  `src/` -> `apps/web/src/`, unedited.

**Required verification procedure**, run once the move and both `package.json` files
(§3, §4) and the regenerated lockfile (§5) are in place — this is the same method
REQ-005 already established and re-used verbatim, not a new check invented for this
requirement:

1. From the repo root, run `npm run build && npm run start` (the root scripts delegate to
   `apps/web` per §3).
2. Request all four locale routes — `/ru`, `/uz`, `/en`, `/kk` — and confirm each response
   renders with an `<html lang="...">` value matching its route segment.
3. Confirm no missing-translation-key errors or fallback warnings appear for any of the
   four locales while doing so.
4. Request `/health` and confirm it returns HTTP 200.

This is the acceptance criterion's own required check (REQ-007 AC3 in
`docs/agents/requirements.yaml`), stated here as a concrete verification point rather
than left for FRONTEND-DEV/TEST-RUNNER to infer from "no visual/behavioral surface
changes" (§7).

## 6. Explicit out of scope (do not touch in this requirement)

Per the requirement text, the following stay at the repo root, untouched by this
requirement, and are **not** to be edited even incidentally:

- `Dockerfile` — currently `COPY package.json package-lock.json ./` and
  `COPY . .` assume a single-app root layout and will not build correctly against the
  post-move tree. This requirement does not fix that. Docker breakage between REQ-007
  landing and REQ-008 landing is expected and accepted (requirement text is explicit on
  this).
- `deploy/` — untouched.
- `.github/workflows/ci-cd.yml` — untouched. Its `build` job's `npm ci` / `npm run lint`
  / `npm run build` / `docker build` steps keep running unchanged at the root; the first
  three are expected to keep working because of the delegating root scripts (§3), the
  `docker build` step is expected to break (Docker fix is REQ-008's scope, not this
  one's — do not "fix" it here even though it will fail; fixing it in this requirement
  would be scope creep on a requirement whose own text forbids it).
- `README.md`, `AGENTS.md`, `CLAUDE.md`, `.gitignore` — untouched.
- `docs/` — untouched by the move itself. (Requirement status / decision records are
  updated by DOC-UPDATER at WF-02 Step 6 per the normal workflow, not by this design or
  by FRONTEND-DEV's implementation step.)
- `apps/bot/` — not created. Out of scope per decision 0003 (REQ-009).
- `packages/` — not created. Out of scope per decision 0003 (created only when a second
  consumer of shared code exists).
- REQ-001a..REQ-006 entries in `docs/agents/requirements.yaml` — not rewritten or
  renumbered. Their root-relative path citations stand as historical record per decision
  0003's explicit instruction; any reader resolves them post-migration as
  `apps/web/<old path>`. This design does not touch `requirements.yaml`.

## 9. Open questions (not resolved here — flag for CODE-DESIGN-VALIDATOR / ORCH)

1. **Root `package.json` `"name"` value.** The requirement text does not specify what
   the new root manifest's `name` field should be (only that it must differ in role from
   `apps/web`'s `"app"`). Candidates an implementer might pick include the repo name
   (`aiqadam-next`) or a workspace-specific name (`aiqadam-monorepo`). This design does
   not pick one — FRONTEND-DEV should choose the repo's existing name (`aiqadam-next`,
   matching the GitHub repo) unless ORCH/REVIEWER states a preference, since that is the
   least surprising default and requires no new naming decision.
2. **tsconfig path aliases.** If `tsconfig.json` (moving unchanged to `apps/web/`) uses
   any `paths` alias keyed to root-relative assumptions (e.g. `@/*` -> `./src/*`), the
   alias itself does not need to change since `tsconfig.json` and `src/` move together
   as a unit and the alias is relative to `apps/web/` after the move — but this design
   flags it for FRONTEND-DEV to verify with an actual build (`npm run build -w apps/web`
   from the new root), not assume.
3. **Whether `apps/web/eslint.config.mjs` needs a root companion.** The root
   `package.json`'s `lint` script delegates to `apps/web`'s lint script, which reads
   `apps/web/eslint.config.mjs` from its own workspace directory — this should work
   unmodified under `npm run lint -w apps/web`, but this design does not have a way to
   verify ESLint's config-resolution behavior without actually running it, so
   FRONTEND-DEV/TEST-RUNNER must confirm `npm run lint` at the root actually lints
   `apps/web/src` and not an empty/wrong tree.
4. **`.next/` build artifact directory** currently exists at repo root
   (untracked/gitignored). This design does not require moving or deleting it — it is
   a build output, not a source file, and will simply be regenerated under
   `apps/web/.next/` on the next build. Flagging only so FRONTEND-DEV doesn't mistake a
   stale root `.next/` for a build success signal post-move.
