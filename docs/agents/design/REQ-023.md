# REQ-023 — Waitlist auto-promotion on a freed seat, halting at T-24h

**Requirement:** USER-STORIES B4 ("Get in when a seat frees up"), PRD 6's auto-promotion
rule. `depends_on: REQ-022`.

**Surface:** `apps/bot/**` (bot requirement). No design tokens apply — Telegram text/
button copy only, same as every other bot design in this pipeline (REQ-018/020/021/022).

**No schema change.** Checked `apps/bot/src/db/schema.ts` directly: `registrations`
already has every column this design needs — `admission` (the `admission` pgEnum already
has `'waitlisted'`/`'admitted'`, REQ-011), `created_at` (the waitlist-ordering column,
REQ-021), `qr_token` (nullable, unique-indexed, REQ-011/REQ-020), and
`registrations_waitlist_order_idx` (event_id, created_at) WHERE admission='waitlisted'
(REQ-011, already used by `getWaitlistPosition`). `events` already has `status`,
`starts_at`, `ends_at`, `capacity`. `audit_log` is unchanged. **No `ALTER TABLE`, no new
column, no new enum value, no new index — `DATA-DESIGNER` is not dispatched for this
run**, same precedent as REQ-017/REQ-020/REQ-021/REQ-022. Design question 2 (below)
explains why no "send-marker" column is needed either.

## 0. Design question 1 — trigger point (resolved)

**Auto-promotion is invoked from within `withdrawRegistration`'s own transaction
(`apps/bot/src/domain/registration.ts`, REQ-022 §2.2), not as a separate polling job.**

Checked directly, per this task's instruction: `withdrawRegistration` is the only
existing path anywhere in this codebase that transitions a registration's `admission`
value *out of* `'admitted'` (its step 4 UPDATE, REQ-022 §2.2). REQ-022's own design
states this explicitly as its scope boundary ("the `admission` column transition **is**
the signal REQ-023 will read... this requirement's job is only to make that state
transition happen... REQ-023's later consumption point", REQ-022 §2.2's closing note).
There is no scheduled-job runner, cron, or queue anywhere in `apps/bot/src/**` — adding
one would be new infrastructure this requirement does not need, since the seat-freeing
event and the moment auto-promotion must react to it are the same database transaction.

Concretely: `promoteFromWaitlistIfEligible` (§3 below) is called with the *same* `tx`
handle `withdrawRegistration`'s `db.transaction(async (tx) => { ... })` callback already
holds — never a second, nested `db.transaction(...)` call. This is what makes the
promotion write and the withdrawal write atomic together: either both commit, or (on any
error) both roll back, and no external scheduler ever needs to notice "a seat freed" as a
separate, racy signal.

**Gating: promotion is only attempted when the withdrawn row's pre-withdrawal admission
was `'admitted'`.** `withdrawRegistration`'s step 1 read (REQ-022 §2.2) already captures
the row's `admission` value before the UPDATE. Withdrawing a `'requested'` or
`'waitlisted'` registration frees no seat, so `promoteFromWaitlistIfEligible` is not
called at all in that case — not merely called and found to be a no-op via the
capacity-full check (§2 below), but skipped outright, avoiding two extra `SELECT`s on the
overwhelmingly common non-admitted-withdrawal path. This is a new, explicit branch in
`withdrawRegistration`'s existing step sequence, inserted after step 4 (the UPDATE) and
its own step 5 (`writeAuditLog` for `registration.withdraw`):

```
withdrawRegistration's transaction, extended:
  ...steps 1-5 exactly as REQ-022 §2.2 (row lock, decide, UPDATE admission='withdrawn',
  writeAuditLog "registration.withdraw")...
  step 6 (NEW) — only when the row's admission read in step 1 was 'admitted':
    call promoteFromWaitlistIfEligible(tx, row.eventId, at)  (§3)
  step 7 (NEW) — return { kind: "withdrawn", promotion } instead of { kind: "withdrawn" },
    where `promotion` is the PromotionOutcome from step 6, or a fixed
    { kind: "not-attempted" } value when step 6 was skipped (admission read in step 1 was
    not 'admitted').
```

This changes `WithdrawOutcome`'s `"withdrawn"` member's shape (§4 below) — a targeted
extension of REQ-022's existing exported type, not a rewrite of it.

## 2. The two pure decisions

### 2.1 `isAutoPromotionHalted` — the T-24h check (`domain/event.ts`)

```
export function isAutoPromotionHalted(startsAt: Date, evaluationTime: Date): boolean;
```

Same "evaluation time is an explicit parameter, never the clock read inside the
function" discipline as `isFinished`/`isRegistrationOpen` (decisions/0006) — placed
alongside them in `domain/event.ts`, not in `registration.ts`, since it is a pure
property of an event's timing, not of any one registration.

**The rule, stated in prose only (never as an executable comparison), per this role's
zero-implementation-code rule:** compare the amount of time remaining before
`startsAt` (i.e. `startsAt` minus `evaluationTime`) against exactly 24 hours
(24 × 60 × 60 × 1000 milliseconds). When 24 hours or less remain — including the exact
instant of T-24h itself — auto-promotion is halted (result: `true`). When strictly more
than 24 hours remain, auto-promotion is allowed (result: `false`). This mirrors the
"strictly less than the boundary is open" convention `isRegistrationOpen` already
establishes for `registrationClosesAt`, applied to the halt side instead of the open
side: the boundary instant itself belongs to the *halted* state, not the *eligible* one.

Both stated acceptance criteria sit well clear of this boundary — AC1's event is 48h out
(halted = false, 48h > 24h) and AC2's is 12h out (halted = true, 12h ≤ 24h) — so no
acceptance criterion tests the exact 24h instant; the boundary convention above is stated
precisely anyway so `TEST-DESIGNER`/`BACKEND-DEV` never have to guess it.

### 2.2 `decidePromotionEligibility` — pure, no I/O (`domain/registration.ts`)

```
export interface PromotionEligibilityInput {
  eventStatus: "draft" | "published" | "cancelled";
  startsAt: Date;
  endsAt: Date;
  seatsLeft: number;
}

export type PromotionEligibility =
  | { ok: true }
  | { ok: false; reason: "event-not-eligible" }
  | { ok: false; reason: "halted-t24h" }
  | { ok: false; reason: "capacity-full" };

export function decidePromotionEligibility(
  input: PromotionEligibilityInput,
  evaluationTime: Date,
): PromotionEligibility;
```

First-match-wins table, same convention `decideWithdrawOutcome`/`decideRegistrationOutcome`
already establish (described here in prose, never as executable branching):

| # | Condition | Result |
|---|---|---|
| 1 | `eventStatus` is not `'published'`, OR `isFinished(endsAt, evaluationTime)` is true | `{ ok: false, reason: "event-not-eligible" }` — covers both explicit refusals the requirement names: "never promote into a cancelled or finished event" (a cancelled event has `eventStatus === 'cancelled'`; a `'draft'` event is included defensively even though the requirement's own precondition is "while the event is published" — draft events have no live waitlist to promote from in practice, but the check costs nothing and closes the gap structurally rather than by convention) |
| 2 | `isAutoPromotionHalted(startsAt, evaluationTime)` is true | `{ ok: false, reason: "halted-t24h" }` — AC2's rule |
| 3 | `seatsLeft <= 0` | `{ ok: false, reason: "capacity-full" }` — the atomic re-check: nothing to promote into if the seat is (still, or again) taken |
| 4 | Otherwise | `{ ok: true }` |

Row 3 is what makes running the promotion path twice for the same freed seat safe with
no new column — see §5.

## 3. `promoteFromWaitlistIfEligible` — the transactional actor (AC1, AC2, AC3, AC4, AC5, AC7)

```
export type PromotionOutcome =
  | { kind: "not-attempted" }
  | { kind: "event-not-found" }
  | { kind: "event-not-eligible" }
  | { kind: "halted-t24h" }
  | { kind: "capacity-full" }
  | { kind: "no-waitlist" }
  | { kind: "promoted"; registrationId: string; promotedUserId: string; qrToken: string };

export async function promoteFromWaitlistIfEligible(
  tx: DbClient["db"],
  eventId: string,
  evaluationTime: Date,
): Promise<PromotionOutcome>;
```

`tx` is always the same transaction handle the caller (`withdrawRegistration`, §0) is
already inside — this function never opens its own `db.transaction(...)`. `{ kind:
"not-attempted" }` is never returned by this function itself (mirroring
`decideRegistrationOutcome`'s own "not-found" precedent, REQ-020 §2.2) — it exists only
as the value `withdrawRegistration` substitutes when it skips calling this function
entirely (§0's gating).

Steps:

1. `SELECT id, status, starts_at, ends_at, capacity FROM events WHERE id = eventId FOR
   UPDATE` — the exact lock discipline `registerForEvent` (REQ-020 §3.2 step 2) already
   uses on this same table, reused here for the same reason: this is the row whose
   admitted-count a concurrent `registerForEvent` call for the *same* event is also about
   to read-then-write (AC4). No row found → return `{ kind: "event-not-found" }`
   (defensive; unreachable via the withdraw path since the row was just read moments
   earlier in the same transaction to obtain `eventId`, kept for the same "never assume,
   always guard" discipline this codebase's other domain functions already follow).
2. `SELECT count(*) FROM registrations WHERE event_id = eventId AND admission =
   'admitted'` (fresh, inside `tx`, same shape as `countAdmittedRegistrations` /
   `registerForEvent`'s own step 4, REQ-020 §3.2 step 4) → `admittedCount`. Compute
   `seatsLeft = computeSeatsLeft(event.capacity, admittedCount)` (unchanged, REQ-017 §1).
3. Call `decidePromotionEligibility({ eventStatus: event.status, startsAt: event.startsAt,
   endsAt: event.endsAt, seatsLeft }, evaluationTime)` (§2.2, pure). If not `ok`: return
   `{ kind: eligibility.reason }` — no further reads, no write, no audit row.
4. `SELECT id, user_id FROM registrations WHERE event_id = eventId AND admission =
   'waitlisted' ORDER BY created_at ASC, id ASC LIMIT 1 FOR UPDATE` — identical
   event/admission filter and `(created_at, id)` tie-break `getWaitlistPosition` already
   uses to rank waitlisted rows (REQ-021 §2.2/§2.3), here used to *select* rank 1 instead
   of counting rows ahead of a known target; `FOR UPDATE` because this row is about to be
   written. No row found (empty waitlist) → return `{ kind: "no-waitlist" }` — **no
   error**, satisfying AC3 directly.
5. `UPDATE registrations SET admission = 'admitted', qr_token = <a fresh
   generateQrToken() call> WHERE id = <the row found in step 4>` — the `SET` clause names
   only these two columns; `created_at`/`source`/`invited_by_user_id`/etc. are left
   untouched, same "never in the SET clause, never touched" discipline REQ-022 §3.1
   already establishes for its own row-reuse UPDATE.
6. `writeAuditLog(tx, { actorUserId: null, action: "registration.promote", entity:
   "registration", entityId: <the promoted row's id>, payload: { eventId }, at:
   evaluationTime })` — `actorUserId: null` because this is a system-initiated action with
   no human actor to attribute (the exact precedent `writeAuditLog`'s own header comment
   already documents, first exercised by REQ-018's S5 rework). Exactly one call, reached
   only on this one branch, same transaction as step 5's UPDATE — this is what makes
   **AC5** ("each promotion writes exactly one audit_log row") true by construction, the
   same argument REQ-022 §2.2 already makes for `registration.withdraw`.
7. Return `{ kind: "promoted", registrationId: <promoted row's id>, promotedUserId:
   <promoted row's user_id>, qrToken: <the value written in step 5> }`.

### 3.1 Why this never over-admits under a concurrent registration (AC4)

Both `promoteFromWaitlistIfEligible` (step 1 above) and `registerForEvent` (REQ-020 §3.2
step 2) take `SELECT ... FROM events WHERE id = eventId FOR UPDATE` as the *first*
database operation touching a shared row, inside their own transaction, before either one
computes `seatsLeft`. Postgres serializes the two transactions on that lock: whichever
commits first releases the lock, and the second transaction's own step 1 blocks until
then — so its subsequent `admittedCount` read (step 2 here / REQ-020 §3.2 step 4 there)
is always fresh relative to the other transaction's completed write, never a stale
read-then-write race. This is the exact same argument REQ-020's own design already makes
for two concurrent `registerForEvent` calls on the last seat; promotion reuses it
unchanged rather than inventing a second locking scheme. AC4's automated concurrency test
(≥20 iterations racing a withdrawal-triggered promotion against a fresh registration for
the same event) exercises this lock, not new logic — there is no separate "reserve the
seat" step anywhere in this design that could be skipped.

**No deadlock between the two transactions:** `withdrawRegistration` locks its own
withdrawn registration's row first (REQ-022 §2.2 step 1), then (via this function) the
`events` row, then a *different* registration row (the waitlisted candidate, step 4
above). `registerForEvent` locks the `events` row first, then its own caller's
`(event_id, user_id)` row (REQ-020 §3.2 step 3) — always a third, distinct registration
row (the registering person's own, never the withdrawn row or the waitlisted candidate,
since those belong to two other people). The only row ever contended by *both*
transactions is `events` — a single shared resource cannot produce a lock cycle, so no
new deadlock potential is introduced.

## 5. Design question 2 — at-most-once notification, no new column (resolved)

**No schema change, no new "send-marker" column.** The mechanism is the row's own
`admission` transition itself, exactly the same proof-of-absence REQ-022 §2.2 already
established for seat-freeing ("the `admission` column transition **is** the signal... no
new 'seats freed' event, flag, or table is introduced").

Walking through what "running the promotion path twice for the same freed seat" actually
means against this design, per this task's own framing:

- **A given waitlisted registration row can be selected by step 4 (§3) at most once,
  ever.** The moment step 5's `UPDATE` commits, that row's `admission` is `'admitted'` —
  step 4's `WHERE admission = 'waitlisted'` filter can never select it again, on any later
  call, by any caller. There is no code path that re-reads a row as `'waitlisted'` after
  this design has already promoted it; the state transition is one-way for the purposes
  of this function (nothing in this design's scope ever moves a row back to
  `'waitlisted'`).
- **A second invocation of `promoteFromWaitlistIfEligible` for the same event, with no
  intervening seat-freeing event, finds `seatsLeft <= 0`** (§2.2 row 3): the first call's
  step 5 already raised `admittedCount` back up to `capacity`, so the second call's own
  step 2 recomputes `seatsLeft` as `0` (or negative, impossible in practice but handled
  identically) and refuses at row 3 of §2.2 before ever reaching step 4's selection. It
  therefore promotes nobody and calls `writeAuditLog`/sends nothing — **AC7** ("running
  the promotion path twice for the same freed seat sends exactly one notification") holds
  because the second run takes no action at all, not because a marker suppressed a
  duplicate action.
- If a second call *did* somehow occur against a genuinely different, second freed seat
  (a second withdrawal), it would correctly promote the *next* longest-waiting person —
  a distinct registration, a distinct notification, which is the intended behavior, not a
  duplicate.

**Explicit scope boundary, stated per this task's instruction rather than left implicit:**
this reasoning covers "the promotion path re-run without a fresh transaction commit in
between" (the literal shape of AC7's test). It does **not** cover a crash between this
function's transaction committing and the notification actually being sent over the
Telegram API in the handler (§6.2) — that is a genuine, separate at-least-once-delivery
gap this design does not close, because closing it durably needs exactly the kind of
persistent, retryable outbox/idempotency ledger REQ-025 is scoped to build. **REQ-025,
when built, should key its ledger on `(registration_id, notification_kind)` and treat a
row already in `admission = 'admitted'` with no corresponding "sent" ledger entry as the
signal to retry the send — replacing this design's implicit, DB-state-only mechanism,
never duplicating it with a second, parallel marker.** This gap is named explicitly here
so it is not silently assumed solved.

## 6. Notification mechanism (AC6)

### 6.1 New read: `getUserForNotificationById` (`domain/user.ts`)

```
export interface UserForNotification {
  tgId: bigint | null;
  lang: string | null;
  chapterDefaultLang: string | null;
  blocked: boolean;
}

export async function getUserForNotificationById(
  db: DbClient["db"],
  userId: string,
): Promise<UserForNotification | null>;
```

Needed because the promoted person is a *different* Telegram user than the one whose
`ctx` triggered the withdrawal — every existing lookup in `domain/user.ts`
(`getFlowUserByTgId`, `getUserWithChapterByTgId`) resolves *by* `tg_id`, keyed off
`ctx.from.id` of the acting caller; none resolves a user's own `tgId`/`lang` starting
*from* an internal `users.id`, which is exactly what `promotedUserId` (§3 step 7) is.
Same join shape as `getFlowUserByTgId` (`users` left-joined to `chapters` for the
default-lang fallback), filtered by `users.id` instead of `users.tg_id`; a plain read, no
lock (the authoritative write already happened inside `promoteFromWaitlistIfEligible`'s
transaction, which has already committed by the time this is called — see §6.2 step 1).

### 6.2 Where the send happens — `handlers/withdraw.ts`'s confirm callback, post-commit

Domain code stays framework-free (decisions/0004: no grammY import in `domain/**`), so
the actual Telegram send is composed in the handler, not inside
`promoteFromWaitlistIfEligible`. This follows the exact pattern
`handlers/registration.ts`'s own callback already uses: display-data reads happen *after*
`registerForEvent`'s transaction has committed, never inside its atomicity boundary
(REQ-020 §7.1's own comment: "display data... is fetched only when actually needed,
after the transaction has already committed").

Extending `makeWithdrawConfirmCallbackHandler` (REQ-022 §4.2), after step 2 (the
`withdrawRegistration` call) and before/alongside step 4 (replying to the withdrawer):

1. If `outcome.kind === "withdrawn"` and `outcome.promotion.kind === "promoted"`:
   - `getUserForNotificationById(db, outcome.promotion.promotedUserId)` → the promoted
     person's `tgId`/`lang`. If the row has a null `tgId` (defensive — every row reaching
     `'admitted'` was created through a Telegram flow that always sets `tgId`, per
     `resolveOrCreateUser`'s own invariant, REQ-014; kept as a guard rather than an
     assumption, same no-speculation discipline this codebase's other reads already
     apply): skip the send, do not error the withdrawer's own reply path.
   - Resolve the promoted person's language via `resolveLang` (existing function,
     unchanged) from their own `lang`/`chapterDefaultLang` — **never** the withdrawer's
     `lang`, since these are two different people who may have two different language
     preferences.
   - Compose the promotion message (§6.3's new catalog keys) using the *promoted* row's
     own event title/date-time (fetched via `getEventByIdWithChapterTimezone`, unchanged,
     same as `registration.ts`'s own admitted-outcome composition) and
     `outcome.promotion.qrToken`.
   - **(SECURITY-REVIEWER Step 2c fix, MINOR)** S10's own sentence has a second clause
     beyond the transactional/broadcast_opt_in distinction: "`blocked` users are skipped
     in both cases." `getUserForNotificationById` therefore also projects `users.blocked`,
     and this step skips the send (same shape as the null-`tgId` guard above, silently, no
     effect on the withdrawer's own reply) when the resolved promoted user's
     `blocked === true`. This applies only to the notification send — the promotion
     itself (admission, the audit row, seat accounting) already committed inside
     `promoteFromWaitlistIfEligible`'s transaction before this step ever runs, and is
     unaffected by the person being blocked.
   - Send via `ctx.api.sendMessage(<promoted person's tgId>, <composed text>)` — grammY's
     `Context.api` is bound to the bot instance, not to the current update's chat, so it
     can address any `chat_id`/Telegram user id, not only the caller who triggered this
     callback. This is the one new "send to someone other than the current `ctx`'s own
     user" call site in this codebase — flagged explicitly since no existing handler does
     this today (checked directly: every `ctx.reply(...)` call in
     `apps/bot/src/handlers/*.ts` replies to the same chat the update came from).
2. This send is **transactional** in the PRD-9/S10 sense — it is sent unconditionally,
   never gated on the promoted person's `broadcast_opt_in` (which governs only marketing
   sends, S10) — there is no `broadcast_opt_in` check anywhere in this step, by omission,
   matching S10's own table ("waitlist promotion... is always sent, ignoring
   broadcast_opt_in").
3. This send never blocks or affects the withdrawer's own reply (step 4 of REQ-022 §4.2,
   unchanged) — a failure to notify the promoted person (e.g. they blocked the bot) is not
   surfaced to the withdrawer at all; this design does not add error handling around the
   `ctx.api.sendMessage` call beyond letting the framework's own promise-rejection
   behavior apply, since no acceptance criterion in scope specifies a particular
   send-failure UX.

### 6.4 Open gap, flagged rather than silently resolved: no QR *delivery* mechanism exists yet anywhere in this codebase

Checked directly: `registration.ts`'s own `"admitted"` reply (the direct-registration
confirmation, not promotion) **does not render or send `qr_token` in any form today** —
`composeRegistrationReply`'s `"admitted"` case is prefix/title/date-time/what-next only,
with no QR value, no QR image, no deep link. `checkin.ts`'s own header comment
independently confirms "no qr_token is read" anywhere on the staff side either. So "the
promoted person is notified with their QR" (this requirement's own phrase) is being
satisfied here the same way the *direct*-admission path would satisfy it today if asked
to — by including the raw `qr_token` string value as plain text (§6.3's `qrLabel` line) —
because no requirement in scope (this one or any prior one) has yet introduced actual QR
*image* rendering or a scannable deep link, and inventing one here would be new scope
this requirement's acceptance criteria do not ask for. **This is a pre-existing gap in
the direct-registration path too, not something REQ-023 introduces** — flagged as a
finding for `ORCH` to file as its own issue (a future requirement should give both the
direct-admission and the promotion paths a single, shared "render/send the ticket" QR
mechanism, rather than each inventing its own), not silently patched over here.

## 7. Design question 3 — T-24h visibility (resolved: existing surface, no new UI)

**The existing `/events` command (REQ-017, `handlers/event.ts`'s
`makeEventsListHandler`) already makes a T-24h-halted freed seat visible, with zero code
change.** Checked `apps/bot/src/domain/event.ts`'s `computeSeatsLeft`/`buildSeatsLine`
and their call site in `handlers/event.ts` directly, per this task's instruction:

- `computeSeatsLeft(capacity, admittedCount)` and `buildSeatsLine(seatsLeft)` are
  recomputed **live**, on every `/events` call, from a fresh `countAdmittedRegistrations`
  read (REQ-017 §1's own "computed, never stored, never cached" discipline, restated —
  this design adds no caching anywhere near these functions).
- The instant a withdrawal frees a seat and `promoteFromWaitlistIfEligible` refuses to
  fill it (halted-t24h, or any other refusal reason), `admittedCount` for that event stays
  one lower than `capacity` — so the very next `/events` call for that chapter shows that
  event's `seatsLine` as `{ kind: "seatsLeft", count: N }` (`N ≥ 1`) via the exact same
  code path any other under-capacity event already goes through, not a new one.
- `/events` is available to **any chapter member**, not gated by
  `checkOrganizerForChapter`/`requireOrganizerForChapter` (REQ-017 §0's own reuse
  decision, confirmed at `handlers/event.ts` line ~409: `resolveActingUser` is used only
  for its `chapterId`, no organizer check applied). An organizer is, structurally, also a
  member of their own chapter, so they already have this surface available with no
  separate "organizer view" needed.

**Named explicitly as an open question (not silently resolved as "fully sufficient"):**
`/events`' `seatsLeft` count does not, by itself, distinguish "nobody has registered for
this seat yet" from "a seat froze at T-24h with a non-empty waitlist behind it" — an
organizer seeing "1 seat left" has no signal from this surface alone that a waitlist
exists and manual promotion (Release 3, out of scope here) is warranted. Checked
`handlers/event.ts`'s `/event_edit` (`formatEventDump`) directly too: it dumps raw event
fields (title, capacity, dates, status, etc.) but **never** an admitted count, a
seats-left figure, or a waitlist size — so today's organizer-facing edit view gives even
less visibility than `/events` does. Closing this precisely (e.g., an organizer-facing
"N seats left, M waiting" combined figure) is left as a recommendation for a future
requirement (most naturally, whatever Release 3 requirement builds the manual-promotion
UI this requirement's own T-24h halt defers to) rather than invented here — no acceptance
criterion in scope asks for a new UI element, only that the freed seat be "visible to the
organizer somewhere," which `/events` already satisfies today, as-is.

## 8. Open questions (not silently resolved)

1. **QR delivery mechanism** (§6.4) — this design reuses the only thing that exists today
   (the raw `qr_token` string), flagged as a pre-existing gap shared with the
   direct-registration path, not invented or fixed here.
2. **T-24h visibility precision** (§7) — `/events`' seats-left count is sufficient to
   satisfy "visible to the organizer somewhere" as literally stated, but does not by
   itself signal "and there's a waitlist behind it" — left for a future requirement.
3. **Send-failure UX for the promotion notification** (§6.2 step 3) — not specified by any
   acceptance criterion in scope; this design lets it fail silently relative to the
   withdrawer's own reply rather than inventing a retry/error-surface policy.
4. **REQ-025's future ledger key** (§5's closing paragraph) — a recommendation for that
   future design to consider, not binding on it, since REQ-025 is not designed yet.
