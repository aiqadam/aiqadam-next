# REQ-020 — Registration for an open event with atomic capacity enforcement and `qr_token` issuance

**Requirement:** second slice of PRD 14 build-order step 3, PRD 11a critical-path story
B2 ("Take a seat at an open event"). Implements PRD FR-4's open-event row
(`requires_invite=false`, `requires_approval=false` → admitted if seats remain, else
waitlisted) and the `qr_token` half of PRD FR-14. depends_on: REQ-017, REQ-019.

**Release-1 scope boundary, restated:** PRD FR-4's other three rows
(`requires_approval`, either `requires_invite` case) are Release 2 and are **not**
implemented here. This design reads `events.requires_invite`/`requires_approval` and
refuses clearly rather than silently admitting — it does not implement an invite or
approval flow.

**Surface:** `apps/bot/**` (bot requirement).

**No schema change.** Checked `apps/bot/src/db/schema.ts` line-by-line against every
column this design needs: `registrations.qr_token` (nullable `text`, already carries a
`uniqueIndex`) and `registrations.source` (`NOT NULL text`) **already exist**, added by
REQ-011's schema. `registrations.admission` (`requested|waitlisted|admitted|rejected|
withdrawn`), the `uq_registrations_event_user` unique index, `events.requires_invite`/
`requires_approval`/`registration_closes_at`/`capacity`, and `users.pending_source`
(REQ-016) all already exist. **`DATA-DESIGNER` is not needed for this requirement** —
this is a `CODE-DESIGNER`-only Step 1, same as REQ-017's precedent (§10 confirms this
explicitly, mirroring REQ-017.md §10's own confirmation paragraph).

**Files this design expects:**
- `apps/bot/src/domain/registration.ts` (**new**) — everything registration-specific:
  the pure outcome decision, the atomic transactional write, token generation, source
  resolution (§2–§5)
- `apps/bot/src/domain/event.ts` (existing) — reused unchanged: `computeSeatsLeft`,
  `isRegistrationOpen`, `isFinished`, `countAdmittedRegistrations`, `getPendingSource`,
  `getEventByIdWithChapterTimezone`, `buildEventCardContent` (via its already-computed

- `apps/bot/src/domain/eventAuthorization.ts` (existing) — `resolveActingUser` reused
  unchanged to resolve the tapping user's `id`, same mechanism REQ-017 §4.2 already

- `apps/bot/src/handlers/registration.ts` (**new**) — the `register:<eventId>` callback

  send gains a `reply_markup` (the Register button), replacing REQ-017's inert CTA line

## 0. Reuse decisions and scope boundaries, stated up front

- **The only entry point to a full event card today is REQ-017's `/start` deep-link
  resolution** (`resolveEventDeepLink` in `handlers/start.ts`) — REQ-017 §0 deliberately
  renders `/events`' upcoming list as plain rows with no per-row card. This design does
  not add a second card-rendering surface; the Register button is attached at that one
  existing send site. (Flagged as an open question, §8.1, whether a future requirement
  should add a second entry point — not decided here.)
- **The button is always shown on a card that renders at all.** A card only renders for
  a published, not-yet-finished event (REQ-017/REQ-016's existing gate on
  `resolveEventDeepLink`, unchanged). This design does **not** pre-compute
  "is registration actually still possible" before deciding whether to draw the button —
  it always draws it, and the full outcome decision (§2) runs fresh, inside the atomic
  transaction, at the moment the button is pressed. This keeps card rendering cheap (no
  extra query per render, consistent with REQ-017 §8 open question 5's load-justified
  precedent) and keeps exactly one place (§2's `decideRegistrationOutcome`) that decides
  what happens — never two copies of the same branching logic that could drift apart.
- **Registration is not gated on profile completeness.** Neither the requirement text
  nor any acceptance criterion mentions REQ-019's profile fields. Flagged explicitly as
  an open question (§8.2), not silently assumed.
- **The register callback needs no additional consent check.** Reaching the card at all
  already required `consent_pd_at` to be non-null (REQ-016 rework, `resolveEventDeepLink`
  §-level gate, unchanged). A `registrations` row stores no new personal data beyond
  `user_id` — S1 is already satisfied by the existing gate the card sits behind.

## 1. Atomic capacity mechanism — the security/correctness core (S7, AC1)

### 1.1 Chosen approach: lock the `events` row with `SELECT ... FOR UPDATE`, inside one `db.transaction`, at Postgres's default `READ COMMITTED` isolation

Concretely, `registerForEvent` (§3) runs, inside a single `db.transaction(async (tx) => { ... })`:

1. `SELECT ... FROM events WHERE id = $eventId FOR UPDATE` (the event's full row, same
   column set `getEventById` already reads) — takes an exclusive row lock on that one
   `events` row for the lifetime of the transaction.
2. `SELECT ... FROM registrations WHERE event_id = $eventId AND user_id = $userId LIMIT 1`
   — any existing registration for this (event, user) pair.
3. `countAdmittedRegistrations(tx, eventId)` — the existing REQ-016 function, called
   against `tx` (same "either `db` or a transaction's `tx`" convention `writeAuditLog`
   already documents).
4. Decide the outcome (§2, pure, no I/O).
5. If the outcome writes a row (`admitted` or `waitlisted`, §2): one `INSERT INTO
   registrations (...)` (§3.2) + one `INSERT INTO audit_log (...)` (§6), same
   transaction.
6. Transaction commits (or the function returns before any write, for every non-writing
   outcome — nothing to roll back).

**Why this serializes correctly.** Step 1's `FOR UPDATE` lock is acquired on the single
`events` row identified by `eventId`. Postgres blocks any *second* transaction's own
`SELECT ... FOR UPDATE` against that same row until the first transaction commits or
rolls back. So two concurrent `registerForEvent` calls for the *same* event — whether
from two different users racing for the last seat, or the same user double-tapping — are
forced to run steps 2–5 one at a from a **strictly serial** order relative to each other:
the second transaction's `countAdmittedRegistrations` (step 3) only ever executes after
the first transaction's `INSERT` (step 5) has already committed, so it observes the
already-updated count. This is what makes "check-and-write atomic, not read-then-write"
true here: the *check* (steps 2–4) and the *write* (step 5) are not literally one SQL
statement, but no other transaction can interleave its own check between this
transaction's check and its write, because the lock is held across the whole span.
Registrations for *different* events never contend — the lock is per-event-row, not
global — so this adds no cross-event bottleneck.

### 1.2 Why this over the two alternatives the task named

- **`SERIALIZABLE` isolation + retry-on-conflict:** correct, but Postgres surfaces a
  concurrent conflict as a `40001 serialization_failure` error raised to the *losing*
  transaction, which the caller must catch and retry. This codebase has **no existing
  retry-on-database-error pattern anywhere** (confirmed: no other `domain/*.ts` file
  catches a Postgres error code and re-runs its own transaction) — adding one here would
  be new, cross-cutting infrastructure for a single call site, at a stated peak load of
  0.06 requests/second (PRD 1) where the actual contention this guards against is rare in
  practice and only needs to be *correct*, not fast. `FOR UPDATE` produces the same
  correctness guarantee (§1.1) by making the second transaction **wait**, not **fail** —
  no retry logic anywhere, nothing new for `TEST-RUNNER`/`SECURITY-REVIEWER` to reason
  about beyond "the lock held."
- **A single `INSERT ... SELECT ... WHERE (SELECT count(*) ...) < capacity` conditional
  insert:** at Postgres's default `READ COMMITTED` isolation, a bare conditional
  subquery inside one `INSERT` statement does **not** by itself prevent two concurrent
  statements from each evaluating `count(*) < capacity` as true before either commits —
  the classic lost-update race S7's negative case names directly. Making a single
  statement genuinely safe would require folding the same `FOR UPDATE` lock into that
  statement's own subquery, which is expressible in raw SQL but not idiomatically in
  Drizzle's query builder (confirmed: Drizzle's `insert().select(...)` chain has no
  documented row-locking hook on the source query). The two-step form in §1.1 uses
  exactly Drizzle's own query-builder surface — `db.select(...).from(events).where(...)
  .for("update")` is a real, typed method (`PgSelectBuilder.for(strength, config)`,
  confirmed present in `node_modules/drizzle-orm/pg-core/query-builders/select.d.ts`) —
  with no raw SQL needed, matching every other domain module in this codebase
  (decisions/0004's framework-free style, and no `sql\`...\`` escape hatch used anywhere
  in `domain/event.ts`, `domain/venue.ts`, or `domain/eventStaff.ts` today).

### 1.3 Reads that participate in the atomicity boundary vs. reads that don't

Steps 1–5 above (and only those) run inside the locked transaction. Everything the
confirmation *message* needs beyond the bare outcome — the chapter-local date/time text,
the venue name (§6.4) — is fetched **after** the transaction has already committed, via
the existing `getEventByIdWithChapterTimezone` + `getVenueById` (both read-only, both
unchanged). Display formatting has no bearing on whether two transactions raced for the
same seat, so it does not need to run inside the lock — keeping the locked section as
short as possible (steps 1–5 only) minimizes how long any second, blocked registrant
actually waits.

## 2. The pure outcome decision (AC1, AC2, AC4, AC6)

### 2.1 Input shape

```
export interface RegistrationDecisionInput {
  existingAdmission: "requested" | "waitlisted" | "admitted" | "rejected" | "withdrawn" | null;
  eventStatus: "draft" | "published" | "cancelled";
  requiresInvite: boolean;
  requiresApproval: boolean;
  registrationClosesAt: Date | null;
  endsAt: Date;
  seatsLeft: number;
}

export type RegistrationOutcome =
  | { kind: "not-found" }
  | { kind: "already-registered"; admission: "requested" | "waitlisted" | "admitted" | "rejected" | "withdrawn" }
  | { kind: "event-cancelled" }
  | { kind: "event-finished" }
  | { kind: "registration-closed" }
  | { kind: "requires-invite" }
  | { kind: "requires-approval" }
  | { kind: "admitted" }
  | { kind: "waitlisted" };
```

### 2.2 The rule, stated as a first-match-wins table (never as executable branching)

| # | Condition | Result |
|---|---|---|
| 1 | `existingAdmission` is not null | `{ kind: "already-registered", admission: existingAdmission }` |
| 2 | `eventStatus === "cancelled"` | `{ kind: "event-cancelled" }` |
| 3 | `isFinished(endsAt, evaluationTime)` is true (reused from `domain/event.ts`) | `{ kind: "event-finished" }` |
| 4 | `isRegistrationOpen(registrationClosesAt, evaluationTime)` is false (reused) | `{ kind: "registration-closed" }` |
| 5 | `requiresInvite === true` | `{ kind: "requires-invite" }` |
| 6 | `requiresApproval === true` | `{ kind: "requires-approval" }` |
| 7 | `seatsLeft > 0` (computed via reused `computeSeatsLeft`) | `{ kind: "admitted" }` |
| 8 | (none of the above) | `{ kind: "waitlisted" }` |

Row 1 is checked **before every other row**, unconditionally — a person who already has
a row for this event always sees their current status, regardless of what state the
event itself is in now (an event could have since closed/cancelled/finished after they
registered; that doesn't change what "current status" means for AC2). Rows 2–4 are event
lifecycle gates (closed/cancelled/finished), checked before rows 5–6 so a
requires-invite event that has also since closed still reports the more fundamental
"closed" reason first — this ordering choice is arbitrary between rows 2–6 (nothing in
the requirement ranks them relative to each other) but is stated explicitly here so
`BACKEND-DEV` implements one fixed order, not an unspecified one.

### 2.3 Signature (pure, no I/O — unit-testable without a DB, exactly REQ-017's `computeSeatsLeft`/`isRegistrationOpen` discipline)

```
export function decideRegistrationOutcome(
  input: RegistrationDecisionInput,
  evaluationTime: Date,
): RegistrationOutcome;
```

`not-found` (§2.1's union member) is never returned by this pure function — it is
produced only by `registerForEvent` (§3) itself, for the defensive case where the
locked `SELECT` in step 1 finds no row at all (an event id that no longer exists; the
same "unreachable in practice, guarded anyway" discipline `createEvent`/`createVenue`
already establish elsewhere in this codebase).

## 3. `registerForEvent` — the atomic write (AC1, AC2, AC3, AC5, AC6, AC7)

### 3.1 Signature

```
export async function registerForEvent(
  db: DbClient["db"],
  userId: string,
  eventId: string,
  evaluationTime: Date,
): Promise<RegistrationOutcome & { registrationId?: string; qrToken?: string }>;
```

`registrationId`/`qrToken` are present only when `kind` is `"admitted"` (both) or
`"waitlisted"` (`registrationId` only — §4's closing note on why a waitlisted row never
gets a token). Every other `kind` carries neither.

### 3.2 What it does, as an ordered list (never as `if`/`return` code)

1. Open `db.transaction(async (tx) => { ... })`.
2. `SELECT` the event's full row (same column set as `getEventById`) from `events`
   `WHERE id = eventId`, with `.for("update")` — the lock from §1.1. If no row: return
   `{ kind: "not-found" }` immediately (transaction has nothing to commit).
3. `SELECT admission FROM registrations WHERE event_id = eventId AND user_id = userId
   LIMIT 1` against `tx` — `existingAdmission` (or `null`).
4. `countAdmittedRegistrations(tx, eventId)` (reused, called against `tx`).
5. `computeSeatsLeft(event.capacity, admittedCount)` (reused).
6. Build a `RegistrationDecisionInput` (§2.1) from the fetched event row + the count, and
   call `decideRegistrationOutcome` (§2.3, pure — no `tx` passed to it).
7. If the outcome's `kind` is anything other than `"admitted"` or `"waitlisted"`: return
   it unchanged. Nothing is written.
8. Otherwise (`"admitted"` or `"waitlisted"`):
   a. `getPendingSource(tx, userId)` (reused, REQ-016) → `pendingSource`.
   b. `resolveRegistrationSource(pendingSource)` (§5) → `source`.
   c. When the outcome is `"admitted"`: `generateQrToken()` (§4) → `qrToken`. When the
      outcome is `"waitlisted"`: `qrToken` stays `null` — a waitlisted registration is
      not yet admitted and has nothing to check in with; assigning one is REQ-021/the
      waitlist-promotion requirement's own concern, not this one's.
   d. `INSERT INTO registrations (event_id, user_id, admission, source, qr_token)
      VALUES (eventId, userId, outcome.kind, source, qrToken)` against `tx`, `RETURNING
      id`.
   e. If `pendingSource` was non-null: `clearPendingSource(tx, userId)` (§5.2) — the
      REQ-016 schema comment's own stated contract ("...until REQ-020 copies it into
      registrations.source and clears this back to NULL").
   f. `writeAuditLog(tx, { actorUserId: userId, action: outcome.kind === "admitted" ?
      "registration.admit" : "registration.waitlist", entity: "registration", entityId:
      <the inserted row's id>, payload: { eventId }, at: evaluationTime })` — exactly
      once, same transaction as the insert (§6 elaborates the AC7/S8 reasoning for
      writing this on *both* outcomes, not admitted alone).
   g. Return `{ kind: outcome.kind, registrationId: <id>, qrToken }` (qrToken omitted /
      undefined for `"waitlisted"`).

No step above retries, catches a database error code, or loops. The only thing that can
make step 2's `SELECT ... FOR UPDATE` take noticeably long is waiting behind another
transaction already holding the same event's lock — never a business-logic retry.

## 4. `qr_token` generation (S4, AC3)

### 4.1 Signature

```
export function generateQrToken(): string;
```

### 4.2 Exact rule (stated in prose, not as code)

Calls Node's built-in CSPRNG — `randomBytes` from the `node:crypto` module (never
`Math.random`, never a counter, never a hash of `userId` or any other predictable
input) — requesting **32 bytes** (256 bits, well clear of S4's ≥128-bit / ≥16-byte
floor, with headroom named explicitly rather than the exact minimum), then hex-encodes
the result to a 64-character string. This is the entire function: one CSPRNG call, one
encoding step, no loop, no parameters, no I/O.

`git grep -n "Math.random" apps/bot/src` must return nothing that participates in
token generation anywhere in this design — `generateQrToken` is the only place a token
is ever produced, and it never appears elsewhere in this file or `handlers/
registration.ts`.

### 4.3 Uniqueness

`registrations.qr_token` already carries `uniqueIndex("registrations_qr_token_unique")`
(REQ-011 schema, unchanged) as the durable backstop. At 32 random bytes the collision
probability across even a lifetime of this project's stated scale (PRD 1: ~1,000 users,
~10 events/year) is astronomically below any threshold worth engineering a
retry-on-collision loop for — flagged explicitly as an open question (§8.3) rather than
silently deciding whether `BACKEND-DEV` should add one anyway, since "insert fails on
unique violation" is a real, if vanishingly unlikely, path this design does not specify
a recovery step for.

### 4.4 Encoding for the check-in deep link (S4, PRD FR-14)

The value this function returns **is** the token stored in `qr_token` — plain, not
pre-formatted. The `?start=ci_<qr_token>` deep-link payload the requirement names is
assembled only where it is actually consumed: `apps/bot/src/domain/event.ts`'s
`parseStartPayload` currently recognizes only the `e_` prefix (REQ-016 §6.2) and has no
`ci_` branch yet — confirmed by reading it (§6 of this file); building or consuming
that payload shape is explicitly out of this requirement's scope (REQ-026 renders the
QR image that encodes it; REQ-028/029 parse it at check-in). This design produces and
stores the raw token only.

## 5. Source resolution and `pending_source` clearing (AC5)

### 5.1 `resolveRegistrationSource`

```
export function resolveRegistrationSource(pendingSource: string | null): string;
```

Rule, stated in prose: returns `pendingSource` unchanged when it is not `null`; returns
the literal string `"direct"` when `pendingSource` is `null`. Nothing else — no
allow-list, no validation of the channel string's shape (REQ-016 §6.2 already leaves the
channel free-text, unvalidated against a closed vocabulary — this function does not
add a validation this codebase's own upstream design already deliberately omitted).

`"direct"` is the value written for anyone who reaches the Register button without ever
having opened a channel-suffixed deep link — i.e. every registration today, since the
only card entry point (§0) is the deep link itself, but a channel suffix on that link is
optional (`parseStartPayload`'s `channel: string | null`). No requirement or decision
record names a canonical "no channel" sentinel, so `"direct"` is chosen here as this
design's own explicit answer, not silently left for `BACKEND-DEV` to invent case-by-case.

### 5.2 `clearPendingSource`

```
export async function clearPendingSource(db: DbClient["db"], userId: string): Promise<void>;
```

One `UPDATE users SET pending_source = NULL WHERE id = userId`. Same shape as the
existing `setPendingSource` (`domain/event.ts`), called only from inside
`registerForEvent`'s own transaction (§3.2 step 8e), and only when a value was actually
present — an unconditional clear would be harmless too (setting `NULL` to `NULL` is a
no-op), but §3.2 states the condition explicitly so the intent (this write exists to
consume a value that was there) is not left implicit.

## 6. Why an `audit_log` row is written on *both* `admitted` and `waitlisted` (AC7, S8)

AC7's own text is scoped to admission ("Each admission writes exactly one audit_log
row"). `security-invariants.md` S8 is worded more broadly ("every status change writes
exactly one AuditLog row"). A new `registrations` row moving from "did not exist" to
`waitlisted` is itself a status change under S8's own wording, even though AC7's literal
text does not test that branch. This design resolves the two readings by writing exactly
one `audit_log` row for **every** row `registerForEvent` inserts, regardless of which of
the two writing outcomes produced it (§3.2 step 8f: `action` is `"registration.admit"`
for `admitted`, `"registration.waitlist"` for `waitlisted"`) — this satisfies AC7's
literal requirement (an admission always gets exactly one row) without contradicting
S8's broader one, and without inventing a case where a status change is deliberately
left unaudited. Flagged in §8.4 as a reading `SECURITY-REVIEWER` should confirm rather
than a silent assumption.

Every non-writing outcome (`already-registered`, `event-cancelled`, `event-finished`,
`registration-closed`, `requires-invite`, `requires-approval`, `not-found`) writes **no**
audit row — nothing changed, so there is nothing to log (mirrors this codebase's own
existing discipline: `writeAuditLog` is only ever called from inside a mutation
function, never from a pure refusal path, per `domain/auditLog.ts`'s own header note).

## 7. Handler and card wiring (all ACs — the actual entry point)

### 7.1 `apps/bot/src/handlers/registration.ts` (new)

```
export const REGISTER_CALLBACK_PATTERN = /^register:(.+)$/;
```

A callback-query handler, registered in `index.ts` via `bot.callbackQuery
(REGISTER_CALLBACK_PATTERN, ...)`, following the exact convention `CHAPTER_CALLBACK_
PATTERN`'s handler already uses in `handlers/start.ts` (re-`.exec()` the pattern against
`ctx.callbackQuery?.data ?? ""` to recover the captured `eventId`, `await
ctx.answerCallbackQuery()` on every path). Steps, in prose:

1. Recover `eventId` from the callback data; if the pattern somehow doesn't match
   (defensive, unreachable in practice — Telegram only ever calls a registered handler
   with data its own pattern matched), answer the callback and stop.
2. `resolveActingUser(db, ctx.from.id)` (reused, `domain/eventAuthorization.ts`, no
   organizer check needed — every role may register).
3. If `null` (no `users` row — defensive; unreachable via the normal path since a
   deep-link handler already created one before ever showing a card): answer the
   callback, reply with a generic "please /start first" text (reusing whatever generic
   no-user copy already exists, e.g. the pattern `event.notAuthorized`/`checkin.
   notAuthorized` already establish for this exact "no user row" case elsewhere), stop.
4. `registerForEvent(db, actingUser.id, eventId, new Date())` (§3 — the current instant
   read here, in the handler, never inside the domain function itself, per
   decisions/0006).
5. `answerCallbackQuery()`.
6. Compose the reply text from `outcome.kind` (§7.2) and `ctx.reply(...)` it.

### 7.2 Reply composition per outcome (content shape — AC2, AC4, AC5, AC6)

| `outcome.kind` | Message shape |
|---|---|
| `admitted` | `registration.confirmedPrefix` + event title + chapter-local date/time text + venue name (all three sourced from `getEventByIdWithChapterTimezone` + `getVenueById`, fetched after the transaction, §1.3) + `registration.whatNext` (a fixed "what happens next" line naming that a QR/check-in code exists — not rendered here, REQ-026's scope) |
| `waitlisted` | `registration.waitlistedPrefix` + event title + date/time. Deliberately minimal — REQ-021 owns the full waitlist-position UX; this is only the "not admitted, but you're recorded" floor the requirement's own scope note allows. |
| `already-registered` | `registration.alreadyRegisteredPrefix` + a status label resolved from `outcome.admission` via a fixed lookup table (`registration.statusAdmitted` / `statusWaitlisted` / `statusRequested` / `statusRejected` / `statusWithdrawn`, one catalog string per `admission` enum value — a table, not a computed string) + event title + date/time |
| `event-cancelled` | `registration.refusedCancelled` + `event.deepLinkSeeUpcoming` (reused, onward path) |
| `event-finished` | `registration.refusedFinished` + `event.deepLinkSeeUpcoming` (reused) |
| `registration-closed` | `registration.refusedClosed` + `event.deepLinkSeeUpcoming` (reused) |
| `requires-invite` | `registration.refusedRequiresInvite` (names the reason explicitly — no onward path required by AC6, none added, to avoid inventing UX beyond what was asked) |
| `requires-approval` | `registration.refusedRequiresApproval` |
| `not-found` | `event.deepLinkNotAvailable` + `event.deepLinkSeeUpcoming` (reused verbatim — same generic non-disclosure wording REQ-016/017 already established for an unknown/gone event id) |

Every one of the three states AC4 names (closed/cancelled/finished) pairs a stated
reason with `event.deepLinkSeeUpcoming` as its onward path, satisfying AC4's "never a
dead end" wording without introducing a second "see upcoming" string.

string already uses; the bot has no visual/CSS surface, so `docs/Design system for AI
agents/readme.md`'s token/spacing rules do not apply here, consistent with REQ-016 §9's
identical reasoning for its own catalog additions.

## 9. Open questions (not silently resolved)

1. **A second card entry point.** (§0) Only the `/start` deep link renders a full card
   today; `/events` renders rows only (REQ-017 §0/§8.1). If a future requirement adds a
   tappable `/events` row, it needs its own Register button wired the same way — not
   assumed to happen automatically here.
2. **Whether registration should require a completed REQ-019 profile first.** (§0) No
   acceptance criterion states this; this design does not gate on it. If the product
   intends "must finish your profile before you can take a seat," that is a distinct,
   undecided requirement.
3. **No retry-on-`qr_token`-collision loop.** (§4.3) The unique index is the only
   backstop; a literal collision would surface as an unhandled insert failure inside
   `registerForEvent`'s transaction. Given the collision odds at this project's stated
   scale, this design does not propose recovery logic, but names the gap rather than
   assuming it away.
4. **The AC7/S8 audit-row reading for `waitlisted`.** (§6) This design writes one row on
   both `admitted` and `waitlisted`, reasoned from S8's broader "every status change"
   wording. `SECURITY-REVIEWER` should confirm this reading rather than this design's
   own say-so being taken as settled.
5. **Whether `requires-invite`/`requires-approval` refusals need an onward path too.**
   (§7.2) AC6 only requires "a clear refusal naming the reason"; AC4's onward-path
   requirement is scoped textually to the closed/cancelled/finished trio. This design
   adds no `deepLinkSeeUpcoming` pointer to the invite/approval refusals, reasoning that
   inventing one is scope beyond what was asked — but a future reviewer may reasonably
   prefer consistency across all refusal messages.
6. **The exact ordering among rows 2–6 of §2.2's table** is this design's own arbitrary
   choice (lifecycle gates before access-gates) since nothing in the requirement or PRD
   ranks them — stated explicitly so an implementer does not need to guess, not because
   the chosen order is provably the only correct one.

## 10. No new schema — explicit confirmation for Step 1b

Every column this design writes or reads already exists: `registrations.event_id/
user_id/admission/source/qr_token` (REQ-011), `events.capacity/status/requires_invite/
requires_approval/registration_closes_at/ends_at` (REQ-011), `users.pending_source`
(REQ-016). No `ALTER TABLE`, no new table, no new enum value, no new index is proposed
anywhere in this document — `registrations_qr_token_unique` and
`uq_registrations_event_user` (both already present) are the only indexes this design
relies on, unchanged. `DATA-DESIGNER` is not dispatched for this run.

| AC | Design element |
|---|---|
| AC1 — two concurrent registrations for the last seat: exactly one admitted, never two | §1's `SELECT ... FOR UPDATE` lock on the `events` row, held for the full span of §3.2 steps 2–8, serializing every concurrent `registerForEvent` call for that event |
