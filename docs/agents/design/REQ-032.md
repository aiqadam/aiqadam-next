# REQ-032 — No-show reason capture (asked once, no reminder)

**Requirement:** issue #35 (title says "Chapter interest wishlist" — misleading; that
scope belongs to Release 3 per the issue's own release-boundary text, confirmed by
reading it directly). Implements USER-STORIES D3 / STORY-DETAILS D3 ("Say what got in
the way") and PRD 13 acceptance criterion 8's `no_show` half. `depends_on: [REQ-031]`.
**FINAL requirement of Release 1 and of Phase 7.**

**Surface:** `apps/bot/**` (bot requirement).

**Schema: NO change is needed.** See §0 — `registrations.no_show_reason` already
exists, added by REQ-011's migration, as a plain nullable `text` column with no `CHECK`
constraint. This is a materially different situation from REQ-031, which needed a new
table. §0 still routes one confirmation question to `DATA-DESIGNER` (whether the
existing single-column shape should stay as-is or be split), but there is no blocking
schema dependency the way REQ-031 §0 had.

**Files this design expects:**
- `apps/bot/src/db/schema.ts` — **no change** (§0). `registrations.no_show_reason`
  (existing, REQ-011) is reused as-is.
- `apps/bot/src/domain/registration.ts` (existing — **extended**) — `isNoShow` (§1),
  `NoShowReasonCode` (§1.1), `getRegistrationNoShowContext` (§2.1), `writeNoShowReason`
  (§2.2)
- `apps/bot/src/domain/notification.ts` (existing — **extended**) — `NotificationKind`
  gains one new member, `"no_show_reason_request"` (§3.1)
- `apps/bot/src/domain/event.ts` (existing) — reused unchanged: `getEventById`
- `apps/bot/src/scheduler/noShowJobs.ts` (**new**) — the single `ScheduledJobDefinition`
  (§3)
- `apps/bot/src/handlers/noShow.ts` (**new**) — the fixed-reason callback, the "other"
  callback, and the generic reply-to-message text listener (§4)
- `apps/bot/src/i18n/types.ts`, `ru.ts`, `en.ts` — new `noShow.*` catalog keys (§5)
- `apps/bot/src/index.ts` — registers the new scheduled job and the new callback query /
  `message:text` handlers

## 0. Schema — resolved, one confirmation question left for DATA-DESIGNER

`apps/bot/src/db/schema.ts` line 282 already declares:

```
noShowReason: text("no_show_reason"),
```

nullable, no `CHECK`, present since REQ-011's initial migration
(`apps/bot/drizzle/0001_tired_annihilus.sql`). `REQ-011.md` §5's own derivation table
already states the exact formula this requirement now implements: `no_show =
admission = 'admitted' AND checked_in_at IS NULL AND $evaluation_time > ends_at`
(columnless), with `no_show_reason` "a real stored column, sharply distinguished from
the derived, columnless `no_show` boolean above." Nothing in this codebase, per a grep
of `apps/bot/src`, currently reads or writes `no_show_reason` anywhere — this
requirement is the column's first consumer.

**Confirmation question for DATA-DESIGNER (not a blocking dependency, unlike REQ-031
§0):** should the existing single free-text column stay as the only store for BOTH the
five fixed-reason codes AND the free-text "other" answer (this design's own
recommendation, §1.1), or should DATA-DESIGNER instead split it into two columns — a
constrained `reason_code` (one of the five literals, nullable) plus a separate nullable
`reason_free_text` — to make PRD FR-16's factsheet "why people missed it" aggregation
by category cleaner than parsing one mixed-content text column? Neither this
artefact's own requirement text nor any acceptance criterion forces either shape: AC2
only tests "selecting a reason writes it to `registrations.no_show_reason`, verified by
reading the row back" — satisfied by either shape, since a two-column split would still
have DATA-DESIGNER name which physical column(s) `no_show_reason` maps to. This design
proceeds on the recommended single-column shape (§1.1) but does not treat that choice as
final — flagged here, not silently resolved, exactly as REQ-031 §0.2 flagged
`topic_votes`'s shape without resolving it unilaterally.

No `CHECK` constraint is proposed for the fixed-reason set: because the same column also
receives arbitrary free text (the "other" answer), a `CHECK ... IN (five literals)`
would reject every free-text answer and cannot express "one of five literals OR any
other non-empty string" as a useful constraint — the closed set is enforced entirely at
the application layer (§1.1's fixed `NoShowReasonCode` union, and the fixed five-button
keyboard, §4.1, which is the only way a code value ever reaches the write function).

## 1. The computed `no_show` derivation — `domain/registration.ts`

Never stored (requirement's own explicit instruction, restated verbatim from REQ-011
§5): no boolean column, no materializing job, anywhere.

```
export function isNoShow(
  admission: AdmissionState,
  checkedInAt: Date | null,
  endsAt: Date | null,
  evaluationTime: Date,
): boolean;
```

Rule, stated exactly (first-match-wins table, per this codebase's own
`isFinished`/`isAutoPromotionHalted` convention of taking `evaluationTime` as an
explicit parameter, decisions/0006 — never reads the clock itself):

| Condition | Result |
|---|---|
| `admission !== 'admitted'` | `false` — a registration that was never admitted cannot be a no-show, regardless of `checkedInAt`/`endsAt`. |
| `admission === 'admitted'` AND `checkedInAt !== null` | `false` — the person checked in; not a no-show, regardless of `endsAt`. |
| `admission === 'admitted'` AND `checkedInAt === null` AND `endsAt === null` | `false` — the event has no recorded end time, so "has the event ended" cannot be evaluated; no-show is undeterminable, not assumed true. |
| `admission === 'admitted'` AND `checkedInAt === null` AND `endsAt !== null` AND `evaluationTime` is at or before `endsAt` | `false` — the event has not finished yet; too early to call it a no-show. |
| `admission === 'admitted'` AND `checkedInAt === null` AND `endsAt !== null` AND `evaluationTime` is strictly after `endsAt` | `true` — the exact condition the requirement states verbatim. |

This is the same predicate `isFinished(endsAt, evaluationTime)` already computes for
its own "strictly after" half — `isNoShow` does not call `isFinished` internally (no
executable composition shown here per the zero-implementation-code rule), but
BACKEND-DEV may choose to express the last two rows in terms of it; that is an
implementation-level reuse decision, not a design one.

### 1.1 `NoShowReasonCode` — the five fixed reasons, a closed union

```
export type NoShowReasonCode =
  | "work_ran_over"
  | "illness"
  | "forgot"
  | "transport"
  | "lost_interest";

export const NO_SHOW_REASON_CODES: readonly NoShowReasonCode[] =
  ["work_ran_over", "illness", "forgot", "transport", "lost_interest"];
```

Order matches the requirement text's own listed order (STORY-DETAILS D3), same
convention `FEEDBACK_FIELD_ORDER` (REQ-031 §2.1) already established for its own fixed
field order. These five literal strings — never a localized label — are what
`writeNoShowReason` (§2.2) stores when a fixed-reason button is tapped; the "other"
free-text answer stores the respondent's raw trimmed text instead, in the exact same
column (§0's recommended single-column shape). This mirrors this schema's existing
convention of storing canonical, language-invariant values in enum-like columns
(`admission`, `events.format`) rather than a display string — a factsheet later reading
this column can distinguish a coded answer from a free-text one by checking membership
in `NO_SHOW_REASON_CODES`.

### 1.2 Reading the current registration/event context — `getRegistrationNoShowContext`

```
export interface RegistrationNoShowContext {
  userId: string;
  eventId: string;
  admission: AdmissionState;
  checkedInAt: Date | null;
  noShowReason: string | null;
}

export async function getRegistrationNoShowContext(
  db: DbClient["db"],
  registrationId: string,
): Promise<RegistrationNoShowContext | null>;
// SELECT user_id, event_id, admission, checked_in_at, no_show_reason FROM
// registrations WHERE id = $registrationId LIMIT 1. A new function rather than
// extending getRegistrationFeedbackContext (REQ-031 §2.5, existing) -- that
// function's own callers (feedbackJobs.ts) have no reason to read
// no_show_reason, and this design does not reshape a contract it has no reason
// to touch, mirroring REQ-031 §2.5's own precedent of adding a new function
// instead.
```

`noShowReason` here (not `checkedInAt` alone) is what makes the "asked once, never
again" write-side gate concrete (§4.1 step 8, §4.2 step 8): a registration whose
`no_show_reason` is already non-`null` has already been answered, and no handler in this
design ever overwrites an existing answer.

### 1.3 Writing the answer — the one and only write path

```
export async function writeNoShowReason(
  db: DbClient["db"],
  registrationId: string,
  reason: string,
  at: Date,
): Promise<void>;
// UPDATE registrations SET no_show_reason = $reason, updated_at = $at WHERE
// id = $registrationId. reason is either one of the five NoShowReasonCode
// literals (§1.1, fixed-reason button path, §4.1) or the respondent's raw
// trimmed free text (the "other" path, §4.2/§4.3) -- both are plain strings by
// the time they reach this function; it does not itself distinguish which
// kind of string it was handed. This is the ONLY function anywhere in this
// design (or, by inspection of the current codebase, anywhere in
// apps/bot/src) that ever writes registrations.no_show_reason.
```

No `INSERT`/upsert shape is needed here (unlike REQ-031 §2.3's `writeFeedbackNps`) —
`registrations` rows already exist by the time this job ever runs (a registration is
created at registration time, long before an event can finish), so every call is a
plain `UPDATE` against an existing row.

## 2. Design questions 1–3, resolved explicitly

**Design question 1 (schema):** resolved in §0 — no new column. The existing
`registrations.no_show_reason` (`text`, nullable, no `CHECK`) is reused unchanged. One
confirmation question (single column vs. a `reason_code`/`reason_free_text` split) is
routed to DATA-DESIGNER, non-blocking.

**Design question 2 ("asked once, no reminder" mechanism):** confirmed — the existing
`notification_ledger` mechanism alone is sufficient, with **no new `asked_at` column
anywhere**, unlike REQ-031's `broadcast_opt_in_asked_at`. The reasoning REQ-031 §0.3
needed a separate column does not apply here: `broadcast_opt_in_asked_at` existed to
distinguish "never asked" from "asked and declined" on `users.broadcast_opt_in`, a
column whose own two possible values (`true`/`false`) cannot encode a third state.
`no_show_reason` has no such collision — `NULL` unambiguously means "not yet answered"
(whether because it was never asked, or asked and left unanswered — this requirement
treats both identically, since STORY-DETAILS D3 states silence is an acceptable answer
and no acceptance criterion distinguishes "never sent" from "sent, no reply"). The
question this design actually needs answered is narrower than REQ-031's: not "was this
person ever asked" (a durable state needing its own column) but "was THIS SEND already
attempted for THIS registration" — and that is exactly what
`notification_ledger`'s own `UNIQUE(registration_id, kind)` constraint
(`sendLedgeredNotification`, REQ-025, reused unchanged) already guarantees: the first
successful send inserts a ledger row keyed on `(registrationId, "no_show_reason_request")`;
every later attempt (a T+24h or T+48h re-run of the same job selecting the same
still-not-checked-in registration) collides on that row and returns
`skipped-already-sent`, never a second send. No asked-at tracking beyond the ledger's own
send record is needed because there is nothing else to track: unlike the broadcast ask,
there is no separate "answer" state living outside the ledger that could independently
race ahead of "was it sent" (the answer itself, when it arrives, lands in
`no_show_reason` directly — a column this design already reads at send time purely as a
defensive recheck, §3.4 step 3, not as the once-only gate itself).

**Design question 3 (where the derivation lives):** `domain/registration.ts`'s existing
style (§1) — the same module `isFinished`'s sibling predicates
(`isRegistrationOpen`, `isAutoPromotionHalted`) already live in, per `event.ts`'s actual
file, corrected: `isFinished` itself lives in `apps/bot/src/domain/event.ts`
(confirmed by inspection), operating purely on event-shaped inputs
(`endsAt`, `evaluationTime`). `isNoShow` additionally needs `admission`/`checkedInAt`,
which are registration-shaped inputs — placing it in `domain/registration.ts` (where
every other registration-state predicate in this codebase already lives —
`decideRegistrationOutcome`, `decideCheckinToggleOutcome`, `decideWithdrawOutcome`) is
the better fit than `event.ts`, since its output is a property of a *registration*, not
of an event in isolation (the same event can have both no-show and non-no-show
registrations). The exact boolean logic is confirmed verbatim in §1's table:
`admission === 'admitted' AND checkedInAt === null AND evaluationTime` strictly after
`endsAt` (with `endsAt === null` treated as "not yet determinable," §1's third row — a
detail the requirement text's own shorthand omits but REQ-011 §5's derivation table
already established this design does not silently deviate from).

## 3. The single scheduled job (`apps/bot/src/scheduler/noShowJobs.ts`, new)

Unlike REQ-031's two jobs (a request plus a reminder), this requirement needs exactly
**one** job — the fourth and final Release-1 consumer of `scheduler/runner.ts`
(REQ-025/026/031), reusing `ScheduledJobDefinition`/`startScheduledJobs` unchanged.
There is no second, reminder job — STORY-DETAILS D3's own refusal ("Reminding") is
what AC3 tests, and the absence of a second job is the structural mechanism behind it,
the same way REQ-031 §5.1's two distinct `NotificationKind`s were the mechanism behind
its own "exactly one reminder" AC.

### 3.1 `NotificationKind` — one addition

`domain/notification.ts`'s `NotificationKind` union gains `"no_show_reason_request"` —
a one-line TypeScript change, not a migration, per the same reasoning REQ-031 §5.1
already states (`notification_ledger.kind` is already `text`).

### 3.2 Selecting candidates — `selectRegistrationsForNoShowReasonRequest`

```
export interface NoShowJobCandidate {
  registrationId: string;
  userId: string;
}

export async function selectRegistrationsForNoShowReasonRequest(
  db: DbClient["db"],
  evaluationTime: Date,
): Promise<NoShowJobCandidate[]>;
```

Selection condition, stated exactly (mirrors `selectRegistrationsForFeedbackRequest`'s
table-driven style, `domain/feedbackJobs` — REQ-031 §5.2 — adapted from "checked in"
to its structural opposite):

| Clause | Condition |
|---|---|
| Only the never-checked-in | `registrations.checked_in_at IS NULL` — the mirror image of REQ-031 §5.2's own `IS NOT NULL` clause, and (together with the next two rows) is AC1's entire mechanism: a registration that WAS checked in never reaches this candidate list. |
| Only admitted registrations | `registrations.admission = 'admitted'` — a `requested`/`waitlisted`/`rejected`/`withdrawn` registration was never a candidate for attendance in the first place and is not a no-show by §1's own rule table. |
| Only currently-published events | `events.status = 'published'` |
| The event has actually ended | `events.ends_at IS NOT NULL` AND `events.ends_at <= evaluationTime` — the exact "now > ends_at" half of §1's derivation, evaluated at selection time. |
| A bounded catch-up window, not unbounded | `events.ends_at > evaluationTime - CATCH_UP_WINDOW` — same reasoning REQ-031 §5.2 already states verbatim (an unbounded backward scan would re-select every past no-show forever; `sendLedgeredNotification`'s own accepted under-sending risk, REQ-025 §3.2, means nothing legitimate is lost by bounding it). `CATCH_UP_WINDOW`'s exact size is left to BACKEND-DEV (§6 open question), same as REQ-031's own open question 3. |

No `NOT EXISTS` clause against `notification_ledger` or a `no_show_reason IS NULL`
clause is added to the selection query itself — unlike REQ-031 §5.3's reminder query,
there is no second job here whose selection needs to exclude "already engaged"
candidates; the send-time recheck (§3.4 step 3) and `sendLedgeredNotification`'s own
ledger constraint are what prevent a duplicate ask, exactly as reasoned in §2's design
question 2.

### 3.3 The job definition — `makeNoShowReasonRequestJob`

```
export function makeNoShowReasonRequestJob(
  db: DbClient["db"],
  sender: NotificationSender,
  intervalMs: number,
): ScheduledJobDefinition;
```

`run(evaluationTime)`: for each `selectRegistrationsForNoShowReasonRequest` candidate,
call `sendLedgeredNotification({ kind: "no_show_reason_request", classification:
"transactional", registrationId, userId, composeMessage })`. **`classification:
"transactional"`** is what satisfies **AC6** ("the message reaches a user with
`broadcast_opt_in = false`") structurally — the identical mechanism REQ-031 §5.4 already
established: `sendLedgeredNotification`'s own step 3 (REQ-025, `domain/notification.ts`)
never reads `broadcastOptIn` for a transactional send.

### 3.4 `composeMessage` — the at-send-time recheck

1. `context = getRegistrationNoShowContext(db, registrationId)` (§1.2); `context ===
   null`, `context.admission !== "admitted"`, or `context.checkedInAt !== null` →
   `{ kind: "skip" }` — the person checked in (or the registration state changed)
   between selection and send, the same class of recheck REQ-031 §5.4 step 1 and
   REQ-026's own reminder jobs already perform.
2. `event = getEventById(db, context.eventId)` (existing, reused unchanged); `event ===
   null`, `event.status !== "published"`, or `event.endsAt === null` or `evaluationTime`
   is not strictly after `event.endsAt` → `{ kind: "skip" }` — re-verifies §1's own
   derivation directly at send time, not merely trusting the selection query.
3. `context.noShowReason !== null` → `{ kind: "skip" }` — an answer already exists
   (answered through some other path before this send, or — since this is a
   single-send job with no reminder — this branch is expected to be unreachable in
   ordinary operation, the same "defensive, unreachable in practice" convention
   REQ-016/018/029/030/031 already document explicitly).
4. Otherwise: `{ kind: "text", text: <catalog.noShow.prompt>, buttons: <the five fixed-
   reason buttons plus one "other" button, §4.1's keyboard> }`.

### 3.5 Registration in `index.ts`

```
startScheduledJobs([
  ...,
  makeNoShowReasonRequestJob(db, notificationSender, 300000),
]);
```

Same `intervalMs` (300000 = 5 minutes) as every existing Release-1 job — no acceptance
criterion asks for a different cadence.

## 4. `handlers/noShow.ts` (new)

Every handler follows the identical **derive-current-state-first, then gate the write
on it** discipline already established by every prior Release-1 flow (REQ-019 §4.6,
REQ-030 §8.2–§8.3, REQ-031 §6): resolve the tapping/replying person, re-derive the
registration's current `no_show_reason` fresh from the database, and only then decide
whether to write anything. A stale tap/reply after the question is already answered is
always a no-op, never an error, never a second write.

### 4.1 `noshow:reason:<code>:<registrationId>` callback — the five fixed-reason buttons

```
export const NO_SHOW_REASON_PATTERN = /^noshow:reason:([a-z_]+):(.+)$/;

export function makeNoShowReasonCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Sequence:
1. Extract `codeStr`/`registrationId` from the pattern; no match → `ctx.
   answerCallbackQuery()`, return (defensive, unreachable).
2. `codeStr` not a member of `NO_SHOW_REASON_CODES` (§1.1) → `ctx.
   answerCallbackQuery()`, return (defensive, unreachable — the five buttons this design
   ever sends, §3.4 step 4, only ever emit one of these five literals by construction).
3. `tgId = ctx.from?.id`; `undefined` → `ctx.answerCallbackQuery()`, return.
4. `flowUser = getFlowUserByTgId(db, BigInt(tgId))` (REQ-014, reused unchanged); `null`
   → `ctx.answerCallbackQuery()`, return.
5. `context = getRegistrationNoShowContext(db, registrationId)` (§1.2); `context ===
   null` → `ctx.answerCallbackQuery({ text: noShow.staleMessage, show_alert: true })`,
   return.
6. **Ownership check (S3):** `context.userId !== flowUser.id` → `ctx.answerCallbackQuery
   ({ text: noShow.notYours, show_alert: true })`, **no write**, return — the same
   concrete negative case REQ-031 §6.1 step 6 already establishes for a forwarded or
   otherwise leaked button.
7. `ctx.answerCallbackQuery()` (Telegram UX requirement, once ownership is confirmed).
8. **Gate:** `context.noShowReason !== null` → no write (already answered — the
   structural mechanism behind AC3's "no further message/write," restated here as "no
   further write," since the read-side gate for whether a message is even sent already
   lives in §3.4 step 3). Only when `context.noShowReason === null`:
   `writeNoShowReason(db, registrationId, codeStr, new Date())` (§1.3).
9. `ctx.reply(catalog.noShow.thanksMessage)` — a short acknowledgement, sent whether or
   not step 8's gate actually wrote (a stale re-tap gets the same friendly
   acknowledgement rather than silence or an error, mirroring REQ-019/REQ-031's
   "always advance, never dead-end" discipline applied here to a single-step flow that
   has no further prompt to advance to).

### 4.2 `noshow:other:<registrationId>` callback — the free-text option

```
export const NO_SHOW_OTHER_PATTERN = /^noshow:other:(.+)$/;

export function makeNoShowOtherCallbackHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

Identical to §4.1 steps 3–7 (no `codeStr` to validate), then:

8. **Gate:** `context.noShowReason !== null` → `ctx.reply(catalog.
   noShow.alreadyAnswered)`, return — already answered, no free-text prompt sent.
9. Otherwise: `ctx.reply(<formatNoShowTextPrompt(catalog.noShow.otherPrompt,
   registrationId)>, { reply_markup: { force_reply: true } })` (§4.4) — the free-text
   `force_reply` prompt, carrying the ref line the reply listener (§4.3) parses back.

### 4.3 The generic reply-to-message text listener — the free-text answer path

```
export function makeNoShowTextReplyHandler(db: DbClient["db"]) {
  return async (ctx: Context): Promise<void> => { ... };
}
```

**Why a ref line is still needed even though this flow has only one text-answerable
question per registration (unlike REQ-031's three sibling optional fields):** REQ-031
§1.2's field-disambiguation problem (distinguishing WHICH of several sibling fields a
reply answers) genuinely does not apply here — there is only one free-text slot per
registration, so no "which field" ambiguity exists. But REQ-031's OTHER, more basic
problem still applies unchanged: **which registration** a bare reply belongs to. The
same person can hold more than one `admitted`-but-never-checked-in registration across
different events (no acceptance criterion or invariant rules this out), and this
design's own job can have more than one no-show ask "outstanding" for the same person at
once. A ref line carrying the `registrationId` (no field name needed, since there is
only one field) is therefore still required — this design's ref-line mechanism is a
strict subset of REQ-031 §3.1's, not a full copy of it.

Sequence:
1. `text = ctx.message?.text`; `undefined`, blank, or starts with `"/"` → return.
2. `repliedToText = ctx.message?.reply_to_message?.text`; `undefined` → return — not a
   no-show-flow message, deferring silently to any other `message:text` listener,
   mirroring REQ-031 §6.3 step 2/REQ-019's own convention.
3. `parsed = parseNoShowReplyContext(repliedToText)` (§4.4); `!ok` → return — a reply to
   some other bot message, not this flow's own prompt.
4. `tgId = ctx.from?.id`; `undefined` → return.
5. `flowUser = getFlowUserByTgId(db, BigInt(tgId))`; `null` → return.
6. `context = getRegistrationNoShowContext(db, parsed.registrationId)` (§1.2);
   `context === null` OR `context.userId !== flowUser.id` → return — the same S3
   ownership gate as §4.1 step 6, silent here (a passive listener, not an explicit
   command), mirroring REQ-031 §6.3 step 6.
7. **Gate:** `context.noShowReason !== null` → return — already answered; a reply to a
   still-repliable but now-superseded prompt is a silent no-op, the same "recheck at
   write time" discipline REQ-031 §6.3 step 8/§6.1 step 9/§6.2 step 9 already use for
   every other stale-tap or stale-reply case in this codebase.
8. `value = text.trim()`; blank after trimming → return (nothing meaningful to store —
   Telegram does not normally deliver a whitespace-only text message, so this is
   defensive).
9. `writeNoShowReason(db, parsed.registrationId, value, new Date())` (§1.3).
10. `ctx.reply(catalog.noShow.thanksMessage)`.

No Skip keyword is matched here (unlike REQ-031 §4's `isFeedbackSkipReply`) — this
flow has no separate "skip this one field, move to the next" step to skip past (there
is no next step, §4.5), and silence (never replying at all) is already the accepted
"skip" per STORY-DETAILS D3's own framing — a person who ignores the free-text prompt
entirely simply never triggers this handler, which is the correct outcome with no
keyword needed.

### 4.4 The prompt/ref-line render/parse pair and the fixed-reason keyboard

```
export function formatNoShowTextPrompt(
  promptBody: string,
  registrationId: string,
): string;
// Rule: promptBody, then a blank line, then one fixed-prefix line:
// "No-show ref: " + registrationId. Used only for the "other" free-text
// prompt (§4.2) -- the five fixed-reason buttons and the "other" button
// itself (§4.1's/§4.2's own inline keyboard) need no ref line, since
// callback_data already carries the registration id directly.

export type ParseNoShowReplyResult =
  | { ok: true; registrationId: string }
  | { ok: false };

export function parseNoShowReplyContext(
  repliedToText: string,
): ParseNoShowReplyResult;
// Rule: split repliedToText on newlines. Find the first line starting with
// the exact literal prefix "No-show ref: "; its value (everything after the
// prefix, trimmed) is the registrationId. Line missing -> { ok: false }.
// Line present -> { ok: true, registrationId }.
```

`"No-show ref: "` is a fixed, non-localized literal despite living in the catalog table
(§5) — the same treatment REQ-031 §7's `refLinePrefix`/`fieldLinePrefix` and REQ-030
§7.1's `"Name: "`/`"Company: "`/`"Phone: "` already receive: a machine-parseable anchor,
not a sentence meant to be read meaningfully by a person in their own language.

**The prompt keyboard (§3.4 step 4):** five buttons, one per `NoShowReasonCode` (§1.1),
label = that language's own catalog string for the code (§5), `callback_data` =
`"noshow:reason:" + code + ":" + registrationId`; plus a sixth button, label =
`catalog.noShow.otherLabel`, `callback_data` = `"noshow:other:" + registrationId`.
Longest instance (`"noshow:reason:lost_interest:"` at 28 bytes plus a 36-byte UUID,
totalling 64 bytes) is exactly at, not over, the 64-byte `callback_data` cap — a detail
BACKEND-DEV should re-verify against Telegram's exact byte-counting rule (UTF-8 byte
length, not character count) before finalizing the literal `"lost_interest"` code
string; if it turns out to be one byte over, shortening only that one code string (e.g.
`"lost_int"`) is a pure implementation-level fix that does not change this design's
shape.

### 4.5 No follow-up step after the answer — a stated scope boundary

Unlike REQ-031's multi-field flow (`advanceFeedbackFlow`, REQ-031 §6.4), there is no
"next question" here — STORY-DETAILS D3 describes exactly one question. §4.1 step 9/
§4.3 step 10 both end the interaction with a single acknowledgement message, never a
further prompt.
