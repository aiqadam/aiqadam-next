# REQ-025 — Scheduled job runner and the idempotent send-once notification ledger

**Requirement:** PRD 14 build-order step 4 (first slice), PRD FR-7, PRD 9, PRD 12.8,
security-invariants.md S9/S10. `depends_on: REQ-024`.

**Surface:** `apps/bot/**` (bot requirement). No design tokens apply — this requirement
introduces no user-visible screen or new copy; it is a send mechanism other requirements'
copy already routes through (or will route through, for REQ-026). Same "no tokens" note
as REQ-018/020/021/022/023/024.

**Content shape:** no new copy. The one existing message this requirement's migration
touches — `withdraw.ts`'s promotion notification — keeps its exact existing text and
catalog keys (`Catalog.promotion.*`, REQ-023 §6.3); only the mechanism that sends it
changes (ledger-backed, rate-limited, instead of a bare `ctx.api.sendMessage` call).

**Schema change: YES — flagged for DATA-DESIGNER, not designed here.** See §1.

## 0. Scope decisions stated up front (per this task's instructions)

### 0.1 `staff.ts` migration — OUT OF SCOPE for REQ-025, stays as ISS-0020

`docs/issues/ISS-0020.yaml` (filed by REVIEWER during WF02-REQ-023) documents that
`apps/bot/src/handlers/staff.ts`'s assignment/removal notifications never check
`users.blocked`. Judgment: **do not migrate `staff.ts` onto this requirement's ledgered
send API.** Two independent reasons, either one sufficient on its own:

1. **The ledger's key doesn't fit staff.ts's data at all.** This design's
   `notification_ledger` table (§1) is keyed on `(registration_id, kind)` — that key
   exists because S9's restart-idempotency problem is about *Registration*-scoped
   notifications sent from a scheduled job or a retryable batch. `staff.ts`'s
   assignment/removal notifications have no `Registration` row anywhere in their path —
   they are keyed on `(event_id, user_id)` via `EventStaff`, a structurally different
   entity. Routing them through `sendLedgeredNotification` (§3) would require either
   inventing a second, differently-shaped ledger key (out of scope: no acceptance
   criterion here asks for one) or passing a fabricated/unrelated `registrationId` into
   the existing key (semantically wrong — it would let an assignment notification and a
   real registration notification collide on the same ledger row by coincidence, or
   silently violate the "nullable in practice" assumption a future reader might make).
2. **S9 (restart-idempotency) does not apply to `staff.ts`'s sends in the first place.**
   Every `staff.ts` notification is a synchronous, request-scoped, one-off `await
   ctx.api.sendMessage(...)` call made once, inline, inside the same handler invocation
   that just committed the assignment/removal — there is no scheduled job, no batch, no
   retry path that could re-run it after a restart. `staff.ts`'s header comment (line
   ~90) already states this reasoning for why it was built this way in REQ-018: "no
   restart/retry path exists for a single request-scoped API call, so S9 is not at risk
   here." ISS-0020's actual defect is narrower and different: a missing `blocked` check
   (an S10 gap, not an S9 gap) — exactly what REQ-023 fixed for
   `sendPromotionNotification` by adding a `blocked` projection and a guard, with no
   ledger involved at all.

ISS-0020's own recommended fix (add `blocked: users.blocked` to `getUserByTgUsername` or
a similar accessor, skip the send when `blocked === true`, mirroring `withdraw.ts`'s
existing guard) is unaffected by this requirement and should be picked up as its own,
separate fix-run — not folded into REQ-025's build.

### 0.2 `withdrawRegistration`'s promotion send — migration path, precisely

`docs/agents/design/REQ-023.md §5`'s closing paragraph already names the intended
target: *"REQ-025, when built, should key its ledger on `(registration_id,
notification_kind)` and treat a row already in `admission = 'admitted'` with no
corresponding 'sent' ledger entry as the signal to retry the send — replacing this
design's implicit, DB-state-only mechanism, never duplicating it with a second, parallel
marker."* This design follows that exactly:

- **What is replaced:** REQ-023's *implicit* at-most-once argument — "a given waitlisted
  registration row can be selected [for promotion] at most once, ever," which happens to
  make the one existing call to `sendPromotionNotification` run at most once *per
  successful promotion*, but gives **no protection at all** against a crash between the
  promotion's DB commit and the Telegram send actually completing (REQ-023 §5 names this
  exact gap and defers it to REQ-025 by name).
- **What replaces it:** `sendPromotionNotification` (`handlers/withdraw.ts`) is rewritten
  to call this requirement's shared `sendLedgeredNotification` (§3) with `kind:
  "waitlist_promotion"`, keyed on **the promoted registration's own id**
  (`PromotionOutcome`'s `"promoted"` variant's existing `registrationId` field,
  `domain/registration.ts`, REQ-023 §3 step 7 — not the withdrawn registration's id). This
  is a real database `UNIQUE(registration_id, kind)` guard (§1) instead of a reasoning
  argument about `admission` transitions — so even a hypothetical future retry of the
  promotion-notification step (one does not exist today, but nothing before this
  requirement prevented one from being added unsafely) is now guarded structurally, not
  by convention.
- **Exact call-site rewrite** (§4 below) — `BACKEND-DEV` implements this precisely,
  nothing left to infer.

## 1. Schema change — flagged for DATA-DESIGNER

**Resolved:** see `docs/agents/design/REQ-025-schema.md` (DATA-DESIGNER) for the exact
`notification_ledger` table shape, the `text`-vs-`pgEnum` decision for `kind`, and the
`created_at`/`DEFAULT now()` timestamp decision (which corrects this section's own
`audit_log.at` citation — see that document's §8).

**A new table is required.** Checked `apps/bot/src/db/schema.ts` directly: no table
anywhere records "this notification was sent" — S9's own negative case ("idempotency
enforced by an in-memory set that a restart clears") is exactly the gap. Per this
project's established convention (REQ-011, REQ-024, etc.), the requirement is stated
here for DATA-DESIGNER to design; **the actual columns/types/migration are not decided
by this document.**

**Requirement for DATA-DESIGNER**, stated precisely:

- New table, suggested name `notification_ledger` (working name only — DATA-DESIGNER
  may rename).
- Must hold, at minimum: a reference to the `registrations` row the notification is
  about (FK to `registrations.id`), a "kind" value from a closed set (see the
  application-level `NotificationKind` union in §2 — Release 1 needs exactly six
  values: `admission_result`, `waitlist_promotion`, `reminder_24h`, `reminder_3h`,
  `feedback_request`, `event_cancelled`; S10 names two more Release-3 marketing kinds
  — "new-event announcements", "wishlist matches" — that will extend this set later, so
  whichever representation DATA-DESIGNER picks should not make adding a seventh value
  disproportionately costly), and the moment the row was written.
- **DATA-DESIGNER's own call, not decided here:** `text` (open, app-validated, per
  `chapters.code`/`users.role`'s existing precedent) vs. a native Postgres `pgEnum`
  (closed, safety-critical, per `admission`/`eventStatus`'s existing precedent, REQ-011's
  stated reasoning) for the "kind" column — REQ-011's own comment already frames this
  exact tradeoff (ALTER TYPE cost vs. structural invalidity-prevention) for a
  comparable closed set.
- **The load-bearing constraint AC2 tests directly: `UNIQUE(registration_id, kind)`.**
  This is not a suggestion — it is the literal mechanism this requirement's central
  property (S9) depends on. No in-memory or apparently-equivalent alternative satisfies
  AC2, which requires the constraint to reject a duplicate insert attempted directly
  against the table.
- No "sent by" actor column is needed (unlike `audit_log`, which already separately
  records every status change per S8) — this table's only job is the idempotency guard,
  not an audit trail. Whether it also needs `created_at`/`updated_at` columns for
  consistency with every other table in this schema is DATA-DESIGNER's call; the "moment
  sent" value (however named) must be a caller-supplied `Date`, never `defaultNow()`
  inside the column definition — matching this schema's `decisions/0006` "evaluation
  time is an explicit parameter" discipline already applied to `audit_log.at`.
- No `onDelete: "cascade"` on the FK to `registrations` — match this schema's existing
  restrict-everywhere convention (every other FK in `schema.ts` uses `onDelete:
  "restrict"`).

## 3. `sendLedgeredNotification` — the shared send API (AC1, AC2, AC3, AC4, AC5)

New file: `apps/bot/src/domain/notification.ts` (same file as §2). Framework-free
(decisions/0004) — the interface below never imports `grammy`; the concrete Telegram
call is injected via `NotificationSender` (§5), whose *interface* is declared here but
whose *implementation* (which does import `grammy`) lives in `scheduler/rateLimiter.ts`.

```
export interface NotificationSender {
  send(tgId: bigint, text: string): Promise<void>;
}

export interface SendNotificationInput {
  db: DbClient["db"];
  sender: NotificationSender;
  registrationId: string;
  kind: NotificationKind;
  classification: SendClassification;
  userId: string;
  composeMessage: (resolvedLang: BotLang) => Promise<string> | string;
}

export type SendOutcome =
  | { kind: "sent" }
  | { kind: "skipped-already-sent" }
  | { kind: "skipped-blocked" }
  | { kind: "skipped-no-broadcast-opt-in" }
  | { kind: "skipped-no-telegram-id" }
  | { kind: "failed"; error: unknown };

export async function sendLedgeredNotification(
  input: SendNotificationInput,
): Promise<SendOutcome>;
```

### 3.1 Sequencing — stated as an ordered rule table, not as code

| Step | Action | Outcome on failure/refusal |
|---|---|---|
| 1 | Look up the user via `getUserForNotificationById(db, userId)` (`domain/user.ts`, §6 — gains a `broadcastOptIn` projection in this requirement). | Row not found, or found with `tgId === null` → return `{ kind: "skipped-no-telegram-id" }`. No ledger row written — nothing was going to be attempted. |
| 2 | Check `user.blocked`. This check runs **unconditionally, before the classification branch below** — S10's "blocked users are skipped in both cases" is a single check that precedes, not follows, the transactional/marketing split. | `blocked === true` → return `{ kind: "skipped-blocked" }`. No ledger row written. (AC4.) |
| 3 | If `input.classification === "marketing"`, check `user.broadcastOptIn`. | `false` → return `{ kind: "skipped-no-broadcast-opt-in" }`. No ledger row written. If `input.classification === "transactional"`, this step is skipped entirely — `broadcastOptIn` is never read for a transactional send. (AC3.) |
| 4 | Attempt `INSERT INTO notification_ledger (registration_id, kind, ...) VALUES (input.registrationId, input.kind, ...)` as a single, ordinary `INSERT` statement (a single statement is already atomic in Postgres — no `db.transaction(...)` wrapper is needed around this step alone). | The insert violates the `UNIQUE(registration_id, kind)` constraint (Postgres error code `23505`) → this is caught and treated as a normal, expected outcome — return `{ kind: "skipped-already-sent" }`, **do not proceed to step 5.** This is the mechanism that makes AC1's second run a no-op. Any other insert error is treated as `{ kind: "failed", error }`. |
| 5 | Only reached if step 4's insert committed. Call `input.composeMessage(resolvedLang)` (where `resolvedLang = resolveLang(user.lang, user.chapterDefaultLang)`, the existing function, unchanged) to obtain the message text, then call `input.sender.send(user.tgId, text)` (§5 — this is where the rate limiter and 429 backoff live). | On success → return `{ kind: "sent" }`. On an error the sender does not itself recover from (its backoff/retry budget exhausted, §5) → return `{ kind: "failed", error }`. **The already-committed ledger row from step 4 is never rolled back or deleted here** — see §3.2. |

`sendLedgeredNotification` **never throws** for any of the outcomes above — every branch
returns a `SendOutcome` value. Callers that must not let a notification failure affect
their own reply (e.g. `withdraw.ts`, §4) do not need a `try`/`catch` around this call.

### 3.2 The crux: what happens if the process crashes between step 4's commit and step 5's completion — accepted, named risk

This is the exact question AC1 is about, stated precisely rather than left implicit:

- **The ledger row is written (step 4, committed) strictly *before* the Telegram send is
  even attempted (step 5).** This ordering is deliberate and is the one that must be
  used — the reverse order (send first, record second) is rejected below.
- **If a crash happens between step 4's commit and step 5's `sender.send(...)` call
  returning** (whether the crash happens before the HTTP request is even made, mid-flight,
  or after Telegram has actually delivered the message but before the response reaches
  this process), **a later re-run of `sendLedgeredNotification` for the same
  `(registrationId, kind)` will find the ledger row already present at step 4 and return
  `{ kind: "skipped-already-sent" }` without ever calling `sender.send` again.** This is
  correct for the case where Telegram *did* receive and deliver the message (no
  duplicate — the property this requirement exists to guarantee) but it is **also** what
  happens in the rarer case where Telegram never actually received it — the notification
  is then **silently, permanently not delivered.**
- **This is an accepted, explicitly named risk, not an oversight.** Telegram's Bot API
  offers no two-phase-commit or transactional guarantee spanning an external HTTP call
  and this process's own Postgres transaction — no design can make "the DB write commits"
  and "the HTTP call succeeds" atomic against each other without a mechanism (an
  outbox-pattern reconciliation job reading Telegram's own delivery confirmations, which
  Telegram's `sendMessage` API does not expose in a way this system could poll) that is
  out of scope for this requirement and not asked for by any acceptance criterion. Between
  the two possible failure directions — **occasionally under-sending** (this design) or
  **occasionally over-sending** (the rejected alternative below) — under-sending is the
  one consistent with S9's own stated harm ("the failure mode is messaging a real person
  repeatedly") and with this requirement's explicit instruction that "an in-memory set is
  explicitly insufficient" for the opposite reason (it under-*guards*, i.e. over-sends,
  on every restart).
- **Why the reverse order (send first, insert the ledger row second) is rejected:** if the
  Telegram send succeeds and *then* the process crashes before the ledger insert commits,
  a later re-run has no record that anything was sent, and will send again —
  a genuine duplicate delivery, exactly S9's negative case. Insert-then-send can only ever
  under-send; send-then-insert can over-send. Only the first is acceptable here.
- **What this means for AC1's test construction, stated explicitly for TEST-DESIGNER:**
  the acceptance criterion's "exactly ONE message delivered" claim is provable only when
  the process is killed *after* `sender.send(...)` (step 5) has actually returned in the
  first run — i.e., after the message genuinely went out — and *then* the second process
  re-runs the same `sendLedgeredNotification` call. Killing the process **mid-flight**
  inside step 5 (before the send call returns) is a different, also-true scenario (zero
  messages delivered, not one) — both are correct behavior under this design, but only
  the first is what AC1's "exactly one" wording is actually asserting, so the verification
  case must construct the kill point after the stubbed send call has resolved.

### 3.3 Genuine two-process restart test, not a single-run simulation

Per AC1's own wording ("a single-run test does not exercise restart-safety and is not
evidence"), the verification for AC1 must span two separate OS processes (or two
separate script invocations against the same Postgres database, each with its own fresh
process memory) — a single Node process calling `sendLedgeredNotification` twice in the
same run would not exercise the property this design is actually about (the DB-backed
constraint surviving a memory wipe), only that calling it twice in-process is safe, which
an in-memory guard would also pass. This is `TEST-DESIGNER`'s concern to encode precisely
in `docs/agents/test-specs/REQ-025.md`, named here so it is not silently left as an
in-process test.

## 4. `withdraw.ts`'s migration — exact rewrite

`handlers/withdraw.ts`'s `sendPromotionNotification` function (REQ-023) is rewritten.
Current signature and call site (as of this design):

```
async function sendPromotionNotification(
  db: DbClient["db"],
  ctx: Context,
  withdrawnRegistrationId: string,
  promotedUserId: string,
  qrToken: string,
): Promise<void>;
```

**New signature:**

```
async function sendPromotionNotification(
  db: DbClient["db"],
  sender: NotificationSender,
  promotedRegistrationId: string,
  promotedUserId: string,
  qrToken: string,
): Promise<void>;
```

Changes, stated precisely:

1. The parameter `ctx: Context` is **removed** — the function no longer calls
   `ctx.api.sendMessage` directly. In its place, a `sender: NotificationSender` (§3, §5)
   is threaded in from the caller.
2. The parameter is renamed `withdrawnRegistrationId` → `promotedRegistrationId`, and its
   value at the one call site changes from `registrationId` (the *withdrawn* row's id,
   the callback's own `WITHDRAW_CONFIRM_PATTERN` match) to `outcome.promotion.registrationId`
   (the *promoted* row's id, already present on `PromotionOutcome`'s `"promoted"` variant,
   REQ-023 §3 step 7). This is the id `getEventIdForRegistration` is called with too — the
   event is the same either way, so this is a pure rename plus a source-value change, not
   a behavior change for the event/date-time lookup.
3. The function body's existing guard/compose logic (blocked check, null-`tgId` guard,
   language resolution, event/date-time/qrToken message composition) is **replaced by
   `sendLedgeredNotification`'s own steps (§3.1)** — those checks now live once, centrally,
   not duplicated in this handler. The function becomes a thin call:
   - `composeMessage: async (lang) => { ...build the exact same
     [admittedPrefix, eventTitle, dateTimeText, qrLabel + qrToken, whatNext] text as
     REQ-023 §6.3 already does, using `getCatalog(lang)` and
     `getEventByIdWithChapterTimezone`, unchanged... }`
   - a single call: `await sendLedgeredNotification({ db, sender, registrationId:
     promotedRegistrationId, kind: "waitlist_promotion", classification: "transactional",
     userId: promotedUserId, composeMessage })`.
   - The function's own return type stays `Promise<void>` — the caller (the confirm
     callback handler, unchanged in this respect) does not branch on the `SendOutcome`,
     matching REQ-023 §6.2 step 3's existing "never blocks or affects the withdrawer's own
     reply" precedent; a `SendOutcome` of anything other than `"sent"` is simply not acted
     on by this call site (a future requirement could log it, but no acceptance criterion
     here asks for that).
4. `makeWithdrawConfirmCallbackHandler(db: DbClient["db"])`'s own factory signature gains
   a second parameter: `makeWithdrawConfirmCallbackHandler(db: DbClient["db"], sender:
   NotificationSender)`, and its one internal call site
   (`sendPromotionNotification(db, ctx, registrationId, ...)`) changes to
   `sendPromotionNotification(db, sender, outcome.promotion.registrationId, ...)` —
   reached only inside the existing `if (outcome.kind === "withdrawn" &&
   outcome.promotion.kind === "promoted")` branch, unchanged.
5. `index.ts`'s one registration line,
   `bot.callbackQuery(WITHDRAW_CONFIRM_PATTERN, makeWithdrawConfirmCallbackHandler(db));`,
   changes to pass the process-wide `sender` instance (§5) as the second argument — the
   same instance every other future call site (REQ-026's reminder jobs, REQ-027's
   cancellation notice) will also receive, constructed once at startup.

## 5. Rate limiting and 429 backoff — `NotificationSender`'s concrete implementation (AC6)

New file: `apps/bot/src/scheduler/rateLimiter.ts`. This file **does** import `grammy`
(it wraps `Bot["api"]`) — it is the one place `NotificationSender`'s interface (declared
framework-free in `domain/notification.ts`, §3) is actually implemented.

```
export interface RateLimiterConfig {
  maxMessagesPerSecond: number;
  maxRetries: number;
  initialBackoffMs: number;
  maxBackoffMs: number;
}

export function createRateLimitedSender(
  bot: Bot,
  config: RateLimiterConfig,
): NotificationSender;
```

**Defaults this design fixes** (technical parameters, not a product ambiguity — stated
as concrete numbers so `TEST-DESIGNER` has something precise to test against, per this
role's "don't silently resolve an ambiguity" rule read the other way: an implementation
default with no user-facing consequence is not the kind of ambiguity that rule is about):
`maxMessagesPerSecond: 25` (PRD FR-15's own stated ceiling), `maxRetries: 5`,
`initialBackoffMs: 1000`, `maxBackoffMs: 30000`.

**Behavior, stated as a rule table, not as code:**

| Concern | Rule |
|---|---|
| Pacing (proactive) | Outgoing `send` calls are paced so that no more than `maxMessagesPerSecond` actual Telegram API calls are made in any rolling one-second window — a call arriving while the window's quota is exhausted waits until quota frees up before making its HTTP request, rather than being dropped or erroring. |
| 429 response (reactive) | When the underlying Telegram call rejects with a 429 (grammY surfaces this as a `GrammyError` whose `error_code` is `429`, carrying a `parameters.retry_after` value in seconds per the Telegram Bot API's own documented shape), the sender waits `retry_after` seconds — or `initialBackoffMs` if `retry_after` is absent — and retries the **same** logical send. |
| Backoff growth | Each successive 429 for the same logical send doubles the previous wait, capped at `maxBackoffMs`, up to `maxRetries` total attempts. |
| Exhaustion | After `maxRetries` attempts all end in 429 (or any other error), the call rejects (propagates to `sendLedgeredNotification`'s step 5 as a caught error, returned as `{ kind: "failed", error }` — never an uncaught throw past that boundary, per §3.1). |
| Non-429 errors | Any error other than a 429 (e.g. the recipient blocked the bot, `Forbidden`) is not retried — it propagates immediately as a single attempt's failure, since retrying it would not change the outcome. |

**AC6's exact scenario:** a stub returning 429 then 200 exercises exactly one retry
(attempt 1 → 429 → wait `retry_after` or `initialBackoffMs` → attempt 2 → 200) — the
message is sent exactly once at the underlying Telegram-call level (the retry replaces
the failed attempt, it does not add a second, independent send), satisfying "message
ultimately delivered exactly once."

## 7. The scheduled job runner — the first scheduling infrastructure in this codebase

Checked directly, per this task's instruction: `grep -rn "setInterval|setTimeout|cron|
schedule" apps/bot/src` finds no scheduling mechanism anywhere — REQ-023's own design
(§0) explicitly noted "there is no scheduled-job runner, cron, or queue anywhere in
`apps/bot/src/**`" when it deliberately chose *not* to need one. **This requirement
introduces the first one**, per PRD 1's constraint ("one Postgres and one bot process are
sufficient... do not add infrastructure") — no Redis, no external queue, a plain
in-process timer.

New file: `apps/bot/src/scheduler/runner.ts`.

```
export interface ScheduledJobDefinition {
  name: string;
  intervalMs: number;
  run: (evaluationTime: Date) => Promise<void>;
}

export interface SchedulerHandle {
  stop(): void;
}

export function startScheduledJobs(
  jobs: readonly ScheduledJobDefinition[],
): SchedulerHandle;
```

**Behavior, stated as a rule table:**

| Concern | Rule |
|---|---|
| Timer mechanism | Each `ScheduledJobDefinition` gets its own interval timer (`setInterval`-based — a plain in-process timer, not a new external dependency), firing every `intervalMs`. |
| Immediate first run | Each job's `run` is also invoked once immediately when `startScheduledJobs` is called, not only after the first `intervalMs` elapses — so a process that was down when a job "should" have fired catches up promptly on restart rather than waiting a full interval. |
| Overlap guard | Per job, a running-flag is tracked. If a timer tick fires while that same job's previous `run(...)` call has not yet resolved, the new tick is skipped entirely for that job (not queued, not run concurrently) — this codebase's `db.transaction`/row-lock discipline already assumes callers do not issue overlapping writes for the same logical unit of work; the scheduler enforces "at most one in-flight run per job" as a structural guarantee rather than relying on every future job body to reimplement its own re-entrancy guard. |
| Failure isolation | If a job's `run(...)` promise rejects, the rejection is caught and logged (via this codebase's existing `log.ts` logger) — it never escapes to crash the process or stop other jobs' timers. One job's bug must not take down the bot process or every other job. |
| Stopping | `stop()` clears every job's timer — used only for graceful shutdown/tests, not by any acceptance criterion here. |

**`index.ts` wiring for this requirement:** `startScheduledJobs([])` — an **empty**
job list. REQ-025's own acceptance criteria do not ship a concrete reminder job (that is
REQ-026's "T-24h/T-3h" scope, and REQ-027's cancellation notice); this requirement's job
is the runner mechanism plus the ledger/send/rate-limit machinery those future jobs will
call into. AC1's restart scenario is verified directly against `sendLedgeredNotification`
(§3) with a literal `kind: "reminder_24h"` argument, standing in for what REQ-026's actual
job body will eventually call — it does not require a real T-24h business-logic job to
exist yet. `index.ts` also constructs the one process-wide `NotificationSender` here
(`createRateLimitedSender(bot, { ...defaults from §5 })`), passed to `startScheduledJobs`
job bodies (none yet) and to `makeWithdrawConfirmCallbackHandler` (§4 point 5).

   the `UNIQUE(registration_id, kind)` constraint, and the caller-supplied-timestamp
   discipline).
2. **Whether a failed `sendLedgeredNotification` (`{ kind: "failed" }`, §3.1 step 5)
   should ever be retried by a later scheduled tick of the same job**, and if so, how a
   future job body would distinguish "never attempted" from "attempted and the Telegram
   call itself failed after the ledger row already committed" (§3.2's named risk) — the
   ledger row exists either way, so a later retry attempt would currently be
   indistinguishable from "already sent" and would be silently skipped. No acceptance
   criterion here asks for a reconciliation/retry-after-ledger-commit mechanism; this is
   left as a known limitation for a future requirement (most naturally REQ-026, which
   will be the first requirement to actually run this send repeatedly on a schedule) to
   decide whether it needs one.
3. **Whether `staff.ts`'s ISS-0020 gap should be fixed in its own dedicated run before or
   after REQ-025/026/027 land** — a scheduling question for `ORCH`, not a design question;
   this document only confirms the fix does not belong inside REQ-025's own scope (§0.1).
