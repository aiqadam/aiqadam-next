## 0. Reuse decisions, stated up front

### 0.1 Concurrency mechanism — reuses REQ-020/023/030's row-lock pattern, not a new one

Traced against `domain/registration.ts`'s three existing writers that gate on capacity:

- `registerForEvent` (REQ-020 §3.2 step 2): `SELECT ... FROM events WHERE id = $1 FOR UPDATE`
  inside `db.transaction`, THEN a fresh `SELECT count(*) ... WHERE admission = 'admitted'`
  inside the same transaction, THEN the pure decision, THEN the conditional write.
- `promoteFromWaitlistIfEligible` (REQ-023 §3 step 1): identical shape — lock `events` first,
  re-count admitted inside the same tx, decide, write.
- `commitWalkin` (REQ-030 §6.2 step 1): identical shape, plus a boolean `overrideConfirmed`
  parameter threaded into the pure decision (`decideWalkinOutcome`), which returns
  `needs-override-confirmation` when `seatsLeft <= 0 && !overrideConfirmed`, or admits when
  `seatsLeft > 0 || overrideConfirmed`.

**This design reuses the exact same shape for approval, with `commitWalkin`'s
`overrideConfirmed` threading as the direct precedent** (§2 below defines
`decideApprovalOutcome` as a structural copy of `decideWalkinOutcome`'s override branch).
The `SELECT ... FOR UPDATE` on the `events` row is what makes AC5's concurrency guarantee
hold: Postgres serializes any two transactions that both take a row lock on the same
`events.id` — the second transaction's `SELECT ... FOR UPDATE` blocks until the first
commits or rolls back, so the second transaction's subsequent admitted-count re-read
always sees the first transaction's already-committed write. Two concurrent approvals for
the last seat therefore cannot both observe `seatsLeft > 0`: the loser's fresh count (read
after the lock is granted, never before) already reflects the winner's commit, and the
loser is routed to `needs-override-confirmation` instead of writing. This is a
conditional-write-inside-a-lock pattern, not a `SELECT` count checked outside a
transaction and written after — the same distinction REQ-020's own docstring names ("the
check and the write must be atomic, not read-then-write", S7's negative case, verbatim).
This is also exactly what makes AC5 testable with a real Postgres and 20+ repeats
(TEST-DESIGNER's scope): the row lock is a database-level serialization primitive, not an
in-process mutex, so it holds across separate connections/processes the way a concurrency
test needs it to.

### 0.2 Capacity override — reuses REQ-030's shape, NOT REQ-029's `overrideAdmitAndCheckIn`, with the difference traced

Two existing "explicit confirmed override + audit" precedents were read in full:

- **REQ-029's `overrideAdmitAndCheckIn`** (`domain/registration.ts` line ~1520): admits AND
  checks in in the same write (`admission: "admitted", checkedInAt: at, checkedInBy: ...,
  checkInMethod: "manual"`), one audit action `"registration.override_admit_checkin"`.
  Its own pure decision, `decideOverrideOutcome`, has **no capacity/seatsLeft parameter at
  all** — by design (its own comment: "this transition IS the explicit override, so
  re-running the capacity gate here would contradict the very invariant it exists to
  satisfy"). This function exists to resolve a **QR check-in refusal** (the person scanned
  a valid token but their `admission` was not `"admitted"` — `requested`/`waitlisted`/
  `rejected`/`withdrawn`), a person **physically at the door**. It is not conditioned on
  capacity at all; the organizer can invoke it regardless of seats left, because at that
  point the person is standing there and check-in is happening in the same act as the
  admit. **This does not fit REQ-035's shape**: REQ-035's approve happens away from the
  door (an organizer working through a request list, days before the event), must NOT set
  `checkedInAt`/`checkedInBy`/`checkInMethod` (the person hasn't shown up yet), and DOES
  need a genuine capacity gate (approving a fourth request when only 3 seats remain must
  require confirmation; approving the fourth when 5 seats remain must not).
- **REQ-030's `commitWalkin`** (`domain/walkin.ts` §5/§6): a boolean `overrideConfirmed`
  parameter flows into the pure decision `decideWalkinOutcome`, which — inside the SAME
  locked-and-recounted transaction — returns `needs-override-confirmation` when
  `seatsLeft <= 0 && !overrideConfirmed`, or an admitting outcome when
  `seatsLeft > 0 || overrideConfirmed`. The audit action string itself differs by branch:
  `seatsLeft > 0 ? "registration.walkin_admit" : "registration.walkin_override_admit"` —
  the override is recorded by **which audit action string is written**, not a separate
  boolean payload field, and this is what "logs the override" means operationally in this
  codebase's existing convention.

**Decision: REQ-035's approval reuses REQ-030's exact shape** — an `overrideConfirmed`
boolean parameter, threaded through a new pure decision function (`decideApprovalOutcome`,
§2) that needs a `needs-override-confirmation` branch, and a distinct audit action string
per branch (`"registration.approve"` vs. `"registration.approve_override"`, §4) — applied
to a plain admit (no check-in fields touched), never REQ-029's admit+checkin combination.

### 0.3 Notification kind — `admission_result` is reused for BOTH approve and reject, traced to show why one kind cannot collide

`domain/notification.ts`'s `NotificationKind` union already contains `"admission_result"`
(added by an earlier requirement, never yet called from production code — confirmed by
`grep`: its only current appearances are in `notification.test.ts`). `notification_ledger`
carries `UNIQUE(registration_id, kind)` — the entire idempotency mechanism is per
`(registration, kind)` pair, not per outcome value.

**Why one kind is sufficient, not two:** a single `registrations` row's `admission` column
starts at `"requested"` (REQ-034) and this requirement's own two writers (§3, §4) are the
ONLY writers in the whole codebase that transition a `"requested"` row onward, to exactly
one of `"admitted"` or `"rejected"` — both terminal for this requirement's purposes (a
rejected row is never later approved; an approved row's REQ-029/REQ-030 override paths
send no `admission_result`-kind notification at all, confirmed by reading both files above
— `overrideAdmitAndCheckIn`'s caller (`checkinQr.ts`) and `commitWalkin` each only
`ctx.reply` directly to the *organizer*, never call `sendLedgeredNotification` for the
*attendee*). Therefore, for any single registration, at most ONE of "approve" or "reject"
ever calls `sendLedgeredNotification` with `kind: "admission_result"` — the unique index is
never asked to hold two different sends for the same registration under the same kind,
because the second call site structurally never fires for a row the first one already
claimed (both check `admission === "requested"` as their own precondition inside the same
locked transaction that performs the state transition — see §3/§4). **Conclusion: no new
`NotificationKind` literal is added.** The outcome-specific content (approved vs. rejected
+ reason + onward path) lives entirely in `composeMessage`'s branching, not in the ledger
key — matching `sendLedgeredNotification`'s own documented purpose (idempotency across
retries of the SAME logical send), not "distinguish outcome A from outcome B," which no
part of REQ-025's design ever assigns to `kind`. This satisfies the issue text's "distinct
kind per outcome so an approve and a later state change cannot collide on one ledger key"
by construction: there is no "later state change" reachable from an already-decided
registration that would attempt a second `admission_result` send for the same row, because
no such code path exists anywhere in this design or the ones it builds on.

### 0.4 Zero Wishlist — confirmed

No table, migration, or row named `wishlist` (or any synonym) appears anywhere in this
design. The reject path's onward offer reuses the **exact existing string**
`catalog.event.deepLinkSeeUpcoming` (`i18n/en.ts` line 74, `"See what's coming up with
/events"`) — the identical reuse REQ-027's cancellation-notice design already established
for the same purpose (`docs/agents/design/REQ-027.md` §4, "reuses REQ-017's existing
`/events` pattern exactly, no new key"). No new catalog key is created for the onward
path itself; only the reason line and a fixed rejection-header line are new (§7).

### 0.5 Authorization — reuses `requireOrganizerForChapter` unchanged, checked on every handler, not the menu

`domain/eventAuthorization.ts`'s `requireOrganizerForChapter(db, tgId, targetChapterId)`
(REQ-016) is the exact function every callback handler in §6 calls FIRST, before reading
or writing anything else — the same discipline `checkinQr.ts`'s
`makeCheckinOverrideCallbackHandler` already establishes for REQ-029's organizer-only
override callback. `EventStaff` rows grant no rights here: this function's own logic
(`checkOrganizerForChapter`) never consults `event_staff` at all — only `users.role` and
`users.chapterId` — so an EventStaff member (whose `users.role` is `"member"`, per
`docs/agents/design/REQ-018.md`'s convention: EventStaff is a *separate* grant table, not
a role value) is refused with `{ ok: false, reason: "not-organizer" }` structurally,
without this design needing to special-case it.

## 2. The pure decision — `decideApprovalOutcome`

**New function, `domain/registration.ts`, structural copy of `decideWalkinOutcome`'s
override-threading shape (§0.1/§0.2), applied to the narrower "approve a requested row"
case — no event-status/finished checks are added here beyond what AC requires**, because
approving an already-cancelled or already-finished event's request is out of this
requirement's stated AC list; open question 3 below flags this explicitly rather than
silently adding or silently omitting a check no AC asks for.

```
export interface ApprovalDecisionInput {
  registrationExists: boolean;
  admission: AdmissionState | null;
  seatsLeft: number;
  overrideConfirmed: boolean;
}

export type ApprovalOutcome =
  | { kind: "not-found" }
  | { kind: "not-requested"; admission: AdmissionState }
  | { kind: "needs-override-confirmation" }
  | { kind: "approve" }
  | { kind: "approve-override" };
```

**First-match-wins table, implemented in this exact order:**

| # | Condition | Result |
|---|---|---|
| 1 | `!registrationExists` | `{ kind: "not-found" }` |
| 2 | `admission !== "requested"` | `{ kind: "not-requested", admission }` |
| 3 | `seatsLeft > 0` | `{ kind: "approve" }` |
| 4 | `overrideConfirmed` (only reached when `seatsLeft <= 0`) | `{ kind: "approve-override" }` |
| 5 | (else — `seatsLeft <= 0 && !overrideConfirmed`) | `{ kind: "needs-override-confirmation" }` |

Row 2 is what makes a double-approve (or approve-after-reject) a no-op refusal rather than
a second write — the same "every non-writing outcome returns unchanged" discipline every
other transactional writer in this file already follows. Rows 3–5 are `decideWalkinOutcome`'s
own override-threading table (§0.1), narrowed to two outcome-producing branches
(`approve`/`approve-override`) instead of walk-in's combined admit+checkin branch, because
this decision never touches `checkedInAt`/`checkedInBy`/`checkInMethod` (§0.2).

## 3. `approveRequest` — the transactional write

```
export type ApproveRequestResult = ApprovalOutcome & {
  eventId?: string;
  userId?: string;
  qrToken?: string;
};

export async function approveRequest(
  db: DbClient["db"],
  registrationId: string,
  organizerUserId: string,
  overrideConfirmed: boolean,
  at: Date,
): Promise<ApproveRequestResult>;
```

**Steps, inside one `db.transaction`:**

1. `SELECT id, eventId, userId, admission FROM registrations WHERE id = $1 FOR UPDATE` —
   locks the registration row (not the event row directly; see step 2's own lock).
2. If found: `SELECT id, capacity FROM events WHERE id = registration.eventId FOR UPDATE`
   — locks the `events` row, the SAME serialization point REQ-020/023/030 already use
   (§0.1). If the registration row itself is not found, skip straight to the decision with
   `registrationExists: false` (no event lock needed).
3. Fresh admitted count: `SELECT count(*) FROM registrations WHERE eventId = $1 AND
   admission = 'admitted'` inside the same transaction (reuses `countAdmittedRegistrations`,
   already exported from `domain/event.ts`).
4. `seatsLeft = computeSeatsLeft(event.capacity, admittedCount)` (existing pure function,
   unchanged).
5. Call `decideApprovalOutcome` (pure, §2) with the locked registration's own
   `admission`/existence, `seatsLeft`, and the caller-supplied `overrideConfirmed`.
6. `not-found` / `not-requested` / `needs-override-confirmation` all return unchanged: no
   write, no audit row (mirrors every other non-writing branch in this file).
7. `approve` / `approve-override` (the two writing branches):
   - `qrToken = generateQrToken()` — **the existing function** (line ~90 of this same
     file), called here and nowhere newly defined (PRD FR-14, the issue's own explicit
     instruction — "not a second generator").
   - `UPDATE registrations SET admission = 'admitted', qrToken = $1 WHERE id = $2` — only
     these two columns; `checkedInAt`/`checkedInBy`/`checkInMethod` are never touched
     (§0.2's traced distinction from REQ-029's override).
   - `writeAuditLog(tx, { actorUserId: organizerUserId, action: outcome.kind === "approve"
     ? "registration.approve" : "registration.approve_override", entity: "registration",
     entityId: registrationId, payload: { eventId }, at })` — exactly one row, same
     transaction as the `UPDATE` (S8), mirrors `commitWalkin`'s own
     `seatsLeft > 0 ? ... : ..._override` audit-action-naming convention (§0.2).
8. Return the outcome plus `eventId`/`userId` (for the caller to compose and send the
   notification outside this transaction, same separation `registerForEvent`'s caller
   already uses — the notification send is not part of the atomic write) and `qrToken`
   when a writing branch fired.

## 4. `rejectRequest` — the pure decision and the transactional write

### 4.1 `decideRejectionOutcome` — pure, no I/O

```
export interface RejectionDecisionInput {
  registrationExists: boolean;
  admission: AdmissionState | null;
}

export type RejectionOutcome =
  | { kind: "not-found" }
  | { kind: "not-requested"; admission: AdmissionState }
  | { kind: "reject" };

export function decideRejectionOutcome(input: RejectionDecisionInput): RejectionOutcome;
```

First-match-wins table: (1) `!registrationExists` → `not-found`; (2) `admission !==
"requested"` → `{ kind: "not-requested", admission }`; (3) else → `{ kind: "reject" }`.
No capacity input at all — rejecting never touches `seatsLeft` (rejecting a request never
consumes or frees a seat by itself; it simply never becomes an admitted seat).

### 4.2 `rejectRequest` — the transactional write

```
export async function rejectRequest(
  db: DbClient["db"],
  registrationId: string,
  organizerUserId: string,
  reason: string,
  at: Date,
): Promise<RejectionOutcome & { eventId?: string; userId?: string }>;
```

Steps, inside one `db.transaction`: (1) `SELECT ... FROM registrations WHERE id = $1 FOR
UPDATE`; (2) `decideRejectionOutcome` (pure); (3) non-`reject` outcomes return unchanged,
no write, no audit row; (4) `reject`: `UPDATE registrations SET admission = 'rejected',
noShowReason` is **not** touched (that column is a different concept, REQ-032's no-show
reason — this design reuses no column for the rejection reason text itself; §Open
Question 1 below names where the reason text is carried, since no AC requires it be
stored on the row at all, only that the notification *message* contains it); (5)
`writeAuditLog(tx, { actorUserId: organizerUserId, action: "registration.reject", entity:
"registration", entityId: registrationId, payload: { eventId, reason }, at })` — the
reason is captured in the audit payload (already a `jsonb`/free-form column per
`auditLog.ts`'s existing `payload: Record<string, unknown> | null` shape, no schema
change), exactly one row, same transaction as the `UPDATE` (S8).

## 5. The notification sends — both via `sendLedgeredNotification`, both `kind: "admission_result"`, both `classification: "transactional"`

Both approve and reject call the EXISTING `sendLedgeredNotification` (`domain/
notification.ts`, unchanged signature) exactly once, from the handler layer (§6), after
the transactional write above has committed — same two-phase separation
`promoteFromWaitlistIfEligible`'s own caller already uses (write commits first, send
happens after, never inside the same DB transaction, since a Telegram API call must never
hold a Postgres row lock open).

| Field | Approve call | Reject call |
|---|---|---|
| `kind` | `"admission_result"` | `"admission_result"` |
| `classification` | `"transactional"` (S10 — admission result is always sent, ignoring `broadcast_opt_in`) | `"transactional"` |
| `registrationId` | the approved registration's id | the rejected registration's id |
| `userId` | the registrant's `userId` (returned by `approveRequest`) | the registrant's `userId` (returned by `rejectRequest`) |
| `composeMessage` | returns `{ kind: "text", text: <approved message> }` — event title/date-time (fetched the same way `registerForEvent`'s caller already fetches them) plus a line stating the qr_token is ready (mirrors `registerForEvent`'s existing "admitted" confirmation composition, `handlers/registration.ts`, reused pattern not reused code, since this call site is a different handler) | returns `{ kind: "text", text: <rejected message> }` — the organizer's `reason` (verbatim, trimmed) AND the onward-path line `catalog.event.deepLinkSeeUpcoming` (§0.4), both always present in the composed text |

Because `classification: "transactional"` is passed explicitly (never defaulted — the
type has no `?`, per `notification.ts`'s own AC5 comment), `sendLedgeredNotification`'s
Step 3 (the marketing-only `broadcast_opt_in` gate) is structurally never reached for
either send — this is what makes S10's "reaches a user with `broadcast_opt_in=false`"
true by construction, not by a runtime check this design adds.

## 6. Handlers — `apps/bot/src/handlers/organizerRequests.ts` (new file)

Framework-free domain logic lives entirely in §1–§5 above (decisions/0004) — this file
only sequences calls, checks authorization, and sends replies, the same division every
other handler file in this codebase already follows.

### 6.1 `/requests <event_id>` — the list command

```
export function makeRequestsListHandler(db: DbClient["db"]);
```

1. Resolve `tgId`/`lang` (same pattern as every other handler).
2. Parse `event_id` from the command args (same first-token parse `checkin.ts` uses when
   no search query is supplied — the search query for this surface arrives via a callback
   flow, not the initial command, per Open Question 2).
3. `getEventById` — not-found → the existing "event not found" style reply, a NEW catalog
   key (§7) since this is a different command's own not-found line.
4. **`requireOrganizerForChapter(db, BigInt(tgId), event.chapterId)`** — checked HERE, on
   the command handler itself, before any list data is fetched (S2). Refusal → a NEW
   "not authorized" catalog key (deliberately distinct wording from `checkin.notAuthorized`,
   since this is an organizer-only screen, not an event-staff one — reusing the check-in
   string would misdescribe who is allowed).
5. `listPendingRequestsForOrganizer` (§1) → render via a new `renderRequestsListMessage`
   composition function (mirrors `renderCheckinListMessage`'s shape: header line with the
   event title and pending count, one inline-keyboard row per request showing
   `displayName [+ " — " + company]`, each row's callback data `req:open:<registrationId>`
   — opening a request shows the full detail (position/student/source) plus Approve/Reject
   buttons, since F3's per-row fields (company, position, student, source) do not all fit
   on one keyboard button label the way check-in's single `company` field does).
6. Pagination and the search hint reuse `PAGE_SIZE`/`SEARCH_RESULT_LIMIT` from `checkin.ts`
   (§1.1) — a `req:page:<eventId>:<n>` callback, structurally identical to
   `CHECKIN_PAGE_PATTERN`.

### 6.2 `req:open:<registrationId>` — detail view

Re-runs `requireOrganizerForChapter` (S2 — checked on this action too, not only the list
entry), then renders one request's full detail (all six fields from §1's
`PendingRequestListItem`, still never phone/email) with two buttons: `req:approve:<id>`
and `req:reject:<id>`.

### 6.3 `req:approve:<registrationId>` — the approve callback

1. Re-run `requireOrganizerForChapter` against the registration's own event's `chapterId`
   (fetched via a small existing-shaped read, mirroring `getEventIdForRegistration` +
   `getEventById`) — S2's negative case (chapter-A organizer, chapter-B event) is refused
   here, on this exact handler, not only at step 5.
2. Call `approveRequest(db, registrationId, organizerUserId, overrideConfirmed: false, at)`.
3. `not-found`/`not-requested` → a NEW "no longer pending" catalog key, no further action.
4. `needs-override-confirmation` → render a confirmation prompt (mirrors
   `formatWalkinOverrideMessage`'s existing shape: states the current admitted count vs.
   capacity, asks for explicit confirmation) with two buttons: `req:approve:confirm:<id>`
   (re-invokes step 2 with `overrideConfirmed: true`) and a Cancel button that leaves the
   registration untouched (AC4's "dismissing it leaves admission='requested' unchanged" —
   true because the Cancel button's callback performs no domain call at all, only edits
   the message back to the detail view or a no-op acknowledgement).
5. `approve` / `approve-override` → send the approval notification (§5), then reply to the
   organizer confirming the action, then remove/replace the just-decided request from the
   still-open list view if one is in scope (Open Question 4).

### 6.4 `req:reject:<registrationId>` — the reject-with-reason flow

STORY-DETAILS F3 requires a reason; this needs a short free-text capture, which this
codebase already has a precedent for (REQ-032's no-show "other" reason free-text path,
`domain/registration.ts`'s `writeNoShowReason` call site) — a `ctx.session`-free
prompt-then-await-next-message pattern grammY conversations already support elsewhere in
this codebase (Open Question 5 names the exact mechanism choice, since this design does
not prescribe grammY session/conversation plumbing — that is implementation, not design).

1. Re-run `requireOrganizerForChapter` (same as §6.3 step 1).
2. Prompt the organizer for a reason (a new catalog key).
3. On the next text message from that organizer (scoped to this specific
   registrationId — the exact scoping mechanism is BACKEND-DEV's plumbing choice, Open
   Question 5), call `rejectRequest(db, registrationId, organizerUserId, reasonText, at)`.
4. `not-found`/`not-requested` → the same "no longer pending" catalog key as §6.3 step 3.
5. `reject` → send the rejection notification (§5, reason + onward path both present),
   reply to the organizer confirming the action.

## 8. Open questions (not silently resolved)

1. **Where the rejection reason text is carried between the handler's capture and
   `rejectRequest`'s call** — this design passes it as a plain `reason: string` parameter
   and stores it only in the `audit_log.payload` (§4.2) and the notification text (§5), not
   on `registrations` itself (no AC asks for a stored, queryable rejection-reason column,
   and `registrations.noShowReason` is a different, unrelated concept per REQ-032). If a
   later requirement needs to list past rejection reasons outside the audit log, that is a
   new stored-data question for `DATA-DESIGNER`, not something this design should
   preemptively add a column for.
2. **The exact plumbing location for the shared `PAGE_SIZE`/`SEARCH_RESULT_LIMIT`
   constants and the search-filter helper** (currently exported from `handlers/checkin.ts`)
   — whether this requirement imports them from that file as-is, or whether BACKEND-DEV
   hoists them to a shared module first, is an implementation-level plumbing choice with no
   behavioral consequence either way.
3. **Whether approving/rejecting a request for an event that has since been cancelled or
   has finished should be refused with a distinct message** — no AC in this requirement's
   list names that case, and §2/§4.1's decision tables deliberately do not add an
   event-status check no AC requires. If Release 2's later requirements (REQ-036's
   scheduled auto-decline, explicitly out of this requirement's scope per the issue text)
   need this, it is that requirement's concern, not silently added here.
4. **Whether the list view auto-refreshes/removes a just-decided row from an
   organizer's other open session viewing the same list** — no AC requires cross-session
   consistency of an open list view; the decided row simply stops appearing the next time
   `/requests` or a page turn is invoked, the same "no push update to a stale rendered
   list" behavior `checkin.ts`'s own toggle handler already accepts (its own design note:
   "the stale row's button is deliberately left as-is until the next full render").
5. **The exact mechanism for scoping "the organizer's next text message" to the specific
   reject-in-progress registration** (grammY conversations plugin, a short-lived in-memory
   map keyed by `(organizerUserId, registrationId)`, or a stored pending-action row) is
   implementation, not design — BACKEND-DEV chooses the mechanism; this design only
   specifies the resulting `rejectRequest(db, registrationId, organizerUserId, reasonText,
   at)` call must eventually fire with the organizer-supplied text.
