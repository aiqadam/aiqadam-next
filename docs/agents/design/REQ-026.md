## 0. REQ-011's `agenda[]` shape — confirmed sufficient, not a blocker

Checked `apps/bot/src/domain/event.ts` directly, per this task's mandatory instruction:

```
export interface AgendaItem {
  kind: string;
  at: string; // ISO timestamp
  label: string;
}
```

A doors item is identified as **the element whose `kind` field equals the literal string
`"doors"`** — this is not an invention of this design; it is the exact same check
`validateAgenda` (REQ-016, `event.ts` line 73/80) already uses to enforce "at most one
doors item" and "doors item not later than `starts_at`", and the exact same check
`docs/agents/design/REQ-011.md` §3's proven `jsonb_path_query_first(...'$[*] ? (@.kind ==
"doors").at')` query performs at the database level. REQ-017's card renderer
(`buildEventCardContent`) already maps every `agenda` item (doors included) through this
same `kind`/`at`/`label` shape. **This is sufficient to build REQ-026 on — not a
blocker.** No competing convention is introduced here; this design reuses `kind ===
"doors"` exactly as REQ-016/017 already do.

REQ-016's own validation (`validateAgenda`) additionally guarantees, for any published
event, that **at most one** `agenda` item has `kind === "doors"` — so "the doors item"
(singular) is well-defined for every event this design will ever read.

## 1. What must change in REQ-025's already-built files (stated precisely — a design
extension, not a rewrite)

Reading `apps/bot/src/domain/notification.ts` and `apps/bot/src/scheduler/rateLimiter.ts`
directly: REQ-025's `NotificationSender.send(tgId, text)` sends **plain text only** — no
inline keyboard, no photo. REQ-026 needs both (T-24h's two buttons; T-3h's QR photo with
caption). This is a genuine, load-bearing gap in REQ-025's send API that REQ-026 must
close — the requirement text says "reuse `sendLedgeredNotification`, don't reimplement,"
which this design honors by **extending** that one shared function's capability, not by
building a second, parallel send path alongside it.

### 1.1 `domain/notification.ts` — type changes


### 1.2 `sendLedgeredNotification`'s step 5 — the ordered rule table, REQ-025's §3.1
extended (not replaced)

Steps 1-4 are **unchanged from REQ-025** (user lookup, blocked check, marketing
broadcast-opt-in check, the atomic ledger `INSERT`). Only step 5 changes:

| Step | Action | Outcome |
|---|---|---|
| 5 | Only reached once step 4's insert has committed. Call `input.composeMessage(resolvedLang)`. | Result `{ kind: "skip" }` → return `{ kind: "skipped-stale" }`. **No `sender` call is made** — this is the at-send-time recheck's outcome (§3 below) for a registration that stopped being admitted, or an event that stopped being published, between selection and send. | | | Result `{ kind: "photo", photo, caption }` → call `input.sender.sendPhoto(user.tgId, photo, caption)`. |
| | | Either call succeeding → return `{ kind: "sent" }`. Either call throwing → return `{ kind: "failed", error }`, exactly as REQ-025 already specifies. |

### 1.3 `scheduler/rateLimiter.ts` — `createRateLimitedSender`'s extended behavior

| Concern | Rule |
|---|---|
| `send(tgId, text, buttons?)` | Unchanged pacing/429/backoff mechanism (REQ-025 §5). ## 3. New domain reads: `domain/reminders.ts` (new file, framework-free, no `grammy`)

### 3.1 Candidate selection — one query per job, evaluation-time-as-parameter

```
export interface ReminderCandidate {
  registrationId: string;
  userId: string;
}

export async function selectRegistrationsForReminder24h(
  db: DbClient["db"],
  evaluationTime: Date,
): Promise<ReminderCandidate[]>;

export async function selectRegistrationsForReminder3h(
  db: DbClient["db"],
  evaluationTime: Date,
): Promise<ReminderCandidate[]>;
```

Both are one `SELECT` joining `registrations` → `events`, filtered by:

| Filter | `selectRegistrationsForReminder24h` | `selectRegistrationsForReminder3h` |
|---|---|---|
| `registrations.admission` | `= 'admitted'` | `= 'admitted'` |
| `events.status` | `= 'published'` | `= 'published'` |
| `events.starts_at` | `> evaluationTime` AND `<= evaluationTime + 24h` | `> evaluationTime` AND `<= evaluationTime + 3h` |

This is a **selection window**, not a single-instant match — a registration whose event
starts in 23h59m is still selected by the 24h query on this tick and every subsequent
tick until `starts_at` passes, exactly as it is by a re-run after a restart. This is
deliberately over-inclusive: `sendLedgeredNotification`'s `UNIQUE(registration_id, kind)`
ledger constraint (REQ-025 §3.1 step 4) is what actually enforces "sent at most once" —
the selection query's only job is "don't miss the window," never "be the sole
idempotency guard." Same division of responsibility REQ-025 §3.2 already establishes
between "what selects a candidate" (a job, here) and "what guarantees at-most-once" (the
ledger, unchanged).

No lower bound narrower than the window's own width is needed: the two acceptance
criteria this selects for (AC1, AC5/AC6/AC7/AC8) are both about "the window has been
entered," not "the window was entered on this exact tick."

### 3.2 Doors-item lookup — signature only, rule stated in prose (not code)

```
export function findDoorsAgendaItem(agenda: AgendaItem[] | null): AgendaItem | null;
```

**Rule, stated exactly, implemented literally:**

| Input | Output |
|---|---|
| `agenda` is `null`, or an array with no element whose `kind` equals the literal string `"doors"` | `null` — no doors time to render; the T-3h message quotes `starts_at` alone (AC8). |
| `agenda` contains exactly one element whose `kind` equals `"doors"` | that element. |
| `agenda` contains more than one element whose `kind` equals `"doors"` | unreachable for any event this design ever reads — REQ-016's `validateAgenda` (already implemented, `event.ts` line 73-76) refuses a second doors item at edit time, before an event can ever be published with two. This function does not need — and must not add — its own handling for that case. |

This function lives in `domain/event.ts` (alongside `AgendaItem`, `validateAgenda`), not
`domain/reminders.ts`, since it operates purely on the `AgendaItem[]` shape REQ-011/016
already own there.

## 4. New domain write: `domain/registration.ts`'s reconfirm path (AC1, AC2)

Mirrors `decideWithdrawOutcome`/`withdrawRegistration`'s existing shape exactly (same
file, same conventions) — a pure decision function plus a transactional write, not a new
pattern.

```
export interface ReconfirmDecisionInput {
  registrationExists: boolean;
  ownerUserId: string | null;
  actingUserId: string;
  admission: AdmissionState | null;
}

export type ReconfirmOutcome =
  | { kind: "not-found" }
  | { kind: "not-owner" }
  | { kind: "not-eligible"; admission: AdmissionState }
  | { kind: "reconfirmed" };

export function decideReconfirmOutcome(input: ReconfirmDecisionInput): ReconfirmOutcome;

export async function reconfirmRegistration(
  db: DbClient["db"],
  registrationId: string,
  actingUserId: string,
  at: Date,
): Promise<ReconfirmOutcome>;
```

**`decideReconfirmOutcome`'s table, first-match-wins** (same convention
`decideWithdrawOutcome` already documents in its own header comment):

| Order | Condition | Result |
|---|---|---|
| 1 | `!registrationExists` | `{ kind: "not-found" }` |
| 2 | `ownerUserId !== actingUserId` | `{ kind: "not-owner" }` |
| 3 | `admission !== "admitted"` | `{ kind: "not-eligible", admission }` — covers the race where the person withdrew (via `/withdraw` or the T-24h decline button on another device) between the reminder being sent and "I'll be there" being tapped. |
| else | | `{ kind: "reconfirmed" }` |

**`reconfirmRegistration`'s transaction, same shape as `withdrawRegistration`'s (§2.2 in
`registration.ts`'s existing header comments):**

1. `SELECT ... FOR UPDATE` the registration row (id, `user_id`, `admission`) — fresh read
   inside this transaction, never reused from whatever data populated the reminder
   message (same discipline `withdrawRegistration` §2.3 already states).
2. Build `ReconfirmDecisionInput` from that row plus the caller's `actingUserId`; call
   `decideReconfirmOutcome` (pure).
3. Any outcome other than `"reconfirmed"` → return unchanged, **no write, no audit row**
   (same "every non-writing outcome returns unchanged" discipline `withdrawRegistration`
   §2.2 step 3 already follows).
4. `"reconfirmed"` → one `UPDATE registrations SET reconfirmed_at = at WHERE id = ...`
   (this is the **only** column touched — `admission` is never written by this function,
   which is what makes AC2's "admission UNCHANGED" true structurally, not by convention),
   then one `writeAuditLog` row (`action: "registration.reconfirm"`, `entity:
   "registration"`, `entityId`, `payload: { eventId: row.eventId }`, `at` — same shape
   every other write in this file already uses, S8).
5. Return `{ kind: "reconfirmed" }`.

## 5. The two scheduled jobs: `scheduler/reminderJobs.ts` (new file)

```
export function makeReminder24hJob(
  db: DbClient["db"],
  sender: NotificationSender,
  intervalMs: number,
): ScheduledJobDefinition;

export function makeReminder3hJob(
  db: DbClient["db"],
  sender: NotificationSender,
  botUsername: string,
  intervalMs: number,
): ScheduledJobDefinition;
```

Each returns a `ScheduledJobDefinition` (`runner.ts`, REQ-025 §7 — unchanged interface)
whose `run(evaluationTime)`:

1. Calls the matching `selectRegistrationsFor...` (§3.1) with `evaluationTime`.
2. For each returned `{ registrationId, userId }`, calls `sendLedgeredNotification` with
   `db`, `sender`, that `registrationId`, `kind: "reminder_24h"` (or `"reminder_3h"`),
   `classification: "transactional"`, that `userId`, and the `composeMessage` closure
   specified in §5.1/§5.2 below. Candidates are processed one at a time (matches this
   codebase's existing `for (const row of rows) { await ... }` sequential-await
   precedent in `handlers/my.ts` §3 step 5 — no `Promise.all` fan-out, so the rate
   limiter's pacing (§1.3) sees a predictable, ordered stream of calls rather than a
   burst).
3. A single candidate's `sendLedgeredNotification` outcome is not branched on by the job
   (matches REQ-024 §5 open question 3's "let the framework's own promise-rejection
   behavior apply" precedent, extended: `sendLedgeredNotification` itself never throws,
   per REQ-025 §3.1's closing line, so there is nothing to catch here regardless). One
   candidate's `"failed"` outcome does not stop the loop from processing the rest.

`intervalMs`: **300000 (5 minutes)** for both jobs — a technical scheduling parameter,
not a product ambiguity (same "concrete numbers so TEST-DESIGNER has something precise
to test against" reasoning REQ-025 §5 already states for its own rate-limiter defaults).
Five minutes keeps both reminder windows (§3.1) comfortably wide relative to the tick
interval at PRD 1's stated load, and the ledger (not the tick cadence) is what actually
guarantees at-most-once delivery, so a shorter or longer interval would not change
correctness — only latency within the window.

### 5.1 T-24h `composeMessage(lang)` — text + two buttons (AC1, AC2, AC4, AC10)

1. Call `getRegistrationAdmissionAndEvent(db, registrationId)` (§2).
2. If the result is `null`, or `admission !== "admitted"` → return `{ kind: "skip" }`
   (AC4's race case: withdrawn between selection and send).
3. Otherwise call `getEventByIdWithChapterTimezone(db, eventId)` (REQ-017, unchanged). If
   the event is `null`, or `status !== "published"` → return `{ kind: "skip" }` (a
   cancelled event gets REQ-027's message instead, never this one, per the requirement
   text).
4. Compose:
   ```
   text = [
     catalog.reminder24h.prompt,
     event.title,
     formatDateTimeInTimezone(event.startsAt, event.chapterTimezone, lang),
   ].join("\n")

   buttons = [
     { label: catalog.reminder24h.confirmButton, callbackData: `reminder24h:confirm:${registrationId}` },
     { label: catalog.reminder24h.declineButton, callbackData: `reminder24h:decline:${registrationId}` },
   ]
   ```
5. Return `{ kind: "text", text, buttons }`.

This is the **one message with two buttons** AC1 requires — a single `composeMessage`
call producing a single `ComposedMessage`, sent by a single `sendLedgeredNotification`
call keyed `(registrationId, "reminder_24h")`.

### 5.2 T-3h `composeMessage(lang)` — photo + caption (AC5, AC6, AC7, AC8, AC10)

1. Steps 1-3 identical to §5.1 (recheck admission and event status; `{ kind: "skip" }`
   on either failing).
2. Fetch the venue: `getVenueById(db, event.venueId)` (`domain/venue.ts`, unchanged) —
   `null` when `venueId` is `null` (defensive; every published event has a venue per
   REQ-016's publish gate, so this is not expected to occur in practice, same
   "unreachable in practice, guarded anyway" discipline this file's other reads already
   follow).
3. `doorsItem = findDoorsAgendaItem(event.agenda)` (§3.2).
4. Compose the caption's lines, in order:
   - `catalog.reminder3h.header`
   - `event.title`
   - **When `doorsItem !== null`:** `` `${catalog.reminder3h.doorsLabel} ${formatDateTimeInTimezone(new Date(doorsItem.at), event.chapterTimezone, lang)}` `` — **this exact call**, same function, same three arguments in the same order as `buildEventCardContent`'s `agendaLines` mapping already applies to this same doors item (`domain/event.ts`, the `agendaLines` line inside `buildEventCardContent`) — this identity of call-and-arguments is what makes AC7's "byte-for-byte identical to REQ-017's event card" hold **structurally**, not by coincidence of two independently-written format strings agreeing.
   - `` `${catalog.reminder3h.startLabel} ${formatDateTimeInTimezone(event.startsAt, event.chapterTimezone, lang)}` `` — always present, doors or not (AC6, AC8).
   - `venue?.address ?? ""`
   - `venue?.yandexUrl ?? ""`
   - `venue?.googleUrl ?? ""`
   joined with `"\n"`.
5. `png = await renderCheckInQrPng({ botUsername, qrToken })` (REQ-024's shared renderer,
   unchanged, reused exactly as `handlers/my.ts` already calls it) — **`qrToken` here is
   the registration's own `qr_token`** (read alongside `admission`/`eventId` — §2's
   `getRegistrationAdmissionAndEvent` gains a `qrToken: string | null` field for this
   purpose, since the T-3h path is the first `composeMessage` caller that needs it). If
   `qrToken` is `null` (defensive — every admitted registration has one per REQ-020 §3.2
   step 8; unreachable in practice), return `{ kind: "skip" }` rather than sending a
   caption-only message that silently drops AC5's QR requirement.
6. Return `{ kind: "photo", photo: png, caption }`.

**AC8's negative case, stated explicitly:** when `event.agenda` is non-empty but every
element's `kind` is something other than `"doors"` (e.g. `"networking"`, `"close"`),
`findDoorsAgendaItem` (§3.2's table, row 1) returns `null` — the doors line is omitted
and no other agenda item's time is ever rendered anywhere in this composition (the loop
above never iterates `agenda` for anything but the one `findDoorsAgendaItem` lookup), so
a loose "any agenda item" match is structurally impossible here.

`getRegistrationAdmissionAndEvent`'s `qrToken` field (§2, amended):

```
export interface RegistrationAdmissionAndEvent {
  admission: AdmissionState;
  eventId: string;
  userId: string;
  qrToken: string | null;
}
```

## 7. New handler module: `handlers/reminder24h.ts` (AC1, AC2)

Same `<domain>:<action>:<param>` `callback_data` convention `withdraw.ts` already
establishes (§4.1's own header note).

```
export const REMINDER24H_CONFIRM_PATTERN = /^reminder24h:confirm:(.+)$/;
export const REMINDER24H_DECLINE_PATTERN = /^reminder24h:decline:(.+)$/;

export function makeReminder24hConfirmCallbackHandler(
  db: DbClient["db"],
): (ctx: Context) => Promise<void>;

export function makeReminder24hDeclineCallbackHandler(
  db: DbClient["db"],
  sender: NotificationSender,
): (ctx: Context) => Promise<void>;
```

### 7.1 Confirm handler ("I'll be there") — AC2's first half

1. Extract `registrationId` from `REMINDER24H_CONFIRM_PATTERN`'s capture group (defensive
   `undefined` guard, same shape `withdraw.ts`'s confirm handler already uses).
2. Resolve `actingUser` via `resolveActingUser(db, BigInt(ctx.from.id))` (unchanged,
   `eventAuthorization.js`) — `null` → `ctx.answerCallbackQuery()` then
   `catalog.profile.startFirst`, same precedent.
3. Call `reconfirmRegistration(db, registrationId, actingUser.id, new Date())` (§4).
4. `ctx.answerCallbackQuery()`.
5. Reply per outcome: `"reconfirmed"` → `catalog.reminder24h.reconfirmedReply`;
   `"not-owner"`/`"not-found"` → `catalog.withdraw.refusedNotFound` (same
   non-disclosure discipline `withdraw.ts`'s confirm handler already follows for the
   analogous case); `"not-eligible"` → `catalog.withdraw.refusedNotEligible` (reused —
   the person is no longer in a state this button can act on, same string
   `/withdraw`'s own confirm handler already uses for the equivalent condition).

### 7.2 Decline handler ("Can't make it") — AC2's second half, promotion reuse

1. Extract `registrationId` from `REMINDER24H_DECLINE_PATTERN`. Resolve `actingUser`,
   same as §7.1 steps 1-2.
2. Call `withdrawRegistration(db, registrationId, actingUser.id, new Date())`
   (`domain/registration.ts`, **unchanged, reused exactly** as the requirement instructs
   — this one call is what makes seat-freeing and REQ-023's auto-promotion fire; no part
   of this handler reimplements withdrawal or promotion logic).
3. `ctx.answerCallbackQuery()`.
4. If `outcome.kind === "withdrawn" && outcome.promotion.kind === "promoted"` → call the
   now-exported `sendPromotionNotification(db, sender, outcome.promotion.registrationId,
   outcome.promotion.promotedUserId, outcome.promotion.qrToken)` (§1.4) — **identical
   call**, same function, `withdraw.ts`'s own confirm handler already makes in the same
   circumstance.
5. Reply per outcome: `"withdrawn"` → `catalog.withdraw.confirmedReply` (reused, §6);
   `"not-owner"`/`"not-found"` → `catalog.withdraw.refusedNotFound`; `"checked-in"` →
   `catalog.withdraw.refusedCheckedIn`; `"not-eligible"` → `catalog.withdraw.refusedNotEligible`
   — every branch identical in shape to `withdraw.ts`'s own confirm handler's switch
   (§4.2 step 4), because it is the same domain outcome type (`WithdrawOutcome`).

No `reminder24h:cancel` pattern exists — unlike `/withdraw`'s two-step
confirm-then-confirm flow, the reminder message itself **is** the confirmation UI (PRD
FR-7 specifies exactly two buttons); tapping either button acts immediately.

## 8. `index.ts` wiring (AC1, AC3, AC5-AC10 — end-to-end assembly)

**A real sequencing fix, stated precisely, not left to BACKEND-DEV to discover:** the QR
image (`renderCheckInQrPng`, §5.2 step 5) needs `botUsername`. `handlers/my.ts` reads it
from `ctx.me.username` (populated per-update by grammY once the bot has started) — a
scheduled job has no `ctx`. Today's `index.ts` calls `startScheduledJobs([])`
**immediately after `new Bot(...)`**, before `bot.start()` — and `runner.ts`'s own
"immediate first run" rule (REQ-025 §7) means a job's `run` can fire **before** grammY
has ever fetched the bot's own identity. This is fine today only because REQ-025 passes
an **empty** job list. REQ-026 ships real jobs, so this ordering must change:

1. `index.ts` calls `await bot.init()` **before** `startScheduledJobs(...)` — this is the
   grammY call that populates `bot.botInfo` (the same information `ctx.me` is a
   per-update shorthand for), and it resolves quickly (one `getMe` API call), unlike
   `bot.start()` itself which does not resolve during normal long-polling operation.
2. `const botUsername = bot.botInfo.username;` is read once, after that `await`, and
   passed into `makeReminder3hJob(db, notificationSender, botUsername, 300000)`.
3. `startScheduledJobs([ makeReminder24hJob(db, notificationSender, 300000),
   makeReminder3hJob(db, notificationSender, botUsername, 300000) ])` replaces REQ-025's
   `startScheduledJobs([])`.
4. `bot.start()` remains the file's last call, unchanged in position (it is a
   fire-and-forget long-polling loop, same as today).
5. Two new registrations alongside `/withdraw`'s existing ones:
   ```
   bot.callbackQuery(REMINDER24H_CONFIRM_PATTERN, makeReminder24hConfirmCallbackHandler(db));
   bot.callbackQuery(REMINDER24H_DECLINE_PATTERN, makeReminder24hDeclineCallbackHandler(db, notificationSender));
   ```

No other existing `index.ts` line changes.

## 9. Open questions (not silently resolved)

1. **Ledger key reuse across a withdraw-then-re-register cycle on the same registration
   row.** REQ-022's `registerForEvent` reuses (UPDATEs) a withdrawn row's existing id
   rather than inserting a fresh one. If a person is admitted, gets a `reminder_24h`
   ledger row written, withdraws, then re-registers and is re-admitted to the **same**
   registration id before the event, `notification_ledger`'s `UNIQUE(registration_id,
   kind)` constraint means they will **never** receive a second `reminder_24h` (or
   `reminder_3h`) for that id — the ledger cannot distinguish two separate admission
   "episodes" on the same row. No acceptance criterion in scope exercises this sequence,
   and REQ-025's own §8 open question 2 already names a structurally identical
   limitation (no reconciliation/retry-after-ledger-commit mechanism exists). Left as a
   known limitation, not solved here — a future requirement should decide whether the
   ledger key needs an episode/generation discriminator.
2. **`sendPhoto`'s pacing bucket vs. `send`'s.** §1.3 states they share one rolling
   window; this matches Telegram's own per-bot (not per-method) rate limit, but no
   acceptance criterion in scope constructs a mixed burst of text-and-photo sends to
   verify the shared window specifically — stated here so TEST-DESIGNER knows the
   sharing is a design decision, not an oversight, in case it needs its own case.
3. **A failed T-3h `sendPhoto` after the ledger row committed** falls under the exact
   same accepted-risk analysis REQ-025 §3.2 already states for `send` — under-sending,
   never over-sending, never retried automatically. Not a new question, restated here so
   it is visibly considered for the photo path too, not assumed to only cover text.
