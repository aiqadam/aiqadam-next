# Design — REQ-008: Repoint Dockerfile/compose/CI at apps/web

**Type:** infra/config change. No React components, props, tokens, or UI surface are
involved — this doc replaces the component-structure/props/tokens sections with the
file-by-file change mapping WF-02 Step 1 calls for on a non-UI requirement.

## 0. Verified current state (read from the live files, not from the requirement text)

### Dockerfile (repo root)

Already rewritten by out-of-process commit `2c58702` ("feat: move site into apps/web
monorepo layout [WF02-REQ-007] (#37)") — this landed as part of the REQ-007 PR, not as a
separate uncommitted change, and **was not run through this pipeline's design/review
gates**. Current content, read directly:

```
FROM node:22.14.0-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
COPY apps/web/package.json ./apps/web/package.json
RUN npm ci
COPY . .
RUN npm run build

FROM node:22.14.0-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production
ENV PORT=3000
COPY --from=builder /app/apps/web/public ./apps/web/public
COPY --from=builder /app/apps/web/.next ./apps/web/.next
COPY --from=builder /app/apps/web/package.json ./apps/web/package.json
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/package.json ./package.json
EXPOSE 3000
USER node
CMD ["npm", "start"]
```

Findings from independently re-deriving this against the workspace layout (not trusting
that the prior commit got it right just because it exists):

- Root `package.json` declares `"workspaces": ["apps/*"]` and delegates every script
  (`build`/`start`/`lint`/`dev`) to `npm run <script> -w apps/web`. There is exactly one
  lockfile, `package-lock.json`, at repo root — confirmed no `apps/web/package-lock.json`
  exists. So `npm ci` at repo root, given `package.json` + `package-lock.json` +
  `apps/web/package.json`, is sufficient input for npm to resolve and install the
  workspace's dependencies. **Matches AC1's install-input requirement.**
- `apps/web/package.json`'s `build`/`start` scripts are plain `next build` / `next start`
  — no custom port flag, no `output: "standalone"` in `apps/web/next.config.ts` (verified:
  the config only wraps `next-intl`'s plugin, no other options set). So the runtime image
  needs the **full** `node_modules` tree (prod + dev deps, since `npm ci` with no
  `--omit=dev` flag installs both) available at `/app/node_modules`, not a pruned
  `standalone` output — which is exactly what the current runtime stage does
  (`COPY --from=builder /app/node_modules ./node_modules`).
- npm workspaces materializes the workspace as a symlink at `node_modules/app` (package
  name in `apps/web/package.json` is `"app"`) pointing at `apps/web` — confirmed present
  locally (`node_modules/app -> apps/web`). On Linux, npm creates this as a **relative**
  symlink (`../apps/web`), not absolute. Because the runtime stage recreates the same
  relative layout under the same `/app` WORKDIR (`./apps/web/public`, `./apps/web/.next`,
  `./apps/web/package.json`, `./node_modules`), the copied symlink's relative target
  still resolves correctly inside the runtime image. This is a structural inference from
  how `COPY --from` preserves symlinks and how npm workspace symlinks are relative on
  Linux — it has **not** been exercised by an actual `docker build && docker run`, which
  is exactly what Step 2/FRONTEND-DEV's job is (per this requirement's instruction not to
  run docker commands at design time).
- `PORT` handling (the specific question this design step was asked to resolve): read
  `node_modules/next/dist/bin/next` directly. The `start` command's port option is
  declared as:
  `new Option('-p, --port <port>', ...).argParser(parseValidPositiveInteger).default(3000).env('PORT')`
  — i.e. commander's `.env('PORT')` binding means that when no `-p`/`--port` flag is
  passed, the option's value is read from `process.env.PORT`, falling back to `3000` only
  if `PORT` is also unset. Root `npm start` → `npm run start -w apps/web` → `next start`
  passes no `-p` flag anywhere in this chain. **Confirmed from source, not inferred:**
  `next start` with no CLI port flag honors `PORT` from the environment. This satisfies
  the mechanism AC2 needs (`docker run -e PORT=3120 ... aiqadam-next:req008` should bind
  3120) — the actual bind must still be confirmed by running the container (Step 2), but
  the code path exists and works as required.
- Dockerfile's own `ENV PORT=3000` / `EXPOSE 3000` are just defaults/documentation; both
  `docker run -e PORT=3120` (AC2) and the compose files' `environment: PORT: "3120"`
  override this at runtime. No functional issue, and not a mismatch worth changing —
  `EXPOSE` is advisory only and doesn't restrict the actual bound port.
- `/health` route lives at `apps/web/src/app/health/route.ts` (confirmed via glob) and is
  matched by the `proxy.ts` middleware's negative-lookahead matcher
  (`/((?!api|_next|health|.*\\..*).*)`), so it is excluded from the `next-intl` locale
  routing and reachable at the bare `/health` path the compose healthchecks and AC2 both
  hit. No Dockerfile change is needed for this — the route is part of the Next.js build
  output already copied via `apps/web/.next`.

**Conclusion on the Dockerfile: no diff is required.** The out-of-process commit already
performed the exact restructuring REQ-008 asks for (workspace-aware `npm ci` inputs,
`apps/web/`-scoped COPY of build output/public assets in the runtime stage, unchanged
`PORT`-driven `CMD ["npm", "start"]`). This design doc's job is to make that verification
explicit and attach it to REQ-008's gates, since the commit itself never went through
Step 1/1b/2b.

## 2. Acceptance criteria → verification mapping

1. **`docker build -t aiqadam-next:req008 .` exits 0.**
   Verification: Step 2 runs the exact command from repo root and quotes the real exit
   code and tail of build output. Design-level basis: `npm ci` at root resolves via the
   three COPYed manifests (§0); `npm run build` delegates to `next build -w apps/web`
   which needs nothing outside what `COPY . .` supplies.

2. **`docker run --rm -e PORT=3120 -p 3120:3120 aiqadam-next:req008` serves 200 at
   `/health` and renders `/ru`, `/uz`, `/en`, `/kk` with matching `<html lang>`.**
   Verification: Step 2 runs the container and curls all five paths, quoting real HTTP
   status and response bodies/headers. Design-level basis: `next start`'s `-p/--port`
   commander option is bound with `.env('PORT')` (confirmed by reading
   `node_modules/next/dist/bin/next` — see §0), so no `-p` flag anywhere in the
   `npm start` → `npm run start -w apps/web` → `next start` chain means `PORT=3120` from
   the environment is what gets bound. `/health` is a route under `apps/web/src/app/`
   excluded from locale routing by `proxy.ts`'s matcher and present in the copied
   `.next` build output. The four locale routes are handled by the existing `next-intl`
   routing (`apps/web/src/app/[locale]/...`, unaffected by this requirement — REQ-008
   touches no application code).

3. **`docker compose -p aiqadam-next-qa -f deploy/docker-compose.qa.yml config` parses
   and resolves `build.context: ..` + `dockerfile: Dockerfile` to the repo-root
   Dockerfile.**
   Verification: Step 2 runs the literal command and quotes the resolved `context`/
   `dockerfile` fields in the YAML `config` output. Design-level basis: `context: ..`
   from `deploy/` is repo root regardless of what moved under it; `deploy/` itself did
   not move in REQ-007.

4. **`deploy/deploy.sh` is unchanged (`git diff --stat` shows no modification).**
   Verification: Step 2 (and REVIEWER/RELEASE-VALIDATOR independently) run
   `git diff --stat master...HEAD -- deploy/deploy.sh` and confirm empty output. Since
   this design calls for zero edits to any file including this one, satisfying this AC
   is automatic as long as no step touches the file — call out explicitly in the Step 2
   handoff that this file must not appear in `artifacts_out`.

## 3. Open questions

- **Whether the `node_modules/app` workspace symlink actually survives `COPY --from=
  builder` and resolves inside the runtime stage as reasoned in §0** is inferred from how
  Docker's `COPY` preserves symlinks and how npm creates relative workspace symlinks on
  Linux — it is not something this design step can confirm without running `docker
  build`/`docker run`, which this step is explicitly barred from doing. **This is the one
  load-bearing assumption AC1/AC2 depend on that Step 2 must treat as a first-class thing
  to check**, not just run the build and declare success if it doesn't happen to crash on
  a code path that never touches `node_modules/app` — e.g. actually confirm the
  `next-intl` locale middleware and any other workspace-internal import resolve, not just
  that the HTTP server starts.
- **`docs/guides/deploy_guide.md` and `docs/guides/frontend_developer_guide.md` still
  reference pre-monorepo paths** (`src/app/health/route.ts`, `[src/app/health/route.ts]`
  instead of `apps/web/src/app/health/route.ts`, and the guide's `src/` tree diagram).
  This is stale documentation left over from REQ-007, not something REQ-008's acceptance
  criteria ask this run to fix, and this design step does not resolve it — flagging it
  per `core-directives.md`'s "No Issue Left Local-Only" for ORCH to route to DOC-UPDATER
  or file as its own issue, rather than silently folding a docs fix into this requirement's
  scope.
- **Whether commit `2c58702`'s unreviewed Dockerfile change should be treated as
  retroactively satisfying REQ-008, or whether REQ-008 should still produce its own
  commit** (even a no-op/verification-only one) so the requirement has its own audit
  trail through the pipeline's gates: this is a process question for ORCH/GIT_MERGE, not
  a design question — noting it here since it affects how Step 2/Step Final should be
  structured (Step 2's job becomes "verify and report," with no `artifacts_out` diff to
  `Dockerfile` itself, which is an unusual but valid shape for this workflow).
